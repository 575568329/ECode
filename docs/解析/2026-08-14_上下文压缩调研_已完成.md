# 上下文压缩调研报告

> 2026-08-14，为 M5 压缩算法设计做网上调研。聚焦「编码 Agent 的上下文压缩最新实践」，不凭记忆。
> 核心问题：多级压缩（工具内容 / 对话）+ context 与 history 分离（压缩不破坏对话历史）。

---

## 一、Claude 官方 Context Engineering 三原语（最权威）

来源：[Claude Platform Cookbook — Context Engineering: Memory, Compaction, and Tool Clearing](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)

Anthropic 把上下文管理抽象为三个正交原语，针对不同痛点分层组合：

### 1. Tool-Result Clearing（工具输出清理）— 对应「闲时压缩工具内容」
- **思想**：tool_use（调用记录）保留，但庞大的 tool_result（返回内容）用占位符替代。模型知道「我执行过这个操作」，需要具体数据时重新调用工具。
- **适用**：可低成本重新获取的数据（本地文件读、无害 API 查询）。bash 输出 30KB、read_file 大文件是典型大户。
- **API 参数**（`clear_tool_uses_20250919`，服务端原生）：
  - `trigger`：触发清理的 token 阈值（如 30000）
  - `keep`：保留最近 N 次工具调用的完整结果（如最近 4 次）
  - `clear_at_least`：每次至少释放的 token 数（**避免高频微量清理打断 prompt cache**——缓存雪崩）
  - `exclude_tools`：排除特定工具（如记忆工具，防刚写入的索引被清）
- **效果**：100 轮网页搜索评估中，token 消耗降 **84%**，保留对话核心。

### 2. Compaction（对话压缩）— 对应「主动压缩对话内容」
- **思想**：对窗口内**所有内容**（user 指令、assistant 思考、工具调用与结果）做高保真摘要，用浓缩总结替代历史细节。
- **适用**：无法重新获取的隐性上下文（推理过程、已做决定）的最后防线。
- **触发**：服务端达 token 阈值自动触发，生成 summary block，下一轮丢弃该 block 之前的所有历史。
- **Prompt 策略**（关键）：默认保留「状态、下一步、学习成果」；**编码 Agent 必须显式覆盖**——「Focus on preserving code snippets, variable names, and technical decisions」。要保留特定细节（报错栈、重试次数）必须在 prompt 里明说。

### 3. Memory（持久记忆系统）
- **思想**：结构化外部记事本，模型自己决定何时存取，跨会话持久。
- **实现**：客户端文件系统（API 只给协议）。System Prompt 强制「ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE」。
- **双轨**（claude-code 实战）：用户定义记忆（CLAUDE.md，硬编码规范）+ 模型自动记忆（调试中总结的坑/偏好）。

### 三原语的关系：分层组合，非互斥
```
Tool Clearing（低阈值 ~30K）→ 先解决体量最大的工具输出
Compaction（高阈值 ~150K）→ 再压缩推理记录
Memory（跨会话）→ 稳定信息外置于对话窗口
```

## 二、claude-code 的阈值演进（实战教训）

来源：[Hyperdev — How Claude Code Got Better by Protecting More Context](https://hyperdev.matsuoka.com/p/how-claude-code-got-better-by-protecting)

| | 旧策略 | 新策略 |
|---|---|---|
| 触发阈值 | 90-95%（常因空间不足失败）| **64-75%**（200k 窗口 150k 触发）|
| 缓冲 | 极限压榨 | 留 25%（约 50k）空闲 |
| 哲学 | 最大化利用率 | **land the plane before resetting**（让当前任务先优雅完成再压缩）|

**核心洞察**：「free context space」不是浪费，是模型思考 + 完成当前任务的跑道。提早停止（留缓冲）反而**维持一致质量**，比极限压榨更可靠。

**对 ECode 的启示**：buffer 不能只 13000（v3 的值），应按 contextWindow 比例留（如 25%）。GLM 128k → 触发阈值约 96k，留 32k 缓冲。

## 四、对 ECode M5 的核心启示

### 启示 1：Context 与 History 必须分离（用户核心要求 ✓）
- **Claude 的做法**：Message List 是完整记录，靠「就地编辑」（clear/compact）动态管理——没有分离的 history。
- **ECode 应做得更稳**（用户要求）：**history 文件完整 append-only 永不压缩**（对话历史是用户数据，要保存好）；**只压缩 runtime context**（喂 LLM 的 messages）。
- **模型**：
  ```
  History（~/.ecode/sessions/*.jsonl）   Context（runtime messages[]）
  完整对话记录，append-only，永不压缩  →  派生 →  喂 provider.run，可压缩
  /history 恢复拿完整历史              ←  续写  ←  压缩只改 context，不动 history 文件
  ```
- **压缩产物不落 history**（v3 的 boundary 方案废弃）：压缩是 runtime 优化，history 始终完整。/history restore 恢复完整历史到 context（重置压缩态——可接受，恢复是新会话）。

### 启示 2：多级压缩（用户说的「很多层」）
ECode M5 做两级（对应 Claude 三原语的前两个，Memory 由 history 承担）：
- **Level 1 Tool Clearing**（闲时 / 低阈值）：tool_result 占位符化，保留 tool_use。低阈值触发（context ~50%）。
- **Level 2 Compaction**（主动 / 高阈值）：summarize 旧消息。高阈值触发（context ~75%）。

### 启示 3：阈值留缓冲（land the plane）
- 不极限压榨。按 contextWindow 比例留缓冲（25%）。
- GLM 128k：Compaction 触发 ~96k，留 32k 缓冲。
- Tool Clearing 更早（~64k，工具输出是大户）。

### 启示 4：摘要 Prompt 策略
- 编码 Agent 必须**显式覆盖**默认摘要 prompt。
- ECode 摘要 prompt：「保留代码片段、变量名、文件路径、技术决策、未完成事项；省略寒暄和重复」。

### 启示 5：clear_at_least 避免缓存雪崩
- 清理要「划算」（一次清够多），避免高频微量清理打断 prompt cache。ECode 暂无 prompt cache（GLM 端点），但概念预留。

## 五、ECode M5 压缩架构方向（基于调研修正）

```
┌─────────────────────────────────────────────────────────┐
│ History（永不压缩）                                       │
│ ~/.ecode/sessions/<id>.jsonl — append-only 完整对话记录   │
│ /history 恢复 / 审计 / 导出 — 用户数据，保存好            │
└─────────────────────────────────────────────────────────┘
                         │ 派生（restore / 新对话）
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Context（runtime messages[]，可压缩，喂 provider.run）    │
│                                                          │
│  每轮 provider.run 前 TokenCounter 判定：                │
│   ├─ > 50% contextWindow → Level 1 Tool Clearing         │
│   │   （tool_result 占位符化，保留 tool_use + 最近 N 次） │
│   ├─ > 75% contextWindow → Level 2 Compaction            │
│   │   （summarize 旧消息 → [summary, ...tail]）          │
│   └─ 400 context-too-long → 兜底 Compaction              │
│                                                          │
│  手动：/compact → Level 2                                │
└─────────────────────────────────────────────────────────┘
```

**与 v3 的关键差异**：
1. ~~history boundary~~ → **history 不动**（完整保存，压缩只影响 context）
2. ~~单级 compaction~~ → **两级**（Tool Clearing + Compaction）
3. ~~buffer 13000 固定~~ → **按 contextWindow 比例**（25% 缓冲）
4. 摘要 prompt 显式保留代码/路径/决策
