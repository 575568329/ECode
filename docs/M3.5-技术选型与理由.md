## 二、关键决策详解

### 2.1 UI 范式:Ink + React(官方 npm Ink,不 fork)

**选择**:用官方 `ink`(npm Ink 6)+ React 19,对标 CCode。**不走** Claude Code 的自研 Ink fork。

**为什么选 Ink + React**:
1. **同 TS 栈、Node 原生**:Ink 是纯 JS reconciler + Yoga 布局,无 native 依赖,Node 22 直接跑。ECode 现有 `tsx` 开发链不动。
2. **CCode 现成参照**:CCode 就是 TS + Node 20 + npm Ink 6 + React 19(`D:\Study\CCode\cCli`),输入组件、流式渲染、权限弹窗都有源码可参照——ECode 不用从零摸索。
3. **生态成熟**:Ink 是"React for terminal"的事实标准,`<Static>` / `useInput` / `useApp` 等 API 稳定。

**OpenTUI 为什么出局**(关键事实,推翻早期"Node 换 koffi 即可"的误判):
> OpenTUI 核心**不是纯 TS 库**,而是「**Zig 写的 native 引擎 + TS 绑定**」。
> ——出处:[OpenTUI 官方文档](https://opentui.com/docs/getting-started/):"a native terminal UI core **written in Zig** with TypeScript bindings"

- 要用 OpenTUI 的渲染器(`createCliRenderer()`)就必须走 **FFI**。
- **Node 下用 FFI = Node 26+ 的 `--experimental-ffi`**(实验特性、非 LTS)。ECode 现状是 Node 22(`project.md`),走不通。
- 纯 `import @opentui/core` 不需 FFI,但"**不创建 native renderer**"=用不了全屏 TUI 的核心价值。
- **结论**:OpenTUI 这条路(opencode 路线)和 **Bun 绑定**——opencode 选 Bun 不是偏好,是 OpenTUI 的 Zig native 架构逼的。ECode 不用 Bun → OpenTUI 出局。
- **🔬 spike 实测(2026-08-04,坐实出局)**:`@opentui/core` 虽有 Node 后端(`loadBackend()` 尝试 `require('node:ffi')`),但 ECode Node v22.22.2 **实测无 `node:ffi` 内置模块**(`ERR_UNKNOWN_BUILTIN_MODULE`)、也无 `--experimental-ffi` flag → 落入 `createUnsupportedBackend`,跑不起来。注:`@opentui/core` 有 `index.node.js`/`index.bun.js` 双入口 + `bun-ffi-structs`(跨运行时 FFI struct),设计上意图支持 Node,但 Node 22 缺 `node:ffi` 是硬阻塞。**出局依据从"推断"升级为"实测"**——未来 Node 26+ 若内置 `node:ffi`,可重估。OpenTUI 归属 anomalyco(`github.com/anomalyco/opentui`),非 SST;opencode(SST)只是使用者。

**Ink 的已知风险(已知,有兜底)**:
| 风险 | 说明 | 兜底 |
|------|------|------|
| `ink-multiline-input` 不成熟 | CCode 用 0.1.0 版,体验打折 | M3.5 输入选 **L2 单行**,绕开 multiline;L3 多行再自研 |
| Ink 默认实现可能需补丁 | gemini-cli / qwen-code 都 fork 了 ink(`@jrichman/ink`) | 先用官方,**必要时局部打补丁**(CCode 路),不整体 fork |
| 流式渲染抖动 | React VDOM diff 重绘已完成内容 | 用 `<Static>` 固化已完成消息(见 §2.3) |

**关联**:调研文档 §3.2(CCode)、§4.1(范式收敛)、§5.3(D1 对比表)。

### 2.2 两段式推进结构(降低决断风险的钥匙)

**选择**:M3.5 切两段,**阶段 ①(UI 无关)→ 阶段 ②(Ink REPL)**。

```
阶段 ① —— agent core 事件化(UI 无关,必须先做)
  · runAgent: Promise<void> → AsyncGenerator<AgentEvent>
  · Provider stream() 占位 → 真实流式实现
  · AbortController 中断(保 tool_use/tool_result 配对)
  · slash 命令分发(纯逻辑)
  · CLAUDE.md 读取注入(纯 system prompt 层)
  · 权限判定逻辑(tool registry 加 dangerous 标记 + permission_request 事件 + deny 回喂 isError tool_result)
  → 交付:现有 one-shot `ecode "任务"` 立刻享受逐字流式 + 工具执行前 dangerous 拦截

阶段 ② —— Ink REPL 外壳(UI 范式相关)
  · App(<Static> 固化 + 流式区 + 输入)
  · 输入框 L2 / Markdown 渲染 / 工具面板 / PermissionDialog 弹窗
  · session 级 yes-always(内存)+ allow 白名单(.ecode/settings.local.json)+ 工作区信任
  → 交付:沉浸式 REPL + 完整权限交互
```

**为什么两段式(核心论证)**:
- **D1 选错也能改**:阶段 ① 的 agent core 事件化是 UI 无关的。哪怕 Ink 这条路后续要换(比如补丁太重、想转 readline),阶段 ② 的 UI 层可替换,**阶段 ① 一行不动**。
- **阶段 ① 独立交付价值**:做完,现有 one-shot CLI 立刻从"等整段输出"变成"逐字流式",不等 Ink 也能用。
- **契合已有架构**:M3 已在 `providers/types.ts` 占位 `stream()` 签名和 `ECodeStreamPart` 类型(见 [M3-实施方案](./M3-实施方案.md) §3.5),阶段 ① 是把这个占位填实。

**代价**:两段式要求 agent core 先重构为事件流,有一定工作量。但这是"把 M3.5 的核心(事件化)和 UI 解耦",收益远大于成本。

**关联**:调研文档 §4.5(AgentLoop↔UI 解耦:事件流是共识)、§5.4(推进结构)。

### 2.3 流式渲染:Provider `stream()` + Ink `<Static>`

**选择**:Provider 层实现真实 `stream()`(SSE → `ECodeStreamPart`),UI 层用 Ink `<Static>` 固化已完成消息。

**为什么不抖(核心机制)**:
- Ink 默认每次 React 重渲染会重新 diff **所有**输出,流式时已打印的内容被反复重绘 → 抖动。
- **`<Static>`**:把"已完成、不再变"的消息放进 `<Static>`,Ink 只渲染一次后**固化**(O(n) → O(1));只有"进行中"的流式区放普通 `<Box>` 动态更新。
- 这是 CCode 验证过的方案(调研文档 §4.2)。

**Provider stream() 实现要点**(阶段 ①):
- openai / claude 各实现:SDK `stream: true` → SSE 解析 → 转 `ECodeStreamPart`(`text_delta` / `tool_call_start` / `tool_call_delta` / `tool_call_end` / `usage` / `stop`)。
- **tool_call 流式难点**:input 是分片 JSON,要按 `id` 累积拼接,`tool_call_end` 时才 `JSON.parse`。

**关联**:`providers/types.ts:83-89`(`ECodeStreamPart` 已定义)、`:99-104`(`stream()` 签名已占位);调研文档 §4.2。

### 2.4 CLAUDE.md 兼容(参考 CCode fallback 策略)

**选择**:ECode 读取项目指令文件注入 system prompt,**兼容 CLAUDE.md**,参考 CCode 的 fallback 策略。

**CCode 的聪明折中(直接借鉴)**:
- **`ECODE.md` 优先 + `CLAUDE.md` fallback**:同层目录先找 ECODE.md,有就不读 CLAUDE.md。
  - 出处:CCode `src/config/instructions-loader.ts:35`(`CANDIDATE_NAMES = ['CCODE.md', 'CLAUDE.md']`)
- **配置主权在自己手里**(`.ecode/`),但用户既有的 CLAUDE.md 内容能直接复用——**不依赖 Claude 生态,又兼容它**。

**ECode 采纳的 4 层路径**(对齐 CCode `instructions-loader.ts:72-116`):

| 层 | 路径 | 说明 |
|----|------|------|
| 全局 | `~/.ecode/ECODE.md` → `~/.claude/CLAUDE.md` | 用户全局指令 |
| 项目根 | `<gitRoot>/ECODE.md` → `<gitRoot>/CLAUDE.md` | 项目级(入库) |
| 配置目录 | `<gitRoot>/.ecode/ECODE.md` → `<gitRoot>/.claude/CLAUDE.md` | 项目配置目录 |
| cwd | `<cwd>/ECODE.md` → `<cwd>/CLAUDE.md`(仅当 cwd ≠ gitRoot) | 当前目录 |

**注入方式**:`<instructions source="..." level="...">` 标签包裹,多文件拼接进 system prompt(对齐 CCode `instructions-loader.ts:150-166`)。

**明确不做(YAGNI,CCode 也没做)**:
- ❌ `@import` 递归(Claude 本尊有,深度 5 + 环检测,`claudemd.ts`;ECode 不需要)
- ❌ `CLAUDE.local.md`(私有项目指令;一期不做)
- ❌ 子目录递归懒加载
- ❌ `.claude/rules/*.md` 条件规则

> ✅ **已定**:要 `ECODE.md` 优先层(对齐 CCode `CCODE.md` 模式)——同层 `ECODE.md` 优先 → `CLAUDE.md` fallback。ECode 品牌主权 + 兼容用户既有 Claude 文件。

**关联**:CCode `instructions-loader.ts`(ccode-perm-reference 报告 §2)。

### 2.5 权限:完整系统(档 A,参考 CCode)—— 合并进 M3.5

**选择**:M3.5 做**完整权限系统(档 A,CCode 式极简)**,参考 CCode 实现。原计划的独立 M3.6 已并入 M3.5。

**档 A 完整清单(参考 CCode)**:

| 机制 | CCode 出处 | ECode 落地 | 属两段式 |
|------|-----------|-----------|:---:|
| dangerous 二元标记 | `tools/core/types.ts:67`(工具自声明) | tool registry 加 `dangerous` 字段 | ① |
| permission_request 事件 | `core/tool-pipeline.ts:92-116`(工具执行前拦截,请求在 :99) | `AgentEvent` 加事件类型,UI 接 resolve 回调 | ① |
| deny 回喂 LLM | `core/tool-pipeline.ts:110-113`(`isError` tool_result) | ECode 已有 error variant,直接复用 | ① |
| 单一 PermissionDialog | `ui/PermissionDialog.tsx:35-39` | Ink 弹窗组件(~150 行) | ② |
| allow 白名单(仅 allow) | `config/permissions.ts:83`(`.ccode/settings.local.json`) | `.ecode/settings.local.json` | ② |
| session 级 yes-always | `ui/useChat.ts:203-214`(内存 Set,不持久化) | React state | ② |
| 工作区信任 | `core/workspace-trust.ts:14-61` | 启动检测 cwd 敏感目录 | ② |
| PreToolUse hook block | `core/tool-pipeline.ts:128-147` | 需先有 hook 系统(后置,M5+) | — |

> 档 A 与两段式天然适配:**判定逻辑**(dangerous 标记 + 规则匹配 + deny 回喂)是 UI 无关的,放阶段 ①;**交互**(弹窗 + yes-always + 白名单读写)依赖 Ink,放阶段 ②。阶段 ① 先把 dangerous 拦截跑通(最简 y/N 也能工作),阶段 ② 再上完整 UI 与白名单。

**为什么档 A 合并进 M3.5,不再独立 M3.6**:
1. **档 A 本就轻**:CCode 实践证明同栈对标产品 3-4 天落地。M3.5 装得下,无需单独里程碑。
2. **权限 UI 依赖 M3.5 阶段 ② 的 Ink**:与其等 REPL 做完再回头接权限,不如在同一里程碑内一气呵成,边界天然清晰。
3. **产品更完整**:合并后 M3.5 = "能交互 + 能持久化指令 + 能控制权限"的**完整可用产品级里程碑**,而不是"能交互但没权限"的半成品。
4. **判定/交互解耦**:两段式把权限拆成"阶段 ① 判定 + 阶段 ② 交互",阶段 ① 不依赖 UI,先跑通最简拦截,降低风险。

**为什么选档 A(CCode 式),不选档 B/C**(基于两份调研 agent 对照):
- **档 A(CCode 式极简)**:dangerous 二元 + allow 白名单 + session yes-always + 工作区信任。**3-4 天**。
- **档 B(真兼容最小集)**:读 `.claude/settings.json` + 四档模式 + allow/deny/ask + 持久化。~1-1.5 周。
- **档 C(完整 1:1)**:加 Bash 完整 14 步管线(**2622 行**,`bashPermissions.ts`)。2-3 周+。

| 档 | 兼容 Claude 配置? | 工作量 | Claude 用户规则迁移 |
|----|:---:|---|---|
| **A · CCode 式(选定)** | ❌ 自建 `.ecode/` | 3-4 天 | 权限规则失效(CLAUDE.md 可复用,权限自建体系) |
| B · 真兼容最小集 | ✅ 读 `.claude/` | ~1-1.5 周 | 规则直接生效 |
| C · 完整 1:1 | ✅ 完整 | 2-3 周+ | 完全等同 |

**选档 A 的理由**(用户决断 + 调研支撑):
- **CCode 实践证明极简够用**:同栈对标产品,CCode 砍掉四档模式 / plan / deny / 危险命令识别 / yes-always 持久化,只留 dangerous 二元 + allow,产品照样跑。
- **不追求读 `.claude/settings.json`**:ECode 配置主权在 `.ecode/`(呼应 §2.4 CLAUDE.md 的 fallback 哲学——自建为主、兼容为辅)。Claude 用户迁移过来,ECode 的 CLAUDE.md 能复用(§2.4),但权限规则是 ECode 自己的体系。
- **避免 Bash 2622 行的陷阱**:permissions-spec 调研明确警告(风险 #5)"Bash 完整权限管线会拖垮里程碑"。档 A 用 dangerous 二元标记,绕开整个 Bash 命令解析。

**5 个权限风险警告(permissions-spec 调研,实施时逐一对照)**:
1. **bypass 免疫 safetyCheck**:bypassPermissions 模式下危险命令仍要二次确认(档 A 暂不做四档模式,但 dangerous 二元天然免疫此问题)。
2. **env var 不对称剥离**:不同 provider 对 env var 的剥离方向不一致,序列化 system prompt 时注意。
3. **CLAUDE.md OVERRIDE 语义**:注入时若用 "OVERRIDE" 等强指令词,可能被模型误解为系统级覆盖。用中性 `<instructions>` 标签。
4. **settings.local.json 自动 gitignore**:`.ecode/settings.local.json` 含 allow 规则可能含路径,需自动加入 gitignore。
5. **Bash 工作量陷阱**:档 A 已规避(不用 Bash 2622 行管线)。

**关联**:CCode 全部 file:line 见 ccode-perm-reference 报告;Claude 本尊规格见 permissions-spec 报告。

### 2.6 输入 / 富文本 / 中断 / Windows / 进程(简要)

**输入(D2 = L2)**:单行 + 上下历史 + Tab 补全(slash 命令 / 文件路径)。基于 `ink-text-input` 扩展或自研。**不碰** `ink-multiline-input`(不成熟);L3(Emacs/vim/Ctrl+R)留演进。

**富文本(D3)**:`marked`(markdown 解析)+ `cli-highlight`(代码高亮)。**不用 shiki**(太重,启动慢)。
- **流式坑**:流式期 markdown 不完整语法会渲染错乱。对策:流式期渲染纯文本,**完成时 full markdown render**(避开 token 缓存/不完整语法坑)。

**中断**:`AbortController` + signal(Esc / Ctrl+C)。
- **难点(保配对)**:中断发生在"工具执行后、result 回传前"时,`tool_use` 没配对 `tool_result` → API 400。对策:中断时为已 start 未 result 的 tool_call **合成 `tool_result`(isError:"用户中断")** 再终止。原理详 见 M3.5-方案解析。

**Windows(D7)**:基础 + `stdin.prependListener` 拦原始字节(CCode `stdin` 处理方式,中档方案)。**不上 ffi**(opencode 的 `bun:ffi` 直操 kernel32 方案,Node 下要换 koffi,未验证且过重)。

**进程(D8)**:渐进式——先单进程跑,事件流用判别联合 + 预留 `event ↔ NDJSON` 双向序列化函数。未来切 client-server 分离时(仿 codex 双轨制),server 端 `runAgent` yield 事件 → JSON.stringify 每行 → SSE/pipe 给 client,**零重构**。

## 三、未采纳方案及理由

### 3.1 为什么不用 OpenTUI + SolidJS(opencode 路线)
- **核心是 Zig native**,Node 下用渲染器需 **Node 26.4.0 + `--experimental-ffi`**(实验特性)。ECode 是 Node 22,走不通。
- 这条路和 **Bun 绑定**(opencode 选 Bun 是被 OpenTUI 架构逼的)。ECode 不切 Bun(见 §3.3)。
- 详见 §2.1。

### 3.2 为什么不自研 Ink fork(Claude Code 路线)
- Claude Code 自研 Ink fork + React Compiler + yoga + 自研渲染管线,投入是**顶级规模**(单 REPL 文件 5005 行)。
- ECode 是单人开源产品,学其**设计思想**(事件流、双缓冲防抖、权限交互),**不学实现规模**。用官方 Ink + 必要时局部补丁即可。

### 3.3 为什么不切 Bun 运行时
- M1 已定 Node.js(多端兼容、企业环境兼容、知识迁移性)。详见 [M1-技术选型与理由 §4.1](./M1-技术选型与理由.md)。
