## 支点 1：交互入口模式

### Q1：REPL / 管道 / 无头模式分别是什么意思和效果？

**REPL（Read-Eval-Print Loop，交互模式）**
"人坐在终端前和 agent 对话"。ECode 用 Ink+React 渲染全屏 TUI：欢迎屏、输入框、状态栏、消息流、工具折叠面板。跑完一轮不退出，可继续追问。支持斜杠命令、↑↓ 翻历史、Ctrl+C 中断、Ctrl+O 翻全文、`/resume` 切换历史会话。
- 触发：`ecode`（无参 + 交互终端 TTY）或 `ecode --repl`（强制，即便非 TTY）
- 适合：人在终端前开发

**管道（Pipe）**
Unix 的 **IO 机制**（stdin/stdout 重定向），不是 ECode 的"模式"。把别的程序输出喂给 ECode（输入管道 `echo "x" | ecode`），或把 ECode 输出喂给别的程序（输出管道 `ecode "x" | jq`）。
- ECode 现状：无参+非TTY 直接退出（Ink 要抢占 stdin，没输入源会卡死）；有任务时（`ecode "任务"`）走 one-shot 流式输出，stdout 能被管道消费——但输出是**人类可读逐字流式文本**，程序无法可靠解析

**无头模式（Headless，CC 用 `-p` / `--print`）**
显式的**非交互运行模式**：给 prompt → agent 跑 → 输出结果 → 退出。核心价值是**结构化输出**（`--output-format text|json|stream-json`），让程序能解析。
- `json`：结束后一次性输出完整结果对象（result/sessionId/cost/rounds）
- `stream-json`：逐事件 NDJSON（每行一个 JSON 事件，管道可增量消费）
- 适合：CI、pre-commit hook、脚本化、被别的程序集成

### 三者关系

| 概念 | 本质 | ECode 现状 |
|------|------|-----------|
| REPL | **交互语义**（人对话） | ✅ 完整 |
| 管道 | **IO 机制**（输入/输出重定向） | 🟡 有任务时可输出；无 stdin 输入管道 |
| 无头 | **运行语义**（非交互 + 结构化输出） | ❌ 无 `-p`、无结构化输出、无 stdin 管道输入 |

One-shot（现状）介于中间：非交互，但只输出人类可读文本。三者常配合：`echo "任务" | ecode -p --output-format json | jq '.result'`。

### 现状（已完成 ✅）

`src/repl-mode.ts` 的 `selectEntryMode` 纯函数三分支：

| 模式 | 触发 | 实现 |
|------|------|------|
| REPL | `--repl` / 无参 + TTY | `index.ts → startRepl()` 动态 import Ink+React，`render(<App/>)` 常驻 |
| One-shot | `ecode "task"` | `index.ts → runAgent()` 流式 `console.log` |
| Usage | 无参 + 非 TTY | `printUsage()` 退出（避免 Ink 抢占无输入 stdin） |

续接族（`--continue` / `-c` / `--resume <id>`）与查询族（`--sessions` / `--list-models`）是独立分支，已在 `index.ts` 落地。

### 决策：补无头模式 `ecode -p`（P1）

**要做。** 理由——ECode 定位开源产品，需能被 CI / pre-commit / 脚本调用。当前 one-shot 只输出人类可读流式文本，程序无法解析；无头模式 = one-shot + 结构化输出 + 明确语义标志。

### 架构设计（轻量，复用已有事件流，不碰 agent core）

```
入口判定扩展（src/repl-mode.ts）:
  EntryMode 增加 'headless' 分支
  触发优先级: -p/--print > 有任务+非TTY > (其余不变)
    -p/--print         → headless（最强,显式要机器输出）
    有任务 + 非TTY     → headless（管道场景）
    有任务 + TTY       → oneshot（人类可读流式,现状）

新增 CLI 选项（src/index.ts parseArgs）:
  -p / --print                           显式无头
  --output-format text|json|stream-json   默认 text
  --max-turns N                          迭代轮数上限（CI 安全闸）

数据流（新增 src/headless.ts,纯消费层）:
  runAgentStream(task, { signal, system, resumed })
    → consume AgentEvent 流
    → OutputFormatter(format):
       text:        最终 assistant 文本（等价 one-shot 输出）
       json:        结束后一次性输出 { result, sessionId, cost, rounds }
       stream-json: 逐事件 NDJSON（每行一个 JSON 事件,管道可增量解析）

复用资产（零改动）:
  - runAgentStream / AgentEvent 判别联合（支点 2 产物）
  - 续接 (--continue/--resume) 已有逻辑
  仅新增: selectEntryMode 一分支 + OutputFormatter 一层 + 3 个 CLI 选项
```

**关键约束**：
- 无头模式**不加载 Ink/React**（保持 one-shot 的快启动优势）
- `--max-turns` 默认无限制，CI 可显式设防（防止跑飞烧 token）
- `stream-json` 每行独立 JSON，便于 `jq` / 管道增量消费

**不做（YAGNI）**：不学 CC 的多输出样式（explanatory/learning）——产品包装层，先 text/json/stream-json 三档够用。

### Q2：管道左侧的数据是用户给的吗？

**不是。** 左侧数据 = 左边那个命令**自己跑出来的输出**。`|` 的作用是把左边命令吐出来的东西自动接到右边当输入。用户给的不是数据本身，而是"安排了哪个命令在左边跑"。

```bash
cat 报告.md  | ecode -p "总结"   # 左=cat 读出的文件全文
git diff     | ecode -p "审查"   # 左=git 吐出的代码改动
ls *.ts      | ecode -p "解释"   # 左=ls 列出的文件名
echo "一句话" | ecode -p "翻译"  # 左=echo 打印的字（这种才是用户写的）
```

比喻：`|` 像流水线/接力跑——第一道工序（左边命令）产出什么，原样递给下一道（ECode）。

**对 ECode 的要求**：愿意接住别人递来的数据当输入。现在 ECode 在"没任务+管道里"直接退出（怕 Ink 抢占没输入的 stdin），需改成"检测到管道喂入就读进来用"。

### Q3：管道/无头模式的本质场景是什么？

**"不打开 ecode 对话界面，把步骤用管道拼好，跑完输出就行。"** = 自动化/脚本化。

```bash
cat error.log | ecode -p "分析这个报错" > 结果.txt   # 读日志→分析→存档,全程不碰界面
```

- **REPL** = 坐下来跟它一起干活（交互、追问）
- **管道/无头** = "这事我不想盯着，你跑完把结果给我"（一次性、自动化）

核心价值：让 ECode 从"给人手动开的聊天窗口"变成"能给 shell 脚本调用的命令行工具"——解锁 CI / git hook / 批处理等所有自动化场景。

### 技术实现详解（讨论补强）

> 原则：**复用主干道 `runAgentStream`，只动入口（管道）与出口（无头），核心循环一行不改。** 支点 2「地基稳」的红利——消费层薄到这点代码就够。

#### 现有零件盘点（不用造）

| 零件 | 位置 | 复用方式 |
|------|------|---------|
| `parseArgs`（node:util） | `index.ts:40` | 加 3 个选项即可 |
| `selectEntryMode` 纯函数 | `repl-mode.ts` | 加 `headless` 分支 |
| `runAgentStream` 异步生成器 | `agent.ts:213` | 核心循环，不改 |
| `process.stdin.isTTY`（Node 原生） | — | 检测管道喂入 |

#### 无头模式实现

1. **parseArgs 加 3 选项**：`-p/--print`、`--output-format text|json|stream-json`、`--max-turns N`
2. **selectEntryMode 加 `headless` 分支**：`-p` 或「有任务+非TTY」触发
3. **新建 `headless.ts`**（纯输出消费层，约 30 行）——`for await` 消费 `runAgentStream`，按 format 分三路写 stdout
4. **不加载 Ink/React**（保持 one-shot 快启动优势）

#### 出口三格式（同一事件流，三种倒法）

| 格式 | 比喻 | 输出形态 | 给谁 |
|------|------|---------|------|
| `text` | 人话逐字 | 流式文字 | 人（= 现在 one-shot） |
| `json` | 成绩单 | 跑完一次性 1 个对象 `{result,sessionId,rounds,cost}` | 只要最终结果的脚本 |
| `stream-json` | 直播弹幕 | NDJSON，每事件一行，边跑边吐 | CI / 进度监控 / jq 增量解析 |

实例（任务"总结 a.txt"）：

- json：`{"result":"a.txt 讲的是...","sessionId":"...","rounds":3,"cost":0.05}`
- stream-json：每行一个 `{"type":"text_delta"/"tool_use"/"tool_result"/"completed",...}`

#### 核心机制

- **`for await (const event of runAgentStream(...))`**：异步迭代消费事件流（agent 边干边吐，"传送带来一碟接一碟"）。`runAgent` wrapper（`agent.ts:491`）已是此模式，无头层复用同样消费方式、只换出口动作。
- **`process.stdout.write(x)`**：把 x 送出 stdout 大门（**送出动作，非汇总**）。去向只看命令行怎么接：终端→屏幕、`|`→下游程序、`>`→文件。汇总靠循环里先存变量（如 json 分支的 `result`）。
- **为何用 write 不用 console.log**：write 原样写不加换行，能精确控制 NDJSON「一行一个」与 text 逐字不换行；console.log 的自动换行会破坏格式。

#### 管道输入实现

1. **检测**：`process.stdin.isTTY === false` → 有管道/重定向喂入
2. **读取**：`for await (const chunk of process.stdin)` 收集成字符串
3. **拼接**：用 `<pipe_input>` 标签包起来拼进任务，让模型区分「管道素材」与「用户指令」：

```ts
const task = stdinText
  ? `<pipe_input>\n${stdinText}\n</pipe_input>\n\n${userTask}`
  : userTask;
```

#### 正交两维度（关键认知）

无头 / 管道**不是二选一**，是两个独立维度，可任意组合：

| 维度 | 管什么 | 选项 |
|------|--------|------|
| 无头 vs REPL | 怎么跑（非交互 vs 对话） | `-p` |
| 管道 / 重定向 | 输入输出接哪 | `\|` `<` `>` |

组合例：`cat err.log | ecode -p "分析" | jq '.result' > 答.txt`（管道喂入 + 无头跑 + 管道接走 + 写文件）

#### YAGNI（不做）

- 不学 CC 多输出样式（explanatory/learning）——三档够覆盖自动化场景
- 不改 `runAgentStream` 核心循环
- 无头不加载 Ink/React

## 支点 3：内置工具集

> 本支点只确定**内置基础工具**这一层（不含 MCP / Skill）。跨平台为必检维度，见文档顶部全局约束。

### 现状盘点

ECode 注册了 5 个工具（`src/tools/registry.ts`）：

| 工具 | 干啥 | 实现原料 |
|------|------|---------|
| `read_file` | 读文件 | Node `fs` |
| `bash` | 跑 shell 命令（dangerous） | Node `child_process` |
| `edit_file` | 精确替换 oldText→newText | Node `fs` |
| `grep` | 搜文件内容 | 正则 + 遍历 |
| `glob` | 按名字找文件 | 模式匹配 |

**两个发现**：
- **`write_file` 缺失**：UI 层（`tool-panel.tsx` / `format-transcript.ts` / `permission-dialog.tsx`）已为 write_file 预留折叠规则与权限分组，但核心 `registry.ts` 未注册 → "计划了但漏落地"。
- **`edit_file` 匹配失败兜底已实现**（`src/tools/edit-file.ts`）：0 次匹配回喂真实内容（带行号）/ 多次匹配要求补上下文 / 唯一匹配替换写回。→ **主文档总表原标注「edit 匹配失败恢复闭环（P0）」过时，应划掉。**

### 三层归类边界（内置 / MCP / Skill）

| 层 | 本质 | 归属 |
|----|------|------|
| **内置工具** | agent 随身装备，开箱即用 | 文件 CRUD / 搜索 / 执行 / 任务管理 / 通用 fetch |
| **MCP** | 接外部系统的桥，按需装 | GitHub / Slack / Jira / 数据库 / Git 远程 PR |
| **Skill** | 菜谱（组合工具 + 方法论），**不是工具** | 代码审查 / 部署 / 重构 / 写测试 / commit 规范 |

**判断口诀**：① 是"动作"还是"方法"？→ 方法 = Skill；② 接外部系统吗？→ 是 = MCP；③ 通用必备吗？→ 是 = 内置。

### 跨平台视角（bash 战场）

11 个工具里 **10 个跨平台白嫖，只有 bash 系（bash / delete / move / ls）是真战场**——靠 shell，而 shell 各平台方言不通（Win 的 cmd/PowerShell ≠ Unix 的 bash）。

**三招治跨平台**：
1. **环境上下文注入**（最前置、最省钱）—— 把平台/shell/cwd/版本同步给 LLM，让它写对命令
2. **专用工具**（治本）—— delete/move/ls 用 Node `fs` 实现，**绕开 shell**（跨平台倒逼这三个从"可选专用"升级为"必做专用"）
3. **统一 shell**（治标）—— bash 工具在 Windows 自探测 Git Bash/WSL，让 agent 永远写 bash 语法（呼应 CLAUDE.md §9.3 自探测原则）

> **shell 概念**：shell = 你敲命令、它去执行的"服务员"程序。每平台都有 shell，但**不一定是 bash**——Linux/Mac/WSL 自带 bash；Windows 原生只有 cmd/PowerShell，要装 Git Bash 或开 WSL 才有 bash。

### 环境上下文注入（横切机制，归属待定）

LLM 是"隔墙的盲人"——看不到你电脑环境，不告诉它就靠猜（猜错就写错命令）。通过 system prompt（`buildSystemPrompt()`）注入：

| 状态 | 为什么 |
|------|--------|
| 平台 / shell | 决定命令语法 |
| 工作目录 | 知道在哪个项目 |
| 运行时版本 | API 可用性 |
| 项目特征 | 包管理器 / 框架 / 分支 |
| 当前时间 | 时效判断 |

**跨平台适配（第21项）怎么做**：环境注入是跨平台三招里最前置、最省钱的一招。完整三招——① **环境注入**（本节：告诉 LLM 平台/shell，让它写对命令）；② **专用工具**（delete/move/ls 用 Node `fs` 绕开 shell）；③ **统一 shell**（bash 工具在 Windows 自探测 Git Bash/WSL）。三招即第21项的核心方案，详细见支点21。

**归属待议**：环境注入作为跨平台一招可并入第21项；但它本质是"通用上下文注入"（不只跨平台，还有项目特征/时间等），是否单列支点待定。

### 决策

| 工具 | 动作 | 理由 |
|------|------|------|
| `write_file` | 补 | 基础能力，UI 已预留 |
| `TodoWrite` | 补 | 任务管理（操作内存状态，非外部） |
| `fetch` | 补 | 通用网络（Node 18+ 全局 fetch） |
| `delete_file` / `move` / `ls` | 从 bash 代劳升级为专用工具（Node fs） | 跨平台倒逼 + 安全 + 免审批 |
| `edit_file` 兜底 | 无需动作（已完成） | 仅修正主文档过时标注 |

### 架构设计

- 新增 4 个 fs 专用工具：`write_file` / `delete_file` / `move` / `ls`——均用 Node `fs`（`writeFileSync` / `rm` / `rename` / `readdir`），在 `registry.ts` 声明式加一条即可（无需改 executor switch）
- 新增 `TodoWrite`：维护 agent 内存 `Todo[]` 状态 + UI 渲染（不调 fs/网络）
- 新增 `fetch`：Node 18+ 全局 `fetch()`
- 三层边界：内置只放通用必备；特定系统 → MCP（支点10）；工作流 → Skill（支点13）
- bash 工具跨平台：Windows 自探测 Git Bash/WSL（属第21项）

## 支点 4：上下文管理（token / 压缩 / 截断）

> 控制"喂给 LLM 的对话历史有多大"。LLM 有上下文窗口上限（如 GLM 1M token），对话越长历史越膨胀，超了 API 就报错。上下文管理的活：**检测快满了 → 压缩历史（留近的、摘要旧的）→ 不超**。本支点机制讨论 + 两个待办功能实现细节。

### 现状盘点（L1-L4 四级机制，全部已实现）

核心代码在 `src/context-manager.ts` + `src/agent.ts`，分四级防线：

| 级别 | 干啥 | 函数 | 触发 |
|------|------|------|------|
| **L1 阈值检测** | 监控历史是否逼近窗口上限 | `isOverThreshold`（窗口×0.8） | 每轮迭代前 |
| **L2 主动压缩** | 快满了先压（先白嫖后花钱） | `maybeCompress` | 每轮迭代前 |
| **L3 响应式恢复** | API 真报超限了，抢救 | `forceCompact` | API 报上下文窗口错误时 |
| **L4 熔断** | 抢救 3 次还不行，放弃报错 | `MAX_CONTEXT_RETRIES=3` | L3 重试计数 |

**L2 级联策略（先省后花）**：
1. **`trimToolResultContents`**（零 LLM 成本）—— 把旧的 `tool_result`（工具输出，往往是 token 大头）替换成占位符 `[已清除以节省上下文：旧工具输出...]`，保留 `tool_use_id` 配对。只删工具输出，留对话本身。
2. **`compressMessages`**（花一次 LLM 调用）—— trim 后还超，让 LLM 把旧消息摘要成一条 `[上下文压缩摘要]...`，拼上最近消息。

### 两条铁律（压缩必须遵守，否则崩）

1. **不劈开"工具往返"**：`tool_use`（模型说"调工具 X"）和配对的 `tool_result`（工具返回）必须连在一起，压缩时**不能拆散**。拆散 → API 400（`tool_result.tool_use_id` 找不到配对的 `tool_use.id`）。`splitForCompression` 保证只在往返边界切。
2. **压缩后结构不变**：压完仍是合法 messages（每个 tool_result 有配对 tool_use）。`verifyMessagesPairing` 压完检查一遍。

### 现状结论

- **L1-L4 全部已实现**，机制完整。
- **🔴-1（forceCompact 死代码）已修复**：`agent.ts:312` 实际调用了 `forceCompact`，不再是死代码。→ 主文档总表原标注"接线响应式恢复 🔴-1"、第二部分 🔴-1 条目**均过时，应划掉**。
- 唯一缺口：**参数硬编码 + 无手动入口**（见下两节）。

### 待办功能 1：`/compact` 手动压缩（已注册但未实现）

**现状**：`/compact` 在 `slash-commands.ts` 已注册（输入能识别、能补全），但 `app.tsx:214` 执行时 fall through 到"尚未实现"存根——现在压缩**全是自动的**（L2 每轮 + L3 抢救），用户没有手动入口。

**场景**：你跟 agent 改了 20 个文件（历史很长），第一阶段干完了想开第二阶段。旧历史占着 token，想手动收一下——`/compact` → 旧对话压成摘要 → 显示"已压缩 12K→4K"→ 省下的 token 给新阶段。

**实现思路**：
1. `handleCommand('compact')` 不再 fall through，改为调用 `api.compact()`
2. `useAgentStream` 暴露 `compact()` 方法，复用现成 `forceCompact` / `compressMessages`
3. 压缩结果替换 `completedMessages`，UI 显示压缩前后 token 对比
4. **约束**：只在 idle 态（非 streaming）执行，避免和正在跑的 agent 循环冲突

### 待办功能 2：暴露压缩参数配置（现硬编码）

**现状**：保留条数写死在 `context-manager.ts`，无配置入口（无配置文件、无 CLI、无斜杠命令可调）：

| 参数 | 含义 | 硬编码值 |
|------|------|---------|
| `keepRounds` | 保留最近几个工具往返组 | 6 |
| `keepRecent` | 保留最近几个 tool_result 原文 | 3 |
| `COMPRESS_THRESHOLD_RATIO` | 触发阈值（窗口×N） | 0.8 |

**场景**：默认留 6 个往返，但小项目想只留 3 个更省 token；大项目跨文件改动多，想留 10 个防压缩太激进丢上下文——现在都改不了。

**实现思路**：
1. 配置系统（支点15）加"上下文管理"块：`{ "context": { "compressKeepRounds": 6, "compressKeepRecent": 3 } }`
2. `context-manager.ts` 函数从配置读默认值，去掉硬编码
3. （可选）暴露成斜杠命令即时调，如 `/config context.compressKeepRounds 10`

### 跨平台维度

两个待办功能都是纯 JS/TS 逻辑（压缩 + 配置读写），不涉及 shell / 路径 / 原生二进制 → **跨平台无忧 ✅**。

## 支点 7：权限系统

> agent 执行有副作用操作（改文件 / 跑命令 / 删东西）前的**审批闸门**——根据规则决定"直接放行 / 先问 / 直接拒"。完整设计见 M4 三件套（[`实施方案`](../里程碑/M4-实施方案.md) / [`方案解析`](../里程碑/M4-方案解析.md) / [`技术选型`](../里程碑/M4-技术选型与理由.md)）+ [`三源交叉验证报告`](../里程碑/M4-权限系统三源交叉验证报告.md)（扒透 CC / opencode / CCode，`file:line` 实证）。本支点记讨论确认的决策。

### 核心判断：走 opencode 精简路线，不抄 CC 重工业

| 对比 | CC | opencode | 选谁 |
|------|-----|----------|------|
| bash 权限代码量 | 2621 行（`bashPermissions.ts`） | 精简（arity 字典） | **opencode** |
| 命令解析 | tree-sitter AST（原生二进制依赖） | arity 字典（纯 TS） | **opencode**（tree-sitter 撞 §9.3 Windows 红线） |
| 配置合并 | 5 层 source | 扁平 last wins | **opencode**（直观） |

CCode 太简陋（不分级、无路径保护），CC 太重——**opencode 是 ECode 的甜点**。

### 两层架构：模式（粗旋钮）+ 规则（精细名单）

| 层 | 比喻 | 管什么 |
|----|------|--------|
| **模式** | 门卫严格度（查每个人 / 认识的脸放行 / 开门不查） | 整体宽松度 |
| **规则** | 门卫手里的名单（白名单进 / 黑名单拦 / 灰名单问） | 具体命令 / 路径 |

**规则优先于模式**：名单明确的按名单；名单没提的才看模式。例：bypass 模式下名单写了 `deny: Bash(rm -rf *)` 照样拦。

### 权限流水线（工具执行前 5 步）

```
工具要执行
  ① deny 规则命中？→ 直接拒
  ② ask 规则命中？→ 弹窗问
  ③ allow 规则命中？→ 放行
  ④ 都没命中 → 看模式兜底（bypass 全放行 / acceptEdits 编辑放行 / default 危险才问）
  ⑤ 仍需问 → 弹窗（allow 这次 / allow_always / deny）
```

### 三档模式（砍 plan）

| 模式 | 语义 | 场景 |
|------|------|------|
| `default` | 危险操作才问 | 日常谨慎 |
| `acceptEdits` | edit/write 自动放行，bash 仍按规则 | **日常主力**（批量改文件不烦） |
| `bypass` | 全放行（明确警示） | CI / 自动化 / 调试 |

**砍掉** `plan`（用 deny 规则 `edit:{"*":"deny"}` 模拟更灵活，推 M5+）、`dontAsk`（headless 已能 deny）。切换：Shift+Tab 循环 + CLI `--permission-mode`。

### 规则配置 + 优先级

`.ecode/settings.json`：
```jsonc
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(npm run *)", "Read(./src/**)"],   // 放心
    "deny":  ["Bash(rm -rf *)", "Edit(.env)"],         // 危险
    "ask":   ["Bash(git push *)"]                      // 敏感
  }
}
```

语法两式：`Bash(npm test)` 精确 / `Bash(npm run *)` 通配。

**优先级：last wins**（仿 opencode）——两层配置扁平合并（用户级 `~/.ecode` 在前、项目级 `.ecode` 在后），**项目级覆盖用户级**（最后匹配胜出）。比 CC 的 5 层 + deny 全局优先直观。

### allow_always 默认不写盘

allow_always 只存内存（本次会话有效），**不写 settings.json**。防误点导致危险操作永久放行。要真持久化，用户手写配置文件（明确意图）。仿 opencode。

### 工具默认策略（现状缺口盘点）

| 工具 | 现状 | 该问? | 动作 |
|------|------|-------|------|
| `bash` | ✅ 问 | 该问 | 已纳入 |
| `read_file` / `grep` / `glob` | 不问 | 不该问（读，无副作用） | ✅ 对 |
| `edit_file` | **不问** | **该问！**（改文件） | ❌ **补**（CC/opencode/CCode 都问） |
| `write_file` / `fetch` / `delete` / `move` | 未注册 | 该问 | 注册时配 |
| `TodoWrite` / `ls` | 未注册 | 不该问 | 注册时配 |

**关键缺口**：`edit_file` 改文件却不问——agent 改代码不打招呼。待补工具注册时一并配权限，不能再漏。

### 命令分级：arity 字典（不用 tree-sitter）

bash 不能整个"一刀切问"，要分级（`npm test` 安全、`rm -rf` 危险）。借鉴 opencode **arity 字典**：维护"命令前缀→token 数"字典（git/npm/docker Top30），`git checkout main` → 归约 `git checkout`，allow_always 生成 `git checkout *`。纯 TS 无依赖，跨平台。**不用 tree-sitter**（原生二进制撞 §9.3 红线）。

### 安全网：路径越界 + 敏感文件黑名单（P0 必做）

性价比最高，堵 90% 问题：
- **敏感文件**（抄 CC `filesystem.ts:57-79`）：`.env` / `.env.*` / `.gitconfig` / `.bashrc` / `.git` / `.vscode` 等 → 编辑总问（即使 acceptEdits）
- **路径越界**（仿 opencode）：读写工作目录外 → 问（防 agent 乱翻电脑）

### 审批 UI：保留 3 选项 + 425ms grace period

现状 `permission-dialog.tsx` 三选项（allow / allow_always / deny）够用。**425ms grace period 是 ECode 独有亮点**（三源调研都没定位到独立 grace period），必须保留。升级方向：allow_always 二次确认（防误点）+ reject 反馈框（拒绝时告诉 agent 该干啥）。

### 死循环检测（doom_loop）

仿 opencode：同工具 + 相同输入连续 3 次 → 触发 `doom_loop` 权限 ask，用户选 continue / abort（不硬中断）。

### 待修 bug

🔴-2：`allow`（允许这次）vs `allow_always`（永久）语义崩塌——选"这次"被记成"永久"。

### 跨平台维度

- 命令分级 arity 字典：纯 TS，跨平台无忧 ✅
- 路径越界检测：`path.resolve` + symlink 归一（跨平台）；不做 Windows NTFS 攻击防护（YAGNI）
- 不用 tree-sitter：避开原生二进制撞 §9.3 红线 ✅
- 敏感文件黑名单：文件名匹配，跨平台无忧 ✅

### 决策总表

| 项 | 决策 |
|----|------|
| 路线 | opencode 精简（非 CC 重工业） |
| 模式 | 三档（砍 plan / dontAsk） |
| 命令解析 | arity 字典（非 tree-sitter） |
| 规则引擎 | 扁平 last wins（项目覆盖用户） |
| allow_always | 默认不写盘 |
| 安全网 | 路径越界 + 敏感文件（P0） |

## 支点 8：记忆系统

> 解决 LLM"金鱼记忆"——把记忆写文件，每次调用注入 system prompt，LLM 永远记得。本支点含 **memory 三层自动加载** + **自动生成 skill**（经验沉淀闭环，跨支点13）。

### 记忆的本质

LLM 每次调用都是全新的，不记得上次。解决：把记忆写进文件，每次调用都塞进 system prompt——它就"每次都看到"了。

### 现状

| CLAUDE.md → system prompt 注入 | ✅ `loadInstructions()` + `buildSystemPrompt()`（`instructions-loader.ts` 35 行，读 home+cwd 两层 CLAUDE.md/ECODE.md） |
| `docs/memory/` 分类记忆 | 🟡 **纯约定无代码**（grep src/ 零命中，靠 AI 自觉 read） |

核心机制（CLAUDE.md 注入）已实现，主文档 ✅ 准确。**缺口**：memory 不自动加载 + 无经验沉淀闭环。

### 待办 1：memory 自动加载（三层架构）

加载时读三层，合并注入 system prompt（跟 `loadInstructions(dirs)` 多目录读 CLAUDE.md 同模式）：

| 层 | 位置 | git | 放什么 |

memory 读写 = 纯 TS 文件 IO，无 shell/原生二进制 → 跨平台无忧 ✅。唯一注意：user 目录定位走 `resolveDataDir`（见上）。

## 支点 9：子代理 Subagent

> 主代理干不过来的活，派"分身"独立跑，分身带回结论，主代理综合后回用户。**本支点先定"要做"，细节后续讨论。**

### 本质：指挥官 + 侦察兵

- **主代理 = 指挥官**：综合情报、做决策、组织最终回复给用户
- **子代理 = 侦察兵**：独立跑（独立上下文 / 人设 / 工具），只回**结论**
- 主代理拿到结论后还要自己加工组织 → 所以子代理**不能回完整过程**（否则主代理退化成"传话筒" + 污染主上下文，与场景1初衷矛盾）

### 三个真实场景

1. **保住主上下文**（最常用）：派去读/分析大量文件，只回摘要
2. **并行加速**：多个分身并行处理多个模块，主代理汇总
3. **专项人设**：`.ecode/agents/*.md` 定义专家分身（如 test-writer）

### CC 机制（借鉴）

`Task` 工具（入参 description + prompt）→ 派子代理 → 独立 messages + 系统提示词 + 工具集 → 回最终文本。子代理中间过程主代理一概看不到。

### ECode 复用红利（关键）

子代理 = **递归调一次 `runAgentStream`**（换系统提示词 + 工具子集 + 空 messages）—— 不造新循环，地基直接复用（跟支点1 无头模式复用同一循环同理）。

### 权限边界（安全红线，必须现在定）

子代理也是 agent，会调 read/write/bash。**风险：权限代持绕过审批**——你给主代理 default 模式（改文件要审批），主代理想偷偷改 → 派子代理"帮我改"。若子代理权限 ≥ 主代理，审批形同虚设。

**红线：子代理权限 ⊆ 主代理权限**（只能更严，不能更宽）。
- 默认：继承主代理当前模式（default/acceptEdits/bypass）+ 全部权限规则
- 可被 `.ecode/agents/*.md` 的 `tools:` 字段**收紧**（限定工具子集，如 Explore 只读）
- 子代理调工具仍走权限流水线（deny→ask→allow→mode）；ask 弹窗归主对话（不让子代理自己弹）

### 记忆处理（必须现在定边界）

- **读**：默认读项目 CLAUDE.md + memory（子代理需要项目背景，如"用 npm 不用 pnpm"），复用 `loadInstructions`。专项人设可覆盖（独立系统提示词 → 不读 CLAUDE.md）
- **写 / 沉淀**：子代理**不独立沉淀记忆**，跑完即弃。结论回到主代理，由主代理决定记不记
- **会话**：子代理**不独立存 session**（是主对话的一次工具调用，不是独立会话）

### 决策（本次拍板）

| 项 | 决策 |
|----|------|
| 要不要 | ✅ **要做**（先定下功能，细节后续讨论） |
| 优先级 | 保持 **P2（M5+）** |
| 结果回收 | **只回最终结论**（侦察兵模式）。主代理拿结论后自己组织最终回复，**不回完整过程** |
| 实时可观测 | **后续增强**：先做基础子代理（派出去→跑完→回结论，黑盒），再加"子代理跑时能查看他在干啥"（实时进度，关联支点17） |
| **权限边界** | **子代理 ⊆ 主代理**（只能更严不能更宽，防权限代持）；默认继承模式+规则，可被人设 `tools:` 收紧；ask 弹窗归主对话 |
| **记忆** | 默认读项目 CLAUDE.md + memory（可被人设覆盖）；**不独立沉淀记忆 / 不存 session**，跑完即弃，结论回主代理 |
| 人设 `.ecode/agents/` | 待定，后续细节讨论 |

## 支点 10：MCP 扩展（Model Context Protocol）

> 给 agent 装"第三方 App"的应用商店协议。别人写好的工具服务器，接上就能用，不用自造。本支点先定形态，**砍掉的部分标注"待查证"不锁死**，后续查资料再确认。

### 本质：App Store 协议

- 内置工具（read/write/bash）= 手机自带应用
- MCP server = App Store 第三方 App（GitHub/Slack/数据库…）
- agent = 手机，装上就能干更多事

### 为什么 ECode 要 MCP

**生态红利**：CC 生态已有大量现成 MCP server，接上协议白嫖全部，不用自造垂直工具。MCP 是事实标准（CC/Cursor/Windsurf 都支持），不接就脱离生态。

### 机制（接上后怎么工作）

1. 配置登记一个 MCP server
2. agent 启动时连上（本地 stdio / 远程 Streamable HTTP）
3. server 告诉 agent "我有这些工具"
4. 工具**透明加入**工具列表，跟 read/write 并列
5. LLM 需要时**自动调用**（跟内置工具一样，**不用 / 命令触发**）

### 配置归属：MCP 独立注册（不进 config，防替换误删）

**MCP 安装态独立注册表（`~/.ecode/mcp/`），不进 config.json** —— VS Code 扩展模式（扩展独立装，不混 settings）。

**为什么**：MCP 若进 config，用户替换 config.json（换项目 / 拷贝覆盖）会**不知情地连坐删除 MCP**（用户本意不是删 MCP）。独立注册后，替换 config 不动 MCP。

**生命周期**：
- 安装 MCP → 写注册表 + 把它的 hook 绑定注册到系统 hooks
- 替换 config → 不动注册表 → MCP 还在
- **显式卸载 MCP → 才删注册表 + 解绑 hooks**（解绑唯一触发是显式卸载，不是替换 config）

**与 config 的关系**：config.json 不放 MCP 安装态；可放项目级「启用哪些 MCP」开关（只改启用集，不删 MCP）。

> ⏳ 详细设计（注册表格式、启用开关、与 config 边界、MCP 绑定 hook 的注册/解绑机制）待 MCP 里程碑讨论。关联支点15 配置系统（「配置 vs 安装注册」分层——MCP/skill/plugin 这类安装态都该独立注册）。

### 触发/管理矩阵（关键设计——自动 vs 手动）

| 能力 | 怎么触发 | /命令 | 归属 |
|------|---------|:---:|------|
| 内置工具（read/write/bash） | LLM 自动 | ❌ | 支点3 |
| **MCP Tools** | **LLM 自动** | ❌ 不用 | 支点10 |
| **Skill** | 用户手动选 | ✅ 执行 | 支点13 |
| **MCP 状态查看** | 用户手动 `/mcp` | ✅ **只读** | 支点10+14+17 |

**逻辑**：MCP Tools 跟内置工具一样自动调；手动触发的预设工作流全归 Skill（支点13）；MCP 的 / 命令是"查看状态"不是"执行"。

### 三个原语（取舍）

| 原语 | 触发 | 决策 | 理由 |
|------|------|------|------|
| **Tools** | 自动 | ✅ **做** | 核心，LLM 自动调 |
| Prompts | 手动 | ❌ **砍（待查证）** | 跟 Skill 功能重复；待查证后定 |
| Resources | 只读 | ⏸ 后置（待查证） | Tools 暂能替代；待查证 |

### 传输（分阶段，已查证纠正）

- **阶段1：stdio**（本地起步）——个人 CLI 合理：简单、隐私、凭证不出机器
- **阶段2：Streamable HTTP + OAuth**（远程）——**跟上趋势，不是"砍掉"**

> **查证纠正（2026-08）**：旧 HTTP+SSE 已废弃（spec 2025-11-25），远程标准现为 **Streamable HTTP**（spec 2026-03-26 起）。趋势朝远程/hosted 走（stdio 爆 RCE 漏洞 CSA Labs 2026-04 + 企业推远程）。个人 CLI 阶段1 stdio 起步，阶段2 必补远程。
> 来源：[MCP 官方博客-传输未来](https://blog.modelcontextprotocol.io/posts/2025-12-19-mcp-transport-future/) · [SSE vs Streamable HTTP](https://brightdata.com/blog/ai/sse-vs-streamable-http) · [stdio RCE 漏洞（CSA）](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-rce-design-vulnerability-20260423-csa/)

### 安全红线

**MCP server 是第三方不可信代码**：
- ✅ MCP 工具必须纳入权限系统（走审批，呼应支点7）
- ✅ 装哪个 server 要用户**显式登记**（配置手动加，不自动跑）
- ✅ 防 stdio RCE（CSA Labs 2026-04 设计漏洞）——当不可信代码，最小权限

### `/mcp` 管理命令（只读可观测，呼应支点17）

显示：server 清单（名字 + 本地/远程）+ 连接状态（✅ connected / ❌ failed / 🔄 connecting）+ 暴露工具清单 +（可选）版本/最近调用。

### 跨平台注意

MCP server 是 spawn 出来的**真子进程**，但**不是** §9.4 的 fire-and-forget，是**持续双向通信**（JSON-RPC over stdio）。启动命令跨平台可能不同（npx / node 直接跑），配置要支持平台无关启动。

### 决策（本次拍板）

| 项 | 决策 |
|----|------|
| 做不做 | ✅ **做** |
| 优先级 | 保持 **P2（M5+）** |
| 传输 | 阶段1 stdio → 阶段2 Streamable HTTP |
| 原语 | 做 **Tools**；砍 **Prompts**（待查证）；**Resources** 后置（待查证） |
| 触发 | Tools 自动调（不用 / 命令）；手动触发归 Skill |
| 管理 | `/mcp` 只读查看 server + 状态 + 工具 |
| 安全 | 不可信代码 + 权限系统 + 显式登记 + 防 stdio RCE |

### 关联支点

- **支点7 权限**：MCP 工具纳入审批
- **支点13 Skill**：手动触发的归这（砍 MCP Prompts 的依据）
- **支点14 斜杠命令**：`/mcp`
- **支点17 可观测性**：`/mcp` 状态查看

## 支点 12：Hooks 系统（事件钩子）

> 在 agent 生命周期的关键事件点上挂自定义脚本，agent 走到那自动跑（Git hooks 的 agent 版）。调研 CC 官方机制 + ECode 源码挂点后定方案。

### 三个核心 hook 是什么（比喻）

| Hook | 比喻 | 时机 | 能干啥 | 不能干啥 |
|------|------|------|--------|---------|
| PreToolUse | 🚪 门卫 | 工具执行**前** | 拦截(deny)/改输入/提醒 | — |
| PostToolUse | 📋 监工 | 工具执行**后** | 改输出/记账/通知 | 撤回已执行的 |
| Stop | ✅ 验收员 | agent 要停 | 打回继续干/反馈 | — |

### hook vs 权限规则边界

| | 权限规则（支点7） | Hooks（本支点） |
|---|---|---|
| 形态 | 静态黑白名单 | 动态脚本 |
| 适合 | 简单模式（禁 `rm -rf`） | 复杂判断（调 git / 跑测试 / 副作用） |
| 硬度 | 硬底线（deny 不可翻盘） | 只能收紧不能放宽 |

执行顺序：`PreToolUse hook → 权限规则 → 工具执行 → PostToolUse hook`。权限 deny 是硬边界，hook 不能覆盖。

### 配置分层（系统 hooks 防覆盖机制——核心）

**系统 hooks 写代码里，不进配置文件，用户改不了。**

| 层 | 位置 | 可改 |
|----|------|------|
| 系统内置 | **代码注册（hardcoded registry）** | ❌ 不可改 |
| 用户级 | `~/.ecode/` config 的 hooks 块 | 用户 |
| 项目级 | `.ecode/` config（git 跟踪） | 团队 |
| 项目本地 | `.ecode/` config（gitignore） | 个人 |

- **系统 hooks 强制叠加**：永远执行，用户 config **无法删除/覆盖**，只能追加自己的
- 例：ECode 内置 PreToolUse 拦 `rm -rf /`、保护 `.env`（用户关不掉）
- 呼应权限系统：权限 `deny` = 声明式硬底线，系统 hooks = 动态硬底线
- **系统级/用户级解耦（普遍原则）**：系统级一切（hooks + 其依赖）都在代码里，**跟 config.json 零依赖**——用户删/替换 config 碰不到系统功能。系统 hooks 自包含，不调 MCP、不读 config
- **MCP 绑定的 hook 随 MCP 生灭**：MCP 安装时注册其 hook 到系统 hooks，卸载时解绑（解绑唯一触发是显式卸载，非替换 config）。详见支点10「MCP 独立注册」
- **用户级降级兜底**：用户 hooks/MCP 若因 config 变动缺失 → 执行时依赖检查 + 优雅降级（跳过+警告，不崩），呼应 §9

### CC 事件全集（~15 个，分类）

- **会话**：SessionStart / SessionEnd
- **对话回合**：UserPromptSubmit / Stop / StopFailure
- **工具**：PreToolUse / PostToolUse / PostToolUseFailure
- **权限/通知**：PermissionRequest / Notification
- **子代理/配置/文件**：SubagentStart/Stop / ConfigChange / FileChanged / UserPromptExpansion

### ECode 先做 6 个核心事件

`SessionStart / SessionEnd / UserPromptSubmit / PreToolUse / PostToolUse / Stop`。其他（Subagent/ConfigChange/FileChanged 等）记录，看情况加。

### ECode 落地（源码已定位挂点）

工具调用全在 `src/agent.ts` 单文件：

| Hook | 挂点 | 范式 |
|------|------|------|
| PreToolUse | `agent.ts:374`（权限检查前） | 仿 `permissionGate` 加 `hooks.preToolUse` 注入回调 |
| PostToolUse | `agent.ts:429`（executeTool 后、结果回传前） | 同上 |
| Stop | 4 处 `completed` yield（359/461/482/500） | 抽 `emitCompleted()` 收口 |

**关键判定**：Pre/Post **不能用事件流**（单向通知承载不了"等决策"），必须 Promise-await 注入回调（`permissionGate` 已是 PreToolUse 雏形）。Stop 可复用事件流。

### 跨平台坑

hook 是 shell 命令，Windows 跑啥 shell？跟 bash 工具共用 shell 分流（呼应支点21 / §9.3）。

### 决策（本次拍板）

| 项 | 决策 |
|----|------|
| 优先级 | **P2（M5+）** |
| 先做事件 | **6 核心**（SessionStart/End + UserPromptSubmit + Pre/PostToolUse + Stop） |
| 其他事件 | 记录，看情况加 |
| 系统 hooks | **代码注册，强制叠加，用户不可覆盖** |
| 用户 hooks | 进 config.json 的 hooks 块（分层：用户/项目/项目本地） |
| 实现 | 仿 `permissionGate` 注入回调，挂 `agent.ts:374/429/emitCompleted` |
| handler 类型 | 先做 command（shell），http/prompt/agent 后置 |

### 关联支点

- **支点7 权限**：hook vs 规则边界，系统 hooks = 动态硬底线
- **支点9 子代理**：SubagentStart/Stop 事件

## 支点 13：技能 Skills（可复用工作流）

> 可复用的「工作流菜谱」——把成功经验沉淀成 skill，下次照菜谱干。**枢纽支点**：收拢支点8（自动生成）/ 支点10（砍 MCP Prompts 归这）/ 支点12（自动归纳依赖 hooks）的 skill 相关决策。

### 一句话 + 场景

把一次性摸索出来的成功流程写成 skill，下次照菜谱干，不重新摸索。场景：部署流程、代码审查 checklist、调试某类 bug 的步骤、提 PR 的标准动作——写一次反复用。

### 完整设计

| 维度 | 设计 |
|------|------|
| 两种来源 | ① **手写**（用户/团队写 SKILL.md）② **自动生成**（agent 总结经验沉淀） |
| 格式 | `SKILL.md` + YAML frontmatter（`name`/`description`/`disable-model-invocation`），一目录一 skill。抄 OpenClaw，对齐 agentskills.io 社区规范 |
| 注入（技术核心） | **懒加载**：启动只把 name+description 拼进 system prompt（catalog），触发后才读正文 → 防 prompt 爆炸 |
| 触发 | ① 手动 `/skill xxx` ② 自动：LLM 匹配 description 自动用。**两个都做** |
| 自动生成质量命门 | **proposal 审批队列**：agent 生成的 skill 不直接落盘 → 进提案库 → 安全扫描 → 用户 `/accept` 才转正 |
| 归纳方式 | **用 LLM 归纳**（从 transcript 抽可复用工作流），非正则（OpenClaw 正则识别率低） |

### 懒加载注入（为什么是核心）

```
启动：system prompt 只放 skill 目录（name + description 一行一个）← 便宜
   ↓
LLM 看任务 → 匹配某 skill 的 description → 决定用
   ↓
触发：才把那个 skill 正文读出来注入 ← 按需，不爆 prompt
```

跟 ECode 现在 CLAUDE.md **全量注入**不同——skill 是**按需注入**，skill 多了也不撑爆上下文。

### 自动生成 = 经验沉淀闭环（支点8「越用越好用」）

```
干完任务（摸索着干）→ LLM 总结"这次怎么干"→ 写成 SKILL.md 提案
                                              ↓ 进审批队列
                          用户 /accept → 入库 → 下次类似任务复用
```

**依赖支点12 hooks**：每任务后触发总结（Stop hook）→ 这就是 hooks 是 P2、skill 是 P3（13 依赖 12）。

### 跟前面支点的关系（收拢）

- **支点8**：自动生成 skill = 经验沉淀闭环（主体归这）
- **支点10**：砍 MCP Prompts，手动触发预设工作流全归 Skill
- **支点12**：自动归纳依赖 hooks 审批链

### 跨平台维度

skill 是纯 TS 文件 IO + frontmatter 解析，无 shell/原生二进制 → 跨平台无忧 ✅。

### 决策（本次拍板）

| 项 | 决策 |
|----|------|
| 优先级 | **P3（M5+）** |
| 分阶段 | 阶段1 **手写**（SKILL.md + 懒加载 + /skill 手动+自动匹配）先行；阶段2 **自动生成**（LLM 归纳 + proposal 审批队列）后置（依赖 hooks） |
| 格式 | SKILL.md + frontmatter，抄 OpenClaw 对齐 agentskills.io |
| 注入 | 懒加载（catalog + 触发读正文） |
| 触发 | 手动 + 自动都做 |
| 审批队列 | 自动生成的 skill 必经 `/accept` 审批才入库（质量命门，**必做**） |
| 归纳 | 用 LLM 非正则 |
| 依赖 | 支点12 hooks（自动归纳的触发） |

## 支点 23：多渠道对话接入（Web UI / IM 微信飞书）

> 把 ECode 的对话能力从终端扩展到**浏览器 + IM 聊天软件**。agent loop 不变，起网络服务把对话暴露给外部渠道。远期，参考 OpenClaw 多渠道但单机简化。

### 本质：agent 后端与对话前端分离

终端 REPL 只是"对话前端"之一。后端/前端分离后，前端可以是：

- 终端（现在）
- **Web 浏览器**（WebChat——浏览器里跟 agent 对话）
- **IM**（微信/飞书/钉钉/Telegram——在聊天软件里 @agent 对话）

### 跟 MCP 的区别（关键，别混）

| | 方向 | 干啥 |
|---|------|------|
| MCP（支点10） | agent → 外部 | agent 调外部工具 |
| **多渠道接入（本支点）** | 外部 → agent | 外部渠道连 agent 对话 |

方向相反。MCP 加的是"工具"，本支点加的是"对话渠道"。

### 两种接入形态

**① Web UI（浏览器对话）**
- ECode 起本地 HTTP+WS 服务（localhost:端口）
- 浏览器加载前端 → WS 双向通信 → 复用 `runAgentStream`
- = 终端 REPL 搬到浏览器

**② IM 接入（微信/飞书/钉钉等）**
- agent 接 IM 平台 bot API，在聊天里 @agent 对话
- 每个平台一个适配器（adapter）
- **现实约束**：微信个人号无官方 bot API（企业微信/飞书/钉钉有）→ 各平台可行性待调研

### 架构（参考 OpenClaw Gateway，单机简化）

```
浏览器 / 微信 / 飞书  ──各自适配器──▶  ECode 对话服务（HTTP+WS + 会话路由）
                                          │
                                          ▼
                                     runAgentStream（不改）
```

OpenClaw 调研（`docs/调研/20260806085241_OpenClaw参考研究.md`）已预见此需求，归"远期 TUI/后端分离"：WS 帧三件套协议可参考，但 Gateway/跨设备/pairing 外围对单机过度设计。

### 决策（本次拍板）

| 项 | 决策 |
|----|------|
| 做不做 | ✅ **记为新支点（远期）** |
| 优先级 | **P3 远期**（核心 REPL M3.5 还在打磨，先不分散；IM 各平台 API/合规工作量大） |
| 归属 | **单列支点23**，不塞支点1（本地进程入口 vs 网络服务型接入，性质不同） |
| 架构 | 后端/前端分离 + 渠道适配器，复用 `runAgentStream` |
| IM 可行性 | 待调研（微信无个人 bot API 是硬约束） |

## 支点 16：UI / UX —— 用户插话机制

> 本支点记 UI/UX 里最复杂的一项：**用户插话**。完整方案见 [`用户插话机制方案.md`](用户插话机制方案.md)（已扒透 CC 源码，`文件:行号` 级证据）。基础流式渲染 / 工具折叠 / pager 已完成，此处只记插话。

### 什么是用户插话

agent 正在跑（streaming + 工具调用循环）时，用户能继续打字、发出去、参与进当前对话——而不是干等它跑完。

### 现状：运行中输入框彻底禁用（行业最保守一档）

`app.tsx:277` `disabled={api.isRunning}` → InputBar 在 agent 跑时锁死，打不了字，只能 Esc/Ctrl+C 中断。CC 相反——运行中不禁用输入，还把插话做成核心交互（tip 系统明确鼓励 *"Hit Enter to queue up additional messages while Claude is working"*）。

### 两种插话语义 + 选型

| 语义 | 行为 | 选型 |
|------|------|------|
| **排队式**（mid-turn drain） | 话排队，等当前工具跑完、下轮问 LLM 前塞进去，LLM 同轮可见 | ✅ **选定**（对齐 CC 键盘默认 `'next'`） |
| **打断式**（interrupt） | 立即掐断当前任务 | ❌ 不推荐（风险高，CC 都没做默认） |

**场景**：agent 正连串改代码（读文件 → grep → edit...），你想到"先看 README" → 打字 + Enter → 排队 → agent 跑完当前 edit → 下轮问 LLM 前插进去 → LLM 下一轮就去读 README。没打断、没无视、自然衔接。

### 核心设计（4 处改动，agent core 极小侵入）

```
InputBar        去掉 disabled，输入框常驻；running hint 移到下方
app.tsx         handleSubmit 判断 isRunning：普通文本 → enqueue（入队），不再 submit
useAgentStream  + queuedInputRef 队列 + enqueue() + drainQueued 回调
agent.ts        for 循环末尾（toolCalls 跑完、agent.ts:415 后）加 drain：
                  const queued = opts.drainQueued?.() ?? []
                  → push 进 messages + yield 'user_message_injected' 事件
```

**drain 点（心脏）**：`agent.ts:415` toolCalls for 循环右括号后、重复检测前。这是 tool_result 已配对闭环、stream 未启的**安全窗口**——只 append 一条 user message，不破坏 tool_use_id 配对。

### 改动量

~80 行产品代码 + ~50 行测试，6 文件（input-bar / app / use-agent-stream / agent / agent-events / types+reducer）。

### 关键约束（防崩）

1. **drain 前查 `signal.aborted`**：abort 窗口期不注入（竞态保护）
2. **drain 后 `lastSignature = ''`**：用户插话 = 新意图，重复检测基线清零（否则下轮同工具被误判死循环）
3. **slash 命令不进队列**：App 层拦截照旧（对齐 CC，slash 是元操作不进 LLM）
4. **队列真相源在 UI 层**（`useAgentStream.queuedInputRef`），agent core 只暴露 `drainQueued` 回调单次取走——保持 agent 无状态 generator 特性

### 跨平台维度

纯 TS 键盘交互 + 数组队列，不涉及 shell / 路径 / 原生二进制 → **跨平台无忧 ✅**。

### 决策

| 项 | 动作 |
|------|------|
| 输入框常驻 | 去掉 `disabled={isRunning}` |
| 插话语义 | 排队式（mid-turn drain），对齐 CC `'next'` |
| 打断式 | YAGNI，不做（除非未来有 sleep 类可中断工具） |
| 优先级 now/next/later | YAGNI，不引入（键盘只有一种语义） |
| 实施时机 | 归支点16（UI/UX 可选增强），P1 |

详见：[`用户插话机制方案.md`](用户插话机制方案.md)

### 研究结论：CC 命令的三类两模型（扩展性真相）

研究 CC 源码 + 文档，命令分三类、**两套执行模型**：

| 类型 | 来源 | 怎么执行 |
|---|---|---|
| 内置 | 代码 | **代码 handler 直接跑**，不经过 LLM（`/clear` `/cost`） |
| 自定义 | `~/.claude/commands/*.md` 或 `.claude/commands/*.md` | **`.md` 内容当提示词注入对话**，LLM 跑 |
| MCP | MCP server 的 **Prompts** 能力 | 同自定义，注入对话 LLM 跑，命令名 `/mcp__server__prompt` |

**杀手锏**：用户放一个 `.md` 文件就加一个命令，**零代码**。frontmatter 控制 `description`/`argument-hint`/`allowed-tools`；`$ARGUMENTS` 传参；`@file` 引文件、`!cmd` 跑 bash 把输出塞进提示词。

### 扩展性 = 两层

**第一层：内置命令自包含化**（代码组织）
- `SlashCommandDef` 自带 `handler(ctx)`，加内置命令一处搞定、不动 `app.tsx`
- `CommandContext` 打包依赖（api / openResume / cwd / model），handler 纯函数可测
- 支撑外部 push（未来插件/MCP 也能注册代码命令）

```ts
interface SlashCommandDef {
  name: string;
  description: string;
  handler: (ctx: CommandContext) => void | Promise<void>;
}
// app.tsx 统一分发，无 switch：
const cmd = registry.find(c => c.name === name);
await cmd?.handler(ctx);
```

**第二层：自定义命令 `.md` 注入**（真正的「快速接入」）
- 用户放 `.ecode/commands/xxx.md` → 自动成 `/xxx`
- 执行 = `.md` 内容注入对话交给 LLM
- 零代码——CC 扩展哲学的精华

### 三类统一注册，执行分流

```
注册表 = 内置(handler) + 自定义(.md) + MCP(prompts)
   ↓
补全 picker 自动覆盖三类（picker 已有，数据源换合并表）
   ↓
执行分流：内置 → handler(ctx) 跑代码（不进 LLM）
         自定义/MCP → 内容注入对话（进 LLM）
```

### 自定义命令第一版做全（本次拍板）

| 能力 | 做法 |
|---|---|
| frontmatter | `description` + `argument-hint`（最小集） |

### 三层 `.md` 作用域（本次拍板）

| 作用域 | 位置 | 说明 |

| 用户级 | `~/.ecode/commands/`（走 `resolveDataDir`） | 个人跨项目复用 |

## 支点 24：多模态输入（图片上传与解析）

> 定位：用户把图片喂给 ECode → 编码成多模态 message → 送 vision 模型。**ECode 自己不解析**（解析是 LLM 的能力）。本轮深扒了 CC（`D:\Study\claude-code-main`）和 OpenCode（`D:\Study\opencode`）源码，机制级结论如下。

### 架构红利：content 已为多模态预留（好消息）

源码确认 `ECodeMessage.content` **已经是 `string | ECodeContentBlock[]` 联合类型**（`providers/types.ts:30`）。加图片是**给联合加一个 `image` 分支**，不是把 string 推翻重做。

三个穷尽式 switch（`transform.ts` / `token-counter.ts` / `context-manager.ts` 的 `default: never`）会**编译器强制报错提醒补 case**——加 image variant 后不会漏。

### 协议两派（transform 各写一套）

| 派 | 格式 | ECode 适用 |
|---|---|---|
| Anthropic 原生 | `{type:'image', source:{type:'base64', data, media_type}}` | claude provider |
| OpenAI 兼容 | `{type:'image_url', image_url:{url:'data:image/...;base64,...'}}` | **GLM/DeepSeek（ECode 默认主力）** |

ECode 内部统一 base64，发送按端点转。

### 核心机制（源码实证，推翻"Windows 做不到"误判）

> **终端不传图片。按键（Ctrl+V / Alt+V）只是信号，触发后 `spawn` 系统剪贴板命令去问 OS 要图片二进制，完全绕开终端字节流。**

CC 和 OpenCode 都是这个机制。所以"Windows Terminal 不支持粘贴图片"对终端没错，但产品**绕开终端**——这就是 Windows 下也能粘图的真实原因。

### 平台分流（抄 CC/OpenCode，WSL 方案抄 OpenCode）

| 平台 | 命令 | 来源 |
|---|---|---|
| macOS | `osascript`（AppleScript 写临时 PNG → 读文件） | CC/OpenCode 一致 |
| **Windows + WSL** | `powershell.exe` + `.NET System.Windows.Forms.Clipboard.GetImage()` + PNG MemoryStream → base64 | OpenCode：**WSL 也走 Windows powershell.exe**（`release().includes("WSL")` 分流）——呼应 §9.3，CC 没做这个桥（缺陷） |
| Linux X11 | `xclip -selection clipboard -t image/png -o` | 一致 |
| Linux Wayland | `wl-paste -t image/png` | 一致 |

### 输入方式（本次拍板）

| 方式 | 定位 | 机制 |
|---|---|---|
| **粘贴** | **主力** | Ctrl+V（mac/linux）/ Alt+V（windows）→ spawn 系统命令 → base64 → image block |
| `@文件路径` | 备用 | 复用 @file 解析器分流（图片→image block） |
| `read-image` 工具 | LLM 主动 | agent loop 里自己调（现有 read-file.ts 强制 utf-8，读图乱码，需新工具） |

**为什么 Windows 用 Alt+V**：Ctrl+V 被 Windows 终端抢占当系统文本粘贴（发非空文本），应用收不到按键做图片协调，所以 Windows 专门用 Alt+V 绕开（CC `defaultBindings.ts:12` 实证）。

### Ctrl+V 的特殊处理（优先级低，第一版简化）

源码看，CC/OpenCode 的 Ctrl+V 是**统一粘贴协调器**，要处理 5 种情况：文本粘贴 / 图片粘贴 / 拖拽文件路径 / 空粘贴检测图 / 长粘贴分片重组（CC `usePasteHandler.ts`、OpenCode `prompt/index.tsx:370-390`）。

**第一版简化（本次拍板）**：Ctrl+V / Alt+V 都当**纯图片触发器**（spawn 读剪贴板，有图就注入），完整的统一协调器（5 种情况）作为后续增强，**优先级低**。要的是「能粘图」核心体验，不是粘贴的复杂分流。

### 占位符两段式（抄 CC/OpenCode）

输入框插 `[Image #1]` 纯文本占位（可编辑/可回放历史），submit 时替换成真实 image block。

### 图片预处理

- sharp 压到 **5MB / 长边 1568px**（CC 实证）
- **WSL2 BMP 坑**：WSL2 默认给 BMP，检测魔数 `0x42 0x4d` 转 PNG（CC `imagePaste.ts:209`）

### 三个硬障碍（动手前必须解决）

### 成本统计算法（研究重点）

#### 核心问题：cache token 不归一化，成本必错

不同 provider 的 cache 字段**语义相反**——有的是"互斥分项"，有的是"子集"。同一句话（1000 token，950 命中缓存）在三家算法不同：

| provider | usage 返回 | 语义 | 正确算法 |
|---|---|---|---|
| Anthropic | `input_tokens=50`, `cache_read=950`, `cache_creation=0` | 互斥分项 | `50×input价 + 950×read价`（直接加） |
| OpenAI 标准 | `prompt_tokens=1000`, `cached_tokens=950` | 子集 | `(1000-950)×input价 + 950×cache价`（**必须减**） |
| **DeepSeek** | `prompt_cache_hit=950`, `prompt_cache_miss=50`（**顶层**字段） | **互斥分项** | 直接加（字段名不同，语义同 Anthropic） |
| **GLM**（智谱） | `prompt_tokens=1000`, `prompt_tokens_details.cached_tokens=950`（**嵌套**） | **子集** | **必须减**（OpenAI 风格） |

**ECode 现状全错**：`transform.ts:86,189` / `openai.ts:54` 只取一个总量、cache 字段全丢；`claude.ts:79` Anthropic 流式 inputTokens 写死 0。

> **大坑**：DeepSeek 和 GLM 都是"OpenAI 兼容端点"，但 cache 字段**路径 + 语义都不同**（DeepSeek 顶层互斥，GLM 嵌套子集）。**不能假设兼容端点字段一致**。

#### 归一化模型（transform 出口统一）

不管 provider 怎么报，transform 出口一律吐**互斥五项**（Anthropic 风格作目标，天然分项最干净）：

```ts
interface ECodeUsage {
  input;       // 非缓存输入       → 计费 ×input价，     Ctx% 含
  cacheRead;   // 缓存命中          → 计费 ×cacheRead价，  Ctx% 含
  cacheWrite;  // 缓存写入          → 计费 ×cacheWrite价， Ctx% 含
  output;      // 生成(含reasoning) → 计费 ×output价，    Ctx% 不含
  reasoning;   // 思考(⊂output)     → 只展示，不计费，    Ctx% 不含
}
```

**reasoning 是展示项不是计费项**：DeepSeek/GLM 的 `reasoning_tokens` 是 `completion_tokens` 的子集（沿用 OpenAI 规范），按 completion 单价计费不额外收费。若再 `reasoning×out价` 会把思考 token 算两遍（双计）。→ 成本公式只算前四项。

归一化用**字段探测**（不靠 config 标注，呼应 §1.1 自探测优先；opencode 多路径兜底思路）：

```
if (usage.prompt_cache_hit_tokens != null)        → DeepSeek（互斥，直接透传）
else if (usage.prompt_tokens_details?.cached_tokens != null) → OpenAI/GLM（子集，减法）
// Anthropic 在 claude.ts 单独处理（原生分项）
```

#### 两个核心公式

**成本**（四项 × 绝对单价，per M tok）：

```
cost = (input×P.input + cacheRead×P.cacheRead + cacheWrite×P.cacheWrite + output×P.output) / 1_000_000
```

**Ctx%**（CC 口径，纯 input 侧三项和）：

```
ctx% = (input + cacheRead + cacheWrite) / contextWindow × 100
```

不加 output/reasoning——它们是本轮生成，下轮才进窗口。Ctx% 回答"下次发多少进窗口"，纯 input 侧最干净。

#### 累积语义（两个层面，都有坑）

- **单轮流式**：usage 累积式——`message_start` 给 input/cache 三项，`message_delta` 可能再发 0。**必须 `>0` 守卫防覆盖**（CC `updateUsage` 坑）；output 取 `message_delta` 最终值。
- **跨轮累积**：四项各自 `+=` 给 `/cost`；但 **Ctx% 用 per-call 三项和覆写**（每轮最新值），不能用累积值——这是 🔴-3 修法扩展到三项。

#### 单价表（绝对值，cache 一等字段）

`ModelConfig` 扩 `cost: { input, output, cacheRead, cacheWrite }`（per M tok 绝对值，**非倍率**——不同家倍率差很多：Anthropic read≈0.1×input，GLM 国内 5 折/海外约 1.83 折，DeepSeek hit 约 2%~0.83%）。

- 内置 GLM/DeepSeek 默认价起步（不联网），config 可覆盖
- **未知模型 fallback** + `hasUnknownModelCost` 标记，`/cost` 显示"⚠️ 单价未知，成本仅估算"（抄 CC `modelCost.ts:89`）
- **必须配置驱动**：DeepSeek 官方告警即将峰谷定价+整体调价，GLM 国内/海外折扣不同——硬编码必过期
- 抽成独立 `cost-tracker.ts`（现状硬编码在 `status-bar.tsx:27`，所有模型通用 deepseek 价 → 换模型就错）

### 持久化策略（本次拍板）

## 支点 18：后台任务（长运行 shell 不阻塞 agent loop）

> 跑测试 / dev server / 长构建是高频刚需，但 ECode 现 bash 是 `execSync` 同步阻塞——长命令卡死整个 agent loop。本支点做"后台任务"：命令后台跑、agent 不阻塞、完成主动通知。**P1**。

### 本质：后台任务 vs 子代理（别混）

正交两维度——**被调度的是什么**（shell 命令没脑子 vs agent 循环有脑子）× **怎么调度**（前台阻塞 vs 后台不阻塞+通知）。支点18 专指 **shell 命令的后台化**；子代理的后台运行归支点9。两者共享调度底座（task id + 输出流 + 完成通知），但支点18 不套 agent（opencode 把 background 强绑子 agent 是教训——dev server 不需 LLM 推理却被迫多包一层 agent，浪费 token）。

### 三方实现对比（源码实证）

| 维度 | **CC**（最简洁，源码实证） | **opencode**（双轨） | **openclaw**（工业级，太重） |
|---|---|---|---|
| 触发 | `run_in_background` + 超时自动后台 + 用户手动 promote（三路径） | 仅子 agent 场景（实验开关） | 任务化（cron/CLI task） |
| 输出缓冲 | **纯落盘**，内存零保留 | 内存窗口(~100KB) + spill 文件(50KB) | 进程 Map + SQLite 双写 |
| 查询 | TaskOutput：tail 读 + offset 增量 | 同 | push 投递 |
| kill | TaskStop（别名 KillShell） | cancel scope | AbortController + 60s grace |
| 完成通知 | `markTaskNotified`（主动注入） | **合成 message 注入**（`<task_result>`） | heartbeat wake |
| 状态机 | running/done | Deferred+token（race-free） | 含 **`lost`** + sweeper |
| 崩溃恢复 | 跟 session（路径含 sessionId） | **无**（注释明说临时方案） | 双写持久化 + 重启恢复 |

**CC 输出缓冲精华**（`diskOutput.ts` 源码级）：每个 task 一个文件 `{项目temp}/{sessionId}/tasks/{taskId}.output`，**输出全落盘、内存零保留**；`DiskTaskOutput` 类用 write queue（string[]）+ 单线程 drain，**写完立即 splice 清空让 GC 回收**（源码注释强调"绝不能在 #writeAllChunks 里 await，否则 queue 堆积内存膨胀"）；磁盘 cap `5GB`，超了置 capped 标记停写；**安全** `O_NOFOLLOW` 防符号链接攻击 + `O_EXCL` 防覆盖；路径含 sessionId 防 `/clear` 换 id 后读空（inc-4586 真实踩坑）；查询默认 8MB，更大时前缀 "[XKB of earlier output omitted]"。

**opencode 教训**：V2 **刻意砍掉 bash background**（`core/src/tool/bash.ts:71-77`），列四前置条件——**durable status / restart recovery / owner-bound get/wait/cancel / bounded stream**。这是"做不到这四点就别上线"的 checklist。

### ECode 现状（要改的是根）

`src/tools/bash.ts:7` 用 **`execSync` 同步阻塞**，maxBuffer 10MB（**内存**）、timeout 30s；`agent.ts:422` `await executeTool`。后果：长命令卡死 loop、输出超 10MB 直接报错（非截断）、超 30s 被杀。后台任务不是"加个参数"，是**把 `execSync` 换成 `spawn`（异步）**——根本性改动。

### 核心机制四件套（本次拍板）

**① 触发**：bash 加 `run_in_background?: boolean`。首版只做**显式 `run_in_background: true`**一条路径（CC 的"超时自动后台""用户手动 promote"后置 YAGNI）。

**② 输出缓冲**：**抄 CC 纯落盘**（不要 opencode 双轨 / openclaw 双写——用户拍板"不要复杂的"）。`spawn` → stdout/stderr pipe → 落盘 `{resolveDataDir()}/tasks/{taskId}.output`（**复用 §9.3 resolveDataDir，别用 homedir**）；抄 `DiskTaskOutput`（write queue + drain + 写完即 GC）；cap 给 **100MB**（CC 的 5GB 对 CLI 太大）；抄安全 `O_NOFOLLOW` + `O_EXCL`（Windows 用字符串 flag 'wx'）。

**③ 完成通知（一步到位，主动注入——本次重点）**：

后台 child exit → registry 回调 → 注入 `<background_task_result id exit outputTail>` 到 messages + emit `background_task_completed` 事件。

**唤醒 agent（关键认知）**：注入点**不在 `agent.ts` loop 内部**（loop 是单次 submit 生命周期，跑到无 toolCalls 即 return），而在 **`use-agent-stream` 层**——后台完成 = 启动新一轮（复用 submit 路径，但触发源是后台事件而非用户）。机制：
- agent **idle**（没在跑）→ 自动启动新一轮（messages 含后台结果，LLM 主动告知用户"测试跑完了"）
- agent **running** → 后台完成事件**排队**，本轮 `completed` 后再触发
- **并发红线**：绝不能两个 `runAgentStream` 并发（messages 冲突崩溃），后台唤醒必须串行排队

**④ 控制 + 查询**：加两个工具（`registry.ts` 加声明）
- `TaskOutput`：tail 读（>上限前缀 omitted）+ offset 增量读（抄 `getTaskOutputDelta`）
- `TaskStop`：`child.kill()`；**Windows kill 进程树用 `taskkill /T /PID`**（跨平台坑，必处理）

### UI 交互三问（本次重点，用户明确点出）

**Q1：后台执行时能继续对话？** → 能。`run_in_background` → executeTool 立即返回（spawn 不 await child）→ agent loop 不阻塞 → 本轮 agent 可继续调别的工具/回文本，本轮结束用户可继续 submit。loop 天然支持。

**Q2：完成时视觉区分？** → 新增 `AgentEvent` 类型 `background_task_completed`（task_id / command / exitCode / outputTail）；`ChatView`/`tool-panel` **专属渲染**（如 `⏳→✓ [bg] task #abc · npm test` + 颜色），和普通 tool_result 折叠组区分开；StatusBar 加后台任务计数（"⚙ 2 bg running"）。

**Q3：对话途中完成如何唤醒？** → 见 ③ 事件驱动唤醒：agent idle 自动响应、running 排队；**不打断用户输入框**（Ink 输入框独立），通知只在对话流追加，agent 自动响应作为新 turn。

### 生命周期（本次拍板）

主进程死 → **所有后台任务 kill**（agent 子进程同死），**只保留输出记录**（落盘文件留着，可事后查）。不做 detach / orphan / 重启恢复（openclaw 那套不要）。

## 支点 19：Git 自动化 —— ❌ 已撤销（能力分散归位）

### 为什么砍

实证：CC（184 个工具文件）和 opencode 都**没有专门 git 工具**，git 全走 bash/shell。说明 git 操作能力 bash 已覆盖，独立支点价值薄。逐项拆解：

- **自动 commit**：风险高（agent 代码未必对就 commit，污染历史）；CC 不自动 commit，与「git 历史干净」偏好（CLAUDE.md §七）直接冲突。

- **自动 PR**：依赖 gh CLI + 远端 token，对本地 CLI 偏重，砍。

### 决策

撤销独立支点。git 操作走 bash（现状已支持）；真要的安全网（敏感拦截）在支点7/12 落地时带上。

## 支点 20：插件系统（打包分发） —— ❌ 已撤销（能力分散归位）

### 实证（CC / opencode / openclaw 真实源码）

三家都做了 plugin，但分量天差地别：

| | CC | opencode | openclaw |
|---|---|---|---|
| 做没做 | 做，生产级 | 做，**最轻** | 做，**产品核心** |
| manifest | `.claude-plugin/plugin.json`（Zod） | 没有，复用 `package.json` | `openclaw.plugin.json`（256KB） |
| 分发 | marketplace 多源 + 版本缓存 | **无 marketplace**，只 npm + `file://` | ClawHub 自家 registry |
| 代码量 | `utils/plugins/` ~45 文件 + pluginLoader 3300 行 | `packages/plugin` SDK（V1+V2 双轨） | `src/plugins/` **200+ 文件** |

**最该抄的一行**——opencode 文件投放（扔文件即发现，绕过 plugin 包）：

- `{skill,skills}/**/SKILL.md` → 自动发现 skill（还兼容 `.claude/skills/`、`.agents/skills/`）
- `{command,commands}/**/*.md` → 自动发现斜杠命令
- `{agent,agents}/**/*.md` → 自动发现 agent persona

零 manifest、零安装逻辑、零 marketplace，一份 glob + 读文件 + 注册器。

### 为什么砍

- **打包分发整套（marketplace + manifest + 版本缓存 + 安装管线）太重**：CC 45 文件、openclaw 200 文件，远超单包个人 CLI 的 ROI（YAGNI）。openclaw 是因为做「多渠道 gateway 重产品」才把 plugin 做成核心，ECode 不是。
- **plugin 包装层没必要**：plugin 打包的零件（命令/技能/hook/MCP）本就是各自独立的扩展点，再套一层「plugin」是冗余。
- **轻量内核（文件投放）不是新东西**：它本质就是「扔文件到约定目录自动发现注册」，这正是支点13（skill）/支点14（命令）本就要做的注册机制。

### 能力归属（不丢，分散到对应支点）

| 支点20 原能力 | 归宿 | 理由 |
|---|---|---|
| 打包的零件（命令/技能/hook/MCP） | 支点10/12/13/14 | 本就各自独立扩展点，不用 plugin 再包一层 |
| 轻量内核：文件投放发现 | 支点13（SKILL.md 懒加载注入）/支点14（命令 .md 注入） | 这俩支点实现时直接抄 opencode 的 glob——零 manifest |
| 安装 / 启停 / 注册表 | 支点15 | 已定（独立注册表，VS Code 扩展模式） |
| marketplace + manifest + 版本缓存 + 安装管线 | **砍** | CC 45 文件 / openclaw 200 文件，个人项目 YAGNI |

### 决策

撤销独立支点。扩展性走「MCP（工具层标准协议）+ SKILL.md（skill 层事实标准）+ 文件投放（命令/agent 层）」三件套，分别归支点10/13/14，不做 marketplace。若未来确有「用户要装第三方包」诉求，直接抄 `.claude-plugin/plugin.json`（openclaw 已主动兼容该格式，生态外部性最好），属 P2 远期。

### 免费午餐（记入支点13）

**SKILL.md 是三家事实标准**（CC / openclaw / opencode 全部识别，opencode/openclaw 还主动兼容 CC 的 `.claude/skills/` 格式）。ECode 支点13 用 SKILL.md（frontmatter + 正文）格式定义 skill = **零成本跨工具生态兼容**——别人写的 CC/AGENTS skill 包直接能用，反之亦然。这是定格式时的硬约束，别自造。

### 关联支点

支点10（MCP=工具层扩展协议）、支点12（hook 归支点自带）、支点13（skill 抄 opencode glob + SKILL.md 事实标准）、支点14（命令 .md 文件投放）、支点15（安装注册表）
