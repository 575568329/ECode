# ECode 后续 M5 实施方案：上下文压缩

> 日期：2026-08-14 · 状态：**草案待审阅 v10（架构定型）**
> **演进**：v1-v3 范围摸索 → v4-v9 算法/存储/投影迭代 → **v10 架构定型**（基于 [deepseek-harness + opencode 架构调研](../解析/2026-08-14_压缩架构定型调研_已完成.md)）。
> v10 三大定型（用户指导）：
> 1. **插件化骨架**（学 deepseek-harness）：压缩是抽象 Service + 多 Provider 策略插件 + 事件钩子触发,加新策略=写插件零改动。**不学 opencode 单体硬编码**。
> 2. **算法精而非多**：只上两级默认策略(免模型工具清除 + LLM 锚定摘要),靠策略接口留扩展位(外溢/overflow/model 切换预压都是未来插件)。
> 3. **★ 解决切换 model 超限**（补两家空白）：监听 /model 切换 → 立即新窗口预检 → 主动迭代压缩 + 警告 + /clear 兜底。两家都没做。
>
> 存储层沿用 v9 投影模型(history 全量 append-only + boundary 追加 + buildContextMessages 投影,restore 不触发压缩)。Skill → M6、MCP → M7 后置。

## 1. 核心架构：Context 与 History 分离（★ v9 投影模型，修正"恢复即压缩"缺陷）

> 设计依据：[history/context 分离调研](../解析/2026-08-14_history与context分离及memory调研_已完成.md)
> 关键认知：**history（给用户看的）和 context（喂 LLM 的）本就是两份东西**。不是"压缩不影响 history"，而是"history 全量存、context 是它的投影子集"。四家里 opencode 做得最干净（DB 全量 + filterCompacted 投影），ECode 抄它。

```
┌─────────────────────────────────────────────────────────────┐
│ History（对话历史 · 给用户看 · 全量 append-only · 永不压缩） │
│ ~/.ecode/sessions/<id>.jsonl                                 │
│ 存：全部原始 Message + 压缩时追加 boundary 行（含 summary +  │
│      tailStartId，但旧消息不删）                              │
│ 用途：/history 列表 + restore 后 UI 展示完整历史 / 审计 /导出│
└─────────────────────────────────────────────────────────────┘
          │ restoreFull(sid) 拿全量（给 UI）
          │ buildContextMessages(all) 投影（给 LLM）★ 纯函数
          ▼
┌─────────────────────────────────────────────────────────────┐
│ Context（喂 provider.run · 全量的投影子集 · 每轮现场算）     │
│ buildContextMessages(allMessages):                          │
│   找最后一个 boundary → 返回 [summary, ...tail, ...新消息]  │
│   无 boundary → 返回全量（新会话/未压缩）                    │
│                                                              │
│ ★ restore 不往 context 灌全量：restoreSession 只切 sessionId│
│   + 刷 UI（UI 用全量）；context 由 loop 每轮现场投影。       │
│   → 永不会"恢复即压缩"（投影永远尊重已持久化 boundary）      │
│                                                              │
│  压缩（TokenCounter 每轮 provider.run 前判定）：             │
│   Level 1 Tool Clearing（无 LLM，清旧 tool_result content）  │
│   Level 2 Compaction（summarize → 追加 boundary 到 history） │
└─────────────────────────────────────────────────────────────┘
```

**★ 修正 v4-v8 的缺陷**：
- ~~v4「restore 拿完整历史到 context，可能立即再触发压缩，但这是正确的——恢复本就是重新开始」~~ → **这是错的**（用户指出）。restore 把全量灌进 context = aider 反面教材。正确：context 是投影子集，restore 零成本。
- ~~v4「压缩永远不动 history 文件」~~ → **不完全对**。压缩要往 history **追加** boundary 行（含 summary + tailStartId），但**不删旧消息**。history 仍完整（append-only），只是多了 boundary 标记。投影函数靠这些标记工作。

**为什么是投影模型而非"压缩替换"**（抄 opencode）：
- 单一数据源（history 全量）+ 投影（buildContextMessages），UI/LLM 各取所需
- UI 看全量（含已压缩部分，boundary 处显"已压缩"标记）
- LLM 用投影（summary + recent + 新消息）
- restore 只切 sessionId，context 自动是投影子集——**天然不触发压缩**

### 1.5 压缩策略骨架（★ v10 插件化，学 deepseek-harness）

> 调研：[压缩架构定型](../解析/2026-08-14_压缩架构定型调研_已完成.md)。deepseek 把压缩做成「抽象 Service + 多 Provider 插件 + 事件钩子」,opencode 是单体硬编码。**ECode 学 deepseek 骨架**——加新策略=写插件零改动。

**为什么不学 opencode 单体**：opencode 的 prune/select/process 焊死在一个 Layer,加新策略只能 fork。deepseek 每种压缩手段(摘要/裁剪/外溢)是独立插件,可选依赖组合(`ctx.get('toolResultPruner')`,没装照跑)。

**策略接口**（`src/services/compaction/strategy.ts`，对应 deepseek `CompactionEngine`）：
```ts
/** 压缩策略契约：一种压缩手段 = 一个实现 */
export interface CompactionStrategy {
  readonly name: string                    // 'tool-clear' / 'summarize' / 未来 'spill'
  readonly cost: 'free' | 'llm'           // 成本档（编排器按成本递增排序：free 先 llm 后）
  /** 该不该跑（predicate，编排器每轮问） */
  shouldRun(ctx: CompactionContext): boolean
  /** 怎么跑（执行，返回变换后的 context + boundary 信息写 history） */
  run(ctx: CompactionContext): Promise<CompactionResult>
}

export interface CompactionContext {
  messages: Message[]                      // 当前 context（投影后，喂 LLM 的）
  allHistory: Message[]                    // 全量 history（投影源，append-only）
  tokenCount: number                       // 当前 token（实时重测量，非过期代理）
  contextWindow: number                    // 当前模型窗口（模型感知，切换后变）
  effectiveWindow: number                  // contextWindow × 0.9
  trigger: 'pressure' | 'overflow' | 'manual' | 'model-switch'  // 触发来源
}
```

**编排器**（`src/services/compaction/orchestrator.ts`）：注册策略 registry,按 `cost` 排序(free 先),每轮/事件触发时遍历：`shouldRun` 为真就 `run`,直到 token 降到阈值下或策略用尽。

**触发=事件钩子**（策略不关心何时被调,对应 deepseek 事件机制）：
- `pre-turn`（每轮 provider.run 前,pressure 预防）
- `on-provider-error`（400 overflow,反应式救场）
- `on-model-switch`（★ ECode 补的,切换即预检,见 §3.6）
- 手动 `/compact`

**M5 默认注册两个策略**（精而非多）：
1. `tool-clear`（cost: free）——免模型工具结果清除（§3.1）
2. `summarize`（cost: llm）——LLM 锚定摘要（§3.2）

**未来加策略=写新插件注册**（零改动现有）：`spill`（外溢到文件）/ `overflow-reactive`（反应式重放）/ 按模型定制策略……都通过实现 `CompactionStrategy` + register 接入。

## 2. 目标 & 验收

**目标**：长对话不因上下文超限崩溃；工具输出不占满窗口；**恢复历史会话不触发压缩**（history/context 分离）；对话历史完整保存。

**验收**：
- **Level 1 Tool Clearing**：context 超 L1 阈值，旧 tool_result 占位符化（保留 tool_use + 最近 N 次），模型仍知执行过什么
- **Level 2 Compaction**：context 超 L2 阈值 / `/compact` / 400 兜底 → summarize 旧消息，往 history 追加 boundary 行
- **★ Context/History 分离**：`buildContextMessages` 投影正确（无 boundary 返回全量；有 boundary 返回 summary+tail+新消息）
- **★ restore 不触发压缩**：恢复长历史会话 → UI 显示全量，但 context（喂 LLM）是投影子集，不会立即压缩
- **History 完整**：history 文件含全部原始消息 + boundary 行（append-only，旧消息不删）
- **摘要质量**：压缩后 LLM 仍引用压缩前的文件路径/技术决策
- **400 不重试**：context-too-long 走压缩，非退避重试

**不做**（后置）：
- Memory 系统（跨会话结构化记忆）—— 见 [memory 调研](../解析/2026-08-14_history与context分离及memory调研_已完成.md)，独立小改或后续
- AGENTS.md 接 runtime（低成本高收益，但独立于 M5 压缩，可先做）—— 见调研档1
- 多级管线高级策略（snipCompact / reactive / 锚点摘要）
- prompt cache 雪崩优化（GLM 端点暂无 prompt cache）
- Skill/MCP（M6）

## 3. 压缩策略实现（★ v10：两个默认策略插件，精而非多）

> 架构：§1.5 策略骨架（deepseek 插件化）。算法依据：[压缩源码调研](../解析/2026-08-14_上下文压缩源码调研_已完成.md)。
> M5 只实现两个策略（最高 ROI）+ 接口留扩展位。学 deepseek「prune(免模型) 先 + summarize(LLM) 后」的成本递增编排。

### 3.1 Level 1: Tool Clearing（闲时清工具内容，抄 claude-code microCompact）

**痛点**：tool_result（bash 30KB、read_file 大文件、grep 命中）是 token 大户。

**算法**（`src/services/toolClear.ts`，抄 claude-code `microCompact.ts`）：
- 只替换 **tool_result 的 content**（tool_use 不动——模型知道调过什么）
- 保留最近 K 条（默认 4）完整结果，其余 content → `'[旧工具结果已清理：约 X tokens，需要时重新执行]'`
- 无 LLM 调用（纯本地，便宜，每轮可跑）
- ★ **API 不变量保护**（抄 claude-code `adjustIndexToPreserveAPIInvariants`）：保留区有 tool_result 必带回配对的 tool_use，**绝不切断对**（否则 API 400）

### 3.2 Level 2: Compaction（主动压缩对话，opencode select + 滚动 summary）

**算法**（`src/services/compact.ts`，抄 opencode `compaction.ts`）：
```ts
export async function compactMessages(
  messages: Message[],
  opts: { provider: LLMProvider; providerReq: ProviderReq; previousSummary?: string },
): Promise<CompactResult>
```
**select 切分**（抄 opencode `:128`）：recent 预算（默认 8000 token）从尾部累加吃满；切分点那条消息按字符精确劈开。head（去摘要）+ recent（原样保留）。head 过滤掉旧 compaction 消息。

**★ 摘要 Prompt**（opencode `SUMMARY_TEMPLATE` 结构化 + claude-code `<analysis>` 草稿剥离）：
```
CRITICAL: 只用文本回复，不要调用任何工具。
先在 <analysis> 里按时序分析对话（用户意图/处理方式/关键决策/代码片段/文件名/错误及修复/用户反馈），
再在 <summary> 里按以下结构输出（保持段落顺序，即使空也保留）：
## 目标
- [用户想完成什么]
## 重要细节
- [约束/偏好/决策及原因/关键文件路径/函数名/命令/错误信息；无则 (none)]
## 工作状态
### 已完成 / ### 进行中 / ### 受阻
## 下一步
1. [立即的下一步]
## 相关文件
- [文件路径: 为什么重要]
规则：精炼要点不要散文；精确保留文件路径/符号/命令/错误串/URL；不要提及压缩过程。
```
产出后 **strip `<analysis>`**（草稿提升质量但无信息价值，抄 claude-code `formatCompactSummary`）。

**★ 滚动 summary**（抄 opencode `buildPrompt` `:161`，处理多次压缩的关键）：
- 有 previousSummary → prompt 加「用上述对话更新下面的锚定摘要：保留仍成立的细节，删除过时的，合并新事实」+ 上轮 summary
- 上轮 compaction 的 recent（上次原样保留的尾部）拼进这次摘要的 context
- **解决「多次压缩信息逐级丢失」**（单次全量重摘要会丢，滚动更新保留连续性）

**summary 消息格式**（抄 opencode Compaction 类型，runtime 结构不落 history）：
```ts
{ type: 'compaction', summary: string, recent: string }  // recent 供下轮滚动
```
喂 LLM 时，compaction 后的真实消息才进 context。

### 3.3 Level 3: 兜底（抄 aider 递归 / codex 开新窗口）

**触发**：L2 摘要后仍超限（极长历史），或摘要 LLM 调用本身塞不下。

**算法**（抄 aider `summarize_real`）：递归二分（尾部留 half 原样，头部摘要，仍超递归 depth+1，base case `len<=4 或 depth>3` 整段摘要）。
**终极兜底**（抄 codex `compact_token_budget`）：递归都失败 → 开新窗口（只保 system + 最近一条 user + 「历史已截断」提示），保证可用。

### 3.4 编排器协调（v10 策略 registry，非硬编码 L1/L2/L3）

编排器（orchestrator）注册策略,按 `cost` 递增排序（free 先 llm 后）。触发时遍历：
```
事件触发（pre-turn / on-provider-error / on-model-switch / manual）：
  for strategy of registry.sortByCost():   // tool-clear(free) 先，summarize(llm) 后
    if strategy.shouldRun(ctx):             // 各策略自己判阈值
      result = await strategy.run(ctx)
      if result.tokensDropped: 写 boundary 到 history + 重置投影
      if tokenCount <= threshold: break      // 降下来了就停
```
不再硬编码"先 L1 后 L2"——编排器按 cost 自动让免模型策略先跑(清完可能就够,省 LLM 调用)。

### 3.5 失败降级（四家综合）

- **摘要 prompt 自身超限** → opencode 预检闸 `estimate(summaryPrompt) > context - output` 直接放弃
- **LLM 调用失败** → 静默 no-op 下轮重试（opencode）+ 多模型兜底（aider weak model 摘要）
- **熔断器** → 连续 3 次失败停（claude-code `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3`）
- **compact 调用本身 413** → 按轮分组从头删重试（claude-code）/ 删最旧（codex）
- **★ 免模型 prune 是 durable 的**（学 deepseek）：即使后续摘要失败,已裁剪的工具结果不回滚
- **都失败** → 终极兜底（开新窗口保 system+最近 user，codex）

### 3.6 ★ 切换 model 时 context window 变化怎么救（v10 补两家空白）

> 调研：[架构定型](../解析/2026-08-14_压缩架构定型调研_已完成.md) §三。deepseek/opencode 都**没有**"监听切换主动预压缩",只靠"下一轮阈值检查 + 被拒反应式"。**ECode 补这个空白**。

**场景**：1M 模型聊到 80 万 token，`/model` 切 200k——下一发必超限。

**ECode 方案**（比两家多一道 `on-model-switch` 主动预检）：
1. **监听 /model 切换事件**：TuiApp `setConfig`（切 model）后触发 `on-model-switch`
2. **立即新窗口预检**：用新 model 的 contextWindow（models.dev 查）+ **实时重测量**当前 context tokenCount（学 deepseek 实时测，**不学 opencode 过期代理值**）
3. **已超则主动迭代压缩**：跑编排器（compactionRetries，多次 compactRegion 直到低于新阈值或达上限）
4. **警告 + /clear 兜底**：迭代后仍超 → banner「当前对话已超出 <新model> 的窗口（X/Y），建议 /clear 起新会话或继续压缩」+ 允许用户选择

```ts
// TuiApp onModelSwitch（/model 切换后）
onModelSwitch(newModel) {
  const newWindow = resolveContextWindow(newModel, cfg.contextWindow)
  const tokens = tokenCounter.measure(allHistory)  // 实时重测，非代理
  if (tokens > newWindow * 0.9) {
    // 主动迭代压缩到新窗口
    orchestrator.run({ trigger: 'model-switch', contextWindow: newWindow, ... })
    if (still overflow) setBanner('对话超出 ${newModel} 窗口，建议 /clear')
  }
}
```

**为什么两家没做但 ECode 该做**：两家都是通用框架（用户可能不切 model），ECode 的 `/model` 是核心特性（M4 做的跨 provider 切换），切换超限是高频真实场景。补这道预检 = 差异化优势。

**80 万→200k 单次不够**：编排器迭代压缩（多次 summarize），免模型 prune durable 保底。仍不够 → 开新窗口兜底（§3.5）。

## 4. token 计数（★ v5 修正：usage 锚定 + 估算，不装 tokenizer）

**v4 错误**：装 gpt-tokenizer（~1MB，对 GLM 也是估算，过度）。

**v5（调研修正，抄 claude-code `tokenCountWithEstimation`）**：
- **主路径：API usage 锚定 + chars/4 增量估算**（零依赖，零模型差异）
- 每轮 provider.run 后，从 Delta.usage 的 `input_tokens` 更新**精确基准**（服务端算的，最准）
- 新消息用 chars/4 粗估（JSON/代码 chars/2，图片固定 ~2000）增量累加到基准
- 压缩/clearing 后标记「待重新锚定」（下次 usage 回来重置基准，防漂移）

```ts
// src/services/tokenizer.ts（零依赖，不装 gpt-tokenizer）
export class TokenCounter {
  private anchoredTokens = 0   // 最后一次 API usage 的 input_tokens（精确基准）
  private anchoredMsgCount = 0 // 锚定时 messages 长度
  private pendingEstimate = 0  // 锚定后新增量的估算

  /** provider.run 后调，用服务端精确 usage 重新锚定 */
  anchor(inputTokens: number, msgCount: number) {
    this.anchoredTokens = inputTokens
    this.anchoredMsgCount = msgCount
    this.pendingEstimate = 0
  }

  /** 估算当前 system + messages 的 token 数（锚定 + 增量 chars/4） */
  estimate(system: string, messages: Message[]): number {
    const sysTokens = Math.ceil(system.length / 4)
    if (messages.length < this.anchoredMsgCount) {
      // 压缩/clearing 后 messages 变短 → 全量估算（待下次 usage 重新锚定）
      return sysTokens + estimateMessagesChars(messages)
    }
    // 增量：锚定点之后的新消息
    let inc = 0
    for (let i = this.anchoredMsgCount; i < messages.length; i++) inc += estimateMessageChars(messages[i])
    return this.anchoredTokens + inc + sysTokens  // sys 可能变，每次算
  }
}
// estimateMessageChars: text → len/4；tool_use input JSON → len/2+20；tool_result → len/4+10
```

**为什么不用真实 tokenizer**（调研）：claude-code/codex/opencode 三家都不用——各模型 tokenizer 不同（tiktoken 只准 OpenAI），装重依赖且对 GLM 仍估算。usage 锚定有服务端精确基准防漂移，足够准。

## 5. contextWindow 获取（★ v7：models.dev 远程库，抄 opencode）

**v4 错误**：硬编码 128k（错值）。
**v5 不足**：内置查表写死——模型更新/新模型涌现表很快过时。
**v6 偏向 litellm**：但 litellm 是 Python 生态副产品，models.dev 更适合（见下）。
**v7（用户定 + 调研确认）**：用 **models.dev**（opencode 团队维护、自家产品在用、同 TS 栈可参考、收录智谱）。

**选型理由**（vs litellm）：
- models.dev：**opencode 自家产品在用**（吃狗粮，维护上心）、专门做模型库（聚焦）、**同 TS 栈**（`models-dev.ts` 集成代码 ECode 可直接参考）、[收录智谱](https://models.dev/labs/zhipuai)（GLM-5/GLM-5-Turbo/GLM-4.6）
- litellm：Python 生态、模型库是副产物（主业 proxy）

**GLM 真实窗口（★ 纠正 v4/v5 的 1M 错误）**：GLM-5 = **200K**（[z.ai/blog/glm-5 官方](https://z.ai/blog/glm-5)，训练期 32K→128K→200K 渐进扩展），非 1M。GLM-4.6 = 200K。

**四级 fallback**（抄 opencode `models-dev.ts`）：
```ts

const FALLBACK_TABLE = { 'glm-5': 200_000, 'glm-4.6': 200_000, 'glm-4': 128_000, /* 应急最小表 */ }

export async function resolveContextWindow(model: string, configOverride?: number): Promise<number> {

  const db = await loadModelsDb()                                    // 2. models.dev（缓存+离线兜底）

  const fb = matchFallbackTable(model, FALLBACK_TABLE)               // 3. 内置最小表
  if (fb) return fb
  process.stderr.write(`[CONTEXT] 未知模型 ${model}，用安全默认 32000。可配 contextWindow 覆盖。\n`)
  return 32_000                                                       // 4. 安全默认 + 告警
}

/** models.dev 加载（抄 opencode）：缓存命中→用缓存；过期→后台拉新；首次无缓存→同步拉(10s timeout) */
async function loadModelsDb(): Promise<ModelsDb> {
  // ① 缓存未过期 → 直接读（零网络）
  // ② 缓存过期/不存在 → 拉 MODELS_URL（10s timeout + 2 次退避 + 原子写 tempfile+rename + Flock 跨进程锁）
  // ③ 拉失败/无网络 → 构建期快照 ECODE_MODELS_SNAPSHOT（离线兜底）

```

**关键设计**（opencode 验证可行）：
- **5min 缓存**（抄 opencode，非 aider 的 24h——models.dev 更新更勤，5min 够新且不频繁拉）
- **离线兜底**：构建期打包 models.dev 快照（抄 opencode `OPENCODE_MODELS_DEV`，esbuild define 注入）+ 内置最小表
- **原子写** tempfile + rename（防半截写）+ **Flock 跨进程锁**（防多 CLI 并发刷）
- **10s timeout + 2 次退避**（不卡死启动）
- **匹配**：canonical 名子串（抄 claude-code longest-id-first）
- **effective = raw × 0.9**（留 headroom，抄 codex）

**阈值（绝对值）**：


## 6. loop 集成（onBeforeRequest hook + 原地 mutate + P0 修订）

### 6.1 onBeforeRequest hook（架构师建议，单行注入）

LoopRunOptions 加：
```ts
onBeforeRequest?: (messages: Message[]) => Promise<{ messages: Message[]; compacted: boolean }>
```

loop 每轮 provider.run 前：
```ts
if (opts.onBeforeRequest) {
  const { messages: newMsgs, compacted } = await opts.onBeforeRequest(messages)
  if (compacted) {
    // P0-1：原地 mutate（TuiApp/cli 靠 messagesRef mutation）
    messages.length = 0; messages.push(...newMsgs)
    opts.callbacks.onCompacted?.(messages)  // P1-1：通知 UI 重建 committed
  }
}
```

### 6.2 onBeforeRequest 实现（两级 + 阈值）

```ts
const tokenCounter = new TokenCounter()
// v5：绝对值阈值（派生自真实 contextWindow，非百分比）
const ctx = resolveContextWindow(providerReq.model, providerReq.contextWindow)
const effectiveWindow = Math.floor(ctx * 0.9)
const LEVEL1_THRESHOLD = effectiveWindow - 30000  // Tool Clearing（工具大户早清）
const LEVEL2_THRESHOLD = effectiveWindow - 20000  // Compaction（留 buffer land the plane）

onBeforeRequest: async (messages) => {
  const tokens = tokenCounter.estimate(system, messages)
  // Level 1: Tool Clearing（低阈值，工具输出大户）
  if (tokens > LEVEL1_THRESHOLD) {
    const r = clearToolResults(messages, { keepRecent: 4 })
    if (r.clearedCount > 0) {
      messages = r.messages
      onWarn(`已清理 ${r.clearedCount} 个工具输出（释放 ~${r.freedTokens} tokens）`)
    }
  }
  // Level 2: Compaction（高阈值）
  const afterClear = tokenCounter.estimate(system, messages)
  if (afterClear > LEVEL2_THRESHOLD) {
    if (++compactCount > MAX_COMPACTS) { onWarn('建议 /clear 起新会话'); return { messages, compacted: true } }
    const r = await compactMessages(messages, { provider, providerReq })
    onWarn(`已压缩对话（移除 ${r.removedCount} 条）`)
    return { messages: r.messages, compacted: true }
  }
  return { messages, compacted: false }
}
```
**provider.run 后**：`tokenCounter.anchor(usage.input_tokens, messages.length)`（用服务端精确 usage 重新锚定基准）。

### 6.3 400 兜底分支（loop recoverable 内，错误码专属）

```ts
if (streamError.code === 'CONTEXT_TOO_LONG') {
  if (pushedThisRound) messages.pop()  // 回滚半截（P1-9）
  const r = await compactMessages(messages, { provider, providerReq })
  messages.length = 0; messages.push(...r.messages)  // 原地 mutate
  opts.callbacks.onCompacted?.(messages)

}
```

### 6.4 /compact 命令（手动 Level 2）

CommandRegistry action 扩 `'compact'` + 注册。TuiApp onCommand → compactMessages → 原地 mutate + setCommitted + tokenCounter.reset。

### 6.5 前置：errors.ts CONTEXT_TOO_LONG 分类（P0）

## 7. History 持久化 + Context 投影（★ v9 投影模型，修正 v4"history 不动"缺陷）

> 调研：[history/context 分离](../解析/2026-08-14_history与context分离及memory调研_已完成.md)。抄 opencode：存储全量 + 运行时投影。

**v4 缺陷（废弃）**：v4 说「history 不动，restore 拿全量到 context，恢复可能立即触发压缩但这是正确的」——**这是错的**（用户指出）。全量灌 context = aider 反面教材。

**v9 方案（opencode 投影模型）**：

### 7.1 History 存储全量 + boundary 追加（append-only，旧消息不删）
- `FileHistoryStore` 保持 append-only（现状不动）
- **压缩时**：往同一个 `<sid>.jsonl` **追加**一行 boundary（不删旧消息）：
  ```ts
  { compact_boundary: true, summary: '<strip analysis 后的摘要>', tailStartId: '<tail 起始 message id>', preTokens: 95234 }
  ```
  旧消息留在前面（history 完整），boundary 是投影锚点。

### 7.2 Context 投影（纯函数，每轮现场算）
新增 `src/core/context.ts`（对应 opencode `filterCompacted`）：
```ts
/** 从全量 messages 投影出喂 LLM 的 context（无副作用） */
export function buildContextMessages(allMessages: Message[]): Message[] {
  // 找最后一个 compact_boundary 行
  // 有 boundary → 返回 [summary_msg, ...从 tailStartId 的尾部, ...boundary 后的新消息]
  // 无 boundary → 返回全量（新会话/未压缩）
}
```
- `runLoop` 改造：每轮从 history 现场取 context——`buildContextMessages(history.restoreFull(sid))`，不再直接吃全量 messagesRef
- `messagesRef` 只存"本轮要追加的新消息"，历史来自 store + 投影

### 7.3 restore 零成本（★ 不触发压缩）
- `restoreSession` 改成**只切 sessionId + 刷 UI**（UI 用 restoreFull 全量渲染），**不往 context 灌全量**
- context 由 loop 每轮现场投影 → **永远尊重已持久化 boundary → 恢复即投影子集 → 天然不触发压缩**
- UI 在 boundary 处显示"已压缩（移除 N 条）"标记（用户知道这段被压缩过，但仍可回看全量）

### 7.4 两份 restore 接口
- `restoreFull(sid)`：全量消息（UI 展示 / 导出 / 审计用）—— 现有 restore 改名
- `buildContextMessages(restoreFull(sid))`：投影子集（喂 LLM）—— loop 每轮调

### 7.5 HistoryStore 接口扩展
```ts
/** 压缩时追加 boundary 行（append-only，旧消息不删；投影锚点） */
appendCompactBoundary(summary: string, tailStartId: string, preTokens: number): void
/** 全量读取（UI/投影用） */
restoreFull(sessionId: string): Message[]  // 含 boundary 行（buildContextMessages 识别）
```

**结果**：history 完整保存（全量 + boundary，用户回看/导出/审计）；context 是投影子集（防超限）；**restore 零成本不触发压缩**。三者职责清晰，单一数据源（history）+ 投影（context）。
