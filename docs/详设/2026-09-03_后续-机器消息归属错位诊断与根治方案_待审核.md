# 后续-机器消息归属错位诊断与一次性根治方案

## 0. 一句话

后台任务通知、loop-guard 提醒、续写指令等**机器生成的消息**被渲染成用户气泡（❯ 前缀），
用户看到「自己在说什么鬼话」。根因：这些消息走 user 角色通道进 transcript，而显示层只认
角色不认来源。本方案用**消息级元数据（meta 标记）+ 全创建点改造 + 三端渲染分流**一次性根治。

## 1. 真机案例（2026-09-03）

用户在主对话看到（❯ 用户输入格式渲染）：

```
❯ [task] #t2（cd D:/Study/ECode && npx tsc --noEmit > /tmp/tsc2.txt 2>&1; ）已完成 exit 0——输出可用 task_output("t2") 读取
```

用户质疑：「这种信息为什么会用用户输入的格式渲染？是你在用主对话进行测试吗？」

——不是测试。是 t2 后台任务完成通知经 user 通道进 transcript，被 TUI 当用户气泡渲染。

## 2. 机制链路（为什么 user 角色会被渲染成 ❯）

1. **通知的必要性**：后台任务完成时模型必须知道「该去读输出了」——通知必须进 LLM 上下文。
2. **协议约束**：tool_result 必须严格配对 tool_use，信息性回喂不能伪造工具结果 → 只能走
   user 角色文本消息（`loop.ts` M9-P3 注释明确此约束）。
3. **运输路径**：
   - 模型忙时：`afterTools` feedback（`session.ts:1712`）→ user 消息
   - 模型闲时：拼进下一条用户输入（`session.ts:1286`：`input = \`${input}\n${n}\``）
4. **渲染断层**：transcript 里 role='user' → `commit.ts` 一律渲染成用户气泡 →
   **机器文案顶着用户的脸出现**。

## 3. 问题全景盘点（全部冒充形态）

| # | 消息 | 生成点 | 当前防冒充手段 | 残留问题 |
|---|---|---|---|---|
| N1 | task 后台任务完成通知 | tasks.ts collectNotifications | 无 | 空闲时拼进用户输入、忙时走 feedback——两形态都冒充；**本案例元凶** |
| N2 | loop-guard nudge/abort | session.ts loopGuardRound | 无 | 同 N1 双形态；用户也真机撞见（❯ [loop-guard] 最近 8 轮…） |
| N3 | quality lint/test 回喂 | makeAfterTools quality 段 | 无 | 同上 |
| N4 | CONTINUE_PROMPT 续写指令 | loop.ts length 分支 | commit.ts **精确字符串过滤**（先例） | 能工作但脆弱：文案一改即失效；web 端未过滤 |
| N5 | 审查卡（review card） | session.ts maybeRunReview | 文本前缀 `[审查器附注（` + commit.ts splitReviewCard（先例） | 前缀匹配同样脆弱；**审查卡内容含前缀串时误判**；web 端未拆 |
| N6 | 插话包装 | loop.ts iter≥2 pollUserInput | 包装文案声明「用户发来新消息」 | 真用户插话，包装是必要语义——不算冒充（对照项） |
| N7 | 轮末兜底续投 pendingReviewCard | startTurn 拼进 input | 同 N5 | 同上 |

**已确认无冒充**：用户真插话（N6）、审批超时反馈（走 tool_result is_error，有真 tool_use 配对）。

## 4. 对标与原则

- **M11-P7 审查卡修复先例**：曾以「统一冒充用户消息」被判归属谎言 + 注入放大面，
  加 `kind:'review'` 结构化标记——本方案把同一原则推广到全部机器消息。
- **CONTINUE_PROMPT/REVIEW_CARD 前缀过滤先例**：方向对（显示层过滤），手段脆（字符串匹配）。
- **原则**：消息的**来源应当是一等数据（结构化标记），不是可被内容碰撞的文本特征**；
  模型侧语义不变（仍以 user 角色可见），显示侧按来源分流。

## 5. 方案：meta 元数据 + 三端分流

### 5.1 数据结构（core/types.ts）

```ts
/** 消息来源标记（2026-09-03 机器消息归属根治）：system 注入的机器消息带 meta，
 *  显示层据此分流（不渲染成用户气泡），协议翻译层剥除（不外发）。用户消息永无此字段。 */
export type MessageMeta =
  | { kind: 'task-notify' }   // 后台任务完成通知
  | { kind: 'loop-guard' }    // loopGuard nudge/abort 回喂
  | { kind: 'quality' }       // lint/test 回喂
  | { kind: 'continue' }      // max_tokens 续写指令（CONTINUE_PROMPT）
  | { kind: 'review-card' }   // 纠偏审查卡
  | { kind: 'interject' }     // 插话（含用户真插话的包装体——渲染为插话样式而非普通气泡）

export interface Message {
  role: 'user' | 'assistant'
  content: ContentBlock[]
  /** 机器/系统注入标记——仅内存与落盘态，协议请求体剥除 */
  meta?: MessageMeta
}
```

### 5.2 创建点改造（全部 7 处）

| 点 | 改法 |
|---|---|
| tasks.ts collectNotifications | 返回 `{text, meta}` 对（不再裸 string） |
| session.ts:1286 空闲拼接 | **废除拼接**——改为逐条独立 `runLoop` 输入？不行（会开新轮）。改为：通知带 meta 走 `startTurn` 的「预注入消息」参数，作为独立 user 消息 push（带 meta）后接用户输入 |
| session.ts afterTools feedback | feedback 变 `{text, meta?}`；loop.ts 构造 fbMsg 时带上 |
| loop.ts CONTINUE_PROMPT | continueMsg 带 `meta:{kind:'continue'}` |
| loop.ts 插话包装 | interjectMsg 带 `meta:{kind: q.kind === 'review' ? 'review-card' : 'interject'}` |
| session.ts quality 段 | 同 feedback 通道 |
| loopGuard feedback | 同 feedback 通道（kind:'loop-guard'） |

### 5.3 落盘与恢复（history.ts）

- append 时 meta 随行序列化（`{role, content, meta}`）；restoreFull 原样带回。
- 兼容：旧会话行无 meta 字段 → 视为用户消息（现状行为），零迁移。

### 5.4 渲染分流

- **TUI commit.ts**：删 CONTINUE_PROMPT 精确过滤与 splitReviewCard 前缀解析——改为
  `m.meta` 直读：continue/review-card/task-notify/loop-guard/quality → 各自 item 形态
  （continue 不渲染或渲染成系统行；review-card 渲染为 review-card item；通知/守卫渲染成
  系统提示行样式，非用户气泡）。
- **web store.ts/Conversation.tsx**：session/read 恢复与 `user` 帧构造时读 meta——
  机器消息渲染为 system 样式行（复用现有 kind:'system'）。
- **协议翻译层（anthropic.ts/openai.ts）**：构造请求时剥 meta（字段本就不在协议 schema，
  TS 结构化剥除，非字符串处理）。**已核实两文件均白名单式构造 content，多余字段自然不外发——
  只需确认无 rest 展开泄漏**（实施时验证）。

### 5.5 防回归

- loop-guard/commit/protocol 现有测试补 meta 断言；
- 新增：commit.ts 对带 meta 消息不生成 user 气泡 item；
- 移除 commit.ts 对 CONTINUE_PROMPT 的字符串依赖后，loop.ts 文案改动不再破 UI。

## 6. 验收标准

1. 真机复现原案例：后台任务完成后，用户气泡区无任何 `[task]`/`[loop-guard]` 文本；
   通知以系统样式行呈现（或按产品拍板不呈现，模型侧仍可见）。
2. 空闲态下一条用户输入触发通知注入：用户输入气泡只含用户文本，通知独立成行。
3. 旧会话恢复：无 meta 的历史行渲染行为与升级前完全一致。
4. 协议安全：anthropic/openai 请求体无 meta 字段（测试断言翻译输出无 'meta' 键）。
5. 全量 tsc + 触碰面测试绿；CONTINUE_PROMPT/REVIEW_CARD 字符串匹配代码全部退役。

## 7. 边界与不做

- 不改 afterTools 的 feedback 协议形状（loop.ts 接口不动，meta 在宿主侧已带上）——
  实施时若发现 loop.ts 必须感知，则最小扩展（feedback 可选 meta 字段），不做大重构。
- 不做消息来源的权限/信任分级（安全隔离维度，另立）。
- 插话（N6）用户语义保留，只加 interject 标记供样式区分。

## 8. 实施记录（2026-09-03 执行批，全部落地）

**数据层**（core/types.ts）：`Message.meta?: MessageMeta` 七枚举（task-notify/loop-guard/quality/
continue/review-card/interject/system-notice）；用户消息永无此字段（判据即存在性）。

**创建点改造**（7 处全改）：
- tasks.ts `collectNotifications()` → `Array<{text, meta}>` 结构化返回
- session.ts 空闲拼接（原 L1286）→ **废除字符串拼接**，改「预注入消息」：startTurn 内先 push
  带 meta 的独立 user 消息（落 transcript + history），用户输入照常追加其后
- session.ts pendingReviewCard 空闲注入 → 同上（kind:review-card）
- session.ts makeAfterTools → feedback+meta 成对携带（loopGuard 优先；quality 仅在无 feedback
  时接手——原实现 quality 会覆盖 guard feedback，属顺带修正的行为偏差，语义更正确）
- loop.ts afterTools → 最小扩展（§7 预案启用）：返回值可带 meta，fbMsg 随行
- loop.ts CONTINUE_PROMPT / 插话 → continueMsg/interjectMsg 带 meta

**渲染分流**：
- TUI commit.ts：CONTINUE_PROMPT 精确匹配 + REVIEW_CARD_MARK 前缀解析**全部退役**——
  meta 直读：continue 不渲染；review-card 沿用既有 item；task-notify/loop-guard/quality/
  interject/system-notice → 新 `system-note` item（◎ 系统行）
- web store.ts loadHistory：meta 行 → kind:'system'（既有样式）；interject 例外（用户插话
  保真文本以 user 气泡呈现？——否，按「机器包装体」整体以 system 行呈现，原文本在内）

**落盘**（history.ts）：meta 随行序列化/恢复；旧会话无 meta 字段 → 用户消息（零迁移）。

**协议**：anthropic/openai 均白名单构造 content，meta 天然不外发（补测试断言锁住）。

**测试**（+9 条）：commit 分流 6 条（含「用户文本恰含 [task] 前缀但无 meta 仍为用户气泡」的
无碰撞断言）+ guard feedback meta 1 条 + 插话 meta 1 条 + 协议无泄漏 1 条；tasks.test 适配
结构化返回。触碰面 148+9 全绿，tsc 净。

**行为变化说明（唯一）**：原 makeAfterTools 中 quality feedback 会**覆盖**同轮 loopGuard
feedback（后写胜出）；改造后 guard 优先、quality 不覆盖（止损语义优先）——更正确，记录在案。
