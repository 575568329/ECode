# ECode 后续 M11 实施方案：Subagent（并发子代理）+ Todo 任务清单 + 主循环插话

> 日期：2026-08-17（v1.2/v1.3/v1.4：2026-08-18）· 状态：**设计稿 v1.4（待启动；v1.1 核码审阅三 P0 重设计；v1.2 扩 todo；v1.3 扩插话；v1.4 角色审阅修 F1-F4 + L1-L4）**
> 主题一句话：LLM 能把独立子任务**并发**委派给隔离的子代理跑完拿结论——task 是普通工具，心脏零改动；顺手补上两家标配的 todo 任务清单（多步任务的进度跟踪面）与主循环插话（运行中用户消息排队+步间注入，长任务期间不再只能干等或 Ctrl+C）。
> 来源：观察区 subagent 项（M7 §H2）经三轮用户拍板（并发直上/日志隔离/禁 ask_user）+ 两手源码调研（CC/opencode/deepseek-harness）+ 核码审阅；todo 为 M1M2 审阅报告 P2 差距项，主循环插话为原 v1"不做"项经用户拍板转正（2026-08-18，仅主循环侧——给运行中子代理插话/wake 仍不做），两家一手核对见 §7.1。

## 0. 目标与验收

**目标**：主 LLM 可在单轮里发起多个并发子代理（各自独立上下文跑完返回结论）；子代理改文件有快照、有确认门、进 git 提交集；日志可按 agentId 切轨迹；运行时可见进度且不破活动区高度预算。**（v1.2）**主 LLM 有 todo 任务清单工具跟踪多步任务进度，transcript 内联可见，rewind/恢复会话自动一致。**（v1.3）**主循环运行中（流式/工具执行/子代理长任务期间）用户仍可输入消息——排队+步间注入，不再只能在"干等"与"Ctrl+C 全弃"之间二选一。

**验收**：
- **task 工具**：`makeTaskTool(deps)` **工厂创建**（TuiApp/cli 装配时 register——静态 BUILTIN_TOOLS 数组拿不到动态父要素，见 §1 注入通路）；`task(description, prompt, type?)`；**readonly:true（并行池+免确认**——task 自身免确认合理，副作用确认由子循环的 confirm 把守**）**——单消息多 task_use 即并发，无硬上限
- **隔离**：子代理全新 messages（prompt 为首条 user）；**禁配三张：task（递归一层封顶）+ ask_user**（交互权归主循环——疑问写进返回结果，由主 agent 决定是否代问用户）**+ todo（清单主权归主 agent——子代理 transcript 独立，其清单无人可见，且并发写共享清单必冲突，opencode 同款禁配）**；其余工具从主 Registry **现取现建**裁剪版（含 MCP/plugin 运行期注册的工具）
- **history**：子代理消息**不进主会话 JSONL**（NoopHistoryStore + transcript 独立 `~/.ecode/agents/<agentId>.jsonl`——execute 结束 finally 全量序列化子 messages，abort 路径也落盘）
- **并发安全（四道）**：confirm 经**装配层串行队列**包装父回调（askUserBridge 同款——原单槽是覆盖式，并发必炸，见审阅 P0-1）；checkpoint 内部 promise 链**串行化**（nextSeq 并发竞态，P1-5）；子代理用**独立 QualityGate/orchestrator 实例**（熔断/压缩计数不与父及其他子互扰，P1-2）；工具 prompt 教学"并行任务不碰相同文件"
- **超窗安全**：子代理配**独立压缩钩子**（makeOnBeforeRequest 工厂 + 独立 orchestrator + NoopHistory）——不配则 CONTEXT_TOO_LONG（recoverable:false）会炸穿父循环（审阅 P0-2）
- **autoCommit 只归父轮末**：子代理 afterTools **剥离 autoCommit**（仅 quality 回喂；文件集经父 onBeforeWrite 收集，父轮末统一提交——审阅 P1-1）
- **日志**：LogEntry 加可选 `agentId` + Logger 四方法加可选尾参（两处，P2-5），子代理包装 logger 注入；agentId 取 use.id **尾部时间序段+短哈希**（前 4 位是协议固定前缀必撞号，P1-4）；iterNum=各自循环轮数
- **UI**：动态区每运行中子代理恒 1 行；超高度预算压缩为合计行；结束后随本轮 commit 进 Static；onWarn 转发告警中心（带 description 前缀）、onActivity/onIter **不配**（不与父抢 ActivityBar/StatusBar）
- **顺带修**：stop 谎报防御（'end' 但有 tool_use 也继续喂结果）
- **（v1.2）todo 工具**：`todo(todos)` builtin 静态注册（无动态父要素，与 task 的装配期工厂成对照）；**全量替换语义**（每次写入完整清单，两家同构）；readonly:true（对话内状态无外部副作用——并行免确认）；**无独立 Store——状态即消息**（渲染读 tool_use input；rewind 投影跳过旧清单、/history 恢复重放消息，一致性免费）；transcript 内联渲染（摘要行 + 展开逐项，ASCII 状态符防 ambiguous 宽度错位）；system 指引行 + 防漂移测试同步
- **（v1.3）主循环插话**：忙碌态输入框保持激活（现状 `inactive` 含 runningRef 一并放开），Enter=**入队**（非立即 submit）；**双时点投递**——步间（loop 迭代顶部拉取 `pollUserInput` 回调，追加 user 消息，模型下一轮请求即见）+ 轮末兜底（runLoop settle 后队列有剩余自动组下一轮 submit）；排队项紧贴输入框 dim 单行显示（不占动态区高度预算），Ctrl+U 清空；Ctrl+C 语义不变（中断当前轮，**队列保留**并轮末续投——CC 同款"停当前不停插话"）；注入消息是普通 Message——落盘/恢复/rewind 零特殊处理

**不做**（后置）：子代理运行中插话/wake（harness inbox 形态——**注意与 v1.3 主循环插话分维度：给运行中子代理塞消息仍不做，"跑完即返"不变**；主循环插话在子代理整轮返回后的下一迭代边界注入，模型据此调整方向——这正是"有问题让主进程提问"的天然路径）、外部 CLI 子代理（`runtime:'external'` 接口位预留不做——注意与 type 参数分维度，P2-2）、后台 run_in_background（M10 P3 之后再合，合并时统一 task_output/task_stop 的 TaskRegistry 命名语义——M10 后台进程与 M11 子代理两语义，P2-4）、用户自定义 agent 定义文件、task_id 续接同一子会话（opencode 特性，P2-8a）、plugin `agents` 组件与 SubagentStart/Stop hook（观察区原位）。**（v1.2）todo 侧不做**：activeForm（CC 有——叙述位给 spinner 显示，ECode 无此 UI）/ priority（opencode 有——ECode 无优先级渲染位）/ 持久 Store 与常驻面板（StatusBar 当前任务显示——需要时再加"扫投影最后 todo input"的派生纯函数）/ 多清单与子代理独立清单（禁配即无此需求）。**（v1.3）插话侧不做**：自动打断（CC `hasInterruptibleToolInProgress` 机会性 abort——中断仍是用户显式 Ctrl+C，自动打断具破坏性且意外）/ 斜杠命令排队（忙碌态 `/xxx` 直接提示"运行中暂不能执行命令"，安全命令白名单后置）/ 插话带图片 blocks（v1 文本，blocks 通道随需）/ 队列多轮拆分（多条合并为一条注入，逐条独立成轮后置）。

## 1. 核心形态与三处关键设计

### 1.1 基本形态：task 工具内嵌 runLoop 新调用

```
父：TuiApp.submit ──► runLoop(messagesRef.current, input, optsA)      ← 主循环
                            │ LLM 单消息发 N 个 task_use
                            ▼ readonly 并行池 Promise.all（免确认）
子×N：task.execute ──► runLoop([], prompt, optsBᵢ) ──► 取最后 assistant 文本
                            │                        作 tool_result 回父循环
                            ▼
                     父循环下轮看到 N 个结果继续
```

### 1.2 注入通路：makeTaskTool(deps) 工厂（审阅 P0-3 修正）

Tool 接口 `execute(args, ctx: ToolContext)` 的参数面（cwd/signal/onBeforeWrite/sandbox）**够不到** optsB 需要的 provider/providerReq/system/confirm/logger/quality——且 providerReq 随 /model 切换、confirm 是 TuiApp 闭包、signal 每轮新建 AbortController，全是动态值，静态 import 必 stale。解法：

- `makeTaskTool(deps: SubagentDeps): Tool` 工厂在 **TuiApp/cli 装配时**创建并 register（deps 里全是 getter 或引用，如 skillRegistry 的模块级单例模式 + askUserBridge 的 set 桥模式的合体）
- `SubagentDeps = { getProviderReq(), getProvider(), makeConfirmQueue(), logger, qualityFactory, checkpoint?, cwd, registry（主，供裁剪现取）, ctxWindow... }`
- BUILTIN_TOOLS 单一事实源与防漂移测试同步调整（注意 v1.4：ask_user 实际是**静态数组 + 模块级 set 桥**拿动态 UI——task 不走此路，装配期工厂直接 register，防漂移测试按"注册表实际含 task"断言而非 BUILTIN_TOOLS 数组）

### 1.3 confirm 串行队列（审阅 P0-1 修正）

`ActiveState.confirm` 是**覆盖式单槽**（TuiApp setActive 直接覆盖，无排队）——父循环靠"副作用串行"天然不并发；并发子代理的 confirm 并发到达时后者覆盖前者，前者 resolve 闭包丢失 → Promise 永挂 → 父 Promise.all 死锁。解法：装配层包串行队列——

```ts
// makeConfirmQueue：askUserBridge queue 链同款
const queueConfirm = (use) => (queue = queue.then(() => parentConfirm(use), () => parentConfirm(use)))
```

子代理 optsB 的 confirm 全走 queueConfirm；父轮内的 task 已在并行池、父自己的副作用工具在串行池——两者也可能并发（父轮 = task + 混排副作用工具），父 optsA 的 confirm 一并换 queueConfirm 最稳（行为不变：单请求时队列深度 1）。

### 1.4 超窗策略（审阅 P0-2 修正）

子代理不配 `onBeforeRequest` 时，CONTEXT_TOO_LONG（recoverable:false）直接 throw 炸出子 runLoop → invokeTool re-throw → 父 Promise.all reject → 父走自己的压缩兜底（父 messages 可能不长，无意义）→ LLM 再发 task → 循环烧钱。解法：**子代理配独立压缩链**——`makeOnBeforeRequest(独立 orchestrator + summarize 策略, provider, providerReq, 子 system, { history: NoopHistoryStore, onCompacted: no-op, ... })`：boundary 只进子代理内存 messages（D7 语义不变）；orchestrator 实例独立（consecutiveFailures 熔断不共享，同 P1-2 原理）。task.execute 另 catch CONTEXT_TOO_LONG 兜底转可读 is_error（"子代理上下文超限，任务过大，建议拆分"——双保险）。

### 1.5 optsB 构造总表（makeSubagentOpts(parentDeps, agentId, type)）

| 项 | 来源 | 说明 |
|---|---|---|
| messages | `[]` | prompt 作首条 user（loop 的 userInput 参数即 prompt） |
| provider/providerReq | deps getter 现取 | 同模型同配置 |
| tools | **裁剪版 Registry（现取现建）** | 主 registry `list()`（**接口扩展：ToolRegistry 加 `list(): Tool[]`**，审阅 P1-3——specs() 不含 readonly/execute 无法重建）排除 task + ask_user + todo（v1.2：清单主权归主 agent，§6.4）；快照与运行期注册的漂移可接受（MCP 重连后新工具下个子代理才见，调用失败转 is_error 自纠） |
| history | NoopHistoryStore | 不碰主会话 |
| system | **骨架 + 项目级 ECODE.md 段**（P2-1 采纳：子代理改代码需知项目规范；复用 instructions 加载器，只取项目级） | 见 §2 |
| callbacks.onText/onToolStart/onToolResult | 喂进度缓冲 | 环形数组尾部窗（动态区行 + Ctrl+O 展开数据源）；**绝不 setActive** |
| callbacks.onUsage | 转发主 onUsage | 成本归并（注意 /cost"本轮"语义被并发稀释为最后到达者——文档化，P2-6） |
| callbacks.onWarn | 转发主 onWarn **带 description 前缀** | 告警中心数据源（重试/压缩/超时都进来）；不配=静默丢失（审阅 P1-6） |
| callbacks.onActivity / onIter | **不配** | 不与父抢 ActivityBar/StatusBar（运行可见性由子代理行承担） |
| confirm | **queueConfirm（§1.3 串行队列）** | 不再是"单槽排队"想当然 |
| signal | 父 signal | Ctrl+C 连子代理一起停（审阅验证链路成立） |
| toolCtx | 新构造 | cwd/signal 同父；onBeforeWrite **用父回调**（checkpoint 快照 + editedFilesRef 归主，父轮末统一 autoCommit——审阅 P1-1：autoCommit 只在父 afterTools） |
| afterTools | **剥离 autoCommit 的包装**：仅 quality.afterRound 回喂 + 警告转发 | 子代理用**独立 QualityGate 实例**（commands/runner/warn 三注入，廉价——审阅 P1-2：实例级熔断计数并发互踩） |
| onBeforeRequest/onCompacted | **独立压缩链（§1.4）** | 独立 orchestrator；onCompacted no-op |
| logger | 包装 logger 注入 agentId | §4 |
| maxIterations | 钳 min(父值, 25) | 防跑飞 |

**递归封顶**在裁剪 Registry 实现（不注入 task 即物理不可能递归）。

**返回契约**：execute 的 finally 里全量序列化子 messages 落 `~/.ecode/agents/<agentId>.jsonl`（P2-3：callbacks 逐条写缺工具入参与轮次边界，改 finally 全量——abort 路径也落盘）；返回最后一条 assistant 文本（无文本兜底指路 transcript 路径）；16k 截断；**超时自实现**（execute 内 AbortSignal.timeout(10min) 与父 signal 取或——loop 层不实施 timeout_ms，bash 自管同款，P2-7）。

## 2. 两层提示词模板（调研定稿）

**task 工具 description**（教主 LLM 调用纪律——防滥用主手段）：

```
把独立的子任务委派给并发子代理。子代理看不到当前对话，prompt 必须自包含。

何时用：大范围搜索/多文件调研归纳/互相独立的并行子任务/不需要过程细节只要结论的工作。
何时不用（直接自己做更快更准）：读指定文件、找特定定义、2-3 个文件内的小改动、
  需要当前对话上下文的任务。

写 prompt 像给刚进门的同事 briefing：目标与原因、涉及文件/目录、验收标准、期望返回格式。
禁止"根据你的发现修 bug"这类委派理解的写法——写清文件路径与具体要改什么。
明确告知是写代码还是只调研。并行任务给不同子代理时，让它们碰不同的文件。
```

**子代理 system 骨架**（type 两种——参数名用 `type`，进程形态预留位另名 `runtime`，P2-2）：

- **general（全能型）**：`你是独立子任务代理，prompt 是你的全部背景，缺信息用工具自查不要猜。只做 prompt 说的事。完成后只输出结论：结果/关键发现/产物路径三段——调用者只拿这段文字，过程细节不会被看到。你不能向用户提问；有疑问就把不确定点写进结论。你不能派子任务。` + 通用行为准则（广搜窄读/不建文档文件——CC SHARED_GUIDELINES 同款）+ **项目级 ECODE.md 段**
- **explore（调研型）**：general 骨架 + **只读宣言**（无写类工具，尝试会失败——CC Explore 同款）+ 返回绝对路径 + 彻底度跟随 prompt（quick/medium/very thorough）

task 参数：`{ description: 3-5 词, prompt: 任务书, type?: 'general' | 'explore'（默认 general） }`。

**与 M10 后台任务的工具面区分（v1.4 补）**：M11 上线日模型工具面同时存在 `task`（子代理）与 `task_output`/`task_stop`（后台命令轮询）——description 末尾必须加一句"本工具阻塞至子代理返回结论，无 task_id/task_output 轮询——那是 bash run_in_background 后台命令的机制"（P2-4 的命名统一等合并，教学歧义上线即存在，不等）。

## 3. UI 展示（S4 定稿）

- **折叠态（动态区）**：每运行中子代理恒 1 行 `⏺ 「重构成因」 · grep src/loop.ts…`（description + 最近工具活动，进度缓冲尾部）；**运行中子代理行上限 3**（v1.4 定值——超屏预算体系 2026-08-18 拍板不建，合计行不再引用"高度预算"概念）：超 3 折叠为 `⏺ 5 个子代理运行中（重构成因 · 依赖盘点 · 测试梳理…）` 合计行
- **展开（Ctrl+O 体系内）**：进度缓冲尾部滚动窗（最近 ~10 行 + `⋯ 共 N 行`——高度感知封顶）
- **结束**：随本轮 commit 进 Static——ToolGroupView 里 task 条目展开显示返回结论全文；transcript 路径在工具结果尾部（用户可 cat 全程；description 教 LLM 不主动读——CC "output_file 但别偷看"的 ECode 版）
- **告警中心**：启动/结束/超时/失败各行 info/warn（onWarn 前缀转发 + task 级事件）

## 6. Todo 任务清单工具（v1.2 扩入）

> 2026-08-18 用户拍板并入。M1M2 审阅报告曾列为 P2 差距项（CC/opencode 标配、ECode 缺），一直未排期；本次一手核对两家实现（CC TodoWriteTool / opencode todowrite）确认**同构度高**：全量替换语义 + 三态 status + transcript 内联渲染，差异只在状态归宿（CC per-agent 内存 store / opencode per-session DB），而两者的动因（持久 UI / 事件桥）ECode 均不存在。

### 6.1 形态：builtin 静态工具 + 全量替换

- **`todo(todos)`**，BUILTIN_TOOLS 静态注册（无动态父要素——与 task 的装配期工厂成对照，`src/tools/builtin/todo.ts`）；**readonly:true**（写的是对话内清单，无文件/网络副作用——并行池+免确认）
- **schema（AJV 扁平化，遵循工具接口约束）**：`{ todos: [{ content: string(1..200), status: 'pending'|'in_progress'|'completed' }] }`，maxItems **20**（每项渲染 1 行，20 行已在活动区高度预算内——超限即 AJV 拒绝转 is_error 自纠）；不加 activeForm/priority（见"不做"）
- **全量替换语义**：每次调用写入完整清单（非增量修改）——LLM 漏项/重排天然自洽，无需 diff 协议；两家同构
- **返回**：确认文本 + 轻教学（CC 同款："清单已更新（3/5 完成）。继续用清单跟踪进度，完成一项立即更新。"——tool_result 是模型下次看到的反馈位，顺带维持使用纪律）

### 6.2 状态归宿：消息即状态，无独立 Store

- **不建 TodoStore**：当前清单 = 投影内最后一次 todo 调用的 input。渲染直接读 tool_use input（ToolCallView 本就拿到 input 渲染其他工具）；**不存在第二个真相源**
- 由此免费获得两个一致性：**/rewind**——区间跳过投影后，旧清单调用自然不可见（模型视角回退到更早清单，与用户视角一致）；**/history 恢复**——消息重放即状态恢复（tool_use input 本就进会话 JSONL，零特殊处理，对照 ImageBlock 需要 _path 转译）
- CC 的 per-agent store / opencode 的 DB store 动因分别是持久 UI 面板与事件桥广播，ECode 均无——YAGNI。未来若要 StatusBar 常驻当前任务，加一个"扫投影消息取最后 todo input"的纯派生函数即可，不动本设计

### 6.3 渲染：transcript 内联清单

- **摘要行（折叠态/组内）**：`todo · 3/5 完成`（完成数/总数，进行中项标题）
- **展开**：逐项一行，状态符**只用 ASCII**——`[x]` completed / `[->]` in_progress / `[ ]` pending（ambiguous 宽度教训：中文终端下 ☐✔▸ 类符号宽 2 vs Ink 算 1 必错位）；in_progress 行着 theme 强调色
- 渲染挂在 ToolCallView 既有分发上（todo 特化分支），随本轮结束进 Static，无动态区常驻位（不与子代理行/高度预算抢地盘）

### 6.4 指引行与子代理禁配

- **system.ts 工具选择指引**加一行 + `tests/core/system.test.ts` 防漂移同步（M10 教训：task_output/task_stop 漏指引行就是防漂移测试抓的）。指引要点：**3 步以上多步任务才建清单**；每完成一项立即更新；同一时间只保持一项 in_progress；全部完成后整体标 completed 收尾；单步任务/小改动/纯问答不建
- **工具 description** 教使用纪律（防滥用主手段，与 task 工具同风格）：何时不该用清单 + content 写法（短句概括动作对象，不复述上下文）
- **压缩交互（v1.4 补审阅 F4）**：消息即状态在 rewind/恢复之外还有第三种投影变换——**压缩**：boundary 摘要掉旧 todo tool_use 后若 tail 无新调用，模型"忘了清单"（CC 的 store 方案天然免疫）。修法：summarize 策略提示词加一句"对话含 todo 清单时，摘要必须包含当前清单各项与状态"；P6 加压缩后清单可见性测试
- **子代理禁配**：裁剪排除清单加 todo（§1.5 已同步）——理由：清单是主 agent 的计划主权（子代理只有一段任务书，无多步规划面）；子代理 transcript 独立，其清单无人可见（纯浪费 token）；并发子代理写共享清单必冲突。opencode 同款（general 型 deny todowrite）；CC 现版本虽允许（per-agent state 消除了冲突面），但其子代理清单同样无 UI 通道，ECode 取更紧的 opencode 口径

## 7. 主循环插话（v1.3 扩入）

> 2026-08-18 用户拍板（原 v1"不做"项转正，仅主循环侧）。动机：M11 子代理单任务最长 10 分钟、bash/压缩/quality 轮次也常有数十秒——期间用户发现方向错了或想补充上下文，现状只有"干等"或"Ctrl+C 全弃"（`TuiApp.tsx` 忙碌态 `inactive` 含 `runningRef.current`，输入框完全锁死）两个劣选。

### 7.1 三家一手对照（本节设计依据）

| 家 | 形态 | 关键机制 |
|---|---|---|
| CC | **排队 + 机会性打断** | `handlePromptSubmit.ts`：忙碌态 submit 一律 `enqueue`；仅当在跑工具全部 `interruptBehavior:'cancel'` 时额外 `abort('interrupt')` 让排队消息立即落地（query.ts 跳过中断说明消息——排队消息本身就是上下文）；Esc=纯中断，中断后队列照常续投 |
| deepseek-harness | **双时点收件箱** | `agent/inbox.ts`：`next-step`（步间注入——steering，运行中循环在步边界 claim，模型边跑边见）与 `next-turn`（轮末投递）两个 target；持久化事件流，replay-once |
| opencode | 会话级消息队列 | busy 时消息入 session 队列，空闲逐条消费 |

ECode 取 **harness 双时点为骨架 + CC 的"中断不弃队列"语义**：步间注入是主路径（模型在多轮任务中途即可看到插话调头，省掉整个走偏的后半程），轮末兜底覆盖"turn 在两次注入点之间结束"的场景。

### 7.2 双时点投递

```
用户 Enter（忙碌中）──► 队列（TuiApp ref）──► ①步间：loop 迭代顶部（iter≥2，下一轮 LLM 请求前）
                                                  pollUserInput() 拉取 → 追加 user Message → 模型即见
                                          └──► ②轮末：runLoop settle 后队列有剩余 → 自动组下一轮 submit
```

- **心脏改动一处（additive 可选回调）**：`LoopRunOptions` 加 `pollUserInput?: () => string | null`——迭代顶部拉取，返回非空即以首条 user 消息同构的 append 路径追加（无 feature 条件分支，与 onBeforeRequest/afterTools/userBlocks 同类分支面模式）。**子代理 optsB 不配此回调**（插话目标是主循环，子代理照旧跑完即返）
- **注入位与 quality 回喂的顺序**：tool_result（user）→ afterTools 回喂（user）→ 插话（user）——插话拉取发生在下一迭代顶部，天然排在回喂之后；连续多条 user 消息双协议均合法（翻译层原样 append）
- **多条合并**：队列多条一次性拉取合并为一条（`\n\n` join）——一次模型响应消化；逐条独立成轮后置（见"不做"）
- **消息即状态红利**：注入的插话是普通 Message——HistoryStore 落盘、/history 恢复、/rewind 区间跳过全部零特殊处理（与 todo 同一设计哲学，无第二真相源）

### 7.3 TUI 与键位

- **输入框**：忙碌态保持激活（`inactive` 去掉 `runningRef.current`；overlay/confirm 仍独占——ConfirmPrompt 弹窗期间本就无输入焦点，不冲突）；placeholder 改"（处理中，Enter 排队插话，Ctrl+C 中断）"
- **排队显示**：紧贴输入框上方 dim 单行 `已排队：改用方案B（Ctrl+U 清空）`，多条时 `已排队 3 条（Ctrl+U 清空）`——**不占动态区高度预算**（不与子代理行/todo 展开抢地盘）；投递后消失（内容转为正常 user 消息进轮内渲染）
- **Ctrl+U**：清空未投递队列（readline 清行习惯键位；防"排了又后悔"）
- **Ctrl+C 语义不变且队列保留**：中断当前轮 → settle → 轮末兜底看到队列 → 自动续投（CC 同款"停当前不停插话"：排了"改用方案B"再 Ctrl+C，新方向立即开跑）。想全停：先 Ctrl+U 再 Ctrl+C。此组合语义写进 placeholder 之外的 /help 与自测用例

### 7.4 边界与语义细则

- **斜杠命令**：忙碌态 Enter 且文本以 `/` 开头 → 提示"运行中暂不能执行命令"（不排队不执行）；安全命令白名单后置
- **图片插话（v1.4 修正：随 M10 真机修复批 v2 标签形态免费支持，废弃原"禁止排队"设计）**：v2 形态下 `[图片#N]` 标签即普通输入框文本——插话文本含标签照常排队，轮末自动续投走同一 submit 通道按 v2 文本引用剪枝组装 blocks（删标签=删图同语义）；P7 加"插话标签随续投组装 blocks"测试锁定。原 v1"pendingImages 则不排队"基于已退役的附件行形态，作废
- **abort 后队列续投的自证性**：续投走轮末兜底通道（非新增路径），与正常轮末排队同代码
- **UserPromptSubmit hook 覆盖插话（v1.4 补：原设计漏——hook 分发在 TuiApp.submit 内，loop 内部 append 会绕过，M9-P0 接的线被撕开）**：Enter 入队时（TuiApp 侧）异步过 hook dispatch——block 则提示"插话被 hook 拦截"不入队，additionalContext 拼接进排队文本；pollUserInput 保持同步签名不动（loop 侧无法 await）
- **confirm 弹窗期间**：无输入焦点（弹窗独占），不产生排队；弹窗 resolve 后恢复
- **并发子代理期间**：主循环 await 在 executeTools 内，插话在子代理整批返回后的下一迭代顶部注入——**不会**打断子代理（与"跑完即返"一致），模型在子代理结果+插话齐备的下一轮里调整方向
- **流式期间不可达（v1.4 写明防误解）**：插话只在迭代顶部注入——模型长流式回复进行中（数十秒）排队等待至该轮流完，下轮请求才见（三家同款已知边界）
