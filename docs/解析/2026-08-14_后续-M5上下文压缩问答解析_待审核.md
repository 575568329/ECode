# ECode M5 上下文压缩问答解析

## 0. 先建立心智模型：一份数据，两种读法

整个 M5 压缩只用一张图就能讲清：

```
              ┌────────────────────────────────────────────────┐
              │ 唯一存储：~/.ecode/sessions/<id>.jsonl          │
              │ append-only：全部 Message + boundary 行         │
              │ （原始对话一个字不丢；压缩只加标记行，不删内容）  │
              └────────────────────▲───────────────────────────┘
                                   │ 每条消息/边界追加写入
Memory  messagesRef: HistoryLine[] ─┤（同一份的内存工作副本）
              │
              │ 读时变换（视图不落盘，现算现用）
              │
   ┌──────────┴──────────┐
   ▼                     ▼
用户读法（UI）          LLM 读法（投影）
messagesToCommitted()  buildContextMessages()
全量渲染 + 压缩点标记    [summary + tail] 子集喂模型
```

**一句话心智模型：history 是唯一真相（append-only 永不删改），用户读全量、LLM 读投影；「压缩」不是删除操作，只是追加一行标记 + 改变投影的输出。**

后面所有问答都是这张图的展开。

## Q1：什么时候触发压缩？是对话结束后吗？

**不是对话后——是「每轮请求前」的预防性检查。**超限的请求发出去也是被 400 拒，白跑一趟；发出前压掉，请求必成功。

### 触发判定（hook.ts）

```
每轮 provider.run 前（loop.ts 调 onBeforeRequest hook）
  │
  ├─ trigger 判定，三个来源：
  │    pressure（常规）──── 估算投影 context > 阈值？
  │    overflow（兜底）──── API 已被 400 拒 / 强制
  │    manual（手动）────── /compact（同时重置熔断计数）
  │
  └─ 阈值公式（pressure 用）：
       ctxWindow      = resolveContextWindow(model)   ← models.dev 四级 fallback
       effectiveWindow = ctxWindow × 0.9               ← 留 headroom
       threshold      = effectiveWindow − 20000        ← 留 land-the-plane 空间
       estimated      = estimateContextTokens(system, 投影)  ← bytes/4 估算
       GLM-5（200k）：eff 184k → 阈值 164k
```

### 三条路径对照

| 路径 | trigger | 时机 | 特点 |
|---|---|---|---|
| 自动（主路径）| `pressure` | 每轮请求前，估算超阈才压 | 预防性 |
| 400 兜底 | `overflow` | API 拒了之后 | 救场：压缩后重试，**不走退避**（loop.ts 专属分支）|
| 手动 | `manual` | 用户敲 `/compact` | 强制绕过阈值 + 重置熔断 |

切 model（如 1M→200k）**不自动压缩**——只检测 + banner 提示风险，压缩是用户决策（`/compact`）。

## Q2：给用户看的数据和给 LLM 的数据是分开记录的吗？

**不是。只存一份，LLM 那份根本不落盘——是每轮现算的派生视图。**这就是「投影分离」。

| 形态 | 给谁 | 存在哪 | 生命周期 |
|---|---|---|---|
| **History**（`HistoryLine[]`）| 源头真相 | jsonl + messagesRef | 永久（append-only）|
| UI 视图（`CommittedItem`）| 用户 | 不存，React state | 渲染期 |
| Context 投影（`Message[]`）| LLM | **不存** | 一次请求的生命周期 |
| 序列化转写（分批摘要时）| 摘要 LLM | 不存 | 一次摘要调用的生命周期 |

**为什么不存两份**：两份就要同步——压缩改 LLM 份、新消息追加两份、恢复时对齐……全是 bug 源。单源 + 读时变换：

- 永无不一致（投影永远从 history 派生）
- **恢复零成本**：`restoreFull` 读全量刷 UI；LLM 份不用恢复——下轮请求时投影函数照着已存的 boundary 现算，天然是压缩后的子集 → **恢复历史会话不触发压缩**（M5 验收关键项）
- 审计/revert 天然成立：原文从没被删过

## Q3：压缩后文件里怎么区分？被压缩的数据会被忽略吗？

**会忽略，但机制是「位置性跳过」，不是逐条识别标记。**旧消息本身没有被打任何标记。

### 压缩后的文件长这样

```jsonl
{"role":"user","content":[...]}                    ← msg 0 ┐
{"role":"assistant","content":[...]}               ← msg 1  │ 旧消息原样躺着
...（msg 3..41，没动，也没被打标记）                  │ 被压缩区
                                                   │
{"compact_boundary":true,                          ← ★ 标记行（唯一的标记）
 "summary":"## 目标\n- 重构auth...",                 │   摘要全文存在这
 "tailStartIndex":42,                              │   保留区起点坐标
 "preTokens":95234}                                │   压缩前 token（审计）
                                                   │
{"role":"user","content":[...]}                    ← msg 42 ┐ tail 原文
...（之后的新消息继续追加）                            ┘ 保留区
```

区分方式就一条：行里有 `"compact_boundary": true` 字段（`isBoundary()` 类型守卫）。标记是**独立的一行 + 坐标**，不是给旧消息逐条打 `compacted:true`——那要改写旧数据，破坏 append-only。

### 投影的三个动作（context.ts `buildContextMessages`）

```
① 跳过：msgs.slice(tailStartIndex) 按位置取——0..41 落在取值范围外，自然被忽略
② 顶替：boundary 里存的 summary 包装成一条消息，顶在投影最前（前缀「[此前对话已压缩]」）
③ 保留：tailStartIndex 之后原文逐字保留
（boundary 行本身被滤掉——JSON 标记行绝不发给 LLM）
```

边界细节（都是审阅修出来的）：`tailStartIndex` 双向钳（防损坏数据炸投影）；summary 消息 role 避开与 tail[0] 相同（连续同 role 部分端点 400）；tail 起点若含孤立 tool_result，`preserveToolPairs` 往前扩到纳入配对 tool_use（协议硬约束，切断对 → 400）。

## Q4：每次压缩，上一次的标记会被删除吗？

**永远不会删——append-only 是存储层铁律。**旧 boundary 留在文件里，只是变「沉默」。

```
第一次压缩后：[ msg0..41 ][ boundary1 ][ msg42..60 ]
第二次压缩后：[ msg0..41 ][ boundary1 ][ msg42..60 ][ boundary2 ][ msg61..75 ]
第三次压缩后：[ ...boundary1... ][ ...boundary2... ][ boundary3 ][ msg76.. ]
                 ↑ 不删，永远躺着                        ↑ 投影只认最后一个
```

### 旧 boundary 的三种待遇

| 读者 | 待遇 |
|---|---|
| LLM 投影 | **沉默**：倒序只找最后一个 boundary；旧的被滤掉，其覆盖区域整个落在新 tailStartIndex 之前 |
| UI | 每个 boundary 各生成一个 `⇕ 已压缩（上方 N 条）` 标记——用户看到完整压缩史 |
| 审计/恢复 | 全量保留 |

### 旧摘要的内容丢了吗？——没有，被「滚动」了

```
第二次压缩时：
  previousSummary = 取 boundary1.summary（旧摘要）
  摘要 prompt = 模板 + 「用上述内容更新锚定摘要：保留仍成立的/删除过时的/合并新事实」+ 旧摘要
  → LLM 合并出 boundary2.summary
  head[0] 若是旧 summaryMsg → 剥掉（避免旧摘要同时出现在 system 和对话体，双份表示会漂移）
```

信息链：**boundary1.summary → 合并进 boundary2.summary → 合并进 boundary3.summary**——行永不删，摘要语义滚动前进，不产生「摘要的摘要」（逐级失真）。

## Q5：手动 /compact 和自动压缩一样吗？

**操作同一份数据（messagesRef 同一引用），链路不同、trigger 不同。**

### /compact 入口链路

```
输入 /compact 回车
  → InputStream 斜杠补全 → CommandRegistry（返回 { action: 'compact' }）
    → TuiApp onCommand → compactManual()
        ├─ 空对话 →「（无可压缩对话）」
        ├─「正在压缩对话...」
        ├─ hook(messagesRef.current, 'manual')   ← manual：强制 + 重置熔断
        └─ 成功/未压缩/失败 → 三段文案
```

自动路径：`submit() → runLoop(messagesRef.current) → loop 每轮 onBeforeRequest(messages)`——**同一个数组引用**，boundary 追加后两边立即可见。磁盘 jsonl 不是压缩的读取源（只写不读）；`/history` 恢复时才从它读全量灌回。

### 差异表

| | 手动 /compact | 自动 |
|---|---|---|
| trigger | `manual`（强制 + 重置熔断）| `pressure`（超阈）/`overflow`（400 兜底）|
| 压缩后 | 结束，等下条消息 | 重新投影**立即**发请求 |
| UI 提示 | 正在压缩 → ✓ 已压缩 / 未压缩 / 失败 | 同（onCompacting/onCompactFail 配对）|
| signal | 可中断 | 可中断 |

UI 提示已对称（含压缩中提示、失败提示、对话流内 `⇕` 标记）。

## Q6：切到小窗口模型（如 600k→200k）怎么压？

**分批 map-reduce。**这是 M5 后期补的能力——此前单发摘要请求自己就会超窗（head 592k > 摘要窗口 200k），死锁，只能 /clear。

### 分批流程（summarize.ts）

```
head 超批预算？
  ├─ 否 → 单次摘要（结构化 messages 直发；日常渐进压缩全走这条）
  └─ 是 → ① serialize 转写成纯文本副本（tool result 超 2000 字符截断；
             超大单块头尾 50/50 中间 [truncated]——codex 式）
         ② 减法批预算组批：window×0.9 − 4096输出 − 8k buffer − 1.5k system
         ③ map 并行（Promise.all 保序），批首作用域声明：
             「第 i/N 段 + 不要写总结性结尾——对话在本段之后仍继续」
         ④ 批 400(CONTEXT_TOO_LONG) → 对半二分重试（depth≤4，仅限「太长」类错误）
         ⑤ reduce：各批摘要（时序标号）+ previousSummary 锚定合并
         ⑥ 校验：summary+tail+system 必须装进新窗口，否则再摘一轮
```

### 真机基准（800k token → GLM-5 200k）

```
串行 103.3s：5 批逐个 12-23s + reduce 10s
并行  58.3s：5 批并发（最慢批 43s 是瓶颈）+ reduce —— 快 44%，零 429
每批估算 170k vs 真实 usage 145k（保守 17%，安全方向，零二分重试）
摘要 815 字符，正确提取文件路径/决策/错误/下一步（结构化 5 段模板）
```

### 批数与边界

批数动态：`head ÷ 批预算`（600k→4 批、800k→5 批、1M→6 批）。head 天然被**上个模型窗口**封顶（当前生态 ≤1M → ≤7 批）。理论边界（reduce 自身装不下）需 16M+ head，不可能撞到；真到那天加一层**层级 reduce**（先每 10 批合并再合并——LangChain collapse / LlamaIndex tree_summarize 同构），架构不用动。

并行选择依据：收益实测（-44%）、成本一行（Promise.all）、风险有兜底（429 → 降级 → 熔断 → 手动重置）、批数天然封顶。真机若频发 429 再加并发限制（YAGNI，不预付）。

## Q7：序列化是什么？为什么不影响 LLM 理解？

**序列化 = 把结构化 Message[] 转写成带标签的纯文本再发摘要请求**（`[User]:` / `[Assistant]:` / `[Assistant tool call]: name(json)` / `[Tool result]:`）。我们是**双形态**：单次路径发原生结构化（质量 + prompt cache），只有分批时转文本（安全切分）。

### 为什么分批必须序列化

| 切在结构化数组上 | 后果 |
|---|---|
| 切在 tool_use/tool_result 中间 | 配对断裂 → API 400 |
| 某批首块是 assistant 的 tool_result | 首条必须 user → 部分端点 400 |
| role 连续 | 部分端点 400 |

文本化后这些协议约束**全部消失**——每批就是一条 user 消息，怎么切都合法。且「调用→结果」在文本里物理相邻，语义关系靠相邻性表达，对读者反而更直观。

### 为什么不影响理解（三层原因）

1. **底层真相：LLM 从没见过「结构」**——API 服务端在到达模型前就把 messages 套 chat template 拼成纯 token 序列了。role 靠模板标记（`<|user|>`）还是文本标签（`[User]:`）表达，对模型只是 token 不同，没有本质区别。
2. **训练语料里遍地都是**——「名字: 内容」是论坛/issue/聊天记录里最常见的对话形态，模型见过千万次；四个标签本身就是自解释的自然语言。
3. **任务是「读剧本」不是「演对手戏」**——原生形态隐含「你在参与对话（接话）」，转写形态隐含「你在读记录（总结它）」。摘要本来就不该接话，后者框架反而更准。

**丢的恰好都是 API 记账不是语义**：tool_use_id、block 类型、精确轮次——摘要不需要。代价（诚实清单）：prompt cache 必 miss（claude-code 为省钱专门保留结构化）、标签注入边角、极小保真度差异——正是单次路径不用它的原因。

## Q8：token 怎么算准？——bytes/4 的教训

**chars/4 对中文低估约 4 倍**（1 汉字 ≈ 0.6-1.0 token，JS `length` 记 1 → 只估出 0.25）。渐进压缩靠 usage 锚定掩盖了；分批场景估算误差**直接决定批大小**（低估 = 必 400），是分批可用性的前提。

**修法：估算器改 `Buffer.byteLength/4`**（UTF-8 中文 3 字节/字 ≈ 0.75 token，恰好覆盖 GLM 区间；对齐 codex `approx_token_count`；ASCII 场景行为不变）。真机验证：170k 估 vs 145k 实，保守 17%。

时序上 usage 锚定防漂移：请求后的 `usage.input_tokens`（服务端实测）重锚基准，请求前的判定用「上轮精确值 + 本轮新增 bytes/4 增量」估算。估算错了还有两道网：二分重试（批级）+ 400 兜底（请求级）。

## Q9：关键设计决策浓缩表

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | **投影分离**（单源 + 读时变换）| 永无两份数据的同步问题；恢复不触发压缩 |
| 2 | **append-only + boundary 坐标**（不逐条打标）| 存储不可变，压缩 = 追加一行；审计/revert 天然成立 |
| 3 | **位置性跳过**（slice(tailStartIndex)）| 不改旧数据即可「忽略」它 |
| 4 | **滚动锚定摘要**（previousSummary 回喂更新）| 行不删而语义滚动，避免摘要套娃失真 |
| 5 | **每轮请求前触发**（非对话后）| 预防性：超限请求必失败，发出前压掉 |
| 6 | **双路径载荷**（单次结构化 / 分批序列化）| 装得下要质量+缓存，必须切要安全 |
| 7 | **分批 map-reduce + 并行** | 跨模型大落差唯一不丢内容的解；tree_summarize 理论背书 |
| 8 | **bytes/4 估算** | 中文场景 chars/4 低估 4 倍，分批必先修 |
| 9 | **三层自愈**（保守预算 → 二分重试 → 400 兜底）| 估算永远可能错，机制保证装得下 |
| 10 | **熔断 + manual 重置** | 连续 3 败停自动重试；用户明确要求时给机会 |
