## 核心问题与选型总览

| 支点 | 核心问题 | 选型 | 关键理由 |
|------|---------|------|---------|
| **9 子代理** | 怎么派「独立上下文的分身」？ | 递归 `runAgentStream`（换 system+tools 子集+空 messages），侦察兵模式（只回结论） | 复用核心循环（总纲 4.3 loop 不动）；CC 同构（递归 `query()`） |

| **9 防递归** | 怎么防子代理派子代理？ | 深度限制（默认 1）+ 子代理默认无 Task 工具 | 取 opencode 保守默认 + 双保险 |
| **10 协议** | 自己造协议还是用标准？ | **官方 `@modelcontextprotocol/sdk`**（v1.30.0） | 生态红利（白嫖 CC/Cursor 现成 server）；不自造 |
| **10 原语** | 三原语做哪些？ | **只做 Tools**，砍 Prompts（归 Skill）/Resources（后置） | YAGNI + 功能收敛 |
| **10 传输** | stdio 还是 HTTP？ | **阶段1 stdio → 阶段2 Streamable HTTP+OAuth** | 个人 CLI 起步 stdio；远程跟标准（HTTP+SSE 已废弃 2025-03-26） |
| **10 配置** | MCP 进 config 还是独立注册？ | **独立注册表 `~/.ecode/mcp/registry.json`** | 防「替换 config 连坐删 MCP」（ECode 独有决策，待审阅） |

| **12 事件** | 做多少事件？ | **6 核心**（SessionStart/End + UserPromptSubmit + Pre/PostToolUse + Stop） | YAGNI（CC 30+，80% 是协作/内部场景） |
| **12 安全** | hook 能放宽权限吗？ | **只能收紧不能放宽**；系统 hooks 代码注册强制叠加 | 权限 deny 是硬边界，hook allow 翻不了盘（CC 安全核心） |

## 第一部分：子代理（支点 9）技术选型

### 9-T1：递归 `runAgentStream` vs 独立 session 实体

| 选项 | 代表实现 | 优点 | 缺点 |
|------|---------|------|------|
| **A. 递归调用**（选） | CC `runAgent.ts:748-757` 递归 `query()` | 复用核心循环、零新基础设施、`runAgentStream` 天然可重入 | 子代理 session 不在 UI 独立可见（归支点 17） |
| B. 独立 session 实体 | opencode `task.ts:156` child session（`parentID`） | 子代理 session 可独立持久化/可观测 | 引入 session 父子链 + 新基础设施 |

**选 A 理由**：ECode 已有事件流解耦 + `runAgentStream(task, opts)` 接受 `system/tools/allow/permissionMode/denyRules/permissionGate` 注入——天然支持子代理，只需加 `tools` 选项（实施方案阶段 0）。子代理独立可观测归支点 17（M6+），一期不做。

### 9-T2：侦察兵模式（只回最终结论文本）

**选型**：子代理跑完，**只取最后一条 assistant 消息的 text** 回主代理，中间所有 tool_use/tool_result **不外泄**。

**理由**（双源佐证）：
- CC `agentToolUtils.ts:276-357` `finalizeAgentTool` —— 取最后一条 assistant 的 text blocks；空则向前回溯。
- opencode `task.ts:188` `result.parts.findLast(item => item.type === "text")?.text`。

**核心价值**：保主上下文经济。若回完整过程（子代理读 10 文件 = 10 轮 tool），主上下文被污染，子代理失去意义（详见 [方案解析 Q1](./M5-方案解析[待实现].md#q1子代理的本质是什么为什么侦察兵模式)）。

### 9-T3：子代理权限继承策略【⚠️ 重新讨论支点 9 已锁定决策，需用户拍板】

> **⚠️ 本节重新讨论支点 9 已锁定决策（[支点讨论记录](../功能方案/支点讨论记录[已完成].md) L661-663）**。原锁定 = **A**（继承全部规则，含 allow）；M5 阶段重新倾向 **B**（只继承 deny）。**这是方向反转，非细节待定，需用户明确确认**。审阅建议选 B（理由见 [审阅问题清单 F3](./M5-文档审阅问题清单[待审阅].md)）。选 B 则子代理需**独立 AllowList 实例**（不回写主）。

| 选项 | 代表实现 | 继承范围 | 严格度 |
|------|---------|---------|--------|
| **A. 继承全部规则**（支点 9 已锁定，L661-663） | — | 继承 denyRules + 已批准 allow | 中 |
| **B. 只继承 deny**（更严） | opencode `subagent-permissions.ts`（28 行） | 只继承 deny + external_directory，allow 子代理自决；额外强制 deny task/todowrite | 严 |
| C. 父模式直接覆盖 | CC `runAgent.ts:412-498` | 父 bypass/acceptEdits/auto 优先不可覆盖，否则 agent frontmatter 覆盖 | 灵活 |

**ECode 倾向**：取 B 的精神（**继承 deny 硬规则 + 人设 tools 收紧 + 默认不放行新危险操作**），但 ask 弹窗归主对话（子代理共享主 `permissionGate`，不让子代理自己弹）。allow 是否完全继承待用户拍板——倾向「不继承 allow」（更严，子代理每个危险操作都问主对话）。

> **请审阅**：A vs B 的严格度取舍。ECode 倾向 B（opencode 式），理由是子代理是「不可信的分身」（人设可被构造），给它最小权限最安全。

### 9-T4：防递归爆炸

**选型**：双保险——(1) 嵌套深度限制（默认 **1**，可配 `subagentDepth`，仿 opencode `task.ts:104-117`）；(2) 子代理工具表默认不含 Task 工具（仿 opencode 强制 deny `task.ts:139-172`）。

**对比**：
- opencode：深度 1 + 砍 Task 工具（双保险，**ECode 取此**）。
- CC：默认深度 **3**，Agent 工具在子代理中默认可用、仅深度受限时移除（软限制，较松）。

**选 opencode 式理由**：一期保守——一层就够（侦察兵模式），多层侦察（审查派实现）属进阶，需时再上调深度 + 放开 Task 工具（向 CC 式靠拢）。

### 9-T5：人设格式（`.ecode/agents/*.md` frontmatter）

**选型**：抄 CC frontmatter，**一期只做 5 字段**（YAGNI），完整 17 字段预留扩展。

| 字段 | CC（完整 17） | ECode 一期 | 说明 |
|------|--------------|-----------|------|
| `name` | ✅ 必填 | ✅ 必填 | lowercase+连字符唯一标识（**身份只由 name 决定**，不受文件名/子目录影响，CC 核实） |
| `description` | ✅ 必填 | ✅ 必填 | 何时派（主 LLM 据此自动委派）+ catalog 注入 |
| 正文（prompt） | ✅ 必填 | ✅ 必填 | 人设正文 |
| `tools` | 可选 | ✅ 可选 | 限定工具子集（收紧权限） |
| `model` | `'inherit'`/alias/ID | ✅ 可选 | 支点 22 模型路由前置 |
| `disallowedTools` | 可选 | ⏸ 后置 | CC: 先于 tools 应用 |
| `permissionMode` | 可选 | ⏸ 后置 | 一期继承主代理 |
| `mcpServers`/`hooks`/`skills`/`memory`/`effort`/`background`/`isolation`/`color`/… | 可选 | ⏸ 后置 | CC 完整 17 字段 |

> **🔴 核实纠偏**：CC 子代理 frontmatter **不存在 `glob` 字段**（早先假设有）。访问控制走 `tools`/`disallowedTools` + PreToolUse hooks，**不是** `glob` 文件模式。ECode 一期不做文件级访问控制（M4 path-guard 已护硬边界）。

**加载优先级（抄 CC `loadAgentsDir.ts:193-221`）**：built-in → user（`~/.ecode/agents/`，走 `resolveDataDir`）→ project（`.ecode/agents/`），后者覆盖前者。

## 第二部分：MCP（支点 10）技术选型

### 10-T1：用官方 SDK，不自造协议

**选型**：`@modelcontextprotocol/sdk`（**v1.30.0，2026-07-27 发布**，联网核实 npm）。

**精确导入路径（v1.30.0，区分大小写）**：
```ts
// Client
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";
// Server（ECode 是 client 角色，但 SDK 类型需 server 端）
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
```

**理由**：
- 生态红利：CC（`services/mcp/client.ts:7-38`）、opencode（`mcp/index.ts:6-17`）**都用官方 SDK**，不自造。自造=脱离生态、重复造轮子、协议演进掉队。
- ESM 友好：SDK 是 ESM，与 ECode 单包 ESM 架构契合。
- v2 拆包说明：SDK v2 拆成 `@modelcontextprotocol/server`/`client` 独立包，**原 `@modelcontextprotocol/sdk` 本身从未发过 2.x**——ECode 锁 v1.30.0（稳定单包）。

### 10-T2：MCP 规范版本与传输演进【联网核实】

**当前规范版本 = `2026-07-28`**（modelcontextprotocol.io，核实日期 2026-08-08）。HEADLINE 变化：移除 `initialize` 握手与 `Mcp-Session-Id`、引入 `server/discover` RPC、Multi Round-Trip Requests、header 路由、正式 feature-lifecycle 策略（SEP-2596）。

| 传输 | 引入/状态 | ECode 决策 | 依据 |
|------|----------|-----------|------|
| **stdio** | 本地首选（零网络开销） | ✅ **阶段1** | 规范 Architecture：「Local MCP servers that use STDIO typically serve a single MCP client... optimal performance with no network overhead.」 |
| **Streamable HTTP** | 引入 `2025-03-26`（替代 HTTP+SSE） | ⏸ **阶段2** + OAuth | 规范原文：「Streamable HTTP was introduced in protocol version 2025-03-26 as a replacement for the HTTP+SSE transport from protocol version 2024-11-05.」 |
| ~~HTTP+SSE~~ | **废弃自 `2025-03-26`**（SEP-2596 Deprecated） | ❌ **不做** | 规范原文：「deprecated since protocol version 2025-03-26... New implementations SHOULD NOT adopt it.」 |
| ~~旧 stdio session 机制~~ | `2025-11-25` 引入带 session 的 Streamable HTTP，session 机制 `2026-07-28` 移除 | — | 不影响 ECode（stateless 即可） |

> **🔴 核实纠偏**：早先以为「HTTP+SSE 在 2025-11-25 废弃」——**错**。废弃自 `2025-03-26`。`2025-11-25` 实际是引入带 session 的 Streamable HTTP（session 机制后在 2026-07-28 移除）。ECode 阶段2 直接做 stateless Streamable HTTP，跳过 session 机制。

### 10-T3：三原语取舍——只做 Tools

| 原语 | 规范定位（原文核实） | ECode | 理由 |
|------|-------------------|-------|------|
| **Tools** | "executable function, model takes an action"（`tools/list` + `tools/call`） | ✅ **做** | 核心，LLM 自动调 |
| **Prompts** | "reusable templates, user-controlled structured interaction"（`prompts/list` + `prompts/get`） | ❌ **砍** | 与支点 13 Skill 功能重复（手动触发的预设工作流）；`/mcp` 只做只读状态 |
| **Resources** | "data sources, application-controlled context"（`resources/list` + `resources/read`） | ⏸ **后置** | Tools 暂能替代（读数据用工具调） |
| ~~Sampling/Logging~~ | `2026-07-28` 起 **Deprecated** | ❌ | 规范已弃 |
| Elicitation | 当前活跃 client 原语（`elicitation/create`，MRTR 下发） | ⏸ 后置 | 一期不做 |

> **⚠️ 矛盾（待审阅）**：支点 10 早先「砍 MCP Prompts 归 Skill」，但 CC 的 `/mcp` 命令恰恰走 Prompts。ECode 一期砍 Prompts（Skill 替代），`/mcp` 只做只读状态查看。若未来发现 Prompts 有不可替代价值（如 server 端预设工作流无 Skill 时），再补。

### 10-T4：配置独立注册表（ECode 独有决策）【⚠️ 与支点 10 已锁定决策（L697-710）一致；如要重新讨论请显式说明】

**选型**：MCP 安装态存**独立注册表 `~/.ecode/mcp/registry.json`**，**不进 config.json**（VS Code 扩展模式）。

| 方案 | 代表实现 | 优点 | 缺点 |
|------|---------|------|------|
| **A. 独立注册表**（选，ECode 独有） | VS Code 扩展 registry | 替换 config 不连坐删 MCP；显式卸载才删 | 多一个文件、配置分散 |
| B. 进 config | CC `.mcp.json`（`config.ts:911-1024`）+ opencode `opencode.json mcp`（`core/v1/config/mcp.ts`） | 配置集中、与现有 config 一体 | 替换 config 不知情连坐删 MCP |

**选 A 理由**：MCP 若进 config，用户替换 config.json（换项目/拷贝覆盖）会**不知情地连坐删除 MCP**（用户本意不是删 MCP）。独立注册后，替换 config 不动 MCP。

> **请审阅**：A vs B。ECode 选 A（防连坐删），代价是配置分散。若用户更习惯 CC/opencode 式（mcp 块进 settings），可改。

### 10-T5：工具命名与适配

**选型**：命名空间 `mcp__{server}__{tool}`（抄 CC `mcpStringUtils.ts:50-52`）；适配成 ECode `ToolDefinition`。

**适配**（双源佐证）：
- CC：`MCPTool` 模板（`tools/MCPTool/MCPTool.ts:27-77`）+ per-tool spread 重写 name/description/call（`services/mcp/client.ts:1743-1804`）。
- opencode：`mcp/catalog.ts:42-83` `convertTool` 一函数——`inputSchema→jsonSchema`，execute 调 `client.callTool`，工具名 sanitize（非字母数字下划线横线转 `_`）。

**ECode 实现**：MCP `tools/list` 发现工具 → 适配 `ToolDefinition`（name=`mcp__server__tool`、description/parameters 来自 MCP、execute=callTool 闭包、**`dangerous=true`** 统一）→ 合并进 `runAgentStream` 的 `tools`。容错抄 opencode：`TolerantListToolsResultSchema`（坏 outputSchema 降级）+ `ToolListChanged` 热更新。

### 10-T6：OAuth 2.1（阶段2 远程）【联网核实】

**选型（阶段2）**：HTTP 传输**可选**鉴权；实现时 **SHOULD 遵循 OAuth 2.1**（规范原文，2026-07-28）。

**强制要求（规范原文）**：
- OAuth 2.1 + **Authorization Code + PKCE**（OAuth 2.1 唯一允许的公开客户端流程）。
- **RFC 8707 Resource Indicators**（`resource` 参数 MUST 同时出现在 auth 与 token 请求）。
- **RFC 9728 Protected Resource Metadata**。
- **RFC 9207 `iss` 校验**。
- 每请求 `Authorization: Bearer`。
- Discovery：MUST 支持 RFC 8414 AS Metadata 或 OIDC Discovery 1.0 之一。

> **🔴 核实纠偏**：早先以为「Dynamic Client Registration (RFC 7591) 当前支持」——**部分错**。DCR 已于 `2026-07-28` **废弃**，由 *Client ID Metadata Documents* (draft-ietf-oauth-client-id-metadata-document-00) 取代（PR #2858），DCR 保留向后兼容。ECode 阶段2 用 Client ID Metadata Documents，DCR 仅兼容回退。

**双源实证**：CC `services/mcp/auth.ts` ClaudeAuthProvider（authorization_code + refresh_token public client）；opencode `mcp/index.ts:806-942` + `auth.ts`（port 19876 callback + state CSRF + 0o600 token 文件锁）。

### 10-T7：stdio RCE 防护（安全红线）【联网核实】

**背景（CVE）**：OX Security 2026-04-15 披露 *"The Mother of All AI Supply Chains"*——stdio 传输「unsafe defaults」，用户输入未消毒直接流入 `StdioServerParameters`，造成 configuration-to-command 执行（design flaw baked into 官方 SDK 各语言）。影响：150M+ downloads、7000+ 公开服务器、~20 万脆弱实例、10+ CVE、6 平台线上 RCE 成功（LiteLLM/LangChain/IBM LangFlow）。Anthropic 称该行为"expected"，未改协议架构。

**ECode 选型**：主动补一层**命令 allowlist**（在 spawn 前 sanitize/校验 `command`）。

**对比**：
- **opencode 没做**——`command` 直接传 `StdioClientTransport`（`mcp/index.ts`），RCE 风险完全靠配置文件信任域承担。
- **CC**：配置级信任 + 权限审批。

> **🔴 核实纠偏**：早先以为「CSA Labs 推荐 Streamable HTTP 作为更安全趋势」——**不成立**。CSA Labs 页面 403 无法读取（存在性经搜索结果佐证）；OX Security + The Hacker News 推荐的缓解是 **SDK 级 manifest-only/命令白名单/沙箱/输入消毒**，**没有任何可读来源把「切到 HTTP 传输」作为缓解**。HTTP 的鉴权优势（OAuth 2.1）来自规范，不来自该 CVE。ECode 防护靠命令 allowlist，不靠「换传输」。

**进程清理**：stdio server 退出时递归 kill 子孙进程（opencode `mcp/index.ts:418-440` 用 `pgrep -P`，Windows 跳过——ECode 跨平台走 taskkill /T）。

## 第三部分：Hooks（支点 12）技术选型

### 12-T1：settings.json command hook（非 TS 插件 hook）

**选型**：CC 式 **settings.json hooks 块 + shell command handler**。

**关键发现（核实）**：opencode **未实现** Claude-Code 式 settings.json hooks（无 `hooks` 配置键、无 matcher/command/exit-code/JSON-decision）。opencode 的扩展点是 `packages/plugin/src/index.ts` 的 **TS 函数 `Hooks` interface**（`tool.execute.before/after`），由插件注册、`plugin.trigger` 串行调用、**就地 mutate output**——**不是 shell 脚本**。

| 方案 | 形态 | 配置 | 谁能用 | ECode |
|------|------|------|--------|-------|
| **CC settings.json hook**（选） | shell command | settings.json hooks 块 | 任何用户（写 shell） | ✅ |
| opencode TS 插件 hook | TS 函数 | 写 TS 插件注册 | 开发者（写 TS） | ❌ 后置借鉴 |

**选 CC 式理由**：贴近 CC 生态（用户已有的 hooks 配置可迁移），shell command 门槛低（用户不用写 TS）。

### 12-T2：只做 6 核心事件（YAGNI）

**选型**：`SessionStart / SessionEnd / UserPromptSubmit / PreToolUse / PostToolUse / Stop`。

**CC 实际 30+ 事件**（官方文档 plugins-reference，2026-08 实证）。**砍掉的理由**：
- `TeammateIdle/TaskCreated/TaskCompleted/SubagentStart/SubagentStop` → CC 多 agent/子代理可观测，ECode 单机（子代理可观测归支点 17）。
- `WorktreeCreate/WorktreeRemove` → CC worktree 隔离，ECode 不做。
- `Elicitation/ElicitationResult` → MCP elicitation，ECode MCP 一期不做。
- `Notification/MessageDisplay/PermissionRequest/PermissionDenied` → UI 通知，ECode 走事件流。
- `PreCompact/PostCompact/UserPromptExpansion/PostToolBatch` → 进阶，按需加。
- `FileChanged/CwdChanged/DirectoryAdded/ConfigChange/InstructionsLoaded/Setup` → 文件/配置监听，按需加。

### 12-T3：handler 类型——一期只做 command

**选型**：一期只做 **`command`** handler（shell）。CC 实际 handler（源码 `schemas/hooks.ts:176-189` 核实）：**4 种持久化**（`command` shell / `http` POST + url/headers/allowedEnvVars / `prompt` 注入为 prompt / `agent` 触发 agent）+ 1 种进程内 `callback`（不可持久化，`types/hooks.ts:210-226`）。`http`/`prompt`/`agent` 后置（YAGNI）。

> **🔴 核实纠偏**：早先写「CC 5 种 handler 含 `mcp_tool`」——**凭空捏造，已删**。CC 源码 `schemas/hooks.ts` discriminatedUnion 只有 4 种持久化类型 + 1 callback，**无 `mcp_tool` 类型**（审阅 F2 核实）。

### 12-T4：Pre/Post Promise-await + Stop 回调

**选型**：
- **Pre/PostToolUse**：`await opts.hooks?.preToolUse(...)`（仿 ECode 已有 `permissionGate`，`agent.ts:461`）——hook 要能 deny/改输入/暂停执行，必须等决策，不能 fire-and-forget。
- **Stop**：回调（hook 返回 `stopHookContinue` 控制），抽 `emitCompleted()` 收口（仿 CC `query/stopHooks.ts:65-81` + `stop_hook_active` 防递归）。

**理由（详见 [方案解析 Q19](./M5-方案解析[待实现].md)）**：Pre/Post 要「等决策」必须 Promise-await；Stop「打回继续」需反馈到 loop 也用回调。事件流（单向通知）承载不了「等决策」。

### 12-T5：hook 只能收紧不能放宽（安全核心）

**选型**：权限求值顺序 `hooks → deny → ask → permission mode → allow → canUseTool`（CC 官方 6 步，agent-sdk/permissions，2026-08 实证）。

**铁律**：
- hook 返回 `deny`（exit 2 / `permissionDecision:"deny"`）→ **直接生效，覆盖 allow 规则**（"A blocking hook takes precedence over allow rules"）。
- hook 返回 `allow` → **仍查 deny/ask 规则**：规则 deny→deny、规则 ask→仍弹窗。**hook allow 不能绕过 deny/ask**。
- hook 多条决策取最严格：`deny > ask > allow`（CC `PermissionBehavior` 无 `defer`，源码 `types/permissions.ts:44` + 聚合 `utils/hooks.ts:2820-2846` 核实）。

**结论**：权限 deny 是硬边界，hook allow 翻不了盘；hook 只能**收紧**（deny/ask），不能**放宽**（allow 绕 deny/ask）。这是安全核心（CC `toolHooks.ts:332-433` `resolveHookPermissionDecision`）。

### 12-T6：系统 hooks 代码注册、强制叠加

**选型**：系统 hooks 写代码里（hardcoded registry），**不进 config，不可覆盖**，用户 config 只能追加、不能删除。例：ECode 内置 PreToolUse 拦 `rm -rf /`、保护 `.env`（用户关不掉）。

**分层**：系统内置（代码）> 项目本地（gitignore）> 项目（git）> 用户（`~/.ecode/`）。

**与 M4 的关系**：M4 path-guard 已做敏感文件/越界硬安全网（声明式），系统 hooks 是其「动态版」（可跑任意判断/副作用）。两者互补不重复。

### 12-T7：跨平台 shell（呼应 §9.3）

**选型**：hook command 跨平台走 **bash 工具同款 shell 分流**（复用 `getShellInfo()` 已自探测 Git Bash/WSL，支点 3），不另造。

**CC 实证**（`utils/hooks.ts:747-850` `execCommandHook`）：默认 `'bash'`；Windows + bash 走 Git Bash（Cygwin）+ 路径 POSIX 化（`windowsPathToPosixPath`）；设 `CLAUDE_PROJECT_DIR` = stable project root。ECode 复用 `executeBash` 的 shell 探测。
