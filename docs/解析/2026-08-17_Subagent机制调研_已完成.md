# Subagent 机制调研（子代理的调用纪律 / 硬限制 / 提示词模板 / 运行时展示）

> 2026-08-17，subagent 立项前调研（观察区项：M7 §H2 SubagentStart/Stop 事件 + plugin `agents` 组件）。**方案已立：`详设/2026-08-17_后续-M11-Subagent实施方案_已完成.md`（S1-S10 全部收敛为 M11-D1~D13，对账见其附录）。**起因用户三问：怎么指派、怎么防止主 LLM 滥用、提示词模板怎么让子代理准确完成任务、运行时能否展开查看且不破坏活动区。本地一手源码（claude-code-main / opencode；codex 无 subagent、aider/pi 无此功能）。**本文只记事实与 ECode 视角的落点推演，不是实施方案**——方案待立项时另立文档。

## 1. ECode 视角的核心结论（先说落点）

**1. subagent 对 ECode 是零新基建的能力。** AgentLoop 是心脏且无状态复入——子代理 = 宿主工具的 execute 里嵌一个新 `runLoop`（全新 messages、同 provider/config/ToolRegistry），跑完把最终 assistant 文本作为 tool_result 返回。两个 Registry 分支面的既定优势：`task` 就是又一个 `register()` 的普通工具，心脏零改动。子代理与父对话的唯一通道 = 入参 prompt + 返回文本，上下文天然隔离。

**2. 防"主 LLM 什么都丢给 subagent"，业界的答案不是硬限制，是工具 description 的反例教学。** 两家都在 description 里写"何时**不要**用"清单（读指定文件用 Read / 找类定义用 Grep / 2-3 个文件内搜索用 Read / 与 agent 定义无关的任务），外加"已委派的活不要自己重复做"。没有频率限制、没有成本提示、没有默认禁用。**而且两家都主动鼓励并发调用**（"Launch multiple agents concurrently whenever possible"）——业界共识是**防错用（该用轻工具时别开子代理），不防多用**。ECode 沿此方向：调用纪律写在 task 工具 description，不建开关类基建（对齐"Agent 优先不产品化"）。

**3. 真正的硬限制只有一条被两家共同实施：递归一层封顶。** CC 在工具过滤层对子代理**移除 Agent 工具**（硬编码）；opencode 用深度计数（`subagent_depth` 默认 1）+ 权限派生（子代理无显式 allow 则自动补 `task: deny`）。并发与迭代在两家都**没有**硬上限（CC 的 maxTurns 是 agent 定义可选项，无全局默认；opencode 无独立限制）。

**4. 提示词是两层模板：入口工具 description 教主 LLM 怎么写任务书，子代理 system prompt 定角色与返回契约。** 关键细节（ECode 模板要抄的）：
- 主侧："像给刚进门的聪明同事 briefing——它没看过这段对话"；**反"委派理解"**："不要写'根据你的发现修 bug'——那是把综合推给子代理；要写能证明你自己理解了的 prompt（文件路径/行号/具体改什么）"；明确告知"写代码还是只调研"。
- 子侧：擅长领域声明 + 行为准则 + **返回契约**（"完成时回复简明报告，调用者会转述给用户，只要要点"）；只读型子代理配一整段**只读宣言**（"你没有编辑工具，尝试会失败"）。

**5. 运行时展示的业解：折叠一行 + 进度流式渲染 + 终端高度自适应降级 + 全量事后可看。** CC 运行中把子代理每条 tool 消息压成一行实时滚；**视口不够时自动切超压缩摘要**（行数预算 = 工具数×每工具预估行数 + 缓冲 > 终端行数时降级）——这正是"展开查看不破坏活动区"的现成答案，与 ECode 防超屏体系（动态区任何组件不得超视口）同一约束。完整 transcript 落盘事后看。

**6. 返回契约：最终 assistant 文本一条。** CC 硬截断 100k 字符；opencode XML 包裹（`<task id state>`）且 task_id 可续接同一子会话（二段对话）。"结果对用户不可见、主 agent 必须转述"写进 usage notes——ECode 的 tool_result 走 ToolGroupView 展示，天然满足"用户能看"且无需转述强制。

## 3. 三家循环形态对照（2026-08-17 补读 opencode/deepseek-harness 一手源码）

| 维度 | ECode | opencode | deepseek-harness |
|---|---|---|---|
| 循环形态 | 单层 for（无状态函数，messages 入参） | 单层 `while(true)`（session/prompt.ts:1088） | 常驻 Agent 对象三层循环（kick→turn→step） |
| 状态放哪 | 内存 HistoryLine[] | 每轮从 DB 重读（filterCompactedEffect 投影过滤，循环零状态） | 事件溯源 session（chunk 级 append 带 seq 可回放）+ inbox 两级队列（next-turn/next-step） |
| 继续条件 | iter 计数 + stopReason 状态机 | 最后消息形态（finish reason + 有无未完成 tool calls） | turnEnds 原因 + inbox.hasPending（队列空才真结束） |
| 工具执行 | executeTools（读并行/写串行） | processor 流式边收边执行 | executeToolCalls 结果 splice 进 next-step |
| 特殊机制 | afterTools 回喂/压缩兜底 | 任务插队（tasks.pop：subtask/compaction 循环头部重入）+ overflow 自动压缩 + DOOM_LOOP 阈值 3 | idle 唤醒（turn 间 inbox 有消息自动续）+ hook waterfall 改写决策 + max-tokens sticky |
| 子代理形态 | （本调研）task 内嵌 runLoop 新调用 | task 工具开子 session（同一套循环换 sessionID） | subagent/ 8 子包：fork-in-process / spawn-in-process / subagent-claude-code / subagent-codex / acp |

**三个发现（对 ECode 的输入）**：
1. **stop 谎报防御**（opencode prompt.ts:1103 注释原文明说 provider 会谎报）：stop_reason 为 end 但 assistant 带 tool_calls 时也要继续喂结果——ECode 现在信 stopReason（'end' 即 break），遇谎报端点会丢工具调用；改法=break 前加 `newToolUses.length > 0` 检查（**独立小修，不必等 subagent**）。
2. **函数 vs 对象的取舍边界**：harness 的 turn/step 分离 + inbox 是"子代理运行中可被插话"（wake）的形态——ECode subagent 已定"跑完即返不支持插话"，不需要；一次性请求驱动的 loop 用函数、常驻可唤醒的 agent 才需要对象+队列——ECode 函数式选择的适用边界由此确认。
3. **外部子代理接口位**：harness 把"进程内 fork"和"spawn 外部 CLI（claude-code/codex）当子代理"做成同一抽象两端（8 子包）——ECode 将来若想驱使外部 CLI，task 工具的 kind 位可预留（'in-process' | 'external'），现在不做。

## 4. 与 ECode 既有机制的映射（立项时的复用面）

- **实施形态（2026-08-17 讨论）**：子代理 = task 工具 execute 里嵌一次 **`runLoop([], prompt, optsB)`**——同一个 runLoop 函数新起调用（无状态函数天然互不干扰，循环代码零新增），非复用父循环、非 OS 子进程（调研确认两家"subprocess"实为同进程新会话；OS 隔离仅 CC worktree/remote 特性）。跑完取最后 assistant 文本作 tool_result 回父循环。optsB 与父 optsA 的差异即子代理全部特化：

| 项 | 父 optsA | 子 optsB |
|---|---|---|
| messages | 全量 HistoryLine[] | `[]`（prompt 作首条 user） |
| provider/providerReq | 同 | **同**（传引用） |
| tools | 全量 Registry | 裁剪版（排除 task 自己——递归封顶在此，CC filterToolsForAgent 同款） |
| history | 主会话 JSONL | NoopHistoryStore 或独立文件（**不能追加主会话**——/rewind 恢复与投影截断会错乱）；transcript 另存 `~/.ecode/agents/<id>.jsonl` 供 Static 回看 |
| callbacks.onText 等 | 进动态区 | 喂 task 进度缓冲（尾部滚动窗），**绝不直接 setActive** |
| confirm | 主 ConfirmPrompt | 同一通道（单槽排队，S8） |
| signal | abortRef | 传递父 signal（Ctrl+C 连子代理一起停） |
| checkpoint/quality | 挂 | 照挂（onBeforeWrite/afterTools 按 ToolContext/工具名工作，与循环无关） |
| logger | 主 logger | 包装 logger 注入 agentId（S9） |

- **工具注册**：`task` 工具 `register()` 进 ToolRegistry，readonly:true（并行池语义，S8 拍板——子代理内部的副作用确认由子循环自己的 confirm 通道守）。
- **权限系统**：子代理工具集裁剪可复用 M9-P5 权限规则的资源维度扩展（`Agent(x)` 规则位已留，四维模型）。
- **hooks**：SubagentStart/Stop 事件挂 HookRunner（观察区已有位）。
- **checkpoint**：子代理改文件与主循环同走 onBeforeWrite 快照（同一会话目录，/rewind 粒度自然覆盖）。
- **quality 回喂**：afterTools 的轮末聚合对子代理轮同样生效（EDIT_TOOLS 判定按工具名，与哪个循环无关）。
- **成本**：子代理 usage 回传主循环 onUsage 即可归并（Statusbar/`/cost` 零改动）。
