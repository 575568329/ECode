## 一、背景与目标

### 1.1 M1 留下的债

M1 的 `agent.ts` 直接 `import Anthropic from '@anthropic-ai/sdk'`，把 Anthropic 协议**焊死**在 agent loop 里：

```ts
// 当前 src/agent.ts 的耦合点
const anthropic = new Anthropic({ apiKey, authToken, baseURL });
const messages: Anthropic.MessageParam[] = [...];          // Anthropic 专属类型
const response = await anthropic.messages.create({ ... }); // Anthropic 专属调用
// response.content 是 Anthropic 的 ContentBlock[]，含 tool_use/tool_result
```

后果：换模型 = 改 agent loop 内部。M2 要**在 agent 和 SDK 之间插一层 Provider 抽象**，让 loop 只操作一套内部统一格式。

### 1.2 M2 交付目标（对应 00-开发规划 M2）

| # | 交付目标 | 衡量标准 |
|---|---------|---------|
| 1 | 抹平 Claude `tool_use` 与 OpenAI `function_call` 协议差异 | 同一任务两种协议都能完成 |
| 2 | 一套代码接多个模型，加新模型只改配置不改代码 | 新增模型零代码改动（有测试证明） |
| 3 | 模型能力探测（不假设所有模型支持 tool） | 不支持 tool 的模型不挂、有降级 |

### 1.3 非目标（明确不做，避免范围蔓延）

- ❌ **流式输出** — 属 M3+（见 [M1-方案解析](./M1-方案解析.md) §2.4）。M2 接口设计为非流式，但预留 `stream()` 扩展点，M3 平滑过渡
- ❌ **Session 持久化 / REPL 多轮** — 属 M3
- ❌ **会话级连接池 / Provider 实例缓存** — M2 非流式 + 无状态，单实例足够；CCode 的 `createSession/dispose` 留到流式阶段再引入

## 二、设计决策（含理由，对标调研结论）

### 决策 1：两个 Provider —— Anthropic 原生 + OpenAI 兼容

**选择**：`ClaudeProvider`（直接用 `@anthropic-ai/sdk`）+ `OpenAIProvider`（直接用 `openai` SDK）。

**理由**：
- 00-开发规划已定"2 个核心 Provider，各家兼容这两套协议，无需为每个模型写代码"
- GLM / DeepSeek 都提供 OpenAI 兼容端点 → 套 `OpenAIProvider` 即可
- Claude Code 走"原生 Anthropic only"，CCode 走"Anthropic 原生 + LangChain 兼容"。**ECode 取 CCode 的双协议路线，但拒绝 LangChain**（见决策 5）

### 决策 2：内部统一格式用 content-block 判别联合

**选择**：定义 ECode 自己的 `ECodeMessage` / `ECodeContentBlock`，agent loop 只认这套，provider 各自翻译。

**理由**：
- Anthropic 是 content-block 数组，OpenAI 是 string/数组 + tool_calls 字段 —— 两种"形状"必须有一层中间态
- CCode 的 `Message { role, content: TextContent|ToolCallContent|ToolResultContent|ImageContent }` 已验证可行
- 中间态设计成流式友好的 block 数组（即使 M2 非流式），M3 加流式时**Transform 层不用重写**

### 决策 3：非流式接口先行，流式留扩展点

**选择**：M2 的 `ModelProvider.complete()` 返回 `Promise<ECodeResponse>`（非流式批处理）。

**理由**：
- 当前 agent loop 就是非流式 `messages.create()`，M2 只是把调用边界抽出，**不重写 loop 的响应处理**
- 流式属 M3+（规划明确），YAGNI 原则不在 M2 引入
- 接口预留 `stream()` 方法注释，M3 增量添加，不改既有 `complete()` 契约

### 决策 4：能力静态声明，不做 runtime 探测

**选择**：在 config.json 里声明每个模型的 `capabilities: ['tools' | 'vision' | ...]`，agent 据此决定是否发 tools。

**理由**：
- Claude Code 的 `_SUPPORTED_CAPABILITIES` 和 CCode 的 `visionModels` 白名单都是"声明式"，**不是发探测请求**
- runtime 探测有成本（额外请求）、不可靠（结果随模型更新变）、且大多数兼容端点不暴露能力查询
- continue.dev 的 `PROVIDER_TOOL_SUPPORT` 也是静态声明模式

### 决策 5：OpenAI 侧直接用 `openai` SDK，不用 LangChain

**选择**：`OpenAIProvider` 直接 `import OpenAI from 'openai'`。

**理由**：
- ECode 核心原则之一是"**手写核心、拒绝框架黑盒**"（见 00-开发规划"三个不可动摇的原则"）
- LangChain 把消息转换、工具绑定、流式合并全包进黑盒，违背"自主可控"
- CCode 用 LangChain 是它的选择；ECode 明确走手写 Transform 路线，**这是与 CCode 的关键分歧点**
- 00-开发规划已把 `openai` 列为关键依赖（非 `langchain`）

### 决策 6：配置用 JSON（不用 CCode 的 YAML）

**选择**：`~/.ecode/config.json`。

**理由**：00-开发规划已定 JSON。JSON 不支持注释是缺点（CCode 选 YAML 正为此），但权衡后保持与规划一致 + 无额外依赖（YAML 需 `js-yaml`）。**若后期用户反馈配置复杂，再评估迁 YAML**。

## 三、核心类型契约（接口先行 —— TDD 的"红灯"基础）

> 所有类型定义在 `src/providers/types.ts`。这是 M2 最关键的契约，先定它再写实现。

### 3.1 内部统一内容块（判别联合）

```ts
/** 内部统一内容块 —— agent loop 和 provider 都只操作它 */
export type ECodeContentBlock =
  | { type: 'text'; text: string }
  | { type: 'tool_call'; id: string; name: string; input: Record<string, unknown> }
  | { type: 'tool_result'; tool_use_id: string; content: string; is_error?: boolean };
```

- `text`：LLM 的思考/回答文本
- `tool_call`：LLM 请求调工具（对应 Anthropic `tool_use` / OpenAI `tool_calls`）
- `tool_result`：工具执行结果回传（对应 Anthropic `tool_result` block / OpenAI `role:'tool'` 消息）

### 3.2 内部统一消息

```ts
export interface ECodeMessage {
  role: 'user' | 'assistant';
  content: string | ECodeContentBlock[];
}
```

- 初始用户任务：`{ role: 'user', content: '改 xxx' }`（string 形式）
- 工具结果回传：`{ role: 'user', content: [{ type: 'tool_result', ... }] }`
- LLM 回复：`{ role: 'assistant', content: [{ type: 'text'...}, { type: 'tool_call'...}] }`

### 3.3 统一 LLM 响应

```ts
export interface ECodeResponse {
  content: ECodeContentBlock[];   // 仅 text + tool_call（provider 翻译掉协议外壳）
  stopReason: 'end_turn' | 'tool_use' | 'max_tokens';
  usage: { inputTokens: number; outputTokens: number };
}
```

- `stopReason` 统一用 Anthropic 词汇（CCode 的 `ProviderWrapper` 也是这么做的：`stop→end_turn`、`tool_calls→tool_use`、`length→max_tokens`）
- agent loop 不再直接读 `response.stop_reason`，改读 `stopReason`

### 3.4 统一请求 + 工具定义

```ts
export interface ECodeToolDefinition {
  name: string;
  description: string;
  parameters: {                    // 中性命名（非 Anthropic 的 input_schema）
    type: 'object';
    properties: Record<string, unknown>;
    required?: string[];
  };
}

export interface ChatRequest {
  model: string;
  system: string;
  messages: ECodeMessage[];
  tools: ECodeToolDefinition[];
  maxTokens?: number;
}
```

> ⚠️ **破坏性改动**：当前 `src/tools/types.ts` 的 `ToolDefinition` 用 Anthropic 的 `input_schema` 字段名。M2 将其重命名为中性的 `parameters`。这是 M2 协议中立化的必要改动（属 M2 范围内，非无关重构），需同步改 `tools/*.ts` 各工具定义。

### 3.5 Provider 接口

```ts
export interface ModelProvider {
  readonly name: string;                          // 'claude' | 'openai'
  readonly protocol: 'anthropic' | 'openai';
  /** 非流式：一次性返回完整响应。agent loop 当前唯一入口 */
  complete(request: ChatRequest): Promise<ECodeResponse>;
  // TODO(M3+): stream(request: ChatRequest): AsyncIterable<ECodeStreamChunk>;
}
```

agent loop 只依赖 `ModelProvider` 接口，**不 import 任何 SDK 类型**。换模型 = 换注入的 Provider 实例，loop 一行不动。

### 3.6 能力声明类型

```ts
export type ModelCapability = 'tools' | 'vision' | 'thinking' | 'fast_mode';

export interface ModelConfig {
  provider: string;                 // 指向 config.providers 里的 key
  capabilities: ModelCapability[];  // 静态声明
}
```

## 四、架构与调用链

### 4.1 分层（Provider 层插入位置）

```
src/agent.ts (Agent Loop)
      ↓ 只依赖 ModelProvider 接口 + 内部统一格式
src/providers/
  ├── types.ts          ECodeMessage / ECodeContentBlock / ModelProvider 契约
  ├── factory.ts        createProvider(modelName) ← 读 config 选 Provider
  ├── claude.ts         ClaudeProvider（@anthropic-ai/sdk）
  ├── openai.ts         OpenAIProvider（openai SDK）
  ├── transform.ts      双向翻译：内部格式 ↔ 两家协议
  └── config.ts         ~/.ecode/config.json 读写 + 能力查询
```

### 4.2 调用链（一次 LLM 调用的流转）

```
agent.ts: provider.complete({ model, system, messages, tools })
              │
              ▼  ClaudeProvider
   transform.toAnthropicRequest()  内部格式 → Anthropic MessageParam[]
              │
              ▼
   sdk.messages.create()           真正发请求（withRetry 包裹）
              │
              ▼
   transform.fromAnthropicResponse() Anthropic ContentBlock[] → ECodeResponse
              │
              ▼  返回 ECodeResponse，agent loop 处理（与 M1 一致）
```

OpenAIProvider 同构，只是翻译目标是 OpenAI 的 `ChatCompletionMessageParam[]` + `tool_calls`。

### 4.3 agent.ts 的改动（最小化）

| 当前（M1） | M2 后 |
|-----------|-------|
| `import Anthropic` + `new Anthropic()` | `const provider = createProvider(model)`（从 config 解析） |
| `messages: Anthropic.MessageParam[]` | `messages: ECodeMessage[]` |
| `anthropic.messages.create({ model, system, messages, tools })` | `provider.complete({ model, system, messages, tools })` |
| 直接遍历 `response.content` 的 Anthropic block | 遍历 `response.content` 的 ECode block（字段名更中性） |

loop 的核心结构（while 循环、配对约束、重复检测）**不动**。

## 五、配置系统设计

### 5.1 `~/.ecode/config.json` Schema

```jsonc
{
  "defaultModel": "glm-5.2",
  "providers": {
    "claude": {
      "protocol": "anthropic",
      "baseURL": "https://api.anthropic.com",
      "apiKeyEnv": "ANTHROPIC_API_KEY"
    },
    "glm": {
      "protocol": "openai",
      "baseURL": "https://open.bigmodel.cn/api/paas/v4",
      "apiKeyEnv": "ZHIPUAI_API_KEY",
      "models": ["glm-5.2", "glm-4.7"]
    },
    "deepseek": {
      "protocol": "openai",
      "baseURL": "https://api.deepseek.com",
      "apiKeyEnv": "DEEPSEEK_API_KEY",
      "models": ["deepseek-chat"]
    }
  },
  "models": {
    "glm-5.2":      { "provider": "glm",      "capabilities": ["tools"] },
    "glm-4.7":      { "provider": "glm",      "capabilities": ["tools"] },
    "deepseek-chat":{ "provider": "deepseek", "capabilities": ["tools"] },
    "claude-sonnet-4-5": { "provider": "claude", "capabilities": ["tools", "vision", "thinking"] }
  }
}
```

**设计要点**：
- `providers` 按**厂商**分组（每个厂商一个 baseURL + 一批模型），`protocol` 决定走哪个 Provider 适配器
- `apiKeyEnv` 指向环境变量名（不在 config 里明文存 key —— 安全）
- `models` 是**扁平的模型→配置映射**，`--model glm-5.2` 直接 O(1) 查到 provider 和能力，无需遍历（比 CCode 的"遍历 providers.models 反查"更直接）
- 能力放 `models[].capabilities`，对齐 Claude Code 的 `_SUPPORTED_CAPABILITIES` 声明模式

### 5.2 配置加载与降级

- 读取顺序：`~/.ecode/config.json` → 若不存在 → 用内置默认配置（预置 GLM/DeepSeek，保证开箱可用）
- 校验：缺 `apiKeyEnv` 对应的环境变量 → 启动报错并提示如何配置（参考 M1 当前缺 key 的处理 [agent.ts:39-43](../src/agent.ts#L39-L43)）
- 预留：未来 config 版本字段 `"version"`，便于迁移（学 CCode 的迁移闸门，但 M2 先不做迁移逻辑）

### 5.3 能力查询 API

```ts
// src/providers/config.ts
export function getModelConfig(model: string): ModelConfig;        // 查不到抛错
export function hasCapability(model: string, cap: ModelCapability): boolean;
export function listAvailableModels(): Array<{ model: string; provider: string }>;
```

agent loop 据此决定是否带 `tools`：`hasCapability(model, 'tools') ? tools : []`。

## 十、风险与对策（整合 CCode 踩坑）

| 风险 | 来源 | 对策 |
|------|------|------|
| OpenAI 兼容端点（如 GLM）流式下 `tool_calls` 丢失 | CCode `OpenAICompatProvider` 的 GLM fallback | M2 非流式不受影响；M3 加流式时复刻 CCode 两级 fallback（additional_kwargs 提取 + 非流式重试） |
| Anthropic 要求 user/assistant 角色严格交替 | CCode `mergeConsecutiveRoles()` | Transform 层做交替校验/合并，并加 tool_use/tool_result 配对断言（CCode `assertToolCallResultPairing`） |
| `tool_use_id` / `tool_call_id` 配对错误 → 400 | M1 已踩过 | Transform 单测覆盖配对，回传 id 必须原样 |
| Prompt cache `cache_control` 第三方代理不支持 | CCode `CCODE_DISABLE_PROMPT_CACHE` | M2 不启用 prompt cache（属优化，M5+），避免兼容性问题 |
| 环境变量缺失导致难排查 | — | factory 启动即校验 `apiKeyEnv`，缺则报错指明缺哪个 |
