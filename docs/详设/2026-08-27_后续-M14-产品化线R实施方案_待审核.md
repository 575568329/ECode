# M14 产品化线 R（配对+中继+E2EE+IM 扩展）实施方案

> 状态：**待审核（v1.0——orca 两路源码细读已回填，openclaw 克隆在途仅影响 R4 框架细节参考）**
> 前置：M14 V 线+C 线已全部完成（`9f94b99`→`7f8af5a`，1346+3skip）；本方案是 M14 主方案 §8.4 拍板的"R 线开工前另出细化方案"。
> 定调（2026-08-24 用户拍板）：**奔产品非个人自用**——用户零安装、扫码即连；中继官方运营+开源自部署双形态。

## 1. 背景与目标

ECode 当前多端形态（M13 交付）：daemon 本机 HTTP+SSE（loopback 缺省/局域网可选）+ Web/PWA 直连 + 飞书 IM 长连接。远程访问依赖用户自建网络（Tailscale/端口转发），产品化目标是把它变成**扫码即连的原厂体验**：

- 用户在家用手机访问公司电脑上的 ECode，不需要懂任何网络概念；
- 通道安全不依赖传输方信任（中继不可信威胁模型，E2EE）；
- 设备可管理（配对/命名/吊销），token 泄漏影响面可控；
- IM 面扩展微信（ClawBot iLink）与企微，覆盖国内主流 IM 三选二以上。

**非目标**（防蔓延）：
- 不做公网云跑 daemon（语义错误：ECode 操作运行侧文件系统）；
- 不做群聊 @（YAGNI 已拍，除非场景反转）；
- 不做 Tailscale 集成（降为开发者自用文档附录）；
- 官方运营中继的**服务端扩缩容/多租户计费**不在本方案（自部署形态先交付，运营形态按需演进）。

## 2. 威胁模型与信任根（本方案的地基）

**信任边界重画**：M12-C2 起的信任根是「能连到 loopback/局域网端口的持有 token 者」。中继形态下 daemon 无入站监听（纯出站 WS），旧信任根空转——信任必须**逐连接绑定凭据**：

```
[M14-C2 现状]                          [R 线目标]
daemon(入站 HTTP) ←token─ web/手机      daemon(出站 WS) ──密文── relay ──密文── web/手机
  信任根: 网络可达 + token                信任根: 设备身份（配对建立的密钥对）
  中继: 无                                中继: 不可信（只转发密文，无 decrypt 能力）
```

**威胁清单**（逐条对应设计项）：

| # | 威胁 | 对策 | 落点 |
|---|---|---|---|
| T1 | 中继运营方/被攻破的中继读取会话内容 | E2EE：中继只见密文信封 | R3 |
| T2 | 中继调包公钥（MITM 配对） | 配对 offer 内嵌公钥 pinning（带外 QR 承载） | R1 |
| T3 | 旧设备 token 泄漏后长期可用 | 设备注册表+吊销+90 天滚动过期（可选档） | R1 |
| T4 | 录制重放密文帧 | nonce 域绑定 sessionId/方向/帧类型+接收侧计数器 | R3 |
| T5 | 断线重连时旧连接复活/帧序错乱 | generation 代次+租约+两侧看门狗 | R2 |
| T6 | 微信通道他人冒用触发命令 | sender 白名单（缺省拒）+回执者校验 | R4 |
| T7 | 审批被非目标用户应答 | 审批短码+命令指纹（IM 文本通道） | R4 |
| T8 | 本机恶意进程读 server.json 代答审批 | per-device token 隔离（primary 独占 confirm 豁免——C2① 已立） | R1 消费 |

**明文裸窗期披露**：R1/R2 交付但 R3 未完成前，中继通道靠 TLS+per-device token 过渡（中继可见明文，但需主动作恶；自部署形态下用户即运营方，风险自担）。R3 完成后才达成"中继只见密文"目标——批次顺序不可倒置的理由。

## 3. 总体架构

```
┌────────────── 公司电脑（用户侧）──────────────┐      ┌──── relay（公网 443）────┐      ┌─ 手机/Web ─┐
│ ecode daemon                                  │      │                          │      │            │
│  ├─ 宿主层（M13 两层宿主，零改动）              │ WS出站 │  控制信道（代次+租约）      │ WS   │ PWA/Web    │
│  ├─ relay 客户端（R2：出站连接+事件重放缓冲）    │ ────▶ │  帧路由（密文信封转发）     │ ◀─── │ relay 客户端│
│  ├─ E2EE 端点（R3：会话密钥派生/加解密）        │      │  设备注册表查询（只存公钥）  │      │  E2EE 端点  │
│  └─ 配对服务（R1：QR/设备注册表）               │      └──────────────────────────┘      └────────────┘
│ web 直连形态（loopback/局域网）并行保留 ─────────┘
└───────────────────────────────────────────────┘
```

要点：
- **daemon 纯出站**：现有 HTTP serve 形态完整保留（本地/局域网直连不受影响）；relay 客户端是**并行的第二传输面**，不是替换；
- **mux 帧为加密载荷单位**：MuxFrame 信封（内层协议枚举零改动——M13 架构批的设计再次兑现）整体作为 E2EE 明文，加密封包后走 relay；
- **多客户端同 relay 收敛**：与 M12-G2「双客户端同帧验收」同构，relay 侧广播语义 = 现 mux 全量广播 + muxFilter per-device 过滤（钩子已在 `multi.ts:53`）。

## 5. R1 配对码 + per-device token（3 天）

### 5.1 orca 蓝本实测结论（2026-08-27 源码细读，锚点见附录 A）

**配对流（orca 全貌）**：桌面端生成 offer → 编 QR（`orca://pair?code=<base64url(JSON)>`，query 而非 fragment——相机 intent 兼容；schema zod 校验）→ 手机扫码后 **4 帧握手**（2 往返）：

```
C→S 明文 e2ee_hello{publicKeyB64}        ← 客户端临时 Curve25519 公钥
S→C 明文 e2ee_ready                       ← 仅证明收到
C→S 密文 e2ee_auth{deviceToken,...}       ← 能解密即隐式验证服务端持 pinned 私钥
S→C 密文 e2ee_authenticated               ← v2 附 transcriptHash
```

offer 结构（`src/shared/mobile-relay-pairing-offer.ts:70-81`）：`{ v, endpoint, deviceToken, publicKeyB64, pairedDeviceId, scope, relay?:{ directorUrl, cellUrl, assignmentEpoch, relayHostId, inviteToken, inviteExpiresAt, e2eeFraming } }`——**公钥 pinning 在 offer 里**（schema 注释明说 "pinned by the pairing offer"），relay 形态还内嵌 invite（TTL **≤10min+30s 时钟偏差**，`MAX_INVITE_TTL_MS`/`INVITE_EXPIRY_CLOCK_SKEW_MS` 常量）。

**per-device token**：`randomBytes(24).toString('hex')`（192-bit CSPRNG）；**请求体字段而非 HTTP header**（E2EE 握手加密帧携带 + 之后每条 RPC 逐条复验，通道绑定 token 优先于请求字段、不一致即拒）。

**DeviceEntry 字段集**（`src/main/runtime/device-registry.ts:17-29`）：`deviceId(uuid) / name / token / scope / pairedAt / lastSeenAt(0=pending 未扫码，UI 过滤) / relayBinding? / reach`。关键不变量：**persist-before-memory-swap**（每次变更先落盘再换内存）、getOrCreatePendingDevice 防孤儿（未扫码 token 复用）、rotatePendingDevice 防泄露（暴露即作废）、lastSeen 刷新 250ms 合并写。

**吊销三步序**（`runtime-rpc.ts:630-657`）：①持久 revoke outbox 先写成功（云侧清理落盘）→ ②removeDevice 删本地记录 → ③terminateDeviceConnections(token) 立即切断活连接。**顺序不可倒**（本地先删则 outbox 失败即泄漏窗口）。

**scope × reach 两正交轴**：scope=能调什么（mobile 白名单 ~200 只读方法 vs runtime 全量）；reach=网络暴露到哪（this-computer vs network——决定 WS 绑 127.0.0.1 还是 0.0.0.0）。旧记录缺 scope 默认 mobile（不扩权）。

**orca 没做的**：无 90 天滚动过期（token 永不过期只有手动吊销——D7 决策依据）；无 OS keychain（0600/ACL JSON 明文——orca 自认短板，ECode 同为 daemon 形态同难，keychain 用户已拍板永不）。

### 5.2 ECode R1 设计（按 orca 蓝本+ECode 凭据分级改造）

- **配对入口**（D1）：`ecode pair` 终端 QR（qrcode-terminal 库）+ 同屏打印 URL（`https://<web>/#pairing=<...>` **fragment 承载**——orca createWebClientUrl 同款，防凭据进代理日志/Referer）；web 已连接端「添加设备」页随 R5；
- **offer 结构**：`{ v:1, webUrl, deviceToken, daemonPublicKeyB64, deviceName?, expiresAt }`——本机/局域网形态无 relay 段；R2 后追加 `relay:{ cellUrl, assignmentEpoch, relayHostId, inviteToken, inviteExpiresAt }`；
- **握手**：4 帧同款（E2EE 端点在 R3 交付前，R1 过渡形态 = TLS+token 直连 WebSocket——web 侧先只验 deviceToken，公钥 pinning 随 R3 生效，裸窗期披露见 §2）；
- **DeviceRegistry**：ECode 化字段 `{ deviceId, name, secret, scope, reach, pairedAt, lastSeenAt, revoked? }`——`secret` 直接喂 `CredentialStore.add(secret, 'device')`（C2① 的 extraCredentials 通道）；scope 取值 `{ readonly, chat, full }`（D2），reach 取值 `{ local, lan, relay }`；持久化 `~/.ecode/devices.json`（0600，persist-before-swap 不变量照抄）；
- **吊销**：三步序照抄（R1 无 relay 段时 outbox 退化为本地日志审计条目）；被吊销设备下一请求 401→web 回配对流（token 失效同 M13 修复语义）；
- **命令面边界**：device 级 `confirm 豁免`已禁（C2①）；scope 进一步限命令面（readonly=device 级只读命令+对话、full=model/set 等——D2 拍板粒度）。

### 5.3 文件面

`src/server/pairing.ts`（offer 生成/DeviceRegistry/吊销）+ `src/server/devices.ts`（注册表持久化）+ `src/cli/index.ts` 加 `ecode pair` 分流 + qrcode-terminal 依赖 + web 配对接入页（R5）。

## 6. R2 中继服务端 + daemon 出站连接（≥5 天）

### 6.1 orca 蓝本实测结论（控制信道与代次租约）

**连接模型**：daemon **纯出站**——控制腿拨 `wss://{cell}/v1/host/control`，数据腿按需拨 `wss://{cell}/v1/host/data/{connId}`（每客户端连接一条 connId socket）；零中继态入站监听。控制信道 = JSON 文本帧（binary 即协议违规）、maxPayload 64KB、禁 perMessageDeflate、`Authorization: Bearer {relayJwt}`；数据信道 1MB 允许 binary。

**4 步握手**：`host-hello{relayHostId, assignmentEpoch, hostPublicKeyB64, appVersion, previousGeneration?, controlResumeSecret?}` → 服务端 `host-challenge{challengeId, relay 临时公钥, nonce, box 密文}` → daemon `host-challenge-ack{proofB64}` → `host-hello-ack{generation, controlResumeSecret, leaseExpiresAt, activeConnIds, pendingConns}`。

**generation+租约（防旧连接复活的核心）**：generation 服务端在 ack 分配（>0）；**rebind = 带 previousGeneration+controlResumeSecret 重连恢复同一代并接管存量连接**；新代意味着服务端已宣告旧 control 作废。controlResumeSecret = 32 字节 base64url，每次 activate 换新值；二者必须**成对**出现在 challenge transcript 中被验证。lease TTL 服务端策略（orca 实测 60s~1h 都有），续租 = 到期前 rebind 同代（提前 60-120s 随机量触发，失败 5-15s 随机重试）。旧 control 退役：rebind 成功后无在途请求即关，否则等 10.1s（请求 deadline+余量）强关。

**双侧看门狗（镜像边界）**：服务端每 15s 发 `{type:'ping',t}` 客户端回 `{type:'pong',t}`；客户端镜像守「**任何入站字节**」75s 静默即 `socket.terminate()`（15s 检查周期）——两侧合起来保证半开/僵死 socket ≤75s 被收割。

**director/cell 发现**：两级——① token 交换（POST relayTokenEndpoint，云 accessToken → relayToken）②分配（POST directorUrl/v1/assign → cellUrl+assignmentEpoch+lease）。**自部署单 cell 可简化**：两级合成静态配置（固定 cellUrl、epoch 单调自增），删 region 偏好/多 cell 迁移池/reconnect 快车道；**drain 消息保留**（运维优雅下线需要：graceMs 内不接新、存量排空）。**orca relay 服务端本体不在其仓库**（仓库内是桌面客户端+协议契约+测试替身）——服务端行为从契约反推，最小形态见 6.3。

**关闭码语义**（协议契约）：4401 未授权 / 4404 / 4408 / 4409 WRONG_CELL / 4429 限流 / 4503——客户端按码选恢复策略（重认证/退避/重新 resolve-director）。

### 6.2 信任根迁移（loopback → 逐连接凭据绑定）

orca 直连通道（LAN/loopback ws+token）**没有弃用**，与 relay 并存挂在同一分发层（MobileSocketWiring 一 dispatcher 两 transport）。relay 传输强制更严凭据（requireV2——v1 握手直接 4001）。逐连接绑定三件套：

1. **握手 context 与 socket 元数据强一致**：hello 的 transport+relayHostId 必须匹配该 socket 实际 transport（防握手跨通道搬运）；
2. **relayDeviceId ≠ device.deviceId → 拒**：外层 relay 凭据不能冒充别的本地设备；
3. **auth 帧必须携带与握手一致的 transcriptHash 且字段形状精确**（多一字段少一字段都拒——防语义漂移注入）。

**host-proof（daemon↔cell 互证）**：cell 用 daemon 静态公钥开 box 质询，明文 = 域标签 + 16 字段 transcript（协议域/版本/relayOrigin/临时公钥/nonce/challengeId/身份三元组/relayHostId/hostPublicKey/assignmentEpoch/previousGeneration/resumeRequested）+ 32B secret；时效 ±30s skew、质询窗口 ≤10s；应答 = HMAC-SHA256(secret, 域标签||transcript)。语义 = **cell 逐质询证明"它认识这个 daemon"**——不再依赖连接来自本机回环。

### 6.3 ECode R2 设计

- **relay 包** `relay/`（独立 npm 包 `ecode-relay`，D3）：Node+ws 零其他依赖。最小 cell 三端点：
  - `POST /v1/assign`（自部署：静态返回 cellUrl+epoch——director 退化）；
  - `GET /v1/host/control`（Bearer JWT → 4 步握手 → 登记 generation/lease/connTicket，15s ping/75s 静默踢）；
  - `GET /v1/connect/{relayHostId}`（手机/web 腿：验 invite/resume → 建 pending conn → 推 `conn-open` 给 daemon → 双向字节 splice）+ `GET /v1/host/data/{connId}`（验 connTicket+当前 generation，attachDeadline ≤60s 内拼接）。
- **E2EE 载荷映射（推荐 orca 模型）**：每 web/手机客户端一条 connId 数据 socket，**MuxFrame 信封整体作为 E2EE 明文载荷**——E2EE 层无需理解流 id（多路复用留 MuxFrame 层，M13 架构再兑现）；**SSE 下行帧迁到 WS 数据腿回包**（relay 形态全双工；本地直连形态 SSE 不动）。
- **daemon 侧** `src/server/relayClient.ts`：出站控制腿（rebind/续租/看门狗镜像/reqId 请求族）+ 数据腿拨接；挂在现有 multi.ts 分发层旁（direct=HTTP+SSE 保留，relay=新 transport——MobileSocketWiring 两 transport 模式照抄）。
- **事件重放缓冲（C1①b 移入）**：relay 侧每 sessionId 环形留存 N 帧密文（D6 定 N），重连凭 resumeSecret+generation 拉增量；web 侧 seq 追踪（MuxFrame 已带 seq）配合去重。
- **代次/租约/看门狗参数照抄 orca**：15s ping / 75s 静默 / rebind 提前 60-120s / 请求 10s 超时——实测过的值不自创。

## 7. R3 E2EE（2-3 天）

### 7.1 orca v2 实测结论（防重放的完整机制）

**nonce 域（24 字节确定性布局，无 RNG）**：`sessionId[0..12] || version=2 || directionByte || payloadKindByte || 0x00 || counter(u64 BE)`——绑定 sessionId+方向+帧类型+严格计数器；同时明文内嵌 42 字节 header（同四元组）再整体加密，header 强等值校验。

**接收侧计数器**：每 session 每方向一个严格递增计数器，打开帧时必须**精确等于**期望值（非窗口容忍——错位即解密失败）；解密失败也计数（awaiting_auth 期 1 次即断 4001，ready 期连续 5 次断 4003）；出站计数器只在入队成功后消费（防空洞）。重放实证：捕获的 auth 帧在新连接上重放被拒。

**密钥调度（per-socket 新鲜）**：双方各出 32B 随机 nonce（客户端新 keypair+clientNonce，daemon 静态 keypair+desktopNonce）→ ECDH 共享密钥 → `HKDF-SHA256(ikm=sharedSecret, salt=域标签||双 nonce, info="session"||SHA256(transcript), 96B)` → **双向分钥 + sessionId 三段**（mobileToDesktopKey 32B || desktopToMobileKey 32B || sessionId 32B）——方向分钥+transcript 绑定 = 每 socket 密钥唯一且握手不可替换。

**v1 五缺陷（为何重做 v2——ECode 勿重踩）**：①密钥只由静态公钥决定，同一客户端每次连接同钥（跨连接重放成立）；②nonce 纯随机+接收侧无状态（任意帧无限重放）；③无方向分离（双向同钥同 nonce 空间，自反射攻击面）；④无 transcript/context 绑定（握手可重放可跨 transport 搬运）；⑤无 sessionId（帧无法绑会话）。

**密文覆盖面**：RPC 全载荷（文本+binary）+ e2ee_auth（含 deviceToken）全密文；**明文 = 控制面全部 + 数据面首帧 host-data-auth + 连接腿 relay-auth/relay-hello + E2EE 握手 e2ee_hello/e2ee_ready**（密钥交换必须明文）。relay 可见：谁连谁/代次/票据/帧大小与时序；不可见：任何内容与设备 token。

### 7.2 ECode R3 设计

- **算法面**：X25519 + HKDF-SHA256 + AES-256-GCM（Node crypto 与浏览器 WebCrypto 同款，两端零第三方加密库；orca 用 tweetnacl secretbox——ECode 统一到 GCM 是既有栈顺手，nonce 确定性布局照抄）；
- **三件移植**：nonce 域构造（sessionId 12B||v||dir||kind||pad||counter）、严格递增计数器+失败计数断连、HKDF 双向分钥+transcript 绑定——orca 这三层 ~200 行含测试可整体搬思路；
- **密钥层级**：配对时 ECDH（R1 的 daemon 静态公钥已在 offer）→ 每 socket 再派生（双方 nonce+transcript）；sessionId 段直接复用 ECode MuxFrame 的 sessionId 域；
- **PWA 侧**：WebCrypto X25519 全支持已核验（§7 库选型注）——`SubtleCrypto.deriveBits` HKDF 同样标准；两端加解密封装成同形模块（`src/server/e2ee.ts` + `web/src/e2ee.ts`，接口对齐便于契约测试）。

## 8. R4 微信 ClawBot + 企微 gateway（2-3 天）

- **架构**：`src/server/im/wechat.ts` + `wecom.ts`，飞书 gateway 同款第三/四客户端形态（接 mux 协议，非独立系统）；
- **微信 iLink**（官方 ClawBot，~5 HTTP 接口：二维码登录/收发消息）三限制内建：被动回复（**定位"用户发起式"轻交互面**——查状态/插话/简单命令；主动通知走飞书/企微/web）、context_token 24h（过期暂停+记录）、纯文本（审批三键退化数字回复）；
- **sender 白名单+回执者校验**（T6）：对齐 feishu allowUsers 缺省拒（M13 审阅 P0-1 前车之鉴）；
- **审批短码+命令指纹**（T7）：数字回复必须带目标审批短码+preview 命令指纹（截断下仍可核对）；绑定随 context_token 过期作废；
- **企微**：应用消息 API 完整（文本/卡片）；回调需公网——**正好搭 relay**（R2 交付后的第一个非 E2EE 帧消费场景？决策点：企微回调理走 relay 控制信道还是独立出站轮询）。

## 12. 验收门

- **G-R1**：真机扫码配对成功+第二台设备配对+吊销后帧被拒+回配对流；
- **G-R2**：daemon 断网 30s 重连帧序不乱（generation 断言）+手机弱网（飞行模式开关）续传无丢帧（重放缓冲）；
- **G-R3**：relay 侧抓包全密文（除路由信封）+重放录制帧被拒（计数器断言）；
- **G-R4**：微信真机发消息触发轮次+审批数字回复（短码核对）+非白名单 sender 被拒；
- **G-R5**：干净 VPS 按文档 15 分钟起 relay 并完成端到端配对对话。
