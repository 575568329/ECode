# 后续-loopGuard观测类工具假阳性诊断与方案

> 日期：2026-09-03。动机：真机触发——agent 等待全量测试（后台任务）时用相同参数反复调
> `task_output` 轮询，被 M13-B2 loop-guard 的同参检测器先警告后终止（两连击）。守卫目标
> （抓模型卡死循环）正当，但对「同参数=有收益」的观测类工具产生了**假阳性**。
> 本文定位这是**设计问题（不变式不精确）而非 bug**，给出三层方案待拍板。

## 1. 案例还原（2026-09-03 真机日志）

场景：用户要求「一次性改好停滞续写」→ 全量 vitest 约 90s，agent 后台跑测后短间隔轮询
`task_output(task_id)` 读结果。行为序列：

1. 连续多轮 `task_output("t1", wait_ms:10000)`——**参数完全相同**（等价用法，工具语义即如此）
2. 第 8 轮同参 → `[loop-guard] 最近 8 轮在以完全相同的参数调用相同工具，请重新判断这是否必要`（nudge）
3. 换 grep 管道后台重跑后继续短轮询 → 换法后签名变了、旧 streak 已清零（P2-4 补注：签名一变
   即从 1 重数），但新签名下**又一轮连续 8 次同参** → 再次触发
   `[loop-guard] 检测到同参数工具循环，本轮已终止`（**abort，本轮结果丢弃**）

## 2. 机制现状（代码事实，行号以 e4137c3 为准，符号名为权威锚）

### 2.1 检测器（host/session.ts）

- 签名：`roundUses.push(`${use.name}:${JSON.stringify(use.input)}`)`（onToolResult 时点，
  实施处符号：`roundUses` 采集行——e4137c3 时点约 L1333）
- 判定（`loopGuardRound`，e4137c3 时点约 L1700-1718）：本轮签名排序后与上轮**完全相同** →
  `sigStreak++`；阈值 `SIG_NUDGE: 8` 提醒 → 再犯 `sigStreak >= SIG_NUDGE` 且已提醒 →
  `guardAbort('same-args')` 终止
- 阈值常量：`HostSession.GUARD`（e4137c3 时点 L163；2026-09-03 审阅 P2-3 起去 private 供测试派生）
- 解除条件：签名一变即清零重计（`sigStreak = 1`）

### 2.2 数据面缺口（根因所在）

> **实施偏差记录（2026-09-03 执行批）**：本节原方案是扩 `afterTools` round 传 resultHead。
> 实施时发现宿主 `onToolResult(id, name, result)` 回调本就携带全量 ToolResult 且是 roundUses
> 的现成采集点——P1 改在 onToolResult 采集 resultHead，**loop.ts 零接口变更**：
> 不动 `LoopRunOptions.afterTools` 形状（旧调用方/子代理/测试三方零兼容面，验收 3 自动满足），
> resultHead 不经 afterTools 数据通道。语义与原方案完全一致（同参且同果才累计）。

原方案记录（已按上述方式替代实现）：`afterTools` 回调形状（core/loop.ts，`LoopRunOptions.afterTools`）：

```ts
afterTools?: (round: { tools: Array<{ name: string; isError: boolean }> }) => ...
```

**round 只有工具名与成败，没有结果内容**——宿主拿不到「这次调用是否有新产出」，
只能用「参数签名相同」近似「无收益重复」。近似在变更类工具上成立（同参重跑同一命令
大概率同一结果），在观测类工具上系统性不成立（见 §3）。

### 2.3 指引面自相矛盾（帮凶）

`task_output` 工具描述（task_tools.ts L10）写「wait_ms 可短等新输出或退出」——
**系统指引鼓励的用法被系统守卫惩罚**：短等轮询的正确形态就是同参数连发。
两个组件对「什么算浪费」没有共享定义。

## 3. 定性：设计问题，非 bug

| 视角 | 论证 |
|---|---|
| 不变式不精确 | 检测器隐含假设「同参数调用 = 无收益重复」。正确不变式应为「同参数**且结果无变化**」。参数签名是结果收益的劣质代理 |
| 工具二分 | **变更类**（bash/edit_file/write_file）：同参重试确实多为空转，现有判定成立；**观测类**（task_output/read_file/grep 同参复查）：同参重复是其**协议内正确用法**，每次返回增量/可能变化 |
| 非冤枉的成分 | agent 侧短 wait_ms 连发确实低效（正确姿势：单次大 wait_ms 等待或先做别的再回来）；两级设计（先 nudge 后 abort）+ 签名一变即清零，误杀代价一轮、有 maxIter 兜底——守卫抓真死循环的价值依然成立 |

结论：**已知取舍的假阳性类别**。修复方向是让判定「结果感知」，而非废除守卫。

## 4. 对标（2026-09-03 调研沉淀）

- **aider reflection**：失败回喂让模型自纠，且对「无效重复」的判定带**结果信息**（编辑是否成功
  应用/lint 是否通过），不是裸参数比对——同参但结果变化的调用不会进 reflection 循环
- **CC/opencode**：未见对同参调用的硬终止（CC 依赖模型自身纪律 + max turns 兜底）；
  ECode 的 loop-guard 是超前的自保机制，正因超前才踩到没人踩过的假阳性面
- 通用结论：业界对「重复检测」普遍以**状态/结果变化**为准（文件 mtime/返回值 diff），
  裸参数指纹是 ECode 的简化实现

## 5. 方案分层（待拍板）

### P0 提示词层（已落地 2026-09-03 执行批）

- `task_tools.ts` task_output 描述追加防连发提示（按 wait_ms **实际上限 10000** 表述——
  原方案草拟的「如 60000」超出 schema 上限，系笔误，执行时修正）
- bash 后台运行回执文案（bash.ts）同步提示
- 成本≈0；消除「指引鼓励连发」的自相矛盾；不解决检测本身

### P1 结果感知（已落地 2026-09-03 执行批，按 §2.2 偏差记录以 onToolResult 采集）

- ~~loop.ts `afterTools` 的 round 扩展~~ → **实施走 `onToolResult`**：宿主采集签名处本就持有
  全量 `ToolResult`，直接取 `r.content.slice(0, 200)` 作 resultHead——loop.ts 零改动、
  resultHead 不经数据通道（防泄漏面更小，安全席语义不变）
- session.ts 同参签名升级：`${name}:${JSON.stringify(input)}:${resultHead}`（**明文截断，
  审阅 P1-2 拍板①**——不用 hash：现有签名即明文形态，保持可读性利于调试日志；
  200 字符截断控内存与敏感面）
  ——**参数同且结果摘要同**才累计 streak；结果变 = 有新信息 = 清零
- 零产出观测类（如 task_output 无新输出时返回「暂无新输出」固定文案）仍会同参同果 →
  依然累计——但这恰是**正确语义**：真等了 8 次还毫无新产出，提醒 agent 换姿势（加大 wait_ms
  或先做别的）正是用户想要的
- 风险：resultHead 进宿主内存，已截断（200 字符）不含敏感全文

### P2 观测工具豁免清单（否决保留记录）

- 维度仿 REMEMBER_TOOLS 建 OBSERVATIONAL_TOOLS 豁免同参追踪
- **否决理由**：治标——把盲区挪位置（观测类真卡死——轮询一个永不完成的任务——反而失去保护）；
  P1 已覆盖其全部收益且语义更准

## 6. 验收标准（2026-09-03 执行批全部兑现，tests/host/loop-guard.test.ts）

1. ✅ 同参同果连续 SIG_NUDGE+4 轮 → nudge/abort（回归锚；轮数按 P2-3 派生自阈值常量，不硬编码）
2. ✅ 同参**异果**连续 SIG_NUDGE+4 轮 → 不触发（本方案核心验收；TDD 红线实证：旧实现下此测试红、新实现绿）
3. ✅ 既有 loop-guard 测试全绿；loop.ts 零接口变更（偏差记录见 §2.2——resultHead 不经 afterTools），向后兼容天然成立
4. ✅ tsc 零错 + 自触碰面测试绿

### P1（应修——不改则实施时会踩坑）

- **P1-1 §2.2 行号漂移**：`afterTools` 形状在 loop.ts 的 **L133**（声明）——正文写「L133/L558」
  中 L558 是调用点周边（实际调用在 L559-561）。行号类引用建议标注「e4137c3 时点」并接受漂移，
  或改引符号名（`LoopRunOptions.afterTools`）为主、行号为辅——符号名不随编辑漂移。
  同理 §2.1 的「L1700-1718」建议改引 `loopGuardRound`。
- **P1-2 §5 P1 resultHead 的哈希必要性存疑**：签名已要 `hash(JSON.stringify(input))`，但现有
  实现是明文 `JSON.stringify(use.input)`（未哈希）——若 P1 引入哈希，签名形态变化会使
  「向后兼容」验收（§6.3）失效（旧测试断言的是明文签名）。建议二选一并写死：
  ①保持明文（resultHead 截断 200 字符后内存可担，签名可读性反而利于调试日志）；
  ②引哈希但把 §6.3 验收改为「新签名形态锁定」。推荐 ①——截断已控风险，明文利于排查。
