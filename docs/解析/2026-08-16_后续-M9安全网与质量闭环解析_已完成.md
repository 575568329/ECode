# M9 安全网与质量闭环解析（新手向）

> 日期：2026-08-16 · 读者定位：刚接触 ECode 的新人（不预设读过 M5 投影设计）
> 读法建议：§0 建立全景 → §1-§2 精读（checkpoint 与 /rewind 是 M9 的心脏，也是最难懂的部分）→ 其余按需。

## 0. M9 解决什么问题

M1-M8 之后 ECode 已经能干活了，但有一个致命场景没设防：**模型改文件是最高频也最危险的动作**——改坏了怎么办？bash 删错东西呢？改完引入 lint 错误还自我感觉良好呢？用户亲手提交的代码会不会被误伤？

M9 给"Agent 改文件"这个动作建立四道防线，外加两个外围设施：

```
        ┌─ 事前围栏 ──────────── P4 沙箱四档 + P5 权限首步（能不准做就不做）
动作 ───┼─ 事中快照 ──────────── P1 checkpoint（做之前先拍下原样）
        ├─ 事后验证 ──────────── P3 quality（做完自动跑 lint/test，失败回喂模型自纠）
        └─ 后悔退路 ──────────── P2 /rewind（文件+对话一起回到过去）、P6 /undo（退掉 ECode 的 git 提交）
外围：P0 hooks 接线修复（M7 的协议层缺口补齐）、P7 LSP 接口位（占位不实施）
```

一句话：**改坏了能回去，改完自动验，权限有纵深**。

## 1. checkpoint：改文件之前，先拍下原样

### 1.1 问题与解法

`write_file` / `edit_file` 是覆盖式写。覆盖一旦发生，原始内容就没了——所以快照必须拍在**执行前**：每个快照点的含义都是"这一次改动**之前**长什么样"（写前基线）。

bash 和 MCP 工具特殊：命令的入参里提取不出可信的文件路径（第三方代码），改用 `git status --porcelain` **近修改集**兜底——把当前所有 dirty 文件全拍一遍。非 git 仓库兜不了底，跳过并警告"改动不可回退"（诚实声明，不假装有快照）。

### 1.2 存储布局：content-addressed

朴素方案（每个点全量拷贝涉及的文件）太贵。ECode 用内容寻址——文件内容的 sha256 就是对象名，**同内容只存一份**：

```
~/.ecode/checkpoints/<sessionId>/
├── objects/
│   ├── a3f2…   ← 对象库：按内容 hash 寻址
│   └── 9c81…      同一文件三轮没改 → hash 相同 → 只存一份
├── 1/meta.json   ← 快照点：{ seq, time, tool,
├── 2/meta.json      messageId, files: [{path, hash→objects}] }
└── …
```

开销从 O(快照点 × 文件数) 降到 O(不同内容数)。磁盘成本几乎只跟"文件真正变过几次"挂钩。

### 1.3 治理三线（不能无限涨）

| 线 | 上限 | 动作 |
|---|---|---|
| 单会话点数 | 100 | 淘汰最旧点 → 重扫剩余点引用集，回收孤儿对象（多点共享一个对象，全部引用点淘汰后才真删） |
| 全局会话目录 | 50 | 按 mtime 淘汰最旧会话目录（整目录删） |
| 单文件大小 | 10MB | 超限跳过该文件 + warn |

### 1.4 快照失败不挡主流程

安全网自身出问题（磁盘满、权限）不能挡住用户的工作——工具实现里 `onBeforeWrite` 用 try/catch 静默包住，失败继续执行原任务，装配方 warn 已记。

### 1.5 对话节点锚：messageId

meta 里的 `messageId` 存的是那次工具调用的 **tool_use id**（§2.3 详述）。它把"文件快照"和"对话位置"串成一件事，是 /rewind 能同时回退两边的钥匙。

## 2. /rewind：后悔药（M9 的心脏）

### 2.1 用户操作流

```
/rewind 回车
  → 面板：快照点列表（最新在上）
     行格式：HH:MM  工具名  文件列表（≤3 个 + "+N"）
     特殊行：(还原前自动) ← 上一次还原前自动拍的点（§2.4）
     输入即搜索 / ↑↓ 选择
  → 回车进二级确认页：
     列出将还原的文件；快照后被用户手动改过的文件 ⚠ 黄字标注"还原将覆盖"
     （不静默覆盖手改——用户确认才动）
     运行中禁用确认（loop 与还原同时写文件会竞态，可看不可退）
  → y 还原 / Esc 取消
```

### 2.2 文件侧：区间逆序还原 + 还原前自动快照

**还原 = 选中点（含自身）及之后全部快照逆序写回。**

为什么逆序：每个快照都是"执行前"基线，从新到旧依次覆盖，每个文件最终留下的是范围内**最早**的基线——语义恰好是"回到那个点执行之前"。

**还原覆盖任何东西之前，先把"现在"拍成一个新快照点**（`tool='rewind-auto'`）：

```
A.c = v4（不管 v4 是模型改的还是用户手改的）
/rewind 选点 1（基线 v1）
  ① snapshot([A.c], tool:'rewind-auto')   ← v4 存下，成为新点
  ② 逆序写回 → A.c = v1
```

这就是**撤销可撤销**：回错了再 `/rewind` 选"(还原前自动)"点，v4 就回来了。套娃不封顶——每次还原都先留底。注意拍的是"外部改动后的现状"：即使你手改过、还原会覆盖你的手改，手改内容也已被存下，最坏再回退一次找回。

### 2.3 对话侧：文件真改、对话不改（最反直觉的一节）

/rewind 同时做两件事，两侧策略**完全不对称**：

| | 文件侧 | 对话侧 |
|---|---|---|
| 还原时发生什么 | **真覆盖**（磁盘写回旧内容） | **只追加一行标记**（几十字节 JSON） |
| 原内容去哪了 | 被覆盖 → 靠 rewind-auto 快照保护 | 哪都没去，一直在原位 |
| 撤销回退 | 从 rewind-auto 快照写回 | 投影不再跳过区间而已 |

对话历史是 append-only 的 JSONL，每条消息产生瞬间就落盘。/rewind 对它一个字节不动，只往末尾追加：

```jsonl
{"role":"user","content":[…]}                     ← 一直在
{"role":"assistant","content":[tool_use toolu_…]} ← 一直在（被回退的那轮）
{"rewind":true,"seq":5,"toolUseId":"toolu_…","time":"…"} ← 回退只加了这行
```

"回退"的效果只存在于**读取时的计算**：每次组装请求上下文，投影函数（`core/context.ts` 的 `buildContextMessages`）现算"跳过标记区间"，算完即弃。三层各自的真相：

- **磁盘 history**：只多一行标记，全量对话原封不动
- **屏幕**：只多一行 `⇺ 已回退`，原文照常滚上去看
- **LLM 上下文**：每次现算的视图——这是唯一"变了"的地方，但它不是存储

**LLM 不知道发生过回退**——没有系统提示、没有标记消息，被回退的轮次在它眼里从未存在。这是刻意的：回退要回得彻底，模型记忆也回到过去，否则它还惦记着自己"已完成"的修改。实操含义：回退后直接说"重新改"很干净；若想让它避开之前的弯路，需要自己把教训写进新输入（它没有"刚才"的记忆，但你描述的约束它看得到）。

### 2.4 锚：tool_use id（不是 ECode 发明的）

标记行里的 `toolUseId` 来自 **LLM 协议**：模型发起工具调用时每个 `tool_use` block 必须带 id（如 `toolu_01XF…`），下一轮 `tool_result` 靠它配对。ECode 全程借用——同一条轨道，tool_result 找结果、快照点找对话位置。

```
模型: tool_use{ id: toolu_01XF…, name: edit_file }   ← id 在这条 assistant 消息里
  │
  ├─ loop 执行前包装透传 use.id（心脏只认回调，不认识 checkpoint）
  ▼
snapshot(sessionId, paths, { tool, messageId: toolu_01XF… })   ← 存进 meta
  │
  ▼ /rewind 选中该点
RewindLine{ toolUseId: toolu_01XF… }   ← 写进对话历史
  │
  ▼ 之后每轮投影
findIndex("含该 tool_use 的 assistant 消息") = 截断起点
```

两个边界：纯聊天轮没有 id 也没有快照点（没改文件无需回退）；ECode 自造的 `CommittedItem.id` 只用于 TUI 渲染 key，与回退链路无关。

### 2.5 区间怎么闭合：起点锚消息、终点标记行

```
lines（append-only 全量数组）                     下标
  user: 帮我改 A                                  0  ┐
  assistant: [tool_use toolu_01 …]                1  │ 保留：锚之前
  （tool_result、后续轮次…）                      2  ┘
  assistant: [tool_use toolu_02, edit B]          3  ← 起点：toolId=toolu_02
  （tool_result toolu_02）                        4  │
  user: 好                                        5  │ 区间 [3..8]
  assistant: 两个都改好了                         6  │ 两端含 → 整段不进请求
  …                                              7  │
  {rewind:true, toolUseId:"toolu_02", seq:5}      8  ← 终点：标记行自身
  user: 重新弄                                    9  ┐ 保留：标记之后
                                                    ┘
```

`rewindSubset`（core/context.ts）三步：**从后往前**找最后一条标记行（下标 = 终点）；拿 `toolUseId` **从前往后**找含该 tool_use 的 assistant 消息（下标 = 起点）；返回 `锚之前的 + 标记之后的`。区间内夹多少纯文本都无所谓——锚只是起点，区间是连续切片。

三条防御分支全部回退到"全量返回"：标记缺 toolUseId / 锚失联 / 多条标记只认最后一条。原则是**宁多传不切错**——切错会产生孤儿 tool_result（协议 400），多传顶多浪费上下文。压缩 boundary 的参考系也建立在过滤后的子集上（实施时终审 P0 修的就是两参考系分叉导致 400 的问题）。

### 2.6 撤销回退：缺锚全量，歪打正着的正确语义

选"(还原前自动)"点回退时，那条新 RewindLine **没有锚**（rewind-auto 快照刻意不带 messageId）→ 投影全量返回 → 被回退的区间整体复活。

这不是缺陷，是**正确语义**：撤销回退 = 上下文与文件一起完整回到回退前。实施复核时确认过反例——如果给它补上"还原范围内最新点的锚"，复活会不完整（最新锚那轮仍被截：文件已还原回改后状态、模型却只记得一半 = 半截状态）。这个行为已用测试锁定（context.test「撤销回退」用例），checkpoint/context 的注释也写明了为什么刻意不补锚。

## 3. quality：改完自动验，失败回喂

轮末（本轮至少一次编辑成功）自动跑 lint / test：探测顺序 config 显式命令 > package.json scripts > 关闭（零配置可用）；失败输出以 **user 文本消息**（`[lint] …` 前缀）回喂——不走 tool_result，因为协议要求 tool_result 必须配对 tool_use，无主 result 会 400。

**熔断**：连续 2 次失败且输出 hash 无变化 → 本次回喂附熔断提示 + 转告警中心 + 此后短路（同一错误反复喂没有意义，别浪费轮次）。输出有变化则重置。60s 超时杀进程，4k 字符头尾截断。

红灯（lint/test 失败）时不 autoCommit（详见 §4）。

## 4. git 轻量：autoCommit + /undo

### 4.1 哲学：不静默改用户 repo

autoCommit **默认 false**；开启后也只提交本轮 ECode 自己改的文件；`/undo` 只退带 ECode 标记的提交，**用户自己的提交绝不动**。

### 4.2 三层保护（每层都是踩过坑修出来的）

1. **trailer 标记**：ECode 的提交 message 第二段带 `Ecode-Commit: <sessionId>`（git 双 `-m` 生成）。/undo 先校验最近提交的 message 含此 trailer，不是 ECode 的直接拒绝："绝不回退用户自己的提交，文件回退可用 /rewind"。用户想撤自己的提交，git 原生 reset/revert 一直都在。
2. **`commit --only -- <files>`**：裸 `git commit` 提交整个 index，会混入用户手动 staged 的文件（终审实证数据丢失）。pathspec 限定只提交指定路径。
3. **`reset --soft` + 逐文件恢复**：/undo 不用 `reset --hard`（会把用户 staged 的一并清掉）。soft 只撤提交记录，然后对该提交自己的文件集逐个恢复：HEAD 里有 → `checkout HEAD --`；没有 → 说明是 ECode 新建的 → `rm`。首个提交（无父）走 `update-ref -d`。commit 失败时尽力退掉本轮 add（不残留 stage 污染）。

## 5. 沙箱四档 + 权限首步（事前围栏）

### 5.1 四档（/sandbox 面板或 Tab 键循环切换）

| 档 | 行为 |
|---|---|
| default | 现状：写/改文件每次确认 |
| read-only | 只读工具放行，副作用整体拒绝（含 MCP） |
| workspace-write | 工作区内写放行；路径解析后前缀校验，`..` 逃逸拦截（win 大小写/分隔符归一） |
| full-access | 全免确认，但 **blockedCommands 通配清单全档硬拒**（内置黑名单 + 用户可配，deny 权限规则仍强制） |

诚实声明：bash 的写目标解析不了，软沙箱不做虚假承诺（对比进程级 OS 沙箱是后置项）。

### 5.2 权限系统首步：Hook(owner) 三态三层

扩展源（skill/plugin）的 hook 首次执行前查规则：**三态** allow/deny/ask × **三层** `~/.ecode/settings.json`（用户）/ `.ecode/settings.json`（项目）/ `.ecode/settings.local.json`（交互记住的落点）。求值：deny 任一层终局 > 逐层首个命中 > 默认 ask。无 UI 环境默认**拒绝**（fail-closed）。用户源 hook 不问（自己的配置自己负责）。

## 7. 实施勘误与修复账（2026-08-16 复核）

**终审修复批 9 项声称，逐条核对：7 项落地、2 项"声称已修实际未进代码"**：

- **P1-3（GC 竞态）虚报 → 已真修**：会话点数满时，revert 的还原前自动快照会触发治理 → 淘汰最旧点 → GC 可能删掉**正要写回的基线** → 还原静默不完整。修法：`snapshot` 拆出 `snapshotCore`（不含治理），revert 的自动快照跳过治理（延迟到下次正常快照，无害）。回归测试锁定。
- **P1-4（缺投影锚）虚报 → 确认不修**：终审声称"自动快照带范围内最新点的锚 + 面板兜底"，复核推演证明该修法会产生半截状态（§2.6），缺锚全量才是正确语义。处置 = 注释写明设计意图 + 测试锁定。

**同批发现并修复的四项**（各带测试）：

| 问题 | 危害 | 修法 |
|---|---|---|
| /undo 遇中文文件名 | `git show` 默认 quotepath 输出八进制转义路径 → cat-file 失败 → reset --soft 已执行后 rm 抛异常，留半完成态 | show 加 `-c core.quotepath=false` |
| MCP 副作用工具无快照 | MCP 写文件不在 /rewind 保护面 | adaptTool 在 callTool 前调 `onBeforeWrite([], mcp名)`——git status 近修改集兜底，loop 包装自动带锚 |
| rename 假路径解析 | porcelain -z 的 rename old 路径是独立 NUL 项，裸 slice(3) 产生假路径，撞名时误拍无关文件 | 解析前校验第三字符是空格 |
| commit 失败 stage 残留 | add 已执行而 commit 失败时，本轮 add 留在用户 index | catch 内尽力 `reset -q -- <files>` |

## 8. 新手 FAQ（真实问答沉淀）

**Q：回退是文件的全量覆盖吗？**
不是。只覆盖快照清单内的文件（每个整文件写回最早的基线），清单外一个不碰。

**Q：回退节点之前的对话也没了吗？**
恰恰相反——之前的全保留，没的是节点**之后**到回退之间的轮次（那次改动引发的整段）。语义是"回到那个时刻"，那个时刻的记忆当然都在。

**Q：被回退的聊天记录存在哪？**
哪都没存——因为从没删过。磁盘上是 append-only，回退只追加一行标记；"不传给 LLM"是每次读取时现算的过滤。

**Q：还能回到回退之前吗？**
能。选"(还原前自动)"点：文件从 rewind-auto 快照还原，对话靠缺锚全量自动复活（§2.6）。双向可逆。

**Q：每次对话都有 id 吗？**
不是对话有 id，是**每次工具调用有 id**（协议自带的 tool_use id，tool_result 靠它配对，ECode 借用当锚）。纯聊天轮没有 id、没有快照点——没改文件也就不需要回退；因此"单独退掉几轮纯文本对话"不支持（那是上下文裁剪不是文件安全网，M9 未立项）。

**Q：P6 之后用户自己还能 git 提交吗？**
随时能。P6 的约束全是单向的——管住 ECode 自己（默认不提交、只提交自己的文件、只退带 trailer 的提交），不管用户。
