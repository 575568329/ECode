## 一、总判定与翻案

### S-P0-1【根因翻案·最重】「fetch 规范」归因失实——真根因是 openai.ts 的 signal 传参位置 bug

- **主张失实**：方案 §1.1「fetch 规范：响应头一旦返回，abort 不再取消 body 流」——**错**。裸 fetch 对照实验（同机同 server）：signal 传对时，头返回 350ms 后 abort → **8ms 内 body reject AbortError + 服务器立即 disconnect**。undici 行为正常。
- **真根因（SDK 源码实证）**：`src/providers/openai.ts` 把 `signal` 混进 `create()` 的 **body 形参**（单参对象展开）；openai v7 `create(body, options?)` 只认**第二参** `RequestOptions.signal`（completions.d.ts:56-58 / request-options.d.ts:56）→ **signal 从未到达 fetch**，还以 `"signal":{}` 污染请求体 JSON。对照实验：signal 放第二参 → abort 后 4ms 流退出 + TCP 立即断；放 body → 101 chunks 全收 31s（= 方案原"证据二"）。
- **连带**：abort-repro 复现脚本 client.mjs 照抄了同一传参错误——**它复现的是 ECode 自己 bug 的症状**。入库哨兵前必须改传法，否则锁死错误行为。
- **修复（一行）**：signal 挪 `create(body, { signal })` 第二参。免费获得：静默流（零 chunk 挂死）场景 Ctrl+C 立即停（逐 chunk 检查在该场景没有执行机会，原方案无解）；P0-B 看门狗的 stall abort 才真正能解除挂起的流读。
- **教训（方法论）**：复现脚本的传参形态必须对照 SDK 类型签名核过再当证据。

### 逐 chunk 检查设计本身成立（实证）

三层结构实验（SDK→provider generator→消费者，ECode 同构）：abort 后下一 chunk 到达即 break → generator return() 传播 → **服务器立即 disconnect**；纯 break（不 abort）同效。代码走查：break 走既有 isAborted 固化路径（loop.ts:326→342-351→453-474），部分产出/占位 tool_result 配对/stopReason=aborted 全链通畅，与迭代顶部检查（L198）分工如方案所述。

## 三、P1（修订应改，共 11 项）

**流链路（心脏+实证）**：
- P1-1 重试与 loop 层 MAX_RETRIES=3 退避叠加无总账（最坏 4 轮×2 请求=8 次）；二次 stall 报错应标 `retryable:false` 走温和终止——stall 是端点故障，回喂模型自纠无意义且与空响应轮防重试风暴哲学（loop.ts:438-447）冲突。重试放 provider 层的唯一理由是压缩链/子代理链也受益，需写明取舍。
- P1-2 重试期间用户 Ctrl+C 未定义：重试前必查 `req.signal.aborted`，已断则放弃。
- P1-3 计时器重置锚点必须统一为**内容性 delta**（text/thinking/tool_use_delta）——按协议 chunk 重置则心跳/空帧假喂狗（智谱保活形态未核验，真机门补抓包）。
- P1-4 验收门「≤1s」实际依赖 P0-1 修复（逐 chunk 检查的时延=下一 chunk 间隔，深思考可 >1s）；signal 修对后 abort 直接解除挂起（4ms）。
- P1-5 中断轮 usage 漏账扩大化：逐 chunk break 跳过 flush → 中断轮 usage 永不上报（usage 恒在流末），高频 Ctrl+C 下 M12 token 统计从偶发漏变常态漏——入方案明示取舍。
- P1-6 压缩链盲区：summarize.ts:218 独立 for-await 同样受害于传参 bug——signal 修复自动覆盖，逐 chunk 检查不覆盖（那边无 loop），方案补一句。

**TUI（性能）**：
- P1-7 案 1 退化场景：尾部单逻辑行超宽（minified JSON 25KB→300+ 物理行）时增量缓存只对已完成逻辑行有效，进行中尾行每帧全量重 wrap——恰是 M14-V2 要治的病态。修正两选一：尾行「稳定物理行前缀」缓存（需单测钉住"追加不影响前缀"的 wrap-ansi 行为防版本漂移）/ 尾部行倒推截断。
- P1-8 方案漏了更烫路径：thinking 帧不走 16ms 合帧直接 setActive（TuiApp.tsx:656-658）+ activityDetail 每帧对思考全文 `Array.from` 码点化再取尾 2000（:1833-1841）+ stripUntrustedAnsi 尾段全量扫描 + 80ms spinner tick 放大——**只修 foldStreamText 压不住长思考会话**。修法便宜：字符串 slice 尾取 + thinking 并入合帧。
- P1-9 TimelineView 每帧手工重建 tool 对象（:123-139）破坏引用恒等设计锚 + ToolLine 无 memo——透传 `e.tool` + memo 化，两行级，并入批 2。
- P1-10 验收门「pty 探针 80-delta 已有」失实：该探针同步瞬间发出（合帧压成个位数 flush）、~4.7KB 文本量、零 RSS 断言——**必须新建**专用探针（25ms 间隔滴流+25KB×N 轮+TUI 自报 rss/heapUsed 轮询断言，消 Windows 孙进程归属问题）；「轮间回落」留 GC 窗口（轮末后 5-10s 取最小或 ≤峰值×70%）否则 flaky。heapUsed 单值判别力不完备（含未回收垃圾），需 --expose-gc 强制 GC 对照进 /doctor。
- P1-11 B1 恒留的宽度账没写明（⚠ full-access 13+分隔符 3=16，avail 有 max(20,·) 保底恒放得下）——不写清保底推理，实施者漏了会破「StatusBar 恒 1 行」帧账触发 win32 全清。

**产品/核验（其余）**：
