## 一、M6 定位与三支点总览

### 1.1 M6 = 把 P3 三个「远期挂载点」长出来

总纲 [`00-开发规划`](../总纲/00-开发规划[进行中].md) §325 明确 M5+ 远期（P3）= 支点 13 + 22 + 23。功能架构 §第一部分定这三个为 **P3（远期）**，且当前状态均为 ⬜ 未开始。M6 的使命就是把它们从「架构图上的框」变成可用的能力。

| 支点 | 一句话 | 核心价值 | 优先级 |
|------|--------|---------|--------|
| **13 Skills** | 可复用工作流「菜谱」（手写 + 自动生成） | 把一次性摸索的成功流程沉淀成可复用资产 | P3 |
| **22 模型路由** | 任务分级派不同模型（复杂→强 / 简单→省） | 能力与成本的最优平衡 | P3 |
| **23 多渠道接入** | 把对话从终端扩展到 Web / IM | agent 能力走出终端，触达更多场景 | P3 |

### 1.2 三支点的共同红利：复用主干道，不造新循环

延续 M5 的核心原则（[`M5-实施方案`](./M5-实施方案[待实现].md) §1.2），M6 三支点同样**复用核心 loop、不动核心**：

| 复用资产 | Skills 怎么用 | 模型路由怎么用 | 多渠道怎么用 |
|---------|--------------|--------------|-------------|
| `runAgentStream`（`src/agent.ts`） | 不动（Skill 是 prompt 注入，不是新循环） | 不动（路由在调用前选模型，注入 opts.provider/model） | **不改**（多渠道是「外部→agent」的新入口，复用同一循环） |
| Provider 层（`src/providers/`） | 不直接用 | **核心消费方**（按路由选 provider+model） | 不直接用 |
| 事件流 `AgentEvent`（`src/agent-events.ts`） | 不用 | 不用 | **渠道适配器消费**（WS 推给 Web/IM） |
| 权限流水线（M4） | Skill 执行的工具仍过闸 | 不用 | 渠道侧鉴权（独立于工具权限） |
| Session（`src/session.ts`） | 不独立存 | 不用 | **每渠道独立 session**（复用支点6） |

**对核心的侵入（审阅 F1/F2 修正）**：`provider`/`model` **现状已在 `RunAgentStreamOptions`**（`src/agent.ts:127` model / `:135` provider，M2/M3.5 落地，**非 M5 阶段0 才加**）。模型路由的「全局 / Skill / 子代理」三触发点在**调用前注入** opts、**不改循环**；但「压缩摘要」触发点需**轻微侵入 `runAgentStream` 内部的 `compressOpts` 构造**（`agent.ts:299` 把 `resolvedModel` 换成 `resolveModelForScenario('compress')`），同 M5 阶段0 改 tools 注入级别（见 §22-T2 + [审阅清单](./M6-文档审阅问题清单[待审阅].md) F2）。

### 1.3 前端维度：TUI 是现状，Web 是决策

**关键事实**（已核实）：ECode 当前是**纯 Ink TUI**（React 渲染到终端）。`package.json` 依赖仅 `ink@7` + `react@19`，**无** react-dom / vite / zustand / shadcn / tailwind。`src/ui/` 下 15 个组件全是终端组件。

> ⚠️ CLAUDE.md §4.2「本项目前端已于 2026-06-05 从 Vue 3 重构为 React 19 + Zustand + shadcn/ui + Tailwind v4 + Vite」——这套 **Web 栈不是 ECode 现状**。它要么是 (a) 为多渠道 Web 前端预埋的技术指引，要么是 (b) 跨项目通用模板的残留。**这是 D2 决策要澄清的根本问题**：M6 要不要把这套 Web 栈真正引入 ECode。

因此本文档的「前端 UI 交互」分两档设计：
- **TUI 交互**（所有支点必做，复用 `src/ui/` 现有组件）；
- **Web 交互**（仅当 D2 选 B 才做，新建独立前端工程）。

## 二、支点 13 Skills —— 技术选型

### 13-T1：格式 = SKILL.md + YAML frontmatter（抄三家事实标准）

**结论**：Skill 文件 = Markdown 正文 + YAML frontmatter，与 Claude Code / OpenClaw / opencode 三家完全一致的格式。

**理由**：
- **零成本跨工具生态兼容**：用户写的 SKILL.md 能被三家工具直接识别，反之亦然。这是功能架构 §支点20 撤销插件系统时论证过的「SKILL.md 三家事实标准」红利。
- 对齐 `agentskills.io` 规范（CC 子代理 frontmatter 17 字段的研究见 [`M5-方案解析`](./M5-方案解析[待实现].md) §子代理 frontmatter；Skill frontmatter 是其子集）。
- 与 M5 子代理的 `.ecode/agents/*.md` 同构（都是 frontmatter + 正文），用户心智统一、loader 逻辑可复用。

### 13-T2：两种来源，手写先行、自动生成后置

**结论**：阶段 1 做**手写**（用户/团队写 SKILL.md），阶段 2 做**自动生成**（agent 总结经验沉淀）。

**理由**：
- 自动生成的**归纳**依赖 LLM 调用（见 13-T5），且**触发依赖 M5 Hooks 的 Stop 事件**（M5 未实现则无法触发）→ 阶段 2 硬依赖 M5。
- 手写 SKILL.md 是纯文件投放 + prompt 注入，**零 LLM 依赖、零 M5 依赖**，可独立先落地。
- YAGNI：先让用户能手动沉淀流程，验证 Skill 价值，再做自动归纳。

### 13-T3：注入方式 = 懒加载（catalog 在先、正文按需）

**结论**：启动时只把每个 skill 的 `name` + `description` 拼进 system prompt（catalog，一行一个），**触发后才读正文**注入。

**理由**：
- **防 prompt 爆炸**：CLAUDE.md 是全量注入（一份文件），但 Skill 数量无上限——全量注入会撑爆主上下文。catalog 只放 name+description（每条 ~一行 token），便宜。
- 与 M5 子代理 catalog 同构（[`M5-实施方案`](./M5-实施方案[待实现].md) §阶段1 `buildAgentsCatalog`），loader 逻辑可复用。
- 「按需注入」是与 CLAUDE.md「全量注入」的关键区分——Skill 是可复用工作流，不是每次都要看的全局指令。

### 13-T4：触发 = 手动 `/skill` + LLM 自动匹配，两个都做

**结论**：用户手动 `/skill <name>` 调用 + LLM 根据 description 自动匹配触发，**两条路径都做**。

**理由**：
- 手动路径满足「我就要用这个流程」的确定性需求。
- 自动匹配让 LLM 在看到任务时主动用合适的 Skill（catalog 里的 description 就是给 LLM 看的匹配依据），降低用户认知负担。
- 两者复用同一套「读正文→注入」逻辑，只是触发源不同（用户命令 vs LLM 决策）。

### 13-T5：自动生成归纳 = LLM（非正则），proposal 审批队列

**结论**：自动生成的 Skill **不直接落盘** → 进 proposal 审批队列 → 安全扫描 → 用户 `/accept` 才转正。归纳用 LLM（非正则）。

**理由**：
- **OpenClaw 教训**（[`OpenClaw参考研究`](../调研/20260806085241_OpenClaw参考研究[已完成].md)）：OpenClaw 的「skill 自动归纳」实际是**纯正则匹配**，假自动——总结工作流必须用 LLM 理解语义，正则只能套模板。ECode 不抄这一坑。
- **质量命门**：agent 自动生成的内容若直接落盘 → 可能固化错误流程 → 下次照着错菜谱干 → 越错越远。必须人工 `/accept` 把关。
- 复用 M4 的「危险操作先问」心智（proposal = 待审批态，类比 permission 的 ask）。

### 13-T6：审批 UI = 复用 `permission-dialog` 模式 + `/accept` 斜杠命令（D4 推荐 A）

**结论**：proposal 审批复用现有 `src/ui/permission-dialog.tsx` 的三态审批弹窗模式 + 新增 `/accept`、`/reject` 斜杠命令批量处理队列。

**理由**：
- `permission-dialog` 已是成熟的三态审批组件（allow / allow_always / deny，M4 验证过），proposal（accept / reject / defer）是同构决策。
- 零新增 UI 组件成本（呼应 §1.7 不重构周边）。
- 斜杠命令路径复用支点 14 的命令注册中心（[`功能架构`](../功能方案/功能架构设计[进行中].md) §支点14）。

### 13-T7：文件投放 = opencode glob 自动发现，零 manifest

**结论**：Skill 发现用 glob（`{skills}/**/SKILL.md`），三层作用域（user `~/.ecode/skills` / project `.ecode/skills` / 系统自带模板），**无 manifest 注册**。

**理由**：
- 功能架构 §支点20 撤销插件系统时定论：opencode 的「文件投放 + glob 自动发现」是唯一值得借鉴的轻量模式，CC 45 文件 / openclaw 200 文件的 marketplace+manifest 机制过重（YAGNI）。
- 三层作用域与子代理（M5）、CLAUDE.md、自定义命令（支点14）同模式，走 `resolveDataDir()`（M5 阶段 0 抽出）。

### 13-T8：frontmatter 字段 = agentskills.io 子集

**结论**：Skill frontmatter 至少含 `name` / `description` / `allowed-tools`（可选，收紧工具子集）/ `model`（可选，模型路由前置，呼应 22-T2）。

**理由**：
- 对齐 CC agentskills.io 规范（M5 已联网核实，见 [`M5-方案解析`](./M5-方案解析[待实现].md)）。
- `allowed-tools` 与子代理 `tools:` **语义同（工具子集收紧），命名异**——Skill 对齐 agentskills.io（`allowed-tools`），子代理对齐 CC 子代理规范（`tools`），规范源不同故命名异（审阅 I5）。
- `model` 让单个 Skill 指定模型（如「代码审查 Skill 派 Claude」），是模型路由的细粒度入口。

## 三、支点 22 模型路由 —— 技术选型

### 22-T1：决策机制 = 规则映射（非 LLM 决策）（D3 推荐 A）

**结论**：路由用**规则映射**（任务类型 / 场景 → 模型 alias），不引入额外 LLM 来决定「该用哪个模型」。

**理由**（功能架构 §支点22 已拍板）：
- **路由本身要轻**：若为「选模型」而调一次 LLM，省下的钱可能还不够这次决策的花费——本末倒置。
- 规则映射可解释、可配置、零额外成本，符合 §1.1 极简导向。
- 远期若规则不够用，可后置升级为「轻量分类器」（仍是规则，非主模型 LLM）。

### 22-T2：路由触发点 = 四处（全局 / 压缩摘要 / 子代理 / Skill）

**结论**：模型路由在四个场景生效。**全局 / Skill / 子代理**三触发点在**调用 `runAgentStream` 之前**注入 `opts.provider/model`（现状已支持，`agent.ts:127/135`），不改循环；**压缩摘要**触发点需轻微侵入 `compressOpts` 构造（审阅 F2）：

| 场景 | 派谁 | 决策来源 |
|------|------|---------|
| 子代理派发（M5 支点9） | 各子代理按人设 `model` 字段 | agent frontmatter `model`（M5 已预留） |
| 上下文压缩摘要（支点4） | 便宜模型（摘要不需强推理） | 规则：compress → cheap alias |
| 全局主对话 | 强 / 默认模型 | config `defaultModel` 或 CLI `--model` |
| Skill 执行（支点13） | Skill 指定模型 | skill frontmatter `model`（13-T8） |

**理由**：
- `provider` / `model` **现状已在 `RunAgentStreamOptions`**（`agent.ts:127/135`，M2/M3.5 落地，**非 M5 阶段0**）→ 路由层在**构造 opts 时**填入即可（全局/Skill/子代理三触发点 `runAgentStream` 内部零改动）。
- 压缩摘要用便宜模型是明确的成本优化点：`compressMessages`（`src/context-manager.ts`）现用主模型，切便宜模型省一次强模型调用。
- 子代理 / Skill 的 `model` 字段是「声明式路由」，最细粒度也最自然。

### 22-T3：复用 Provider 层（支点5 已就绪）

**结论**：路由层**不新建模型抽象**，直接复用 `src/providers/` 的 `listAvailableModels()` / `getContextWindow()` / `hasCapability()` + factory 按 alias 解析 provider+model。

**理由**：
- 支点5（Provider 抽象）已是 ✅ 完成态，多模型能力齐备，路由只是「在已有模型池里选一个」。
- 路由层 = alias（如 `cheap`/`strong`/`reasoning`）→ 具体模型 ID 的映射表，纯配置。

### 22-T4：成本计算依赖支点 17 单价表

**结论**：路由的「省钱」效果可见，依赖支点 17 的 `ModelConfig.cost` 四绝对值字段（input/cacheRead/cacheWrite/output 单价）。

**理由**：
- 没有单价表，「派便宜模型省了多少」无从量化 → 路由价值不可见。
- 支点 17 成本追踪重做是 P1（功能架构 §支点17），M6 路由与之协同：路由省的钱由支点17 的成本公式算出来展示。
- **支点17 当前 🟡**（成本追踪重做中，`ModelConfig.cost` 四绝对值字段尚未落地，`src/providers/types.ts:124-130` 无 cost）→ 路由的「省了多少」可见性**后置于支点17**；路由本身（按规则派模型）不依赖支点17，可先工作（审阅 I2）。

### 22-T5：配置 = config.json 加 `routing` 块

**结论**：路由规则进 `~/.ecode/config.json` 的 `routing` 块（alias → 模型 ID 映射 + 场景规则），**不引入新注册表**。

**理由**：
- 路由是「轻量参数」（功能架构 §支点15 配置边界），属 config.json 职责，非安装态（不像 MCP/Skill 走独立注册表）。
- 与压缩参数（支点4）、权限规则（支点7）同属 config 块，统一收口 `ECodeConfig`。

## 四、支点 23 多渠道接入 —— 技术选型（含核心决策 D2）

### 23-T1：核心决策 D2 —— 前端形态

**这是 M6 最大工作量决策**，三选一：

| 方案 | 做什么 | 工作量 | 推荐度 |
|------|--------|--------|--------|
| **A：纯 CLI 服务化** | agent 后端起本地 HTTP+WS 服务暴露对话 API，**不建 Web UI**；渠道适配器（含未来的 Web/IM）各自实现前端 | 小（后端服务化 + 无头模式扩展） | ⭐ **推荐先做** |
| **B：新建 Web 前端** | 引入 CLAUDE.md §4.2 全套栈（React19+Zustand+shadcn+Tailwind v4+Vite），WebChat 作为第一个渠道 | **大**（一整套 Web 工程 + WS 实时同步） | 按需 |
| **C：IM 优先** | 先做企业微信/飞书/钉钉 bot 适配器 | 中（各平台 bot API 适配） | 按需 |

**推荐 A 先行的理由**：
- **服务化是所有渠道的公共前提**：无论 Web 还是 IM，都要先有「agent 后端能被外部调用」的能力。A 做完，B/C 只是「再加一个前端/适配器」。
- **YAGNI**：核心 REPL（M3.5）仍在打磨，P1 支点（无头/后台任务/多模态）尚未完成，过早分散到 Web 工程风险高。
- **A 本身有价值**：本地 HTTP+WS 服务让 ECode 能被脚本/其他工具/IDE 插件调用（无头模式支点1 的网络版）。
- B 的 Web 栈（CLAUDE.md §4.2）当前 package.json 未装——若用户确认要做 Web，M6 需显式引入这套依赖（影响 §9.3 跨平台原生二进制评估）。

### 23-T2：后端服务框架 = 选型对比

| 选项 | 优点 | 缺点 | 评估 |
|------|------|------|------|
| **原生 `node:http`** | 零依赖（§1.1 极简）、可控 | WS 要手搓、路由样板多 | 候选（最小） |
| **hono** | 轻量、TS 原生、Web 标准、跨运行时 | 需新依赖（纯 TS 无原生二进制，符合 §9.3） | ⭐ 倾向 |
| fastify | 生态成熟、插件多 | 偏重、依赖多 | 过重（YAGNI） |
| express | 老牌、文档多 | 回调风格、偏旧 | 不选 |

**倾向 hono 或原生 http**（二选一，待 D 决策）：hono 省 WS/路由样板，原生 http 零依赖。两者都无原生二进制（§9.3 红线安全）。

### 23-T3：实时通信 = WebSocket，复用事件流

**结论**：渠道侧实时通信用 WebSocket，**直接推送 `AgentEvent` 流**（支点2 事件流解耦的红利）。

**理由**：
- `runAgentStream` 是异步生成器，本就 yield 事件流——WS 把事件流透传给渠道前端，**零额外抽象**。
- TUI（Ink）和 Web 前端消费的是同一份 `AgentEvent` 类型，前端只需把事件渲染成对应 UI（与 TUI 的 reducer 同源）。
- 半双工 HTTP 轮询不适合流式（text_delta 要逐字推），WS 是天然选择。

### 23-T4：会话路由 = 多渠道独立 session

**结论**：每个渠道连接对应一个独立 session，**复用支点6 的数据持久化层**（`src/session.ts` 的 `saveSession`/`loadSession`/`listSessions`），渠道间隔离。

**理由**：
- 多渠道并发时（终端 + Web + IM 同时连），不能共用一个 messages 流——会串话。
- 支点6 session 是 ✅ 完成态，但是**无状态纯函数库**（save/load/list，无运行时 session 表/锁）——提供数据持久化层；**运行时隔离（连接↔sessionId 映射 + 同 session 串行排队锁）由 `session-router` 自建**（审阅 F4/I7，呼应方案解析 §3.4 并发红线）。
- 续接靠 `agent.ts` 的 `ResumeContext`（messages 传回 runAgentStream），**不是 session.ts 方法**（session.ts 无 resume 接口，审阅 F4）。
- **与功能架构的调整**（审阅 I6）：功能架构 §支点23 原写「多渠道并发需子代理隔离」，M6 改用 session.ts 隔离——子代理隔离是 L3 能力层维度，多渠道是 L1 入口层维度，不混；且支点6 已 ✅，非多渠道硬依赖。

### 23-T5：IM 平台调研（仅当 D2 选 C）

**结论**：企业微信 / 飞书 / 钉钉有官方 bot API（可行），**微信个人号无官方 bot API（硬约束）**。

**理由**（功能架构 §支点23 已记）：
- 微信个人号只能靠非官方协议（封号风险），不做。
- 飞书 bot API（长连接 / Webhook）最完善、文档最好 → D5 推荐飞书。
- 各平台适配器是独立模块（`src/channels/feishu.ts` 等），按需做，YAGNI 不预建。

### 23-T6：与支点 1 无头模式的关系

**结论**：无头模式（`ecode -p`，支点1 P1）是**本地管道型入口**，多渠道是**网络型入口**——同属入口族，都复用 `runAgentStream` 不改核心。

**理由**：
- 功能架构 §支点1 已把无头/管道定位为「出口消费层」（`for await` 消费事件流）。多渠道是同一思路的网络版：把事件流推给网络消费者。
- 无头模式（支点1）先落地的话，多渠道的服务化能复用其「纯输出消费层」模式。

### 23-T7：安全 = 本地绑定 + token 鉴权 + 凭证独立

**结论**：本地 HTTP+WS 服务绑定 `127.0.0.1`（不暴露公网）+ 连接 token 鉴权 + 渠道凭证（bot secret 等）独立存储（呼应 §9.2）。

**理由**：
- agent 有文件读写/bash 权限，服务一旦暴露公网 = 远程代码执行。默认 `127.0.0.1` 是硬安全网。
- token 鉴权防本机其他进程随意连。
- bot 凭证走独立注册表（不进 config，防替换误删，同 MCP 模式）。

### F-T2：若做 Web（D2 选 B）= CLAUDE.md §4.2 全套栈

**结论**：Web 前端用 CLAUDE.md §4.2 指定的栈：React 19 + Zustand + shadcn/ui + Tailwind v4 + Vite。

**理由**：
- 这是用户在项目 CLAUDE.md 明确写下的前端规范，若做 Web 应遵循。
- Zustand 按领域拆 store（`taskStore`/`chatStore`/`uiStore`），与 TUI 的 reducer 思路同构。

- **代价**：M6 需新增 react-dom/vite/zustand/shadcn/tailwind 依赖（当前未装），且 Vite 构建链要评估 §9.3 跨平台原生二进制（如 esbuild/rollup 平台包）。

### F-T3：共享层 = AgentEvent + runAgentStream 渠道无关

**结论**：无论 TUI / Web / IM，底层共享 `AgentEvent` 类型 + `runAgentStream`——前端只是「事件消费 + 渲染」的渠道适配器。

**理由**：
- 这是支点2「事件流解耦核心与呈现」的核心红利（功能架构 §4.2）。核心对 UI 零依赖 → 同一核心驱动 REPL / 无头 / Web / IM。
- M6 的前端工作 = 写「事件 → UI」的渲染映射，核心循环一行不改。
