# M13 远程控制与 IM 接入调研（UI 组件库 / 远程网络架构 / 飞书微信通道）

- 日期：2026-08-24
- 状态：已完成
- 背景：用户重定调核心目标——**"在家用移动端控制公司电脑的 ECode 工作，并通过飞书和微信远程交流"**。远程从"非目标"变为核心目标，本调研覆盖三块：UI 组件库选型（看优秀项目用没用框架）、远程网络架构（公司内网→家）、IM 双通道（飞书/微信）。
- 消费方：M13 多端方案 v1.2 修订（远程目标重定调 + IM 批次），拍板点见 §5。

## 1. UI 组件库——三库实证 + 选型

| | harness | orca | opencode |
|---|---|---|---|
| 框架 | React 18 + Vite 6 | React + Tailwind v4（桌面）/ RN+Expo 55（移动） | SolidJS（组件库给桌面端） |
| 组件库 | **零——全手写**（CSS Modules，ui-primitives 依赖仅 micromark/shiki/katex/clsx） | **shadcn 全家桶**：`shadcn + radix-ui + class-variance-authority + lucide-react + tw-animate-css`；`components/ui/` 30+ 组件（button/dialog/dropdown/popover/select/sheet/command/scroll-area/card/tooltip…） | **kobalte（headless）+ Tailwind v4 自组**（Solid 生态无 shadcn 正统） |
| 移动端 | 无专项 | RN 独立 UI（gesture-handler/reanimated/safe-area），与桌面共享逻辑不共享 UI | — |

**ECode 推荐：shadcn/ui**。理由：①与已定 React 19 + Tailwind v4 栈零缝契合（shadcn 本身就是 Radix headless + Tailwind 的组合范式）；②orca 实证 AI 工作台类应用用得住；③ECode 组件需求约 10 个（button/input/dialog/dropdown/select/collapsible/scroll-area/sheet/card/tooltip）shadcn 全有现成代码（copy-in 型，非 npm 黑盒依赖）；④移动端列表态用 sheet/响应式类即可（不做 RN——Q6 拍板响应式 Web 维持）。harness 的零库手写是 35 个 ui-* 包的重投入路线，不学；其 composer-takeover 审批交互等**模式**照抄（见 Web 技术栈调研 §4）。

## 2. 远程网络架构——"家 → 公司内网电脑"五条路

| 路 | 成本 | 公司网穿透 | SSE 支持 | 维护 | 评价 |
|---|---|---|---|---|---|
| **Tailscale** | 免费（6 用户不限设备，2026 v4 定价） | ✅ DERP 走 TCP 443，多数企业防火墙可过（激进 DPI 例外）；无需开端口 | ✅ **L3 透明**——对 HTTP/SSE/WS 全透明，零应用层适配 | 装一次忘掉 | **主路线** |
| Cloudflare Tunnel | 免费无需 VPS（正式隧道需域名） | ✅ 出站 443 | ⚠️ 实证坑多：100s 524 超时（免费/Pro 不可调，Enterprise 才能到 6000s）、SSE 缓冲（cloudflared issue #199/#1449，2026 社区仍在报）；需 cache bypass + 15-20s keepalive | 低 | 备选（ECode 15s 心跳已备，但缓冲坑不控） |
| frp | 需公网 VPS+域名 | ✅ | ✅ | 中（自维护服务端） | 对照组，不如上面两条 |
| 自建中继+配对（orca pairing 式：设备配对码+E2EE+中继 VPS） | VPS+域名 | ✅ | 自控 | 高 | 远期官方中继选项（M12 per-device token 升级位），个人项目暂不做 |
| 公网服务器跑 daemon | — | — | — | — | ❌ 语义错误：ECode 操作的是运行侧文件系统，部署到云=操作云的文件 |

**推荐**：Tailscale 主路线（`ecode serve` 文档引导一节"远程访问"：装 Tailscale → tailscale IP 直连，daemon 零改动）；CF Tunnel 备选写明 SSE 坑；自建中继远期。**安全注意**：Tailscale 下 daemon 仍保留密码/token 鉴权（tailnet 内也防其他设备）；公司电脑装 VPN 客户端的 IT 合规性由用户自担（文档提示）。

**关键架构洞察**：飞书走长连接后（§3），**IM 通道完全不需要网络穿透**——"远程"的网络问题只影响 Web/PWA 客户端；IM 是开箱即达公司电脑的天然远程通道。

## 3. IM 双通道

### 3.1 飞书（远程主通道，条件全齐）

- **企业自建应用 + 长连接模式**：飞书 SDK 建 WebSocket 全双工通道收事件——**服务器只需能出站访问公网，无需公网 IP/域名/回调 URL**（公司电脑零暴露）。官方文档：[使用长连接接收事件](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-guide/overview)、[长连接接收回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/step-1-choose-a-subscription-mode/configure-callback-request-address?lang=zh-CN)。
- **消息卡片按钮回调**（审批的完美形态）：新版卡片交互回调走长连接，用户点"允许/拒绝"直接回传——[卡片回调指南](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/handle-card-callbacks?lang=zh-CN)；卡片支持**更新**（流式输出可逐段编辑卡片模拟）。
- 限制：长连接仅企业自建应用；每应用 ≤50 连接；消息 3 秒内需处理完（超时走异步回复）——Agent 长任务天然异步（先回"收到，跑着"，完成再推卡片）。
- 个人可用性：个人版飞书可建自建应用（个人/小团队免费）。

### 3.2 微信（2026 格局大变——旧拍板前提已失效）

**旧拍板"个人微信不做（封号）"的事实基础已变**：

| 方案 | 合规性 | 现状 |
|---|---|---|
| **官方 ClawBot（iLink 协议）** | ✅ 官方 | **2026-03 微信正式开放个人号 Bot API**（经 OpenClaw 框架对接，扫码登录/收发消息 HTTP 接口；"无需 Hook、不封号"）——[2026 微信机器人开发指南](https://zhuanlan.zhihu.com/p-2019677743126704371)。新出，能力有限（约 5-7 个接口），成熟度待观察 |
| 企业微信自建应用 | ✅ 官方 | 稳定合规主流：应用消息 API（文本/卡片）完整；**回调需公网 URL**（无飞书式长连接——需 Tailscale/CF 前置或轮询）；2 万人次/分钟频控；[发送应用消息](https://developer.work.weixin.qq.com/document/path/94677) |
| 公众号（个人=订阅号） | ✅ 官方 | 48h 窗口/5 条限制，被动回复为主，双向对话弱 |
| wechaty/web 协议个人号 | ❌ 非官方 | web 协议基本失效、封号实证；chatgpt-on-wechat（43k★，已升级 CowAgent）**已移除个人微信渠道**——社区用脚投票 |

### 3.3 IM gateway 架构考虑（ECode 侧设计要点）

- **IM gateway = 第三种客户端形态**：接 mux 协议（与 Web 同构——协议即唯一契约的又一次兑现），不是独立系统。
- 会话映射：单聊 bot ↔ ECode 会话 一对一绑定（`/new` 新建、默认续最近会话）；群聊暂不做（@触发+会话隔离复杂度高，YAGNI）。
- 审批转卡片：approval 可答帧 → 飞书卡片按钮（允许/拒绝/始终允许三键，sensitive 不给始终键）/ 微信文本选项（回复数字）；respond 回 mux。
- 流式：IM 无流式——轮末推送完整回复（或飞书卡片分段编辑更新，观察后定）；跑长任务时先回执"进行中"。
- 参考蓝本：**OpenClaw**（IM channels 框架，飞书+ClawBot 双通道实践文档齐全；本地 `D:\study\openclaw` 是空 git 壳——IM 批立项时拉最新源码细读）。

## 5. 拍板点（待用户定）

1. **微信路径**：A 官方 ClawBot/iLink（新、个人号直达、能力有限待观察）+ 企微兜底；B 只做企微自建应用（稳、但个人用需注册企业+回调需公网前置）；C 先只做飞书，微信观察 ClawBot 成熟度后进。**建议 A**（飞书先行做深，微信用 ClawBot 轻接——同一 gateway 架构双适配）。
2. **IM 批排期**：进 M13 尾部（W8 飞书 + W9 微信，+3~4 人天，总 ~15-16）vs 拆 M14（M13 维持 12 人天先交付 Web/远程）。**建议**：飞书进 M13 尾（远程交流刚需、长连接免穿透是最大卖点）；微信 ClawBot 视成熟度 M14。
3. **远程网络主路线确认**：Tailscale（公司电脑装客户端，IT 合规自担）是否接受；不接受则 CF Tunnel（SSE 坑文档说明）或 frp（需 VPS）。
