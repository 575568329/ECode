# 全屏查看与超屏根治可行性调研

> 状态：进行中（可行性判断完成，待拍板实施）
> 触发：用户两问——①「能像 Claude Code 一样切到另一个页面看吗？滚动状态保留、退出回到对话框继续，中断语义不变」②「如何一劳永逸解决超屏问题？如果解决了，工具信息就能直接全展开了吧」
> 约束：本文档只调研判断，未改任何代码。

---

## 1. 需求还原

| # | 诉求 | 本质 |
|---|------|------|
| 1 | 切到独立页面看子代理/工具输出，退出回到对话框继续，滚动状态保留，中断语义不变 | **临时全屏视图**（进入不破坏主界面、退出完整恢复） |
| 2 | 一劳永逸解决超屏，之后工具信息直接全展开 | 消除「对话流内展开受行数预算钳制」的根源 |

## 2. 现状与根因（ECode）

- 渲染模型：Ink 主缓冲区（main buffer）追加式输出——历史固化进终端 scrollback（Static），当前轮动态区每帧重绘。**动态区帧高 ≥ 终端行数时 Ink 触发 ESC[2J+3J+H 全清**（丢 scrollback、滚轮回顶）——这是 V 线全部预算防护（viewport/allocateDynamic/截断）针对的根因，硬指标「全程无 3J」已探针达成。
- 现有查看通道：Ctrl+T → /output 面板（子代理 transcript/后台任务日志/工具全文三源），↑↓ 行滚 + PgUp/PgDn + g/G + / 搜索，运行中自动跟随——**滚动与内容已就绪，缺的是「独立页面」的隔离感与恢复感**：面板目前渲染在主界面下方区域（与对话同屏共存、随动态区重绘），不是独立全屏页；关闭后无「回到之前状态」的仪式感；offset 关闭即失。

## 3. CC 实证（claude-code-main 源码级）

CC 正是这么做的，证据链：

- `src/ink/components/AlternateScreen.tsx`：**临时全屏组件**，注释原文「Safe for use in **ctrl-o transcript overlays** and similar temporary fullscreen views — **the main screen is preserved**」。机制：
  - mount：写 `ENTER_ALT_SCREEN(DEC 1049) + ESC[2J + ESC[H`（+ 可选 SGR 鼠标跟踪），通知 Ink 实例 `setAltScreenActive(true)`（渲染器把光标锁在视口内；signal-exit 兜底退出 alt screen）
  - unmount：`EXIT_ALT_SCREEN(1049l)` + 关鼠标跟踪——**主缓冲区内容原样恢复**
  - 约束：alt buffer **无 scrollback**，内容高度必须约束在终端行数内，溢出走自绘滚动（flexbox/overflow scroll）——即「全屏视口内 offset 渲染」，与 OutputViewer 已有模型一致
  - **鼠标滚轮**：SGR mouse tracking（?1000h）开启后 wheel 事件作为按键上报，可直接驱动滚动
- `src/components/FullscreenLayout.tsx` + `Messages.tsx`：CC 的消息列表另有全屏布局形态（`isFullscreenEnvEnabled` 开关），且带 **tmux 降级探测**（tmux control-mode 下禁鼠标/降级——`utils/fullscreen.ts` 专文处理，含 `-CC` 模式 env 启发式 + 探针 backstop）
- 结论：用户描述的交互在 CC 里就是 **alt-screen 临时视图**，非幻想功能。

## 4. Windows 兼容性（网上调研）

- **Windows Terminal / conpty 完整支持 DEC 1049**（`CSI ?1049h/l`），语义与 XTerm 扩展一致（光标保存 + 缓冲切换）。官方参考：[Console Virtual Terminal Sequences — Microsoft Learn](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)；社区确认：[Super User: Does Windows Terminal not have alternate screen?](https://superuser.com/questions/1863323/does-windows-terminal-not-have-alternate-screen)
- 已知边缘：[microsoft/terminal#12329](https://github.com/microsoft/terminal/issues/12329)（个别版本切缓冲后无文本显示的 case）——列入实施期探针验证点；[buffer 切换时 STD_OUTPUT_HANDLE 不变](https://github.com/microsoft/terminal/discussions/15920)对 ECode 无影响（走同一 stdout 写）
- tmux：CC 专门做了 control-mode 降级——ECode 用户主力环境是 Windows Terminal/PS，tmux 场景少；首版可「检测到 TMUX env 时不开鼠标跟踪、其余照常」，不阻塞

## 5. 方案 A：Ctrl+T 面板 alt-screen 化（推荐，对应诉求 1）

### 5.1 机制

面板（OutputViewer/OutputListPage）挂载时写 DEC 1049 序列进入 alt buffer，TuiApp 渲染树在 overlay 打开期间**只渲染面板**（主对话树不渲染——React 树级切换，避免主 UI 每帧重绘搅乱 alt buffer）；卸载时写 1049l 恢复主屏。Ink 的重绘写全部落在「当前缓冲区」，无需 Ink 新 API（对照 CC 的裸序列组件方案）。

### 5.2 逐条对应诉求

| 诉求点 | 实现 | 可行性 |
|---|---|---|
| 独立页面 | alt buffer 全屏视口 | ✅ 终端原生机制，CC 同款 |
| 退出回到对话框继续 | 1049l 恢复主缓冲（主对话内容从未离开主缓冲，原样恢复） | ✅ 机制保证 |
| 滚动状态保留 | offset 从组件 state 提升为模块级缓存（按 source key 记忆），再进恢复上次位置 | ✅ 纯状态管理 |
| 中断语义不变 | 面板开着 loop 照常跑（现状即如此）；Ctrl+C 在面板内仍中断轮次（需在面板 useInput 保持 Ctrl+C 处理或放行 useInterrupt） | ✅ 现状+小接线 |
| 子代理实时 | 500ms mtime 轮询已有；alt buffer 内同样每帧重绘 | ✅ |
| 鼠标滚轮（用户明确要） | SGR mouse tracking（?1006h）→ wheel 事件驱动 offset | ✅ 一期必做——ECode 的 Ink（npm 版）无鼠标解析（CC 是自研 fork 才有），需自实现 ~50 行：挂 raw stdin listener 解析 `ESC[<64;yM`（上滚）/`ESC[<65;yM`（下滚）→ offset ±3；Ink 不消费这些序列无冲突。降级：检测 TMUX control-mode 不开跟踪（CC 同款）；不支持鼠标的终端序列无人上报=无事件，无害 |

### 5.3 风险与实施期验证点

1. **conpty alt-screen 行为**（#12329 edge case）——探针先行：pty 下写 1049 序列、断言进入/退出帧与内容恢复
2. **Ink 树切换瞬间**：主树卸载→面板挂载的光标定位与残留（CC 的 setAltScreenActive 光标锁思路照抄；exit handler 补 1049l 兜底——防崩溃后终端困在 alt buffer，黑屏假死是最恶性观感）
3. **高度约束**：面板高度必须 = rows（视口内自绘滚动），绝不能让 alt buffer 产生原生滚动
4. **F 键/搜索/跟随**：现有交互平移，无新风险
5. 工作量估计：**1.5~2 天**（AltScreen 组件 + TuiApp 树切换 + offset 记忆 + **SGR 滚轮解析** + 探针 2 个 + tmux 降级检测一期）

## 6. 方案 B：「一劳永逸解决超屏」路线对比（对应诉求 2）

| 路线 | 说明 | 判断 |
|---|---|---|
| B1 全量 TUI 化（对话整体迁 alt buffer，自绘滚动） | 超屏物理上消失（视口固定窗口） | **否决（现阶段）**：丧失终端原生 scrollback/搜索/复制——「终端即 transcript」是 CC 确立且被用户依赖的核心价值（CC 自己也保留主缓冲模式，alt 只用于临时视图）；改造成本 ≈ 重写渲染层 |
| B2 Static 区全展引导 | 历史（Static/scrollback）**天然无超屏**（append-only，永不重绘触发 3J）——历史工具组展开直接全量固化进 scrollback；当前轮动态区维持预算，轮末 commit 后进 Static | **❌ 否决（2026-08-29 用户拍板）**：历史对话全量展开工具，用户翻看时**容易看不到重点**——历史区保持收起摘要，全量查看统一走 Ctrl+T 面板 |
| B3 现状收敛（不改） | V 线预算已把 3J 压到 0；全量查看走方案 A 面板 | ✅ 与 A 组合即完整答案 |

**关键认知修正**（对诉求 2 的直接回答）：「解决超屏 → 对话流内直接全展开」这个推理方向**部分不成立**——即使超屏根治（B1），把数百行工具输出塞进对话流也只是「塞得下」，可读性仍差且丢终端原生能力；CC 的答案同样是 **transcript overlay（=方案 A）**。真正「一劳永逸」的组合是：

> **动态区（当前轮）保持预算防护（物理必要）+ 历史区（Static）收起摘要（B2 已否决——全量展开伤翻看重点）+ 全量查看走 alt-screen 面板（方案 A，独立页面）**

B2 的「历史组三态展开」增强点随拍板一并否决，不再实施。

## 7. 结论与建议

1. **方案 A（Ctrl+T 面板 alt-screen 化）可行且推荐**：CC 同款机制源码级实证、Windows Terminal/conpty 支持成熟、ECode 基建（面板/滚动/搜索/轮询）全部就绪，缺的只是「进入/退出序列 + 渲染树切换 + offset 记忆」三小块，约 1~1.5 天
2. **超屏「一劳永逸」的正确形态**：不是让对话流无限展开，而是「动态区预算 + 历史区收起摘要 + alt-screen 面板」三层各司其职；B1 全量 TUI 化现阶段否决、B2 历史全展固化用户拍板否决（翻看不到重点）
3. 实施顺序建议：A（面板全屏化）→ 真机用一段时间 → 再决定是否要 B2 的历史组三态展开
4. 实施前必做探针：pty 下 1049 进入/退出与内容恢复（conpty edge case #12329）+ 崩溃路径的 alt-buffer 兜底退出
