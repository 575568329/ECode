# 压缩架构定型调研：deepseek-harness + opencode（问题驱动）

> 2026-08-14。用户要求：不要抄实现,要理解问题/缺陷/化解/思想;压缩要插件化可扩展;算法贵精不贵多;解决切换 model 超限。
> 两个主项目：deepseek-harness（DeepSeek 官方 Agent 框架）、opencode。
> **结论颠覆**：deepseek-harness 才是压缩架构金标准（插件化），opencode 是单体。ECode 应学 deepseek 骨架 + opencode 默认策略 + 补两家空白（model 切换预检）。

## 一、deepseek-harness（dsh）——压缩架构的金标准

### 它是什么
DeepSeek AI 官方的开源 Agent 编程框架（npm `@deepseek-ai/dsh`），对标 claude-code/opencode。架构核心:**Service Definition + Provider 分离,一切皆插件**(底层 Cordis 范式)。有 Web UI + CLI + 全套 session/tool/agent/llm/skill/plan。

### 压缩做成「抽象 Service + 多 Provider 插件」
关键包(`D:\study\deepseek-harness\packages\compaction\`):
- `compaction/`(抽象):`CompactionEngine extends Service`——三方法 `compactIfNeeded`(自动)/`compactNow`(手动)/`compactRegion`(强制压区间)。这是「压缩策略」的形式化契约。
- `compaction-basic/`(Provider 1):LLM 摘要式压缩(自动触发/阈值/retain 尾巴/重试)
- `compaction-tool-result-pruner/`(Provider 2):**免模型工具结果裁剪**(独立插件)
- `spill/`(Provider 3):超大工具结果**外溢到磁盘**,模型只拿定位符+预览
- `command-compact/`:`/compact` 手动命令插件

**★ 插件化思想**:
- Strategy 接口(CompactionEngine)+ 多 Provider 独立可拔插(每个一个包)
- **组合而不耦合**:basic 引用 pruner 是**可选动态查找** `ctx.get('toolResultPruner')`——没装 pruner 照样跑
- 加新策略 = 写新插件,不动现有代码
- 触发与策略解耦:触发靠事件钩子(agent/pre-step、agent/request-error、tools/post-execute),策略不知何时被调
- 唯一子类钩:`summarize()` 留作 override 点(换摘要器只改这一个方法)

**shadow-price 协议**(比 opencode 干净):
- 所有变换(含 prune)写成带显式 shadow 语义的事件:`surfaceOp: { op:'replace', start, end }`
- 每次替换前 append 计量事件声明被盖内容的 token 价(`types.ts:80-88`)
- 投影无损承诺不被就地 mutation 破坏(对比 opencode 的 smell)

### context window 获取(模型感知,实时)
运行时按路由 provider/model 实时查:`ctx.llm.resolveModelInfo(provider, model).context.contextWindow`。阈值派生:`thresholdTokens = window * thresholdRatio`(默认 0.8)、`retainTokens = window * retainRatio`(默认 0.16)。不同模型不同策略(modelPolicies 按 provider/model 覆盖)。

## 二、opencode 投影模型——问题驱动重看(非复述)

### 投影解决的原问题
**如何在不破坏历史的前提下让模型看到的上下文变小?** 朴素做法"就地修改 messages"会丢原始内容(revert/debug/replay/审计全废)。投影=`filterCompacted` 读时变换,存储 append-only 全量,什么都没删,只是"这次请求给模型看哪些"。

### 投影的真实缺陷
1. 全量历史无限累积(存储/读取成本随会话单调增长)
2. 投影每次请求重算(O(n) 扫全量)
3. 摘要链维护——opencode 用**扁平单一锚定摘要**(buildPrompt 喂 previousSummary "Update the anchored summary"),非链式,避免漂移
4. **★ mutation smell**:prune **不是纯投影**——就地改 `part.state.time.compacted`(compaction.ts:317),serialize 渲染成"[Old tool result cleared]"。**原始工具输出真被盖掉了**,投影"无损"承诺被破坏

### opencode 怎么化解
- 重算成本:array 过滤便宜,认了
- 存储增长:隐式接受(会话有生命周期)
- 摘要漂移:单一锚定摘要代替串联
- mutation smell:idempotent flag + 序列化兜底(务实但不干净)

### 对 ECode 的启示
投影思想对(存储=真相之源,模型所见=投影),但**不要抄 opencode 实现**——抄 deepseek 的 shadow-price 协议(变换写带显式语义的事件,不就地改),投影好处全拿没有 smell。

## 三、★ 切换 model 时 context window 变化怎么救(用户核心痛点)

场景:1M 模型聊到 80 万 token,/model 切 200k——下一发必超限。

### 两家做法(都没有"切换即预压缩")
**opencode(两条路)**:
1. 主动(模型感知,但**过期代理值**):每轮 `isOverflow({tokens: lastFinished.tokens, model})`——model 是当前模型,但 tokens 是上一轮旧模型返回计数(代理值,慢半拍)
2. 反应式(被拒救场):provider 返回 context_overflow 错 → `return "compact"` → overflow 路径找上一条 user 消息**重放**(切掉之前历史+压缩+重放用户问题)

**deepseek(两条路,更准)**:
1. 主动(每步、模型感知、**实时重测量**):`agent/pre-step` 钩子 → `resolveModelInfo(currentModel).contextWindow` → `tokenMeter.measure(session)` **对当前真实历史重测** → 超阈值则发前压缩。**切 200k 后下一步自动用新窗口+重测 → 主动压,根本不发超限请求**
2. 反应式:`agent/request-error` 捕获 CONTEXT_WINDOW_EXCEEDED → overflow 路径(绕过常规阈值,先 prune 再摘要,带 maxOverflowRetries)

### 80 万→200k 单次压缩不够怎么办
两家都是**重试循环**:deepseek `compactionRetries`(迭代 compactRegion 直到低于阈值或达上限);opencode 压不动抛 ContextOverflowError 停下。deepseek 还有容错:**免模型 prune 的 durable 减量不丢弃**(摘要失败也不回滚已裁剪)。

### ★ 这是真实空白——ECode 能做得更好
两家都是"下一轮自然触发"或"被拒救场",**没有"监听 model 切换 → 立即新窗口预检 → 主动迭代压缩"**。

**ECode 补空白方案**:
1. 阈值模型感知且**实时重测量**(学 deepseek,别学 opencode 过期代理)
2. 防御纵深=主动+反应式(pre-step 检查 + provider 拒错恢复,带重试上限)
3. **★ 监听 /model 切换事件,切完立即新窗口预检**:若已超,主动迭代压缩(多次直到低于新阈值或达上限)+ 警告 + 允许 /clear 兜底
4. 迭代容错:免模型 prune durable(摘要失败不回滚已裁剪)

## 四、插件化压缩架构思想

### deepseek = 金标准
- Strategy 接口(CompactionEngine 三方法)+ 多 Provider 独立插件(摘要/裁剪/外溢各一个包)
- 可选依赖组合(basic 动态查 pruner,没装照跑)而非固定调用链
- 触发靠事件钩子,策略不关心何时被调
- 加策略=写插件,零改动现有代码

### opencode = 单体(扩展性弱)
- 单体 SessionCompaction Service,prune/select/process 私有 fn,无策略注册
- 仅扩展点:插件钩子(experimental.session.compacting 改 prompt、experimental.chat.messages.transform 粗暴变换)——加不了新策略

### ECode 插件化抽象建议(学 deepseek)
1. 定义 `CompactionStrategy` 接口:`predicate(该不该跑) + run(怎么跑)`
2. 注册制:策略注册 registry,编排器按**成本递增**排序(免模型在前:工具清除/外溢;模型驱动在后:摘要)
3. 策略间可选依赖(非固定链)
4. 触发=事件钩子(pre-turn/post-tool/on-provider-error/on-model-switch),策略不知何时被调
5. 存储/投影分离:产物写 append-only 事件+投影规则,禁止就地改历史

## 五、算法贵精不贵多——ECode 真正需要哪种

### 工具输出清除(免模型)是性价比最高的一级,必须有
- opencode prune:独立/免模型/确定性,后台 pass,从尾保留 4 万 token 工具调用、更早打 flag 清空
- deepseek pruner:独立插件,head/tail 确定性裁剪,pressure 和 overflow 路径都在摘要前先跑;spill 在源头(工具执行后)就外溢
- **为什么最高 ROI**:工具输出是 token 大户,清除不需任何 LLM 调用——免费/瞬时/确定/可逆

### 摘要是必要的但最贵
花一次 LLM 调用,最后手段。opencode 单一锚定摘要(避免嵌套漂移)值得借鉴。

### ECode 最小够用(两级,不上四级管线)
deepseek 实际 prune+spill+summarize 两三级,opencode prune+summarize 两级。ECode:
1. **第一级:免模型工具输出清除**(必做,最高 ROI)——deepseek pruner 的 shadow 事件式(干净)或 opencode prune(flag 式)
2. **第二级:LLM 锚定摘要**(必要,成本最高,仅一级不够时)——opencode 单一锚定摘要 + deepseek retain 尾巴
3. **架构预留三四级**(通过策略接口),M5 不实现:外溢到文件(spill)/反应式 overflow/model 切换预压缩——都是新插件

### ★ 架构定型一句话
> **学 deepseek 的「抽象 Service + 多 Provider 插件 + 事件钩子触发 + log/surface 分离 + shadow-price 计量」做骨架;学 opencode 的「免模型 prune 当第一级 + 单一锚定摘要」做默认策略;补两家都没做的「model 切换即预检+迭代压缩」做差异化;算法只上 prune+summary 两级,靠接口留扩展位。**
