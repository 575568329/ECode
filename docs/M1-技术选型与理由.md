# M1 · 技术选型与理由

> **本文档记录**: 项目技术选型决策过程，每个选择都有明确的理由和取舍分析。
> 技术选型服务于产品交付与自主可控，每个决策都要经得起"为什么这么选"的追问。

---

## 一、核心决策总览

| 决策点 | 结论 | 关键理由 |
|--------|------|---------|
| 语言 | TypeScript strict | 类型安全、工具调用 schema 强依赖类型 |
| 运行时 | Node.js（非 Bun） | 多端兼容、知识迁移性、生产部署零意外 |
| TS 运行方式 | 开发 `tsx` / 发布 `tsc` | dev 快速迭代 + 发布纯 JS |
| 模块系统 | **ESM** | 核心依赖 ESM 优先，避免 `ERR_REQUIRE_ESM` |
| CLI 框架 | M1 手写 → M2 `commander` → 后期 `ink` | 按需引入，不提前抽象 |
| 交互提示 | M3/M4 引 `@inquirer/prompts` | 权限确认 `[y/N]`、模型选择菜单 |
| 测试框架 | **Vitest** | ESM 原生、速度快、mock 体验好 |
| 代码风格 | ESLint + Prettier（后期） | M1 先靠 tsc strict 兜底，后期再上 lint |

## 二、关键决策详解

### 2.1 模块系统：ESM vs CommonJS

**选择**: ESM（`"type": "module"`，使用 `import/export`）

**背景**:
- **ESM** = ES Modules，JavaScript 官方标准（2015 ES6 定案）
- **CommonJS** = Node.js 早期自创（2009 年，当时 JS 还没官方模块标准）

**为什么选 ESM**:
1. **核心依赖都是 ESM 优先**:
   - `@anthropic-ai/sdk` — ESM
   - `openai` — ESM
   - `ai-tokenizer` — ESM
   - 如果用 CommonJS，`require()` 这些包会直接报 `ERR_REQUIRE_ESM`

2. **现代 TypeScript 项目的默认**:
   - TS 官方编译 `module: "NodeNext"` 就是为 ESM 设计
   - Vite/Vitest 生态全面拥抱 ESM

3. **未来兼容性**: ESM 是官方标准，往后 10 年的 JS 包都会优先发 ESM

**代价**:
- 少数只发 CommonJS 的老库（如某些 2015 年前的包）会不兼容，但我们的技术栈没这问题
- `import` 必须带后缀（如 `./foo.js`，即使源码是 `.ts`）——习惯就好

**关联文件**: `package.json` 里的 `"type": "module"`、`tsconfig.json` 里的 `"module": "NodeNext"`

### 2.2 测试框架：Vitest 胜出

**选择**: Vitest

**调研时间**: 2026-07-21
**调研方法**: 专项调研 agent，查证 2026 年最新状态 + 采用率趋势

**三个候选对比**:

| 框架 | ESM 支持 | TS 支持 | Mock 能力 | 配置成本 | 2026 趋势 |
|------|---------|---------|-----------|---------|----------|
| **Vitest** | ✅ 原生 | ✅ 零配置 | ⭐⭐⭐⭐⭐ | 最低 | 📈 ESM 新项目首选 |
| **Jest** | ⚠️ 仍是实验性 | ⚠️ 需 ts-jest | ⭐⭐⭐⭐ | 繁琐 | 📉 存量项目 |
| **node:test** | ✅ 原生 | ✅ Node 23+ | ⭐⭐⭐ | 中等 | 🆕 简单场景可用 |

**为什么 Vitest**:
1. **针对我们的技术栈（TS + ESM + Node）**: Vitest 零配置，Jest 到 2026 年 ESM 仍要 `--experimental-vm-modules` flag
2. **速度**: 比 Jest 快 5-28x（watch mode 频繁跑测试，TDD 体验好）
3. **Mock LLM 的场景**: `vi.mock()` 类型推导最完善 + `msw`（Mock Service Worker）拦 HTTP，正好对应 M5 的"依赖注入 + record/replay 测 agent loop"
4. **采用率**: 2023-2024 增长 400%，npm 380 万/月（2026），ESM+TS 新项目的社区共识

**为什么不选 node:test**:
- 它零依赖确实诱人，对"简单 CLI"够用
- 但我们要 mock LLM SDK、要 record/replay、要 TDD 频繁跑 → 这些正是 Vitest 的增量价值
- node:test 的断言库较弱（仅 `node:assert`）、不支持快照测试、没有 UI

**Jest 的痛点（2026 年仍未解决）**:
> "Jest's architecture was designed around CommonJS module isolation. When Jest encounters ESM code, it must transform it through a compatibility layer that can introduce subtle behavioral differences between your test environment and your production code."  
> —— 来源: tech-insider.org/vitest-vs-jest-2026/

**关联文件**: `vitest.config.ts`（后续配置时建）

### 2.3 TS 运行方式：tsx + tsc 混合

**选择**: 开发用 `tsx`，发布用 `tsc` 编译

**为什么不选单一方案**:

| 方案 | 开发体验 | 生产 | 取舍 |
|------|---------|------|------|
| 只用 `tsx` | 改完即跑，秒级反馈 | 理论能跑，但 npm 发包一般发纯 JS | 学习阶段够用，但非正式发布标准 |
| 只用 `tsc` | 每次改都要编译，慢 | 标准做法 | 开发慢，TDD 节奏被打断 |
| **两者结合** | 开发快 | 发布标准 | ✅ 两全其美 |

**scripts 设计**:
```json
{
  "scripts": {
    "dev": "tsx src/index.ts",              // 开发：秒跑
    "build": "tsc",                          // 发布：编译成 dist/
    "start": "node dist/index.js",           // 生产：跑编译后的 JS
    "test": "vitest"
  }
}
```

**tsx 是什么**:
- 运行时即时编译 TS 的工具（类似 `ts-node` 但更快、ESM 支持更好）
- 原理：拦截 Node 的 `require`/`import`，动态转译 `.ts` 文件
- 不写磁盘，纯内存操作，所以快

### 2.4 CLI 框架：渐进式引入

**选择**: M1 手写 → M2 `commander` → 后期 `ink`

**为什么不一开始就上 commander**:
- M1 只有一个参数（`ecode "任务"`），用 `process.argv[2]` 一行搞定，引依赖是杀鸡用牛刀
- 符合"按需引入、不提前抽象"原则

**commander 解决什么**:
```bash
# 参数多了以后，手写噩梦：
ecode --model deepseek --verbose "帮我改代码"
# 要处理：--model=xx、-m xx、布尔标志、顺序任意、默认值、--help...

# commander 声明式搞定：
program
  .argument('<task>')
  .option('-m, --model <name>', '选择模型', 'glm-5')
  .option('--verbose', '详细输出')
  .parse()
```

**ink 是什么**:
- 用 **React 写终端 TUI**（是的，真的 React：`<Box>`, `<Text>`, `useState`）
- Claude Code 的整个交互界面就是 ink 做的
- 能做出接近 GUI 的终端体验：实时刷新、光标控制、分区布局
- 但 M1-M3 的目标是理解 agent loop，不是打磨 UI，后期再上

**渐进路线的价值**:
- M1 手写 CLI 参数解析 → 从底层理解"命令行参数本质是字符串数组"
- M2 引 commander → 看清"框架抽象了什么体力活"
- 后期 ink → 现代终端交互体验

### 2.5 API 对比学习：融进 M2

**选择**: 不单独加"API 对比"阶段，融进 M2 写 Provider 时自然对比

**背景**:
- 知识库已有 `OpenAI与Anthropic-API协议对比.md`（2026-06，标注"已掌握"）
- 核心区别（system 位置、max_tokens、tool_use vs tool_calls）已读过笔记

**学习方式设计**:
1. **M2 先写 ClaudeProvider**（M1 已经用了 Claude，顺势封装）
2. **再写 OpenAIProvider** → 亲身撞上每个区别：
   - "咦，system 怎么不能放顶层了？" → 撞上 system 位置区别
   - "为什么 `arguments` 是字符串，还得 `JSON.parse`？" → 撞上参数格式区别
   - "回结果怎么不是 tool_result block 了？" → 撞上回传格式区别
3. **写 transform 层**（把两家差异抹平成统一接口）→ 系统化区别，不是零散记忆

**为什么这个方式好**:
- 文档里的对比表是"别人告诉你的结论"
- 手写 Provider 是"你自己踩出来的结论"，理解更深、定位问题更快
- 实际踩过，遇到流式拼接、参数解析等问题时能直接对症

**关联文档**: `knowledge/ai-agents/LLM-API/01-知识点总结/OpenAI与Anthropic-API协议对比.md`

## 四、未采纳的方案及理由

### 4.1 为什么不用 Bun
- **Bun 的优势**: 原生跑 TS、内置测试、速度快
- **为什么不选**: 
  - 你最初的需求就是"Node 支持多端"
  - Bun 在受限环境（企业内网、老 Docker）有兼容坑
  - Node 的知识对你的工作环境（讯飞）和 Java 全栈定位更通用
- **决策轮次**: 第 3 轮讨论（Bun vs Node）

### 4.2 为什么不用 LangGraph
- **社区共识**: "The first time you write the loop yourself, the framework stops being magic."
- **本项目定位**: 自主可控优先，拒绝框架黑盒——核心逻辑自己写，出问题能真正定位和演进
- **决策来源**: 技术路线拍板为"手写 loop + 逐步模块化"

### 4.3 为什么第一版不上 MCP
- **MCP 是什么**: Model Context Protocol，工具层标准，Anthropic 2024/11 发布
- **为什么不上**: 
  - MCP 是 **P2-2 可选**（认知盲区清单里），不是 MVP 核心
  - 工具注册表设计时会预留"外部工具源"抽象，将来接 MCP 不用重构
- **后续计划**: M5+ 或专门的扩展阶段

## 五、技术栈与里程碑能力的对齐

| 里程碑 | 核心能力 | 技术栈支撑 |
|--------|---------|-----------|
| **M1** | Agent loop 协议 | `@anthropic-ai/sdk` 封装 HTTP 细节，专注 loop |
| **M2** | 多模型差异、Provider 抽象 | ESM 让多 SDK 并存无痛；手写两个 Provider 撞出区别 |
| **M3** | 上下文管理、token 计数 | `ai-tokenizer` 通用计数库；ESM 让它零配置导入 |
| **M4** | 权限、编辑正确性 | `@inquirer/prompts` 交互确认；`tsx` 快速迭代调试 |
| **M5+** | 可测试性、可观测性 | Vitest 依赖注入 + mock；ESM 让 mock 更顺滑 |

**核心对齐**: 技术栈的每个选择都服务于产品交付与自主可控，不是堆技能清单。

## 六、项目结构演进规划

测试统一放 `tests/`（镜像 src 结构）。src 按里程碑**渐进分层**（YAGNI，文件够多才拆，避免空目录）：

```
src/
├── index.ts              # Entry 层
├── core/                 # Agent Core（agent.ts 迁入；M3 加 session/context）
├── tools/                # Tool 层（tools.ts 拆；P0-3 加工具时迁入）
│   └── registry / executor / read-file / edit-file / grep / glob
├── provider/             # Provider 层（M2）
├── permission/           # 权限层（M4）
├── system-prompt.ts      # 横切
└── logger/               # runtime-logger.ts（横切）
tests/                    # 镜像 src 结构
```

**拆分时机**：
- **P0-3 / P0-4**：加 `edit_file` / `grep` / `glob` 时，`tools.ts` 拆成 `tools/` 目录（工具从 1 变 4+，值得分文件）
- **M2**：引入 `provider/`（Claude/OpenAI Provider）
- **M3**：`core/`（agent + session + context）
- **M4**：`permission/`

M1 当前保持扁平（5 个源文件，拆了反而碎片化），演进方向以上图为据。
