> 状态：设计稿 v2（吸收三角色审阅 + 用户决策，待用户最终确认 → 实现）
> 范围：对话调度（单 runLoop + pendingQueue）+ 对话气泡（CC 风格）+ thinking loader + 排队/插话 UI + Todo
> 决策来源：用户拍板「C 模型精神（单循环+消息追加）」+「全部一次做完」；动效「只留 thinking loader」；助手辨识「保留 ◆ + 整块左竖线」；三角色审阅修正（见 §14 变更记录）

## 1. 背景与目标

### 1.1 要解决的问题

ECode 当前是成熟的「请求-响应」式 TUI，但在「agent 跑着时用户想说话」这个场景**完全空白**：

- **忙时输入被禁用**：`InputBar disabled={api.isRunning}`（`src/ui/app.tsx:339`），agent 一跑就吞键，用户只能干等或 Ctrl+C 硬中断（整流作废，丢上下文）。
- **compact 竞态丢消息**：`/compact` 不设 isRunning、完成时 `messages: compressed` 覆盖真相源（`use-agent-stream.ts:185-206`），期间提交被冲掉。
- **对话气泡缺失**：用户/助手靠 `❯ 你`/`◆ ECode` 文字前缀区分（`chat-view.tsx:24-54`），前缀冗余（"你"/"ECode" 可去），无 CC 式背景色/块感对照。
- **动效简陋**：光标静态 `_`（`input-bar.tsx:181`）；助手思考时无 loader（streaming 直接出文字）；spinner 只服务工具运行。
- **无 Todo**：src/ 内 0 行 todo 代码，agent 无法展示任务规划。

### 1.2 目标（Done 定义）

| 维度 | 验收标准 |
|---|---|
| 对话调度 | agent 忙时用户可继续输入；消息**不丢**、按序处理；compact 期间提交不丢；Ctrl+C 中断不死循环、不丢中断前历史 |
| 排队反馈 | 提交瞬间 100ms 内有"已排队"强反馈（StatusBar `待处理:N`）；排队消息灰显预览（InputBar 上方）；不与正式消息双显 |
| 对话气泡 | 用户 = `›` + 浅色背景（去"你"）；助手 = `◆` + brand 左竖线（去"ECode"，整块可辨识） |
| 动效 | 助手思考时显示 thinking loader（星形 spinner，取代"直接出文字"）；光标保持静态 `_`（不闪烁，避重渲染坑） |
| Todo | agent 可读写任务清单；常驻 InputBar 上方；completed 折叠 + maxHeight；`◻/◾/✓` 符号 |

### 1.3 非目标（YAGNI）

- **不做抢占式插话**（abort 后自动重跑）——abort 续接是 M4 级难题（`agent.ts:540` 自承），本轮 Ctrl+C 兜底。
- **不做 sticky header**（滚动时标识固定顶部）——Ink TUI 的 `<Static>` append-only + less pager 都不支持，终端做不到。
- **不做光标闪烁**——Ink 下 setInterval 与 streaming 叠加重渲染 + Windows Terminal 光标抖动，价值不抵风险（用户已确认砍）。
- 不做 CC 式优先级队列（now/next/later）、TaskListV2（id/owner/依赖）、单工具中止、spinner 卡顿变红。

## 2. 现状基线（探索结论）

### 2.1 对话调度（`use-agent-stream.ts`）

- `submit`（`:78-137`）：同步 setState 加 user 到 `completedMessages`（UI 层）→ AbortController 覆盖 `abortRef` → async IIFE `for await runAgentStream(text, {resumed})` → completed 回填 `sessionRef.current = {id,messages,...}`。
- **缺陷**：user 消息只进 UI 层，不进 LLM history；LLM history 由 agent 内部自管，completed 才回填。→ "忙时无法追加消息"根因。
- `compact`（`:185-206`）：竞态三连（不设 isRunning + await 数十秒 + 完成覆盖）。
- `submit` 内无 isRunning 守卫（`:78-89`），仅靠 InputBar disabled 物理拦；命令路径绕开。

### 2.2 agent 主循环（`agent.ts`）

- `runAgentStream(text, opts)`：`for` 迭代（MAX_ITERATIONS=25）+ 内部 while drain；每轮 provider.stream → 文本/tool。
- `messages = opts.resumed ? [...opts.resumed.messages, {role:'user',content:task}] : [{role:'user',content:task}]`（`:257-259`）——**契约兼容 runLoop**：每轮 text=出队 user、resumed.messages=messagesRef 历史。
- completed 带回 `{sessionId,task,createdAt,messages,reason}`（`:390-403`/`:525-536`）；aborted 分支也 yield messages（含中断前 partial，`:543-555`）。
- 中断：唯一中断点在 `consumeStream` chunk 循环（`:162`）；AbortError → completed(reason:'aborted')。
- **结论：agent.ts 不用改**。runLoop 每轮 `runAgentStream(text, {resumed:{messages:messagesRef}})` 完全契合。

### 2.3 UI 层

## 3. 架构决策：单 runLoop + pendingQueue（C 模型落地）

### 3.1 模型与 pendingQueue 决策

用户选定 C 的精神：**单 runLoop 处理所有消息 + 消息追加**。核心诉求：统一（compact/插话/排队同一机制）、不堵后续、agent.ts 不改。

**落地关键决策：用显式 `pendingQueue` 承载待处理消息，而非从 `messagesRef` 结构推断"末尾 user 即未响应"。**

**理由（三角色审阅验证）**：纯结构推断（末尾 role 判定 / id 比较 / processedLen 指针）在「中断或出错期间用户又提交」场景**会死锁**——中断占位与期间新 user 的顺序冲突，新 user 被误判已响应而永不处理。显式 `pendingQueue` 把"待处理"独立出来：submit 入队、runLoop 出队，结构清晰、无死锁、可单测，且 queue 直接做排队 UI 数据源（顺带解决"排队数据来源不清"）。

**对用户透明**：体验完全等同 C（忙时输入不丢、按序、compact 统一），仅内部数据载体更可靠。

### 3.2 数据结构

```
pendingQueue: string[]                    // 待处理 user 文本（显式队列，runLoop 消费，排队 UI 数据源）
messagesRef: ECodeMessage[]               // LLM history 真相源（agent completed 全量回填，现状行为保留）
sessionRef: { id, task, createdAt } | null // 会话元信息（completed 回填 id；messages 由 messagesRef 持有）
busyRef: 'idle' | 'running' | 'compacting' // 显式状态机（替代散布的 isRunning/isCompacting 标志，解 compact 并发）
abortRef: AbortController | null
compactQueued: boolean                    // runLoop 跑期间触发 compact 的排队标志
```

> 抽出 `src/ui/agent-loop-controller.ts`（非 React 类）封装以上逻辑，hook 只做 controller ↔ setState 桥接。纯逻辑可独立单测（快），hook 测 React 集成。

### 3.3 submit 流程

```
submit(text):
  pendingQueue.push(text)                 // 入队（待处理；不进 messagesRef，避免与 agent 当前轮 history 重复）
  setState queuedMessages 追加 text        // UI 排队预览（灰显）+ 提交瞬间强反馈
  setState pendingCount++                 // StatusBar "待处理:N"
  ensureRunLoop()
```

### 3.4 ensureRunLoop + runLoop

```
ensureRunLoop():
  if busyRef !== 'idle': return           // running/compacting 时，runLoop/doCompact 自行 drain，不重入
  busyRef = 'running'; setState isRunning:true
  void runLoop()

async runLoop():
  try:
    while (pendingQueue.length > 0):
      const text = pendingQueue.shift()
      // 该消息从"排队"转"正式"：移出 queuedMessages，进 completedMessages（正式 user 气泡，避免双显）
      setState: queuedMessages 移除 text；completedMessages 追加 {kind:'user', text}；pendingCount--
      const controller = new AbortController(); abortRef = controller
      try:
        for await (event of runAgentStream(text, {
                     model, system, signal: controller.signal, allow, permissionGate,
                     resumed: sessionRef ? {...sessionRef, messages: messagesRef} : undefined
                   })):
          apply(event)                    // reducer 处理 streaming/tools/permission/completed→UI
          if event.type === 'completed': break
        // completed（含 aborted）：统一回填会话元信息 + 全量 messagesRef（中断前 partial 也保留，不丢历史）
        if event.sessionId:
          sessionRef = { id:event.sessionId, task:event.task, createdAt:event.createdAt }
        messagesRef = event.messages ?? messagesRef   // agent 视角全量（含本轮 user+assistant / 中断前 partial）
        // ⚠️ aborted 也设 sessionRef（实现修正，见 §14）：否则 resumed=undefined，messagesRef 里的 partial 白存。
        //    非抢占：不自动重跑被中断的任务，仅保留历史供用户手动续接。
      catch (err): apply({type:'error', error:...})    // 兜底；runLoop 继续 shift 下一条，不死循环
      // 循环回去：若期间又 submit 入队，继续 shift；否则退出
  finally:
    busyRef = 'idle'; setState isRunning:false
    if compactQueued: compactQueued=false; void doCompact()   // 排队的 compact 在 idle 时执行
```

**关键特性**：
- **无 delta merge、无 processedLen**：pendingQueue 是唯一待处理来源；aborted/error 后继续 shift 下一条，不死锁。
- **不丢中断前历史**：aborted 时 `messagesRef = event.messages`（agent 中断前已 push 的 partial assistant + tool_result 全保留，`:386/:489`）。
- **无双源同步**：messagesRef 由 agent completed 全量回填（现状契约），pendingQueue 独立。

### 3.5 中断（Ctrl+C）

```
abort(): abortRef.current?.abort()
```
- agent AbortError → completed(reason:'aborted') → messagesRef 回填中断前历史。
- runLoop 继续 shift queue（若期间有新 submit）；无则退出。**不死锁**（queue 独立于 messagesRef 结构）。
- UI：warning 系统消息 `— 已中断 —`（纯 UI，**不 push 进 messagesRef**，避免污染 LLM history；用户重 submit 即新一轮）。
- 非抢占（不自动重跑）；避开 abort 续接难题。

### 3.6 compact（状态机互斥，修竞态）

```
compact():
  if busyRef !== 'idle': compactQueued = true; return   // runLoop/doCompact 完成后执行
  void doCompact()

async doCompact():
  busyRef = 'compacting'; setState isCompacting:true
  try:
    const compressed = await compactMessages(messagesRef, {model, system})
    if compressed:
      messagesRef = compressed
      setState: completedMessages = messagesToDisplayMessages(messagesRef); staticKey++
  finally:
    setState isCompacting:false; busyRef = 'idle'
    ensureRunLoop()                       // 若 queue 有期间 submit，drain
```
- **无 delta merge 问题**：compact 期间 submit 入 pendingQueue（不进 messagesRef），compact 用 messagesRef 快照压缩，完成后 ensureRunLoop drain queue。
- **状态机保证不并发**：busyRef 互斥（running/compacting/idle），doCompact 与 runLoop 不交错（解审阅 P0 并发漏洞）。

### 3.7 clear / switchSession 同步（审阅 P2-9）

```
clear():           sessionRef=null; messagesRef=[]; pendingQueue=[]; setState(清空 + staticKey++)
switchSession(r,h): sessionRef=r; messagesRef=[...r.messages]; pendingQueue=[]; setState(history + staticKey++)
```

### 3.8 isRunning 语义

`isRunning = (busyRef === 'running')`。**不再用于禁用 InputBar**（§4）。仅驱动 busy 提示 + Ctrl+C 可用性。

## 4. 插话与排队 UI

### 4.1 InputBar 永不禁用

- `src/ui/app.tsx:339`：移除 `disabled={api.isRunning}`，InputBar 永远可输入。
- busy 时（busyRef≠idle）：InputBar 的 `› + 输入 + _` 形态**不变**；busy 提示移到 InputBar **上方独立行**（thinking loader / 工具摘要）或 StatusBar，**不挤用户输入**（审阅 P1：塞 InputBar 单行会挤掉输入）。
- 现 `input-bar.tsx:159-166` 的 disabled 分支删除（不再有 disabled 态）。

### 4.2 排队预览 + 提交瞬间强反馈

- `queuedMessages: string[]`（state，= pendingQueue 镜像）：渲染 InputBar **正上方**，每条 `›` + muted 灰显 + 文本（静态无动效）。
- **提交瞬间强反馈**（审阅产品 P0，对抗"消息没发出去"困惑）：submit 时排队消息**即时出现**（灰显，InputBar 上方）+ StatusBar 持续显示 `待处理:N`（pendingCount）。~~闪现 `+ 已排队`~~ 砍掉（KISS：即时出现 + 计数已是强反馈，无需额外闪现 state，见 `queued-messages.tsx` 注释）。
- **数据源显式**：queuedMessages = pendingQueue（直接，解决"数据来源不清"）。
- **不双显**（审阅 P0）：user submit 进 queuedMessages（动态区）；runLoop 出队时移到 completedMessages（Static 正式）。同一消息任一时刻只在一处。

### 4.3 中断可发现性

StatusBar 在 isRunning 时显示 `ctrl+c 中断`（保留现有提示，但不再以禁用输入为代价）。

## 10. 测试策略

- **controller 纯逻辑**（核心，mock runAgentStream 为 async generator）：
  - 忙时 submit → queue 入队 → 当前轮完成后出队按序处理（不丢）。
  - 期间多次 submit → 全部按序。
  - aborted → messagesRef 保留中断前 partial → 继续 drain queue（不死循环）。
  - error → 不重跑同一条 → drain 下一条。
  - compact 期间 submit → 入队 → compact 完成后 drain。
  - 状态机转移：idle→running→idle / idle→compacting→idle / running 时 compact 排队。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| pendingQueue 与 messagesRef 状态不一致 | 消息错乱 | controller 单一管理；messagesRef 只由 agent completed 回填；queue 只由 submit 入/runLoop 出 |
| compact 与 runLoop 并发 | merge 冲突 | busyRef 状态机互斥；compactQueued 排队标志 |
| 去 disabled 后斜杠命令被当 user 消息喂 LLM | 命令失效 | **前置核证**：grep `onSubmit=`/`api.submit` 全路径，确认所有斜杠命令在 app 层分流（不进 submit/queue） |
| aborted 丢中断前历史 | 上下文断裂 | messagesRef = event.messages（aborted 也回填，含 partial） |
| `<Static>` append-only 与 queued 预览 | 双显/渲染错乱 | queued 在动态区（可变），正式 user 出队时才进 Static；不双显 |
| 用户气泡背景色跨行渲染 | 视觉破碎 | ui-preview 先验证；不稳则降级首行背景 |
| sticky header 用户预期落空 | 误解 | 文档 +Done 定义明确"Ink 不可行，用左竖线等效" |
| 抽 controller 后 hook 集成回归 | 状态不同步 | 1a 纯逻辑单测 + 1b hook 集成测分离 |

## 12. 与 CC 的预期差距（管理预期）

交付后与 CC 的差距（本轮非目标）：
- ❌ **抢占式插话**：CC 中途插话能影响 agent 当前决策；ECode 是"下轮处理"+ Ctrl+C。最大差距。
- ❌ **Todo 高级特性**：无 id/owner/依赖；agent 无法表达"任务 A 等 B"。
- ❌ **单工具中止**：Ctrl+C 是整流中断，不能停单个工具。
- ❌ **sticky header**：终端限制，CC 也没有。
- ✅ 对话调度（不丢、按序、compact 不丢）、气泡视觉、排队预览：可对标。
