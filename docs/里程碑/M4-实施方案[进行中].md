# M4 实施方案

> **里程碑**：M4 "信任问题" —— 安全进阶 + 正确性 + 健壮性  
> **实施模式**：TDD（Red → Green → Refactor），5 个 Phase 顺序推进  
> **预计工期**：12-15 天（按每天 4-6 小时计）

---

## 一、总体架构与模块划分

```
src/
├── permission/
│   ├── permission-manager.ts      # 权限管理器（四档模式 + 规则引擎）
│   ├── command-parser.ts          # Bash 命令解析（主命令 + 危险参数提取）
│   ├── settings-loader.ts         # 读取 .claude/settings.json
│   └── rules.ts                   # 规则类型定义（allow/deny/ask）
├── tools/
│   ├── edit-file.ts               # 增强版 edit（fuzzy search + 回喂真实行）
│   ├── tool-executor.ts           # 工具执行器（增加验证钩子）
│   └── validation.ts              # 后置验证（tsc/test/lint）
├── agent/
│   ├── retry-policy.ts            # API 重试策略（指数退避 + jitter）
│   ├── loop-detector.ts           # 死循环检测（滑动窗口 + 哈希）
│   └── error-handler.ts           # 结构化错误类型
└── agent.ts                       # 主 loop（集成错误恢复 + 混合流式）
```

## 二、Phase 划分与实施顺序

### Phase 1：权限系统进阶（档位 B/C）

**目标**：从二元 dangerous/safe 升级到四档模式 + 精细规则。

#### 1.1 接口设计

```ts
// src/permission/types.ts
export type PermissionMode = 'default' | 'acceptEdits' | 'plan' | 'bypass';

export interface PermissionSettings {
  mode: PermissionMode;
  allowedCommands?: string[];       // 白名单命令（如 ["git status", "npm test"]）
  deniedCommands?: string[];        // 黑名单命令（如 ["rm -rf"]）
  alwaysAllowPaths?: string[];      // 白名单路径（如 ["src/**", "tests/**"]）
  alwaysDenyPaths?: string[];       // 黑名单路径（如 [".env", "node_modules"]）
}

export interface PermissionCheck {
  tool: string;
  input: unknown;
  context: {
    filePath?: string;
    command?: string;
  };
}

export type PermissionVerdict = 
  | { action: 'allow'; reason: string }
  | { action: 'deny'; reason: string }
  | { action: 'ask'; reason: string; options?: string[] };
```

#### 1.2 实施步骤

**Step 1.1：settings.json 加载器**（1 天）
- [ ] 读取 `~/.claude/settings.json`（不存在则用默认值）
- [ ] 解析 `permissionMode` 字段，映射到四档
- [ ] 单元测试：JSON 格式正确性、缺失字段降级

**Step 1.2：命令解析器**（2 天）
- [ ] 实现 `parseCommand(cmd: string)`：
  - 管道分割（`|`）
  - 引号处理（`"` / `'`）
  - 主命令提取（第一个非选项 token）
  - 危险参数识别（`-rf` / `--force` / `-D`）
- [ ] 单元测试：覆盖 20+ 边缘 case（嵌套引号、转义、&&/|| 逻辑）

**Step 1.3：规则引擎**（2 天）
- [ ] 实现 `PermissionManager.check()`：
  - deny 规则优先级最高（命中直接拒绝）
  - ask 规则次之（需确认）
  - allow 规则兜底（自动通过）
  - 路径检查（glob 匹配 `alwaysAllowPaths` / `alwaysDenyPaths`）
- [ ] 档位逻辑：
  - `default`：危险操作 ask，其余 allow
  - `acceptEdits`：edit/write 自动 allow，其余按 default
  - `plan`：所有操作 ask
  - `bypass`：所有操作 allow（开发模式）
- [ ] 单元测试：每个档位 + 规则组合（20+ cases）

**Step 1.4：集成到 agent loop**（1 天）
- [ ] 工具执行前调用 `PermissionManager.check()`
- [ ] verdict = deny → 直接返回 tool_result.is_error
- [ ] verdict = ask → 调用 `askUser()` 获取用户决策
- [ ] 日志：每次检查记录 `[permission] tool=edit_file, verdict=allow, reason=...`
- [ ] 集成测试：模拟危险命令被拦截

**验收标准**：
- ✅ `.claude/settings.json` 的 `permissionMode` 能正确映射到四档
- ✅ `rm -rf /` 被拒绝，`npm test` 被允许
- ✅ `acceptEdits` 模式下 edit_file 自动通过，bash 仍需确认
- ✅ 所有单元测试通过（覆盖率 > 90%）

### Phase 2：edit 工具正确性闭环

**目标**：匹配失败时回喂真实行，让 LLM 自我修正。

#### 2.1 接口设计

```ts
// src/tools/edit-file.ts
export interface EditFileInput {
  file_path: string;
  old_string: string;
  new_string: string;
  line_number?: number;  // 新增：精确行号模式（可选）
}

export interface EditFileResult {
  success: boolean;
  message: string;
  context?: {            // 匹配失败时返回

    endLine: number;
    suggestion: string;     // 提示信息（缩进/空格差异）
  };
}
```

#### 2.2 实施步骤

**Step 2.1：fuzzy search 实现**（1 天）
- [ ] 引入 `fastest-levenshtein`
- [ ] 实现 `findClosestMatch(fileContent: string, target: string, windowSize = 5)`：
  - 对文件每一行计算 Levenshtein 距离
  - 返回距离最小的行号 + 上下文窗口（±5 行）
- [ ] 单元测试：构造"有微小差异"的文件，验证能找到正确行

**Step 2.2：增强 edit_file 工具**（2 天）
- [ ] 匹配失败时调用 `findClosestMatch`
- [ ] 返回增强的 tool_result：
  ```json
  {
    "is_error": true,
    "content": "匹配失败。文件 src/agent.ts 第 45-55 行实际内容：\n<actual lines>\n请检查缩进（期望 2 空格，实际 4 空格）"
  }
  ```
- [ ] 支持 `line_number` 精确模式（跳过匹配，直接替换指定行）
- [ ] 单元测试：
  - 匹配成功 case
  - 匹配失败 → 返回上下文
  - 行号模式

**Step 2.3：重试逻辑**（1 天）
- [ ] 在 `agent.ts` 中记录"同一文件+位置"的编辑次数
- [ ] 超过 3 次 → 返回特殊 stop_reason，提示"换思路"
- [ ] 集成测试：模拟匹配失败 → LLM 重试 → 成功（需 Mock SDK）

**Step 2.4：日志与可观测**（0.5 天）
- [ ] 每次编辑记录：`[edit] file=src/agent.ts, match=success, lines_changed=3`
- [ ] 匹配失败记录：`[edit] file=..., match=failed, closest_line=45, distance=3`

**验收标准**：
- ✅ 故意构造"缩进错误"的 old_string，工具能返回正确的真实行
- ✅ 模拟 LLM 根据真实行重试，能成功匹配
- ✅ 行号模式能精确替换指定行
- ✅ 单元测试覆盖率 > 85%

### Phase 3：错误恢复三条路径

**目标**：API 退避 + 工具错误回喂 + 死循环检测。

#### 3.1 接口设计

```ts
// src/agent/retry-policy.ts
export class RetryPolicy {
  constructor(
    public maxRetries: number = 3,
    public baseDelay: number = 1000,
    public maxDelay: number = 60000
  ) {}

  async execute<T>(fn: () => Promise<T>): Promise<T>;
  shouldRetry(err: unknown): boolean;
}

// src/agent/loop-detector.ts
export class LoopDetector {
  check(toolName: string, input: unknown): void;  // throws LoopDetectedError
  reset(): void;
}

// src/agent/error-handler.ts
export class APIError extends Error {
  constructor(public status: number, message: string) {}
}
export class LoopDetectedError extends Error {}
export class MaxIterationsError extends Error {}
```

#### 3.2 实施步骤

**Step 3.1：API 重试策略**（1.5 天）
- [ ] 实现 `RetryPolicy.execute()`：
  - 指数退避：delay = baseDelay * 2^attempt
  - 随机 jitter：+= random(0, 1000)
  - 最大延迟上限：min(delay, maxDelay)
- [ ] 实现 `shouldRetry()`：
  - 429/500/502/503/504 → true
  - 400/401/403 → false
- [ ] 单元测试：
  - Mock API 返回 429 → 验证重试 3 次 + 延迟递增
  - Mock API 返回 400 → 验证立即抛出

**Step 3.2：集成到 Provider**（1 天）
- [ ] `ClaudeProvider` / `OpenAIProvider` 的 `stream()` 包裹 RetryPolicy
- [ ] 日志：每次重试记录 `[retry] attempt 2/3, status=429, delay=2.3s`
- [ ] 集成测试：模拟 API 瞬时 500 → 验证重试成功

**Step 3.3：死循环检测**（1.5 天）
- [ ] 实现 `LoopDetector.check()`：
  - 滑动窗口（最近 5 轮）
  - 动作哈希：`${toolName}:${stableHash(input)}`
  - 重复 ≥3 次 → throw LoopDetectedError
- [ ] 全局迭代计数：25 轮上限 → throw MaxIterationsError
- [ ] 单元测试：构造重复序列，验证触发条件

**Step 3.4：集成到 agent loop**（1 天）
- [ ] 每轮开始时调用 `LoopDetector.check()`
- [ ] 捕获 LoopDetectedError → 返回特殊 stop_reason + 提示"换思路"
- [ ] 日志：`[loop] detected repeat action: read_file(src/agent.ts) x3`
- [ ] 集成测试：模拟"读 → 编辑失败 → 再读"循环 → 验证拦截

**验收标准**：
- ✅ 模拟 API 429 → 验证指数退避（1s, 2s, 4s）
- ✅ 模拟 API 400 → 验证立即失败，不重试
- ✅ 模拟重复调用同一工具 3 次 → 验证触发循环检测
- ✅ 25 轮迭代后自动停止

### Phase 4：强制后置验证

**目标**：文件修改后自动跑 build/test，失败回喂给 LLM。

#### 4.1 接口设计

```ts
// src/tools/validation.ts
export interface ValidationResult {
  success: boolean;
  output: string;       // 编译/测试输出
  command: string;      // 实际执行的命令
  duration: number;     // 耗时（ms）
}

export async function runValidation(
  projectRoot: string,
  options?: {
    skipTests?: boolean;    // 跳过测试（仅编译检查）
    skipLint?: boolean;     // 跳过 lint
  }
): Promise<ValidationResult>;
```

#### 4.2 实施步骤

**Step 4.1：项目类型探测**（0.5 天）
- [ ] 实现 `detectProjectType()`：
  - 存在 `package.json` → Node.js 项目
  - 存在 `tsconfig.json` → TypeScript 项目
  - 存在 `pyproject.toml` / `setup.py` → Python 项目
- [ ] 单元测试：不同项目结构的探测

**Step 4.2：验证命令生成**（1 天）
- [ ] 实现 `getValidationCommands(projectType)`：
  - TypeScript：`tsc --noEmit` 或 `npm run build`
  - Node.js：`npm test`（如果有）
  - Python：`python -m py_compile <changed_files>`
- [ ] 优先使用项目已有脚本（读 package.json 的 scripts 字段）
- [ ] 单元测试：不同项目类型返回正确命令

**Step 4.3：验证执行器**（1 天）
- [ ] 实现 `runValidation()`：
  - 顺序执行：编译 → 测试 → lint
  - 任一步骤失败 → 立即返回（不继续后续步骤）
  - 捕获 stdout + stderr
- [ ] 超时控制：单个命令最多 60 秒
- [ ] 单元测试：Mock 命令执行，验证失败提前返回

**Step 4.4：集成到工具执行器**（1 天）
- [ ] 修改 `tool-executor.ts`：
  ```ts
  if (['edit_file', 'write_file'].includes(tool.name)) {
    const validation = await runValidation(projectRoot);
    if (!validation.success) {
      return {
        is_error: true,
        content: `文件已修改，但验证失败：\n${validation.output}\n请修复`
      };
    }
  }
  ```
- [ ] 配置选项：`validation.enabled`（默认 true，可关闭）
- [ ] 日志：每次验证记录耗时 + 结果
- [ ] 集成测试：编辑文件引入语法错误 → 验证失败 → LLM 收到错误信息

**验收标准**：
- ✅ 编辑文件引入 TypeScript 错误 → 验证失败，错误信息回喂给 LLM
- ✅ 编辑文件导致测试挂 → 验证失败，测试输出回喂
- ✅ 验证通过 → 无额外 tool_result，agent 继续
- ✅ 配置 `validation.enabled=false` → 跳过验证

## 七、回滚与降级策略

如果某个 Phase 遇到阻塞（技术风险、工期超限），降级方案：

| Phase | 阻塞风险 | 降级方案 |
|-------|----------|----------|
| Phase 1 | 命令解析覆盖不全 | 保守策略：解析失败 → 标记 dangerous |
| Phase 2 | fuzzy search 性能差 | 限制搜索窗口（±100 行），超大文件提示用行号模式 |
| Phase 3 | 死循环检测误报 | 提高触发阈值（3 次 → 5 次），或仅警告不中断 |
| Phase 4 | 验证拖慢体验 | 默认关闭，用户可选开启 |
| Phase 5 | 流式渲染复杂度高 | 简化为"工具开始 + 工具结束"两状态 |

## 八、后续演进路线（M5+）
