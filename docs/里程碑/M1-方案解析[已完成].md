## 一、Agent Loop 协议原理

### 1.1 调用链

```
src/index.ts  →  src/agent.ts  →  src/tools.ts
                        ↓
               src/runtime-logger.ts（旁路，全程记录）
```

- `index.ts` = CLI 入口，`process.argv[2]` 取任务，转 `runAgent(task)`。
- `agent.ts` = Agent Loop 主体（心脏）。
- `tools.ts` = 工具定义（`toolDefinitions`）+ 执行器（`executeTool`，switch 分发）。
- `runtime-logger.ts` = 实时落盘日志（主摘要 + raw 旁路双层，崩溃不丢）。

### 1.2 Loop 数据流（每次迭代的 6 步）

```
for (最多 MAX_ITERATIONS=25 轮):
  ① logApiRequest                        记日志
  ② anthropic.messages.create(...)       把全部历史发给 LLM
  ③ logApiResponse                       记日志
  ④ 遍历 response.content 分流：
       - text block    → stdout 流式输出
       - tool_use block → 收集 {id, name, input}
  ⑤ 没有 tool_use → break（LLM 给出最终答案）
  ⑥ assistant 回复原样 push 进 messages         ← 关键
  ⑦ 对每个 tool_use：executeTool → push tool_result  ← id 必须配对
```

### 1.3 三条硬约束（违反会 400 / 死循环）

1. **assistant 回复必须原样 push**（[agent.ts:110-113](../src/agent.ts#L110-L113)）：不能只存文本，要存整个 `response.content`（含所有 text + tool_use block，含 thinking）。
2. **`tool_use_id` 必须配对**（[agent.ts:135-145](../src/agent.ts#L135-L145)）：`tool_result.tool_use_id` == `tool_use.id`，不配对 API 400。
3. **messages 累加不重建**：每轮传完整历史——这就是为什么 M3 必须做上下文压缩。

### 1.4 单次对话 vs 多轮（messages 生命周期）

| 层面 | 是否累加 | 说明 |
|------|---------|------|
| **单次运行内**（loop 内部） | ✅ 累加 | 每轮 push，LLM 能看到完整历史 |
| **跨运行 / 多轮对话** | ❌ 不累加 | `messages` 是函数局部变量，进程退出就没了 |

当前 [agent.ts:55-57](../src/agent.ts#L55-L57) 每次调 `runAgent` 新建数组（只含本次任务）。不支持"追问"——无持久化、无 REPL。`.gitignore` 已预留 `*.session.json`，属 M3 范畴。

## 二、Anthropic SDK 参数详解（v0.32.1）

### 2.1 Client 初始化（双鉴权）

```ts
const anthropic = new Anthropic({
  apiKey: apiKey ?? undefined,        // 官方 Claude（x-api-key 头）
  authToken: authToken ?? undefined,  // 兼容端点如 DeepSeek/GLM（Authorization: Bearer 头）
  baseURL: process.env['ANTHROPIC_BASE_URL'],  // 留空走官方，填了走兼容端点
});
```

两种鉴权二选一：`ANTHROPIC_API_KEY`（官方）或 `ANTHROPIC_AUTH_TOKEN`（兼容端点）。

### 2.2 messages.create 入参

```ts
const response = await anthropic.messages.create({
  model,              // 如 'claude-sonnet-4-20250514' / 'deepseek-v4-pro'
  max_tokens: 4096,   // 输出上限
  system: '...',      // 顶层独立字段（见第三章两家用法差异）
  messages,           // 累加的对话历史
  tools: toolDefinitions,  // 工具清单（input_schema 格式）
});
```

### 2.3 返回结构：content blocks

```ts
response.content: ContentBlock[]   // 数组，可同时含多种 block
```

| block 类型 | 含义 | 处理 |
|-----------|------|------|
| `text` | 最终回答 / 思考文本 | `process.stdout.write` 打印 |
| `tool_use` | 工具调用请求（id/name/input） | 收集执行 |
| `thinking` | 推理过程（Claude 扩展思考 / DeepSeek reasoner） | 当前静默忽略（M3 多轮需带 signature 原样回传） |

```ts
response.stop_reason: 'end_turn' | 'tool_use' | 'max_tokens' | ...
response.usage: { input_tokens, output_tokens }
```

### 2.4 Streaming（M1 未启用，M3+）

```
事件流: message_start → content_block_start → content_block_delta(多次) → content_block_stop → ... → message_delta(stop_reason) → message_stop
```
非流式（当前）等全部生成才返回；流式边生成边吐 `content_block_delta`，UX 更好。

## 三、两家协议对比（Anthropic vs OpenAI，为 M2 铺垫）

### 3.1 核心差异总览

| 维度 | Anthropic (Claude) | OpenAI (GPT) |
|------|-------------------|--------------|
| **端点** | `POST /v1/messages` | `POST /v1/chat/completions` |
| **system 位置** | 顶层独立 `system` 字段 | `messages` 里 `role: 'system'` |
| **工具调用标志** | content 中的 `tool_use` block | `assistant` 消息上的 `tool_calls` 字段 |
| **工具参数格式** | `input` → 对象 ✅ | `function.arguments` → JSON 字符串 ❌（要 parse） |
| **工具结果回传** | `tool_result` block（在 user content 里） | `role: 'tool'` 独立消息 |
| **ID 字段名** | `tool_use_id` | `tool_call_id` |
| **终止信号** | `stop_reason: 'tool_use'/'end_turn'` | `finish_reason: 'tool_calls'/'stop'` |
| **截断信号** | `stop_reason: 'max_tokens'` | `finish_reason: 'length'` |

### 3.2 system：设计哲学差异

| | Anthropic | OpenAI |
|---|-----------|--------|
| 放哪 | **顶层独立字段** `system` | `messages` 第一条 `role: 'system'` |
| 哲学 | system 是"第一公民"，恒定、独立、不混历史 | system 就是一条特殊消息 |
| 分段缓存 | ✅ 数组形式支持 `cache_control`，system 不变→缓存命中省钱 | 靠消息顺序缓存 |

Anthropic 认为 system（人设/规则）恒定，不该和越来越长的历史混；OpenAI 当成对话开头的特殊消息。**实践影响**：Anthropic 独立字段天然适合 prompt caching（几千 token 的 system 每次不变，缓存命中率高）。M2 Provider 抽象时，统一格式怎么表示 system 是决策点。

### 3.3 工具调用请求格式

```ts
// Anthropic — content block 形式
{ content: [
    { type: 'text', text: '让我看一下...' },
    { type: 'tool_use', id: 'toolu_1', name: 'read_file', input: { path: './x' } }  // input 是对象
]}

// OpenAI — tool_calls 字段
{ message: {
    role: 'assistant', content: null,
    tool_calls: [{ id: 'call_1', type: 'function',
      function: { name: 'read_file', arguments: '{"path":"./x"}' } }]}   // arguments 是字符串
}
```

### 3.4 工具结果回传

```ts
// Anthropic — 塞进 user 消息的 content 数组
{ role: 'user', content: [
    { type: 'tool_result', tool_use_id: 'toolu_1', content: '结果', is_error: false }
]}

// OpenAI — 独立的 role: 'tool' 消息
{ role: 'tool', tool_call_id: 'call_1', content: '结果' }
```

### 3.5 工具定义格式

```ts
// Anthropic
{ name, description, input_schema: { type:'object', properties:{...}, required:[...] } }

// OpenAI（多一层 function 嵌套，字段名 parameters）
{ type: 'function', function: { name, description, parameters: { type:'object', ... } } }
```

### 3.6 错误响应

| 含义 | Anthropic | OpenAI | HTTP |
|------|-----------|--------|------|
| 认证失败 | `authentication_error` | `authentication_error` | 401 |
| 请求超限 | `rate_limit_error` | `rate_limit_error` | 429 |
| 服务端错误 | `api_error` | `server_error` | 500 |
| 服务过载 | `overloaded_error` | — | 529 |

### 3.7 Provider 抽象预告（M2）

抹平上述差异：定义统一内部格式，每家写一个 Provider 翻译。
```ts
interface ModelProvider {
  send(messages: Message[], options: SendOptions): Promise<ModelResponse>;
}
interface ModelResponse {
  content: string;
  toolCalls?: Array<{ id: string; name: string; arguments: Record<string, unknown> }>;  // 统一对象
  stopReason: 'end_turn' | 'tool_use' | 'max_tokens';
  usage: { inputTokens: number; outputTokens: number };
}
```
agent loop 只操作统一格式，换模型只换 Provider，loop 一行不动。详见 [00-开发规划 M2](../总纲/00-开发规划[进行中].md)。

## 四、工具实现技术栈

都是 **Node.js 内置 + 少量库**，无特殊框架：

| 能力 | 工具 | 底层技术栈 |
|------|------|-----------|
| **读取** | `read_file` | Node 内置 `fs.readFileSync`（已在用）。按行/范围读可加 `readline` |
| **精确改** | `edit_file`（待实现） | `readFileSync` 读全文 → 字符串精确替换（oldText→newText）→ `writeFileSync` 写回。复杂场景可上 `diff-match-patch`（模糊匹配） |
| **查内容** | `grep`（待实现） | 调系统 `ripgrep`（`execSync('rg pattern')`，最快）或自己 `readdirSync` 递归 + 正则 |
| **查文件** | `glob`（待实现） | `fast-glob` / `glob` 库，按文件名模式匹配（如 `**/*.ts`） |

### 4.1 edit_file 的难点在策略不在技术栈

LLM 给的 oldText 可能和文件实际内容有出入（空格/换行差异），匹配失败怎么办——**把文件真实行回喂给 LLM 让它重试**（aider 核心洞察，把重构成功率从 20% 拉到 61%）。这是逻辑设计，不是库选择。

### 4.2 grep/glob vs bash+cat：为什么专用工具

| 问题 | bash+cat | 专用工具 |
|------|----------|---------|
| **上下文浪费** | `cat package.json` 整文件塞进 LLM（几千 token） | grep 只返回匹配行（几十 token） |
| **不结构化** | 原始字符串，LLM 自己解析 | 文件名+行号+内容，结构化 |
| **权限失控** | bash 能 `rm -rf` | 只读工具天然安全（M4 好做权限） |
| **输出不可控** | cat 大文件撑爆上下文 | 内置分页/截断 |
| **意图模糊** | LLM 得"想"敲什么 shell 命令 | 工具名即意图 |

**最终效果**：更省 token + 更准 + 更安全 + 更快定位。Claude Code 就这么拆（Read/Grep/Glob/Edit 各自独立），bash 只留给"真正执行命令"（跑测试、装依赖）。

## 五、关键设计答疑

### 5.1 System Prompt（P0-1）

**是什么**：发给 LLM 的"人设 + 行为规则"。本项目当前 [agent.ts](../src/agent.ts) 没传 system，所以模型自称"Claude"。

**和 CLAUDE.md 区别**：

| | CLAUDE.md | System Prompt |
|---|-----------|--------------|
| 形态 | 项目里的**文件** | 发给 LLM 的**字符串** |
| 给谁看 | 人 + AI 助手 | LLM |
| 关系 | 是 system prompt 的**数据来源之一** | 运行时拼装的最终产物 |

**传参**：独立顶层字段，不进 messages：
```ts
anthropic.messages.create({
  system: '你是 ECode...',   // 独立参数，恒在最前、永不累积
  messages: [...],           // 对话历史，累加
  tools: [...],
})
```
agent 调 LLM 跟 git commit 无关，每次传三样独立参数。两家差异见第三章 3.2。

### 5.2 死循环防护（P0-4）

LLM 反复做同一件事（重复读文件、重复调失败工具）。防护方法（业界组合）：

1. **迭代上限**（已有 `MAX_ITERATIONS=25`）——硬切保底。
2. **重复动作检测**：记录最近 N 次 `tool_name + input 哈希`，连续重复 → 注入提示或终止。Claude Code / aider 都有。
3. **失败重试上限**：同一工具失败超 K 次 → 不再执行，回喂"换方案"。
4. **token / 成本上限**：累计超阈值 → 终止（P1-5）。
5. **无进展检测**：连续 M 轮无实质变化 → 终止。

M1 先上 ①②，③④⑤ 后续加。

### 5.3 后置验证（P0-5）—— trust but verify

**思想**：模型常谎报"完成且测试通过"（aider 数据 22.6% 失败源于此）。不能靠模型自觉，必须验证。

**⚠️ 为什么不能"每步强制全量 build+test"**：大项目 build 慢、慢电脑卡、用户干等。无脑全量不合理。

**主流框架（Claude Code / opencode）真实做法**：

| 做法 | 说明 |
|------|------|
| ① LLM 自主决定，非框架每步强制 | bash 工具让 LLM 判断"现在该跑测试"再调 |
| ② 绑定逻辑里程碑 | 验证在"功能完成 / 提交前"触发，非每个 micro-change |
| ③ Hooks 做可配置强制 | Stop/PreToolUse hook 在结束前/push 前自动跑（可配开关/超时） |
| ④ Plan-based verification | 计划阶段定好"何时验证、验证什么" |
| ⑤ 增量验证 | 只跑受影响测试 |

**P0-5 设计**（已更新到 [M1-实施方案](./M1-实施方案[已完成].md)）：① system prompt 引导 LLM 完成时自主跑**相关**测试；② 里程碑 hook 可选触发；③ 增量+超时+可关；④ 结果回喂。核心"trust but verify"不变，方式变聪明。

### 5.4 异步 vs 同步（execSync → spawn）

当前 `executeBash` 用 `execSync`（同步阻塞，命令跑多久 Node 卡多久）。

| 方案 | API | 特点 |
|------|-----|------|
| 当前 | `execSync` | 同步阻塞，简单 |
| 最小改动 | `exec`（异步） | 不阻塞，但仍等全部输出 |
| 推荐（M3+） | `spawn` | 事件驱动流式，能实时回显/取消/优雅 kill |

spawn 比 exec 强在：实时回显、流式喂 LLM（M3）、优雅超时 kill（M4 取消）。M1 不急着换（YAGNI）。

**Windows 三坑**：`shell:true` 必须开（否则复合命令 ENOENT）、跨平台命令差异、超时后进程可能没真死（要 taskkill 杀进程树）。

### 5.5 Subagent 本质（M5+）

**不是 shell 开窗口**，是**进程内再起一个 agent loop 实例**（函数调用）：
- 独立 messages / system prompt / 工具子集
- 跑完只把**最终文本**交回主 agent（中间过程不进主上下文 → **隔离上下文消耗**，这是核心价值）
- 落地 = `dispatch_subagent` 工具内部 `await runAgent(subTask, {silent, tools})`

"shell 开窗口"是子进程模式（`spawn('node', ['subagent.js'])`），隔离更强但通信开销大，非主流。

## 六、Agent Loop 入门 Q&A（基础）

**Q: `process.argv[2]` 是啥？**
Node 内置全局数组，存命令行参数。`[0]`=Node 路径，`[1]`=脚本路径，`[2]` 起是用户参数。`argv[2]` = 任务描述。

**Q: `spawn` 是插件还是命令？**
都不是。是 Node 内置 API（`node:child_process` 模块函数），和 `execSync`/`exec` 同模块，不用装。

**心智模型**（看 import 就知道东西哪来）：
- Node 内置模块：`child_process` / `fs` / `path` / `http` — 运行时自带，import 即用
- npm 包：`@anthropic-ai/sdk` / `vitest` / `tsx` — 要 `npm install`
- shell 命令：`ls` / `npm test` — 用 spawn/execSync 去调

**Q: `truncate(content, 50_000)` 啥意思？**
截断到 5 万字符防撑爆上下文。`50_000` 的 `_` 是 JS 数字分隔符（ES2021），给人看。read_file 用 50k，bash 用 30k（噪音多）。M1 粗暴硬切，M3 换智能压缩。
