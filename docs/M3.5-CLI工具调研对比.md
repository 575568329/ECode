## 三、深度剖析

### 3.1 Claude Code(本尊)—— 顶级投入,自研一切

**技术栈**:Bun + TypeScript(strict)+ React(Compiler 全面采用,每文件 `_c(N)` 自动 memoize)+ **完全自研的 Ink fork**(非 npm Ink)+ yoga + Commander.js + Zod v4。重依赖(OTel/gRPC/analytics)动态 `import()` 延迟加载,`feature('XXX')` 构建期字面量 DCE。

**入口链**:`entrypoints/cli.tsx`(fast-path 分流)→ `main.tsx`(4683 行 Commander)→ `screens/REPL.tsx`(5005 行,主 REPL/agent loop)。

**值得借鉴的设计**:

1. **流式"不抖"的真正秘密 = 渲染层 diff 策略,不是 React memo**。自研管线:`React 树 → reconciler → yoga → Screen 单元格缓冲 → 与上帧 diff → Patch[] → optimizer 合并 → ANSI 写 stdout`。两标志:`prevFrameContaminated`(污染时禁增量)、`layoutShifted`(布局变才宽 damage,稳态帧 O(changed cells))。
2. **ScrollBox 硬件滚动**:emit `DECSTBM + SU/SD` 序列而非重写 viewport。
3. **`useLayoutEffect` 启用 raw mode**:避免 cooked mode 泄漏按键回显。
4. **可编辑权限前缀** `yes-prefix-edited`:即时编辑 `npm run:*`,把拒绝变 feedback。
5. **per-tool PermissionRequest 组件**:`permissionComponentForTool` switch 分发。
6. **Spinner 最小展示时长**(thinking ≥ 2s)防 jank。
7. **JSONL + partialCompactConversation**:compact 保留 pre-compact 消息供审计。
8. **XTVERSION 异步探测**:绕 SSH 丢 `TERM_PROGRAM`。
9. **kill ring(Emacs 风格)**。

**代价/局限**:**自研 Ink fork 是顶级投入**,Anthropic 专职团队的活,不适合 M3.5 照搬。大文件实测(`wc -l`):REPL.tsx **5005 行**(875KB)/ Tool.ts **792 行** / commands.ts **754 行**——内部极复杂(注:早期调研误记 Tool.ts/commands.ts 为"29K/25K 行",实为字节数 29KB/25KB 误标成行数)。

**一句话**:天花板。**学设计思想**(事件流、diff 防抖、权限交互、partial compact),**不学实现规模**(自研 Ink / 巨型文件)。

### 3.2 CCode(社区对标)—— npm Ink 6 实战样本

**技术栈**:Node 20+ + React 19 + **npm Ink 6** + TypeScript(ESM)。辅以 `ink-multiline-input`/`ink-spinner`/`ink-text-input`。

**入口架构(双模式)**:
- **Pipe 模式**(非交互):有 prompt **不启动 React/Ink**,纯 stdout 跑完即退——对应 ECode 现在的 one-shot
- **交互模式**(REPL):无 prompt 启动 Ink
- 主循环:`AgentLoop.run()` = **`AsyncGenerator<AgentEvent>`**,`for await...of` 消费,事件分 4 个语义子 union(exhaustive switch)

**值得借鉴的设计**:

1. **`<Static>` 固化已完成消息(最大亮点)**:O(n)→O(1),用 npm Ink 做长对话的必学招。
2. **双模式(Pipe + REPL)**:non-TTY/带参走老路,TTY 走 REPL。ECode 可直接照搬。
3. **AgentLoop = AsyncGenerator<事件>**:与 ECode 已有 `stream()` + `ECodeStreamPart` 契合。
4. **Windows 兼容实战**:`stdin.prependListener('data')` 拦原始字节,补全扫描码。
5. **双击 Ctrl+C 退出**(2000ms);generation 计数器防竞态;dual-track ref+state;互斥弹窗模式。
6. **JSONL 树形 session**(uuid+parentUuid,fork)。

**工具展示**:三态(running spinner+计时 / done ✓+diff / error ✗)+ ⎿ 折叠 + 结构化 meta。**权限**:Yes/Yes-always/No + diff + 三级优先级链。

**代价/局限**:**`ink-multiline-input` 才 0.1.0 不成熟**,InputBar 大量自研;无 vim、无 Ctrl+R;`ctrl+o expand` 未实现。

**一句话**:ECode 最直接的 Ink 参照系。**它的成功和踩的坑都是前车之鉴。**

### 3.3 opencode(SST)—— TS 同栈,OpenTUI+SolidJS ⭐ 对 ECode 价值最高

**技术栈**:Bun + TypeScript + **OpenTUI(anomalyco 出品 `github.com/anomalyco/opentui`,opencode/SST 采用;`@opentui/core`+`@opentui/solid`)+ SolidJS 1.9.10**(非 React)+ Effect-TS + drizzle(SQLite)+ Vercel AI SDK。

> **关键**:三个本地项目中**唯一与 ECode 同 TS 栈**(虽用 Bun)。OpenTUI 是 SST 发的**独立 npm 包**,可 `npm add` 直接装。

**架构核心——客户端-服务器分离(独有)**:CLI 启动常驻 daemon(HTTP server),LLM/工具/session 在 server 端;TUI 是**纯客户端**,HTTP+SSE 通信。收益:TUI 崩不丢会话、可 headless、可多客户端、可远程。

**响应式范式(非 React VDOM diff)**:`createCliRenderer({targetFps:60, useKittyKeyboard:{}})` + SolidJS signal/store。server SSE event → `produce`/`reconcile` 精确 patch → 只更新依赖字段组件 → OpenTUI 局部 diff。

**值得借鉴的设计**:

1. **客户端-服务器分离**:长会话/可恢复/远程的更优架构(但复杂)。
2. **Extmarks 输入装饰**:输入框内联渲染文件/@agent/paste 摘要的虚拟文本,**编辑器级输入体验**。
3. **Paste summary**:大段粘贴自动摘要(省 token 留上下文)。
4. **Prompt stash**(类 git stash):`/stash`/`/pop`。
5. **命令四用**:一个 command 对象 = slash = 快捷键 = palette 项。
6. **Context Epoch**:baseline 作 provider cache 稳定键,提升 cache hit。
7. **Sticky scroll + 局部 diff**:比 `<Static>` 优雅。
8. **权限差异化展示**:edit 给 diff、bash 给 `$ {cmd}`、glob 给 pattern。
9. **Effect-TS 资源管理**:`Effect.acquireRelease` 保证清理顺序。
10. **Windows Ctrl+C 三重防护**:`bun:ffi` 直操 kernel32 + hook setRawMode + setImmediate + 轮询 backstop。

**代价/局限**:
- **Bun 运行时**:ECode 用 Node。OpenTUI 渲染器是 **Zig native**(见本节顶部),Node 下走渲染器需运行时 FFI;opencode 的 Windows 终端控制用 `bun:ffi`(`terminal-win32.ts:1`)直操 kernel32,Node 下无 `bun:ffi` 等价物,需换运行时 FFI 方案(koffi 或 Node `--experimental-ffi`)——**选 OpenTUI 必须先验证 Node 兼容**(详见选型 §2.1,结论:走不通)。
- CS 分离复杂度高(单人单次用,单进程更简单)。
- OpenTUI 0.4.5 新生态,SST 自用为主,文档/社区不如 Ink。
- Effect-TS 学习曲线。

**一句话**:对 ECode 价值最高——**同 TS 栈、OpenTUI 可 npm 装、组件全、设计现代**。**但跑 Bun + CS 分离,这两点必须先验证/权衡。**

### 3.4 codex(OpenAI)—— Rust + ratatui 深度 fork,工程纪律标杆

**技术栈**:Rust 2024 + **ratatui 0.29(深度 fork)+ crossterm 0.28(深度 fork)** + tokio + sqlx(SQLite)。70+ crate 的超细 workspace。早期 TS+Ink 版已于 2025-05 废弃迁 Rust。

> fork 证据:`[patch.crates-io]` 指向 nornagon 的 crossterm/ratatui fork;启用 ratatui 不稳定 feature `scrolling-regions` / `unstable-backend-writer`(绕默认双缓冲,性能关键)/ `unstable-rendered-line-info`。

**架构核心——双轨制 + NDJSON protocol**:
- `should_use_app_server_tui()` 切换:Legacy in-process(`codex_tui::run_main`)↔ app-server(client/server,`codex_tui_app_server::run_main`)。**比 opencode"一上来就 CS"更务实——默认单进程,预留 CS 能力**。
- **wire protocol = NDJSON 流**(`protocol` crate):每行一个 JSON 事件。这让任意语言/工具可作 client(IDE/Web 都能接)。

**值得借鉴的设计**:

1. **双轨制架构**:先 in-process,预留 protocol 抽象,未来切 CS。ECode 可照此**渐进式**演进 D8。
2. **NDJSON wire protocol**:事件流的可插拔设计参考。
3. **流式防抖 = fork 绕双缓冲 + markdown 增量解析**:印证"流式不抖要动渲染层"。markdown 用 pulldown-cmark 流式 feed。
4. **双配置(审批 + 沙箱正交,简洁,M4 可借鉴)**:
   - `approval_policy`(审批策略):`untrusted`(默认,任何写/执行都问)/ `on-request` / `on-failure`(失败才问)/ `never`(不问)。
   - `sandbox_mode`(沙箱范围):`read-only` / `workspace-write`(可写 cwd) / `danger-full-access`(无限制)。
   - 内部更细 `SandboxPermission` 枚举(DiskWriteCwd / NetworkFullAccess / ...)。
   > 出处:codex protocol crate + [ChatGPT Learn「Agent approvals & security」](https://learn.chatgpt.com/docs/agent-approvals-security)。早期调研误把 `read-only/auto/full-access` 当成单一"approval 三档"——实际 `auto` 非枚举值,read-only/full-access 属 `sandbox_mode`,审批是另一套 `approval_policy`。
5. **跨平台沙箱**:macOS sandbox-exec / Linux Landlock+seccomp / Windows windows-sandbox-rs。无 OS 沙箱时退化到环境变量开关。
6. **session 双存储**:JSONL(append,崩溃不丢)+ SQLite(查询/resume picker)。**Fork session**(从某点分支探索,不影响原线)是亮点。
7. **工程纪律**:`clippy` 设 `unwrap_used="deny"` / `expect_used="deny"`(强制错误处理);release `lto="thin"` + `codegen-units=1`。

**代价/局限**:Rust,与 ECode 栈不同(纯设计借鉴,实现不可迁移);UI 细节(chatwidget/diff_render/slash 列表)公开资料未深读;Windows 仍在打磨(源码注释原话"reconsider when officially supported on Windows")。

**一句话**:codex 是**工程纪律和架构取舍的标杆**——双轨制、NDJSON 协议、approval 三档、JSONL+SQLite 双存储都值得 ECode 借鉴(实现层面 Rust 不可迁移)。

## 四、横向议题:关键设计,各家怎么解

### 4.1 UI 范式:四种路线并存

| 路线 | 代表 | 心智模型 | 流式防闪 | 框架是否需 fork |
|------|------|----------|----------|----------------|
| **行式 readline** | aider | append-only 天然固化 | 逐字 append | 无框架 |
| **npm Ink + React** | CCode、gemini-cli、qwen-code | React reconciler+Yoga+VDOM diff | `<Static>` | **是**(gemini-cli/qwen-code 都 fork;CCode 用官方但 multiline 要自研补丁) |
| **自研 Ink fork + React** | Claude Code | 同上但自研渲染管线 | 双缓冲+双标志+intern | 本身就是 fork |
| **OpenTUI + SolidJS** | opencode | 细粒度 signal,无 VDOM diff | sticky+局部diff | 否(用 SST 官方包) |
| **ratatui + crossterm fork** | codex | 中心化状态机 | fork 绕双缓冲+增量解析 | 是(深度 fork) |

**观察**:全屏 TUI 是事实标准。**对 ECode(TS 栈),路线收敛到两种:Ink+React 或 OpenTUI+SolidJS**。**关键警示:Ink 路线多家大厂选择 fork 而非用官方,说明 ink 默认实现可能不够用——ECode 选 Ink 要有"可能需 fork 或重度打补丁"的心理准备。**

### 4.2 流式渲染"不抖"各家解法

- **CCode**(便宜):`<Static>` 固化已完成。
- **Claude Code**(贵):自研双缓冲+双标志+intern 池+硬件滚动。
- **opencode**(优雅):SolidJS 细粒度响应式 `produce`/`reconcile` 精确 patch + sticky scroll。
- **codex**(硬核):fork ratatui 启用 `unstable-backend-writer` 绕默认双缓冲 + markdown 增量解析。
- **共性**:流式"不抖"是渲染层 diff 问题,**不是 React memo 问题**。四家都动了渲染层。

### 4.4 Windows 兼容(⚠️ ECode win32 优先,重点)

投入递增:
- **CCode**(中):`stdin.prependListener` 拦原始字节。
- **Claude Code**(重):自实现 ANSI parser + XTVERSION 探测 + 逐终端白名单。
- **opencode**(最硬核):`bun:ffi` 直操 kernel32 + Ctrl+C 三重防护。**但依赖 bun:ffi,Node 下无等价物需换运行时 FFI(koffi/experimental-ffi)**。
- **codex**:crossterm 跨平台 + windows-sys + windows-sandbox-rs。**源码明说"仍在打磨"**。

**结论**:全屏 TUI 在 Windows **没有捷径**。**OpenTUI 的 ffi(Zig native + bun:ffi)在 Node 下需换运行时 FFI,是 (c) 路线的关键风险**(选型 §2.1 结论:走不通)。这条成本必须算进 D1/D7。

### 4.5 AgentLoop ↔ UI 解耦:事件流是共识(四种实现)

- **CCode**:`AsyncGenerator<AgentEvent>` + `for await`,4 子 union。
- **Claude Code**:组件订阅 stream。
- **opencode**:server SSE → SolidJS store patch(因 CS 分离,事件流天然是网络协议)。
- **codex**:**NDJSON wire protocol**(每行一 JSON 事件,可被任意 client 消费)。
- **共性**:agent core 都**不直接 console.log**,产出结构化事件流。

**对 ECode**:这是 M3.5 **真正核心**(比 UI 范式重要)。`runAgent()` 要改 yield 事件流,Provider `stream()` 要实现。**这层做好,UI 是 readline/Ink/OpenTUI 都能接。** 可参考 codex 的 NDJSON 协议设计(为未来 IDE/Web client 留口子)。

### 4.6 工具调用展示(标准范式)

四项目高度一致:多态(running spinner+计时 / done ✓+diff / error ✗ / [denied])+ 折叠 + 结构化 meta + 工具名映射。ECode 现有 `⚡✅` 已是雏形。

### 4.7 权限确认

- **codex**(简洁,M4 可借鉴):**双配置** `approval_policy`(untrusted/on-request/on-failure/never)+ `sandbox_mode`(read-only/workspace-write/danger-full-access)+ 跨平台沙箱。
- **Claude Code**(最强):可编辑前缀 + feedback + per-tool 组件。
- **opencode**(完整):once/always/reject + 差异化 + 全屏。
- **CCode**(够用):Yes/Yes-always/No + diff。
- **注**:权限属 ECode **M4**,M3.5 可先不做或最简版。

### 4.8 session 存储(JSONL vs SQLite vs 双存储)

- **JSONL**(Claude Code / CCode):append、可流式读、git 友好。
- **SQLite**(opencode):结构化查询、事务、多客户端。
- **双存储 JSONL+SQLite**(codex):JSONL 崩溃不丢 + SQLite 查询/resume。**最稳**。
- **ECode 现状**:`session.ts` 纯数据层,原子写 tmp+rename,**整 JSON 重写非 append**。当前够用(YAGNI);若要 resume picker 搜索,可考虑 codex 式双存储。

## 五、对 ECode M3.5 的启示与待决断点

> **再次声明**:本节只列启示和待决断点,**不替读者做选型决断**。

### 5.1 强共识(几乎不用决断,照做)

1. **AgentLoop 事件化是 M3.5 真正核心**(无论 UI 选什么)。`runAgent` 改产出事件流,Provider 实现 `stream()`。与 UI 范式正交,先做。
2. **事件流用语义化判别联合**(仿 CCode 4 子 union + exhaustive switch),与已有 `ECodeStreamPart` 对齐/扩展。可参考 codex NDJSON 协议为未来 client 留口子。
3. **中断用 AbortController**,保持 `tool_use`/`tool_result` 配对(中断难点:工具执行后回传前,合成 tool_result 或跳过本轮——需专门设计)。
4. **流式"不抖"**:走 TUI 则用固化策略(Ink `<Static>` / OpenTUI sticky)。
5. **双模式(Pipe + REPL)**:non-TTY/带参走 one-shot(现有),TTY 走 REPL。CCode 已验证。
6. **session 存储**:当前 JSON 重写够用(YAGNI);SQLite 对单进程过重;未来要 resume 搜索可考虑 codex 式双存储。
7. **进程架构渐进式**(仿 codex 双轨制):先 in-process,预留 protocol 抽象,未来按需切 CS。

### 5.3 D1 范式选型详细对比(核心)

| | (a) 行式 readline | (b) npm Ink + React | (c) OpenTUI + SolidJS | (d) 自研 Ink |
|---|---|---|---|---|
| **对标** | aider | CCode、gemini-cli、qwen-code | opencode | Claude Code |
| **同栈迁移成本** | 低(Node 内置) | 低(TS,有 CCode 现成参照) | **低(TS,OpenTUI 可 npm 装)** | 极高 |
| **实时工具面板/状态栏** | ❌ | ✅ | ✅ | ✅ |
| **流式不抖** | 天然不重绘 | `<Static>` | sticky+局部diff | 自研 |
| **内置组件丰富度** | 无 | 中(multiline **不成熟**) | **高(Markdown/Diff/Scrollbox/Textarea/shiki 内置)** | 无 |
| **框架是否需 fork/重度补丁** | — | **是**(gemini-cli/qwen-code 都 fork;CCode 官方+multiline 自研) | 否(用官方包) | — |
| **输入体验天花板** | L1-L2 | L2(自研到 L3) | L2 + L+ 装饰 | L3 |
| **Windows 兼容难度** | 小 | 中(prependListener) | **大(ffi,Node 需换 koffi)** | 大 |
| **心智模型** | 简单 | React(VDOM diff) | SolidJS(signal) | React 自研 |
| **生态/文档成熟度** | 高(Node 内置) | 高(Ink 成熟) | 中(OpenTUI 新,SST 自用) | — |
| **工作量** | 小 | 中 | 中(需验证 Node 兼容) | 极大 |
| **风险** | 体验到不了"对标" | ink 可能需 fork/重度补丁;multiline 不成熟 | **Zig native + bun:ffi,Node 下需运行时 FFI(选型 §2.1 判定走不通)** | 无底洞 |

**选型核心张力**:
- **项目原则**:"手写核心、拒绝框架黑盒" vs 引入 UI 框架(React 或 SolidJS)。
  - 反驳:UI 框架是**渲染层**,非 **agent 核心**。agent loop/Provider/上下文仍自己写。不违反核心原则。
- **(b) Ink vs (c) OpenTUI**:都 TS 栈、都能对标。
  - Ink 更成熟,但 **multiline 不成熟 + 多家大厂选择 fork** 是双重风险信号。
  - OpenTUI 组件更全、设计更现代,但**新生态 + Node 兼容未验证**是关键风险。
- **可演进性(降低决断风险的钥匙)**:无论选哪个,**阶段①事件化**做好后,UI 层可替换(先 readline,后升 Ink/OpenTUI,agent core 不动)。**选错了也能改。**

### 5.4 建议的推进结构(无论 D1 选啥)

M3.5 切两段,降低 D1 决断风险:
- **阶段 ①(UI 无关,必须做)**:`runAgent` 事件化 + Provider `stream()` 实现 + AbortController 中断(保配对)+ slash 命令分发(纯逻辑)。**做完,现有 one-shot 立刻享受逐字流式**——独立交付价值。
- **阶段 ②(UI 范式相关,等 D1 定)**:沉浸 REPL 外壳。这里才分 readline / Ink / OpenTUI。

> 💡 **若 D1 在 (b) Ink vs (c) OpenTUI 间犹豫**:可先花 1-2 小时做**兼容性/可行性 spike**——`npm add @opentui/core` 在 Node 跑个 hello world,验证 Node 兼容(尤其 ffi 部分);同时 `npm add ink` 跑个 `<Static>` demo。用实证消除 (c) 的"Node 兼容未验证"风险,再决断。
