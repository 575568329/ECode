# M13 多会话并发与 Web 同步调研（同项目多对话 + 多基座单流）

- 日期：2026-08-24
- 状态：已完成
- 背景与问题：M13 前置拍板（M12 方案 §15）后用户追问两连——「同项目多个对话同时进行怎么办」「一个 Web 怎么同步多个基座」。带着问题源码实证 deepseek-harness（重点）与 opencode（对照），两家本地源码 `D:\study\deepseek-harness` / `D:\study\opencode`（2026-08-21 拉取的最新版）。
- 结论一句话：**两家都完整支持同项目多对话并发，模式高度一致——「会话级并发 + 项目级（或进程级）共享」；Web 同步用一条聚合流（mux）而非每项目一条连接。ECode 现有 ProjectRegistry 天生是 opencode 流派骨架，差「对话轻对象化」一步。**

## 1. 两家流派对照

| 维度 | deepseek-harness | opencode | ECode 现状 | ECode 目标（M13） |
|---|---|---|---|---|
| 基座（重资源容器）粒度 | **进程级**：host Context 一个大基座（LLM 客户端全局一套） | **项目级**：Instance 按 directory 缓存一套重资源 | 项目级：ProjectRegistry path→HostSession（makeDeps 全套重装配） | 保持项目级（ProjectHost），不学 harness 上提进程级 |
| 对话建模 | Session（事件日志）+ Agent（独立循环）1:1，各自 Inbox/Scope | Session 轻对象（DB 行）+ Runner 独立状态机 | 宿主内单份 messages，restore=换台 | ConversationHost 轻对象，同项目 N 个并行 |
| 同目录多对话 | 完全允许，无 FS 互斥 | 完全允许，`assertNotBusy` 只查同 sessionID | 不支持（单活跃） | 支持 |
| 重资源共享 | LLM/持久化进程级；tools 按 agent scope | Config/Provider/MCP/LSP/Snapshot/ToolRegistry/Plugin 全 Instance 级；Database 进程级 | tools+MCP+checkpoint+quality 全套在（项目级）宿主内 | 拆两层：项目级共享 + 会话级私有 |
| 事件流 | **mux 单流**：所有 session 事件汇入同一条 SSE 广播 | pub/sub 总线按 topic 广播 | 每项目一条 `/api/p/<path>/events` | mux 单流 + 帧带 project/sessionId |
| 历史恢复 | `session.history` 按 beforeSeq 分页（消息条数对齐），全量重放非快照 | `GET /session/:id/message` 查询 | `session/read`（枚举已有已路由） | 同左，配会话级宿主 |
| 会话回收 | **不存在**：AgentRegistry Map 只增不减，无任何定时器/TTL/sweep；RPC 无 delete 方法（archive 只隐藏不释放） | **不存在**：Instance 加载后永不卸载（ScopedCache capacity=∞）；两个局部例外=Runner onIdle 自动删自身（run-state.ts:60-63，仅协调器对象不动重资源）+snapshot 每小时 git gc --prune=7.days（纯磁盘）；HTTP 层不暴露 delete | sweepIdle 项目粒度（订阅/审批挂起不收，60s sweep/30min 阈值——**三家里最激进**） | 项目基座常驻不收（两家实证支持）；会话级 sweep 保留但阈值放宽（会话持有完整 messages 内存态比 harness 事件日志重，收内存不收磁盘） |
| 冲突防护（并发写同项目） | 无（FS 无隔离，共享真实文件系统） | 务实两锁：edit per-file Semaphore（进程全局）+ snapshot per-gitdir Semaphore；**write 无锁** | checkpoint content-addressed（哈希天然去重） | 对齐 opencode 水平即可，不建大机制 |

## 2. deepseek-harness 实证细节（重点参考）

### 2.1 会话对象建模：Session + Agent 1:1，每对话独立循环

- Session 是纯追加事件日志容器：`packages/core/session/src/index.ts:425-426`（`private log: SessionEvent[] = []`）、`:604-655`（append）；SessionStore 全局 `Map<SessionId, SessionEntry>`（`:793`）。
- Agent 接口 1:1 绑 session：`packages/core/agent/src/runtime-types.ts:64-70`（`{ id, session, inbox, ctx }`）；AgentRegistry `Map<SessionId, AgentEntry>`（`packages/core/agent/src/index.ts:257`）。
- ReactLoopAgent 每实例独立驱动：`packages/core/agent-loop/src/agent.ts:64`，构造即建独立 `Inbox`/`Scope`/`Context`（`:80-97`）；`kick()` 独立 while 循环（`:210-223`）——多对话并发=多个 kick 链并行在 event loop，互不阻塞。

### 2.2 session 与目录：cwd 不可变字段，多对话同目录零互斥

- `header.cwd` 创建时写入不可变（`packages/core/session/src/types.ts:61-73`，校验绝对路径 `index.ts:112-117`）；创建链 `packages/host/apiproxy/src/api-proxy.ts:1618-1619`、`:2096`（解析优先级 workspace 路径 > 请求指定 > 默认）。
- 同 sessionId 不同 cwd 才报错（幂等保护，`api-proxy.ts:989-1001`、`:1648-1650`）；**不同 sessionId 同 cwd 完全合法**；`ensureSession` 对同 cwd 只 `mkdir`（`:1609-1613`），无文件锁。
- Workspace 是**目录级聚合视图而非资源容器**：`packages/workspace/workspace/src/types.ts:23-51`（`{ path, sessionIds }`）、`entity.ts:109-148`（attach 校验 cwd canonical 匹配）——只管列表归属，不持资源。

### 2.3 生命周期：幂等单飞创建 + 持久化 resume

- 路由 `POST /api/session.create`（`packages/host/apiproxy/src/fetch/handler.ts:93`）→ `ensureSession`（`api-proxy.ts:1563-1652`）：`sessionCreations Map` 并发同 key 只建一次（`:1072`，**deferred 单飞——与 ECode ProjectRegistry 同款**）；已活直接返（`:1572-1577`）；持久化已有则 resume（`:1579-1607`；冷会话首次访问 resume：`packages/api/remotes/src/agent-lookup.ts:144-172`）。

### 2.4 mux 单流：一条 SSE 装下所有项目所有对话（Web 同步的直接答案）

- `GET /api/events.mux`（`api-proxy.ts:3344-3446`）：每个连接一个 FrameQueue 加入全局 `muxQueues`（`:1077`），**所有 session 的事件广播到所有 mux 消费者**，帧带 sessionId 前端过滤。
- 连接建立三连：① `session/subscribed` baseline（当前活会话清单，`:3347-3349`）——前端初始列表不用先打 REST；② 重放未决 approval/question 帧（`:3350-3361`）；③ 各会话 inbox 快照（`:3365-3370`）。
- host 级事件另流 `GET /api/events.host`（`:3448-3550`）：会话创建/销毁、running 翻转——列表实时增删不靠轮询。
- 反例（M12 调研已记）：mux 全广播零 per-client 过滤——ECode loopback 场景可接受，per-client 会话过滤留在 M13 升级位。

### 2.5 列表与恢复

- `session.list` 合并 attached（内存）+ cold（持久化）按 updatedAt 降序（`api-proxy.ts:1948-1949`、`:1670-1730`）；Summary 含 cwd/running/parentSessionId（`packages/host/apiproxy/src/api/sessions.ts:177-222`）。
- `session.history` 分页（`:2158-2186`）：单位是**消息条数**（默认 50）按消息边界对齐（`:232-258` paginate）；attached 内存读 / 冷会话持久化 inspect（`:1478-1483`）——全量重放，非快照。

## 3. opencode 实证细节（ECode 改造的直接蓝本）

### 3.1 两层架构：Instance（项目基座）+ Session（轻对话）

- InstanceState：按 directory 键控的 ScopedCache 延迟初始化（`packages/opencode/src/effect/instance-state.ts`）——`makeGlobalNode` 全局 + per-directory 一套。
- Instance 级共享清单（全部 `InstanceState.make`）：Config（`config.ts:600`）、Provider（`provider.ts:1370`）、**MCP**（`mcp/index.ts:492`）、LSP（`lsp/lsp.ts:145`）、Snapshot git 仓库（`snapshot/index.ts:66`）、ToolRegistry（`tool/registry.ts:121`）、Plugin/Permission/SessionStatus/SessionRunState；Database 进程级全局（`packages/core/src/database/database.ts:57`）。
- Session 级私有：消息（`session_id` 外键查询 `session.ts:828-851`）、Runner 循环（`run-state.ts:35-38` `Map<SessionID, Runner>`）、Processor 闭包。
- Session.create 只是写 DB 行不启动循环（`session.ts:667-689`）；Info schema 含 directory/projectID/parentID（`:224-244`）。

### 3.2 并发无目录互斥

- `assertNotBusy` 只查同 sessionID（`run-state.ts:71-75`）；Runner 状态机 Idle|Running|Shell per-session（`runner.ts:33-37`）——同目录 100 个 session 并发跑无任何目录级锁。
- 请求路由两级：`?directory=` / `x-opencode-directory` / session 记录的 directory 三源定目录（`middleware/workspace-routing.ts:148-186`）→ `InstanceContextMiddleware` load-or-create Instance（`middleware/instance-context.ts:23-35`）。

### 3.3 API 形态与会话操作

- 路由组（`server/routes/instance/httpapi/groups/session.ts:78-105`）：list/get/create/remove/update/**fork**/abort/**prompt（同步流式）/prompt_async（204 fire-and-forget）/command/shell/revert/messages/children/share/summarize。
- 回收：无自动回收，手动 `DELETE /session/:id`（`session.ts:606-627` 递归删子会话）+ 归档（`:757-759`，list 默认过滤）；Instance 级 `disposeInstance` 清整套 MCP/LSP。

### 3.4 冲突防护的务实水平（ECode 对齐基准）

- edit 工具 per-file 信号量，**进程级全局**（`tool/edit.ts:35-45`、`:88` read→ask→write 原子段）——跨 session 同文件 edit 串行。
- snapshot per-gitdir 信号量（`snapshot/index.ts:55-64`、`:165` track/patch/restore/revert/diff 全包裹）——防两 session 并发 git 操作损 index。
- **write 工具无锁**（`tool/write.ts:38-101` 直写）——跨 session 写同文件 last-write-wins；revert+write 交错有竞态。两家都没把并发写当架构问题，靠"用户别同时让两个对话改同一个文件"的社会约束。

### 3.5 空闲回收实证（2026-08-24 补充调研：两家都是纯常驻，ECode 最激进）

> 追问「web 长时间没对话基座会收吗」引出的专项查证，全库 grep `idle|ttl|timeout|sweep|prune|evict|gc` 无漏判。

- **harness 零回收**：`AgentRegistry.store`（`core/agent/src/index.ts:257`）只增不减，唯一 delete 在 `detachEntered`（`:518`）且只由显式 `AgentHandle.dispose()` 触发——而 Web 场景 dispose 仅两处调用：SDK `shutdown()`（`sdk/server/src/server.ts:150-181`）/ACP stdio 断连 quiesce（`acp/acp/src/index.ts:451-517`）。RPC 映射无 session.delete（`host/apiproxy/src/api/rpc-map.ts:25-36` 仅 list/search/create/history/models/selectModel/rename/fork/prompt/attachment/updateQueue/cancel）；archiveSession 只加归档集合不释放资源（`api/workspace.ts:100-108`）。MCP 连接只有断线重连监督无 idle 断开（`mcp/mcp-client/src/connection.ts:123`）；LSP 实例池 `evictIfCurrent` 只在实例已死时删（`lsp/lsp-stdio/src/index.ts:330-333`）。
- **opencode 零回收（两局部例外）**：InstanceStore.cache 只在显式 dispose 动（`project/instance-store.ts:43`，finalizer `:192` 仅 Scope 关闭）；InstanceState `ScopedCache` capacity=∞ 永不驱逐（`effect/instance-state.ts:31`）；HTTP 17 个 session handler 无 delete（`server/src/handlers/session.ts`）；业务层 `Session.remove`（`session/session.ts:606-627`）只删 DB 行+发事件，不释放 Instance 资源；MCP 显式 disconnect API 存在但无 idle 调用（`mcp/index.ts:653-658`）；LSP clients 数组从不按 idle 清（`lsp/lsp.ts:192`）。例外①Runner onIdle 自动删自身（`session/run-state.ts:60-63`——只删协调器对象，重资源不动）；例外②snapshot 每小时 git gc（`snapshot/index.ts:761-766`，启动 1 分钟后首跑，`git gc --prune=7.days` 纯磁盘）。
- **对 M13 的印证**：项目基座常驻（A2 方向）两家实证支持——内存换冷启动延迟，划算；ECode 会话级 sweep 是比两家多做的事，理由充分（ECode 会话持完整 messages 内存态，比 harness 事件日志重），保留但阈值放宽；ECode 现行项目级 sweep 在拆两层后退役为"项目基座不收"。

## 4. ECode 改造清单（M13 第一批架构批输入）

> 依赖关系：B 依赖 A（mux 帧带 sessionId 前提是会话级宿主）；C1/C3 独立可先行；C2 语义被 A4 吸收升级。

### A. 两层宿主（会话级并发的本体）

1. **HostSession 拆分**：ProjectHost（项目级共享：MCP manager/checkpoint/config getter/logger/quality 命令探测/hooks 表）+ ConversationHost（会话级私有：messages/loop 运行态/InMemoryChannel/ApprovalBroker/插话队列/usage 累计器）——对齐 opencode Instance/Session 分层；ECode `makeDeps` 拆「项目级构造一次」与「会话级各造一份」两段。
2. **ProjectRegistry 升维**：path→ProjectHost（锁语义不变=进程层面项目唯一）+ ProjectHost 内 `Map<sessionId, ConversationHost>`；创建幂等单飞（harness `sessionCreations` 同款）；sweepIdle 降会话粒度（项目基座常驻倾向，闲置收会话）。
3. **协议帧升维**：帧结构加 `project` + `sessionId`（事件枚举值不动；seq 保持会话级单调）。
4. **serveMulti 路由两级**：`/api/p/<path>/cmd` 增 sessionId 维度（或收敛为 `/api/cmd { project, sessionId, op }` 统一带路由）。

### B. mux 单流（Web 多基座同步）

1. `GET /api/events.mux`：一条 SSE 汇所有项目所有会话（复用现有 drain 背压/15s 心跳/token/loopback 工程包）；`/api/p/<path>/events` 保留为单项目调试端点。
2. host 级生命周期帧：`project/added·removed`、`session/created·removed`（新增枚举）——Web 左侧列表实时增删不轮询。
3. 连接 baseline：打开先推活会话清单 + 重放 pending 审批（broker 订阅即重放已有，只差汇流层接上）。

### C. 与已拍板三小块的融合（M12 方案 §15）

1. meta.cwd：不变，仍独立可先行。
2. `session/restore` **语义升级**：原「补 case 调 restoreFrom 换台」被 A 吸收——restore = ensure 会话级宿主载入该会话（幂等单飞），restoreFrom 复用；命令本身仍是 M13 必做，实现随架构批走。
3. `/api/projects` 增强（∪ 历史聚合 meta.cwd 去重）：不变。

### D. 冲突防护（对齐 opencode 水平，不建大机制）

- ECode checkpoint content-addressed 哈希去重天然适配多会话（同内容快照无害共存），快照目录层面无需 gitdir 锁（无共享 git index 操作）。
- edit 工具 per-file 锁：挂账观察（真出现两对话编辑同文件的实践再上，与 opencode 相同的信号量方案 10 行内可补）。
- git autoCommit：仅父轮末提交，多会话交织为提交历史交织（低危，git 原子），挂账观察。

### 量级与排期

- 原 §15 三小块（半天）→ 合并架构批后 **5-7 天**（A 是大头：HostSession 拆分是 M12 以来最大单笔手术；B/C 顺流而下）。
- 顺序建议：A1+A2（宿主两层）→ A3+A4+B（协议升维+mux）→ C 融合验收 → Web UI（M13 主体）消费最终形态，避免 UI 先写后返工。
- **「明确不做」继续成立**：活流回填/SSE 补帧（mux 是汇流不是回放，历史恢复仍走 session/read 分页——两家同款全量重放路线）；TUI 跨进程连 serve。
