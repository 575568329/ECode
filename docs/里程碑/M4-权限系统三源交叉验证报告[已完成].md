## 三、共识与分歧

### 3.1 三源共识（强信号，可放心采纳）

1. **CLAUDE.md 不参与权限判定**——三源全部验证：CC 把 CLAUDE.md 作受保护路径但不作规则源；opencode 把它仅作 system prompt；CCode 同样。**给 ECode 的启示**：instructions-loader 和 permission 模块完全隔离，不要耦合。
2. **deny 优先于 ask 优先于 allow**——CC 在 `hasPermissionsToUseToolInner` 显式分阶段；opencode 通过 `findLast` 让用户规则覆盖默认；CCode 没有规则层。**给 ECode 的启示**：评估顺序遵循 deny → ask → allow。
3. **allow_always 至少要 session 内存**——三源都有；CC 还做了 5 层磁盘持久化；opencode 和 CCode 都只内存。**给 ECode 的启示**：M4 至少要做到内存 allow_always（已有），项目级写盘是加分项。
4. **bash 是最特殊的工具**——CC 给 bash 单独写 2621 行；opencode 给 bash 单独的 arity 字典 + tree-sitter；CCode 干脆不分级（最危险）。**给 ECode 的启示**：bash 必须单独建子模块，不能与其他工具混用同一规则集。
5. **危险工具列表有共识**——bash / write / edit / MCP 都被三源标为危险（CCode 全部 dangerous=true；opencode 全部 `*:allow` 但主动 ask；CC 走 `checkWritePermissionForTool`）。
6. **路径越界 = 性价比最高的安全网**——CC 做了 symlink + macOS `/var` + Windows NTFS 备用数据流 + 8.3 短名全套；opencode 做了 `containsPath` + `external_directory` 权限；CCode 完全没做（最大缺口）。**给 ECode 的启示**：必须做，至少做到 opencode 的水平。

### 3.2 三源分歧（关键决策点）

1. **模式数量**：CC 5+ 种（含 ant 内部），opencode 2 种，CCode 0 种。**ECode 单包 CLI 不需要 CC 的全部模式**——`default/acceptEdits/bypass` 三档足够；`plan` 和 `dontAsk` 是 YAGNI。
2. **命令解析策略**：CC 和 opencode 都用 tree-sitter，CCode 不解析。但 **opencode 的 arity 字典思路 ≠ tree-sitter AST**——它用预生成的「命令前缀 → token 数」字典归约，远比 tree-sitter 轻。**ECode 应该借鉴 opencode arity 字典而非 CC tree-sitter**。
3. **配置合并优先级**：CC 是"层级 + 首匹配"，opencode 是"扁平 + last wins"。**opencode 的 last wins 更易推理**，配置文件修改更直观。
4. **allow_always 持久化**：CC 写盘（多层），opencode 和 CCode 都只内存。**业界实际趋势是不写盘**（避免误点导致永久放行）；用户必须手写配置文件来持久化。**ECode 默认应只 session 内存，写盘是用户主动行为**。
5. **审批 UI 选项数**：CC 5 选项（最强，含可编辑前缀），opencode 3 阶段状态机（最现代），CCode 3 固定（最简）。**ECode 当前 = CCode（3 固定选项）**；opencode 的"always 二次确认 + reject 反馈框"是性价比最高的升级方向。
6. **ruleset 表达能力**：CC 最强（3 种匹配类型 + 复合命令防护 + 命令注入检测 + Windows 路径攻击防护）；opencode 中等（pattern + 通配符 + arity 模板）；CCode 最弱（不支持参数模式）。**ECode 应取 opencode 水平**——支持 pattern + 通配符，不必引入 Windows NTFS 攻击防护（YAGNI）。

### 3.3 各源独有特色

- **CC 独有**：5 模式 + classifier（Haiku LLM 自动分类，feature flag 控制）+ 可编辑前缀审批 + per-tool 组件 + 企业策略 + MDM + 5 层配置源 + Windows 路径攻击全套防护 + cd+git RCE 检测 + sed 危险操作检测 + ZSH 危险命令 + 命令注入特征检测 + 只读命令白名单（5 套：git/gh/docker/rg/pyright）+ auto 模式分类器拒绝文案
- **opencode 独有**：tree-sitter 生成双 pattern（source + arity prefix）+ last-wins 合并 + doom_loop 权限 + 3 阶段审批状态机 + always 二次确认 + reject 带反馈框 + 子代理 ruleset 继承 + ACP（Agent Client Protocol）+ `OPENCODE_PERMISSION` 环境变量 + 环境变量 `*.env` 默认 ask + macOS MDM
- **CCode 独有**：基本没有（最简），唯一独有的：git commit 时拦敏感文件名 + `--no-tools` 完全禁用工具开关 + sidechain 子代理跳过

## 四、对 ECode M4 的推荐设计

### 4.1 总体哲学：借鉴 opencode 的"现代精简"，避开 CC 的"重工业流水线"

ECode 的项目定位（单包 CLI + 手写 agent + 拒绝框架黑盒）决定了不能照搬 CC 2621 行的 bashPermissions.ts。**opencode 的设计语言最契合 ECode**：
- 同 TS 栈
- 模块边界清晰（permission/index.ts + arity.ts + tool/shell.ts）
- 配置表达式强（last wins + 通配符 + always pattern）
- 持久化策略保守（默认内存，不写盘）

### 4.2 模式体系：保留 3 档，砍掉 plan 和 dontAsk

| 模式 | 语义 | 借鉴 |
|---|---|---|
| `default` | 危险工具 ask，安全工具 allow | 三源共识 |
| `acceptEdits` | edit/write 自动 allow（在工作目录内），bash 仍按规则 | CC `modeValidation.ts:7-15`（acceptEdits 自动放行 `mkdir/touch/rm/rmdir/mv/cp/sed`） |
| `bypass` | 全部 allow（仅开发调试，明确警示） | CC `bypassPermissions` + opencode `--auto` |

**砍掉**：
- `plan`：opencode 用 deny edit 规则模拟，比独立模式更灵活；ECode 可放到 M5+
- `dontAsk`：headless 已经能 deny，不需要独立模式
- `auto`（CC classifier）：依赖 LLM 分类，成本高，开源产品不合适

**切换方式**：
- CLI：`--permission-mode <default|acceptEdits|bypass>` + `--dangerously-skip-permissions`（= bypass）
- 会话内：Shift+Tab 循环（仿 CC `getNextPermissionMode.ts:34-79`）
- 配置：`.ecode/settings.json` 的 `permissions.defaultMode` 字段

### 4.3 命令分级：借鉴 opencode arity 字典，自研不依赖 tree-sitter

ECode M4 实施方案的"自研轻量解析器（200 行，无依赖）"思路正确，但具体实现应该参考 opencode 的 arity 字典而非从零设计。

**opencode arity 思路**（`packages/opencode/src/permission/arity.ts:24-161`）：
- 维护一份"命令前缀 → 期望 token 数"字典
- 把 `git checkout main` 归约成 `git checkout`（前 2 个 token）
- allow_always 生成规则 `git checkout *`，下次 `git checkout feature/x` 自动放行

**ECode 推荐实现**：
1. 第 1 步：split + 引号处理（150 行）
2. 第 2 步：维护一份常用命令 arity 字典（git/npm/pnpm/yarn/node/python/docker/kubectl 等 Top 30）
3. 第 3 步：未命中字典的命令按"第一个 token"做前缀（保守归约）
4. 第 4 步：识别 `&&`/`||`/`;`/`|` 复合命令，分别归约（CC `bashPermissions.ts:885-893` 的"前缀规则不匹配复合命令"教训）

**不要做**：
- tree-sitter AST（原生二进制依赖 + Windows 兼容 = §9.3 红线冲突）
- 完整 Bash grammar（shell-quote / bash-parser，过重）

### 4.4 路径越界 + 敏感文件黑名单：100 行成本堵 90% 问题

这是性价比最高的安全网，必须优先实现。

**敏感文件**（直接抄 CC `filesystem.ts:57-79`）：
```ts
const DANGEROUS_FILES = [
  '.gitconfig', '.gitmodules', '.bashrc', '.bash_profile',
  '.zshrc', '.zprofile', '.profile', '.ripgreprc',
  '.mcp.json', '.claude.json', '.env', '.env.*',
];
const DANGEROUS_DIRECTORIES = ['.git', '.vscode', '.idea', '.claude', '.ecode'];
// 编辑这些总是 ask（即使 acceptEdits 模式）
```

**路径越界**（仿 opencode `external-directory.ts:15-45`）：
```ts
function isExternalDirectory(path: string, workspaceRoots: string[]): boolean {
  const resolved = resolve(path);
  return !workspaceRoots.some(root => containsPath(resolved, root));
}
// 越界 → ask（permission key = 'external_directory'）
```

**不要做**（YAGNI）：
- Windows NTFS 备用数据流检测
- 8.3 短名检测
- macOS `/var → /private/var` symlink 归一化（先验证 ECode 是否有 macOS 用户，否则推后）

### 4.5 审批 UI：当前 3 选项已够用，升级方向是 always 二次确认 + reject 反馈框

ECode 当前 `src/ui/permission-dialog.tsx:9-19` 的 3 选项（allow/allow_always/deny）+ 425ms grace period 已经是三源中较完整的设计。

**保留**：
- 3 选项（不要扩到 CC 的 5 选项，复杂度过高）
- 425ms grace period（**三源调研中 ECode 独有**——CC/opencode/CCode 都未在源码定位到独立 grace period 常量；这是 ECode 已超过三源的设计点，**必须保留**）

**升级方向**（按优先级）：
1. **allow_always 二次确认**（仿 opencode `permission.shared.ts:127-135`）：选中后展开确认面板，显示将持久化的 pattern 列表。**防止误点**。
2. **reject 反馈框**（仿 opencode `footer.permission.tsx:104,287`）：用户拒绝时可输入反馈，反馈作为 user message 回喂给 LLM。**ECode 当前 deny 直接结束**，这是体验缺口。
3. **bash 命令高亮**（仿 CC `destructiveWarning`）：检测到 `rm -rf` / `git push --force` 等危险模式时高亮提示（仅警告不影响逻辑）。

**不要做**：
- CC 的可编辑前缀 `yes-prefix-edited`（实现复杂，价值边际）
- per-tool 组件 switch（YAGNI，统一 UI 够用）

### 4.6 权限持久化：内存 + 项目级手动配置

**内存层**：保留当前 `AllowList`，扩展为 `Rule[]` 数组（支持 pattern + action）。

**项目级**：读取 `.ecode/settings.json`（不读 `.claude/`，避免路径误导，对应 §9.3 红线）。
```jsonc
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(npm run *)", "Read(./src/**)"],
    "deny": ["Bash(rm -rf *)", "Edit(.env)"],
    "ask": ["Bash(git push *)"]
  }
}
```

**allow_always 持久化**：默认 **不写盘**（仿 opencode）。理由：
1. 防止用户误点"always"导致危险操作永久放行
2. 让配置文件保持"用户手写"的明确语义
3. 跨会话一致性需要用户主动 commit

如果一定要持久化，提供命令 `/permissions save`（仿 opencode 命令面板）让用户显式触发。

### 4.7 规则引擎：扁平 + last wins（仿 opencode）

**不要做** CC 的 5 层 source 分层（userSettings/projectSettings/localSettings/flagSettings/policySettings），ECode 单包 CLI 只需 2 层：
- `.ecode/settings.json`（项目级，git 跟踪）
- `~/.ecode/settings.json`（用户级，全局）

**合并策略**：last wins（仿 opencode `permission/index.ts:28-37`），用户级 + 项目级规则扁平合并，最后一条匹配胜出。比 CC 的"deny 全局优先"更直观。

**规则语法**：直接借鉴 CC 三种匹配类型，简化为 2 种：
- `Bash(npm run test)`（exact）
- `Bash(npm run *)`（wildcard，`*` 通配）

砍掉 CC 的 legacy `Bash(npm:*)` prefix 语法（YAGNI，新项目不必兼容历史）。

### 4.8 死循环检测：直接抄 opencode

ECode M4 实施方案 Phase 3 已规划"重复动作检测（滑动窗口 + 哈希）"。opencode 的实现是最简版本：

```ts
// 仿 opencode session/processor.ts:29,356-380
const DOOM_LOOP_THRESHOLD = 3;
// 同一工具 + 相同输入 hash 连续 3 次 → 触发 'doom_loop' 权限 ask
```

把它做成权限 key（仿 opencode `doom_loop`），让用户可以选"continue anyway"或"abort"，而不是硬中断。

### 4.9 YAGNI 削减清单（不要做）

| 项 | 出处 | 不做的理由 |
|---|---|---|
| tree-sitter AST 解析 | CC + opencode | 原生二进制依赖，Windows 兼容与 §9.3 红线冲突 |
| 5 种权限模式 | CC | plan/dontAsk/auto 是 Anthropic 内部需求，开源产品用不到 |
| classifier（LLM 自动分类） | CC auto 模式 | 调用成本高，开源产品不适合 |
| 5 层配置源 | CC | ECode 只需 user/project 2 层 |
| 企业策略 / MDM | CC + opencode | 开源产品无需 |
| Windows NTFS 备用数据流 / 8.3 短名检测 | CC | Windows 攻击面 YAGNI，先做 symlink 基本防护 |
| 可编辑前缀 `yes-prefix-edited` | CC | 实现复杂，价值边际 |
| per-tool 审批组件 switch | CC | UI 统一够用 |
| legacy `Bash(npm:*)` prefix 语法 | CC | 新项目不必兼容历史 |
| ZSH 危险命令检测（zmodload 等） | CC | ZSH 用户极少，YAGNI |
| `BareShell` PowerShell 危险规则 | CC | PowerShell 用户极少，YAGNI |

### 4.10 必做清单（按优先级）

| # | 项 | 借鉴 | 工作量估算 |
