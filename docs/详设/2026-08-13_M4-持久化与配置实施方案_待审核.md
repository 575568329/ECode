# ECode M4 持久化与配置实施方案

> 日期：2026-08-13 · 状态：**草案待审阅**
> M1（心脏）+ M2（TUI 最小 Static）+ M3（工具+确认）已完成。M4 是 **MVP 收官**：对话持久化 + 配置完整 + 多 provider + 配置向导。
> **数据分层**（已定，D12）：用户级 `~/.ecode/` 存**重要数据**（config + sessions，防用户清理项目目录时误删）；项目级 `<cwd>/.ecode/` 存 **ephemeral 数据**（logs 运行 trace，丢了不影响体验）。
> 本文基于调研（MVP 详设 §4 + 配置解析 + 现有代码 + 4 家开源 CLI 配置流程对比），拍板 D1-D12，排实施步骤。
> 标 ★ 的决策点已拍板（§3）；审阅时若不认可再议。

---

## 1. 目标 & 验收

**目标**：ECode 能跨会话保存/恢复对话、运行时切 provider/model、透传采样参数、配置无效时有引导入口（`/setup`）。

**验收标准**：
- 对话落盘 `~/.ecode/sessions/<sessionId>.jsonl`，`/history` 列出 + 恢复（重载 messages 重进 Loop）
- `/model` 运行时切 provider/model（anthropic ↔ openai 协议），无需重启
- 配置透传采样参数（temperature / topP / maxTokens / thinking）
- 配置无效（缺 apiKey/baseURL/model）时进 REPL + banner 提示 `/setup` 或编辑 config.json；`/setup` 弹向导（type/baseURL/apiKey/model），写文件权限 600
- OpenaiProvider 接入（DeepSeek 等经 OpenAI 协议端点）

---

## 2. 范围

**M4 做**：
- Config 完整版（providers map + current + per-provider 采样参数）
- 采样参数透传（interface / loop / anthropic.ts 三层）
- HistoryStore 真存储（JSONL + sessions 目录 + restore）
- OpenaiProvider（OpenAI 协议翻译）
- `/model` 命令（运行时切 + ModelPicker UI）
- `/history` 命令（列表 + 恢复 + HistoryPicker UI）
- 配置向导（`/setup` 命令触发，Wizard 组件，REPL-only；不强制弹，用户主动调用）

**M4 不做**（留后续）：
- 会话搜索/全文检索（`/history` 仅按时间列表）
- 多会话并行（同时开多个）
- 配置热重载（改 config 文件要重启，除非 /model 切）
- 向导的 model 预填模板库（用户手输 model 名，逗号分隔多个）
- `/config` 应用内面板（MVP 用 `$EDITOR` 打开 config.json，面板后置，借鉴 claude-code）
- 跨设备同步（本地文件，不接云）

## 3. 决策结论（已拍板 ★）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **D1** | HistoryStore 存储布局 | `~/.ecode/sessions/<sessionId>.jsonl`；**首行 meta**（`{meta, sessionId, createdAt, model, firstUser}`）+ 后续 Message 行 | meta 行让 `/history` 列表只读首行（不全量解析），N 会话 = N 次读首行 |
| **D2** | `/history` 恢复机制 | 选中 → 读 JSONL 还原 `Message[]` → 注入 messagesRef + 重建 committed；**起新 sessionId**（旧会话只读，续写进新文件） | "继续"语义是新运行；旧文件不可变更安全 |
| **D3** | `/model` 运行时切换架构 | **方案 A**：TuiAppDeps 持 `providerRegistry` + `config`（providers map + current）；每次 submit 按 `providers[current.name].type` 取实现（P0-1：type 派生，不存 current.type）+ 注入配置；`/model` 只改 current 状态 | 心脏不变（仍收单个 provider + providerReq，TuiApp 动态解析） |
| **D4** | 采样参数透传层级 | `LLMProviderRunRequest` + `loop.providerReq` + TuiApp 构造三层加 `temperature?/topP?/maxTokens?/thinking?`；从 `config.providers[name]` 读，随 current 切换 | 透传链路 M3 已建（providerReq），M4 只扩字段 |
| **D5** | Select 组件来源 | **自建**（参考 SlashSuggest 上下选中 + ConfirmPrompt 全屏覆盖范式） | 零新依赖，与项目风格一致（@inkjs/ui 未装且 M2 决定不用） |
| **D6** | 向导插哪 / 形态 | **不强制弹**（用户反馈）——`/setup` 命令触发 Wizard（REPL-only）；配置无效时 cli 进 REPL + banner 提示（D10）；argv 单次模式沿用"生成模板+报错" | 不自作主张弹 UI；非交互无法弹（呼应 M3 argv-confirm） |
| **D7** | OpenaiProvider 是否纳入 | **M4 必做** | `/model` 跨 provider 的核心价值（glm↔deepseek）依赖它；否则只能在 anthropic 兼容端间切，承诺缩水 |
| **D8** | OpenaiProvider 实现：openai SDK vs raw fetch | **openai SDK** | 与 `@anthropic-ai/sdk` 一致（client 缓存按 name）；SDK 处理 SSE 解析 + 重试；raw fetch 要自写 SSE 工作量大。锁主版本 `^`（审阅 P1-1 拍板） |
| **D9** ★ | thinking 参数暴露形态 | **语义枚举** `off/low/medium/high`（config 层），anthropic.ts 内部映射 `{type:'enabled', budget_tokens}` | GLM 实测 thinking 是对象 `{type:'enabled'\|'disabled', budget_tokens}`（非布尔，[智谱文档](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)）；裸 budget_tokens 数字反人类（aider 被批）；codex/claude-code 共识用枚举 |
| **D10** ★ | 「首次运行」判断 | **改为「配置有效性」判断**：不看 config 是否刚生成（created），只看能否拿到有效 provider（apiKey+baseURL+model 齐） | 「首次运行」是历史状态，错判场景多（删 config 重来/换机器/改坏）；「能否跑」是当前状态，本质且行为一致 |
| **D11** ★ | `/config` 命令 | **MVP 用 `$EDITOR` 打开 config.json**（跨平台 start/open/xdg-open），应用内面板后置 | claude-code 的 `/config` 面板可发现性好但重；codex 碎片化入口新手难发现；MVP 先简单打开文件 |
| **D12** ★ | 运行时数据分层 | **用户级** `~/.ecode/`：config.json + sessions/（重要，防误删）；**项目级** `<cwd>/.ecode/`：logs/（ephemeral） | 用户清理项目目录可能误删——对话历史是用户重要数据放用户级保护；日志删不删不影响体验放项目级。核心是数据安全，非 C 盘占用 |

## 4. Config 完整版（P0-1）

### 4.1 扩 M1Config → Config

`src/services/config.ts`：

```ts
export interface ProviderCfg {
  type: 'anthropic' | 'openai'
  baseURL: string
  apiKey: string
  models: string[]
  // M4 新增：采样参数（per-provider；temperature/topP 不顶层堆，藏 per-provider，D4）
  temperature?: number
  topP?: number
  maxTokens?: number
  thinking?: 'off' | 'low' | 'medium' | 'high'   // 思考强度枚举（D9），anthropic.ts 映射 budget_tokens
}

export interface Config {
  providers: Record<string, ProviderCfg>   // 多 provider map
  current: { name: string; model: string } // 当前激活（/model 改这个）
  maxIterations: number
  bashMaxOutputBytes: number
  logLevel: 'debug' | 'info' | 'warn' | 'error'
}
```

### 4.2 解析
- 读 `~/.ecode/config.json`（jsonc-parser 解析，允许注释；统一 `.json`，不 `.jsonc`）+ `.env`
- `providers`：直接读 config 的 `providers` 对象（磁盘格式本就是 name→cfg 的 map，非数组；P2-1）
- `current.name`：config 的 `default.provider` 或第一个 provider key
- `current.model`：`default.model ?? providers[current.name].models[0]`；models 为空 → 配置无效（D10，P2-2）
- **type 派生**：`type = providers[current.name].type`（**不存 `current.type`**，避免幽灵字段；P0-1）
- 采样参数：per-provider，缺省用 provider 默认（anthropic maxTokens=8192）

### 4.3 向后兼容
- **磁盘格式无迁移**：`ConfigFile`（config.ts:39）已解析 `providers: Record<string, ProviderCfg>` + `default`，M4 只改**返回类型**（M1Config 扁平 → Config 含 map）。
- **但消费方全要改**（P2-5）：M1Config → Config 的返回类型变更牵动所有消费方——cli `makeDeps`/`runOnce`、TuiApp `deps.cfg`、loop `providerReq` 构造。见 P0-1/P1-3。

### 4.4 config.json 完整模板（首次运行自动生成，D10：配置无效时也生成给编辑起点）

写全所有可配置项 + 注释说明取值（用户可直接编辑，或跑 `/setup` 向导填）：

## 6. HistoryStore 真存储（P0-3）

### 6.1 扩接口

`src/services/history.ts`：

```ts
export interface SessionMeta {
  sessionId: string
  createdAt: string
  model: string
  firstUser: string   // 首条 user 消息（/history 列表显示）
  messageCount: number
}

export interface HistoryStore {
  append(msg: Message): void                    // 增量（M1 已调，兑现）
  // M4 新增
  loadAll(): SessionMeta[]                       // 列所有会话 meta（读每个文件首行）
  restore(sessionId: string): Message[]          // 读某会话全部 messages
  /** 切换 sessionId（/history 恢复后起新 session 续写，D2：旧文件只读不破坏）。
   *  语义（P1-2）：切 id + 初始化新文件 + 首次 append 前懒写首行 meta。
   *  LogStore 不跟切（sessionId readonly）：恢复后续写日志仍记原启动 sessionId，
   *  可接受——LogStore 是启动期 trace，不跨会话关联。 */
  setSessionId(id: string): void
}
```

### 6.2 落盘（仿 LogStore 模板）
- 路径：`~/.ecode/sessions/<sessionId>.jsonl`（**用户级**，D12：对话历史是用户重要数据，放用户级防清理项目目录时误删；logs 才项目级）
- 首行：`{meta: true, sessionId, createdAt, model, firstUser, messageCount}`
- 后续：每条 `Message` 一行（**存原始 Message，不脱敏**——P0-6：对话要原样恢复喂 LLM，脱敏会让 key 变 `[REDACTED]` 失效；靠文件权限 600 + 用户级目录保护）
- append：增量写（loop finally 已调，M1 占位兑现）
- `loadAll`：扫 sessions 目录，每个文件读首行 meta
- `restore`：读整个 JSONL，过滤 meta 行，还原 Message[]

### 6.3 cli 注入

`src/cli/index.ts:67` `NoopHistoryStore` → 真实现。`makeDeps` 签名扩 `sessionId` 参数（P2-7），构造时传 `join(homedir(), '.ecode', 'sessions')` + sessionId。

> **redact 只给 LogStore**（P0-6）：AGENTS §2.7「Logger 与 HistoryStore 共用脱敏规则」需修订——LogStore 脱敏（trace），HistoryStore 存原文（对话）。实施时同步改 AGENTS §2.7（或开 ADR）。

## 7. OpenaiProvider（P1-1）

### 7.1 协议翻译（`src/providers/openai.ts` 新建）

| 规范模型 (Delta) | OpenAI 协议 | 翻译 |
|---|---|---|
| text | `choices[0].delta.content` | 直传 |
| tool_use_start | `delta.tool_calls[i].function.name` | 提取 |
| tool_use_delta | `delta.tool_calls[i].function.arguments` | 累积 partial_json |
| tool_use_end | `finish_reason==='tool_calls'` | 解析 JSON |
| usage | `usage`（**需请求带 `stream_options:{include_usage:true}`**，P1-6，否则 final chunk 无 usage） | 映射 |
| done | `finish_reason` | stop: 'end'/'length'/'tool_calls' |

### 7.2 system 处理
OpenAI 用 `messages[0]={role:'system'}`（不像 Anthropic 单独 system 参数）。`toOpenaiMsgs` 把 system 注入首条。

### 7.3 注册

`src/cli/index.ts:54` `providerReg.register(new OpenaiProvider())`。

### 7.4 thinking 枚举 → reasoning_effort（P0-5，D9 衔接）

抽象的职责：thinking 是协议无关的语义层，各 Provider 翻译成自己的机制。OpenaiProvider 翻译成 OpenAI 的 `reasoning_effort`：

```ts
// openai.ts stream 构造请求时
if (req.thinking && req.thinking !== 'off') {
  body.reasoning_effort = req.thinking   // 'low' | 'medium' | 'high'
}
// off / 缺省 → 不传（模型默认行为）
```

边界：
- **支持 `reasoning_effort` 的端点**（OpenAI o 系列）→ 生效 ✓
- **不支持的端点**（DeepSeek 等）→ openai SDK / 端点忽略未知参数，**不报错、不影响运行**（DeepSeek 推理是模型自带的 `reasoning_content`，本就无请求开关）
- 枚举对齐：ECode `off/low/medium/high` 直接对应 `reasoning_effort` 的 `low/medium/high`（off→不传；OpenAI 另有 `minimal` 档 ECode 不暴露，YAGNI）

每次 submit（抽 `buildProviderReq(config)` 共用，cli argv 与 TuiApp 共用，避免漂移 P1-3）：
```ts
function buildProviderReq(config: Config): LLMProviderRunRequest {
  const provCfg = config.providers[config.current.name]
  return {
    name: config.current.name,
    baseURL: provCfg.baseURL,
    apiKey: provCfg.apiKey,
    model: config.current.model,
```

### 8.1.1 config 运行时更新机制（P0-2：config 是 state 不是 props）

`config` 放 `TuiAppDeps` 当 props 会让 `/model`（改 current）、`/setup`（重配）变成 mutate props（React 反模式）。改为：
- **TuiApp 内部 `useState<Config>`** 持有 config（初始值从 cli 灌入的 deps 来）。
- `/model` 选中 → `setConfig(c => ({...c, current: {name, model}}))` → 触发重渲染 → 下次 submit 用新 current。
- `/setup` 填完 → 重新 `loadConfig()` → `setConfig(newCfg)` → 继续。
- banner 同理用 `useState<string|undefined>`，配置无效时 set banner，首次 submit 成功后 clear。

> 不用 `instance.rerender()`（ink 支持但绕），state 更自然且粒度细。

## 10. 配置向导与 `/config`（P2-1）

### 10.1 Wizard 组件（`src/tui/Wizard.tsx` 新建，`/setup` 触发）

**不强制弹**（D6 修订 + 用户反馈）：首次/配置无效不自动弹 UI，用户主动输入 `/setup` 才触发。交互流程（Ink）：

1. type（Select: anthropic / openai）—— 仅协议类型，不绑定特定供应商
2. baseURL（TextInput，**不预填**——ECode 通用 CLI 不偏向智谱/任何供应商；给 placeholder 示例「如 https://api.example.com」）
3. apiKey（TextInput）
4. model（TextInput，**多个逗号分隔**：「glm-5.2, glm-4-flash」→ `split(',').map(trim)` 转 `models: string[]`）
5. thinking（Select: off / low / medium / high，D9；默认 medium）
6. 写 `~/.ecode/config.json`（权限 600）+ 重新 loadConfig → 进 REPL

> TextInput/Select **复用自建组件**（`src/tui/TextInput.tsx` + 自建 Select，D5），零新依赖（P2-4）。

### 10.2 cli 插入：配置有效性判断（D10，取代「首次运行」）

**判断条件 = 「配置是否有效」**（不看 config 是否刚生成，只看能否拿到有效 provider：apiKey+baseURL+model 齐）。`src/cli/index.ts` main：

```ts
let cfg: Config
try {
  cfg = loadConfig()
} catch (e) {
  // argv 单次模式（非交互）：沿用报错退出，不弹 UI（D6）
  if (initialInput) throw e
  // REPL + 配置无效：进 REPL + banner 提示（不强制向导，用户自己决定 /setup）
  render(<TuiApp deps={{...}} banner={`配置不完整（${e.message}）。输入 /setup 配置，或编辑 ~/.ecode/config.json`} />)
  return
}
// 配置有效：正常进 REPL
render(<TuiApp deps={{ config: cfg, ... }} />)
```

要点：
- **去掉 `created` 分支和 `[CONFIG_INIT]`**（D10）：config.json 不存在 → 生成完整模板（§4.4）→ 统一走有效性校验（`[NO_API_KEY]`/`[NO_BASE_URL]`/`[NO_MODEL]`，或合并 `[CONFIG_INCOMPLETE]`）。不管首次/非首次，配置无效都走同一条路。
- **banner 不提「首次运行」**，就「配置不完整」——不预设用户是新手（删 config 重来、换机器、改坏都同路）。
- **`/setup` 由用户主动触发**：CommandRegistry 注册 `/setup` → onCommand 分发弹 Wizard → 填完写 config + reload → 继续跑。
- submit 时若仍无效 → 报错兜底引导 `/setup`。
- **配置无效态 deps 契约**（P0-4）：catch 分支传**空壳 Config**（`{providers:{}, current:{name:'',model:''}, ...}`），TuiApp `useState<Config>` 持有；submit 前加卫语句 `if (!config.providers[current.name])` → set banner，**不走 runLoop**（不杀 Loop）。`/setup`/`/config`/`/clear`/`/history` 不受影响（不依赖有效 provider）。
- **banner 全链路**（P0-3）：TuiApp 加 `banner: string | undefined` state；`App` 加 `banner?` prop + 渲染位（Conversation 顶部、醒目提示色）；首次 submit 成功后 clear。附录 A 补 `App.tsx` 改动。

### 10.3 `/config` 命令（D11）

`/config` → 用 `$EDITOR`（缺省系统默认）打开 `~/.ecode/config.json`：
- 跨平台：Windows `start`、macOS `open`、Linux `xdg-open`（按 `process.platform` 分流，不写死，呼应 §2.5）
- **Ink raw mode 抢占处理**（P1-4）：打开 editor 前必须 `process.stdin.setRawMode(false)` + `instance.unmount()`（暂停 Ink，否则 editor 抢不到 cooked mode 终端，显示错乱）；editor 退出后恢复 raw mode + re-mount。
- **跨平台等待退出**（P1-4）：Windows `start` 是 fire-and-forget 等不到退出（AGENTS §5.4）；改用 `child_process.spawn`/`spawnSync` + await 退出事件，保证 editor 关闭后再恢复 Ink。
- `/config` **走 action 交回 TuiApp 处理**（不能在 Command.run 直接 spawn，因为要 suspend Ink，P1-5）。
- MVP 先简单打开文件；应用内 Settings 面板（claude-code 风格）后置（§2 不做）

### 10.4 argv 单次模式（有 initialInput）

非交互，跳过向导/banner，沿用「生成模板 + 报错退出」（呼应 M3 argv-confirm 推迟）。

> **配置有效时 argv 模式也要改 providerReq**（P1-3）：`runOnce`（cli/index.ts:89-94）现在用扁平 `deps.cfg.providerName/baseURL/...`，Config 重构后这些字段没了。改用 `buildProviderReq(config)`（§8.1 抽出，cli 与 TuiApp 共用），否则编译失败。

### 10.5 调研借鉴（4 家开源 CLI 配置流程对比）

| 项目 | 借鉴点 |
|---|---|
| claude-code | 交互向导体验好、`/config` 面板可发现性强（面板后置，MVP 先 $EDITOR）、thinking 用枚举（effortLevel low/med/high） |
| codex | thinking 枚举丰富（none→ultra）、`toml_edit` 结构化写入保留注释（ECode 的 /model 改 current 时注意只动目标键） |
| opencode | JSONC 可注释（ECode 已用 ✓）、采样参数下沉 per-agent/per-model |
| aider | **反例**：裸 think-tokens 数字反人类、首次硬报错不引导 |

> 共识：可注释格式 > 严格 JSON；思考强度用枚举 > 裸数字；采样参数不顶层堆；首次不硬报错要给入口。ECode 的「不强制 + /setup 入口」= claude-code（向导好）与 aider（报错）的中间路线。
