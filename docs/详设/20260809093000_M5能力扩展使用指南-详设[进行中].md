## 数据目录约定

三支点的配置文件都落在 ECode 数据目录下（跨平台单一入口，见 CLAUDE.md §9.3）：

| 平台 | 数据目录 |
|------|---------|
| Windows | `%USERPROFILE%\.ecode\`（即 `C:\Users\<你>\.ecode\`） |
| macOS / Linux | `~/.ecode/` |

**两层作用域**（子代理 / Hooks 都支持）：
- **user 层**（`~/.ecode/`）：全局默认，所有项目共享。
- **project 层**（`<项目根>/.ecode/`）：项目专属，覆盖 user 层（同名 project 胜）。

> MCP 注册表只有 user 层（`~/.ecode/mcp/registry.json`），无 project 层（独立注册，防 config 连坐删）。

## 一、子代理（支点 9）

### 1.1 是什么

主代理可以派出一个**「侦察兵」分身**，给它一个子任务，分身**独立跑一轮**（独立上下文），跑完只把**最终结论**回喂主代理。中间读了哪些文件、调了哪些工具——主代理**完全看不到**（黑盒）。

**解决什么问题**：让主代理读/分析 20 个文件却不撑爆自己的上下文窗口——分身消化掉细节，只回一句话结论。

### 1.2 怎么定义子代理人设（agents）

把一个 `.md` 文件放进 agents 目录，文件 = 一个人设：

```
~/.ecode/agents/code-reviewer.md        ← user 层（全局）
<项目>/.ecode/agents/code-reviewer.md   ← project 层（项目专属，覆盖同名 user）
```

**文件格式**（frontmatter + 正文）：

```markdown
---
name: code-reviewer
description: 审查代码质量与风险，给出改进建议
tools: read_file, grep, glob
model: deepseek-chat
---

你是一个资深代码审查专家。

审查重点：
1. 逻辑正确性与边界条件
2. 安全漏洞（注入、越权、信息泄露）
3. 可读性与命名规范

给出具体 file:line 引用，按严重程度排序。
```

**frontmatter 字段**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | 人设名（主 LLM 据此点名派遣，须与文件名一致） |
| `description` | 建议 | 一句话：何时派这个分身（注入 system prompt 的 catalog） |
| `tools` | 可选 | 工具子集（**收紧权限**，逗号分隔或 `[a, b]`）。不写 = 全工具 |
| `model` | 可选 | 指定模型（M6 模型路由用，当前解析但不路由） |

**正文** = 人设指令（子代理的 system prompt）。

### 1.3 怎么用（用户视角）

**普通用户不需要手动操作**——主代理会自动判断何时派子代理。你只要正常提需求：

```
你：审查 src/auth/ 目录下的代码有没有安全问题
```

主代理会自行调 `Task` 工具派一个子代理去读那批文件，子代理回结论后主代理综合回复你。

**指定人设**：如果你想让主代理用某个特定人设，可以提示：

```
你：用 code-reviewer 人设审查 auth 模块
```

### 1.4 子代理的安全红线

| 规则 | 说明 |
|------|------|
| **权限⊆** | 子代理权限**只能更严不能更宽**——继承主代理的档位 + 全部权限规则（含已批准的 allow），人设 `tools` 可再收紧 |
| **ask 归主对话** | 子代理遇到需审批的危险操作，弹窗出现在**主对话**（不自己弹），由你决定 |
| **防递归** | 子代理默认**不能再派子代理**（嵌套深度上限 1），防递归爆炸 |
| **黑盒** | 子代理的中间过程不进主上下文，只回最终结论文本 |

## 二、MCP（支点 10）

### 2.1 是什么

MCP（Model Context Protocol）= AI 应用的「App Store 协议」。你注册一个 MCP server（第三方工具，如 GitHub、数据库、Slack），它的工具就**自动加入** ECode 的工具表，主代理能直接调用——不用你写代码集成。

**两种原语**：
- **Tools**：透明加入工具表，主代理自动判断何时调（**不用 `/` 命令**）。
- **Prompts**：注册成斜杠命令 `/mcp__server__prompt`，**手动触发**（位置参数模板）。

### 2.2 怎么安装 / 注册 MCP server

MCP 配置在**独立注册表**（不进 config.json，防误删）：

**文件位置**：`~/.ecode/mcp/registry.json`

**首次使用需手动创建该文件**（ECode 不自动跑 server，须显式登记）：

```json
[
  {
    "name": "github",
    "transport": "stdio",
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": {
      "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxxxxxxxxx"
    },
    "enabled": true
  },
  {
    "name": "filesystem",
    "transport": "stdio",
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed/dir"],
    "enabled": true
  }
]
```

**字段说明**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | server 名（工具命名空间前缀：`mcp__<name>__<tool>`） |
| `transport` | ✅ | 传输方式。一期只支持 `"stdio"`（本地）；`"http"` 为远期框架（解析不崩，但不连真 server） |
| `command` | ✅ | 启动命令（如 `"npx"`）。**须经 RCE 白名单校验**（见 2.5） |
| `args` | 可选 | 命令参数数组 |
| `env` | 可选 | 环境变量（放凭证，不进 config.json） |
| `enabled` | ✅ | 是否启用。`/mcp enable/disable` 会改这个 |

**安装后重启 ECode 生效**（启动时连一次，工具合并进工具表）。

### 2.3 怎么用（用户视角）

**Tools（自动调用）**：注册并启用后，主代理**自动**看到 server 的工具并按需调用。你正常提需求即可：

```
你：帮我看看 github 上 ecode 仓库最近的 issue
```

主代理会自动调 `mcp__github__list_issues` 之类的工具（MCP 工具走权限审批，default 模式会弹窗问你）。

**Prompts（手动斜杠命令）**：server 暴露的 prompt 会注册成斜杠命令，格式 `/mcp__<server>__<prompt>`：

```
你：/mcp__github__summarize_issue owner/repo 123
```

位置参数按 prompt 定义的 `arguments` 顺序传入，结果作为 user 消息注入对话。

### 2.4 `/mcp` 命令（管理）

在 REPL 里输入 `/mcp` 管理 MCP servers：

| 命令 | 作用 |
|------|------|
| `/mcp` | 列出所有 server（✓/✗ 启用状态 + transport + command） |
| `/mcp enable <name>` | 启用某 server（写回 registry，**重启生效**） |
| `/mcp disable <name>` | 禁用某 server（写回 registry，**重启生效**） |

> `/mcp` 是**只读管理**——只看状态 + 开关，不在 REPL 里执行 server 操作。

### 2.5 安全（RCE 白名单）

MCP server 通过 `child_process.spawn` 启动，若 registry.json 被篡改可导致任意命令执行（RCE）。ECode 在 spawn 前**强制校验命令头白名单**：

**允许的命令**（19 个安全运行时入口）：
`npx` `npm` `node` `python` `python3` `uvx` `pip` `pip3` `deno` `bun` `java` `javac` `dotnet` `go` `cargo` `ruby` `gem`

- 自动处理：路径提取 basename（`/usr/bin/node` → `node`）+ strip `.exe`（Windows `node.exe` → `node`）+ strip 版本号（`python3.12` → `python3`）。
- 不在白名单的命令（如 `rm`、`sh`、`curl`、`bash`）→ 拒绝 spawn + warn 日志。
- **只校验 command，不校验 args/env**：SDK 用 `spawn(command, args)`（数组传参不经 shell 解释），args 无注入风险。
- MCP 工具统一 `dangerous=true` → 走权限审批（default 模式弹窗，不可信代码最小权限）。

## 三、Hooks（支点 12）

### 3.1 是什么

Hooks = 在 agent 生命周期的关键事件上挂**自定义脚本**。比如：每次工具执行前跑个检查脚本、每次编辑文件后自动跑 lint。

### 3.2 怎么配置

Hooks 配置在 **settings.json**（与权限规则同文件）：

**文件位置**：`~/.ecode/settings.json`（user 层）/ `<项目>/.ecode/settings.json`（project 层）

```json
{
  "defaultMode": "default",
  "allow": ["Bash(npm run *)"],
  "deny": ["Bash(rm -rf *)"],
  "hooks": [
    {
      "event": "PreToolUse",
      "command": "echo '即将执行工具'",
      "matcher": "Bash"
    },
    {
      "event": "PostToolUse",
      "command": "npm run lint"
    }
  ]
}
```

**hooks 字段每项格式**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `event` | ✅ | 事件名（见 3.3）。非法事件静默跳过 |
| `command` | ✅ | shell 命令（跨平台走 Git Bash 分流） |
| `matcher` | 可选 | 工具名匹配（Pre/PostToolUse 用，如 `"Bash"` / `"Edit"`），默认 `"*"`（全工具） |

> `source`（system/user/project）由加载层自动标记，**不在配置里写**。

### 3.3 可用事件

| 事件 | 状态 | 说明 |
|------|------|------|
| `PreToolUse` | ✅ 已实现 | 工具执行**前**（可 deny 拦截 / 改输入） |
| `PostToolUse` | ✅ 已实现 | 工具执行**后**（可 deny 反馈 / 改输出） |
| `SessionStart` | ⏸ 延期 | 会话开始（事件流通知） |
| `SessionEnd` | ⏸ 延期 | 会话结束（事件流通知） |
| `UserPromptSubmit` | ⏸ 延期 | 用户提交输入时（事件流通知） |
| `Stop` | ⏸ 延期 | agent 停止时（可打回继续干） |

> **一期只做 Pre/Post**（需要「等决策」的 Promise-await）。其余 4 个走事件流的钩子延期（设计已留挂点，纯增量后补）。

### 3.4 Hook 命令的决策协议（PreToolUse）

hook 命令通过 **stdin 收到 JSON 上下文**，通过 **stdout / exit code 返回决策**（CC 协议，三通道）：

**输入**（stdin JSON）：
```json
{
  "session_id": "abc123",
  "tool_name": "Bash",
  "tool_input": { "command": "rm -rf /tmp/x" }
}
```

**输出三通道**（任一即可）：

| 通道 | 含义 |
|------|------|
| **exit code 2** | deny（stderr 内容当拒绝原因回喂 LLM） |
| **stdout JSON 顶层** `{"decision":"approve"\|"block","reason":"..."}` | block = deny |
| **stdout JSON 嵌套** `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow"\|"deny"\|"ask","permissionDecisionReason":"...","updatedInput":{...}}}}` | 结构化决策（可改输入） |

> ⚠️ 结构化决策**必须嵌套**在 `hookSpecificOutput` 内——顶层平铺 `permissionDecision` 会被静默丢弃（CC #48760）。

- 多个 hook 决策取**最严格**（deny > ask > allow）。
- hook **超时/失败默认放行**（allow）+ warn（不杀 agent）。

### 3.5 安全红线

| 规则 | 说明 |
|------|------|
| **hook 只能收紧不能放宽** | 权限 `deny` 是硬边界，hook 不能覆盖。执行顺序：`PreToolUse hook → check() 权限 → 执行 → PostToolUse hook` |
| **系统 hook 强制叠加** | 代码注册的系统 hook 恒前置、用户**无法删除/覆盖**（`getEffectiveHooks` = `[...SYSTEM_HOOKS, ...用户hooks]`）。一期 SYSTEM_HOOKS 留空框架（M4 path-guard 已做硬安全网） |
