# 第一部分：HookRunner（hooks 系统，v3 纳入——排在 Plugin 之前实施）

## H0. 定位与拍板（2026-08-15 用户确认）

- **mcp_tool 型 hook（hook 直调 MCP callTool）不做**：三家均无已实现先例（codex 已定义 schema 但标注 not supported yet），ECode 不领先冒进；接口预留执行体形态位。
- **hooks 是 Plugin 的前置**：plugin 清单自带 `hooks/hooks.json`（P6.4 预研），没有 HookRunner 则 plugin 的 hooks 组件无处接入——实施顺序 **hooks → plugin**。
- **分层铁律（用户需求原话）**：用户配置的 hooks 写 config.json；skill/mcp/plugin 扩展自带的 hooks 走**专用注册表**（独立存储，不因 config.json 调整而破坏）——**只有删除和注销才从专用 hooks 里移除**。

## H1. 双源模型（对齐调研结论：claude-code 双通道 + codex 发现式）

```
┌─ 分发时合并（getHooksConfig：快照用户源 + 遍历扩展注册表）────────┐
│                                                                    │
│  源 1（用户）：config.json → hooks 键（用户手写；/config 编辑）      │
│  源 2（扩展）：ExtensionHooksRegistry（内存注册表）                 │
│    - register(owner, hooks)：owner = 'skill:xxx'|'plugin:yyy@mkt'  │
│    - unregister(owner)：仅删除/注销时调（用户改 config 不触碰）      │
│    - 随扩展安装集重建（启动扫描 + 安装/卸载时增删，原子替换防半空）  │
│                                                                    │
│  两源同构 HookSpec[]：{ event, matcher?, handler, timeout? }       │
└────────────────────────────────────────────────────────────────────┘
```

- 用户源读取：config.json 的 `hooks` 键（与 mcpServers 同层，jsonc-parser 解析）；校验 AJV，非法项跳过 + warn（不炸启动）。
- 扩展注册表是唯一写入点：skill 的 frontmatter hooks 字段（会话级，session 结束 unregister）与 plugin 的 hooks.json（持久级，随 plugin 启用集）都经 `register(owner, …)` 进来；**永不写入 config.json**（claude-code 同款隔离）。
- 卸载语义：plugin uninstall/disable → `unregister('plugin:…')`（prune）；skill 会话结束 → unregister。

## H2. 事件集（MVP 最小 6 个，对齐 codex 11 个的子集）

| 事件 | 触发点 | 接入位置 |
|---|---|---|
| `SessionStart` | 启动/恢复会话（source: startup/resume） | TuiApp 挂载 + restoreSession |
| `UserPromptSubmit` | 用户提交输入（分流后、runLoop 前） | TuiApp submit |
| `PreToolUse` | 工具执行前（matcher=工具名，可 block / 改入参） | 装饰 Registry（H4） |
| `PostToolUse` | 工具执行后（matcher=工具名，可附加 context） | 装饰 Registry（H4） |
| `Stop` | 一轮 runLoop 结束 | TuiApp submit 的 finally |
| `SessionEnd` | 退出（含信号路径） | cli exit 链（stopNow 前） |

后置：PreCompact/PostCompact（接压缩编排器）、Notification、SubagentStart/Stop（等 sub-agent）。

## H3. 执行体（MVP 仅 command；其余形态接口预留）

```ts
interface HookSpec {
  event: HookEvent
  /** 工具事件的可选匹配（工具名，支持 | 列表与正则；MCP 工具 mcp__server__tool 同样可匹配） */
  matcher?: string
  handler:
    | { kind: 'command'; command: string; timeout_ms?: number; async?: boolean }
    // 后置形态（接口位预留，MVP 不实现——用户拍板 mcp_tool 不做；prompt/agent 等 sub-agent）
    | { kind: 'mcp_tool'; server: string; tool: string; input: object }
    | { kind: 'prompt'; prompt: string }
  timeout_ms?: number
}
```

- **command 执行**：`spawn`（win32 npx 类包 cmd /c，复用 M6 spawnSpec 规范）+ timeout 默认 60s + stderr 捕获进 LogStore + error 监听（AGENTS §5.4）。Windows `command_windows` 覆盖位。
- **stdin 协议**：hook 输入 JSON（event/session_id/tool_name/tool_input…）经 stdin 喂入；输出协议（stdout JSON）：`continue:false`=block（PreToolUse 阻断工具）、`updatedInput`（改入参）、`additionalContext`（PostToolUse 附加上下文注入下一轮）、`systemMessage`（systemMsgs 显示）；exit code 2 = block（无 JSON 的轻量阻塞）。
- **MCP 工具事件的既有能力**：matcher 可匹配 `mcp__server__tool`（Pre/PostToolUse 装饰层对全部注册工具生效，含 MCP）——即"编辑后自动 format"场景 MVP 已可用（formatter 是 shell 命令），无需 mcp_tool 形态。

## H4. 接入方式：装饰 Registry，心脏零改动

PreToolUse/PostToolUse 的触发点在工具执行前后——**不动 loop.ts**：makeDeps 构造 `hookedRegistry = new HookedToolRegistry(inner, hookRunner)`（代理 get/specs/validate；execute 包装 = PreToolUse（block→is_error tool_result / 改 input）→ inner.execute → PostToolUse（附加 context））。loop 拿到的是代理，零感知。SessionStart/UserPromptSubmit/Stop/SessionEnd 挂 TuiApp 与 cli（本就不属心脏）。

**实现约束：装饰器对 HookRunner 的引用必须经 getter（`() => hookRunnerRef.current`），禁止闭包捕获实例。** hooks 集合在运行期会变（H-P5 的 skill hooks 会话级注册/注销、plugin enable/disable、未来 `/reload`），而 H-P1 双源分发器的模型是原子重建（clear-then-register）；若装饰器捕获旧实例，重建后 Pre/PostToolUse 仍执行旧集合——无任何报错的静默失效（工具照常执行、日志无异常，只有行为与配置对不上）。经 getter 每次工具执行时现取，runner 换了下一跳自动生效。

## H5. 安全（对齐 .mcp.json 首用批准先例 + codex trusted_hash）

- 项目级 hooks 源（`.ecode/hooks.json`？MVP 不做项目级配置文件——用户 hooks 只在 config.json；扩展 hooks 的信任挂在 plugin 安装/项目 skill 首用批准上，复用既有批准机制）
- handler 命令黑名单复用 bash 工具的拦截正则（skill 注册表 hooks 尤其——第三方 SKILL.md 里带 hooks 等于第三方命令执行，必须过确认）
- hooks 执行失败**放行**（warn + LogStore）：hook 是子进程 command，超时/崩溃的失败面大，若失败即阻断，辅助观测就成了主链路的单点故障；block 是显式决策（exit 2 / `continue:false`），只与 hook 的输出语义耦合，不与执行成败耦合

## H6. 实施拆解（Plugin 之前）

| 步 | 内容 | 依赖 |
|---|---|---|
| **H-P1** | `services/hooks/types.ts` + 双源分发器（config 读取 AJV + ExtensionHooksRegistry 原子重建） | 无 |
| **H-P2** | command 执行器（spawn 规范/timeout/stdin-stdout 协议/exit code 2）+ 单测（含 win32 包裹） | H-P1 |
| **H-P3** | HookedToolRegistry（Pre/PostToolUse 装饰，block/改参/附加 context）+ loop 零改动验证 | H-P2 |
| **H-P4** | TuiApp/cli 事件接入（SessionStart/UserPromptSubmit/Stop/SessionEnd）+ systemMsgs 反馈 | H-P3 |
| **H-P5** | skill frontmatter hooks（会话级注册/注销）+ 集成测试 | H-P1,P4 |

# 第二部分：Plugin 系统

## P1. 核心架构：四件套（marketplace + cache + 清单 + 资源接入）

**Plugin 是"资源容器"，本身不执行**。它把若干 skill/command/mcp 配置打包，loader 扫描后分发到各 Registry。四件套（marketplace + 版本化 cache + 清单 + 资源接入）是成熟的第三方分发形态；清单格式贴 Claude 生态兼容格式，可直接消费其官方 marketplace（开局即有生态，此红利已在第三方宿主验证）。

```
┌─ Marketplace（索引仓库，git clone / zip 下载）──────────────────────┐
│  .ecode-plugin/marketplace.json  { name, plugins:[{name, source, ...}] }│
└────────────────────────────┬────────────────────────────────────────┘
                             │ /plugin 面板「安装」（P7）
                             ▼
┌─ 版本化 Cache（~/.ecode/plugins/cache/<marketplace>/<plugin>/<version>/）┐
│  .ecode-plugin/plugin.json   ← 清单（元数据 + 组件声明）                  │
│  skills/  commands/  .mcp.json  hooks/hooks.json                          │
└────────────────────────────┬────────────────────────────────────────┘
                             │ PluginLoader 扫描（启用者）
                             ▼
┌─ 资源接入（分发到既有 Registry，plugin 是基底层，优先级最低）────────────┐
│  skills/    → SkillRegistry（source:'plugin'）                            │
│  commands/  → CommandRegistry（命名空间 /plugin:cmd）                      │
│  .mcp.json  → McpManager（mcpServers 合并，按各自 lifecycle 接入）         │
│  hooks/     → HookRunner（后置，等 hooks 子系统）                          │
└───────────────────────────────────────────────────────────────────────────┘
```

**与 Skill/MCP 的关系**：skill/mcp/command 是"资源类型"，plugin 是"打包分发载体"。无 plugin 时这些资源也能独立配（`~/.ecode/skills/`、`.mcp.json`）；plugin 价值在于把一组相关资源 + 元数据 + 版本 + 来源 一起安装/启用/卸载。

## P2. 目标 & 验收

**目标**：用户 `/plugin` 打开面板——浏览已添加市场的插件、搜索、看详情、安装；管理已安装（启用/禁用/卸载）；添加新市场；启用后其 skill/command/mcp 自动接入，卸载干净。

**验收**：
- `/plugin` 面板「添加市场」页输入 `anthropics/claude-plugins-official` → clone 到 `marketplaces/`，浏览页出现其插件
- 浏览页选中 `context7` → 详情 → 安装 → 从 marketplace 拉取到版本化 cache + enable（行内 `安装中…` → systemMsgs 结果）
- 搜索即时过滤（name/description/marketplace）；部分市场拉取失败降级显示 + banner 提示
- 启用的 plugin 的 skills 进 SkillRegistry（source:'plugin'）、commands 进 CommandRegistry（`/plugin:cmd`）、mcp 进 McpManager 按各自 lifecycle 接入
- 已安装页：禁用 → 组件立即移除；卸载（确认框）→ 删 cache
- plugin 资源优先级最低：用户级/项目级同名覆盖它
- 清单非法 / 路径穿越 → 拒绝加载 + warn，不崩
- **心脏零改动**（loop.ts 无 plugin 字样）

**不做**（后置）：hooks（等 HookRunner）、agents（等 sub-agent）、userConfig 收集 UI、依赖解析 + 跨 marketplace 白名单、git-subdir 部分克隆、企业策略 allowlist/blocklist、autoUpdate + commit sha 比对、安全存储（keychain）、`npm:spec` 安装源（详见 §C）。

## P3. 数据结构

### P3.1 plugin 清单（`.ecode-plugin/plugin.json`，极简 + 目录约定）

清单只放元数据，组件靠**目录约定**自动发现（`skills/`、`commands/`、`.mcp.json`、`hooks/hooks.json` 存在即扫描）——降低作者门槛，零配置可发。同时支持显式声明字段（路径字符串/数组）覆盖约定。

```jsonc
// .ecode-plugin/plugin.json（极简约定型，如 context7）
{
  "name": "context7",                       // 必填，正则 ^[a-z0-9][a-z0-9._-]{0,127}$
  "version": "0.1.0",                       // 默认 0.0.0
  "description": "Up-to-date 文档查询 MCP",
  "author": { "name": "Upstash" },
  "license": "MIT"
  // 组件靠目录约定：skills/ commands/ .mcp.json 存在即扫
}
```

```jsonc
// 显式声明型（可选，覆盖约定）
{
  "name": "my-plugin", "version": "1.0.0",
  "skills": "skills",                       // 相对路径（./开头，必须在 plugin 根内）
  "commands": ["commands", "extra-cmds"],
  "mcpServers": { "foo": { "type":"stdio", "command":"node", "args":["${ECODE_PLUGIN_ROOT}/dist/srv.js"] } }
}
```

**字段集**：元数据（name/version/description/author/homepage/license/keywords/dependencies）+ 组件（skills/commands/mcpServers/hooks/agents，可声明或约定）+ 未知字段静默剥离（`.strip()`，容错——作者加自定义字段不致加载失败）。

**双目录探测**：`.ecode-plugin/` 优先，`.claude-plugin/` 回退（贴 Claude 生态兼容；兼容声明收窄为「skills + mcpServers 两类资源可直接消费」，plugin commands 因同步 Command 契约差异不保证）。

### P3.2 marketplace.json（市场索引）

```jsonc
// .ecode-plugin/marketplace.json
{
  "name": "ecode-plugins-official",
  "owner": { "name": "ECode" },
  "plugins": [
    { "name": "context7", "description": "...", "version": "0.1.0",
      "source": { "source": "github", "repo": "upstash/context7-mcp", "ref": "v0.1.0", "sha": "30287f5e..." } },
    { "name": "my-local", "source": "./plugins/my-local" }   // 市场内相对路径
  ]
}
```
**MVP source 两类**：`github`（owner/repo + ref + sha，git shallow clone）和 `url`（zip + sha256，下载解压）。市场内相对路径（`./xxx`）也支持。

### P3.3 目录布局

```
~/.ecode/plugins/
├── marketplaces/<marketplace-name>/        # clone/fetch 的市场仓库
│   └── .ecode-plugin/marketplace.json
├── cache/<marketplace>/<plugin>/<version>/ # 版本化缓存（主体）
│   ├── .ecode-plugin/plugin.json
│   ├── skills/  commands/  .mcp.json
├── known_marketplaces.json                 # 已添加市场注册表
└── (启用状态在 ~/.ecode/config.json → plugins)
```
版本字符串路径穿越净化（`[^a-zA-Z0-9\-_.]→-`）。

## P4. 流程

### P4.1 添加 marketplace
面板「添加市场」页输入 `<github owner/repo | url>` → git clone 到 `marketplaces/<name>/`（P6.1：异步 spawn + 60s 超时 + Esc 取清 + staging→rename 原子落位）→ 注册进 `known_marketplaces.json` → 刷新浏览页。

### P4.2 安装 plugin
详情页「安装」→ 读 marketplace.json 找 source → 按 source 拉取（P6.1：git spawn / zip fetch，staging 临时目录）→ 去 `.git/` → 校验清单（缺失则合成最小 manifest）+ sha → rename 到版本化 cache（中断不留脏目录）→ 默认 enable。

### P4.3 资源接入（PluginLoader，启动期 + install 后）
```
对每个 enabled plugin（按优先级）：
  skills/    → SkillRegistry.addSource(dir)（source:'plugin'，去重时优先级最低——M6 S5 已冻结的注入口）
  commands/  → CommandRegistry.register（命名 /plugin-name:cmd）
  .mcp.json  → 合并进 mcpServers 配置（plugin 级，基底层）→ McpManager 按各自 lifecycle 接入
  hooks/     → 后置（HookRunner 未就绪）
占位符替换：${ECODE_PLUGIN_ROOT}→cache 绝对路径、${ECODE_PROJECT_DIR}→cwd、${user_config.K}→配置值
```
工具卸载走 M6 M-P1 预留的 `ToolRegistry.unregister`（disable 时移除该 plugin 贡献的 mcp 工具）。

### P4.4 启用/禁用/卸载
- enable/disable：面板已安装页写 `config.json → plugins["plugin@marketplace"] = bool`；disable 走 P6.2 卸载链（McpManager.close 杀子进程 → ToolRegistry.unregister → SkillRegistry 移除 → cache 条目保留）
- uninstall：面板确认框（ConfirmPrompt 复用）→ 先 disable（同卸载链，含杀子进程）→ 删 cache + 移 install 记录

### P4.5 冲突：分层策略 + 可见性 + 消解（★ v3.1 重写，M7-D12）

**分层策略**——不同资源类型的同名冲突用不同机制消解，不建统一排序基建：

| 资源 | 同名处理 | 机制 |
|---|---|---|
| skill | 三级遮蔽：project > user > plugin（M6 S5 冻结的 addSource 注入口已含层级语义） | skill 名 = 斜杠命令名 + LLM 语义触发面，必须唯一生效 |
| command | 天然不撞：plugin 命令带命名空间 `/plugin-name:cmd`（P4.3） | 前缀消解 |
| mcp server | 天然不撞：plugin server 带 `plugin:<name>/<server>` 前缀（P6.2）；用户 config vs 项目 `.mcp.json` 同名沿用 M6 规则（项目覆盖用户） | 前缀消解 + 既有合并规则 |

**排序语义边界**：遮蔽排序只决定"同名资源谁生效"，**不控制 LLM 的调用集合**——LLM 能调用的 = 所有注册成功的工具（不同名的全在）。MCP 也不存在"指定哪个先执行"：调用选择是模型决策，用户控制面只有 server 级 enable/disable（`/mcp` 面板）。**skill 为何不用前缀消解**：SKILL.md 是生态兼容格式（name 裸名）；LLM 触发靠 description 语义匹配，前缀对模型无区分意义；`/format` 比 `/myplugin:format` 手敲自然——代价是重名遮蔽，故下方可见性与消解必须做足。

**可见性**（全部底部非阻断提示，无交互打断——2026-08-15 用户拍板）：

- 底部提示（systemMsgs 通道，与 mcpWarnings 同心智）：启动 load 后一行汇总（`2 个 skill 同名冲突（/skill 查看详情；可直接让我改名或删除其一）`）；plugin 安装/启用后预检一条（`skill format 将被用户级同名遮蔽`）。不弹确认、不阻止安装。
- SkillPanel（/skill）：被遮蔽项**照常列出**、灰显 + `被 <来源> 遮蔽` 标注（复用 M6 被命令遮蔽的 disabled 交互）——数据不消失，状态标清楚。
- `/plugin` 已安装详情：贡献资源清单逐项标生效状态（`skill format：⚠ 被用户级遮蔽`）——"装了 plugin 没效果"的排障在此闭环。
- LogStore warn 兜底；mcp 项目级覆盖用户级同名 server 在 mergeMcpServers 的 warnings 通道补一条（解法指向 M6 已有的 server 级 disable）。

**消解**（提示必须附带出路，不能只报告问题——2026-08-15 用户拍板：**ECode 本身就是 Agent，改名/删除是发一句话的事，不建 disable 基建**）：

- 底部提示文案直接引导自然语言消解——用户说"把用户级 format 改名"或"删掉它"，ECode 用既有工具执行（edit_file 改 SKILL.md frontmatter、文件操作重命名目录、卸载 plugin 走 /plugin 面板），零新基建。产品形态与"Agent 第一公民"一致：对话本身就是通用执行器。
- mcp 同名覆盖（项目级遮蔽用户级）同款引导 + 指向 M6 已有的 server 级 disable（`/mcp` 面板）——server 级 disable 是既有能力，保留。
- **不做** skill 级 disable（config `skills.disabled` / 面板快捷键）：传统 CLI 把消解动作产品化，是因为用户只能手动操作；ECode 用户开口即可。后置：若实践中发现自然语言消解不顺手（频繁冲突的团队项目）再议。

## P6. 子进程治理（★ v2 新增，M7-D8）

Plugin 相对 M6 新增的进程面有两处：**安装期**（git clone / zip 下载）与**运行期**（plugin 贡献的 mcpServers spawn 的 stdio server）。M6 的 McpManager 已覆盖单 server 生命周期（lazyConnect/close/stop/孤儿清理 best-effort），本节补 M7 特有的三块：

### P6.1 安装期子进程（git clone / zip 下载）

- **异步 spawn + 超时**：`git clone --depth 1 --branch <ref>` 用 `child_process.spawn`（禁 execSync 阻塞热路径——安装期间 TUI 必须可渲染进度与可取消）；单 clone 超时默认 60s（超时 kill + 报错可重试）。
- **git 探测**：启动安装前 `git --version` 探测（Windows Git Bash 环境通常有 git；ENOENT → 提示安装 git 或用 url/zip source）。统一 `resolveCommand` 思路：win32 下 git 通常是 git.exe 无需包 cmd，但 PATH 未命中时回退常见安装路径探测（`C:\Program Files\Gitin\git.exe`）。
- **取消**：PluginPanel 安装中允许 Esc 取消 → kill 在飞 git 进程 + 清理半成品临时目录（staging 目录 + rename 原子落位，中断不留脏 cache）。
- **zip source**：Node fetch 下载（无子进程）+ sha256 校验 + 解压到 staging；同样走 staging→rename。

### P6.2 运行期：plugin mcpServers 的子进程归属与卸载链

- **归属**：plugin 的 `.mcp.json` 合并进 mcpServers 后由 M6 McpManager 统一管（spawn/lazy/空闲卸载/死连接降级全部复用）；PluginLoader 不自建进程管理。server 命名空间：`plugin:<plugin-name>/<server>`（防 plugin 间与用户级同名冲突，M7-D4 优先级规则在合并时生效）。
- **disable 卸载链**（①②走 M6 已备接口 close/unregister；**③④需 M7 扩展两个接口**——SkillRegistry.removeSource(dir)（按 plugin 目录移除条目）与 McpManager.removeServer(name)（从配置表移除；M6 审阅确认其不存在，列入 P-P4 交付物，属 M7 扩展而非"已冻结"）：`/plugin disable x` → ① McpManager 对该 plugin 贡献的每个 server `close()`（杀 stdio 子进程）+ `removeServer` ② ToolRegistry.unregister 该 plugin 的全部 `mcp__<server>__*` 工具 ③ SkillRegistry `removeSource`（M7 扩展）移除 source:'plugin' 的条目 ④ metadata cache 条目保留（重新 enable 免重连拉清单）。
- **占位符展开时机**：plugin 的 `${ECODE_PLUGIN_ROOT}` 在**加载时**展开（路径定值），`${ENV_VAR}` 走 M6 同款展开 + 缺失 skip——绝不在清单里存展开后的绝对路径（版本升级 cache 路径变）。

### P6.3 崩溃孤儿兜底（M6 留的口子正式收口）

M6 的 stop() 是 exit handler 内 best-effort（不能 await）。M7 补齐三层：

1. **正常退出**：exit handler 同步发起 `client.close()`（SDK 对 stdio 发 SIGTERM/kills spawned process）；MCP SDK 的 StdioClientTransport 自带子进程跟踪（transport close → child.kill）。
2. **异常兜底**：主进程 uncaughtException / SIGINT 双击路径同样先调 stop() 再 exit（与 LogStore 同步 flush 的顺序：先 stop 杀子进程，再 flush 日志——子进程的 stderr 尾巴也能进日志）。
3. **Windows 进程树兜底**（孤儿复现时启用）：SDK 默认 child.kill 只杀直接子进程，npx→node 的孙进程可能残留——复现后上 `taskkill /PID <pid> /T /F`（进程树）+ spawn 时记 pid（McpManager 的 ServerState 加 `pid?`，connectFn 从 transport 提取）。MVP 不预做（M6 风险表既定：孤儿复现再上）。

### P6.4 hooks 子进程（v3：由第一部分 HookRunner 承接）

plugin 清单的 hooks/hooks.json → `ExtensionHooksRegistry.register('plugin:…', specs)`（H1 双源模型，独立于用户 config.json，卸载/禁用才 unregister——用户拍板的分层铁律）；command 执行复用 H3 执行器（含 P6.1 的 spawn 规范：异步/超时/stderr 捕获/error 监听）。**hooks 先于 plugin 实施（H-P1~P5 → P-P1~P6）**。

## P8. 安全（即使 MVP 也做全）

第三方 plugin 是**无沙箱的可信代码**（skills 是指令注入、mcpServers 可 spawn 任意命令），安全四件套：
1. **官方名预留**：`ecode` / `ecode-official` 等名字不允许第三方 marketplace 注册（防官方伪装）
2. **路径穿越净化**：source 路径/版本字符串/组件路径全部过 sanitize（`..` 拒绝）
3. **sha 校验**：github source 带 sha，clone 后校验 commit；url source 校验 sha256
4. **占位符白名单**：`${ECODE_PLUGIN_ROOT}` / `${ECODE_PROJECT_DIR}` / `${user_config.K}`（K 限白名单键，防读 apiKey）

启用时 systemMsgs 提示"第三方 plugin 含可执行内容，请确认来源"。

| git clone 慢/网络失败 | 中 | shallow clone；失败行内错误可重试 |
| **安装中取消留脏目录** | 中 | staging→rename 原子落位（P6.1）；取消即 kill + rm staging |
| **plugin disable 后子进程残留** | 高 | P6.2 卸载链 close（SDK 杀子进程）+ metadata cache 保留（重启用免重连）；孤儿复现上 taskkill /T（P6.3） |
| **多个 plugin 的 mcpServers 子进程数失控** | 中 | 全走 M6 lifecycle 模型（默认 lazy + 空闲 10min 卸载——不是每 plugin 常驻）；/mcp 面板可逐个断开 |

## B. 参考来源

- **opencode**（反例）：进程内 TS plugin SDK，无 marketplace/版本隔离/安全边界——只适合官方维护组件，不适合第三方发布
- **pi**（extensions，2026-08-15 一手源码调研，v3.1）：进程内代码插件的完整上限形态——factory 函数 + `pi.*` API（31 事件 / 工具 / 命令 / 快捷键 / CLI 旗标 / 渲染器 / Provider+OAuth 注册）；tool_call 钩子"执行时读 runner"（getter）与 runtime stale 机制；npm:spec / git / local 三源 PackageManager + 5 级资源 rank + 同名冲突诊断；项目信任门（项目级资源信任后才加载）。v3.1 吸收：H4 getter 约束、`npm:spec` 后置评估（§C）、冲突可见性思路；其"代码进进程"形态与 ECode 资源容器定位相反，明确不采纳（同 opencode 结论，但实现完成度更高，可作为未来若做代码型扩展的参照）
