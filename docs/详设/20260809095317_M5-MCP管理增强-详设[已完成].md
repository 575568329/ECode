## 一、背景与目标

### 1.1 现状缺口

ECode 当前 MCP 子系统（M5 阶段 3 已落地）只解决了「能连、能用」，管理体验存在 **5 个真盲区**：

| 缺口 | 现状（已核实源码） | 后果 |
|------|------|------|
| 🔴 连接无超时 | `loader.ts` 裸 `Promise.all`（claude/opencode 都是 30s `Promise.race`） | 配错的 server 让**整个 agent 启动卡死** |
| 🔴 `/mcp` 状态不可信 | `app.tsx` 显示 `e.enabled?'✓':'✗'`——是 enabled 开关，不是连接结果 | 用户配错的 server 也显示 ✓，无法确认「装对没」 |
| 🔴 失败原因丢失 | `client.ts:124` `failedConn()` 不带 reason，失败只 `console.warn` | REPL 里看不到为什么连不上 |
| 🔴 无重连/测试手段 | 改配置或 server 崩了只能重启 ECode | 排错成本高 |
| 🔴 进程残留 | SDK `close()`（`stdio.js:143-178`）只 `kill` 直接 child，**不杀孙子**（npx→node 孙子残留） | stdio server 断开后僵尸进程堆积 |

### 1.2 目标

引入 **集中式 `McpManager`**，一次性补齐：
- 30s 连接超时（修启动卡死）+ 超时兜底防 unhandledRejection
- `/mcp` 显示**真实连接状态 + lastError**（超越 claude——它也不显示）
- `/mcp reconnect`（重连 = 测试连通，不重启）
- `/mcp add/remove`（命令式 fast-path 登记，免手写 JSON）
- `/mcp info/tools`（详情 + server 作用 + env 脱敏）
- **Windows 进程树清理**（`taskkill /T` 杀孙子树，POSIX 诚实降级，见 §5）

### 1.3 范围决策（已与 owner 确认）

| 决策 | 结论 | 理由 |
|------|------|------|
| 子命令范围 | list/info/tools/reconnect/add/remove/enable/disable | 一体做比拆两次干净 |
| `add` 形态 | **仅 fast-path**（`--` + `--env`/`--desc`） | REPL 无多步问答子系统（无 clack/inquirer 等价物），交互式后置 |
| registry 作用域 | **user-only**（`~/.ecode/mcp/registry.json`） | YAGNI，project 层后置 |
| stdio 自动重连 | **不做**（靠手动 `/mcp reconnect`） | claude 也不做（进程死了复活不如让用户重连） |
| 进程清理平台 | **win32 `taskkill /T` 杀树（主战场真解决）；POSIX 降级依赖 SDK close（孙子残留=已知限制）** | SDK spawn 无 `detached:true`（`stdio.js:65-75` 已核实），POSIX 进程组方案不工作 |
| http transport | **现状已支持**（`client.ts:17-18,152-166`），**本次只增强 stdio 连接生命周期/UI** | http 生命周期（自动重连/OAuth/debug）后置 |

## 二、对标调研关键结论（claude-code-main + opencode）

| 维度 | claude | opencode | ECode 取舍 |
|------|--------|----------|-----------|

### 3.2 McpManager 契约（`src/mcp/manager.ts`）

```ts
/** 单个 server 的运行时状态（/mcp 显示 + agent 工具表的数据源）。 */
export interface McpServerState {
  name: string;
  status: 'connected' | 'failed' | 'disconnected' | 'disabled';
  transport: 'stdio' | 'http';
  tools: ToolDefinition[];
  prompts: McpPrompt[];
  lastError?: string;          // RCE拦截 / spawn失败 / 超时 / listTools失败 / http 缺 url
  entry: McpRegistryEntry;     // 原始配置（info/add/remove 用）
}

/** 连接池项：connection 可空（disabled/disconnected/failed 态）。 */
interface PoolItem {
  connection: McpConnection | null;
  state: McpServerState;
}

type McpChangeListener = () => void;

export class McpManager {
  private pool = new Map<string, PoolItem>();
  private listeners = new Set<McpChangeListener>();
  private locks = new Map<string, Promise<void>>();  // 每 server 互斥锁（并发 reconnect 串行化）

  constructor(opts?: { connectMcpServer?: typeof connectMcpServer; dataDir?: string });

  // 生命周期（全部走 withLock 串行化，避免并发 spawn 乱飞）
  connectAll(): Promise<void>;               // 读 registry → 全入 pool（enabled→connected/failed，disabled→disabled）
  connect(name: string): Promise<McpServerState>;
  reconnect(name: string): Promise<McpServerState>;  // disconnect→connect（= 测试连通）
  disconnect(name: string): Promise<void>;           // SDK close + win32 taskkill 兜底
  disconnectAll(): Promise<void>;                    // 退出清理（含进程树清理，幂等 disposed flag）

  reload(): Promise<void>;                   // add/remove/enable/disable 写回 registry 后重连

  // 查询（/mcp handler + getRunOpts 用）
  getStatus(name?: string): McpServerState | McpServerState[];
  getAllTools(): ToolDefinition[];           // 合并所有 connected server 工具，喂给 agent
  getAllPrompts(): Array<{ serverName: string; prompt: McpPrompt }>;

  onChange(listener: McpChangeListener): () => void;  // 仅终态 emit（中间态不 emit，防抖动）

  // 互斥锁（每 server 串行化 connect/reconnect/disconnect）
  private withLock<T>(name: string, fn: () => Promise<T>): Promise<T>;
}
```

**核心不变式**：`pool` 是所有状态查询的唯一来源——根除「`/mcp` handler 拿不到连接状态」的盲区。`disabled`/`disconnected`/`failed` 态 `connection=null`，pool 类型闭合。

## 四、连接增强（`client.ts`）

### 4.1 30s 连接超时 + unhandledRejection 兜底（修启动卡死）

```ts
const MCP_CONNECT_TIMEOUT_MS = 30_000;  // 对齐 claude/opencode

function raceWithTimeout<T>(p: Promise<T>, ms: number, onTimeout: () => Promise<void>): Promise<T> {
  // 🔴 关键：超时后主 promise 仍在后台跑（SDK 可能已建 socket/注册 listeners），
  // 后续若 reject 无人接 → unhandledRejection 崩进程。这里挂静默 catch 兜底。
  p.catch(() => {});
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error('MCP_TIMEOUT')), ms);
  });
  return Promise.race([p, timeout])
    .finally(() => timer && clearTimeout(timer))
    .catch(async (e) => {
      if (e instanceof Error && e.message === 'MCP_TIMEOUT') {
        await onTimeout();  // 超时→清理 transport
        throw e;
      }
      throw e;  // 非超时错误透传
    });
}
```

> 审阅指出：`Promise.race` 超时后主 promise（SDK connect/listTools）仍在后台跑，SDK 可能已建 socket/注册 listeners，后续 reject 无人接 → 崩进程。**实现要点**：connectMcpServer 内对整个 `connect→listTools→listPrompts` 链路套 raceWithTimeout；进入前 `p.catch(()=>{})` 静默兜底；超时 → `transport.close()` 清理 + 返回 `failedConn('连接超时(30s)')`。

### 4.2 lastError 链路（超越 claude）

`failedConn()` 改为 `failedConn(reason: string)`：

| 场景 | lastError |
|------|-----------|
| RCE 白名单拦截 | `命令 "<base>" 不在白名单` |
| 非 stdio/http · disabled · http 缺 url | `仅支持 enabled 的 stdio/http transport` / `http transport 缺少 url` |
| connect 抛错 | `连接失败: <err.message>` |
| 超时 | `连接超时(30s)` |
| listTools 抛错 | `获取工具失败: <err.message>` |

manager 把 reason 存进 `state.lastError` → `/mcp` list/info 显示。

### 4.3 McpConnection 加 `pid` 字段（供进程清理用）

```ts
export interface McpConnection {
  readonly serverName: string;
  status: McpConnectionStatus;
  readonly tools: ToolDefinition[];
  readonly prompts: McpPrompt[];
  readonly pid: number | null;   // 【新】stdio child pid（SDK transport.pid，connect 后填）；http=null
  getPrompt(name: string, args?: Record<string, string>): Promise<{ messages: unknown[] }>;
  disconnect(): Promise<void>;
}
```

connectMcpServer 成功后 `connection.pid = (transport as { pid?: number | null }).pid ?? null`（SDK `StdioClientTransport.pid` getter 已公开，`stdio.js:126`）。disconnect 时供 `killProcessTree` 用。

### 4.4 reconnect（manager 层编排，client.ts 不改连接逻辑）

```
reconnect(name):
  withLock(name):                         # 互斥锁，连点两次也串行
    # 1. 清理旧连接（与 disconnect 同构：拿pid→SDK close→taskkill兜底，确保孙子进程被杀，§5.3）
    pid = pool[name].connection?.pid
    await pool[name].connection?.disconnect()   # SDK 优雅杀 child
    await killProcessTree(pid)                  # win32 兜底杀孙子树；POSIX no-op
    # 2. 重建（带 30s 超时）
    const conn = await connectMcpServer(entry)
    pool[name] = { connection: conn, state }
    emitChange()                          # 仅终态 emit 一次（中间态不 emit，防 syncPrompts 抖动）
  返回 state（connected 或 failed 带 lastError）
```

**= 测试连通，不重启 ECode**。失败也返回 state（带 lastError），`/mcp` 显示。

### 4.5 并发与状态转换（修审阅硬伤）

互斥锁保证 connect/reconnect/disconnect 对**同一 server** 串行（连点 `/mcp reconnect github` 两次 → 第二次排队，不会 4 个 spawn 乱飞）。状态转换：

```
disabled ──enable──→ connecting ──→ connected | failed
disconnected ──connect──→ connecting ──→ connected | failed
connected ──reconnect──→ disconnecting ──→ connecting ──→ connected | failed
connected|failed ──disconnect──→ disconnected
* ──disable──→ disabled
```

`connecting`/`disconnecting` 是锁内瞬态，**不 emit、不入 state.status**（对外只暴露 4 终态）。

## 五、跨平台进程树清理（`process-cleanup.ts`，§9 红线）

### 5.1 核心结论（已核实 SDK 源码）

| 平台 | SDK close 能力 | 孙子进程（npx→node） | ECode 补充 |
|------|--------------|---------------------|-----------|
| **win32** | `stdio.js:159-174` kill 直接 child（SIGTERM→SIGKILL 等价） | ❌ 残留 | ✅ **`taskkill /T /F /PID` 杀整树**（基于 Windows 进程父子关系表，不依赖 POSIX 进程组） |
| **POSIX**（linux/darwin） | 同上 kill 直接 child | ❌ 残留 | ⚠️ **降级 no-op**（SDK spawn 无 `detached:true`，`stdio.js:65-75`，进程组方案失效；彻底解需自建 detached transport，列入不做） |

### 5.2 实现

```ts
import { spawn } from 'node:child_process';
import { join } from 'node:path';

/** 平台分类（抽纯函数，测试注入；process.platform 是 readonly 不可靠 mock）。 */
export type Platform = 'win32' | 'posix';
export function detectPlatform(platform: string = process.platform): Platform {
  return platform === 'win32' ? 'win32' : 'posix';
}

/**
 * 兜底杀进程树（在 SDK transport.close() 之后调用，清理 SDK 杀不到的孙子进程）。
 * - win32: taskkill /T /F /PID 基于 Windows 进程父子关系表，杀整树（含 npx→node 孙子）。
 *   用绝对路径（SystemRoot\System32\taskkill.exe），不依赖 PATH（精简环境 CI/容器不漏）。
 * - POSIX: no-op（SDK close 已优雅杀 child；孙子残留=已知限制，见 §5.1）。
 * 幂等：进程已退出时 taskkill 返回错误码，ignore。
 */
export async function killProcessTree(
  pid: number | null | undefined,
  platform: Platform = detectPlatform(),
): Promise<void> {
  if (!pid) return;
  if (platform !== 'win32') return;  // POSIX 降级 no-op
  const taskkill = join(process.env.SystemRoot ?? 'C:\\Windows', 'System32', 'taskkill.exe');
  await new Promise<void>((resolve) => {
    spawn(taskkill, ['/T', '/F', '/PID', String(pid)], { stdio: 'ignore', windowsHide: true })
      .on('close', () => resolve());  // 错误码 ignore（进程已退出）
  });
}
```

### 5.3 disconnect 流程

```
disconnect(name):
  withLock(name):
    pid = pool[name].connection?.pid          # close 前拿（close 后 SDK _process=undefined）
    await pool[name].connection?.disconnect()  # SDK 优雅杀 child（stdin.end→2s→SIGTERM→2s→SIGKILL）
    await killProcessTree(pid)                 # win32 兜底杀孙子树；POSIX no-op
    pool[name].connection = null
    pool[name].state.status = 'disconnected'
    emitChange()
```

> **不重复造轮子**：SDK `close()`（`stdio.js:143-178`）已实现优雅退出（stdin.end→2s→SIGTERM→2s→SIGKILL），ECode 复用之；taskkill /T 仅作 Windows 兜底杀 SDK 杀不到的孙子树。

### 5.4 WSL 考量（§9.3）

| 运行环境 | `process.platform` | 清理分支 |
|---------|-------------------|---------|
| Windows 原生（含 Git Bash） | `'win32'` | `taskkill /T /F /PID`（杀整树） |
| WSL 里跑 ECode | `'linux'` | POSIX 降级 no-op（依赖 SDK close） |
| macOS / Linux 原生 | `'darwin'`/`'linux'` | POSIX 降级 no-op（依赖 SDK close） |

**安全性论证（修正：白名单实为 17 个）**：`process.platform` 判断成立的前提是「ECode 和它 spawn 的 stdio server 同环境」——成立，因为 stdio server 由 SDK `spawn(command, args)`（`stdio.js:65`）直接启动，command 跑在 ECode 同环境。**`taskkill` 由 ECode 自己 spawn（进程清理用，绝对路径 `SystemRoot\System32\taskkill.exe`），不经 RCE 白名单校验**（白名单只校验用户配的 `entry.command`）；且 `/T /F /PID <数字>` 参数由 ECode 从 SDK `transport.pid`（number）填充，无注入面。

**RCE 白名单挡跨边界**：白名单**实际 17 个**（`client.ts:32-47` 已核实：npx/npm/node + python/python3/uvx/pip/pip3 + deno/bun + java/javac + dotnet + go/cargo + ruby/gem）。`wsl.exe`/`cmd.exe`/`powershell.exe` 均不在内 → 用户无法配 `command:"wsl"` 让 Windows ECode 跑 WSL server，避免「taskkill 杀不到 WSL 孙子」的最坑场景。

> ⚠️ **前置依赖声明**：本设计的 `taskkill` 走 `process.platform` 判断**不受** §9.3 影响；但 **registry 物理位置依赖 §9.3**。现状 `paths.ts:20` 是裸 `homedir()`（§9.3 对端自探测一期未做）→ **跨 Windows/WSL 共享 registry 会失效**（WSL 跑 ECode 找 Linux home，Windows 跑找 Windows home，两边不互通）= **已知限制**，待 §9.3 自探测落地后自动消解（调用方零改动，只改 `paths.ts` 一处）。

## 七、数据流与状态同步（`use-agent-stream.ts`）

### 7.1 3 个 ref 全迁（修审阅硬伤）

现状有 3 个 ref（`use-agent-stream.ts:119-121`）：`mcpToolsRef`、`mcpConnectionsRef`、`mcpCmdNamesRef` + 47 行 prompts 注册逻辑（132-166）。全部迁入 manager + `syncPrompts`：

```ts
const mcpManagerRef = useRef<McpManager | null>(null);
const oldCmdNamesRef = useRef<string[]>([]);  // 上一次注册的 prompt 命令名（注销用）

useEffect(() => {
  const manager = new McpManager();
  mcpManagerRef.current = manager;
  const syncPrompts = () => {
    // 注销旧 mcp prompt 斜杠命令
    for (const name of oldCmdNamesRef.current) unregisterCommand(name);
    oldCmdNamesRef.current = [];
    // 注册当前 manager.getAllPrompts()（connection 从 manager.getStatus 取）
    const cmdNames: string[] = [];
    for (const { serverName, prompt } of manager.getAllPrompts()) { ... registerCommand(cmd); cmdNames.push(cmd.name); }
    oldCmdNamesRef.current = cmdNames;
  };
  manager.onChange(syncPrompts);          // 仅终态触发（reconnect/add/remove 后）
  void manager.connectAll().then(syncPrompts);
  return () => { void manager.disconnectAll(); };  // 退出清理（含进程树，幂等）
}, []);
```

- **工具表实时**：`getRunOpts().tools = [...builtin, ...manager.getAllTools()]`——每轮 agent 读 manager（reconnect/add 后自动反映新工具）。去掉 `mcpToolsRef`/`mcpConnectionsRef`。
- **prompts 全量重注册**：`syncPrompts()` 先注销旧、再注册新（reconnect/add/remove 不频繁，全量简单不出错）。
- `mcpCmdNamesRef` 改名 `oldCmdNamesRef`（仅存上一次命令名供注销）。

### 7.2 数据流图

```
启动: useEffect → new McpManager → connectAll() → syncPrompts()（注册初始斜杠命令）
每轮 agent: getRunOpts().tools = [...builtin, ...manager.getAllTools()]   ← 实时读
/mcp <cmd>: handler 解析 → mcpApi.<cmd>(args) → manager 操作 → 返回文本 → addMessage
reconnect/add/remove/enable/disable: manager 终态变更 → emitChange → syncPrompts()（全量重注册）
退出: useEffect cleanup → manager.disconnectAll()（SDK close + win32 taskkill 进程树清理）
```

### 7.3 分层职责

| 层 | 职责 | 文件 |
|----|------|------|
| manager | 状态/连接池/互斥锁/生命周期（纯逻辑，可单测） | `mcp/manager.ts` |
| mcpApi | 操作 + 输出文本格式化（env 脱敏在此） | `ui/use-agent-stream.ts`（返回值） |
| handler | 解析子命令 + addMessage 显示 | `ui/app.tsx` |

## 八、错误处理

| 场景 | 处理 |
|------|------|
| 启动时某 server 连接失败 | 标 `failed` + lastError，**不阻塞其他 server 和 agent 启动**（已实现，保留） |
| **连接超时（主 promise 后台 reject）** | raceWithTimeout 前挂静默 catch（§4.1），超时 → transport.close() + failedConn('超时')；后台 reject 有 handler 不崩进程 |
| **连点 `/mcp reconnect`** | withLock 串行化，第二次排队，不并发 spawn |
| `/mcp reconnect` 失败 | 返回 failed state（带 lastError），`/mcp` 显示，不抛穿 |
| `/mcp add` 后 connect 失败 | server 已写入 registry（enabled），状态 failed + lastError；提示 `/mcp reconnect` 重试 |
| 运行中工具调用断线 | 沿用 adapter：返回 `isError` 给模型，不破回合（M5 已实现，保留） |
| 进程清理失败 | taskkill 错误码 ignore（进程已退出）；不影响 disconnect |
| registry 损坏/非数组 | `loadMcpRegistry` 已降级空数组（保留） |
| **React StrictMode 双 mount**（未来引入） | disconnectAll 幂等（`if (this.disposed) return`），当前未启 StrictMode 但防御 |

**原则**：MCP 失败永远不 crash agent，永远把原因回显给用户（lastError）。

## 九、安全

| 红线 | 说明 |
|------|------|
| RCE 白名单不变（**17 个**） | spawn 前仍过 `SAFE_COMMAND_HEADS`（`client.ts:32-47`），不改成员（§1.7 不重构周边；加 uv/pnpm/yarn 列后置评估） |
| `taskkill` 不进白名单 | ECode 自己 spawn（绝对路径 `SystemRoot\System32\taskkill.exe`），非用户 `entry.command`，不校验；参数 `/T /F /PID <数字>` 从 SDK `transport.pid`(number) 填充，无注入 |
| **env 脱敏**（`/mcp info`） | `maskValue(v)`：`v.length <= 8` → `****`；否则 `slice(0,4) + '...' + slice(-4)`（如 `ghp_xxxx...abcd`）。短值不半脱敏成明文 |
| description | 用户自填纯文本，无安全顾虑（不作为命令执行） |
| add 不自动跑包管理器 | add 只写 registry + spawn 用户声明的 command（过白名单），不替用户 `npm install`（避免 supply chain） |
| 跨边界 spawn | 17 个白名单挡 `wsl`/`cmd`/`powershell`，避免 Windows↔WSL 跨边界进程树清理难题（§5.4） |
