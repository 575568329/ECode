# 图片能力处理调研（拆视觉名门后 P1：非视觉模型读图毒化会话）

> 日期：2026-08-29 · 状态：**已完成**（调研 + 拍板 + 实施，文末实施记录）
> 背景：`78873ab` 拆除 read_file 视觉名门（图片恒直传、端点自证）后，三角色审阅提出 P1——图片块随 tool_result 固化进 history 后，无视觉模型（严格端点）会**每轮请求稳定 400**：错误只经 onWarn 到用户、不进模型上下文（旧名门在工具期报错反而模型可见可自纠）。本文调研四家 CLI 源码 + 两条一手实证，给处置拍板。

## 1. 四家源码实证（本地源码逐行核对，非网络只言片语）

| 项目 | 能力判定 | 拦截点 | 图片相关报错后的行为 |
|---|---|---|---|
| **aider** | 元数据表 `supports_vision`（litellm 价格库 + 自带 model-metadata.json），**查不到 = 不支持**（悲观缺省） | `/add` `/read` 入口直接拒绝（`commands.py:888-895`）；`/paste`/CLI 无检查→发送时**静默丢图**（`base_coder.py:817-827` 返回 None） | API 错误只打印 + 退避重发同请求，**从不回喂模型**（reflection 机制只覆盖编辑格式/lint/test 失败）；BadRequest 不重试直接终止。图片**不进历史**（每轮从 abs_fnames 现读现编码）——切到视觉模型自然重见 |
| **codex**（Rust） | 元数据 `input_modalities`（内置 models.json + 后端 /models 拉取 + ETag 缓存），**缺省乐观假定支持图片**（`openai_models.rs:174-180`） | TUI 两道预检（attach 拦截 + 提交还原）+ **每轮 prompt 归一化剥图**成占位文本（`normalize.rs:328-380`，存储不动） | 图片类 400 有专门分支 `InvalidImageRequest`（枚举注释就叫 **"Image poisoning"**，`error.rs:126-128`）：报 "Invalid image in your last message. Please remove it and try again." 结束本轮；**坏图留历史，下轮继续 400**（`turn.rs:266,314` 先记录后请求）——自己承认的缺口，无自动修复 |
| **opencode** | models.dev `modalities` 元数据（models.dev 插件目录 + 用户 config），**缺省 = 不支持**（悲观缺省） | **请求装配时**（AI SDK middleware transformParams）把不支持的图片 part 替换成 `ERROR: Cannot read xxx (this model does not support image input). Inform the user.`（`transform.ts:410-446`）——**图片不出客户端，由 LLM 口头转告用户** | 400 不重试（`retry.ts:85-98`）→ halt → 错误 toast，会话 idle；历史不清洗，换模型后每次请求按新模型能力重新判定（请求时占位化）。compaction/overflow replay 有彻底占位化（`compaction.ts:482-531`） |
| **Claude Code** | **完全没有能力门**——只查物理规格（5MB/2000px/100 张/格式转换），与本库拆门后同路线 | 无（端点自证） | **唯一有自动恢复**：媒体类 400 先扣留不显示 → reactive compact 把图片剥成 `[image]` 占位（`compact.ts:145-199`）→ 重试一次（`query.ts:1119-1175`）→ 成功继续，失败才浮现错误并提示 **"Run /compact to remove old images from context, or start a new session"**。另有 `sanitizeErrorToolResultContent`（`messages.ts:1884-1907`）专治 is_error tool_result 藏图，注释原话："没有它，恢复的会话**每轮都 400** 且 /fork 都救不回来"——CC 以文档化方式承认并修掉了与本库 P1 同型的问题 |

**路线归纳**：事前门·元数据派（aider 悲观 / codex 乐观 / opencode 请求时软替换）与事后恢复派（CC 独一份）。元数据派共同结构：**存储与发送解耦**——历史永存原图，每次请求按当前模型能力重新装配，换模型自动适配。

## 2. 两条一手实证（改变结论权重）

1. **models.dev 元数据是对的**：直接拉 `models.dev/api.json` 核实，`zhipuai/glm-5.3-flash` 标 `input:[text,image,video,pdf]`（glm-5.3 纯文本、glm-4.6v 有图——分类与官方一致）。当初误拦的锅是本库自己的本地正则名单（只认 `glm-4v` 等），不是社区元数据库滞后。但元数据路线仍有结构性弱点：**元数据错时静默失败**——opencode 会把能看的图替换成"不支持"文本转告用户，用户永远不知道模型其实能看（能力损失不可观测）；而"端点自证"响亮失败，可观测、可恢复。元数据对本库主场景（anthropic 兼容端点透传自定义模型名）映射亦不可靠。
2. **主力端点根本不 400**：真机采样 glm-5.3（models.dev 标纯文本）发 1×1 图到智谱 anthropic 兼容端点 → **200 正常作答**。"每轮毒化"在智谱端点炸不出来，只在严格端点（OpenAI 官方、部分严格兼容端点）成立。P1 实际爆炸半径远小于审阅时的假设。

## 3. 拍板（2026-08-29 用户审阅通过）

- **做**：非重试错误终止 + 会话含图 → warn 追加出路指引（codex "remove it and try again" + CC "/compact to remove old images" 同思路）：`/rewind` 撤回读图、`/compact` 压缩清图（本库压缩链已有图片占位化先例 `summarize.ts:243-248`）、`/model` 切换模型。宿主可观测层，不碰心脏协议面。
- **挂账不做（YAGNI）**：CC 同款"自动剥图重试"——主力端点不 400，触发条件基本不存在；要做需逐端点采样报错文案做匹配，脆弱且当前无收益。
- **否决**：元数据预检回潮（opencode/codex 路线）——与"端点自证"拍板冲突；元数据错时静默丢能力（比响亮报错更难排查）；兼容端点映射不可靠。
