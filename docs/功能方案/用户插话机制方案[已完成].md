# 用户插话机制方案（Running-State User Interjection）【已废弃 → 见消息队列与交互重做方案[已完成].md】

> 研究对象：Claude Code 源码 `D:\Study\claude-code-main`（CC）+ ECode 现状 `D:\Study\ECode`
> 研究动机：用户原话——"可以让用户插话，什么时候能够插进去话需要研究一下。"
> 研究方法：派 Explore 子代理通读 CC 的 PromptInput / REPL / query / keybindings / hooks 全链路，逐条拿到 `文件:行号` 证据；对照 ECode `agent.ts` + `ui/app.tsx` + `ui/input-bar.tsx` + `ui/use-agent-stream.ts` 现状。
> 结论先行：**CC 在运行中不仅不禁用输入，还把"插话"做成了核心交互**——键入 + Enter 默认进入 `priority='next'` 队列，在**当前工具执行完、下一次 LLM 请求前**注入同一轮对话；ESC 才是真"中断"。ECode 现状是运行中输入框完全禁用，只能 ESC/Ctrl+C 中断——是行业里最保守的一档。

## 0. 一句话结论

**ECode 应当照抄 CC 的"默认排队 + 中断点单点化"模型**：去掉 InputBar 的 `disabled={isRunning}`，submit 在运行中改为入队，在 agent loop 每轮 `for iteration` 顶部检查队列并取出一条作为"本轮附加 user message"参与下一轮 LLM 请求。最小可行版（MVP）只做"`next` 优先级 + 轮次边界 drain"，代码改动 ~80 行、4 个文件，不破坏现有 abort/permission/session 闭环。

### 1.1 核心命题：CC 运行中**不禁用**输入

CC 的"运行中"叫 `isLoading`（PromptInput prop）/ `queryGuard.isActive`（提交路径）。这两个状态**不参与**输入框 focus / 渲染门控：

| PromptInput 渲染门控不含 isLoading | `D:\Study\claude-code-main\src\screens\REPL.tsx:4894` | `!toolJSX?.shouldHidePromptInput && !focusedInputDialog && !isExiting && !disabled && !cursor`——没有 `isLoading` |
| Enter 处理不查 isLoading | `D:\Study\claude-code-main\src\components\PromptInput\PromptInput.tsx:984` | `onSubmit` 直接调 `onSubmitProp`，不判断运行态 |
| BaseTextInput 没有 disabled prop | `D:\Study\claude-code-main\src\components\BaseTextInput.tsx:38` | `focus = props.focus && props.showCursor && terminalFocus`，根本没有 `disabled`/`isLoading` 入参 |

### 1.2 提交分流：运行中 → 入队，空闲 → 立即执行

`handlePromptSubmit` 是提交的唯一收口（`D:\Study\claude-code-main\src\utils\handlePromptSubmit.ts`）。它在最顶部做这个判断（第 313–351 行）：

```ts

  if (mode !== 'prompt' && mode !== 'bash') { return }
  if (params.hasInterruptibleToolInProgress) {
    params.abortController?.abort('interrupt')   // 见 §1.5

```

**关键行为**：运行中按 Enter，文字被截下、入队、输入框清空——视觉上跟正常提交**完全一样**，但执行被推迟。这就是用户感知的"插话成功"。

队列本体是模块级单例（`D:\Study\claude-code-main\src\utils\messageQueueManager.ts:53` `const commandQueue: QueuedCommand[] = []`），React 侧通过 `useSyncExternalStore` 订阅（`D:\Study\claude-code-main\src\hooks\useCommandQueue.ts`）。

### 1.3 三种优先级（核心心智模型）

CC 的队列不是 FIFO 这么简单，每条命令带优先级。**优先级决定"什么时候被取出来执行"**。定义在 `D:\Study\claude-code-main\src\types\textInputTypes.ts:276-294`：

| 优先级 | 语义 | 取出时机 | 触发源 |
|--------|------|----------|--------|
| `now` | **中断并发**——abort 当前 in-flight tool（等价 Esc + send），消费者订阅队列变化即 abort | 立即 | chat UI 客户端（UDS）、bridge 消息 |
| `next` | **轮次中排干**——等当前工具调用结束，在 tool_result 与下一次 API 往返之间发送 | 当前工具结束 → 下一次 LLM 请求前 | **键盘输入默认值**（`messageQueueManager.ts:128-135` `enqueue` 默认 `'next'`） |
| `later` | **轮末排干**——等整个 turn 结束，作为新 query 处理 | 当前 turn 完全结束 | `SleepTool` 运行中、特定 task-notification |

**核心结论：键盘用户的默认行为是 `next`——不是等一整个 turn 结束，而是当前工具完事就插进去。** 这跟"轮次边界排队"是两个不同的粒度。

### 1.4 轮次中排干点（agent loop 内的注入位）

这是整个机制的"心脏手术"位——`D:\Study\claude-code-main\src\query.ts:1547-1590`，位于 agent loop 内，**当前轮所有工具执行完之后、下一次 LLM API 调用之前**：

```ts
// Get queued commands snapshot before processing attachments.
// These will be sent as attachments so Claude can respond to them in the current turn.
const sleepRan = toolUseBlocks.some(b => b.name === SLEEP_TOOL_NAME)
const queuedCommandsSnapshot = getCommandsByMaxPriority(sleepRan ? 'later' : 'next')
  .filter(cmd => {
    if (isSlashCommand(cmd)) return false           // 见 §1.6
    if (isMainThread) return cmd.agentId === undefined
    return cmd.mode === 'task-notification' && cmd.agentId === currentAgentId
  })
for await (const attachment of getAttachmentMessages(
  null, updatedToolUseContext, null, queuedCommandsSnapshot,
  [...messagesForQuery, ...assistantMessages, ...toolResults], querySource)) {
  yield attachment
  toolResults.push(attachment)
}
```

排干出来的命令变成**真实的 user message** 追加进 `toolResults`，参与下一次 API 请求——**模型在同一 turn 内就能看到这条用户插话并回应**。

> 对照 ECode：ECode 的 `agent.ts` for 循环（第 253 行起）每轮结构是 `maybeCompress → stream → consume → push assistant → (toolCalls.length===0 则 return) → for tc of toolCalls 执行 → 重复检测 → persistSession → 下一轮`。**CC `query.ts:1547` 对应的 ECode 位置就是 `agent.ts:415`（toolCalls for 循环的右大括号）之后、`agent.ts:417`（重复动作检测）之前**——这是 ECode 实现 mid-turn drain 的天然插入点。

### 2.4 为什么 ECode 现状这么保守

合理推测的原因（非贬义，是工程现实）：

1. **YAGNI**：M3.5 阶段优先把流式渲染、工具折叠、权限审批、session 续接跑通——"插话"是更后置的需求。
2. **避免竞态**：disabled 是最简单的"不会出错"——不存在"用户在工具执行中改了 messages 导致下一轮 API 配对断裂"等坑。
3. **对齐早期 ink 教学习惯**：很多 ink REPL 示例就是"运行时禁用输入"。
4. **没有"队列"概念**：use-agent-stream.ts 里 submit 是个 useCallback，每次创建新 AbortController——本就没设计"运行中入队"的入口。

但 CC 的实证表明：**这并非行业默认**。CC 选择了更难但更接近"对话感"的路径——而且他们在源码注释、tip 系统里明确把"插话"当卖点。ECode 想做到 CC 级体验，这一刀迟早要补。

## 3. 可行性分析：三种插入时机对比

按"什么时候能插进去话"分三档：

### 3.1 选项 A：轮次边界（turn-end drain）

**语义**：当前 turn 完全跑完（LLM 给出最终文本回答、`completed` 事件 yield）后，从队列取一条 user message 作为**新 turn** 启动。

| 维度 | 评估 |
|------|------|
| 实现难度 | ★☆☆☆☆（最易） |
| 代码改动 | ~40 行、3 文件（input-bar 解 disabled + use-agent-stream 加 queue + agent loop 外加 drain） |
| 体验 | 用户看到 agent 跑完一整轮（可能多个工具 + 数十秒）才被响应，**滞后感强**——但比"必须等 idle 才能打字"好 |
| 上下文一致性 | 完全无虞——新 turn 是干净的 messages 累加，不影响 abort/permission 配对 |
| 与 CC 对齐度 | 等价 CC 的 `'later'` 优先级（仅 turn 结束才 drain）。**不是 CC 键盘默认行为** |

**适用判断**：作为 MVP 验证"插话"产品价值，**不推荐作为最终形态**——CC 实测显示键盘默认是 `next`（mid-turn drain），用户体感差距大。

### 3.2 选项 B：工具执行间隙（mid-turn drain）★ 推荐

**语义**：agent loop 每轮里，**当前轮所有工具执行完之后、下一轮 LLM 请求之前**，检查队列，把队首 user message 作为"附加 user message"塞进 messages 数组一起发给 LLM。这是 CC `query.ts:1547-1590` 的精确镜像。

| 维度 | 评估 |
|------|------|
| 实现难度 | ★★★☆☆（中等） |
| 代码改动 | ~80 行、4 文件（详见 §4） |
| 体验 | 用户插话在当前工具跑完就生效（秒级响应），LLM 在同一 turn 内就能看到并调整决策——**CC 默认体验** |
| 上下文一致性 | 安全。注入点在 tool_result 已 push 完成（配对已闭环）、下一轮 stream 还没开始（messages 处于"协调一致"态）的窗口期——messages 数组只是多 append 一条 user message，不破坏 tool_use_id 配对 |
| 与 CC 对齐度 | **完全对齐** CC 键盘默认 `'next'` 优先级 |
| 风险 | 见 §5 |

**适用判断**：推荐作为 ECode 的**第一版"真插话"实现**。代价可控（agent.ts 改动局限于 for 循环末尾），收益是对齐 CC 的核心体验。

### 3.3 选项 C：流式 token 中断（interrupt mid-stream）

**语义**：用户按特定键（如 Enter 或专门键），**立即 abort 当前正在流式接收的 LLM 输出**，把当前已收到的部分 assistant 文本保留 + 把用户插话注入下一轮。

| 维度 | 评估 |
|------|------|
| 实现难度 | ★★★★★（最难） |
| 代码改动 | ~150+ 行、涉及 provider 协议层（stream 中断 + 部分输出保留语义）、agent loop 重大改造 |
| 体验 | "实时纠错"——LLM 还没说完就被打断。CC 的 `'now'` 优先级 + `interrupt-on-submit` 走这条路径，但**仅限可中断工具在跑时**，不是普通流式 token 思考中 |
| 上下文一致性 | 风险高。流式未完成时 abort，需把已收 textDelta 拼成"被截断的 assistant 消息"push 进 messages，再补一条 tool_result（如有部分 tool_use）维持配对——容易出配对断裂 / partial JSON 解析失败 |
| 与 CC 对齐度 | CC **不**对普通文本流做这个——只在 `hasInterruptibleToolInProgress`（如 SleepTool）时触发。CC 不允许用户在 LLM 思考流中插话 |
| 风险 | provider 协议差异大（DeepSeek/OpenAI/Anthropic stream abort 语义不同）、partial assistant 消息如何喂回 LLM 影响后续质量 |

**适用判断**：**不推荐 ECode 实现**。CC 自己都没把"流式 token 中断"做成键盘默认——他们键盘默认是"排队"。ECode 跟着 CC 走"不抢流式、只排工具间隙"是更稳的判断。若未来真要做，应限制为"interruptBehavior=cancel 的工具在跑时"才允许（对齐 CC 的 `interrupt-on-submit`）。

### 3.4 三档对比一览

| | 选项 A（轮次末） | 选项 B（工具间隙）★ | 选项 C（流式中断） |
|---|---|---|---|
| 响应延迟 | 高（数秒~数十秒） | 低（当前工具结束即生效） | 极低（立即） |
| 代码量 | ~40 行 | ~80 行 | ~150+ 行 |
| 风险 | 极低 | 低（配对闭环窗口期注入） | 高（partial assistant / provider 差异） |
| CC 对齐 | `'later'` | `'next'`（键盘默认） | `'now'` / interrupt-on-submit（仅可中断工具） |
| 推荐度 | MVP 验证用 | **首发推荐** | 不推荐（除非有 SleepTool 类需求） |

## 4. 推荐方案：选项 B（mid-turn drain）+ 渐进增强

### 4.1 总体设计

```
┌─────────────────────────────────────────────────────────────┐
│ useAgentStream hook                                          │
│   + queuedInputRef: Ref<string[] | null>                     │
│   + enqueueInput(text): 入队（运行中调用）                   │
│   + submit(text): isRunning ? enqueue : 启动新 turn          │
│   + abort(): 保持现状（abort 整轮）                          │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼ 传入 opts.queuedUserMessages（动态读取）
┌─────────────────────────────────────────────────────────────┐
│ agent.ts runAgentStream（for iteration 循环）                │
│   ... 每轮 stream + 工具执行 ...                              │
│   ↓ 在 toolCalls for 循环结束（line 415）后、重复检测前：    │
│   const queued = opts.drainQueued?.() ?? []                  │
│   for (const q of queued) {                                  │
│     messages.push({ role: 'user', content: q })              │
│     yield { type: 'user_message_injected', text: q }         │
│   }                                                          │
│   ... 重复检测 + persistSession + 下一轮 ...                 │
└─────────────────────────────────────────────────────────────┘
```

**核心设计点**：

1. **队列真相源放 UI 层**（`useAgentStream.queuedInputRef`），不放 agent core。agent core 只暴露一个回调 `drainQueued?: () => string[]`——单次调用取走当前队列快照。这样 agent.ts 保持"无状态 generator"特性，与 `messages` 真相源设计一致（参见 ECode `20260806090927_REPL多轮续接三家参考对照[已完成].md` 共识 #3）。

2. **drain 时机精确对齐 CC**：agent.ts for 循环里 toolCalls 执行完之后（`agent.ts:415` 的 `}` 之后）。这是 tool_result 已配对闭环、stream 未启的"安全窗口"。

3. **新增事件类型 `user_message_injected`**：让 UI 知道"插话被处理了"，渲染一条 kind:user 进 completedMessages。否则用户看不到"我的话进去了"。

4. **不引入优先级**：YAGNI。ECode 暂无 SleepTool / chat UI 客户端，所有键盘输入只有一种语义（mid-turn drain）。日后真有需求再加 `QueuedCommand` 类型与 priority 字段。

5. **slash 命令保持现状**：在 App 层 `handleCommand` 拦截，不进队列、不进 LLM。对齐 CC `query.ts:1573` 的语义（slash 命令不参与 mid-turn drain）。

## 5. 风险分析

### 5.1 中断 vs 排队对上下文一致性的影响

| 风险 | 触发条件 | 缓解 |
|------|----------|------|
| **tool_use_id 配对断裂** | drain 注入 user message 时，前一轮的 tool_result 还没 push 完 | **不会触发**——drain 点选在 `for tc of toolCalls` 完全结束之后（`agent.ts:415`），所有 tool_result 已 push、配对已闭环 |
| **重复工具签名误判** | drain 注入 user message 后，下一轮 LLM 又给出与上轮相同的工具调用 → `agent.ts:417` 重复检测把它判死 | **可能触发**。**缓解**：drain 注入后 `lastSignature = ''` 重置（语义：用户插话意味着新意图，重复检测基线清零） |
| **abort 与 drain 竞态** | 用户在 drain 窗口期按 ESC | abort 走 AbortController.signal，drain 检查 signal.aborted 时抛错 → 走 catch 兜底，不注入。需要在 drain 前加 `if (signal?.aborted) return` |
| **permission 与 drain 交错** | 工具权限弹窗期间用户提交插话 | ECode 现状 permission 时 InputBar 被 PermissionDialog 替换（`app.tsx:262-265`），用户根本看不到 InputBar——本就不会触发 enqueue。沿用现状即可 |
| **session 落盘遗漏** | drain 注入的 user message 没进 session.messages → `--continue` 失忆 | drain 时 `messages.push({role:'user',content:q})` 已写进 messages，persistSession 在每轮末（`agent.ts:444`）会落盘——天然不丢 |
| **多轮 drain 顺序** | 队列多条插话，顺序错乱 | queuedInputRef 用数组 FIFO，drain 时一次性返回全部，顺序保持 |

### 5.2 产品语义风险

| 风险 | 评估 |
|------|------|
| 用户以为"Enter = 立即生效" | UI 必须明确提示。CC 用 tip 系统（`tipRegistry.ts:255-264`）+ footer hint 双保险，ECode 至少要做 footer hint |
| 用户插话被 LLM "无视" | LLM 偶尔不回应用户插话（尤其中文模糊指令）。这是 LLM 行为问题，非机制问题；可考虑 drain 时把 user message 包成"用户补充说明："前缀（CC 没这么做，ECode 也可不动） |
| 队列无限增长 | 用户狂按 Enter 攒一堆。可加上限（CC 似乎没限，但 ECode 可限 10 条），超过则 InputBar 显示"队列已满" |

### 5.3 与现有 abort/permission/session 闭环的兼容性

| 现有机制 | 兼容性 |
|----------|--------|
| AbortController 中断 | 完全兼容。abort 在 drain 窗口期或 stream 期都能正常触发；abort 后队列可选择保留（用户可能想再发）或清空（CC `'chat:killAgents'` 清队列，普通 abort 保留）——ECode 建议**保留**，跟 CC 单击 ESC 一致 |
| permissionGate | 完全兼容。drain 在工具执行之后，permission 弹窗已在工具执行前完成 |
| sessionRef 续接 | 完全兼容。drain 写进 messages，sessionRef 跨轮复用同一会话，落盘 + 续接都不受影响 |
| maybeCompress 上下文压缩 | drain 注入 user message 后 messages 变长，可能在下一轮触发压缩——这是预期行为，不影响 |
| generation 计数器 | 完全兼容。drain 不启新 turn，不增 generation，沿用当前 generation 的 isRunning 状态 |

## 6. 验收标准

### 6.1 功能验收（用户视角）

| # | 场景 | 预期 |
|---|------|------|
| 1 | agent 运行中（streaming），用户键入"等等，先看 README.md" + Enter | 输入框清空、底部出现"(1 queued)"提示、agent **不**中断当前流 |
| 2 | 上一条插话被处理（当前轮工具跑完、下一轮请求前） | ChatView 出现一条 user 消息"等等，先看 README.md"，紧接着 LLM 在同一 turn 内回应（可能调 Read('README.md')） |
| 3 | 运行中连按 3 次 Enter（3 条插话） | 队列计数递增 `(1 queued) → (2 queued) → (3 queued)`，按 FIFO 顺序在连续 3 轮中逐条 drain |
| 4 | 运行中按 ESC | 当前流立即终止，已收到的部分文本作为 assistant 消息落地；**队列保留**（下次 submit 不丢） |
| 5 | 运行中按 Ctrl+C 单击 | 同 ESC |
| 6 | 运行中键入 `/help` + Enter | slash 命令立即在 App 层拦截执行（不进队列、不进 LLM），与现状一致 |
| 7 | 权限弹窗期间 InputBar | 沿用现状——被 PermissionDialog 替换，无法插话（合理） |
| 8 | 队列非空时 agent 自然完成 turn | turn 结束后队列应当被清空（因为 drain 在每轮都跑，turn 自然完成意味着所有插话都被处理过） |
| 9 | abort 后队列保留 | 中断后用户看到"(N queued)"提示，下次 submit 第一条队列项作为新 turn 任务 |

### 6.2 技术验收（代码层）

| # | 断言 |
|---|------|
| 1 | `runAgentStream` 在 for 循环每轮 `toolCalls` 执行完之后调用一次 `opts.drainQueued?.()` |
| 2 | drain 取出的每条 user message 被 push 进 `messages` 数组 + yield 一个 `user_message_injected` 事件 |
| 3 | drain 触发后 `lastSignature` 被重置为 `''`（避免误判重复） |
| 4 | drain 前检查 `signal?.aborted`，aborted 则不注入 |
| 5 | drain 注入的 user message 在 `persistSession(buildSession())` 落盘范围内（即位于每轮末 `agent.ts:444` 之前） |
| 6 | InputBar 的 `disabled` prop 移除或重命名（不再起吞键作用） |
| 7 | `useAgentStream` 暴露 `enqueue(text: string)` 与 `queuedCount: number` |
| 8 | 单测覆盖：运行中 submit → 入队（不创建新 AbortController）、idle 时 submit → 启动新 turn（不污染队列） |
| 9 | 单测覆盖：drain 在 abort 发生时不注入（竞态保护） |
| 10 | 单测覆盖：drain 注入后 `lastSignature` 清零、下一轮重复检测基线重置 |
