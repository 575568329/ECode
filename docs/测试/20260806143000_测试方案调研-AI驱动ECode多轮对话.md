# 测试方案调研：让 AI 驱动 ECode 多轮对话做功能验证

> **目标**：找到一种方法，让 AI（Claude Code / 自动化脚本）能够「打开 ECode 的多轮对话」，对其当前功能（重点是 Phase 2 的工具 Inline/Block 双模式、input 透传，以及 REPL 多轮交互）做端到端验证。
>
> **本文是调研文档**，先理清方案空间、能力边界、已知坑，再定落地路线。**先写文档，后照文档执行**——不在调研阶段盲目试错。

---

## 一、核心矛盾（为什么不能直接跑）

ECode REPL 的输入层是 ink 的 `useInput`（`src/ui/input-bar.tsx:49`），它依赖 **raw-mode TTY**（`process.stdin.setRawMode(true)`）。这带来两个硬约束：

| 尝试 | 结果 | 原因 |
|------|------|------|
| 管道喂入 `echo "任务" \| ecode --repl` | ❌ 输入进不去 | `useInput` 在非 TTY 下收不到按键事件 |
| one-shot `ecode "任务"` | ❌ 测不到 Phase 2 | one-shot 走 `runAgent` 直接 `console.log`，**完全不经过 `tool-panel.tsx`**（Inline/Block 渲染只在 REPL/`<ChatView>` 里） |
| 普通 `Bash` 工具交互 | ❌ 无法保持会话 | Bash 工具是一次性命令执行，不能挂在交互式进程上事后注入输入 |

**结论**：要测 UI 多轮，要么伪造 PTY（真终端），要么在 ink 测试层模拟 stdin（脱离真终端）。下面分四层评估。

## 二、社区调研结论

### 2.1 ink 官方测试方案：`ink-testing-library`

[in官方仓库](https://github.com/vadimdemedes/ink) 与 [ink-testing-library](https://github.com/vadimdemedes/ink-testing-library) 的关键能力：

- `render(<App/>)` 返回 `{ stdin, stdout, lastFrame, frames, rerender, unmount }`
- **支持模拟键盘输入**：`stdin.write('hello')` 可驱动 `useInput` 组件（官方 README 即以此为例）
- `frames` 数组捕获所有渲染帧；`lastFrame()` 取末帧
- **局限**：
  - `backgroundColor` **不渲染**（ink-testing-library 的假 stdout 不画背景色）——已在 Phase 1 踩坑记录
  - 边框字符 `│`、ANSI 颜色码 **会**渲染
  - 不模拟真实终端的 raw mode 时序，但 useInput 的 keypress 分发是有的

> **关键意义**：`stdin.write()` 让我们可能**完全脱离真终端**测多轮交互——而且中文输入走 ink 内部 keypress 解析，比 tmux 更可靠（tmux 中间多一层 send-keys 编码会拆碎多字节字符，见 2.3）。

### 2.2 tmux 驱动方案（真终端 E2E）

经典模式（[drmaciver: Using tmux to test your console applications](https://drmaciver.com/2015/05/using-tmux-to-test-your-console-applications/)、[mattorb: 9 agent wins with tmux and cmux](https://mattorb.com/9-agent-wins-with-tmux-and-cmux/)）：

```
tmux new-session -d -s app "ecode --repl"   # 后台跑（伪 PTY，useInput raw mode 可工作）
tmux send-keys -t app "输入" Enter          # 注入按键
tmux capture-pane -t app -p -e              # 抓屏（-e 保留 ANSI，-p 输出到 stdout）
```

- **已在本机验证可行**（tmux 已装）：欢迎屏、RGB truecolor、边框 `│`、spinner、状态栏、输入栏全部能 `capture-pane -e` 抓到
- `capture-pane` 旗标：`-p` 输出 stdout、`-e` 保留 ANSI、`-S <n>`/-`E <n>` 控制起始/结束行（抓增量用）

### 2.3 tmux 中文输入坑（实测踩到）

本调研首轮验证中，`tmux send-keys "读 package.json..." Enter` 后 agent **纹丝不动**（状态栏 35s 仍 `↑0 ↓0 tok`）。根因查到（[tmux issue #1832](https://github.com/tmux/tmux/issues/1832)、[send-keys stripping spaces #1425](https://github.com/tmux/tmux/issues/1425)）：

- tmux `send-keys` 默认对按键做 UTF-8 编码，可能**拆碎多字节 CJK 字符**
- ink `useInput` 在 raw mode 逐字节/逐序列读 stdin，拆碎后还原不出完整字符 → InputBar 的 `setText(t => t + input)` 累积出错 → Enter 提交的不是预期文本

**规避**：用字面模式发送
```bash
tmux send-keys -t app -l "中文任务"        # -l 字面模式（仍按 UTF-8，但更可控）
tmux send-keys -t app -ll "中文任务"       # -ll 双字面，避免 UTF-8 重编码（tmux ≥ 3.x）
tmux send-keys -t app Enter                # 回车单独发
```
> 待 PoC 验证 `-l`/`-ll` 在本机 tmux 版本下能否让 ink 正确接收中文。

## 四、测试方法分层与能力矩阵

| 层级 | 工具 | 跑在哪 | 真实 LLM | 真实 TTY 渲染 | 多轮交互 | 确定性 | 成本 | CI 可跑 |
|------|------|--------|---------|-------------|---------|--------|------|--------|
| **L0** 纯函数单测 | Vitest | 无 React/无 IO | mock | ❌ | ❌ | ✅ 高 | 零 | ✅ |
| **L1** 组件静态测试 | ink-testing-library `render` | 假 stdout | mock/无 | 部分（无背景色，有边框/ANSI） | ❌（单帧断言） | ✅ 高 | 零 | ✅ |
| **L2** 组件交互测试 | ink-testing-library `render<App>` + `stdin.write` | 假 stdout | **需 mock** | 同 L1 | ✅ | ✅ 高 | 零 | ✅ |
| **L3** tmux E2E | tmux send-keys/capture-pane | 真 PTY | **真实** | ✅（含背景色） | ✅ | ❌ 低（LLM 不确定） | 花 token | ❌（慢/花钱） |

**当前覆盖**：L0 已大量（agent/tools/context/session/permission 纯逻辑）、L1 已有（tool-panel/chat-view 等组件静态断言）。**L2、L3 是空白**。

## 六、测不了 / 难测的功能 + 替代方案

| 难点 | 为什么难 | 替代方案 |
|------|---------|---------|
| **真实背景色**（toolBg/userBg） | ink-testing-library 假 stdout 不画 backgroundColor | L3 tmux `capture-pane -e` 看真色；或代码层断言 `backgroundColor` prop 已传（不强求视觉） |
| **LLM 输出不确定性** | 真实模型每次回复不同，无法精确断言 | L2 用 mock provider 按序返回固定流；L3 只断言结构（出现 `│`/工具名）不断言具体文字 |
| **多轮记忆真实性** | 要验证「第 2 轮能看到第 1 轮历史」 | L2：mock provider 第 2 轮检查收到的 messages 含第 1 轮内容（已有 agent-stream 测试证 resumed） |
| **流式逐字时序** | 帧间隔依赖真实流速度 | L2：mock provider 逐 chunk yield，断言 frames 数组长度递增 |
| **tmux 中文输入** | send-keys 拆碎多字节 | `-l`/`-ll` 字面模式（待 PoC）；或 L2 用 stdin.write 绕开 tmux |
| **Ctrl+C 双击退出** | `process.exit` 会杀测试进程 | L2：mock process.exit 或只断言「第二次 ctrl+c 触发」不真退；用 spy |

## 七、推荐落地方案

### 主路线：L2（ink-testing-library 驱动 App）

**为什么**：确定性、零 LLM 成本、CI 可跑、中文可靠、能覆盖 G1-G4 + F3 + A6 所有交互缺口。这是「AI 驱动多轮对话」的正确抽象——**不是真开终端，而是在测试层模拟终端**。

**前置架构改动（3 处小透传，纯加可选参数，不破坏生产）**：

当前注入链没有 provider 口（生产靠 `createProvider`）：
```
index.ts → <App> → useAgentStream → runAgentStream(text, opts)  // opts 无 provider → 真实 LLM
```

需改成：
1. **`use-agent-stream.ts`**：`UseAgentStreamOptions` 加 `provider?: ModelProvider`；`submit` 的 `streamOpts` 透传 `provider: opts.provider`
2. **`app.tsx`**：`AppProps` 加 `provider?: ModelProvider`；`useAgentStream({ model, system, provider })`
3. **`runAgentStream`**：**无需改**（`RunAgentStreamOptions.provider` 已支持 DI，agent-stream.test.ts 早就在用）

生产路径（index.ts）不传 provider，行为不变。

**L2 测试形态**（新建 `tests/ui/repl-flow.test.tsx`）：
```ts
// mock provider：按调用次数返回不同流（多轮）
let call = 0;
const provider = makeMockProvider({
  1: [text_delta('让我读'), tool_call('read_file', {path:'package.json'}), tool_result('...'), stop('done')],
  2: [text_delta('刚才那个文件...'), stop('done')],  // 第 2 轮验证能看到第 1 轮历史
});
const { stdin, lastFrame, frames } = render(<App provider={provider} cwd="..." />);

// 模拟用户输入 + 回车（ink-testing-library stdin.write 驱动 useInput）
stdin.write('读 package.json');  // 注：待验证是否需逐字符 write 触发 useInput
stdin.write('\r');               // Enter

await waitFor(() => expect(lastFrame()).toContain('package.json'));
// 第 2 轮
stdin.write('它叫什么名字');
stdin.write('\r');
await waitFor(() => expect(lastFrame()).toContain('ecode'));
```

**待 PoC 验证的假设**（写进文档，不盲试）：
1. ⚠️ `stdin.write('整串')` 是否触发 InputBar 的逐字符 `setText` 累积？还是需 `for (ch of str) stdin.write(ch)` 逐字符？——ink 把 stdin data 按 keypress 解析，整串 write 通常被拆成多个 keypress 事件，但需验证中文多字节。
2. ⚠️ `\r` 是否被 ink 识别为 `key.return`？还是需 `\n`？
3. ⚠️ InputBar 的 `onSubmit` → App `handleSubmit` → `api.submit` 链路在测试里是否同步落地用户消息？

> 这 3 点用 5 分钟的 PoC（render `<InputBar>` + stdin.write + 看 lastFrame）就能定，定了再写正式 L2 套件。

### 辅助路线：L3（tmux 冒烟，一次性）

**为什么**：验证「真终端能跑 + 真实 LLM 连通 + 背景色真渲染」——这些 L2 测不了。但**只做冒烟，不做回归**（LLM 不确定 + 花钱 + 慢）。

**形态**：一个 shell 脚本 `tests/e2e/smoke-tmux.sh`：
```bash
tmux new-session -d -s ecode -x 120 -y 40 "npm run dev"
sleep 5
tmux send-keys -t ecode -l "读 package.json 告诉我项目名"   # -l 解决中文
tmux send-keys -t ecode Enter
# 轮询 capture-pane 直到出现工具渲染或超时
for i in $(seq 1 30); do
  out=$(tmux capture-pane -t ecode -p)
  echo "$out" | grep -q 'read_file' && break
  sleep 2
done
tmux capture-pane -t ecode -p | sed 's/\x1b\[[0-9;]*m//g'   # strip ANSI 人工核对
```
- 人工/半自动核对输出，不进 CI 严格断言
- 若要 CI，只断言「非空 + 含工具名」这类弱断言

## 八、落地步骤（照此执行）

1. **PoC（10 分钟）**：先验证 L2 的 3 个待定假设——`render(<InputBar>)` + `stdin.write`，确认输入/回车链路通。不通则回退方案。
2. **架构改动**：给 `useAgentStream` + `App` 加 `provider?` 透传（3 处小改 + 1 个单测）。
3. **L2 套件**：`tests/ui/repl-flow.test.tsx`，覆盖：
   - 单轮：发任务 → mock 返回 tool_call → 断言 Inline/Block 渲染 + 参数摘要
   - 多轮：第 2 轮 mock 检查收到第 1 轮历史（验证续接）
   - 权限弹窗：mock dangerous tool → 断言 PermissionDialog → stdin 选 allow → 工具执行
   - 斜杠命令：`/help`/`/cost`/`/clear` 断言输出
4. **L3 冒烟脚本**：`tests/e2e/smoke-tmux.sh`，用 `-l` 发中文，半自动核对。
5. **回写本文档**：PoC 结论（stdin.write 是否逐字符、`\r` vs `\n`）回填第六节。
