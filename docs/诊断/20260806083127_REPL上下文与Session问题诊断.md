# REPL 上下文与 Session 问题诊断（含名词解释）

> 写给自己看的备忘：讲清楚「为什么 REPL 越聊、存档文件越多 / 状态栏报上下文超了 / agent 多轮失忆」这三件事，以及接下来怎么修。
> **本文核心目标**：把里面所有专业名词翻译成大白话，看完就能拍板下一步。
>
> 创建：2026-08-06 ｜ 状态：待决策 ｜ 关联：M3.5（交互式 CLI）

---

## 0. 一句话总结

你用 REPL（那个能持续对话的终端界面）和 agent 聊天时，**每发一句话，agent 都当成「从零开始的全新对话」来跑**——既记不住上一句，又每次新建一个存档文件。同时状态栏用一个**写死的数字**算「上下文用了多少」，导致明明离真正上限还很远，却显示满了。

这两件事其实是**同一个病**：REPL 没有把「上一轮聊过什么」交给下一轮。

---

## 1. 你看到的现象（对号入座）

| 现象 | 表现 | 根本原因 |
|------|------|----------|
| **A. 存档文件越聊越多** | `.ecode/sessions/` 里聊几句就堆一堆 `.json` 文件 | 每条消息新建一个会话 ID（见根因一） |
| **B. 状态栏报「上下文超了」** | 百分比动不动顶到 99%，以为满了 | 状态栏用了写死的 60K 当分母（见根因二·假超） |
| **C. agent 多轮失忆** | 第二句话问的东西，它不记得第一句聊过 | 同根因一：每轮是全新会话，没有历史 |

## 2. 专业名词速查表（看不懂的都在这）

> 先把下面这些词搞懂，后面的诊断就和读故事一样。

### 2.1 模型 / 上下文相关

- **LLM（大语言模型）**：就是 GLM、DeepSeek、Claude 这些 AI。它的工作方式是「给它一坨文字，它接着往下写」。
- **token（词元）**：模型读写的「最小单位」。粗略理解：**1 个英文单词 ≈ 1~2 个 token，1 个汉字 ≈ 1~2 个 token**。模型不按「字数」算，按 token 算。
- **上下文窗口（context window）**：模型一次**最多能看进去多少 token**。就像人的「短期记忆容量」。
  - GLM-5.2 配置的是 **1,000,000（100 万）token** —— 非常大。
  - DeepSeek 是 128,000（12.8 万）。
  - 超过这个量，模型 API 会直接报错（「太长了，塞不下」）。
- **system prompt（系统提示词）**：每次对话最前面塞给模型的「角色设定 + 规则 + 工具说明」。它**永远在最前面**，每轮都带着。本项目的就是 `CLAUDE.md` 那些规则拼出来的。
- **token 估算 length/4**：怎么知道当前对话用了多少 token？最简单的办法：**字符数 ÷ 4**。本项目就这么估的（仿 Claude Code）。
  - 注意：这只是**估计**，不精确。用来判断「要不要开始压缩」，不需要准。
  - 坑：对中文，这个估法**偏低**（中文实际 token 比字符数÷4 多），所以本地以为「还早」，真实可能更满。

### 2.2 Agent 怎么干活

- **agent loop（agent 循环）**：agent 不是「问一句答一句」，而是一个**循环**：模型说 → 执行 → 把结果喂回去 → 模型再说 → ……直到模型给出「最终回答」（不再喊工具）才停。
- **一轮 / 一次迭代（round / iteration）**：循环跑一圈叫一轮。一个任务可能跑很多轮（读文件、改文件、再读、再改……）。
- **tool_call / tool_use（工具调用请求）**：模型说「我要读 `package.json`」——这是个工具调用请求，带一个唯一 id。
- **tool_result（工具结果）**：执行完工具，把结果喂回给模型。**必须带上刚才那个 id**，让模型知道「这是你刚才要的那个结果」。
- **配对（id 配对）**：`tool_use.id` 和 `tool_result.tool_use_id` **必须一一对应**。对不上，API 直接报 400 错误。这是 agent 开发最硬的约束之一。
- **messages（消息历史）**：整个对话的记录数组。**每轮都把完整历史重新发给模型**（不是只发增量）。所以历史会越滚越大。
- **流式（stream）**：模型回答时「一个字一个字往外吐」，而不是憋到最后一次性给。体验更好。

### 2.3 会话 / 存档相关

- **session（会话）**：一次完整对话的记录，存成一个 `.json` 文件。包含：会话 ID、首句任务、所有消息、轮数、工具调用数等。
- **REPL（交互式终端）**：`ecode` 不带参数启动后，那个能**持续对话、不退出**的界面。对标 Claude Code 的沉浸式终端。
- **one-shot（一次性模式）**：`ecode "你的任务"` 这种，跑完一个任务就退出。和 REPL 相对。
- **会话续接（--continue / --resume）**：接着上次的会话继续聊。命令行里的 `ecode --continue "新问题"` 或 `ecode --resume <id> "新问题"`。
- **resumed（续接上下文）**：代码里的一个参数名。`runAgentStream(task, { resumed: {...} })` 里的 `resumed`，意思是「这是一次续接，请带着上次的历史往下跑」。**REPL 里恰恰从没传过这个参数**——这是病根。
- **UUID**：一串几乎不可能重复的随机 ID（如 `550e8400-e29b-...`）。本项目用它当会话 ID。
- **slug**：从任务文字里榨出来的「文件名友好」短串（如任务「了解一下本项目」→ slug `了解一下本项目`）。文件名长这样：`<UUID>_<slug>.json`。slug 只是好看，唯一性靠 UUID。
- **DisplayMessage vs LLM history**：
  - `DisplayMessage`：**界面显示用的**消息（React state 里存的，给人看）。
  - `LLM history`：**发给模型的**消息（`ECodeMessage[]`）。
  - 项目里明确写了：**这俩不是一回事，严禁从显示用的反推出发给模型的**（会丢工具配对等结构）。

### 2.4 终端 / 颜色 / 写文件

- **ANSI 转义码**：终端里控制颜色、加粗那些看不见的指令（比如 `\x1b[31m` = 红色）。
- **truecolor（1670 万色）**：用 `\x1b[38;2;R;G;Bm` 指定任意 RGB 颜色。现代终端都支持。
- **256 色**：老一点的颜色方案，用 `\x1b[38;5;Nm` 指定一个 0~255 的色号。颜色没那么准。
  - **坑**：测试环境里，ink（渲染库）发现「不太确定终端支不支持真彩色」，就**自动降级成 256 色**。于是测试里期望 `250;179;135`（真彩），实际吐出 `38;5;103`（256 色色号）→ 测试挂。这是环境问题，不是逻辑错。
- **原子写（tmp + rename）**：写文件时先写一个 `.tmp` 临时文件，写完再「改名」成正文件。这样即使写到一半进程被杀，也不会留下半个坏的文件。
- **fire-and-forget（发了就不管）**：调用一个函数但不等它返回（比如存盘），就算它失败也不影响主流程。本项目存 session 就是这路：存失败只 warn 一下，不杀 agent。

## 3. 根因一：为什么存档文件越聊越多 🔴

### 3.1 一句话

**REPL 模式下，你每发一条消息，代码都当成「全新会话」跑——每次生成新 UUID、写新文件。**

### 3.2 为什么

你发消息的代码在 `src/ui/use-agent-stream.ts`，简化后长这样：

```ts
const submit = (text) => {
  // ...
  for await (const event of runAgentStream(text, streamOpts)) { ... }
  //                                       ^^^^^^^^^
  //   streamOpts 里【没有】resumed 字段 —— 没告诉它「这是续接」
};
```

而 agent 核心代码（`src/agent.ts`）的逻辑是：

```ts
// 1. 会话 ID：有 resumed 就复用旧的，没有就【新建一个 UUID】
const sessionId = opts.resumed?.id ?? generateSessionId();  // ← REPL 每轮都走右边：新 UUID

// 2. 消息历史：有 resumed 就带上旧历史，没有就【只放这一句话】
let messages = opts.resumed
  ? [...opts.resumed.messages, { role: 'user', content: task }]  // 续接：带历史
  : [{ role: 'user', content: task }];                           // ← REPL 每轮都走右边：只有这一句
```

因为 REPL 从不传 `resumed`，所以**每条消息**都：① 生成新 UUID → 新文件名；② 只带这一句话，不带历史。

> 注：上次那个 commit「UUID v4 替换时间戳」只修了「同秒运行两次撞 ID」的老毛病，**没修 REPL 每轮新建**这个。所以你才觉得「修了还一样」。

### 3.3 为什么命令行模式（one-shot / --continue）没问题

- `ecode "任务"`（一次性）：一次运行只调一次 `runAgentStream`，从头到尾一个 UUID，多次存盘都是**覆盖同一个文件**。✅
- `ecode --continue "新问题"`：命令行入口显式构造了 `resumed: {...}` 传进去，复用原 ID。✅
- **只有 REPL 坏了**。❌

### 3.4 顺带一个更严重的后果

因为不传 `resumed`，**模型在 REPL 里完全没有跨轮记忆**。你第 2 句话问的东西，模型眼里是一张白纸——文件变多只是表象，「失忆」才是真问题。

## 4. 根因二：为什么上下文「超了」🟡

这个要分**两层**，别混了。

### 4.1 第一层：状态栏「假超」（已修 ✅）

状态栏算「上下文用了百分之几」的代码（`src/ui/app.tsx`）原来是：

```ts
const CONTEXT_WINDOW_TOKENS = 60_000;   // ← 写死的
ctxPercent = inputTokens / 60000 × 100
```

但你的 GLM 真实窗口是 **1,000,000**。于是只要上下文涨到几万 token（读几个文件就会），状态栏就按 60K 一除，**百分比直接顶到 99%**，看起来像「满了」，实际离 1M 还远着呢。

**这就是你看到的「超了」——多半是假的。**

### 4.2 第二层：单轮内上下文确实会膨胀（真超，未修 🔴）

即使修了状态栏，**一个任务在一轮 agent 循环里**，上下文还是会真涨，原因：

1. **消息历史是累加的**：每轮都把全部历史重发给模型。读 5 个文件，这 5 个文件的内容就一直留在历史里。
2. **模型可能重复读同一批大文件**：我在 `docs/logs/runtime/2026-08-05/2026-08-05_054300.md` 日志里数到，**一次运行内 `MEMORY.md` 的完整内容被塞进消息历史 8 次以上**。
3. **中文 token 估低**：`length/4` 对中文低估，本地以为「才一半」，真实可能更满。

后果：单轮跑久了，上下文真涨上去。GLM 1M 窗口很大，一般撑得住；但遇上「读一整个大仓库」这种任务，或窗口更小的模型（DeepSeek 128K），就可能真超。

> 当前代码里**有**压缩机制（`maybeCompress`），80% 阈值会触发摘要压缩。但它依赖本地 token 估算，而中文估算偏低，可能触发不及时。

## 6. 还没修的 + 两个老问题

### 6.1 🔴 REPL 会话续接（核心，待决策）

就是根因一。需要让 REPL 跨轮带上历史，复用同一个会话 ID。改动跨「agent 核心 ↔ UI」的接口，建议走方案 + TDD。

### 6.2 🟡 2 个颜色测试（pre-existing 老问题）

`tests/ui/spinner.test.tsx` 和 `tests/ui/status-bar.test.tsx` 里有断言「颜色应该是真彩色 RGB」。但测试环境里 ink 自动降级成 256 色，断言对不上 → 挂。**纯环境问题，不影响功能**。修法：测试启动时强制 `FORCE_COLOR=3`（强制真彩色）。

### 6.3 🟡 package.json 的 test 脚本

`"test": "vitest"` 默认是 **watch 模式**（跑完不退出，盯着文件变）。在后台任务 / CI 里会卡住。要么改成 `"test": "vitest run"`，要么 CI 里用 `npx vitest run`。这是个小工程问题，顺手能改。

> 这是本次的核心决策点。我的推荐标 ⭐。

### 决策一：contextWindow 已修，要不要现在就单独 commit？

- **⭐ 选项 A：现在单独 commit**（推荐）
  - `fix(ui): 状态栏 contextWindow 改用模型真实窗口，修假超`

- 选项 B：等 REPL 续接一起 commit
  - 攒一起，但 commit 会比较杂。

### 决策二：REPL 会话续接怎么做？

这是大头。我先给方向（确认后进方案模式细化）：

- **⭐ 选项 A：完整续接**（推荐）
  - 让 agent 在「本轮结束」事件里带回 `sessionId` 和最终的 `messages`；
  - REPL 记住这个 ID，下一轮把历史经 `resumed` 传回去；
  - `/clear` 重置 ID 开新会话。
  - **一次根治**：文件增殖 + 失忆，两个一起好。
- 选项 B：先只修「复用 ID 不 proliferate 文件」，不动历史
  - 改动小，但 agent 仍然失忆——只解决一半。
- 选项 C：暂不动 REPL，先做别的

### 决策三：那两个颜色测试 + test 脚本要不要顺手修？

- **⭐ 选项 A：顺手修**（推荐，15 分钟）
  - 颜色测试加 `FORCE_COLOR=3`；`test` 脚本改 `vitest run`。
  - 让测试全绿，后面干活有安全网。
- 选项 B：先不管，以后再说
