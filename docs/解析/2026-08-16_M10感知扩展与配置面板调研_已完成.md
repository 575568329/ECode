## 1. 多模态输入（ImageBlock）

### 1.1 三家一手实现

| 维度 | claude-code | opencode | codex |
|---|---|---|---|
| 图片入口 | 粘贴（三平台：osascript/xclip/PowerShell）+ 路径粘贴/拖拽 + Bridge 附件 + **Read 工具读图** | 无终端粘贴（Web GUI 上传）；Read 工具读图 | 仅 inline data URL；**显式拒绝 remote URL**（8 行校验） |
| 格式判定 | **magic bytes**（`detectImageFormatFromBuffer`，不信任扩展名） | photon WASM 解码推断 | 不判定（透传） |
| 客户端缩放 | **做**：sharp，2000×2000 上限、3.75MB 目标、超 token 预算渐进降质（最终 400×400 q20） | **做**：photon WASM Lanczos3，步进 0.75 降分辨率 + PNG/JPEG 质量阶梯（80/85/70/55/40），配置化（auto_resize/max 2000/max 5MB） | 不做 |
| 回给模型的形态 | **tool_result 的 content 数组放 image block**（`{type:'tool_result', content:[{type:'image', source:{base64}}]}`） | text 确认 + `{type:'file'}` 附件 | — |
| TUI 显示 | `[Image #N]` 占位 + 支持 hyperlink 时渲染 file:// 可点击链接 | — | — |

### 1.2 官方规格

**Anthropic**：单图 ≤5MB（base64 后）；最大 8000×8000px；推荐长边 1568px（**超了服务端自动缩**，传大图只浪费流量不加细节）；token ≈ (w×h)/750（2000×2000 ≈ 5.3k token）；单请求可到 ~100 张。

**GLM-4.6V（智谱当前代视觉模型）**：128K 上下文；调用名 `glm-4.6v`（另有 FlashX 9B 轻量、**Flash 免费**）；支持图像/视频/PDF/文件输入但**不支持混用**（同请求不能既图又文件）；Anthropic 兼容端点（`open.bigmodel.cn/api/anthropic`）接受标准 image block（base64 source）——与 ECode 现有翻译层零摩擦；4.5V 代单图 ≤10MB（比 Anthropic 宽容一倍）。

### 1.3 ECode 设计修正（调研前 → 后）

| # | 修正 | 依据 |
|---|---|---|
| 1 | **ToolResult 接口必须先扩展**：ECode `ToolResult { content: string }` 装不下图。CC 的正路是把 image block 放进 **tool_result 的 content 数组**（Anthropic 协议原生支持）。ECode 需加可选 `blocks?: ContentBlock[]`，loop 透传进 ToolResultBlock——"心脏零改动"口径修正为"接口扩展+透传"（与 M9 onBeforeWrite 同级） | CC `FileReadTool.ts` 的 `mapToolResultToToolResultBlockParam` |
| 2 | **OpenAI 侧协议差异要处理**：chat.completions 的 tool 消息 content 不支持 image——翻译层需把 tool_result 里的 image 转存到紧随的 user 消息 content parts（`image_url` data URI） | OpenAI 协议约束（双协议规范文档 §3 的延伸） |
| 3 | 格式判定改 **magic bytes 优先**（扩展名只做初筛） | CC 同款；扩展名可伪造 |
| 4 | **MVP 不做客户端缩放**（被否决的备选：sharp=原生依赖重、photon WASM=非必要复杂度）——Anthropic 服务端自动缩 + GLM 限制更宽，守卫拒绝+提示即可；缩放链进观察区（触发=图片 token 成本成痛点） | 两家都做缩放是因为它们要护 5MB API 硬限的体验；ECode 守卫拒绝同样安全 |
| 5 | 图片守卫补 **8000×8000px 硬限**（5MB 之外的第二维） | Anthropic 官方 |
| 6 | 无视觉模型守卫的判定现实化：GLM 视觉=独立模型名（glm-4.6v，Flash 免费），非"GLM-4.6 顺带看图"——read_file 读图时若 current model 非 V 系列，直接 is_error 提示"切 /model glm-4.6v" | 智谱模型页 |

## 2. WebSearch

### 2.1 三家路线（ECode 能走哪条）

| | 路线 | ECode 可复制性 |
|---|---|---|
| claude-code | **Anthropic 服务端工具**（`web_search_20250305`，结果从 SSE 流的 server_tool_use 块回来，max_uses 8，allowed/blocked_domains 互斥校验，结果后附 REMINDER 强制列 Sources） | **走不通**——ECode 走 Astron 兼容端点，服务端工具不在协议里 |
| opencode | **本地工具调搜索 MCP**（Exa / Parallel，env 配 key，25s 超时、结果 50k 字符/响应 256KB 截断、按 sessionID hash 分流灰度） | 形态可抄（本地、provider 无关），服务商换智谱 |
| codex | 后端代理 POST `/alpha/search`（ChatGPT 后端专属） | 走不通（专有后端） |

### 2.2 智谱 Web Search API 全规格（已核实，ECode P1 实施依据）

```
POST https://open.bigmodel.cn/api/paas/v4/web_search
Authorization: Bearer <API Key>          ← 与 chat completions 同一把 key
{
  "search_query": "…",                   // 必填，≤70 字符
  "search_engine": "search_std",         // 必填：std(¥0.01)/pro(¥0.03)/pro_sogou(¥0.05)/pro_quark(¥0.05)
  "search_intent": true,                 // 必填：意图识别（改写关键词）
  "count": 10,                           // 1-50，默认 10
  "search_domain_filter": "docs.x.com",  // 域名白名单（单个）
  "search_recency_filter": "oneWeek",    // oneDay/oneWeek/oneMonth/oneYear/noLimit
  "content_size": "medium",              // medium 摘要 / high 详细
  "request_id": "uuid"                   // 幂等
}
→ { search_result: [{ title, content, link, media, icon, publish_date, refer }],
    search_intent: [{ query, intent, keywords }] }
错误码：1701 并发上限 / 1702 无可用引擎 / 1703 引擎无有效数据
```

### 2.3 ECode 设计修正

| # | 修正 | 依据 |
|---|---|---|
| 1 | **engine 默认 `search_std`**（¥0.01/次；被否决备选：默认 pro——质量更高但成本 3 倍，成本可控哲学优先，config 可改） | 价格表 |
| 2 | 工具参数暴露 `domain`（映射 search_domain_filter）与 `recency`——CC 的 allowed_domains 证明模型会用好这个旋钮 | CC schema |
| 3 | 超时 **25s** + 结果截断（单条摘要 500 字、总数 10 条封顶防刷） | opencode 同款限制 |
| 4 | 结果格式化吸收 CC 范式：编号列表（标题/URL/摘要/来源/日期）+ 尾注提醒模型"回答时列出 Sources"（生态习惯，也方便用户核对） | CC WebSearchTool/prompt.ts |
| 5 | 1701/1702/1703 错误码 → recoverable 回喂（模型可换 engine 重试或放弃） | 错误码语义 |

## 3. /config 应用内面板

### 3.1 一手对照

| | claude-code | opencode | codex-rs |
|---|---|---|---|
| CLI 内面板 | **有**：四 Tab（Status/Config/Usage/Gates）；Config 进面板即**搜索模式**（实时过滤设置项）；~19 项几乎全是布尔 toggle + 枚举子菜单（Theme/Model/Language 等 8 种）；↑↓ 导航、Enter/→ 进子菜单、Esc 逐级退 | **无**（CLI 只有 `debug config` 诊断；设置 UI 在 Web GUI） | 无（config/list·read·update JSON-RPC 供远程调） |
| 原始文件逃生口 | **没有**（全部走 saveGlobalConfig API） | — | — |

### 3.2 ECode 取舍

- **吸收**：搜索模式优先——PanelShell 的即时搜索天然就是（CC 专门为此写了 SearchBox，ECode 已有）；布尔项 toggle + 枚举子菜单的交互范式；"面板只放高频项"的克制（CC 19 项没塞 provider 编辑）。
- **不抄**：CC 无逃生口是因为它 first-party 封闭配置；ECode 的 config.json 是 jsonc 全量用户领地（mcpServers/hooks/plugins 全在里面），**保留"打开原始文件"逃生口 + jsonc 非破坏修改**是覆盖不全问题的结构性解药，这点维持 M10 原设计。
- Providers 编辑页保留但降级为"查看 + 提示 $EDITOR 改"（对齐 CC 克制：baseURL/key/models 低频且敏感，面板代编收益低风险高）——原设计"apiKey 脱敏输入框"裁剪。
