## 第一部分：子代理 Subagent（支点 9）

### Q1：子代理的本质是什么？为什么「侦察兵模式」？

**子代理 = 主代理派一个独立上下文的「分身」跑子任务，只回结论，不回过程。**

- **主代理 = 指挥官**：综合情报、做决策、组织最终回复。
- **子代理 = 侦察兵**：独立跑（独立 messages / 人设 / 工具），只回**结论**。

**为什么只回结论不回过程**（关键）：

```
【若回完整过程】子代理读了 10 个文件（10 轮 tool_call）→ 全部回到主代理
                  → 主上下文被 10 轮 tool 污染 → 主代理退化成「传话筒」
                  → 违背「派子代理保主上下文」的初衷

【只回结论】    子代理读完 10 文件 → 只回一段摘要 → 主上下文只多一条结论
                → 主代理综合后回用户 → 上下文经济
```

**三源实证（只回最终文本）**：
- **CC**：`agentToolUtils.ts:276-357` `finalizeAgentTool` —— 取最后一条 assistant 消息的 text blocks；空则向前回溯找最近有 text 的。返回 `{content:[{type:'text'}], totalTokens, usage}`，中间 tool_use 噪声**绝不外泄**。
- **opencode**：`tool/task.ts:213` `result.parts.findLast((item) => item.type === "text")?.text` —— 同样只取最后一段 text，包成 `<task><task_result>...</task_result></task>` XML。
- opencode 文档原话（`task.txt:15`）："The result returned by the agent is **not visible to the user**."

### Q2：ECode 子代理怎么实现？为什么是「递归 runAgentStream」？

**ECode 复用主干道**：子代理 = 递归调一次 `runAgentStream`（换 system + tools 子集 + 空 messages），不造新循环（呼应总纲 4.3「agent loop 不动」）。

**这不是 ECode 瞎想——CC 就是这么做的**：CC 的子代理 = 递归实例化同一个 `query()` 循环（`runAgent.ts:748-757`）：

```ts
// CC runAgent.ts:748 —— 子代理递归调主 query 循环
for await (const message of query({
  messages: initialMessages,        // 独立 messages（子代理的）
  systemPrompt: agentSystemPrompt,  // 独立 system（人设）
  toolUseContext: agentToolUseContext,  // 独立工具上下文
  canUseTool,                       // 独立权限
  ...
})) { ... }
```

子代理拥有**独立的** messages / systemPrompt / tools / mcpClients / abortController（`runAgent.ts`：messages:373 / systemPrompt:508 / tools:661 / mcpClients:650,685 / abortController:524）。ECode 的 `runAgentStream(task, opts)` 同样接受 `system/tools/allow/permissionMode/denyRules/permissionGate` 注入——**天然支持子代理**，只需加 `tools` 选项（实施方案阶段 0）。

**opencode 不同**：子代理用独立 child session（`parentID` 串联，`task.ts:156`）。ECode 选 CC 式（递归调用）而非 opencode 式（独立 session 实体），理由：ECode 已有事件流解耦 + `runAgentStream` 可重入，递归更轻（不引入 session 父子链）。opencode 式的好处（子代理 session 在 UI 独立可见）归支点 17 可观测性（M6+）。

### Q3：权限⊆红线——为什么子代理权限只能更严不能更宽？

**风险场景（权限代持绕过审批）**：

```
你给主代理 default 模式（改文件要审批）
   ↓
主代理想偷偷改文件，但不弹窗 → 派子代理「帮我改这个文件」
   ↓
若子代理权限 ≥ 主代理 → 子代理改文件不弹窗 → 审批形同虚设 ❌
```

**红线**：子代理权限 **⊆ 主代理**（只能更严，不能更宽）。

**三源实证**：
- **CC**：`runAgent.ts:412-498` `agentGetAppState` —— agent 的 permissionMode 除非父是 bypass/acceptEdits/auto，否则被 agent 定义覆盖；async agent 设 `shouldAvoidPermissionPrompts: true`（不能弹 UI，更严）。`allowedTools` 一旦提供**完全替换** session 级 alwaysAllowRules。
- **opencode**：`subagent-permissions.ts`（28 行）—— **只继承父 session 的 deny + external_directory**，子代理自决其余；**额外强制 deny `task`/`todowrite`**（防递归）。注释原话："Parent agent restrictions only govern that agent; the subagent's own permissions determine its capabilities."

**ECode 决策（支点 9 #3）**：默认继承主代理模式 + 全部权限规则（denyRules + 已批准 allow），可被人设 `tools:` 收紧工具子集。ask 弹窗归主对话（子代理共享主 `permissionGate`，不让子代理自己弹）。

> **⚠️ 设计待定（请审阅）**：opencode 的「只继承 deny、allow 子代理自决」比 ECode 现定「继承全部规则（含 allow）」更严。两者取舍见 [技术选型 9-T3](./M5-技术选型与理由[待实现].md)。ECode 倾向：**继承 deny（硬规则）+ 人设 tools 收紧 + 默认不放行新危险操作**，allow 是否继承待用户拍板。

### Q4：子代理会无限递归（子代理派子代理派子代理…）吗？

**会，必须防。** 两源的防法不同：

- **CC**：**允许受控嵌套**，默认主会话下 **3 层**（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`，官方文档 2026-08 实证）。Agent 工具在子代理中**默认可用**，仅当接近/超过深度上限时才被移除。即 CC 靠「深度计数」软限制，不靠「禁工具」硬限制。
- **opencode**：嵌套深度硬限制，默认 **1**（`task.ts:104-117` + `config.ts:84-86` `subagent_depth`）；并**额外强制 deny 子代理的 `task`/`todowrite` 工具**（`task.ts:139-172`）——即 opencode 双保险（深度 1 + 直接砍工具）。

> **⚠️ 纠偏（核实结论）**：早先源码阅读认为「CC 把 Agent 工具放进 ALL_AGENT_DISALLOWED_TOOLS → 默认禁止嵌套」——**不准确**。官方文档（code.claude.com/docs/en/sub-agents，2026-08）明确：嵌套**允许**，默认深度 3，Agent 工具在子代理中默认可用、仅在深度受限时移除。`ALL_AGENT_DISALLOWED_TOOLS` 应理解为「深度受限条件下的禁用集」，非「子代理一律禁用」。

**ECode 决策**（取两源更保守者）：(1) **嵌套深度限制**，默认 **1**（可配 `subagentDepth`，仿 opencode 保守默认，防一层就炸）；(2) **子代理工具表默认不含 Task 工具**（仿 opencode 强制 deny，比 CC 软深度更硬）。双保险防递归爆炸。若将来需要多层侦察（如代码审查派实现派），可上调 `subagentDepth` 放宽至 CC 式 3 层——届时再去掉「禁 Task」改为「深度软限制」（与 CC 对齐）。

### Q5：子代理的记忆/会话怎么处理？

| 维度 | 决策 | 理由 |
|------|------|------|
| **读记忆** | 默认读项目 CLAUDE.md + memory（复用 `loadInstructions`/`buildSystemPrompt`） | 子代理需要项目背景（如「用 npm 不用 pnpm」） |
| **专项人设可覆盖** | 人设独立 system prompt → 不读 CLAUDE.md | 如 Explore 只读 agent 不需要项目记忆（CC `exploreAgent.ts` `omitClaudeMd: true`） |
| **写/沉淀记忆** | **不独立沉淀**，跑完即弃 | 结论回主代理，由主代理决定记不记 |
| **存 session** | **不独立存 session** | 是主对话的一次工具调用，不是独立会话 |

**CC 实证**：子代理可定义 `memory: 'user'|'project'|'local'`（`loadAgentsDir.ts:73-99`），但 ECode 一期不做 agent 独立记忆（YAGNI）。

### Q6：子代理的人设（`.ecode/agents/*.md`）格式怎么定？

**抄 CC frontmatter，一期只做 5 个字段**（YAGNI，预留扩展）：

| 字段 | CC 字段 | ECode 一期 | 说明 |
|------|---------|-----------|------|
| `description` | 必填 | ✅ 必填 | 何时派这个分身（主 LLM 据此决定）+ catalog 注入 system |
| `prompt`（正文） | 必填 | ✅ 必填 | 人设正文（.md body） |
| `tools` | 可选 | ✅ 可选 | 限定工具子集（收紧权限） |
| `model` | `'inherit'`/具体 | ✅ 可选 | 支点 22 模型路由的前置 |
| `permissionMode` | 可选 | ⏸ 后置 | 一期继承主代理 |

**CC 完整字段（15+，ECode 不全做）**：`description / tools / disallowedTools / prompt / model / effort / permissionMode / mcpServers / hooks / maxTurns / skills / initialPrompt / memory / background / isolation`（`loadAgentsDir.ts:73-99`）。

**加载优先级（抄 CC）**：built-in → user（`~/.ecode/agents/`）→ project（`.ecode/agents/`）。后者覆盖前者（`loadAgentsDir.ts:193-221`）。ECode user 目录走 `resolveDataDir`（§9.3 跨平台）。

### Q7：catalog 怎么注入 system prompt？为什么懒加载？

```
启动：system prompt 只放 agents 目录（name + description 一行一个）← 便宜
   ↓
主 LLM 看任务 → 匹配某 agent 的 description → 决定用 Task 工具派它
   ↓
触发：Task 工具 execute 才读那个 agent 正文 → 注入子代理 system ← 按需
```

**为什么懒加载**：ECode 现在 CLAUDE.md 是**全量注入**；agent 人设是**按需注入**（触发才读正文）。agent 多了也不撑爆主上下文（catalog 只放 name+description）。这与支点 13 Skills 的懒加载同构。

## 第二部分：MCP 扩展（支点 10）

### Q8：MCP 的本质是什么？ECode 为什么要做？

**MCP = App Store 协议**：

| 类比 | 实体 |
|------|------|
| 手机自带应用 | 内置工具（read/write/bash） |
| App Store 第三方 App | MCP server（GitHub/Slack/DB…） |
| 手机 | agent（装上就能干更多事） |

**为什么做**：**生态红利**。CC 生态已有大量现成 MCP server，接上协议白嫖全部，不用自造垂直工具。MCP 是事实标准（CC/Cursor/Windsurf 都支持），不接就脱离生态。

### Q9：MCP 三个原语（Tools/Prompts/Resources）取舍——为什么只做 Tools？

| 原语 | 触发 | ECode 决策 | 理由 |
|------|------|-----------|------|
| **Tools** | LLM 自动调 | ✅ **做** | 核心，与内置工具并列，LLM 自动调用 |
| **Prompts** | 手动 `/mcp__server__prompt` | ❌ **砍** | 与支点 13 Skill 功能重复（都是「手动触发的预设工作流」） |
| **Resources** | 只读上下文 | ⏸ **后置** | Tools 暂能替代（读数据用工具调）；待查证后定 |

**触发矩阵（关键设计——自动 vs 手动）**：

| 能力 | 怎么触发 | /命令 | 归属 |
|------|---------|:---:|------|
| 内置工具 | LLM 自动 | ❌ | 支点 3 |
| **MCP Tools** | **LLM 自动** | ❌ | 支点 10 |
| Skill | 用户手动选 | ✅ | 支点 13 |
| MCP 状态查看 | 用户手动 `/mcp` | ✅ 只读 | 支点 10+14+17 |

**逻辑**：MCP Tools 跟内置工具一样自动调（不用 / 命令）；手动触发的预设工作流全归 Skill；`/mcp` 是「查看状态」不是「执行」。

> **⚠️ 一笔矛盾（待审阅）**：支点 10 早先决定「砍 MCP Prompts 归 Skill」，但 CC 的 MCP 命令恰恰走 Prompts。支点 14 讨论记了这笔账。ECode 一期砍 Prompts（Skill 替代），`/mcp` 只做只读状态查看——若未来发现 Prompts 有不可替代价值再补。

### Q10：MCP 传输为什么 stdio 起步、Streamable HTTP 跟进？

**演进时间线（研究核实，规范版本见技术选型 §MCP 规范版本）**：

| 阶段 | 传输 | 场景 | 状态 |
|------|------|------|------|
| **阶段 1** | **stdio** | 本地起步 | ✅ ECode 先做 |
| **阶段 2** | **Streamable HTTP + OAuth** | 远程 | ⏸ ECode 框架先行，OAuth 实现 M6+ |
| （旧） | HTTP+SSE | 远程旧标准 | ❌ **已废弃** |

**为什么 stdio 起步**：个人 CLI 合理——简单、隐私、凭证不出机器。spawn server 子进程，JSON-RPC over stdio 双向通信。

**为什么 Streamable HTTP 跟进**：远程是趋势。旧 HTTP+SSE 已废弃（被 Streamable HTTP 取代）。stdio 还爆过 RCE 漏洞（CSA Labs 报告），企业推远程托管。

**三源传输实证**：
- **CC**：`TransportSchema = enum['stdio','sse','sse-ide','http','ws','sdk']`（`services/mcp/types.ts:23-26`），核心 stdio/SSE/Streamable HTTP。
- **opencode**：`mcp/index.ts:6-17` 用官方 SDK 三传输；**remote 双发试连**——先 StreamableHTTP 再 SSE（`index.ts:269-332`），任一连上即用。
- 两源都用官方 `@modelcontextprotocol/sdk`，不自己造协议。

### Q11：MCP 配置为什么独立注册、不进 config.json？

**MCP 安装态独立注册表（`~/.ecode/mcp/registry.json`），不进 config.json**——VS Code 扩展模式。

**为什么**：MCP 若进 config，用户替换 config.json（换项目/拷贝覆盖）会**不知情地连坐删除 MCP**（用户本意不是删 MCP）。独立注册后，替换 config 不动 MCP；**显式卸载才删注册表**。

**对比三源**：
- **CC**：`.mcp.json`（项目级，git 共享）+ 用户级 + 本地级 + 企业级（`services/mcp/config.ts:911-1024`），优先级 plugin < user < project < local。**CC 把 MCP 放配置文件**。
- **opencode**：`opencode.json` 顶层 `mcp` 字段（`core/v1/config/mcp.ts`）。**也放配置文件**。

> **⚠️ ECode 与两源不同（待审阅）**：ECode 选「独立注册表」而非两源的「进配置文件」，是为防「替换 config 连坐删 MCP」。代价：多一个注册表文件、配置更分散。若用户更习惯 CC/opencode 式（mcp 块进 settings），可改。**这是 ECode 独有决策，需用户确认。**

### Q12：MCP 工具如何命名、如何加入工具表？

**命名空间**：`mcp__{server}__{tool}`（抄 CC `mcpStringUtils.ts:50-52`），避免与内置工具重名，权限规则也按全名匹配。非字母数字下划线横线一律转 `_`（normalizer，`normalization.ts:17-23`）。

**加入工具表**：MCP server 连上后 `tools/list` 发现工具 → 适配成 ECode `ToolDefinition`（name/description/parameters/execute=callTool 闭包/dangerous=true）→ 合并进 `runAgentStream` 的 `tools`。

**透明性**：MCP 工具与内置工具并列，LLM **自动调用**（不用 / 命令）。

**三源适配实证**：
- **CC**：`MCPTool` 模板（`tools/MCPTool/MCPTool.ts:27-77`）+ per-tool spread 重写 name/description/call（`services/mcp/client.ts:1743-1804`）；`fetchToolsForClient` LRU memoize。
- **opencode**：`mcp/catalog.ts:42-83` `convertTool` 一函数——`inputSchema→jsonSchema`，execute 调 `client.callTool`，工具名 sanitize。**容错**：`TolerantListToolsResultSchema`（对坏 outputSchema 降级）+ 分页 + `ToolListChanged` 热更新。

### Q13：MCP 是不可信代码——安全红线有哪些？

MCP server 是第三方不可信代码，五条红线：

1. **走权限审批**：MCP 工具统一 `dangerous=true` → default 模式 ask 弹窗（呼应支点 7）。
2. **显式登记**：装哪个 server 要用户手动登记（不自动跑，最小权限）。
3. **防 stdio RCE**：stdio 启动命令做白名单/校验（⚠️ **opencode 没做**——`command` 直接传 `StdioClientTransport`，RCE 风险完全靠配置文件信任域承担；ECode 应**主动补一层**命令 allowlist）。
4. **进程清理**：stdio server 退出时递归 kill 子孙进程（opencode `mcp/index.ts:418-440` 用 `pgrep -P`，Windows 跳过）。
5. **OAuth 防 CSRF**：远程 OAuth 的 `state` 校验（opencode `index.ts:909-913`）+ token 文件 `0o600` + 文件锁。

### Q14：`/mcp` 命令做什么？

**只读可观测**（不执行）：server 清单（name + 本地/远程 + enabled）+ 连接状态（✅connected / ❌failed / 🔄connecting）+ 暴露工具清单。支持 `/mcp enable|disable <name>`（写回 registry，不改 config）。

## 第三部分：Hooks 系统（支点 12）

### Q15：三个核心 hook 是什么？hook vs 权限规则边界？

| Hook | 比喻 | 时机 | 能干啥 | 不能干啥 |
|------|------|------|--------|---------|
| PreToolUse | 🚪 门卫 | 工具执行**前** | 拦截(deny)/改输入/提醒 | — |
| PostToolUse | 📋 监工 | 工具执行**后** | 改输出/记账/通知 | 撤回已执行的 |
| Stop | ✅ 验收员 | agent 要停 | 打回继续干/反馈 | — |

**hook vs 权限规则**：

| | 权限规则（支点 7） | Hooks（本支点） |
|---|---|---|
| 形态 | 静态黑白名单 | 动态脚本 |
| 适合 | 简单模式（禁 `rm -rf`） | 复杂判断（调 git/跑测试/副作用） |
| 硬度 | 硬底线（deny 不可翻盘） | 只能收紧不能放宽 |

### Q16：Hooks 的执行顺序？hook 能绕过权限 deny 吗？

**执行顺序**：`PreToolUse hook → 权限规则 check() → 工具执行 → PostToolUse hook`。

**hook 不能绕过权限 deny**（安全核心）。CC 实证（`services/tools/toolHooks.ts:332-433` `resolveHookPermissionDecision`）：

- hook 返回 `allow` → **仍要查 rule-based 权限**：若规则是 deny → deny；若规则是 ask → 仍弹窗（hook 批准也不能 bypass ask 规则）。
- hook 返回 `deny` → 直接生效，不走 canUseTool。
- hook 返回 `ask`/无决策 → 走正常 canUseTool。

**结论**：权限 `deny` 是硬边界，hook allow 翻不了盘；hook 只能**收紧**（deny/ask），不能**放宽**（allow 绕过 deny/ask 规则）。

### Q17：为什么 ECode 做 settings.json 式 command hook，而不是 opencode 式 TS 插件 hook？

**关键发现**：opencode **未实现** Claude-Code 式 settings.json hooks（无 `hooks` 配置键、无 matcher/command/exit-code/JSON-decision）。opencode 的扩展点是 `packages/plugin/src/index.ts` 的 **TS 函数 `Hooks` interface**（`tool.execute.before/after` 等），由插件注册、`plugin.trigger` 串行调用、**就地 mutate output**——**不是 shell 脚本**。

| 维度 | CC settings.json hook（ECode 选） | opencode TS 插件 hook |
|------|--------------------------------|---------------------|
| 形态 | shell command（matcher 匹配） | TS 函数 |
| 配置 | settings.json hooks 块 | 写 TS 插件注册 |
| 谁能用 | 任何用户（写 shell） | 开发者（写 TS） |
| 流控 | exit code 2 / JSON decision | mutate output 字段 |
| 生态 | 抄 CC 生态（用户迁移成本低） | opencode 专属 |

**ECode 选 CC 式**：贴近 CC 生态（用户已有的 hooks 配置可迁移），且 shell command 门槛低（用户不用写 TS）。opencode 的 `tool.definition` hook（动态改工具 description/parameters）是独有精巧点，ECode 可后置借鉴。

### Q18：CC 有多少 hook 事件？ECode 为什么只做 6 个？

**CC 共 30+ 个 hook 事件**（官方文档 code.claude.com/docs/en/plugins-reference，2026-08 实证；源码枚举 `entrypoints/sdk/coreTypes.ts:25-53` `HOOK_EVENTS`）：PreToolUse / PostToolUse / PostToolUseFailure / PostToolBatch / Notification / MessageDisplay / UserPromptSubmit / UserPromptExpansion / SessionStart / SessionEnd / Setup / Stop / StopFailure / SubagentStart / SubagentStop / PreCompact / PostCompact / PermissionRequest / PermissionDenied / TeammateIdle / TaskCreated / TaskCompleted / Elicitation / ElicitationResult / ConfigChange / CwdChanged / DirectoryAdded / FileChanged / WorktreeCreate / WorktreeRemove / InstructionsLoaded。

> **核实纠偏**：早先据 `coreTypes.ts:25-53` 统计为「27 个」——官方文档（2026-08）实为 **30+**，多出 `PostToolBatch`/`MessageDisplay`/`UserPromptExpansion`/`DirectoryAdded` 等。源码常量与文档枚举口径略有出入，以官方文档为准。

**ECode 一期只做 6 核心**：`SessionStart / SessionEnd / UserPromptSubmit / PreToolUse / PostToolUse / Stop`。

**砍掉的理由**（YAGNI，~80% 是 CC 协作/团队/内部场景）：
- `TeammateIdle/TaskCreated/TaskCompleted` → CC 多 agent 协作，ECode 单机。
- `WorktreeCreate/WorktreeRemove` → CC worktree 隔离，ECode 不做。
- `Elicitation/ElicitationResult` → MCP elicitation，ECode MCP 一期不做。
- `Notification/PermissionRequest/PermissionDenied` → UI 通知，ECode 走事件流。
- `SubagentStart/SubagentStop` → 子代理可观测，归支点 17（M6+）。
- `PreCompact/PostCompact` → 压缩钩子，ECode 后置。
- `FileChanged/CwdChanged/ConfigChange/InstructionsLoaded` → 文件/配置监听，按需加。

### Q19：Pre/Post hook 为什么必须 Promise-await，Stop 可走事件流？

**Pre/Post 要「等决策」**：PreToolUse 要能 deny/block/改输入——这需要**暂停工具执行、等 hook 返回、再决定是否执行**。事件流是**单向通知**（fire-and-forget），承载不了「等决策」。

**Promise-await 模型**：仿 ECode 已有的 `permissionGate`（`agent.ts:461` `await opts.permissionGate.ask(...)`）——hook 同样用 `await opts.hooks?.preToolUse(...)` 注入回调，拿到决策后再继续。

**Stop 只通知**：Stop hook 要么放行（agent 停）要么打回（继续干）——这可以走事件流（yield hook 事件，UI/runner 处理后决定）。但「打回继续」需要反馈到 loop，所以 ECode 的 Stop hook 实际也用回调（抽 `emitCompleted()` 收口，Stop hook 返回 `stopHookContinue` 控制）。

**CC 实证**：Stop/SubagentStop 同一实现（`utils/hooks.ts:3639-3653`），hook `preventContinuation` → 把 blocking 文本作为新 user message 注入对话继续（`query/stopHooks.ts:65-81`），`stop_hook_active: boolean` 防递归。

### Q20：PreToolUse hook 怎么「阻止/批准/改输入」？（CC 协议）

**CC 三通道**（`utils/hooks.ts:489-737` `processHookJSONOutput`）：

1. **exit code 2**（`hooks.ts:2648-2668`）→ 阻断，stderr 当 reason。
2. **JSON `{decision: 'approve'|'block', reason}`**（`hooks.ts:525-543`）→ block=deny。
3. **JSON `{hookSpecificOutput: {hookEventName:'PreToolUse', permissionDecision:'allow'|'deny'|'ask', permissionDecisionReason, updatedInput}}`**（`hooks.ts:551-575`）→ 三态决策 + **能改工具入参**（updatedInput）。

**stdin/stdout 协议**：
- **stdin**：单行 JSON（`hooks.ts:1006-1007`）。PreToolUse input = `{session_id, transcript_path, cwd, permission_mode, hook_event_name:'PreToolUse', tool_name, tool_input, tool_use_id}`（`hooks.ts:3418-3424` + base `301-328`）。
- **stdout**：纯文本（提示）或 JSON `{continue, suppressOutput, stopReason, decision, reason, systemMessage, permissionDecision, hookSpecificOutput}`（`hooks.ts:399-451`）。

**matcher 语义**（`hooks.ts:1346-1381` `matchesPattern`）：
- 空/`'*'` → 全匹配；
- 纯 `[a-zA-Z0-9_|]` → 精确匹配 / `|` 多选（如 `"Bash|Edit"`）；
- 其他 → 正则（如 `"mcp__github__.*"`）。

> **🔴 实现红线（核实结论）**：`permissionDecision` **必须嵌套在 `hookSpecificOutput` 下**，顶层平铺写法（`{permissionDecision:"deny"}`）会被**静默丢弃**（CC GitHub issue #48760）。若 ECode 一期实现结构化决策通道，JSON 解析必须严格校验嵌套层级，否则 hook 永远「不生效」且无报错——极难排查。

> **多 hook 决策优先级（核实结论）**：同事件多 hook 时取最严格——`deny > ask > allow`（CC `PermissionBehavior` 无 `defer`，源码 `types/permissions.ts:44` + 聚合 `utils/hooks.ts:2820-2846` 核实）。且 PreToolUse 的 `permissionDecision` 与 PostToolUse/Stop/UserPromptSubmit 的顶层 `decision:"block"` 是两套不同字段（PreToolUse 用嵌套三态，其余用顶层 decision），实现时勿混用。

**ECode 一期**：做 exit code 2 + `{decision}` 两通道（够用），`hookSpecificOutput.permissionDecision/updatedInput` 后置（结构化改输入是高级特性——若做须守上面的嵌套红线）。matcher 抄 CC 三段式。

### Q21：系统 hooks 为什么「代码注册、强制叠加、不可覆盖」？

**系统 hooks 写代码里，不进配置文件，用户改不了**（呼应 §9「系统级跟 config.json 零依赖」）：

| 层 | 位置 | 可改 |
|----|------|------|
| 系统内置 | **代码注册（hardcoded registry）** | ❌ 不可改 |
| 用户级 | `~/.ecode/` config hooks 块 | 用户 |
| 项目级 | `.ecode/` config（git 跟踪） | 团队 |
| 项目本地 | `.ecode/` config（gitignore） | 个人 |

**强制叠加**：永远执行，用户 config **无法删除/覆盖**，只能追加自己的。例：ECode 内置 PreToolUse 拦 `rm -rf /`、保护 `.env`（用户关不掉）。

**与权限系统的关系**：权限 `deny` = 声明式硬底线（静态规则），系统 hooks = 动态硬底线（可调 git/跑测试/通知）。两者都不可被用户 config 关闭。

> **注**：M4 path-guard 已做敏感文件/越界硬安全网（声明式），系统 hooks 是其「动态版」（可在 hook 里跑任意判断/副作用）。两者互补，不重复。

### Q22：hook 是 shell 命令，Windows 跑什么 shell？

跨平台坑（呼应 §9.3）：hook command 是 shell 命令，各平台 shell 方言不通。

**CC 实证**（`utils/hooks.ts:747-850` `execCommandHook`）：
- 默认 `'bash'`；Windows + bash 走 **Git Bash (Cygwin)**，路径须 POSIX 化（`windowsPathToPosixPath`）。
- `shell: 'powershell'` → 直接用 pwsh，跳过 POSIX 转换。
- 设 `CLAUDE_PROJECT_DIR` = stable project root。

**ECode 决策**：hook command 跨平台走 **bash 工具同款 shell 分流**（`getShellInfo()` 已自探测 Git Bash/WSL，支点 3 复用）。即 hook 执行器复用 `executeBash` 的 shell 探测，不另造。

### Q23：M5 三支点之间的依赖与互操作？

```
支点 9 子代理 ──┐ 递归 runAgentStream（复用核心）
               ├─ 工具子集（人设 tools 收紧）
               └─ 权限⊆（继承 check + denyRules）
                          ↑
支点 10 MCP ──── 工具透明加入 runAgentStream.tools（dangerous→check）
               └─ 子代理也能用 MCP 工具（CC：MCP 工具在 agent filter 开绿灯，agentToolUtils.ts:82-84）
                          ↑
支点 12 Hooks ── Pre/Post 注入 agent.ts 工具执行块（仿 permissionGate）
               ├─ 系统 hooks 强制叠加（护 .env，与 M4 path-guard 互补）
               └─ Stop hook 打回继续（喂新 user message）
```

- **子代理 × MCP**：子代理工具表可含 MCP 工具（CC 绿灯规则）。
- **子代理 × Hooks**：子代理工具执行同样过 Pre/Post hook（hook 是横切的）。
- **MCP × Hooks**：MCP 工具执行也过 Pre/Post hook（不可信代码双重防护）。

### Q24：M5 的主要风险与缓解？

| 风险 | 影响 | 缓解 |
|------|------|------|
| 子代理权限代持绕过审批 | 安全漏洞 | 权限⊆红线 + 人设 tools 收紧 + ask 归主对话（Q3） |
| 子代理无限递归 | 栈/资源爆炸 | 嵌套深度限制 + 子代理默认无 Task 工具（Q4） |
| MCP stdio RCE | 不可信代码执行 | 命令 allowlist（ECode 补 opencode 没做的，Q13） |
| MCP server 崩了杀 agent | 稳定性 | 连接失败 warn + 跳过 + 优雅降级 |
| hook 脚本卡死/抛错 | 杀 agent | hook 超时 + 失败默认放行 + warn（CC 有 try/catch，opencode 无——ECode 必加） |
| hook allow 越权 | 安全 | hook allow 不 bypass deny/ask 规则（Q16，CC 安全核心） |
| 27 事件过度工程 | 复杂度 | 只做 6 核心，其余按需（Q18） |
