## 一、Skills（支点 13）原理

### 1.1 SKILL.md 三家事实标准

Skill 文件格式 = **Markdown 正文 + YAML frontmatter**，这是 Claude Code / OpenClaw / opencode 三家共同识别的事实标准（功能架构 §支点20 撤销插件系统时论证）。

| 工具 | skill 发现 | frontmatter |
|------|-----------|-------------|
| Claude Code | `SKILL.md` + glob | name/description/allowed-tools 等（agentskills.io 规范，M5 已联网核实 17 字段） |
| OpenClaw | `SKILL.md` + frontmatter | 同构（但其「自动归纳」是正则，假自动——见 1.3） |
| opencode | `{skills}/**/SKILL.md` glob 自动发现 | 零 manifest |

**ECode 选这套格式的红利**：用户写的 SKILL.md 能被三家工具直接用，反之亦然——**零成本跨工具生态兼容**。ECode 不自造格式。

### 1.2 懒加载注入 vs 全量注入（关键区分）

| 项 | CLAUDE.md（支点8） | Skill（支点13） | 子代理 catalog（M5 支点9） |
|----|-------------------|----------------|--------------------------|
| 注入时机 | 启动**全量**注入 | 启动放 **catalog**（name+desc），触发才读正文 | 启动放 catalog（name+desc），派发才用 |
| 数量 | 一份（项目级 1~2 个文件） | **无上限**（用户/团队可写任意多） | 几个~十几个 |
| token 成本 | 固定（一份文件大小） | catalog 极便宜（每条一行），正文按需 | 同 Skill |

**为什么 Skill 用懒加载**：Skill 数量无上限，若全量注入正文 → 主上下文爆炸。catalog 只放 name+description（每条 ~一行 token），LLM 看了 catalog 知道「有哪些菜谱」，触发某个时才读正文注入。这与 M5 子代理 catalog 同构（[`M5-方案解析`](./M5-方案解析[已完成].md) §子代理懒加载）。

### 1.3 自动生成的归纳质量命门（OpenClaw 反面教训）

**OpenClaw 的坑**（[`OpenClaw参考研究`](../调研/20260806085241_OpenClaw参考研究[已完成].md)）：它的「skill 自动归纳」实际是**纯正则匹配**——把对话套进预设模板，假自动。真正的「总结这次怎么干的」必须用 LLM 理解语义，正则只能做死板分类。

**ECode 的做法**：
- 归纳用 **LLM**（非正则）——Stop hook 触发一次 LLM 调用，让它总结本次成功流程 → 写成 SKILL.md 提案。
- 提案**不直接落盘** → 进 proposal 审批队列 → **安全扫描**（自动扫危险模式 + 人工 review，决策点 D7）→ 用户 `/accept` 才转正。

**为什么必须审批**：agent 自动生成的内容若直接入库 → 可能固化错误流程 → 下次照错菜谱干 → 越错越远。人工 `/accept` 是质量闸。这复用 M4 的「危险操作先问」心智。

### 1.4 Skill / 子代理 / MCP / 自定义命令（四者边界，别混）

功能架构 §支点3 三层归类 + 命令：

| 能力 | 本质 | 归属 | 触发 |
|------|------|------|------|
| 内置工具 | 动作（read/write/bash） | 支点3 | LLM 自动调 |
| MCP | 接外部系统（GitHub/DB） | 支点10（M5） | LLM 自动调 |
| **Skill** | **方法论（菜谱：组合工具 + 步骤）** | **支点13（M6）** | 手动 /skill 或 LLM 匹配 |
| 子代理 | 独立上下文跑（有脑） | 支点9（M5） | Task 工具 |
| 自定义命令 | 用户快捷指令（.md 注入） | 支点14 | 斜杠手动 |

**Skill 不是工具**：Skill 是 prompt 注入（菜谱正文塞进对话），它**指挥**工具（read/write/bash）干活，本身不直接执行。这是 Skill 与 MCP/内置工具的根本区别。

## 二、模型路由（支点 22）原理

### 2.1 规则映射 vs LLM 决策（成本算术）

**核心问题**：路由的目的是「省钱」（简单任务派便宜模型）。但「决定派哪个模型」本身要不要花钱？

| 方案 | 决策成本 | 评估 |
|------|---------|------|
| **规则映射**（任务类型→alias） | **0**（查表） | ✅ 选这个 |
| LLM 决策（调一次 LLM 选模型） | 一次 LLM 调用 | ❌ 可能花掉省的钱 |

**算术**：假设 cheap 模型比 strong 便宜 90%。若用 LLM 决策路由，每次任务多一次（可能 strong 的）调用——省下的 90% 可能还不够这次决策。本末倒置。

**规则映射的可解释性**：config 里写死「compress→cheap / subagent→inherit」，用户一眼看懂，可调。远期若规则不够（如要按 prompt 复杂度动态判），可升级为「轻量分类器」（仍是规则/小模型，非主模型 LLM）。

### 2.2 四触发点的注入时机（三处循环外注入 + 压缩轻改）

模型路由的关键设计：**四触发点中三个（全局/Skill/子代理）在调用 `runAgentStream` 之前决定模型、循环内部零改动**；**压缩触发点需轻微侵入 `compressOpts` 构造**（`agent.ts:298-310` 的 `model = resolvedModel` 改为便宜模型），侵入级别同 M5 阶段0 改 `tools` 注入。

```
触发点              决策位置                    注入方式
─────────────────────────────────────────────────────────
全局主对话          index.ts 选模型时            resolveModelForScenario('global') → opts.provider/model
压缩摘要            agent.ts:298-310 compressOpts 构造 → 把 model 从 resolvedModel 换成 resolveModelForScenario('compress')（轻微侵入，非循环外）
子代理派发          M5 createTaskTool            agent.frontmatter.model → resolveAlias → 子代理 opts.model
Skill 执行          skill frontmatter model      skill.model → resolveAlias → 注入对话上下文
```

**为什么这样设计**：`provider`/`model` **现状已在** `RunAgentStreamOptions`（`src/agent.ts:127` `model?` + `:135` `provider?`，M2/M3.5 落地，**非 M5 阶段0**——M5 阶段0 只新增 `tools`）→ 路由层在**构造 opts 时**填入即可。`runAgentStream` 只用 opts 里给的模型，不关心谁决定的——**核心循环除压缩触发点轻微侵入 `compressOpts` 外，其余零改动**（呼应「不动核心」红线，详见实施方案 §阶段3 接线点②）。

### 2.3 alias 设计与成本可见性

**alias** = 逻辑名（`cheap`/`strong`/`reasoning`），映射到具体 `provider + model`。好处：
- **配置解耦**：换底层模型只改 alias 映射，不改 Skill/agent 里写的 `model: strong`。
- **成本可见**：路由省的钱由支点17 的成本公式算（`ModelConfig.cost` 四绝对值，[`功能架构`](../功能方案/功能架构设计[进行中].md) §支点17）。没单价表则路由仍工作但「省了多少」不可见。

## 三、多渠道接入（支点 23）原理

### 3.1 前后端分离的本质

**现状**：终端 REPL 既是「对话前端」又是「agent 后端」，两者耦合在 Ink 里。

**分离后**：agent 后端（runAgentStream + 事件流）独立，前端可以是任意渠道：

```
对话前端（多种）          agent 后端（不变）
─────────────            ──────────────
终端 REPL（Ink）    ─┐
Web 浏览器（WebChat）┼──→  runAgentStream + AgentEvent 流
IM（飞书/钉钉）     ─┘     （核心一行不改）
```

**分离的关键**：支点2 的「事件流解耦」早就为此预留（功能架构 §4.2）——核心 yield 事件、呈现层消费，核心对 UI 零依赖。多渠道只是「再加几个事件消费者」。

### 3.2 事件流解耦红利（多渠道能复用核心的根本原因）

`runAgentStream` 是**异步生成器**，yield `AgentEvent`（text_delta/tool_result/usage/completed...）。任何消费者用 `for await` 接：

| 消费者 | 怎么接 | 现状 |
|--------|--------|------|
| TUI（Ink） | `use-agent-stream.ts` for await → reducer 渲染 | ✅ 已是 |
| 无头模式（支点1） | for await → NDJSON 输出 | ⬜ 待做（P1） |
| **多渠道 WS** | for await → ws.send(event) 推给渠道 | ⬜ M6 阶段4 |
| Web 前端 | WS 接收 → Zustand store 渲染 | ⬜ M6 阶段5（条件） |
| IM 适配器 | for await → 折叠成文本回复 | ⬜ M6 阶段5（条件） |

**核心不变**：所有消费者共享同一 `AgentEvent` 类型 + 同一 `runAgentStream`，差异只在「事件→UI」的渲染映射。这就是 M6 前端工作量可控的根本原因。

### 3.3 WS 协议设计

**为什么 WS 不 HTTP 轮询**：text_delta 要逐字流式推送，HTTP 轮询（客户端定时问）延迟高、浪费请求。WS 双向实时，天然适合流。

**协议**（实施方案 §阶段4）：
- 客户端→服务端：`{type:'message', sessionId, prompt, authToken}`
- 服务端→客户端：透传 `AgentEvent`（text_delta/tool_call_start/tool_result/usage/completed，与 agent-events.ts 实际类型一致，无 tool_call）

**简化**：服务端不重新发明事件类型，直接 JSON.stringify(AgentEvent) 推——客户端按 `event.type` 渲染，与 TUI reducer 同源逻辑。

### 3.4 会话隔离（多渠道并发不串话）

多渠道并发时（终端 + Web + IM 同时连），不能共用一个 messages 流——会串话。

**解法**：每渠道连接 ↔ 独立 sessionId（复用支点6 `session.ts` 的持久化层）。session.ts 是**无状态纯函数库**（导出 `saveSession`/`loadSession`/`listSessions`/`latestSessionId`，**无 resume**），渠道适配器须**自建运行时「连接→sessionId」映射 + 同 session 串行排队锁**（session.ts 无锁）；续接靠 `agent.ts` 的 `ResumeContext`。

**并发红线**（呼应支点18 后台任务的并发约束）：**绝不两个 runAgentStream 同时跑同一 session**——同 session 的并发请求排队（一个跑完再跑下一个）。不同 session 可真并发。

### 3.5 OpenClaw Gateway 简化对比（不抄过度设计）

OpenClaw 是多渠道个人助手网关，功能架构 §本地参考源码标注其**过度设计**：Gateway/ACP/Canvas/跨设备 pairing 全是冗余。

| OpenClaw（过度） | ECode（单机简化） |
|----------------|-----------------|
| Gateway 集中路由 + 多设备 pairing | 本地 HTTP+WS 服务，单机 |
| ACP 协议 | 直接 WS + AgentEvent |
| Canvas 富交互 | 终端/Web 简化 |
| 200 文件的插件/marketplace | glob 文件投放（支点13/14） |

**ECode 只借鉴**：多渠道「后端服务化 + 适配器」的**思想**，不抄其规模。

## 四、M6 与 M5 的关系（依赖详解）

### 4.1 Skills 阶段2 ← M5 Hooks（Stop 事件）

**依赖链**：Skills 自动生成的归纳，由 **Stop hook** 触发——agent 干完活（要停）时，Stop handler 调 LLM 总结本次流程。

**为什么是 Stop**：归纳「这次怎么干的」必须在**干完之后**（Stop = agent 要终止时）。PreToolUse/PostToolUse 是单工具级，看不到全局流程；Stop 是会话级，能俯瞰全程。这是功能架构 §支点13「skill 是 P3、hooks 是 P2（13 依赖 12）」的根因。

**M5 已落地（2026-08-09）**：M6 阶段2（Skills 自动生成）依赖 M5 Hooks 的 Stop 事件——该事件属 M5 §九 ⏸ 尾巴，由 **M6 阶段 C 补齐**后阶段2 可实施。阶段1（Skills 手写）零该依赖。

### 4.2 模型路由 ← M5 子代理（model 字段）

**依赖链**：模型路由的「子代理派发」触发点，依赖 M5 子代理的 frontmatter `model` 字段（[`M5-实施方案`](./M5-实施方案[已完成].md) §三已预留）。

**部分阻塞**：路由的「压缩/全局/Skill」触发点**不依赖 M5**，可独立先做；「子代理」触发点等 M5 子代理落地。

### 4.3 M6「不动核心」红线

M6 三支点全部遵守：
- Skills = prompt 注入（不碰循环）
- 路由 = 三触发点调用前注入 opts（`provider`/`model` 现状已有，非 M5 阶段0）；压缩触发点轻微侵入 `compressOpts`（循环轻改）
- 多渠道 = 新入口复用循环（循环不改）

**唯一地基**是 `RunAgentStreamOptions` 的注入窗——其中 `provider`/`model` **现状已有**（M2/M3.5），`tools`/`permissionGate` 由 M5 阶段0 开窗。这是 M5/M6 共用的「核心扩展窗」，路由层只用现状已有的 `provider`/`model`，**不依赖 M5**。

## 五、前端架构解析

### 5.1 TUI（Ink）事件流消费（现状）

`src/ui/use-agent-stream.ts`（推测路径，基于功能架构）用 `for await` 消费 `runAgentStream` 的 AgentEvent，经 reducer 渲染成 TUI（流式文字 + 工具折叠 + 状态栏）。

**M6 TUI 工作**：零新增重型组件，复用 picker-list（skill 选择）/ permission-dialog（proposal 审批）/ status-bar（模型+路由+渠道）/ model-picker（手动切模型）。详见实施方案 §5.1。

### 5.2 Web 实时同步（若 D2 = B）

Web 前端通过 WS 接收 AgentEvent，Zustand store 消费：
- `chatStore`：消息流（text_delta 累积、tool_result 折叠）
- `uiStore`：弹窗/picker 状态

**与 TUI 同源**：消费同一 `AgentEvent` 类型，渲染逻辑同构。TUI 的 reducer 思路 → Web 的 Zustand store，只是框架不同，事件处理一致。

### 5.3 渲染逻辑复用（TUI/Web 共享）

为避免 TUI/Web 各写一套渲染，尽量把纯逻辑抽成共享函数：
- **markdown 解析**（`marked` 已是依赖，解析纯函数）
- **折叠策略表**（FOLD_STRATEGIES，功能架构 §支点16）
- **成本/Ctx% 计算**（支点17 公式）

这些纯函数 TUI（Ink markdown.tsx）和 Web（React 组件）都能调，是前端跨渠道复用的关键。

## 六、常见问题答疑

**Q1：M6 能不能跳过 M5 直接做？**
A：部分能。Skills 阶段1（手写）零 M5 依赖，可先做；模型路由的压缩/全局触发点不依赖 M5，可先做。但 Skills 阶段2（自动生成）阻塞于 M5 Hooks，路由的子代理触发点阻塞于 M5 子代理。建议 M5 先落地再全面推 M6。

**Q2：不做 Web，多渠道服务化有什么用？**
A：服务化（阶段4）让 ECode 能被**脚本/其他工具/IDE 插件/未来的 Web 或 IM** 调用——它是所有网络渠道的公共前提（D2 推荐 A 先行的理由）。即便不做 Web/IM，本地 HTTP+WS 也让 ECode 从「只能人手动开」变成「能被程序调用」（无头模式支点1 的网络版）。

**Q3：模型路由怎么判断任务复杂度？**
A：**不判断**。规则映射按**场景**派模型，不分析 prompt 复杂度：压缩摘要→cheap（摘要不需强推理）、子代理→继承（除非 frontmatter 指定）、全局→default。简单确定，零额外成本。

**Q4：Skill 和自定义命令（支点14）有什么区别？**
A：自定义命令（`.ecode/commands/xxx.md`）是**用户快捷指令**——`/xxx` 把 .md 内容注入对话，简单直接。Skill（`SKILL.md`）是**可复用工作流菜谱**——有 frontmatter（allowedTools/model）、懒加载 catalog、LLM 自动匹配、自动生成。命令是 Skill 的轻量子集；Skill 是更结构化、可被 LLM 自动发现调用的形态。两者文件投放机制同源（支点14 / 支点13）。

**Q5：多渠道并发会不会把 agent 搞乱？**
A：不会。每渠道独立 session（支点6 隔离），同 session 的并发请求排队（绝不两个 runAgentStream 同 session 并发），不同 session 可真并发。会话路由（session-router）保证不串话。

**Q6：CLAUDE.md §4.2 的 React Web 栈到底是不是 ECode 的？**
A：**当前不是**（package.json 无 react-dom/vite/zustand/shadcn）。这是 D2 决策要澄清的：若用户确认「做多渠道 Web 前端」，那套栈就是 Web 工程的技术指引，M6 阶段5 引入；若不做 Web，那段是跨项目模板残留。请用户审阅时明示。
