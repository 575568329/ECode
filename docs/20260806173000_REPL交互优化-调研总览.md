## 三、方向 A：斜杠命令补全

### 现状（本项目）
- `src/ui/input-bar.tsx:3` 注释：「Tab 补全由 App 层处理（suggestions prop 透传），InputBar 只负责文本 + 历史」。
- 但 `InputBarProps` 实际只有 `onSubmit`/`disabled`，**没有 `suggestions`**；`App` 也没传 → 纯未实现的 TODO。
- `src/slash-commands.ts` 已有声明式 `SLASH_COMMANDS` 注册表（8 条），补全的数据源现成。

### 对标（Claude Code）—— 源码实证
> 来源：`D:\Study\claude-code-main\src\utils\suggestions\commandSuggestions.ts`

- **Fuse.js 模糊匹配**（`threshold: 0.3`，偏严格），key 加权：`commandName(3) > partKey/alias(2) > description(0.5)`。
- **双形态补全**：① picker 列表（`SuggestionItem` 带 `displayText/description/tag/metadata`，↑↓ 导航、Enter/Tab 确认）；② **inline ghost 补全**（`getBestCommandMatch` 返回要补的后缀，灰色提示，Tab 采纳）。
- **排序优先级**：精确名 > 精确别名 > 前缀名 > 前缀别名 > 模糊；同分用**使用频次**（`getSkillUsageScore`）打破平局。
- 输入只有 `/`（无后续）时**分类展示**：recently-used(top5) → builtin → user → project → policy → other。
- `hasCommandArgs`：输入里已有空格（带参数）就不再提示——避免在填参时干扰。
- `findMidInputSlashCommand`：还能识别句中（非行首、前导空白）的 `/command`，支持中段补全。
- **Fuse 索引按 commands 数组身份缓存**（commands 由上层 useMemo 稳定），不在每次按键重建。
- 未匹配的 `/xxx` 仍可当普通文本送出。

> ECode 现成数据源 `SLASH_COMMANDS`（8 条，含 name/description）已足够；ECode 不一定上 Fuse.js——前缀匹配 + 别名即可起步（命令少，YAGNI），后期命令变多再引入模糊。

### 技术可行性
- ink **无原生 autocomplete**（官方 `ink-text-input` 的 `<TextInput>` 不带）。
- ink 内置 `<SelectInput>` 可直接做候选列表（支持 ↑↓ + Enter）。
- 落地路径：InputBar 检测 `/` 前缀 → 用 `SLASH_COMMANDS` 过滤 → 输入栏上方渲染 `<SelectInput>` overlay → 选中补全到输入栏（或直接执行）。
- 按键路由：overlay 显示时，`useInput` 焦点从「逐字符输入」切到「列表选择」；需与全局 Esc/Ctrl+C 并存（已有先例：`PermissionDialog` 就是 Modal 独占 useInput）。

### 工作量 / 风险
- 工作量：**中**（纯 UI 层，不动 agent/数据）。
- 风险：**低**（L2 测试可覆盖，`repl-human.test.tsx` 的 `simulate()` 已能驱动 stdin）。

## 四、方向 B：工具结果可展开折叠 ⚠️ 最大技术变量

### 现状（本项目）
- `src/ui/tool-panel.tsx` 有 `foldContent`（per-tool 静态折叠：bash 成功前3行/错误前5行、grep 前3行、read_file 只行数、edit/write 完整）+ `decideToolMode`（≤1 行 Inline / ≥2 行 Block）。
- Block 末尾显示 `... N more lines`，**但按了没反应**——折叠写死，无交互展开。

### 对标（Claude Code）—— 源码实证 ⚠️ 与 ECode 折叠哲学不同
> 来源：`components/CtrlOToExpand.tsx`、`utils/collapseReadSearch.ts`、`tools/MCPTool/classifyForCollapse.ts`

**关键发现：CC 的折叠不是「逐工具裁剪」，是「连续同类合并成一行摘要」。**

1. **全局 `Ctrl+O` 展开**（`app:toggleTranscript` keybinding），**不是逐个工具点击**。
   `CtrlOToExpand` 只负责渲染 `(ctrl+o to expand)` 灰色提示；在子 agent / virtual list 里隐藏（避免噪音）。
2. **`collapseReadSearchGroups`：把连续的 Grep/Glob/Read/Bash-search 合并成一个摘要组**
   （如 "Searched for 3 patterns, reading 2 files"），遇到 assistant 文本 / 非折叠工具（Edit/Write）就断组。
   这是「对一类工具的批量折叠」，粒度比 ECode 单工具裁剪大得多，长任务时体验干净得多。
3. **分类两套**：
   - 内置工具：调每个工具自己的 `isSearchOrReadCommand` 方法（search/read/list/REPL/memory）；
   - **MCP 工具**：`classifyForCollapse.ts` 显式 allowlist（`SEARCH_TOOLS`/`READ_TOOLS`），`normalize` 统一 camelCase/kebab→snake_case，**未知工具不折叠**（保守）。
4. 摘要组还会扫 bash 结果里的 commit SHA / PR URL，surface 成 "committed abc123, created PR #42"——折叠不只减行，还提炼语义。

> **对 ECode 的启示（重要）**：ECode 现状（`foldContent` 逐工具裁剪 + Block 末尾静态 `... N more lines`）和 CC 是两种哲学。
> CC 的「连续合并 + 全局展开」给了 B 一条**比逐块交互展开更可行**的新路径——见可行性路径 0。

### 技术可行性 —— ⚠️ Static append-only 约束（关键）
- `src/ui/chat-view.tsx:82`：`completedMessages`（含 `kind:'tool'`）渲染在 **`<Static>`** 里。
- `<Static>` 语义（chat-view.tsx:2 注释）：「Ink 把已完成项写入 stdout 一次后**不再 diff**」。
- **后果**：工具块一旦完成进 `<Static>` 就被冻结，**事后改它的展开状态不会被重渲染**——和 repl-human 里 `/clear` 清空观测不到是同一约束。
- 所以「展开任意历史工具块」在当前架构下**做不到**。要实现必须改渲染架构，候选路径：
  0. **借鉴 CC：连续同类合并 + 全局 verbose 模式切换**（⭐ 首选方向，由 CC 源码启示）。
     不做「逐块交互展开」，改为：① 在 reducer 层把连续的 Read/Grep/Bash-search 合并成一行摘要（进 Static 前就算好折叠态，折叠本身不受 Static 约束——静态摘要直接写死）；
     ② 加一个全局 `verboseMode` 状态，Ctrl+O 切换时把所有工具按完整模式重渲染。
     难点仍在 ②：全局切换要对已冻结的 Static 项重渲染。**B 详设第一步 PoC 必须先搞清 CC 自己怎么绕过这个约束**——CC 是否也用 ink 的 `<Static>`？还是另有增量渲染/全量重画机制？这是整个方案的最大未知。
  1. **最近 N 条不进 Static**：把最近若干条消息（含工具）留在动态区（可交互展开），老的继续 Static 冻结。CC 大致就是只对近期可见块支持展开。
  2. **展开=复活重画**：展开时把目标工具从 Static 移到动态区重渲染（破坏 append-only，O(n) 回归，复杂）。
  3. **外部 pager**：展开调起 `less`/系统 pager 看全文，不在主流里改（简单但跳出 REPL 体验）。
- 三条路各有取舍，**详设前必须 PoC** 验证哪条可行（尤其路径 1 对滚动/状态/性能的影响）。

### 工作量 / 风险
- 工作量：**大**（受 Static 约束，可能动渲染架构）。
- 风险：**高**（架构变量，需先 PoC 定方案）。

## 五、方向 C：历史对话切换

### 现状（本项目）
- CLI 启动：`--continue`/`-c`（最近）、`--resume <id>`、`--sessions`（列表）——M3 P4 已实现。
- REPL 内：`/sessions` 能列出（`app.tsx:126`），`/resume` 走「尚未实现」分支（`app.tsx:139`）→ **运行时不能切换到历史会话**。

### 对标（Claude Code）—— 源码实证
> 来源：`screens/ResumeConversation.tsx`、`utils/conversationRecovery.ts`、`utils/sessionStorage.ts`

- 是**独立 screen**（`<ResumeConversation>`），用 `<LogSelector>` picker——不是 REPL 内 overlay。ECode 当前 `/sessions` 是 REPL 内纯文本列表，可升级为 picker（与 A 共用组件）。
- 加载两档：**同 repo**（`loadSameRepoMessageLogsProgressive(worktreePaths)`）/ **全项目**（`loadAllProjectsMessageLogsProgressive`），**渐进加载**，还能按 PR 过滤（`filterByPr`）。
- 选中 `onSelect(log)`：`loadConversationForResume(log)` → `switchSession(id, dir)` 切会话 → `restoreCostStateForSession` 恢复 cost → 进 `<REPL>` 继续。
- **跨项目 resume**：`checkCrossProjectResume` 检测，跨项目时把启动命令**复制到剪贴板**（`setClipboard`）而非直接切——避免在错误 cwd 下恢复。
- `forkSession` 模式：不切 session id，而是 `recordContentReplacement` 派生新会话（不污染原会话）。
- 有 loading / resuming 状态、`onCancel → process.exit`。

### 技术可行性
- 数据层齐：`session.ts` 有 `listSessions`/`saveSession`/`loadSession`（MEMORY 记 M3 P4）。
- `/sessions` 已能列出（可复用其格式）。
- 缺：(1) picker UI（可复用 `<SelectInput>`，与 A 方向同款）；(2) 选中后在 REPL 内 resume——把 CLI 层已有的 resume 逻辑（复用 sessionId/messages）提到 REPL 内接线。
- 踩坑预警：MEMORY debugging#007 Session ID 碰撞→UUID，resume 复用 id 时注意；切换前要保证当前未保存会话不丢（先 save 再切换）。

### 工作量 / 风险
- 工作量：**中**（数据层齐，缺 UI + REPL 内接线）。
- 风险：**中**（resume 状态替换，需保证当前会话不丢）。

## 六、方向 D：防假绿（工程实践，非功能）

不走设计文档，落 testing 约定。本次 `/help` 假绿的机理：测试 setup 调了 `enterConversation()`（先发一条普通消息），把「中途使用」前提带进测试，实际没测「一启动就敲 /help」的真实首条场景——**测试名说测 /help，前提却偷换了**。

5 条防范：
1. **从最小前置状态起步**：被测功能尽量从「真实首次」状态开始，setup 越少越接近真实。
2. **每个「首次触发」功能必有零状态用例**：首条即 X（首条命令、首次提交等）都要从零状态测。
3. **写完测试，故意破坏对应代码验红**（mutation 思维）：能为一处 bug 变红才是真测试；怎么改都绿的就是假绿。
4. **测试名诚实反映前置**：`/help 输出` 掩盖了它依赖「已进对话」；应叫 `对话中途 /help` 或拆成首条/中途两条。
5. **L2 之外保留真实冒烟**：`started` 这类「控制渲染分支」的状态机 bug，L2 单测未必覆盖；定期 `npm run dev` 或上 L3 tmux 过核心路径。

**落地建议**：写进 `docs/memory/preferences.md`（本项目 testing 约定）；repl-human 类 L2 测试加一条 review checklist「是否覆盖首条/零状态」。

## 七、优先级建议

| 代号 | 价值 | 工作量 | 风险 | 建议优先级 | 理由 |
|---|---|---|---|---|---|
| **D** 防假绿 | 中 | 小 | 低 | **立即落地** | 约定级，防再犯，零成本 |
| **A** 斜杠补全 | 中 | 中 | 低 | **P1** | 纯 UI、接口已预留、快赢；picker 组件 C 也复用 |
| **C** 历史切换 | 高 | 中 | 中 | **P1** | 核心功能、数据层齐、价值最高 |
| **B** 工具展开 | 高 | 大 | 高 | **P2** | 体验价值高但受 Static 约束，需先 PoC，最后做 |

**推荐顺序**：D（立即）→ A、C（并列 P1，共建 picker 组件）→ B（P2，先 PoC 攻克 Static 约束）。

A、C 共用一个「命令/会话 picker」组件（基于 `<SelectInput>`），建议详设时一起规划组件复用，避免重复造。
