## 0. 总览：三者同属能力扩展面

三者都通过现有 `ToolRegistry` / `CommandRegistry` 接入心脏——**心脏（AgentLoop）完全不感知 skill / mcp / plugin 概念**，契合详设 §2.4 铁律。

```
                 ┌──────────────────────────────────────────────────────┐
                 │            AgentLoop（心脏·零改动）                    │
                 │   反复调 LLM → 执行工具 → 回喂（只认 Tool 接口）        │
                 └────────────────────────────┬─────────────────────────┘
                                              │ ToolRegistry / CommandRegistry
            ┌─────────────────────────────────┼─────────────────────────────────┐
            │                                 │                                 │
   ┌────────▼─────────┐            ┌──────────▼─────────┐              ┌────────▼─────────┐
   │  内置工具（M3）   │            │   SkillTool        │              │  MCP 工具（动态） │
   │  ls/glob/grep/   │            │   (单入口 Tool)    │              │ mcp__svr__tool…  │
   │  read/write/     │            │                    │              │                  │
   │  edit/bash       │            │                    │              │                  │
   └──────────────────┘            └─────────┬──────────┘              └────────┬─────────┘
                                             │                                  │
                                  ┌──────────▼──────────┐        ┌──────────────▼──────────────┐
                                  │  SkillRegistry      │        │  McpManager                 │
                                  │  发现/解析 SKILL.md  │        │  连接/拉工具/生命周期        │
                                  │  蒸馏接入点（S8）    │        │  官方 SDK Client            │
                                  └──────────▲──────────┘        └──────────────▲──────────────┘
                                             │                                  │
                                             └──────────┬───────────────────────┘
                                                        │ 资源来源
                                              ┌─────────▼──────────┐
                                              │  PluginLoader      │  ← 第三部分（容器/分发）
                                              │  marketplace/cache │
                                              │  扫描 → 注入各 Reg │
                                              └────────────────────┘
```

**三句话**：
1. **Skill** = 把"工作流指令"打包成可被 LLM 主动发现的单元（清单注入 system prompt → LLM 调 SkillTool → 拿 body 干活）。
2. **MCP** = 把"外部工具/服务"通过标准协议接入（官方 SDK 连 server → 拉工具 → 注册成 Tool）。
3. **Plugin** = 把"一组 skill/command/mcp 配置"打包，从 marketplace 安装到本地 cache，loader 扫描后分发到各 Registry。

**关键共识**：三者都是**注册成 Tool / Command 进既有 Registry**，loop 的 executeTools / confirm / AJV 路径全部复用，心脏零改动。Plugin 是上层分发容器，**不引入新执行机制**，只多了 marketplace + cache + 清单。

# 第一部分：Skill 系统

## S1. 核心架构：三层渐进式加载（progressive disclosure）

Skill 区别于"直接写一大段 system prompt"的关键是**省 token**：metadata 始终在 context（几十字），body 仅触发时加载（可能几 KB），附属文件按需 `read_file`。这是 claude-code / opencode / codex 三家共识。

```
┌─ Level 0：清单（始终在 system prompt，受 token 预算约束，每条 ≤250 字符）─┐
│  <available_skills>                                                      │
│    <skill><name>commit</name><description>按约定提交…</description></skill>│
│  </available_skills>                                                     │
└──────────────────────────────────────────────────────────────────────────┘
                          │ LLM 匹配 description 自主决定
                          ▼
┌─ Level 1：body（SkillTool 调用后，作为 tool_result 注入一次）──────────────┐
│  <skill_content name="commit">                                            │
│    # commit  生成提交的完整步骤…（markdown，建议 <500 行）                 │
│    附属文件目录：<baseDir>（相对路径基于它，需要时 read_file）             │
│  </skill_content>                                                         │
└──────────────────────────────────────────────────────────────────────────┘
                          │ LLM 按 body 指令用已有工具干活
                          ▼
┌─ Level 2：附属文件（LLM 按需 read_file skill 目录里的脚本/模板）───────────┐
│  ~/.ecode/skills/commit/templates/commit-msg.txt                          │
└──────────────────────────────────────────────────────────────────────────┘
```

---

## S2. 目标 & 验收

**目标**：用户/团队能把可复用工作流写成 markdown（SKILL.md），ECode 自动发现、LLM 按需加载；并为未来"从对话自动蒸馏 skill"预留扩展接口。

**验收**：
- 放 `~/.ecode/skills/commit/SKILL.md`，启动后 system prompt 含其清单项；问"帮我提交"，LLM 自主调 `Skill` 工具加载 commit 指令并执行
- 清单受 token 预算约束（默认 1% 上下文窗），超预算按权重截断（详见 S7）
- 项目级同名覆盖用户级（首个胜出 + LogStore 记 shadowed）
- Skill 不存在 / frontmatter 非法 → SkillTool 返回 `is_error`（recoverable），不崩主流程
- **心脏零改动**：`loop.ts` 不出现 `skill` 字样

**不做**（后置，见附录 C）：`fork` 子 agent、`paths` 条件激活、body 内联 shell、url source、热重载、BM25 检索选 skill。

## S3. 数据结构：SKILL.md 格式

### S3.1 文件布局（只支持目录格式）

```
~/.ecode/skills/commit/
├── SKILL.md          ← 必需：YAML frontmatter + markdown body
├── templates/        ← 可选：附属文件（LLM 按需 read_file）
└── scripts/          ← 可选
```
扫描 glob：`*/SKILL.md`。frontmatter 无 name 时回退目录名。

### S3.2 frontmatter（★ AJV 校验）

```yaml
---
name: commit                       # 必填。正则 ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$，1-64 字符
description: 按约定生成提交信息     # 必填。≤1024 字符。写清"何时用+做什么"，触发命脉
when_to_use: 用户要求 git 提交时   # 可选。触发线索，清单里拼到 description 后
---
# commit
## 步骤
1. 跑测试（bash: npm test）
2. git diff 看改动
3. 按约定格式写 commit message
```

**校验规则**（`SkillFrontmatterSchema`，解析失败 → 跳过 + warn）：
- `name`：正则校验，缺失回退目录名
- `description`：必填 ≤1024，缺失回退 body 第一段（JetBrains 做法）
- `when_to_use`：可选 string
- 未知字段忽略（前向兼容）

**description 写作规范**（抄 skill-creator 共识）：触发可靠性 100% 取决于 description。模型倾向 under-trigger，要写得**稍微"激进"**——"Use whenever 用户提到提交/git，即使没明说 commit"。触发词前置（清单单条截断 250）。**ECode 无关键词匹配器**——description 是唯一可发现性来源。

### S3.3 规范模型

```ts
// src/services/skill.ts
export interface SkillInfo {
  name: string
  description: string             // 清单展示用（截断 250）
  whenToUse?: string
  body: string                    // markdown 正文（去 frontmatter）
  baseDir: string                 // skill 目录绝对路径（附属文件相对它）
  source: 'user' | 'project' | 'plugin'   // 发现层级
}
```

## S4. 流程

### S4.1 发现（多目录分层 + 首个同名胜出）

| 优先级 | 目录 | 用途 |
|---|---|---|
| 1 | 项目级 `<cwd>/.ecode/skills/`（向上遍历到 home） | 团队共享（入库） |
| 2 | 用户级 `~/.ecode/skills/` | 个人习惯 |
| 3 | plugin 级（第三部分，skill 目录由 plugin 贡献） | 第三方分发 |

realpath + name 去重，首个胜出。跨平台：`os.homedir()`、正斜杠、不依赖 shell `~`（AGENTS §2.5）。

### S4.2 清单注入 system prompt

抄 opencode `<available_skills>` XML 块（结构清晰、LLM 解析稳）。**受 token 预算约束**（S7）：

```ts
// core/system.ts
export function buildSystemPrompt(skills: SkillInfo[], ctxWindow: number): string {
  const budget = Math.max(2000, Math.floor(ctxWindow * 0.01))   // 1% 窗口，下限 2000 字符
  const listing = renderSkillListing(skills, budget)            // 超预算按权重截断
  return BASE_SYSTEM_PROMPT + (listing ? '\n' + listing : '')
}
```

### S4.3 触发（SkillTool 工具调用，无关键词匹配）

```ts
// src/tools/builtin/skill.ts
export const skillTool: Tool = {
  name: 'Skill',
  description: '加载某 Skill 的工作流指令。任务匹配 available_skills 某项描述时调用，传其 name。',
  readonly: true,
  input_schema: { type:'object', properties:{ skill:{ type:'string' } }, required:['skill'] },
  async execute(args, ctx) {
    const info = skillRegistry.get((args as {skill:string}).skill)
    if (!info) return { content:`Skill 不存在。可用：${skillRegistry.list().map(s=>s.name).join(', ')}`, is_error:true }
    return { content: [                                  // 抄 opencode：<skill_content> XML
      `<skill_content name="${info.name}">`, info.body.trim(), '',
      `该 Skill 附属文件目录：${info.baseDir}（相对路径基于此目录，需要时用 read_file 读取）。`,
      '</skill_content>',
    ].join('\n') }
  },
}
```

**body 走 tool_result（非注入新 user message）**：复用 loop 现有 `invokeTool` 路径，零侵入。抄 opencode；claude-code 的 newMessages 注入需 loop 特判，违反铁律，不抄。

### S4.4 执行（inline）

LLM 拿 body 后按步骤用已有工具干活。MVP 只有 inline——skill body 是给当前 loop 的指令，不起新 agent。

## S7. Skill 优化（★ v2 补，调研全景）

### S7.1 token 预算（MVP 必做，抄 claude-code）

skill 多了清单会吃 system prompt。MVP 上预算机制（防爆炸）：

```ts
const MAX_LISTING_DESC_CHARS = 250           // 单条 description 硬截断

function renderSkillListing(skills: SkillInfo[], charBudget: number): string {
  // 1. 每条截断到 250 字符（desc + whenToUse 拼接后）
  // 2. 总长超预算 → 按权重截断（MVP 简化：均匀砍每条到剩余预算均分；极端时降级为 names-only）
  // 3. 无 skill → 返回空串（零开销）

```
GLM-5（200K 窗）：1% ≈ 500 tokens ≈ 2000 字符预算，够列 ~20 个 skill。预算由 M5 的 `resolveContextWindow` 提供。

### S7.2 增量推送（MVP 必做，抄 opencode 三态）

system prompt 每轮都发会浪费。MVP 抄 opencode 的 **baseline/update/removed 三态语义**（比 claude-code 的 sent Set 更干净）：
- 首轮发 `<available_skills>` 全量（baseline）
- skill 集合变化才发 update（标注 "supersedes previous list"）
- 实现位置：system prompt 是每轮重算的——MVP 先用"每轮发全量但受预算约束"（简单），M5 压缩落地后若清单成为负担再上增量（加 `lastSentSignature` 对比）。

> **决策**：MVP **暂不做增量**（YAGNI，清单受预算约束已防爆炸），但 `SkillRegistry` 设计成"可计算变化签名"，为增量预留。

### S7.3 base dir 注入（MVP 必做）

SkillTool 返回 body 时注入 baseDir（S4.3 已含）。skill 携带附属文件（templates/scripts）时，LLM 知道相对路径基于哪。抄 opencode。

| `when_to_use` + pushy description 规范 | ✅ | 命中率，S3.2 |

## S8. 扩展性：从对话蒸馏 Skill（★ v2 新增，用户核心关注）

### S8.1 现状：业界无"全自动蒸馏 skill"成熟实现

调研把"会话→skill"的自动化谱系厘清（详见附录 B）：

| 等级 | 机制 | 代表 | 自动度 |
|---|---|---|---|
| L1 全手动 | 自己写 SKILL.md | 所有人 | 0% |
| **L2 半自动起草** | 人触发，agent 访谈+起草+迭代 | **skill-creator**（zcode/codex）、**claude-code `skillify`**（ant-only） | 人触发+确认 |
| L3 自动上下文蒸馏 | forked subagent 周期抽笔记，服务压缩 | claude-code Session Memory | 自动触发（产易失笔记，非 skill） |
| L4 自动记忆蒸馏 | 人触发 `/learn`，抽"非显然发现"写 AGENTS.md | opencode `/learn` | 人触发（产持久 memory，非 skill） |
| L5 全自动 skill 生成 | 轨迹分割+聚类+RL | arXiv 2606.20363（GUI agent） | 全自动（**论文，且未跑赢 frequency baseline**） |

**关键结论**：即便 claude-code 内部最激进的 `skillify`（用户 `/skillify`→agent 读 session memory + 全部 user messages→4 轮 AskUserQuestion 访谈→起草带 when_to_use/allowed-tools/arguments 的 SKILL.md），仍是**人触发 + agent 起草 + 人确认**。中间隔着"判断什么值得存"这道无人解过的坎——全自动方案连论文都没跑通。

### S8.2 memory vs skill：分两层，不合并

| 维度 | memory（MEMORY.md / AGENTS.md） | skill（SKILL.md） |
|---|---|---|
| 载入 | 被动（常驻/检索） | 主动（description 命中才触发） |
| 形态 | 自由随笔、索引+topic | 结构化指令（frontmatter+流程+成功判据） |
| 粒度 | 一条洞察/偏好 | 一个完整可复用工作流 |
| token | 持续占用（故限 200 行/分层） | 元数据常驻、body 懒载 |

**两者配合**：memory 是 skill 起草的**输入原料**（skillify 显式读 session memory + user messages 起草 skill），但**绝不自动升级**（自动升级正确率无保证，会污染 skill 库）。抄 agent-driven_gen 的分层 + opencode `/learn`。

### S8.3 设计：三个正交抽象 + 单一写入入口（为 L2→L5 预留）

把"蒸馏"拆成可插拔的三件，注册点单一化，心脏零改动：

```ts
// src/services/skill/distill.ts（MVP 只实现 S1，接口先定）
/** 蒸馏原料源 —— 可插拔：session / memory / 消息区间 */
interface DistillSource {
  type: 'session' | 'memory' | 'messageRange'
  collect(): Promise<DistillInput>   // { messages, memoryContent, userCorrections }
}

/** 触发器 —— 决定"何时提议蒸馏"。MVP 只有 manual */
interface DistillTrigger {
  shouldPropose(ctx: TurnContext): DistillProposal | null
}

/** 起草器 —— 原料→候选 SKILL.md（LLM 驱动，抄 skillify 4 轮访谈） */
interface SkillDrafter {
  draft(source: DistillInput, opts): Promise<SkillCandidate>  // { frontmatter, body, targetPath }
  evaluate?(candidate: SkillCandidate, testPrompts: string[]): Promise<QualityReport>  // 质量门钩子
}
```

**写入走 `SkillRegistry.install()` 单一入口**（S5）：无论哪一级蒸馏产出候选，都过 AJV 校验 + 去重 + 落盘 + 清单签名失效。心脏永不知"这个 skill 哪来的"。

### S8.4 演进路线（5 步，每步可独立交付）

| 步 | 做什么 | 自动度 | 依赖 |
|---|---|---|---|
| **S8-a MVP** | `ManualTrigger`（`/skill-create` 命令）+ `SkillDrafter`（读当前会话，skillify 式访谈起草）+ `SkillRegistry.install` | 人触发+确认 | 仅 Skill 基础设施 |
| **S8-b** | SessionMemory（抄 CC：post-turn 抽笔记，服务压缩）—— context distillation，**非 skill** | 自动触发 | sub-agent（后置） |
| **S8-c** | `/learn`（抄 opencode：蒸馏"非显然发现"到分层 AGENTS.md）—— 持久 memory 层 | 人触发 | S8-b |
| **S8-d** | `ThresholdTrigger`：检测"同一工具序列/纠正模式重复 ≥N 次"→ 主动提议"固化成 skill？"（AskUserQuestion，仍人确认） | 半自动提议 | S8-b/c 做信号源 |
| **S8-e 远期** | 全自动判断+固化 —— 等 LLM 判断力 + 评估闭环成熟 | 全自动 | 研究突破 |

**S8-a 即可作为 M6 的 Skill 子系统交付物之一**（轻量：一个 `/skill-create` 命令 + Drafter 走访谈）。S8-b 起依赖 sub-agent 能力，后置到独立里程碑。

# 第二部分：MCP 客户端

## M1. 核心架构：Client + Transport + 适配器 + 生命周期

抄 opencode 四件套骨架（TS、最干净），用官方 SDK（三家源码实证）。

```
┌─ McpManager（生命周期编排）──────────────────────────────────────┐
│  servers: Map<name, { client, status, defs }>                    │
│  start(): 并行连所有已配置 server（急连接，容错）                  │
│  stop():  退出时 SIGTERM 子进程 / 关 HTTP                         │
└────────────────────────────┬─────────────────────────────────────┘
                             │ 每 server 一个
              ┌──────────────┴──────────────┐
              ▼                              ▼
   ┌─ stdio Transport ──────┐    ┌─ StreamableHTTP Transport ────┐
   │ spawn 子进程           │    │ POST 到 https://host/mcp       │
   │ stdin/stdout JSON-RPC  │    │ stderr → LogStore              │
   └───────────┬────────────┘    └──────────────┬─────────────────┘
               │ Client.connect（initialize 握手，SDK 内置）
               ▼
   ┌─ tools/list → 适配器（adaptTool）→ mcp__server__tool 进 Registry ┐
   │  execute → client.callTool → isError? recoverable               │
   │  readonly=false（默认确认）/ skipLocalValidate=true（透传）      │
   └──────────────────────────────────────────────────────────────────┘
```

**设计共识**（三家 + 官方规范）：①用官方 SDK，不自研 JSON-RPC；②Transport 用 SDK 的 `StdioClientTransport` / `StreamableHTTPClientTransport`；③适配器把 `tools/list` 翻译成 ECode Tool；④生命周期管理器维护状态表。

## M2. 目标 & 验收

**目标**：配置里声明 MCP server，ECode 连接、拉工具、注册成 `mcp__server__tool`；LLM 像调内置工具一样调它们。

**验收**：
- stdio server（`npx -y @modelcontextprotocol/server-filesystem <dir>`）→ `mcp__filesystem__*` 出现且可调

## M3. 数据结构

### M3.1 配置 schema（抄业界 de-facto `mcpServers`）

配置来源三处合并（优先级：plugin < 用户级 < 项目级，同名项目级覆盖 + warn）：
- **用户级**：`~/.ecode/config.json` 的 `mcpServers`
- **项目级**：`<cwd>/.mcp.json`（团队共享，secret 用 `${ENV_VAR}` 占位符）
- **plugin 级**：plugin 清单的 `mcpServers`（第三部分，基底层）

```ts
export interface McpServerConfig {
  type: 'stdio' | 'http'
  command?: string; args?: string[]; env?: Record<string,string>; cwd?: string   // stdio
  url?: string; headers?: Record<string,string>                                    // http
  enabled?: boolean; required?: boolean; timeout?: number   // 通用，默认 30000
}
```
**`${ENV_VAR}` 占位符**：加载时替换成 `process.env.XXX`，缺失 warn + skip（呼应 AGENTS §5.2 密钥从环境读）。

### M3.2 McpTool 适配（核心，抄 opencode `convertTool`）

```ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js'
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js'
import { StreamableHTTPClientTransport } from '@modelcontextprotocol/sdk/client/streamableHttp.js'

function adaptTool(serverName: string, def: McpToolDef, client: Client, cfg: McpServerConfig): Tool {
  return {
    name: `mcp__${sanitize(serverName)}__${sanitize(def.name)}`,     // 双下划线（事实标准）
    description: def.description ?? `MCP tool ${def.name} (${serverName})`,
    input_schema: def.inputSchema ?? { type:'object', properties:{} },
    readonly: false,                  // ★ 默认确认（第三方不可信），即使 annotations.readOnlyHint
    skipLocalValidate: true,          // ★ 透传给 server 校验（M4.4）
    timeout_ms: cfg.timeout ?? 30_000,
    async execute(args, ctx) {
      const r = await client.callTool({ name:def.name, arguments:args ?? {} }, undefined,
        { signal:ctx.signal, timeout:cfg.timeout ?? 30_000, resetTimeoutOnProgress:true, onprogress:()=>{} })
      return { content: renderContent(r.content), is_error: r.isError === true }
    },
  }
}
```
**`skipLocalValidate`**（Tool 接口新增可选字段）：MCP server 是实现方，最懂参数约束；server 在 callTool 时参数不对返回 isError/JSON-RPC error，走既有 recoverable 路径。且避免 AJV 对 server schema `$ref`/复杂结构的兼容问题。Registry.validate 对 `skipLocalValidate` 工具直接 ok。

### M4.2 连接
```ts
// stdio（抄 opencode，env 合并 + stderr pipe）
const transport = new StdioClientTransport({
  command: resolveCommand(cfg.command!),        // win32: npx 可能需 cmd /c（M6）
  args: cfg.args ?? [], cwd: cfg.cwd, env: { ...process.env, ...cfg.env }, stderr: 'pipe',
})

// http
const transport = new StreamableHTTPClientTransport(new URL(cfg.url!), { requestInit:{ headers: cfg.headers ?? {} } })

await Promise.race([client.connect(transport), timeout(cfg.timeout ?? 30_000)])  // 外包超时兜底
```

### M4.4 调用（isError → recoverable）

> **v3 推迟说明（2026-08-14 用户拍板）**：Plugin 整体推迟 M7。理由见头部 v3 修订记录——范围蠕变（M5 §C 承诺的 M6 是 Skill+MCP）、无作者生态、commands 资源契约不成立、兼容面收窄。本章调研与设计**完整保留**，M7 启动时直接作为输入；届时若需统一装配骨架，回看 ADR-026（暂缓中）。M6 的 M14（plugin 级 .mcp.json）随 Plugin 一起推迟——MCP 部分只做用户级 config + 项目级 `.mcp.json` 两层。

## P1. 核心架构：四件套（marketplace + cache + 清单 + 资源接入）

**Plugin 是"资源容器"，本身不执行**。它把若干 skill/command/mcp 配置打包，loader 扫描后分发到各 Registry。ZCode/Claude/codex 三家共用同一套格式（清单互通），opencode 是异类（进程内 TS SDK，无 marketplace，不适合"第三方发布"场景）。

```
┌─ Marketplace（索引仓库，git clone / zip 下载）──────────────────────┐
│  .ecode-plugin/marketplace.json  { name, plugins:[{name, source, ...}] }│
└────────────────────────────┬────────────────────────────────────────┘
                             │ /plugin install <name>@<marketplace>
                             ▼
┌─ 版本化 Cache（~/.ecode/plugins/cache/<marketplace>/<plugin>/<version>/）┐
│  .ecode-plugin/plugin.json   ← 清单（元数据 + 组件声明）                  │
│  skills/  commands/  .mcp.json  hooks/hooks.json                          │
└────────────────────────────┬────────────────────────────────────────────┘
                             │ PluginLoader 扫描（启用者）
                             ▼
┌─ 资源接入（分发到既有 Registry，plugin 是基底层，优先级最低）────────────┐
│  skills/    → SkillRegistry（source:'plugin'）                            │
│  commands/  → CommandRegistry（命名空间 /plugin:cmd）                      │
│  .mcp.json  → McpManager（mcpServers 合并，自动连接）                      │
│  hooks/     → HookRunner（后置，等 hooks 子系统）                          │
└───────────────────────────────────────────────────────────────────────────┘
```

**与 Skill/MCP 的关系**：skill/mcp/command 是"资源类型"，plugin 是"打包分发载体"。无 plugin 时这些资源也能独立配（`~/.ecode/skills/`、`.mcp.json`）；plugin 价值在于把一组相关资源 + 元数据 + 版本 + 来源 一起安装/启用/卸载。

**★ 巨大红利用**：贴 Claude 的 `.claude-plugin/` 兼容格式，**可直接消费 Claude 官方 marketplace**（285+ plugin，ZCode 已验证可行）。ECode 开局即有生态。

## P3. 数据结构

### P3.1 plugin 清单（`.ecode-plugin/plugin.json`，★ 极简 + 目录约定）

抄 Claude 极简风格（降低作者门槛，零配置可发）：清单只放元数据，组件靠**目录约定**自动发现（`skills/`、`commands/`、`.mcp.json`、`hooks/hooks.json` 存在即扫描）。同时支持显式声明字段（路径字符串/数组）覆盖约定。

```jsonc
// .ecode-plugin/plugin.json（极简约定型，如 context7）
{
  "name": "context7",                       // 必填，正则 ^[a-z0-9][a-z0-9._-]{0,127}$
  "version": "0.1.0",                       // 默认 0.0.0
  "description": "Up-to-date 文档查询 MCP",
  "author": { "name": "Upstash" },
  "license": "MIT"
  // 组件靠目录约定：skills/ commands/ .mcp.json 存在即扫
}
```

```jsonc
// 显式声明型（可选，覆盖约定）
{
  "name": "my-plugin", "version": "1.0.0",
  "skills": "skills",                       // 相对路径（./开头，必须在 plugin 根内）
  "commands": ["commands", "extra-cmds"],
  "mcpServers": { "foo": { "type":"stdio", "command":"node", "args":["${ECODE_PLUGIN_ROOT}/dist/srv.js"] } }
}
```

**字段集**：元数据（name/version/description/author/homepage/license/keywords/dependencies）+ 组件（skills/commands/mcpServers/hooks/agents，可声明或约定）+ 未知字段静默剥离（`.strip()`，容错——作者加自定义字段不致加载失败）。

### P3.2 marketplace.json（市场索引）

```jsonc
// .ecode-plugin/marketplace.json
{
  "name": "ecode-plugins-official",
  "owner": { "name": "ECode" },
  "plugins": [
    { "name": "context7", "description": "...", "version": "0.1.0",
      "source": { "source": "github", "repo": "upstash/context7-mcp", "ref": "v0.1.0", "sha": "30287f5e..." } },
```

**MVP source 两类**：`github`（owner/repo + ref + sha，git shallow clone）和 `url`（zip + sha256，下载解压）。市场内相对路径（`./xxx`）也支持。

## P4. 流程

### P4.1 添加 marketplace
`/plugin marketplace add <github owner/repo | url>` → git clone 到 `marketplaces/<name>/` → 注册进 `known_marketplaces.json`。

### P4.3 资源接入（PluginLoader，启动期 + install 后）

```
对每个 enabled plugin（按优先级）：
```

- uninstall：删 cache + 移 install 记录

### P4.5 优先级与冲突
资源级 first-match-wins：显式配置（用户级/项目级）> plugin（最低）。plugin 永远可被用户覆盖。同名 plugin 身份 = `name@marketplace`。

## P5. 接口

```ts
// src/services/plugin.ts
export interface PluginLoader {
  addMarketplace(source: string): Promise<void>           // github owner/repo 或 url
  install(name: string, marketplace: string): Promise<void>
  enable(name: string, marketplace: string): void
  disable(name: string, marketplace: string): void
  uninstall(name: string, marketplace: string): Promise<void>
  loadAll(skillReg: SkillRegistry, cmdReg: CommandRegistry, mcp: McpManager): Promise<void>  // 启动期扫描接入
  list(): PluginInfo[]                                     // 给 /plugin 命令
}
// /plugin 斜杠命令（list/install/enable/disable/marketplace add/remove）注册进 CommandRegistry
```

## P6. 错误处理 & 安全

**错误**：marketplace clone 失败/install 拉取失败/清单非法 → 拒绝 + warn，不崩主流程；plugin 依赖未启用 → warn 跳过该依赖（MVP 不强制解析）。

**安全**（★ 即使 MVP 也做，plugin 是可信第三方代码、无进程级沙箱）：
1. **官方名预留**：预留 `ecode-plugins-official` 等名，非 ASCII 字符全禁（防 homograph 冒充）
2. **路径穿越净化**：组件相对路径必须 `./` 开头且 `validatePathWithinBase` 验证不逃逸 plugin 根；版本串净化
3. **完整性校验**：marketplace source 带 sha/sha256，安装时校验
4. **占位符限定**：只替换白名单占位符（`ECODE_PLUGIN_ROOT`/`ECODE_PROJECT_DIR`/`user_config.K`），不任意展开
5. **启用提示**：首次 enable 展示"此 plugin 来自第三方，将获得执行能力"（MVP 文本提示，后置信任 UI）

## P7. Plugin 实施拆解

| 步 | 内容 | 依赖 | 心脏 |
|---|---|---|---|
| **P-P1** | `services/plugin.ts`：plugin.json + marketplace.json 解析（AJV）+ 路径穿越净化 | 无 | 零 |
| **P-P2** | PluginLoader：addMarketplace（git clone）/ install（github+url source 拉取到版本 cache）+ sha 校验 | P-P1 | 零 |
| **P-P3** | loadAll 资源接入（skills→SkillRegistry / commands→CommandRegistry 命名空间 / .mcp.json→McpManager）+ 占位符替换 | Skill+MCP 先行 | 零 |
| **P-P4** | enable/disable/unload + config.json `plugins` 状态 | P-P3 | 零 |
| **P-P5** | `/plugin` 斜杠命令（list/install/enable/disable/marketplace add/remove） | P-P4 | 零 |
| **P-P6** | makeDeps 集成（loadAll 在 Skill/MCP Registry 就绪后） | P-P3 | 零 |

**前置依赖**：Plugin 的 P-P3 依赖 Skill（S-P1）和 MCP（M-P2）先行——plugin 贡献的资源要注入这两个 Registry。故实施顺序 **Skill → MCP → Plugin**。

# 决策结论（M6 全部）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **M6-D1** | Skill 触发方式 | LLM 自主调 SkillTool（无关键词匹配） | 三家共识：description 是唯一可发现性来源 |
| **M6-D2** | Skill body 注入 | 作为 tool_result（`<skill_content>`） | 零侵入心脏；抄 opencode |
| **M6-D3** | Skill 文件格式 | 目录 `name/SKILL.md` + frontmatter（AJV） | 目录携附属文件；缺字段回退 |
| **M6-D4** | Skill 发现层级 | 项目级 > 用户级 > plugin 级；首个胜出 | 项目级更具体；plugin 基底层 |
| **M6-D5** | Skill MVP 优化 | token 预算(1%)+250截断+when_to_use+base dir+AJV | 防爆炸+命中率，成本极低 |
| **M6-D6** | Skill 增量推送 | MVP 暂不做（预算约束已够），留变化签名接口 | YAGNI；M5 压缩后视清单负担再上 |
| **M6-D7** | Skill 蒸馏自动化 | **MVP 做 L2 半自动**（`/skill-create` 访谈起草）；L3-L5 后置 | 业界无全自动成熟实现（论文都没跑通）；三抽象+单一写入入口预留 |
| **M6-D8** | memory vs skill | 分两层不合并；memory 可作 skill 起草输入但不自动升级 | 自动升级正确率无保证会污染 skill 库 |
| **M6-D9** | MCP SDK | 官方 `@modelcontextprotocol/sdk@^1.30` | 三家源码实证；API 稳定有参考 |
| **M6-D10** | MCP transport | stdio + Streamable HTTP 都做 | stdio 社区主流；HTTP 接云端 |
| **M6-D11** | MCP 工具命名 | `mcp__<server>__<tool>` | 事实标准；防冲突 |
| **M6-D12** | MCP 工具确认 | 统一默认确认（readonly=false） | annotations 不可信；第三方代码 |
| **M6-D13** | MCP 参数校验 | 透传 server（skipLocalValidate） | server 最权威；避 AJV 兼容问题 |
| **M6-D14** | MCP 配置 | 用户级 config + 项目级 .mcp.json + plugin 级（基底层） | 对齐业界；secret 从 env 读 |
| **M6-D15** | MCP 生命周期 | 急连接（并行容错）+ required 可 fatal + 退出清理 | 抄 opencode + codex |
| **M6-D16** | resources/prompts | MVP 不做（只 tools） | tools 是主价值；另两类后置 |
| **M6-D17** | Plugin 范式 | marketplace + 版本 cache + 清单 + 资源接入（四件套） | ZCode/Claude/codex 共识；可蹭 Claude 生态 |
| **M6-D18** | Plugin 清单格式 | 极简 + 目录约定（贴 `.claude-plugin` 兼容） | 降低作者门槛；**直接消费 Claude 官方 marketplace** |
| **M6-D19** | Plugin MVP 资源 | skills + commands + mcp 配置；hooks/agents 后置 | 后两者需 HookRunner/sub-agent 先就绪 |
| **M6-D20** | Plugin 优先级 | 基底层最低；用户/项目级覆盖 | 用户永远能覆盖第三方 |
| **M6-D21** | Plugin 安全 | 官方名预留 + 路径穿越净化 + sha 校验 + 占位符白名单 | 即使 MVP 也做（第三方可信代码无沙箱） |
| **M6-D22** | 三者与心脏关系 | 都注册成 Tool/Command 进 Registry，loop.ts 零改动 | 契合详设 §2.4 铁律 |
| **M6-D23** | 实施顺序 | Skill → MCP（v3：Plugin → M7） | Plugin 资源接入依赖前两者 Registry；v3 审阅后用户拍板推迟 |
| **M6-D24** | 装配方式（v3 新增） | **不采纳 ADR-026 AppContext 骨架**：MCP/Skill 显式拿 Registry 引用（makeDeps 内 ~20 行分发）；makeDeps 膨胀失控再开新 ADR supersedes | ADR-026 复评结论：M5 后 makeDeps 22 行未膨胀；M6 的装配正是复评预言的轻量形态 |

## B. 调研依据（精炼）

**Skill 优化全景**（各家实现度，详见决策 D5/D6）：
- claude-code：token 预算 1% 窗口（`prompt.ts` SKILL_BUDGET_CONTEXT_PERCENT=0.01）+ 250 截断 + 预算分配 + bundled 不截断 + 增量推送（sent Set）+ paths 条件激活（`ignore` 库）+ fork 子 agent + 内联 shell + `${CLAUDE_SKILL_DIR}` + 热重载（chokidar）
- opencode：增量推送 SystemContext 三态（baseline/update"supersedes previous list"/removed，`guidance.ts`）+ url source 原子更新（staging/backup/swap）+ base dir + 文件采样（FILE_LIMIT=10）
- codex：BM25/词法检索选 skill（`dynamic_skill_selector`，fielded_bm25+RRF，shadow mode）+ 隐式调用检测 telemetry + 热重载（10s 节流）+ skills-lock.json

**Skill 蒸馏**：
- skill-creator（zcode/codex 公开元 skill）：半自动，"draft→测 2-3 prompt→读结果→改进→repeat"迭代环；description 要 pushy（"models tend to under-trigger"）；三层渐进披露；examples beat rules；改进靠泛化+精简非加 enforcement
- **claude-code `skillify`**（ant-only 内部，`src/skills/bundled/skillify.ts`）：用户 `/skillify`→agent 自动读 `getSessionMemoryContent` + `extractUserMessages(getMessagesAfterCompactBoundary)` → 4 轮 AskUserQuestion 访谈（名称描述→步骤大纲参数→逐步骤拆解含**成功判据**→触发时机）→ 写带 when_to_use/allowed-tools/arguments 的 SKILL.md；`disableModelInvocation:true`（只手动）。**仍半自动**
- 蒸馏谱系 L1-L5（见 S8.1）：L3 claude-code Session Memory（context distillation，产易失笔记）、L4 opencode `/learn`（→AGENTS.md 持久 memory）、L5 arXiv 2606.20363（GUI agent 全自动，**未跑赢 frequency baseline**）
- memory vs skill：agent-driven_gen `.claude/agent-memory/`（被动常驻、人维护）vs skill（主动触发、结构化）

**Plugin**：
- **ZCode 本地一手**（`~/.zcode/cli/plugins/`）：marketplaces（git clone）+ cache（版本化）+ data（启用）+ known_marketplaces.json；`.zcode-plugin/plugin.json`（显式声明 skills/commands/mcpServers/userConfig）；**直接装了 claude-plugins-official（285 plugin）**证明清单互通
- claude-code（发源地，`src/utils/plugins/`）：schemas.ts（PluginManifestSchema + MarketplaceSourceSchema 8 种 + PluginSourceSchema 6 种）+ pluginLoader.ts（discovery/cache/install from git/github/git-subdir/npm/local）+ loadPluginCommands/Agents/Hooks + mcpPluginIntegration；plugin 是基底层优先级最低；安全（官方名预留/homograph 防/org 校验/路径净化/allowlist-blocklist/敏感配置 keychain）
- codex（`codex-rs/core-plugins/`）：manifest.rs + marketplace.rs + marketplace_policy.rs + plugin_bundle_archive(zip)；兼容多格式探测
- opencode（反例）：进程内 TS plugin SDK（`define({id,effect})`），无 marketplace/无版本隔离/无安全边界——只适合官方维护 provider，不适合第三方发布

**MCP 协议**（modelcontextprotocol.io）：Anthropic 2024-11 开源（现捐 Linux Foundation）；两类 transport（stdio spawn / Streamable HTTP）；三类原语（tools 主价值 / resources 只读 / prompts 模板）；`tools/list`→`{name,description,inputSchema}`、`tools/call`→`{content[],isError}`（isError 二分契合 recoverable）；跨 server name 不保证唯一→前缀消歧（`mcp__server__tool` 惯例来源）

## C. 开放问题 / 后置项

**Skill 后置**：增量推送（D6）、paths 条件激活、fork 子 agent、内联 shell + `${SKILL_DIR}`、url source、热重载、BM25 检索、**蒸馏 L3-L5**（S8-b~e：SessionMemory/`/learn`/ThresholdTrigger/全自动）。

**MCP 后置**：resources/prompts、OAuth（交互式）、elicitation/MRTR、per-tool 白黑名单、自动重连、`tools/list_changed`、env_clear 高安全选项、**协议演进**（`@modelcontextprotocol/client@2.0` 无状态核心/`server/discover`——持续关注，适配层薄，升级面小）。

**Plugin 后置**：hooks（等 HookRunner）、agents（等 sub-agent）、userConfig 收集 UI、依赖解析 + 跨 marketplace 白名单、git-subdir 部分克隆、企业策略 allowlist/blocklist、autoUpdate + commit sha 比对、安全存储（keychain）。

**里程碑建议（v3）**：**M6 = Skill（S-P1~P6）→ MCP（M-P1~P7）两个子系统**，独立 PR 交付、各自独立验收。Skill 零依赖先发（含 S8-a 蒸馏最小闭环）；MCP 引入外部依赖+子进程+网络。**Plugin（P-P1~P6）→ M7**（本文第三部分保留为设计储备），M7 启动时若需统一装配骨架回看 ADR-026。
