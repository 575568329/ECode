# CC（Claude Code）UI 设计哲学对比与 ECode 借鉴

> 研究对象：CC 源码 `D:\Study\claude-code-main`（React + ink fork + TypeScript + Bun）
> 研究动机：ECode 对标 CC，从 CC 源码提炼终端 UI 的「视觉层级」设计哲学，反过来审视 ECode 的差距
> 研究方法：派 Explore 深挖 CC 的 running / done / streaming 三态渲染组件与颜色处理，逐条拿到 `文件:行号` 证据
> 对标前提：CC 与 ECode 都是 React + ink，渲染模型可直接 1:1 对比

---

## 一、为什么要研究 CC 的设计哲学

ECode 早期的 UI 视觉靠「直觉拍脑袋」——颜色 token 凭感觉选、亮/灰没有体系。CC 作为同类产品（终端 AI agent）的成熟实现，UI 经过了海量用户验证。研究它的源码，**不是为了照抄像素，而是提炼它解决「信息层级」问题的设计哲学**，用来审视 ECode 自己的取舍。

核心命题：**在一个信息密集、状态多变（流式文本 + 工具调用 + 权限审批 + 错误）的终端界面里，如何让用户一眼看到「重要的」，忽略「次要的」？**

CC 的答案体系化在源码里，下文提炼为 7 条哲学。

---

## 二、CC 的 7 条 UI 设计哲学

### 哲学 1：状态信号集中到单一控件（Single Source of Motion）

**原则**：所有「进行中 / thinking / streaming」的动态信号，集中到顶部 spinner 一个控件承担；文本区永远静止、高可读。

**源码证据**：
- `src/components/messages/AssistantTextMessage.tsx:241`——streaming 文本走默认 `text` 色，**不 dim、不变色、不闪烁**。
- `src/components/Spinner.tsx` + `src/components/Spinner/GlimmerMessage.tsx`——spinner 承担 shimmer（sin 波闪烁）、stalled（渐变红）、flash（tool-use 高光）三种动态。
- `AssistantTextMessage.tsx:232`——文本前导圆点也是静态色，不动。

**为什么**：文本是用户要读的内容，任何动态（闪烁/变色）都干扰阅读。把「还在工作」的信号集中到一个小控件（spinner），既传达状态，又不污染内容区。这是**关注点分离**在视觉层的体现：状态归 spinner，内容归文本。

### 哲学 2：亮 / 灰二元法则（Bright vs Dim Binary）

**原则**：视觉权重只有两档——**亮**（已完成 / brand / 正文 / 语义高亮 / bold）与**灰**（进行中 / 辅助 / dim），中间过渡态极少。

**亮档**：
- `claude`（橙 brand）、`claudeShimmer`——spinner、品牌标识
- `text`（白）——助手正文、默认前景
- `success`（绿）/ `error`（红）——完成标记、错误
- `bold`——工具名、关键标签

**灰档**：
- `dimColor`——running 圆点、queued 圆点、等待提示、计时器、token 计数、模式箭头、状态括号、自动授权容器
- `inactive` `rgb(153,153,153)`、`subtle` `rgb(80,80,80)`——非活跃 / 水印

**源码证据**：`src/components/ToolUseLoader.tsx:19,23`——running 圆点 `{color:undefined, dimColor:true}` → done `{color:'success', dimColor:false}`。颜色 + dim **双轴同时切换**，产生明显的亮度跃升。

**为什么**：二元对比是最强的视觉层级信号。人眼对「亮 / 暗」的感知快于「颜色差异」。CC 不靠花哨多色，而靠「该亮的亮、该灰的灰」建立一目了然的优先级。

### 哲学 3：稳定锚点（Stable Anchor）

**原则**：工具名永远 `bold`、永远同色，**不随状态变化**。状态信号只放在前缀指示器（圆点）上。

**源码证据**：`src/components/messages/AssistantToolUseMessage.tsx:200`——`<Text bold={true} ... color={t8}>{userFacingToolName}</Text>`，无条件 bold，running 和 done 一个样。

**为什么**：用户扫视工具列表时，工具名是定位锚点。若工具名随状态闪烁（运行中灰、完成亮），锚点不稳，视线跳跃。CC 让工具名恒定，状态变化只在最左侧小圆点——**动的是配角，主角不动**。

### 哲学 4：bold / dim 互斥（类型层强制）

**原则**：`bold`（强调）和 `dim`（降级）不能同时作用于同一段文本。CC fork 的 `Text` 组件用 TS 类型强制这一点。

**源码证据**：`src/ink/components/Text.tsx`——
```ts
type WeightProps =
  | { bold?: never; dim?: never }        // 都不设
  | { bold: boolean; dim?: never }       // 只 bold
  | { dim: boolean; bold?: never };      // 只 dim
```

**为什么**：「重要的东西（bold）」不该被「降级（dim）」——这是逻辑矛盾（既强调又弱化）。多数代码库靠注释 / 约定，CC 用**类型系统**在编译期杜绝。这是「防御式编程」在视觉层的落地——**让错误用法不可能编译**，而非靠人记。

### 哲学 5：正文永不 dim（Content is Sacred）

**原则**：助手回答的正文，无论 streaming 还是 done，都保持最高亮度（`text` 白），绝不 dim。

**源码证据**：`AssistantTextMessage.tsx` + `src/components/Markdown.tsx:11-15`——`Markdown` 组件支持 `dimColor` prop，但 `AssistantTextMessage` 调用时**不传**（默认 false）。

**为什么**：内容是用户来这里的全部目的。dim 正文 = 降低可读性 = 伤害核心价值。CC 宁可让 streaming 信号完全靠 spinner 承担（哲学 1），也不牺牲正文可读性。这是**产品价值观**在视觉层的体现：内容 > 状态。

### 哲学 6：容器 dim + 内嵌亮色（Dim Wrapper, Bright Accent）

**原则**：次要的上下文容器整体 dim，但容器内的**关键节点**（如成功 ✓）保持亮色。

**源码证据**：`src/components/messages/UserToolResultMessage/UserToolSuccessMessage.tsx:89-93`——
```tsx
<Text dimColor>                                  {/* 外层容器：dim */}
  <Text color="success">{figures.tick}</Text>    {/* 内嵌关键标记：亮绿 */}
  {' Auto-approved · matched ...'}
</Text>
```

**为什么**：自动授权提示是「次要上下文」（不是主线），整体 dim 降低存在感；但「成功」这个结论是关键信号，不能跟着 dim 掉。这是**精细的层级控制**——不是一刀切 dim 整块，而是容器降级、关键节点保留。

### 哲学 7：时间维度渐进降级（Progressive Degradation over Time）

**原则**：长时间无进展时，不硬切换到警告色，而是**渐变**。

**源码证据**：`src/components/Spinner/useStalledAnimation.ts:42-45`——3 秒无 token 触发，2 秒内从橙色 brand 渐变到暗红 `rgb(171,43,63)`（线性插值 `intensity`）；`GlimmerMessage.tsx` 用 `intensity` 在基色与 ERROR_RED 间插值。

**为什么**：硬切换（突然变红）突兀、焦虑感强；渐变传递「紧急程度随时间升级」的连续信号，给用户反应时间。这是**时间维度的视觉反馈**——把「卡了多久」编码进颜色饱和度。

## 四、值得学习并采纳

### 已采纳（#29，本轮）
**哲学 1 + 2**：`src/ui/tool-panel.tsx` 的 `ToolRunning`，工具名从 `T.tool`（黄亮）→ `T.muted`（灰），spinner 留 `T.brand`（青）作唯一亮点。解决「青 spinner + 黄工具名」双亮冲突，回归二元法则。streaming 正文不 dim（本就符合哲学 5）。

### 待评估采纳
- **哲学 4（bold/dim 类型互斥）**：ECode 用的 ink 原生 `Text` 无此约束。可给 `Text` 包一层类型守卫，或 lint / CR 把关。
  - 收益：防止「既 bold 又 dim」的矛盾样式。
  - 成本：中（需改组件类型 + 全量排查现有用法）。
  - 建议：列入 backlog，等视觉层稳定后做。

- **哲学 7（stalled 渐变）**：ECode 的 spinner 当前是纯循环动画，无「卡顿」反馈。加 stalled 渐变能提升长任务体验（用户能区分「卡了」vs「还在跑」）。
  - 成本：中（需 `lastTokenAt` 时间戳 + rgb 插值 + spinner 组件改造）。
  - 建议：作为 spinner 体系增强的候选，单独评估。

- **哲学 6（容器 dim + 亮节点）**：ECode 暂无「自动授权」类次要上下文。未来加自动权限 / 批量操作时，直接套用此模式即可。

## 五、有理由的偏离：不盲目照搬

**哲学 3（稳定锚点）ECode 没照搬**。CC 工具名恒亮 bold，是因为 CC 工具名是 brand 同色系（橙），和 spinner（橙）视觉统一、不冲突。ECode 工具名是 `T.tool`（黄），spinner 是 `T.brand`（青），**两个对比色都亮**会互相抢眼。

所以 ECode 在 running 态把工具名降到 `muted`（灰），只留 spinner 亮——这是**对哲学 2（二元法则）的优先**，牺牲了哲学 3（锚点恒亮）。

教训：**理解哲学「为何」，而非照抄「行为」**。CC 工具名不降的真正原因是「同色系不冲突」，不是「工具名神圣不可降」。ECode 换了配色（青黄双色），就该按哲学的本意（避免抢眼）调整，而非教条地保持工具名亮。

---

## 六、一句话总结

CC 的 UI 哲学浓缩成五个「大于」：
1. **可读性 > 花哨**（正文永不 dim）
2. **稳定锚点 > 频繁变化**（工具名不动，指示器动）
3. **二元对比 > 多色噪声**（亮 / 灰清晰）
4. **渐进反馈 > 硬切换**（stalled 渐变）
5. **类型约束 > 文档约定**（bold/dim 互斥写进类型）

ECode 当前最该补的是 **哲学 4（类型约束）** 和 **哲学 7（stalled 渐变）**；最该守住的是 **哲学 5（正文不 dim）**——这条 ECode 已做到，别在后续优化里无意破坏它。
