## 0. 目标与验收

**目标**：扩展 LLM 的输入通道（图像、全网搜索）+ 配置的可视化修改（不再手编 JSON）。

**验收**：
- **多模态**：`ToolResult` 扩展可选 `blocks` 字段（image block 经 tool_result content 数组回喂——Anthropic 协议原生支持；OpenAI 侧翻译时转移至紧随 user 消息）；`read_file("截图.png")` → 双协议正确翻译 → 模型能描述图片内容；TUI 占位行；压缩序列化不炸；**PDF 同管道**（v1.2 扩入：`read_file("设计稿.pdf")` → document block，模型侧不支持时 is_error 如实回喂）
- **WebSearch（v1.5-v1.7 三层结构，§2 为准）**：`web_search("query")` 返回编号列表（标题/URL/摘要/来源/日期）+ Sources 提醒回喂；**零配置默认注册 bing 层（免费无 key）**；config 配了搜索类 MCP 时内置不注册；zhipu 层 1701/1702/1703 与 bing 层 429/空结果 recoverable；两 provider 均有限额自护（searchFuse，同会话两次失败短路提示）
- **/config 面板**：`/config` 打开三页签面板（搜索模式优先）；常用项可视化改；**未覆盖的键原样保留**（jsonc 非破坏性修改，保注释）；底部永久"打开原始文件"逃生口
- **图片粘贴（P2，2026-08-17 用户反馈定形：Alt+V 键位 + 占位符显示）**：见 §1.2——Ctrl+V 在终端机制上不可行（raw mode 下是 0x16 字面字符，且图片数据不走 stdin），须专用键位主动读系统剪贴板；显示层恒用短占位符
- **后台子进程任务（P3，v1.3 扩入）**：bash `run_in_background` 立即返回 task_id，输出落文件；task_output 增量读取 / task_stop 终止；**统一杀树**（Unix 进程组 / Win taskkill /T /F + SIGTERM→200ms→SIGKILL）——顺带修复现存缺陷：bash 超时单点 kill 导致 npm 类孙进程泄漏；完成通知轮末注入

**不做**（后置）：**视频/音频输入**（v1.2 调研确认维持：四家终端 CLI 无一做视频；音频仅 codex 在 app-server 协议层定义且非默认 modality、aider 的 /voice 是 Whisper STT 转文字而非音频直发——终端 Agent 场景无真实需求，触发=用户明确提出）、Tavily 适配（接口位留，等真实需求）、多模态输出（模型生图）、keychain（用户拍板：key 无法被完全保护，优先级极低，维持观察区）。

## 1. 多模态输入 ImageBlock（P0，~3-4 天）

**问题**：用户想让 ECode 看截图/UI 图/报错截图——模型有视觉能力（GLM-4V 系列），ECode 的管道只传文本。types.ts 从 M1 就留了 ImageBlock 占位，本节把血肉写上。

**流程图（一张图从文件到模型）**：

```
用户：「看下这个截图哪里错了 D:\shot.png」
  │
  ▼
LLM 调 read_file("D:\shot.png")
  │
  ├─ 文本文件（现状路径）：读内容 → TextBlock → ……不变
  │
  └─ 图片（按扩展名/Magic Number 判定 png/jpeg/webp/gif）
        │ 守卫：≤5MB / 格式在支持列表（超限 is_error 提示压缩）
        ▼
      ImageBlock { type:'image', source:{ type:'base64', media_type, data } }
        （与 Anthropic 协议形态完全一致——toAnthropicMsgs 透传零翻译，审阅 P2-3）
        │
        ├─ TUI 渲染：占位行 [图片 D:\shot.png]（终端显示不了图，诚实占位）
        │
        ├─ Anthropic 翻译（tool_result 的 content 数组原生支持）：
        │     { type:'image', source:{ type:'base64', media_type, data } }
        │
        ├─ OpenAI 翻译（tool 消息不支持 image → 转移至紧随 user 消息）：
        │     content parts { type:'image_url', image_url:{ url:'data:…;base64,…' } }
        │
        └─ 压缩序列化（M5 serializeMessage）：ImageBlock → '[图片 shot.png]'
           （摘要不吞 base64——几十 KB 的编码串进摘要只会污染）
```

**详细讲解**：
- **前置接口扩展（v1.1 调研修订，必做第一步）**：ECode 现行 `ToolResult { content: string }` 装不下图。CC 的正路是把 image block 放进 **tool_result 的 content 数组**（Anthropic 协议原生形态）。扩展：`ToolResult` 加可选 `blocks?: ContentBlock[]`，loop 透传进 `ToolResultBlock`（content 从 string 扩展为 `string | ContentBlock[]`）——口径修正为"接口扩展+透传"（与 M9 onBeforeWrite 同级，非逻辑改动）。**OpenAI 侧差异**：chat.completions 的 tool 消息不支持 image——`toOpenaiMsgs` 把 tool_result 内 image 转移至紧随的 user 消息 content parts（`image_url` data URI）
- **入口只有 read_file 路径引用**（MVP 拍板）：`@文件` 语法、终端粘贴、拖拽后置——CC 的三平台粘贴（osascript/xclip/PowerShell）证明可行但每平台一套，MVP 不付；路径引用零新基建
- **格式判定 magic bytes 优先**（CC `detectImageFormatFromBuffer` 同款）：扩展名只做初筛，读缓冲区前 16 字节判真实格式（扩展名可伪造）
- **限制双维守卫**：单图 ≤5MB（取双端点最严——Anthropic 5MB / GLM 系 10MB）+ **≤8000×8000px**；格式 png/jpeg/webp/gif。
- **解析不兜底（2026-08-17 终拍板：链路打通，解析归模型/生态）**：图片的输入/粘贴/缩放/翻译/传给 LLM 这套**搬运链路照做**（本节全部内容），但 ECode **不替用户决定"用哪个模型看图"**——不默认引导切 glm-4.6v-flash、不引导装 8GB 本地视觉模型（v1.6 曾拟"三层推荐"，撤销）。**无视觉能力守卫的提示只说事实与出路**：`当前模型不支持图片输入。可 /model 切换到有视觉能力的模型（自选），或安装图像理解类 MCP server`——选什么模型/装什么 MCP 是用户的决策（对齐"Agent 优先不产品化"：不建推荐基建，生态解决）。调研事实（flash 免费 1 并发 / ollama Qwen2.5-VL-3B 8GB 量化 / <8GB 无体面方案）留调研文档备查，不进产品文案。
- **不做客户端缩放**（观察区，选型 Jimp 已定）：Anthropic 服务端自动缩到 1568px、传大图只浪费流量不加细节，守卫拒绝+提示即可；触发=图片 token 成本痛
- **token 估算**：(w×h)/750（2000×2000 ≈ 5.3k token），计入压缩估算与 /cost
- **模型守卫现实化**（判定机制；文案唯一口径见上"解析不兜底"条）：GLM 视觉是独立模型名（`glm-4.6v`，128K 上下文，另有 FlashX 轻量与 **Flash 免费**版；不支持图/文件/视频混输入）——read_file 读图时 current model 无视觉能力（models.dev 的视觉标记 + 名称后缀双判定）→ is_error，提示文案与"解析不兜底"条完全一致（不点名推荐/不引导本地部署）
- **system prompt 教学**：加一行"read_file 支持图片路径（png/jpeg/webp/gif），用户让你看图/截图时直接读"

### 1.1 PDF 输入（v1.2 扩入，与图片同管道）

**为什么加**：四家 CLI 源码调研（2026-08-16，附录 B）——CC（`document` block 一等公民 + poppler 页渲染兜底）、opencode（`application/pdf` 与图片同走 FilePart 通道）、aider（`pdfs-2024-09-25` beta header + PDF 计入图片扩展名集）**三家都做**，仅 codex 没有。终端场景"读 PDF 设计稿/论文/接口文档"与看截图同级高频；协议层 Anthropic `document` block（base64 source + `application/pdf`）与 image block 完全同构，翻译/压缩/守卫管道复用，增量极小。

- **类型**：`ContentBlock` 加 `DocumentBlock { type:'document', source:{ type:'base64', media_type:'application/pdf', data } }`；判定按扩展名 `.pdf` + `%PDF-` magic bytes（CC 同款校验）
- **守卫差异**：单 PDF ≤32MB / ≤100 页（Anthropic 官方双限）；超出 is_error 提示拆分——**不做页渲染兜底**（CC 的 pdftoppm 路线引入 poppler 外部依赖，MVP 不付，进观察区）
- **模型侧验证关卡（启动后第一件事）**：GLM-4.6V 官方口径**支持 PDF 输入**（调研已核，但不支持与图/文件混输入）——**未实测的是 Anthropic 兼容端点是否透传 document block**；真机验证 glm-4.6v 的 PDF 输入；不支持则 document block 翻译前守卫 is_error 如实回喂"当前模型不支持 PDF 输入"（Anthropic 直连场景仍可用），**不静默降级**
- **压缩序列化**：`'[PDF 文件名]'` 占位（与图片同规矩，base64 不进摘要）
- **OpenAI 侧**：与 image 同款转移至紧随 user 消息（chat.completions content parts 不支持 document——若智谱端点走 openai 协议且有自有 PDF 形态，验证关卡时一并核实）

### 1.2 图片粘贴（P2，2026-08-17 用户反馈定形）

**为什么 Ctrl+V 不行（机制，不是选择）**：raw mode 下终端把 Ctrl+V 传成字面控制字符（0x16）；且图片数据**不经过终端输入流**——文本粘贴走 stdin，图形剪贴板只在系统剪贴板里。读图必须主动调系统 API，必须有专用键位。

**键位：Alt+V = 从系统剪贴板读图**（用户拍板，避开 Ctrl 系与终端自身快捷键冲突）。三平台读取：
- Windows：`powershell.exe -Sta` 脚本内 `Get-Clipboard -Format Image` + `$img.Save(path, [Drawing.Imaging.ImageFormat]::Png)` **落 PNG 文件**（审阅 P2-4：cmdlet 拿不到原始字节，必须脚本内 Save；`-Sta` 仅 powershell.exe 5.1 支持，pwsh 无此开关——显式调 powershell.exe）；存 `~/.ecode/attachments/<sessionId>/paste-<ts>.png`（**会话附件持久目录**——不放 tmp：tmp 随会话清理会断"恢复可读"，审阅 P1-5；目录挂 retention 清理）
- macOS：`osascript` clipboard → PNG（或 pngpaste，二选一调研定）；Linux：`xclip -selection clipboard -t image/png -o`
- 读不到图（剪贴板是文本）：底部一行提示"剪贴板无图片"，不炸不弹窗

**占位符显示（用户建议）**：粘贴成功后输入行/转录显示 `[图片#1 PNG 12.3KB]`——display/content 分离（M6 手动 skill 先例）：content 是 ImageBlock（base64 只进消息本体），display 恒定短占位，长路径/长串永不刷屏。

**协议影响（审阅 P1-4，必做）**：粘贴的 ImageBlock 进 **user 消息 content**（非 tool_result 路径）——① OpenAI 侧 `toOpenaiMsgs` 现状是 `texts.join('\n')` 纯 string，需支持 content parts（`image_url` data URI，CCode message-converter 同款先例）；② Anthropic 侧透传，ImageBlock 形态与协议形态对齐（§1 统一 `source:{type:'base64', media_type, data}`，零翻译）；③ `TuiApp submit(input, display?)` 扩可选 `blocks?: ContentBlock[]` 通道（display 先例只分离显示，本扩展补内容多模态）。

**零键位增强（顺带）**：终端粘贴截图时常贴出临时文件路径（Windows Terminal 行为）——提交的输入文本恰好是存在的图片路径（按 §1 的扩展名/Magic Number 判定）时，底部提示一行"检测到图片路径，已转为图片输入"，直接转 ImageBlock（display 仍是占位符）。

**防超屏**：占位符单行恒定，无动态区膨胀问题（Alt+V 触发时输入行内容不变，仅 notice 一行）。

## 2. WebSearch 工具（P1，~2 天；2026-08-17 拍板改免费优先三层）

**问题**：模型对"最新的库版本/端点行为/新闻"只能猜或靠 web_fetch 碰运气——fetch 需要 URL，不知道 URL 时无路可走。

**三层 provider（2026-08-17 用户拍板：免费零配置为默认，付费/自建全可选；同日三修：DDG 彻底放弃（用户拍板），免费引擎唯一 cn.bing）**：

```
启动时装配（优先级从高到低，命中即止）：
  ① 搜索类 MCP 判定命中 ──► 本地不注册 web_search，
     搜索能力交给 MCP（工具名形如 mcp__xxx__web_search）——已有生态直接用
     判定规则（审阅 P1-9，lazy 连接下启动时不知工具名，只能按 server 判）：
       a) config.webSearch.preferMcp?: string[] 显式声明 server 名（推荐路径）
       b) 未声明时启发式：server 名含 search/web/searxng
       c) 误判后果=两套搜索工具并存、模型自选（无害，写进文档不修）
  ② config.webSearch = { provider:'bing' }（默认，零配置零 key，国内直连可达）──► 注册内置 web_search
  ③ config.webSearch = { provider:'zhipu', engine?, apiKey? } ──► 注册（质量增强项）
```

**内置 Bing 引擎（默认层，免费无 key，2026-08-17 实测定向）**：
- **DDG 路线彻底放弃（用户拍板"DDG 直接放弃，使用 cn.bing.com"）**：实测 `lite.duckduckgo.com` 国内直连 000（GreatFire/维基确认 2014 年起被墙至今），海外场景也不值得为它维护一套 HTML 解析器（npm 生态 duck-duck-scrape 两年未更新）——**不实现 ddg provider**，海外用户走 MCP 或智谱。
- **抓取方式**：`https://cn.bing.com/search?q=<query>&format=rss`——Bing 官方支持 RSS 输出参数，返回**标准 XML RSS**（`<item><title><link><description>`），标准 XML 解析（比 HTML 抓取稳、无 DOM 反爬）；实测 10 条真实结果，中英文混合质量可用、中文 query 正常、裸 curl 无 UA 也 200。**参数局限**：RSS 端点不暴露时间过滤与域名白名单（`recency`/`domain` 降级——模型侧按结果 pubDate 自行判断，domain 在模型侧过滤）。**pubDate 是本地化格式**（实测 `周一, 17 8月 2026…`，非 RFC 822）——**原文透传、代码不解析**（`new Date()` 解析必 Invalid Date，审阅 P2-5）。
- 诚实边界（写进工具结果尾注）：Bing RSS 版权注释限定"个人非商业聚合用途"——个人使用的 CLI 与抓搜索页 HTML 同性质灰色地带，如实声明；重度可能被风控（429/空结果 → recoverable 回喂，提示配 MCP 或 zhipu）。
- 限额自护（命名 `searchFuse`，与 M9 quality 熔断显式区分——审阅 P2-6）：同会话连续两次失败（429/空结果）→ 本会话内工具改返回"建议配置搜索 MCP 或 webSearch.provider=zhipu"（不再打请求；防反复撞墙）

**智谱 provider（可选层，质量增强）**：接口/engine/参数维持 v1.1 已核实规格（`POST /api/paas/v4/web_search`，engine 默认 std ¥0.01/次，同 key 复用回退规则）——从"唯一默认"降为"配置后的高质量选项"。

**公共约束（两 provider 同构）**：工具参数 `query`（bing 层无 70 字符限制，智谱层保留）+ `domain` 白名单 + `recency`（智谱层原生；bing 层降级语义）；结果格式化同 CC 范式（编号列表 标题/URL/摘要 500 字截断 + Sources 尾注）；25s 超时；readonly 免确认；成本透明（bing 层标"免费"，zhipu 层标单价）。

## 3. /config 应用内面板（P2，~2-3 天）

**问题**：`/config` 现状是 explorer/open 打开配置**文件夹**（M4 D11 实施降级形态——原设计 $EDITOR+suspend 因 Ink raw mode 冲突砍掉；Linux 不注册）——看不到结构、不知道有什么可改、改完才发现键名拼错。

**TUI 设计约束（用户拍板：设计好界面，避免太长、避免覆盖不全）——两个问题的解法是同一个：分层 + 非破坏性**：

```
/config 打开面板（PanelShell tabs，←→ 切页签）
  │
  ├─ 页签①「常规」：高频项可视化改
  │    当前 Provider（列表选）→ 模型（该 provider 的 models 列表选）
  │    → temperature / maxTokens / thinking（枚举选，不手敲数字）
  │
  └─ 页签②「Providers」：provider 列表 → 只读详情（v1.1 降级：低频且敏感，
       面板代编收益低风险高——对齐 CC 的克制，它 19 项里也没有 provider 编辑）
       展示 baseURL/apiKey(脱敏)/models + 「打开原始文件」引导改
  │
  └─ 页签③「高级」：兜底覆盖，两层设计
       ├─ 已知高级键（mcpServers/webSearch/hooks/plugin 启用态）
       │  → 只读展示 + 回车复制该键路径到输入框（引导不代编）
       └─ 底部永久项：「打开原始 config.json」（explorer/open 打开文件夹——
          沿用现状，$EDITOR 内联编辑后置观察区，见"即时生效边界"）
  │
  ▼
保存 = jsonc modify 只改目标键（PluginLoader.setEnabled 同款先例）
  ├─ 用户注释原样保留
  ├─ 面板没覆盖的键一个字节不动   ← "覆盖不全"的结构性解药：
  │     面板不需要覆盖所有内容——改常用项，其余键非破坏性保留
  └─ 超长防抖：页签分组 + PanelShell 既有 12 行窗口滚动 + 详情页单键单页
```

**详细讲解**：
- **非破坏性是本节的命根**：面板永远不重写整个 config.json——jsonc-parser 的 `modify(text, path, value)` 只动目标路径（M7 PluginLoader.setEnabled 与 M4 writeWizardConfig 双先例在生产用它保注释），未识别键、注释、格式全部原样。所以面板"覆盖不全"不构成数据风险，只构成便利性梯度——高频项点选，低频项打开原文件
- **搜索模式优先**（CC 范式吸收）：PanelShell 的即时搜索天然就是 CC 专门写的 SearchBox——设置项多时输入即过滤，新人不用逐页翻
- **交互范式**（CC 吸收）：布尔项 = 回车 toggle（开/关）；枚举项 = 回车进子菜单选（PanelShell 列表）；数值项（temperature/maxTokens）= 枚举档位代替手敲（0/0.2/0.5/0.7/1）
- **current 语义澄清（审阅 P2-8）**：面板改 current/模型 = **落盘改 default 键**（持久启动默认）——与 `/model` 的会话临时切换（setConfig 纯内存不落盘）语义并存，面板内注明两者差异；面板保存后 loadConfig 重读，但 **env 覆盖链**（ECODE_MODEL/ANTHROPIC_API_KEY 等）优先级更高会压过文件值——面板检测到相关 env 存在时提示"环境变量覆盖中，文件值不生效"；重读的 throw 路径（NO_API_KEY 等）面板 catch 展示
- **$EDITOR 后置（审阅 P1-6，不重蹈 M4 覆辙）**：M4 原设计 $EDITOR 需 suspend（unmount→spawn→await→remount），当时砍掉；本版逃生口沿用"打开文件夹+打印路径"现状，$EDITOR 内联编辑连 suspend 机制一起进观察区（触发=用户明确要编辑器内改）
- **即时生效边界**：provider/模型/参数改完即生效（下一轮请求读 config 内存态）；提示"重启生效"的场景=改了 config 文件里的结构（面板保存走落盘+重读）
- **与 CC 的差异化**：CC 无逃生口（first-party 封闭配置 19 项）；ECode config 是 jsonc 全量用户领地（mcpServers/hooks/plugins 全在里面）——**保留逃生口 + 非破坏修改**是覆盖不全的结构性解药，维持原设计

## 4. 后台子进程任务（P3，v1.3 扩入；滑 M11 不阻塞）

**问题**（2026-08-16 四家源码调研后扩入，证据见附录 B）：
1. **长命令阻塞轮次**：npm test / build / dev server / 爬虫脚本动辄分钟级，现有 bash 30s 超时直接杀——模型无法"让它在后台跑，我先干别的"。
2. **现存缺陷（顺带发现）**：bash 超时/中断是**单点 kill**（`child.kill('SIGKILL')` 只杀 bash.exe 自己）——`npm test`/`npm run dev` 起的孙进程全部泄漏成孤儿。四家全部实现进程树杀（CC tree-kill / codex 进程组+kill_on_drop+Win Job Object / opencode taskkill /T/F），ECode 缺。

**四家实现形态**（浓缩，一手证据附录 B）：

| 维度 | CC | codex | opencode | aider |
|---|---|---|---|---|
| 后台任务 | `run_in_background` + TaskOutput(offset 增量)/TaskStop + 15s 自动转后台 + Ctrl+B | Unified Exec：`exec_command` 持久 PTY 会话 + `write_stdin`（上限 64 进程） | BackgroundJob 仅子代理（实验）；shell 无后台 | 无 |
| 输出缓冲 | file mode（stdio 直写文件 fd 零 JS 开销）/ pipe mode 8MB 内存→5GB 磁盘 | HeadTailBuffer 1MiB（头 50%+尾 50% 丢中间） | 滑动窗口+溢出落盘 | 内存无上限 |
| 杀树 | tree-kill SIGKILL（无梯度，反面教材） | 进程组 SIGTERM→50ms→SIGKILL；Linux PDEATHSIG；Win Job Object | Unix `kill(-pid)` SIGTERM→200ms→SIGKILL；Win `taskkill /T /F` | 无 |
| PTY | 不用（管道+文件 fd） | Unified Exec 用 portable-pty（ConPTY） | shell 不用；desktop 用 node-pty | pexpect（非 Win TTY） |

**ECode 方案**（P3，~2-3 天）：
- **bash 加 `run_in_background` 参数**：spawn 时 stdio 直写输出文件（CC file mode 同款，零 JS 开销）`~/.ecode/tmp/task-<id>.log`，立即返回 task_id + 输出文件路径 + 提示用 task_output 读
- **TaskRegistry**：内存 Map（id → { child, outputFile, status, exitCode, startedAt }）+ 会话结束/退出 cleanup 全杀；并发上限 8（codex 64 过宽，MVP 收紧）
- **task_output 工具**：`offset` 增量读（CC getTaskOutputDelta 语义：返回新内容 + newOffset，不加载全文件）+ 可选 `wait_ms` 短等待（等新输出或退出）
- **task_stop 工具**：杀任务（走统一杀树）
- **完成通知（双时点，审阅 P1-7——afterTools 是 iter 级非 turn 末，turn 结束后完成的任务没有 afterTools 可挂）**：
  1. **turn 内**：各 afterTools 检查点——本轮启动且已结束、模型尚未读过的任务，feedback 通道注入 user 文本摘要（`[task] #2 npm test 已完成 exit 0`，与 quality 回喂同通道——M9 偏差②先例）
  2. **跨 turn**：下次 submit 前（TuiApp submit 入口/runLoop 启动前）检查 pendingTaskNotifies——turn 结束后（runningRef 已 false）任务才完成的场景，下次运行前注入
- **统一杀树（已先行落地 2026-08-16：killTree 进 proc.ts，bash/hooks 四路径接入，真实孙进程树测试锁定；出生窗口枚举竞态用杀后复查缓解）**：Unix `detached:true` + `process.kill(-pid)`；Windows `taskkill /PID <pid> /T /F`（opencode 同款，KISS 不上 Job Object）；梯度 SIGTERM→200ms→SIGKILL（给编译进程清理机会；CC 无梯度直接 SIGKILL 是反面教材）
- **治理**：输出文件随会话 tmp 清理；沙箱 blockedCommands/full-access 黑名单同样适用后台命令；**与 M9 checkpoint/rewind 的交互（审阅 P1-8）**：启动时近修改集兜底只覆盖当时已 dirty 的文件，后台任务**之后**改的干净文件无快照（盲区）——**任务完成时对输出涉及文件补拍一次快照**收口；/rewind 面板对"有活跃后台任务"扩展 M9 运行中守卫（确认禁用+提示先 task_stop）

**不做**（后置观察）：PTY 持久交互会话（codex 路线：ConPTY/交互式命令支持重基建；ECode "bash 不支持交互命令"的心智不变）、shell snapshot（CC/codex 的 rc 快照——ECode 是 Git Bash `-c` 每命令新进程（opencode 同款参数注入），Windows 环境 rc 定制价值低）、auto-background 15s / Ctrl+B 手动转后台（运营级特性）、Job Object / PDEATHSIG 硬防护（M12+ 按需——taskkill /T /F 已覆盖主场景；**触发条件新增**：先行落地时实证 taskkill /T 树枚举在进程出生窗口（三层树 bash→中间 sh→node 刚 fork 时）偶发漏最深子进程，杀后 100ms 复查已缓解但孤儿漏网仍需 Job Object 的创建即入组语义才能根治）。
