## 1. P0-A：Ctrl+C 立即停——signal 传参修复 + 流中断

### 1.1 根因（已实证；v1.0 归因证伪留痕）

**真根因是两层叠加，都不在 loop**：

1. **signal 传参位置 bug（主断点）**：`src/providers/openai.ts` 的 `create({ ...req字段, ...(req.signal ? { signal: req.signal } : {}) })` 把 signal 混进 **body 形参**；openai v7 签名是 `create(body, options?)`，signal 合法位置是**第二参** `RequestOptions.signal`（completions.d.ts:56-58 / request-options.d.ts:56）→ **signal 从未传给 fetch**，还以 `"signal":{}` 污染请求体 JSON 发给服务器。五组对照实验（`$TEMP/abort-repro/`，openai@7.4.0 + 慢滴 SSE 服务器，可复跑）：signal 放第二参 → abort 后 **4ms** 流退出 + TCP 立即断；放 body（= ECode 现状）→ 101 chunks 全收跑满 31s、TCP 不断；裸 fetch（无 SDK）正确传参 → 头返回后 abort 8ms 内 body reject + 服务器立即 disconnect。**v1.0 所称「fetch 规范：响应头返回后 abort 不取消 body 流」因此证伪**——undici 行为正常，复现脚本照抄了 ECode 的传参错误，复现的是 bug 症状。
2. **SDK 吞 AbortError（静默形态）**：openai v7 streaming.mjs 显式吞 AbortError 静默退出（"controller.abort() → exit without throwing"）——即便 signal 到位，错误也不上抛，for-await 正常收尾。loop 的 signal 检查（迭代顶部/流末）全排在流结束之后。

**真机日志印证**：三次 Ctrl+C 按压（17:46/17:52/17:53），daemon received 12-33ms 到达、controller 确实 abort（stopReason:aborted 证明 loop signal 置位），收敛 2.692s / 54.070s / 33.841s——三次的 stop 都与该次 LLM 调用 usage 落地相隔 3-5ms（iter12/iter8/iter1 三处一致）：流自然跑完，loop 才轮到检查。最坏情形 = 188.042s 慢响应（iter2 request→usage，output 仅 80）整段不可中断。

**边界澄清**：此前怀疑的「审批挂起 D9 不收敛」「双轮并行残留」是叠加因素（已各自硬化：session.ts controller 集合化 + loop 迭代顶部检查，198ed5f 已提交），主断点是传参 bug。

### 1.2 修复设计（四件，按序）

1. **signal 挪第二参（一行，首动作）**：`create(body, { signal })`。免费获得：**静默流（零 chunk 挂死）场景 Ctrl+C 立即停**（该场景逐 chunk 检查没有执行机会，v1.0 无解）；abort 真正解除挂起的流读（4ms 级）；顺带消除 `"signal":{}` 请求体污染（严格端点可能 4xx）。**压缩链盲区自动覆盖**：summarize.ts:218 独立 for-await 不走 loop 循环，逐 chunk 检查够不着，signal 传对才能救。
2. **loop.ts 流内逐 chunk 硬检查（第二道保险）**：`for await` 循环体顶部 `if (signalAborted(opts.signal)) { isAborted = true; break }`。break 走既有 isAborted 固化路径（loop.ts:326→342-351→453-474 全链走查通畅：部分产出落盘、占位 tool_result 配对、stopReason:aborted）。**无需任何手动关闭面**——三层结构实验（SDK→provider generator→消费者，ECode 同构）证明消费者 break 时两 SDK 均自动 abort/cancel（openai streaming.mjs:75-79 finally / anthropic MessageStream 迭代器 return() 自动 abort），服务器立即 disconnect；v1.0 的「break 后对流对象调关闭面」主张撤销（`response.body?.cancel()` API 亦不存在）。anthropic 线同加检查（belt-and-braces 统一口径）。
3. **TUI「中断中…」本地即时提示**（挂账项）：两处入口都置（TuiApp useInterrupt / F-31 卡上 Ctrl+C）；生命周期复用 interruptedAtRef 丢帧门 + turn/started 复位语义；顺带半句「部分产出已保留」——中断轮的半截产出会合成占位 tool_result 固化进上下文参与后续轮，让用户知情。daemon 因故障无停止帧时提示常挂（可接受）。
4. **loop.ts:323-326 注释随翻案修正**：openai 线「流静默正常收尾」的真因是 signal 未达 fetch + SDK 吞 AbortError；anthropic 线是抛 APIUserAbortError，两线行为不同，不再混述。

**取舍明示（usage 漏账扩大化）**：现状 abort 后流自然跑完还能拿到 usage（诊断日志「stop 与 usage 相隔 3-5ms」即证）；逐 chunk break 后 generator return() 跳过 flush → **中断轮 usage 永不上报**（usage 恒在流末）。Ctrl+C 是高频操作，M12 token 统计的漏账面从「偶发」变「常态」。接受此取舍（中断及时性 > 中断轮计费精度），记台账；如需补救后续可从 daemon 侧 rough-estimate，不在本方案。

### 1.3 测试与验收

- **单测（形态陷阱！）**：现有 AbortRealProvider/SilentAbortProvider 两个模板**都自己监听 signal**——测不出真机根因形态（provider 不响应 signal、按自己节奏吐流）。必须新写**不 addEventListener 的慢滴 provider**（`await sleep(20)` × 50 delta，约 15 行），中途 abort 断言：runLoop 总时长 <300ms（而非 50×20）、acts 含 aborted、部分 text 固化。
- **哨兵入库**（`scripts/abort-stream-probe.mjs`，由 abort-repro 改造，30-60min）：client 侧 **signal 放第二参**（锁死正确传法，防 bug 回归）+ 断言「abort 后 ≤2s 迭代终止且 chunks 未收满」+ catch 分支 APIUserAbortError 计 PASS；server 侧加 **socket 级计数断言**（`server.on('connection')` 计数 + 断开时刻戳，输出「abort 后 N ms socket 断开」——修掉 v1.0 靠 `req.on('close')` 时序巧合的推理链；这也是「止损端点生成」唯一能证明修了的门）。失败 exit 1，CI 外手动档。
- **真机门**：interrupt_latency_probe 计时——**配对规则：received 之后首个 turn_finished**（自然结束也发 turn_finished，09:58:46 孤立一条实证，直接取最后一条会配错）；活跃流期按压收敛 ≤1s。注意该门**依赖第 1 件修复**（逐 chunk 检查的时延 = 下一 chunk 间隔，深思考模型 chunk 间隔可 >1s；signal 修对后 abort 直接解除挂起 4ms 级）。探针扩场景：pty 写 `\x03` 触发（overscreen 探针已有写输入能力）。

估时：0.5 天（含双 provider + 测试 + 哨兵）。

## 2. P0-B：LLM 流停滞看门狗（挂账③，用户已拍板「先记录后实施」）

### 2.1 根因

LLM 请求**无任何超时机制**（仅审批 15min + MCP 单调 30s）。连接黑 hole 或端点长时间不吐字时永远挂着；且静默流场景 P0-A 的逐 chunk 检查没有执行机会——signal 传参修复（P0-A 第 1 件）是本看门狗的地基：stall abort 必须真正到达 fetch 才能解除挂起的流读。

### 2.2 修复设计

- **触发条件**：流内**零内容性 delta**（锚点 = text/thinking/tool_use_delta 三类；**不能按协议 chunk 重置**——空 keep-alive 帧/SSE 注释行会假喂狗，anthropic ping 事件与 openai finish chunk 都可能零 Delta。智谱端点保活形态未核验，真机门补抓包确认）持续 `streamStallMs`（默认 90000，0=关闭）。
- **触发动作（关键修订）**：stall timer 回调 → abort 流 + **显式 yield `{type:'error', code:'STREAM_STALL', recoverable:true}` delta**。不能只 abort signal：openai SDK 吞 AbortError 静默收尾（loop 视角=正常结束，无从重试）；anthropic SDK 把 AbortError 转 APIUserAbortError 抛出 → 被误判为用户中断。显式 error delta 才能让重试语义成立，且 loop 的 isAbort 判定（查用户 signal）天然不受污染。
- **重试约束（防黏连污染）**：**仅「零产出 stall」自动重试 1 次**——stall 前已 yield 任何内容性 delta（半截 text/半截 tool JSON 已被消费方累积）时直接报错，否则透明重发会把「半截+完整重答」黏成一条 assistant 永久固化进 history（provider.run 共 5 个消费点全中：主循环/子代理/审查卡/压缩摘要/蒸馏），且已生成 output 白付双计费。零产出约束下无此问题（KV 缓存下重发 input 大概率命中 cache，成本可控）。**重试前必查 `req.signal.aborted`**（用户已按 Ctrl+C 则放弃，防「明确中断后系统又自发一次请求」）。
- **二次 stall**：标 `retryable:false` 走既有 no_retry 温和终止（loop.ts:395-406）——stall 是端点/网络级故障，回喂模型自纠无意义，且与空响应轮防重试风暴哲学（loop.ts:438-447「不自动重试，重试由用户发起」）一致。
- **叠加总账（写明）**：主链 loop 层已有 MAX_RETRIES=3 指数退避——provider 内重试 1 次 + loop 层 retryable 放行，最坏 4 轮 × 每轮 2 次请求 = 8 次请求。重试放 provider 层（而非复用 loop 链）的理由：压缩摘要流（summarize.ts:218）与子代理链也直接受益，它们不走 loop retry。
- **实现细节**：`AbortSignal.any([req.signal, stallSignal])` 组合（Node 22 实测存在、组合语义正确、不反向污染用户 signal）传第二参（依赖 P0-A 第 1 件）；stall timer 在 run() finally 清掉（anthropic.ts:277-280 摘 listener 是现成先例）。
- **config**：`streamStallMs` 三处齐改（ConfigFile 接口 + loadConfig 透传 + CONFIG_TEMPLATE——`sessionIdleMinutes`/`approvalTimeoutMs` 曾因漏磁盘接口成死键）；键注释写明默认 90s / 0=关闭，及「非流式 thinking 端点（reasoning 憋到尾部才吐）可能误杀，可调大或关闭」逃生指引。
- **可见性**：TUI 活动行「响应停滞，已重试/已中止」；**web/飞书端走 onWarn 链路出等效提示**（C4 已有 warn 渲染），否则 web 用户只见流卡 90s 后凭空重来。审批 15min 超时与 watchdog 阶段不同（工具期 vs 流期），无交互。

### 2.3 测试与验收（mock 通路先拍）

**通路二选一（实施第一步拍板）**：(a) 把 run() 的流消费循环抽成纯异步函数（喂 `AsyncIterable<chunk>`，与 translateOpenaiStream 抽法同款、本仓风格）——fake timers 推进 mock 流与 watchdog 计时器均干净可行（**推荐**）；(b) `vi.mock('openai')` 注入假 stream——此时不建议 fake timers（SDK 内部调度），改注入短阈值真 timer（streamStallMs=200ms，测试总长 <1s）。

用例：零产出 stall → 90s 触发重试 1 次后成功；二次 stall → `retryable:false` 温和终止；慢滴流（delta 间隔 < 阈值）不误杀；**有产出 stall → 直接报错不重试**（断言无第二次请求且 error 上抛）；重试窗口期用户 abort → 放弃重试走中断路径。真机门（拔网线/断端点不永挂）人工档。

估时：0.5-1 天。

## 3. P1-A：TUI 客户端 RSS 膨胀——live 链路全面增量化 + heap 可见性

### 3.1 根因（多热点，非单点）

真机对照：客户端 1.15-1.3G vs daemon 118MB vs 转录 258KB——与数据量无关的渲染堆膨胀（同机此前 245MB→1.8G 同签名）。核验坐实的热点按烫度排序：

1. **live 文本折叠**：`GrayStreaming` → `foldStreamText` → `foldLines` 对**全文**逐逻辑行 wrap-ansi（该路径无缓存，ToolLine 的 foldCache 管不到）；wrap 在 slice 切窗**之前**——头部 wrap 纯浪费。16ms 合帧在 delta 间隔 25ms（40/s）时几乎不合帧，重渲频率≈delta 到达率（上限 62.5/s）；TextEntry memo 对 live 条目恒 miss（timeline reducer 每 delta 产生新 text 引用）。O(n²)。
2. **thinking 摘要路径（更烫）**：thinking 帧不走 16ms 合帧直接 setActive（TuiApp.tsx:656-658）；activityDetail 每帧对思考**全文** `Array.from` 码点数组化（数万字→几十万元素数组）再取尾 2000（:1833-1841）；stripUntrustedAnsi 尾段全量扫描；80ms spinner tick 常驻放大。**只修折叠压不住长思考会话。**
3. **ToolLine 每帧重渲**：TimelineView 每帧手工重建 tool 字面量对象（:123-139）破坏「未动条目引用恒等 → memo 生效」设计锚；ToolLine 自身无 memo——delta flush 期间每个可见工具条目每帧重跑 strip/preview/digest。
4. **reducer 全量拷贝（台账不修）**：`text: last.text + ev.text` 每帧整份新全文（25KB × 40/s ≈ 1MB/s 分配）。侵入性大（需分块累积结构），记诊断台账靠 heapUsed 验证占比，本批不动。

终态 Markdown 路径已核验干净（ink Static 只对新增条目调 children + TextEntry/Markdown 双层 memo + seal 保留引用）——不修。

### 3.2 修复设计

1. **live 折叠增量化 + 尾行退化场景**：逻辑行内容不变则 wrap 结果不变——`foldStreamText` 增 cache 参数（调用方 useRef 持 `{lines, wrappedCount, width}`），每 delta 只 split 逻辑行（快路径：新增段 `indexOf('\n')` 无换行零 split）后对新增行 wrap，头部复用缓存；resize（width 变）整体失效重算。**尾行超宽退化修正（必选其一）**：(a) 尾行「稳定物理行前缀」缓存——wrap-ansi hard/trim:false 贪心断行下已产出物理行不受后续 append 影响（灰字已被 stripper 净化无 ANSI），每帧只重 wrap 尾部未满段，需单测钉住「追加不影响前缀」防 wrap-ansi 版本漂移（**推荐**）；(b) 尾部行倒推截断（行尾 `(maxLines+1)×width+slack` 字符处截断再 wrap，接受首行边界近似）。
2. **thinking 路径**：尾取改字符串 `slice(-2000×N)` 按 `\n` 边界截断（消 Array.from 全量码点化）；thinking 帧并入 16ms 合帧缓冲。
3. **ToolLine 引用恒等**：TimelineView 直接透传 `e.tool`（补齐 ActiveTool 形状）+ ToolLine memo 包裹。两行级。
4. **顺手项**：Markdown.tsx AnsiText 的 wrapAnsi 加 memo（终态重渲脆弱点）；FoldedUserInput 复用同一 cache 参数。
5. **heap 可见性（强化）**：与 rss 同钩子采样 heapUsed（合并为单个 state 对象一次 setState，避免双 5s tick 双份整树重渲）；**单 heapUsed 判别力不完备（含未回收垃圾）**——/doctor 加强制 GC 对照档（`--expose-gc` + `global.gc()` 后采样），rss/heapUsed/external 三值趋势对照才是「活对象泄漏 vs 垃圾未收」的判别器。显示面走 /doctor，不进 StatusBar（宽度+牺牲序都会吃掉）。

### 3.3 测试与验收
