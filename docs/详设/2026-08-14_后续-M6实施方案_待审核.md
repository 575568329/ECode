## 0. 总览：三者同属能力扩展面

三者都通过现有 `ToolRegistry` / `CommandRegistry` 接入心脏——**心脏（AgentLoop）完全不感知 skill / mcp / plugin 概念**，契合详设 §2.4 铁律。

```
                 ┌──────────────────────────────────────────────────────┐
                 │            AgentLoop（心脏·零改动）                    │
                 │   反复调 LLM → 执行工具 → 回喂（只认 Tool 接口）        │
                 └────────────────────────────┬─────────────────────────┘
                                              │ ToolRegistry / CommandRegistry
            ┌─────────────────────────────────┼─────────────────────────────────┐
            │                                 │                                 │
   ┌────────▼─────────┐            ┌──────────▼─────────┐              ┌────────▼─────────┐
   │  内置工具（M3）   │            │   SkillTool        │              │  MCP 工具（动态） │
   │  ls/glob/grep/   │            │   (单入口 Tool)    │              │ mcp__svr__tool…  │
   │  read/write/     │            │                    │              │                  │
   │  edit/bash       │            │                    │              │                  │
   └──────────────────┘            └─────────┬──────────┘              └────────┬─────────┘
                                             │                                  │
                                  ┌──────────▼──────────┐        ┌──────────────▼──────────────┐
                                  │  SkillRegistry      │        │  McpManager                 │
                                  │  发现/解析 SKILL.md  │        │  按需连接/工具缓存/状态机     │
                                  │  蒸馏接入点（S8）    │        │  官方 SDK Client            │
                                  └──────────▲──────────┘        └──────────────▲──────────────┘
                                             │                                  │
                                             └──────────┬───────────────────────┘
                                                        │ 资源来源
                                              ┌─────────▼──────────┐
                                              │  PluginLoader      │  ← 第三部分（容器/分发，M7）
                                              │  marketplace/cache │
                                              │  扫描 → 注入各 Reg │
                                              └────────────────────┘
```

**三句话**：
1. **Skill** = 把"工作流指令"打包成可复用单元，**双触发面**：LLM 按清单 description 自主调 SkillTool 换取 body；用户在输入框 `/skill-name 参数` 手动触发展开。
2. **MCP** = 把"外部工具/服务"通过标准协议接入（官方 SDK 按 lazy 连 server → 工具清单入缓存 → 注册成 Tool → 首次调用才真正连接）。
3. **Plugin** = 把"一组 skill/command/mcp 配置"打包，从 marketplace 安装到本地 cache，loader 扫描后分发到各 Registry。

**关键共识**：三者都是**注册成 Tool / Command 进既有 Registry**，loop 的 executeTools / confirm / AJV 路径全部复用，心脏零改动。Plugin 是上层分发容器，**不引入新执行机制**，只多了 marketplace + cache + 清单。

# 第一部分：Skill 系统

## S1. 核心架构：三层渐进式加载（progressive disclosure）

Skill 区别于"直接写一大段 system prompt"的关键是**省 token**：metadata 常驻 context（几十字），body 仅触发时加载（可能几 KB），附属文件按需 `read_file`。

```
┌─ Level 0：清单（始终在 system prompt，受 token 预算约束，每条 ≤250 字符）─┐
│  <available_skills>                                                      │
│    <skill><name>commit</name><description>按约定提交…</description></skill>│
│  </available_skills>                                                     │
└──────────────────────────────────────────────────────────────────────────┘
                          │ LLM 匹配 description 自主决定
                          ▼
┌─ Level 1：body（SkillTool 调用后，作为 tool_result 注入一次）──────────────┐
│  <skill_content name="commit">                                            │
│    # commit  生成提交的完整步骤…（markdown，建议 <500 行）                 │
│    附属文件目录：<baseDir>（相对路径基于它，需要时 read_file）             │
│  </skill_content>                                                         │
└──────────────────────────────────────────────────────────────────────────┘
                          │ LLM 按 body 指令用已有工具干活
                          ▼
┌─ Level 2：附属文件（LLM 按需 read_file skill 目录里的脚本/模板）───────────┐
│  ~/.ecode/skills/commit/templates/commit-msg.txt                          │
└──────────────────────────────────────────────────────────────────────────┘
```

用户手动触发（S4.4）跳过 Level 0 匹配直接进 Level 1：body 展开为 user 消息。

## S2. 目标 & 验收

**目标**：用户/团队能把可复用工作流写成 markdown（SKILL.md），ECode 自动发现；LLM 按需加载执行，用户可斜杠手动触发并传参；并为"从对话蒸馏 skill"提供创建/升级的单一入口。

**验收**：
- **LLM 面**：放 `~/.ecode/skills/commit/SKILL.md`，启动后 system prompt 含其清单项；问"帮我提交"，LLM 自主调 `Skill` 工具加载 commit 指令并执行
- **手动面**（v4）：敲 `/commit 修复登录 bug` → body 展开（`$ARGUMENTS` 替换；无占位符则末尾追加 `ARGUMENTS: …`）作为 user 消息注入并立即触发一轮；`/` 补全里 skill 与内置命令合并列出
- **SkillPanel**（v5）：`/skill` 面板列出全部手动可用 skill（分组+搜索），Enter 回填 `/skillname ` 到输入框
- **触发面开关**（v4）：`user-invocable: false` → 不进 `/` 补全、直接敲拦截提示；`disable-model-invocation: true` → 不进 LLM 清单，SkillTool 调用返回 is_error
- 清单受 token 预算约束（默认 1% 上下文窗），超预算按权重截断（详见 S7）
- 项目级同名覆盖用户级（首个胜出 + LogStore 记 shadowed）
- Skill 不存在 / frontmatter 非法 → SkillTool 返回 `is_error`（recoverable），不崩主流程
- **升级合并**（v4）：对已有 skill 再 install 走升级模式——versions 备份 + section 级合并 + 冲突预览（S8.3）
- **心脏零改动**：`loop.ts` 不出现 `skill` 字样

**不做**（后置，见附录 C）：`fork` 子 agent、`paths` 条件激活、body 内联 shell、url source、热重载、BM25 检索选 skill、`$1`/命名参数占位符。

## S3. 数据结构：SKILL.md 格式

### S3.1 文件布局（只支持目录格式）

```
~/.ecode/skills/commit/
├── SKILL.md          ← 必需：YAML frontmatter + markdown body
├── templates/        ← 可选：附属文件（LLM 按需 read_file）
├── scripts/          ← 可选
└── versions/         ← 可选：升级备份（install 升级模式自动生成，上限 10 版）
```
扫描 glob：`*/SKILL.md`。frontmatter 无 name 时回退目录名。

### S3.2 frontmatter（★ AJV 校验）

```yaml
---
name: commit                       # 必填。正则 ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$，1-64 字符
description: 按约定生成提交信息     # 必填。≤1024 字符。写清"何时用+做什么"，触发命脉
when_to_use: 用户要求 git 提交时   # 可选。触发线索，清单里拼到 description 后
user-invocable: true               # 可选，默认 true。false → 不进 / 补全（仅 LLM 可调）
disable-model-invocation: false    # 可选，默认 false。true → 不进 LLM 清单（仅手动）
---
# commit
## 步骤
1. 跑测试（bash: npm test）
2. git diff 看改动
3. 按约定格式写 commit message，主题可带 $ARGUMENTS
```

**校验规则**（`SkillFrontmatterSchema`，解析失败 → 跳过 + warn）：
- `name`：正则校验，缺失回退目录名
- `description`：必填 ≤1024，缺失回退 body 第一段
- `when_to_use`：可选 string
- `user-invocable` / `disable-model-invocation`：可选 boolean，默认 true / false——两个布尔独立控制两个触发面，四个组合都合法（如"仅 LLM"「仅手动"「两面都开"「两面都关=休眠"）
- 未知字段忽略（前向兼容）

**description 写作规范**：触发可靠性 100% 取决于 description。模型倾向 under-trigger，要写得**稍微"激进"**——"用户提到提交/git 时即使没明说 commit 也调用"。触发词前置（清单单条截断 250）。**ECode 无关键词匹配器**——description 是 LLM 面唯一可发现性来源（手动面靠 `/` 补全，不依赖 description 质量）。

### S3.3 规范模型

```ts
// src/services/skill.ts
export interface SkillInfo {
  name: string
  description: string             // 清单展示用（截断 250）
  whenToUse?: string
  body: string                    // markdown 正文（去 frontmatter）
  baseDir: string                 // skill 目录绝对路径（附属文件相对它）
  source: 'user' | 'project' | 'plugin'   // 发现层级
  userInvocable: boolean          // 默认 true；false 不进 / 补全
  disableModelInvocation: boolean // 默认 false；true 不进 LLM 清单
}
```

## S4. 流程

### S4.1 发现（多目录分层 + 首个同名胜出）

| 优先级 | 目录 | 用途 |
|---|---|---|
| 1 | 项目级 `<cwd>/.ecode/skills/`（向上遍历到 home；gitignore 负向豁免，见 v3 P1-6） | 团队共享（入库） |
| 2 | 用户级 `~/.ecode/skills/` | 个人习惯 |
| 3 | plugin 级（第三部分，skill 目录由 plugin 贡献） | 第三方分发 |

realpath + name 去重，首个胜出。跨平台：`os.homedir()`、正斜杠、不依赖 shell `~`（AGENTS §2.5）。

### S4.2 清单注入 system prompt（LLM 面入口）

用 `<available_skills>` XML 块注入清单（结构清晰、LLM 解析稳），**受 token 预算约束**（S7）：

```ts
// core/system.ts
export function buildSystemPrompt(skills: SkillInfo[], ctxWindow: number): string {
  const budget = Math.max(2000, Math.floor(ctxWindow * 0.01))   // 1% 窗口，下限 2000 字符
```

### S4.3 触发面一：LLM 自主调（SkillTool 工具调用，无关键词匹配）

```ts
// src/tools/builtin/skill.ts
export const skillTool: Tool = {
  name: 'Skill',
  description: '加载某 Skill 的工作流指令。任务匹配 available_skills 某项描述时调用，传其 name。',
  readonly: true,
  input_schema: { type:'object', properties:{ skill:{ type:'string' } }, required:['skill'] },
  async execute(args, ctx) {
    const info = skillRegistry.get((args as {skill:string}).skill)
    if (!info) return { content:`Skill 不存在。可用：${skillRegistry.list().map(s=>s.name).join(', ')}`, is_error:true }
    if (info.disableModelInvocation)
      return { content:`Skill ${info.name} 设置了 disable-model-invocation，仅限用户手动 /${info.name} 调用`, is_error:true }
    return { content: [                                  // <skill_content> XML 包裹
      `<skill_content name="${info.name}">`, info.body.trim(), '',
      `该 Skill 附属文件目录：${info.baseDir}（相对路径基于此目录，需要时用 read_file 读取）。`,
      '</skill_content>',
    ].join('\n') }
  },
}
```

**body 走 tool_result（非注入新 user message）**：复用 loop 现有 `invokeTool` 回喂路径，零侵入。手动面（S4.4）的 user 消息由 TuiApp 提交层构造，loop 只看到一条普通 user message——两条路径都不需要 loop 特判。

### S4.4 触发面二：用户斜杠手动调（★ v4 新增）

**问题**：LLM 面靠 description 命中，存在 under-trigger；且"我现在就要用这个流程"是确定性意图，不该赌模型判断。**解法**：skill 同时是一条斜杠命令，用户 `/skill-name 参数文本` 直接触发。

**补全合并**：`/` 补全列表 = 内置命令 + skill（过滤 `userInvocable === false`）。skill 条目描述后缀标来源（如 `(skill)`），与内置命令区分；选中回车补全为 `/name `（带尾随空格，提示可接参数）。输入第一个空格后停止命令名匹配，后续文本都是参数。

**分流顺序**（TuiApp submit，`/` 开头时）：内置命令优先 → 未命中查 skill（须 userInvocable）→ 都未命中才按未知命令处理。

**传参展开**（`services/skill.ts` 纯函数）：

```ts
/** 手动触发：body + 参数 → 注入用全文。两条规则保证任何 skill 都不丢参 */
export function expandSkill(info: SkillInfo, args?: string): string {
  let body = info.body
  if (args !== undefined && args !== '') {
    body = body.includes('$ARGUMENTS')
      ? body.replaceAll('$ARGUMENTS', args)                    // ① 有占位符 → 替换
      : `${body}\n\nARGUMENTS: ${args}`                        // ② 无占位符 → 兜底追加
  } else {
    body = body.replaceAll('$ARGUMENTS', '')                   // 未传参剥掉残留占位符
  }
  return [
    `<skill_content name="${info.name}">`, body.trim(), '',
    `该 Skill 附属文件目录：${info.baseDir}（相对路径基于此目录，需要时用 read_file 读取）。`,
    '</skill_content>',
  ].join('\n')
}
```

`$1`/命名参数占位符后置（MVP 只做 `$ARGUMENTS` 一个占位符，够覆盖"给流程一个主题/对象"的绝大多数场景）。

**注入形态**：展开结果作为**一条 user 消息**追加进 messagesRef → 立即触发一轮 LLM 请求。与 LLM 面的对照：

| | LLM 自动调（S4.3） | 手动调（本节） |
|---|---|---|
| 入口 | LLM 发 tool_use('Skill') | 用户敲 `/name args` |
| body 形态 | tool_result（`<skill_content>`） | user 消息（`<skill_content>` 包裹的展开全文） |
| 后续 | LLM 决策，可能在同轮继续调工具 | 立即发起一轮请求 |
| `disable-model-invocation: true` | SkillTool 拒绝（is_error） | 不影响（正是为仅手动设计的） |
| `user-invocable: false` | 不影响 | 补全不显示；直接敲 `/name` 拦截并提示"请让 ECode 使用 ${name} 技能" |

**转录显示**：显示用户原始输入 `/commit 修复登录 bug` 一行；展开全文存进消息供模型消费（显示层走既有消息截断，不额外引入 display/content 分离——后置优化项）。

### S4.5 执行（inline）

LLM 拿 body 后按步骤用已有工具干活。MVP 只有 inline——skill body 是给当前 loop 的指令，不起新 agent。

## S8. 扩展性：从对话蒸馏 Skill

### S8.1 定位：L2 半自动是当前可行档位

"会话→skill"的自动化谱系：L1 全手写 → L2 人触发+agent 起草+人确认 → L3 自动上下文蒸馏（产易失笔记，非 skill）→ L4 自动记忆蒸馏（产 AGENTS.md 类 memory，非 skill）→ L5 全自动 skill 生成（研究阶段，尚无跑赢简单基线的实现）。业界最激进的内部实现也停在"人触发 + 访谈起草 + 人确认"——中间隔着"判断什么值得存"这道无人解过的坎。

**ECode 取 L2**：人触发、agent 起草、人确认；全自动判断+固化远期再议（S8.4）。

### S8.2 memory vs skill：分两层，不合并

| 维度 | memory（MEMORY.md / AGENTS.md） | skill（SKILL.md） |
|---|---|---|
| 载入 | 被动（常驻/检索） | 主动（description 命中才触发） |
| 形态 | 自由随笔、索引+topic | 结构化指令（frontmatter+流程+成功判据） |
| 粒度 | 一条洞察/偏好 | 一个完整可复用工作流 |
| token | 持续占用（故限 200 行/分层） | 元数据常驻、body 懒载 |

**两者配合**：memory 是 skill 起草的**输入原料**，但**绝不自动升级**（自动升级正确率无保证，会污染 skill 库）。

### S8.3 设计：L2 最小闭环 + 升级合并协议（★ v4 补全）

**创建**（v3 已降级，维持）：`/skill-create` 命令 → 读当前会话（messagesRef 全量）→ LLM 一次性起草（name/description/when_to_use/body）→ ConfirmPrompt 预览（可弃/可改）→ `install` 落盘。

**升级已有 skill**（v4 新增；对已有同名 skill 再 install 自动走升级模式）：

```
install(candidate) 检测同名已存在
  1. versions 备份：当前 SKILL.md 存档到 <skill>/versions/vN/（上限 10 版，超出挤掉最旧）
  2. LLM merger 判断（新内容 vs 现有内容），逐 section 三态产出：
       补充     → 新 section（追加）
       等价已有 → 忽略（去重，不重复写入）
       矛盾     → 标记冲突，预览时交用户裁决（保留现有 / 采用新 / 并存改名）
  3. 确定性合并（代码执行，非 LLM 拼全文）：按 ## 二级标题定位——
       同名 section 整体替换；无对应 section 的追加到末尾
  4. ConfirmPrompt 预览（diff 形式：+ 新增 section / ~ 替换 section / ! 冲突项）→ 确认落盘
```

**设计要点**：
- **LLM 只判断，不拼盘**：merger 的产出是"每个 section 的三态判定"，最终文件由确定性代码按 section 边界组装——LLM 拼全文会引入丢内容/重复段落风险。
- **人审卡点收敛两处**：写盘前预览 + 冲突裁决。升级永不静默覆盖（有 versions 兜底可回滚，但回滚是兜底不是流程）。
- **版本上限 10**：versions 是安全网不是版本管理系统，超限淘汰最旧。

三抽象（DistillSource/Trigger/Drafter 接口）等 L3 再定（YAGNI）；MVP 的创建+升级闭环不依赖它们。

### S8.4 演进路线（每步可独立交付）

| 步 | 做什么 | 自动度 | 依赖 |
|---|---|---|---|
| **S8-a MVP** | `/skill-create` 创建 + **升级合并协议**（S8.3） | 人触发+确认 | 仅 Skill 基础设施 |
| **S8-b** | SessionMemory（post-turn 抽笔记，服务压缩）—— context distillation，**非 skill** | 自动触发 | sub-agent（后置） |
| **S8-c** | `/learn`：蒸馏"非显然发现"到分层 AGENTS.md —— 持久 memory 层 | 人触发 | S8-b |
| **S8-d** | `ThresholdTrigger`：检测"同一工具序列/纠正模式重复 ≥N 次"→ 主动提议"固化成 skill？"（仍人确认） | 半自动提议 | S8-b/c 做信号源 |
| **S8-e 远期** | 全自动判断+固化 —— 等 LLM 判断力 + 评估闭环成熟 | 全自动 | 研究突破 |

# 第二部分：MCP 客户端

## M1. 核心架构：按需连接 + 工具缓存 + 状态机

四件套：官方 SDK Client + Transport、适配器（tools/list → ECode Tool）、生命周期管理器（状态机 + 按需连接 + 空闲卸载）。

```
┌─ McpManager（生命周期编排）────────────────────────────────────────┐
│  servers: Map<name, { client?, status, defs, lastUsedAt, inFlight }>│
│  启动：读 metadata cache → 全部工具注册（零连接）                    │
│  lazyConnect(name)：首次调用才连（并发去重 + 60s 失败退避）           │
│  空闲卸载：30s 定时器（unref），idleTimeout 默认 10min → close      │
│  stop()：退出清理全部连接                                            │
└────────────────────────────┬────────────────────────────────────────┘
                             │ 每 server 一个
              ┌──────────────┴──────────────┐
              ▼                             ▼
   ┌─ stdio Transport ──────┐    ┌─ StreamableHTTP Transport ────┐
   │ spawn 子进程           │    │ POST 到 https://host/mcp       │
   │ stdin/stdout JSON-RPC  │    │ stderr → LogStore              │
   └───────────┬────────────┘    └────────────┬───────────────────┘
               │ Client.connect（initialize 握手，SDK 内置）
               ▼
   ┌─ tools/list → 缓存（~/.ecode/mcp-cache.json）+ 适配器 → Registry ─┐
   │  注册与连接解耦：cache 命中 → 不连接也能注册全部工具               │
   │  execute → 未连接先 lazyConnect → client.callTool                │
   │  isError? recoverable / readonly=false 默认确认 / 透传校验       │
   └───────────────────────────────────────────────────────────────────┘
```

**lifecycle 每 server 可配四态**：

| lifecycle | 启动时 | 首次调用 | 掉线 | 空闲 |
|---|---|---|---|---|
| `lazy`（默认） | 不连 | 连 | 不自动重连（60s 退避后可再试） | 10min 断开 |
| `eager` | 连 | — | 不自动重连 | 默认不断开 |
| `keep-alive` | 连 | — | 30s 健康检查自动重连 | 永不断开 |
| `lazy-keep-alive` | 不连 | 连 | 30s 健康检查自动重连 | 永不断开 |

选型逻辑：本地 stdio server 启动便宜、用完可能不用 → lazy；云端 HTTP 启动贵但常驻服务 → keep-alive 系。

## M2. 目标 & 验收

**目标**：配置里声明 MCP server，ECode 按需连接、缓存工具清单、注册成 `mcp__server__tool`；LLM 像调内置工具一样调它们；用户随时可见连接状态并可重连。

**验收**：
- **按需加载**：默认 lazy——启动零连接、零子进程，工具清单来自 cache 可正常列出并供 LLM 调用；首次调用某 server 工具时才连接（连接期间状态可见）
- **缓存**：`~/.ecode/mcp-cache.json` 命中 → 不连接直接注册；server 配置变更（configHash 变）→ 缓存失效，下次连接重拉
- stdio server（`npx -y @modelcontextprotocol/server-filesystem <dir>`）→ `mcp__filesystem__*` 可调；HTTP server（url + headers）同样
- 命名 `mcp__<server>__<tool>`，跨 server 重名不冲突
- **默认每次确认**（ConfirmPrompt 复用 M3），即使 readOnlyHint；重 MCP 会话有"本会话记住（server 级）"选项（v3 P1-3）
- server `isError:true` → tool_result is_error（recoverable）
- **失败不阻塞**：任一 server 连接失败 → 状态 failed + warn；60s 内退避（重复调用直接 is_error 提示"N 秒前失败，可 /mcp reconnect"），60s 后自动降级回 cached
- **空闲卸载**：lazy server 10 分钟无调用自动断开（状态回 cached，工具注册保留）
- **TUI**：StatusBar 显示 `MCP 2/3`；`/mcp` 面板三级可达（列表→详情→工具列表），重连/断开可操作且状态实时刷新；failed 行自动展开错误；`/mcp reconnect <name>` 直达生效
- Ctrl+C → 透传 AbortSignal 中断 callTool
- 退出清理子进程（不留孤儿）
- **心脏零改动**

**不做**（后置）：resources/prompts 原语、OAuth（needs-auth 状态随之）、elicitation/MRTR、per-tool 白黑名单、`tools/list_changed` 增量同步、proxy 元工具暴露模式、面板高级项（直连工具 toggle / token 实时估算 / 60s 自动关 / 键位可配置 / 鼠标支持，见 T4）。

## M3. 数据结构

### M3.1 配置 schema（业界 de-facto `mcpServers`）

配置来源两处合并（优先级：用户级 < 项目级，同名项目级覆盖 + warn；plugin 级随 M7）：
- **用户级**：`~/.ecode/config.json` 的 `mcpServers`
- **项目级**：`<cwd>/.mcp.json`（团队共享，secret 用 `${ENV_VAR}` 占位符；**首用批准**——v3 P1-4，hash 持久化 config）

```ts
export interface McpServerConfig {
  type: 'stdio' | 'http'
  command?: string; args?: string[]; env?: Record<string,string>; cwd?: string   // stdio
  url?: string; headers?: Record<string,string>                                    // http
  enabled?: boolean                              // 默认 true；false → disabled 状态，不注册工具
  lifecycle?: 'lazy' | 'eager' | 'keep-alive' | 'lazy-keep-alive'   // 默认 lazy（v4）
  idleTimeout?: number                           // 分钟，默认 10（lazy）；eager/keep-alive 系默认 0=不断开
  timeout?: number                               // 单次调用/连接超时 ms，默认 30000
}
```
（v2 的 `required` 字段随急连接模型移除——见 v4 修订点 2。）

**`${ENV_VAR}` 占位符**：加载时替换成 `process.env.XXX`，缺失 warn + skip（呼应 AGENTS §5.2 密钥从环境读）。

### M3.2 连接状态机（v4 新增）

```ts
export type McpServerStatus =
  | 'not-connected'   // 未连接且无缓存（如配置了但从未成功连过）
  | 'cached'          // 未连接但有工具缓存（工具已注册，首次调用时连接）
  | 'connecting'      // 连接中（首次调用 / 重连）
  | 'connected'       // 已连接
  | 'failed'          // 连接失败（60s 内；过后自动降级回 cached/not-connected）
  | 'disabled'        // enabled:false
```

- **failed 自动过期**：失败记时间戳，60s 后定时清除并降级——"失败"是瞬时态不是常态，避免失败 server 永远挂红。
- **退避**：failed 后 60s 内 lazyConnect 不再尝试（工具调用直接 is_error 带原因与 `/mcp reconnect` 提示），避免每次调用都撞墙。
- **needs-auth**（OAuth）后置，MVP 无此态。
- 状态变更是事件源：StatusBar / `/mcp` 列表 / systemMsgs 都订阅同一份快照。

### M3.3 McpTool 适配

```ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js'
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js'
import { StreamableHTTPClientTransport } from '@modelcontextprotocol/sdk/client/streamableHttp.js'

function adaptTool(serverName: string, def: McpToolDef, getClient: () => Promise<Client>, cfg: McpServerConfig): Tool {
  return {
    name: `mcp__${sanitize(serverName)}__${sanitize(def.name)}`,     // 双下划线（事实标准）
    description: def.description ?? `MCP tool ${def.name} (${serverName})`,
    input_schema: normalizeSchema(def.inputSchema) ?? { type:'object', properties:{} },  // v3 P1-2 归一化
    readonly: false,                  // ★ 默认确认（第三方不可信），即使 annotations.readOnlyHint
    skipLocalValidate: true,          // ★ 透传给 server 校验（M4.4）
    timeout_ms: cfg.timeout ?? 30_000,
    async execute(args, ctx) {
      const client = await getClient()      // ★ 未连接先 lazyConnect（并发去重 + 退避检查）
      const r = await client.callTool({ name:def.name, arguments:args ?? {} }, undefined,
        { signal:ctx.signal, timeout:cfg.timeout ?? 30_000, resetTimeoutOnProgress:true, onprogress:()=>{} })
      return { content: renderContent(r.content), is_error: r.isError === true }
    },
  }
}
```
**`skipLocalValidate`**（Tool 接口新增可选字段）：MCP server 是实现方，最懂参数约束；server 在 callTool 时参数不对返回 isError/JSON-RPC error，走既有 recoverable 路径。且避免 AJV 对 server schema `$ref`/复杂结构的兼容问题。Registry.validate 对 `skipLocalValidate` 工具直接 ok；`register()` 对此类工具**跳过 ajv 预编译**（v3 P1-2，防外部 schema throw 炸注册循环）。`normalizeSchema`：剥 `$defs`/外部 `$ref`、oneOf 降级为 description 文本、限 properties 数。

`getClient` 是惰性句柄：cache 命中注册时 client 可能还不存在，execute 时才连接——这是"注册与连接解耦"的落点。

### M3.4 工具暴露与 token 预算

**MVP 全量直连注册**：每个 MCP 工具注册为独立 Tool（`mcp__server__tool`），与内置工具同列。理由：与 Skill/内置工具心智一致、实现最简、绝大多数场景单 server 工具数 <20。

**token 计入压缩估算**（v3 P1-1，必做）：M5 的 `estimateContextTokens` 加 tools 参数（specs JSON/4），onBeforeRequest hook 工厂传入 `toolReg.specs()`——否则 MCP 工具 schema 挤爆真实上下文而压缩器无感。

**超阈值 warn**：单 server 工具数 >20 或估算 schema 超预算份额 → 启动 warn 提示配置 `excludeTools`（后置）/ 关注 token 占用。

**proxy 元工具模式后置**：工具极多时收敛为单一 `mcp` 元工具（search/describe/call 按需取 schema，token 开销恒定）。MVP 不做（M6-D28）。

### M3.5 metadata cache（v4 新增）

```
~/.ecode/mcp-cache.json
{
  "filesystem": {
    "configHash": "a1b2…",       // server 定义的 hash（command/args/url/headers）
    "tools": [ { name, description, inputSchema } ],   // tools/list 结果
    "cachedAt": 1692…
  }
}
```
- **写入时机**：连接成功拉到 tools/list 后回写；**读取时机**：启动时读，configHash 命中 → cached 状态 + 注册全部工具（不连接）。
- **失效**：configHash 不匹配 → 缓存作废，该 server 标 not-connected，首次调用连接后重拉。
- **手动刷新**：`/mcp reconnect <name>` 重建连接并回写缓存（工具增删后的人工刷新通道；`tools/list_changed` 增量同步后置）。

## M4. 流程

### M4.1 配置加载合并
用户级 + 项目级合并；同名项目级覆盖 + warn；`${ENV_VAR}` 解析；`enabled===false` → disabled（不注册工具）。项目级 `.mcp.json` 首用弹批准（hash 持久化，v3 P1-4）。

### M4.2 按需连接（lazyConnect）

```ts
// 伪码：并发去重 + 退避 + 状态机推进
async lazyConnect(name: string, signal?: AbortSignal): Promise<Client> {
  const st = this.servers.get(name)!
  if (st.status === 'connected') return st.client!
  if (st.status === 'connecting') return st.connectPromise!        // ★ 并发去重：同 server 共享一个 Promise
  if (st.failedAt && Date.now() - st.failedAt < 60_000)
    throw toAppError({ code:'MCP_BACKOFF', message:`${name} 连接失败（${secs} 秒前），可 /mcp reconnect ${name}` })
  st.status = 'connecting'; this.emitStatus(name)                   // 状态栏/列表实时反馈
  try {
    const client = await this.doConnect(name, signal)               // stdio/http Transport + 握手
    await this.refreshMetadata(name, client)                        // tools/list → 注册增量 → 回写 cache
    st.status = 'connected'; st.lastUsedAt = Date.now(); this.emitStatus(name)
    return client
  } catch (e) {
    st.failedAt = Date.now(); st.status = 'failed'; this.emitStatus(name)
    throw toAppError(e)
  }
}
```

```ts
// stdio（env 合并 + stderr pipe）
const transport = new StdioClientTransport({
  command: resolveCommand(cfg.command!),        // win32: npx 可能需 cmd /c（M5-M6）
  args: cfg.args ?? [], cwd: cfg.cwd, env: { ...process.env, ...cfg.env }, stderr: 'pipe',
})
transport.stderr?.on('data', c => logger.debug(`mcp.${name}`, 'stderr', { text: c.toString() }))
// http
const transport = new StreamableHTTPClientTransport(new URL(cfg.url!), { requestInit:{ headers: cfg.headers ?? {} } })
const client = new Client({ name:'ecode', version: PKG_VERSION })
await Promise.race([client.connect(transport), timeout(cfg.timeout ?? 30_000)])  // 外包超时兜底
```

启动时只连 `eager` / `keep-alive` 的 server（并行、容错，失败标 failed 不阻塞）；lazy 的全部走 cache 注册。

### M4.3 工具发现注册
cache 命中 → 直接按缓存注册（零连接）；未命中且 eager/keep-alive → 连接后 `tools/list` 注册 + 回写；lazy 且无缓存 → 启动时连一次 bootstrap（拿清单后即断，回 idle）。

### M4.4 调用（isError → recoverable）
LLM 调 `mcp__filesystem__read_file` → validate（skipLocalValidate ok）→ confirm（readonly=false；"本会话记住（server 级）"可选）→ `getClient()`（未连接则 lazyConnect）→ `client.callTool` → isError 转 is_error / JSON-RPC 错误 catch 转 toAppError。content 渲染：text 原样 / image→占位 / resource_link→路径 / resource→text。每次调用 `touch(name)` 更新 lastUsedAt。

### M4.5 生命周期（空闲卸载 + 健康检查 + 退出清理）

```
30s interval（unref，不阻退出）：
  ① keep-alive 系未连接 → 重连（失败记 failed，走退避）
  ② 非 keep-alive 系：lastUsedAt 距今超 idleTimeout 且 inFlight===0 → client.close()
     → 状态回 cached（工具注册保留，下次调用 lazyConnect 重连）
退出（process exit handler）：stop() → 全部 client.close()（SDK 发 SIGTERM）
  Windows 孤儿进程复现时再上 taskkill /T 进程树兜底（MVP 先用 SDK 默认）
```

## M6. TUI 呈现（三层 + 二级菜单面板，v5 重写）

**问题**：MCP 是唯一"有外部连接状态"的子系统——用户需要知道配了什么、连没连上、失败为什么、怎么重连；skill 数量多后用户需要浏览、查找、选用；这些交互用纯文本列表命令承载不了（无导航、无操作、信息一次性刷过）。

**答案**：三层感知（常态/反馈）+ 二级菜单面板（浏览/操作）。

| 层 | 位置 | 内容 | 时机 |
|---|---|---|---|
| **常驻** | StatusBar 一段 | `MCP 2/3`（已连/启用数）；连接中瞬时态 `MCP 连接中…` | 有启用的 server 才显示；无配置零开销 |
| **一次性** | systemMsgs | 启动 eager/keep-alive 连接结果；reconnect 结果；skill 升级结果 | 事件发生时 |
| **面板** | overlay（二级菜单） | `/skill` 浏览选用 skill；`/mcp` 查看/操作 server | 用户主动 |

### T1. 面板基础设施：PanelShell + overlay 挂载 + 多级导航

**挂载复用现有 overlay 机制**（ModelPicker / HistoryPicker / Wizard 同款）：TuiApp 的 `overlay` state 加 `skill-panel` / `mcp-panel` 两个 kind，面板组件渲染在对话流下方当前轮区域；overlay 期间 `InputStream inactive`（输入框停用）、面板独占键盘（含 Ctrl+C 语义）——这些行为 ECode 已有，面板零新层。

**渲染约束**：宽度=终端全宽（对齐现有组件）；高度受控（窗口化滚动 12 行 + 提示行）；ambiguous 字符宽度问题沿用现有 symbols 方案；面板打开期间后台 loop 若在流式输出，面板仍钉在当前轮位置不动（Static 之上），流式完成后 systemMsgs 反馈。

**后置**：面板内直连工具 toggle / token 实时估算（等 M6-D28 proxy 模式一起）、60s 无操作自动关、键位可配置（keybindings 覆盖）、鼠标支持。

# 第三部分：Plugin 系统（v3 推迟 → M7，本章保留为 M7 设计储备）

> **v3 推迟说明（2026-08-14 用户拍板）**：Plugin 整体推迟 M7。理由见头部 v3 修订记录——范围蠕变（M5 §C 承诺的 M6 是 Skill+MCP）、无作者生态、commands 资源契约不成立、兼容面收窄。本章调研与设计**完整保留**，M7 启动时直接作为输入；届时若需统一装配骨架，回看 ADR-026（暂缓中）。M6 的 MCP 配置只做用户级 config + 项目级 `.mcp.json` 两层（plugin 级 `.mcp.json` 随 Plugin 推迟）。

## P1. 核心架构：四件套（marketplace + cache + 清单 + 资源接入）

**Plugin 是"资源容器"，本身不执行**。它把若干 skill/command/mcp 配置打包，loader 扫描后分发到各 Registry。四件套（marketplace + 版本化 cache + 清单 + 资源接入）是成熟的第三方分发形态；清单格式贴 Claude 生态兼容格式，可直接消费其官方 marketplace（开局即有生态，此红利已在第三方宿主验证）。

```
┌─ Marketplace（索引仓库，git clone / zip 下载）──────────────────────┐
│  .ecode-plugin/marketplace.json  { name, plugins:[{name, source, ...}] }│
└────────────────────────────┬────────────────────────────────────────┘
                             │ /plugin install <name>@<marketplace>
                             ▼
┌─ 版本化 Cache（~/.ecode/plugins/cache/<marketplace>/<plugin>/<version>/）┐
│  .ecode-plugin/plugin.json   ← 清单（元数据 + 组件声明）                  │
│  skills/  commands/  .mcp.json  hooks/hooks.json                          │
└────────────────────────────┬────────────────────────────────────────┘
                             │ PluginLoader 扫描（启用者）
                             ▼
┌─ 资源接入（分发到既有 Registry，plugin 是基底层，优先级最低）────────────┐
│  skills/    → SkillRegistry（source:'plugin'）                            │
│  commands/  → CommandRegistry（命名空间 /plugin:cmd）                      │
│  .mcp.json  → McpManager（mcpServers 合并，按 lifecycle 接入）            │
│  hooks/     → HookRunner（后置，等 hooks 子系统）                          │
└───────────────────────────────────────────────────────────────────────────┘
```

**与 Skill/MCP 的关系**：skill/mcp/command 是"资源类型"，plugin 是"打包分发载体"。无 plugin 时这些资源也能独立配（`~/.ecode/skills/`、`.mcp.json`）；plugin 价值在于把一组相关资源 + 元数据 + 版本 + 来源 一起安装/启用/卸载。

---

## P2. 目标 & 验收

**目标**：用户 `/plugin` 打开面板——浏览已添加市场的插件、搜索、看详情、安装；管理已安装（启用/禁用/卸载）；添加新市场；启用后其 skill/command/mcp 自动接入，卸载干净。

**验收**：
- `/plugin` 面板「添加市场」页输入 `anthropics/claude-plugins-official` → clone 到 `marketplaces/`，浏览页出现其插件
- 浏览页选中 `context7` → 详情 → 安装 → 从 marketplace 拉取到版本化 cache + enable（行内 `安装中…` → systemMsgs 结果）
- 搜索即时过滤（name/description/marketplace）；部分市场拉取失败降级显示 + banner 提示
- 启用的 plugin 的 skills 进 SkillRegistry（source:'plugin'）、commands 进 CommandRegistry（`/plugin:cmd`）、mcp 进 McpManager 按各自 lifecycle 接入
- 已安装页：禁用 → 组件立即移除；卸载（确认框）→ 删 cache
- plugin 资源优先级最低：用户级/项目级同名覆盖它
- 清单非法 / 路径穿越 → 拒绝加载 + warn，不崩
- **心脏零改动**

**不做**（后置）：hooks（等 HookRunner）、agents（等 sub-agent）、userConfig 收集 UI、依赖解析 + 跨 marketplace 白名单、git-subdir 部分克隆、企业策略 allowlist/blocklist、autoUpdate + commit sha 比对、安全存储（keychain）。

## P3. 数据结构

### P3.1 plugin 清单（`.ecode-plugin/plugin.json`，极简 + 目录约定）

清单只放元数据，组件靠**目录约定**自动发现（`skills/`、`commands/`、`.mcp.json`、`hooks/hooks.json` 存在即扫描）——降低作者门槛，零配置可发。同时支持显式声明字段（路径字符串/数组）覆盖约定。

```jsonc
// .ecode-plugin/plugin.json（极简约定型，如 context7）
{
  "name": "context7",                       // 必填，正则 ^[a-z0-9][a-z0-9._-]{0,127}$
  "version": "0.1.0",                       // 默认 0.0.0
  "description": "Up-to-date 文档查询 MCP",
  "author": { "name": "Upstash" },
  "license": "MIT"
  // 组件靠目录约定：skills/ commands/ .mcp.json 存在即扫
}
```

```jsonc
// 显式声明型（可选，覆盖约定）
{
  "name": "my-plugin", "version": "1.0.0",
  "skills": "skills",                       // 相对路径（./开头，必须在 plugin 根内）
  "commands": ["commands", "extra-cmds"],
  "mcpServers": { "foo": { "type":"stdio", "command":"node", "args":["${ECODE_PLUGIN_ROOT}/dist/srv.js"] } }
}
```

**字段集**：元数据（name/version/description/author/homepage/license/keywords/dependencies）+ 组件（skills/commands/mcpServers/hooks/agents，可声明或约定）+ 未知字段静默剥离（`.strip()`，容错——作者加自定义字段不致加载失败）。

### P3.2 marketplace.json（市场索引）

```jsonc
// .ecode-plugin/marketplace.json
{
  "name": "ecode-plugins-official",
  "owner": { "name": "ECode" },
  "plugins": [
    { "name": "context7", "description": "...", "version": "0.1.0",
      "source": { "source": "github", "repo": "upstash/context7-mcp", "ref": "v0.1.0", "sha": "30287f5e..." } },
    { "name": "my-local", "source": "./plugins/my-local" }   // 市场内相对路径
  ]
}
```
**MVP source 两类**：`github`（owner/repo + ref + sha，git shallow clone）和 `url`（zip + sha256，下载解压）。市场内相对路径（`./xxx`）也支持。

### P3.3 目录布局

```
~/.ecode/plugins/
├── marketplaces/<marketplace-name>/        # clone/fetch 的市场仓库
│   └── .ecode-plugin/marketplace.json
├── cache/<marketplace>/<plugin>/<version>/ # 版本化缓存（主体）
│   ├── .ecode-plugin/plugin.json
│   ├── skills/  commands/  .mcp.json
├── known_marketplaces.json                 # 已添加市场注册表
└── (启用状态在 ~/.ecode/config.json → plugins)
```
版本字符串路径穿越净化（`[^a-zA-Z0-9\-_.]→-`）。

## P4. 流程

### P4.1 添加 marketplace
面板「添加市场」页输入 `<github owner/repo | url>` → git clone 到 `marketplaces/<name>/` → 注册进 `known_marketplaces.json` → 刷新浏览页。

### P4.2 安装 plugin
详情页「安装」→ 读 marketplace.json 找 source → 按 source 拉取（git clone / zip 解压）到临时目录 → 去 `.git/` → 校验清单（缺失则合成最小 manifest）+ sha → 移到版本化 cache → 默认 enable。

### P4.3 资源接入（PluginLoader，启动期 + install 后）
```
对每个 enabled plugin（按优先级）：
  skills/    → SkillRegistry.register（source:'plugin'，去重时优先级最低）
  commands/  → CommandRegistry.register（命名 /plugin-name:cmd）
  .mcp.json  → 合并进 mcpServers 配置（plugin 级，基底层）→ McpManager 按各自 lifecycle 接入
  hooks/     → 后置（HookRunner 未就绪）
占位符替换：${ECODE_PLUGIN_ROOT}→cache 绝对路径、${ECODE_PROJECT_DIR}→cwd、${user_config.K}→配置值
```

### P4.4 启用/禁用/卸载
- enable/disable：写 `config.json → plugins["plugin@marketplace"] = bool`；disable 立即移除组件
- uninstall：删 cache + 移 install 记录

### P4.5 优先级与冲突
资源级 first-match-wins：显式配置（用户级/项目级）> plugin（最低）。plugin 永远可被用户覆盖。同名 plugin 身份 = `name@marketplace`。

## P7. 安全（即使 MVP 也做全）

第三方 plugin 是**无沙箱的可信代码**（skills 是指令注入、mcpServers 可 spawn 任意命令），安全四件套：
1. **官方名预留**：`ecode` / `ecode-official` 等名字不允许第三方 marketplace 注册（防官方伪装）
2. **路径穿越净化**：source 路径/版本字符串/组件路径全部过 sanitize（`..` 拒绝）
3. **sha 校验**：github source 带 sha，clone 后校验 commit；url source 校验 sha256
4. **占位符白名单**：`${ECODE_PLUGIN_ROOT}` / `${ECODE_PROJECT_DIR}` / `${user_config.K}`（K 限白名单键，防读 apiKey）

启用时 systemMsgs 提示"第三方 plugin 含可执行内容，请确认来源"。

# 决策结论（M6 全部）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **M6-D1** | Skill 触发方式 | **双触发面**：LLM 自主调 SkillTool（主）+ 用户 `/skill-name args` 手动调（v4 修订） | description 驱动 LLM 命中是主要路径；确定性意图不赌模型判断，斜杠补齐 |
| **M6-D2** | Skill body 注入（LLM 面） | 作为 tool_result（`<skill_content>`） | 零侵入心脏；复用既有回喂路径 |
| **M6-D3** | Skill 文件格式 | 目录 `name/SKILL.md` + frontmatter（AJV） | 目录携附属文件；缺字段回退 |
| **M6-D4** | Skill 发现层级 | 项目级 > 用户级 > plugin 级；首个胜出 | 项目级更具体；plugin 基底层 |
| **M6-D5** | Skill MVP 优化 | token 预算(1%)+250截断+when_to_use+base dir+AJV | 防爆炸+命中率，成本极低 |
| **M6-D6** | Skill 增量推送 | MVP 暂不做（预算约束已够），留变化签名接口 | YAGNI；M5 压缩后视清单负担再上 |
| **M6-D7** | Skill 蒸馏自动化 | **MVP 做 L2 半自动**（`/skill-create` 访谈起草 + 升级合并）；L3-L5 后置 | 全自动"判断什么值得存"业界尚无成熟实现；人审卡点收敛两处 |
| **M6-D8** | memory vs skill | 分两层不合并；memory 可作 skill 起草输入但不自动升级 | 自动升级正确率无保证会污染 skill 库 |
| **M6-D9** | MCP SDK | 官方 `@modelcontextprotocol/sdk@^1.30` | 官方 SDK 是唯一稳定实现，自研 JSON-RPC 无收益 |
| **M6-D10** | MCP transport | stdio + Streamable HTTP 都做 | stdio 社区主流；HTTP 接云端 |
| **M6-D11** | MCP 工具命名 | `mcp__<server>__<tool>` | 事实标准；防冲突 |
| **M6-D12** | MCP 工具确认 | 统一默认确认（readonly=false） | annotations 不可信；第三方代码 |
| **M6-D13** | MCP 参数校验 | 透传 server（skipLocalValidate） | server 最权威；避 AJV 兼容问题 |
| **M6-D14** | MCP 配置 | 用户级 config + 项目级 .mcp.json（plugin 级随 M7） | 对齐业界；secret 从 env 读 |
| **M6-D15** | MCP 生命周期 | **按需连接**：lazy 默认 + eager/keep-alive 可选 + 空闲卸载 + failed 60s 过期退避（v4 修订，废弃急连接） | 启动零连接降延迟与进程开销；metadata cache 解耦注册与连接；required 字段随急连接移除 |
| **M6-D16** | resources/prompts | MVP 不做（只 tools） | tools 是主价值；另两类后置 |
| **M6-D17** | Plugin 范式 | marketplace + 版本 cache + 清单 + 资源接入（四件套） | 成熟分发形态；贴 Claude 生态兼容格式获开局生态 |
| **M6-D18** | Plugin 清单格式 | 极简 + 目录约定（贴 `.claude-plugin` 兼容） | 降低作者门槛；直接消费 Claude 官方 marketplace |
| **M6-D19** | Plugin MVP 资源 | skills + commands + mcp 配置；hooks/agents 后置 | 后两者需 HookRunner/sub-agent 先就绪 |
| **M6-D20** | Plugin 优先级 | 基底层最低；用户/项目级覆盖 | 用户永远能覆盖第三方 |
| **M6-D21** | Plugin 安全 | 官方名预留 + 路径穿越净化 + sha 校验 + 占位符白名单 | 即使 MVP 也做（第三方可信代码无沙箱） |
| **M6-D22** | 三者与心脏关系 | 都注册成 Tool/Command 进 Registry，loop.ts 零改动 | 契合详设 §2.4 铁律 |
| **M6-D23** | 实施顺序 | Skill → MCP（→ Plugin M7） | Plugin 资源接入依赖前两者 Registry |
| **M6-D24** | 装配方式 | PluginLoader 显式拿 Registry 引用分发，不引入 AppContext 骨架 | ~20 行分发够了；ADR-026 维持暂缓 |
| **M6-D25** | Skill 手动传参 | `$ARGUMENTS` 替换 + 无占位符兜底追加；`$1`/命名参数后置 | 两条规则保证任何 skill 不丢参；MVP 一个占位符够用 |
| **M6-D26** | Skill 双路径注入形态 | 自动=tool_result；手动=user 消息 + 立即触发一轮 | 自动复用回喂零侵入；手动是 TuiApp 层构造普通 user 消息，loop 零特判 |
