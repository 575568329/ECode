## 1. 调研对标（2026-09-03 联网调研）

### 1.1 Claude Code：声明式命令——文件系统即清单

CC 的斜杠命令是 `.claude/commands/*.md` 文件，`/help` 列表由目录扫描**派生**：
加命令=加文件，清单自动出现，**结构上不可能漏登**。skill 同理（SKILL.md frontmatter 声明式）。
启示：能改成「派生」的清单就不要「手工维护」——ECode 的 `/help` 已是派生式（registry.list()），
但 CLI USAGE、手册里的功能表仍是手工串。

### 1.2 OpenCode：JSON Schema 单一事实源

OpenCode 提供 `https://opencode.ai/config.json` 公开 JSON Schema，用户配置文件写 `"$schema": ...`
获得**编辑器级校验/补全**，文档页与 schema 同源。配置文档不是手写的散文，是 schema 的渲染。
启示：schema 即文档。ECode 的 Config 是 TS interface，已有单一事实源，缺的是「派生」通道（见 §4.2 方案 B/C）。

### 1.3 业界文档漂移实践（Moxie Docs/DocDrift/DX 等）

核心论断：**「Drift is structural, not a moral failing」——漂移是结构性问题，靠自觉必输**。
可移植的三条：
- **Path-level drift detection**：代码变更与提及该路径的文档做关联检测（CI 层 diff 检查）
- **Docs as code + 同 PR 修复**：文档修正以小 PR 跟进，不进 backlog
- **低摩擦验证**：「docs as tests——文档里的例子跑不通，构建就红」

### 1.4 对 ECode 现有防线的判断

守则（#7 ecode-config 手册、#9 CONFIG_TEMPLATE）**早就写明触发条件「config schema 变更时」**，
但三层防线里它是唯一没有机器强制的层级：防漂移测试只锁了工具指引（第 1 项），
/doctor 是 LLM 事后抽查（且本轮排查前抽查范围不含手册 vs Config 全字段比对），
清单靠人自觉。M7 hooks、M8 三键漏登后修过一次，本次 review/relay/wechat 再次漏登——
**同型复发证明「人查」层级对高频迭代无效，必须升格为测试锁定**。

## 4. 防复发机制升级（核心：把「人查」升格为「测试锁定」）

三层防线按强度排序：**测试（机器，忘不掉）> /doctor（LLM，抽查）> 守则清单（人，必忘）**。
原则：凡是能写成断言的同步关系，一律下沉到测试层；LLM 与人只兜长尾。

### 4.1 方案 A（主推）：手册↔Config 键一致性防漂移测试

新测试 `tests/services/configManual.test.ts`，两条断言：

1. **手册含键**：用正则从 `src/services/config.ts` 的 `interface Config`/`interface ProviderCfg` 提取全部字段名
   （`^\s{2}(\w+)\??:` 级别的解析即可，无需 TS 编译器——字段名是 ASCII 标识符），
   逐个断言出现在 `ECODE_CONFIG_BODY` 文本中。嵌套对象字段（如 review.provider）断言父键名出现即可。
2. **模板含键**：CONFIG_TEMPLATE 注释内出现的键集合 ⊇ Config 顶层字段集合
   （豁免：`current`/`logLevel` 这类运行时派生键维护一份显式豁免清单，带注释说明为何豁免）。

效果：本次 review/relay/wechat 这类漏登，加字段当天测试就红。**误报可控**——字段名是
短 ASCII 词，正文恰好含该词即通过（宽松匹配只漏报不误报，漏报由 /doctor 第 7 项兜）。

### 4.2 方案 B（增信）：CONFIG_TEMPLATE↔手册↔Config 三方对账测试

同一测试文件补第三条：解析 CONFIG_TEMPLATE 与 ECODE_CONFIG_BODY 中 `"` 包裹的键名集合，
断言两者差集为空（模板有而手册无、或反之都算红）。防「模板加了手册没加」的半更新。

### 4.3 方案 C（长期）：声明式 Config Schema 派生（opencode 模式，另立 ADR 不在本批）

把 Config 字段元数据（名/类型/默认/说明）收敛为**单一事实源 schema 对象**，
CONFIG_TEMPLATE 注释、ecode-config 手册字段表、/config 面板「高级」页、未来 JSON Schema 导出
全部从 schema 对象**渲染派生**——手工文本从源头消失，漂移在结构上不可能。
工程量与收益都大（等价把 config 层重做成声明式），**本批不做**，登记为方向；若做，开 ADR supersedes 本节。

### 5.3 反驳（本方案最大的风险）

防漂移测试测的是「键名出现」而非「语义正确」——手册可以把 sandbox 写成五档但解释错。
机器只能锁事实存在性，语义正确性永远需要 4.5 的 LLM 抽查 + 里程碑三件套人查兜底。
本方案把三类漂移中的「整节遗漏」（本次实际发生的形态）结构性消灭，是收益/成本比最高的一刀；
不追求「文档永不错」的完备性承诺。

### 5.4 开放问题

1. ecode-features 是否并入 ecode-config 成一册（触发词合并）？——分册利于按需加载与职责清晰，但两个内置 skill 增加清单占位；倾向分册，实施批2 时按实际 token 占用定。
2. 方案 C 声明式 schema 的时机——等 config 键增速放缓或 /config 面板扩列需求出现再立项。
