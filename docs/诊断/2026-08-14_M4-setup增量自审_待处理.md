## P1（应修 — 边界/体验）

### S1. 编辑模式 type Select 的 active 依赖预填 setType，但 Select 挂载时序有风险
**Wizard.tsx:113-126（mode onSelect）+ 135-139（type Select）**
mode 选「编辑 astron」时，onSelect 里 `setType(p.cfg.type)` + `setStepIdx(+1)`。type Select 用 `key="type"` 重 mount，挂载时读 `type` state 算 active/initialIdx。
**风险**：React 18 批量更新，setMode/setProviderName/setType/setBaseURL/setApiKey/setModels/setStepIdx 同批，type Select 渲染时这些应已 flush。**测试已验证编辑 astron（anthropic）→ type 步 active 正确**（全回车选 anthropic）。但若 React 调度变化（并发模式严格）可能 stale。
**当前结论**：测试通过，暂不修。若未来出现编辑预填错位，查此处 setStepIdx 与 setType 的 batch 时序。

### S2. name 步输入与现有 provider 重名 / 非法字符 → modify 静默覆盖
**config.ts:287 + Wizard.tsx:90（name commitText）**
新增模式用户输入的 `providerName` 若与现有重名（已有 astron 又输 astron）→ `modify(['providers','astron'], ...)` 变成**编辑**（覆盖现有，不报错）。且 name 含 `/` `.` 空格等非法字符也照写（config 解析仍能读，但语义混乱）。
**修复建议**：Wizard name 步提交前校验——重名提示「已存在，将覆盖」+ 非法字符过滤。或 writeWizardConfig 加 `mode==='add' && 已存在 providerName` → throw `[SETUP_EXISTS]`。

### S3. wizardProviderObject 硬编码 maxTokens: 8192，编辑时丢失用户原 maxTokens/temperature/topP
**config.ts:231-241**
`wizardProviderObject` 只生成 `{type, baseURL, apiKey, models, thinking, maxTokens:8192}`——**不含 temperature/topP**，且 maxTokens 固定 8192。
**后果**：用户原有 `temperature:0.7, topP:0.95, maxTokens:16384` 的 provider，编辑后这三项被覆盖丢失（maxTokens 重置 8192，temp/topP 消失）。
**修复建议**：编辑模式从 existing 读原值合并；或 wizardProviderObject 接受可选 temperature/topP/maxTokens（Wizard 编辑时预填并让用户改）。

### S4. 首次（CONFIG_TEMPLATE 作底）modify 依赖模板的 providers 结构
**config.ts:265-273 + 287**
CONFIG_TEMPLATE 的 providers 里是 `astron`（非空）。首次 `writeWizardConfig({providerName:'default'})` → modify 在模板 providers map 里**新增 'default'**，同时 default 指向 default。结果 config 里 astron（模板示例，apiKey 空）+ default（用户填的）两个 provider 共存。
**后果**：首次 /setup 后 config 里残留模板的 astron 示例（apiKey 空，loadConfig 时若无 env 会因 astron 的空 key 报错——但 default 有效，current=default 不读 astron）。
**真机验证**：未触发此路径（测试用 writeConfig 直接造 config）。实际首次 /setup 可能产生冗余 astron。
**修复建议**：CONFIG_TEMPLATE 作底时清空 providers（`{ "providers": {} }`）再 modify，或首次直接生成干净 config 不走 modify。

## P2（建议 — 可维护性）

### S5. Wizard finish() 里冗余的三元
**Wizard.tsx:99**
```ts
const name = !hasProviders ? 'default' : mode === 'add' ? providerName : providerName
```
`mode === 'add' ? providerName : providerName` 两分支相同——`mode === 'edit'` 时也是 providerName（编辑的 name 在 mode onSelect 设入）。可简化为：
```ts
const name = hasProviders ? providerName : 'default'
```

### S6. steps 数组每次 render 重构造（性能/引用变化）
**Wizard.tsx:56-62**
`steps` 是 IIFE 每次 render 都重新构造新数组。虽然步序列在单次 /setup 内不变（依赖 mode/hasProviders），但每次 render 新引用理论上影响 useMemo/useCallback 依赖。
**当前**：Wizard 无重渲染性能瓶颈（步进频率低），不修。若未来加 useMemo 依赖 steps 需注意。

### S7. 预填的 temperature/topP/maxTokens 无法在 Wizard 修改
**Wizard.tsx STEPS**
Wizard 只 5 个字段步（type/baseURL/apiKey/model/thinking），**不含 temperature/topP/maxTokens**。即使用户 config 有这些，Wizard 也无法查看/修改它们（编辑时会因 S3 丢失）。
**设计取舍**：MVP Wizard 只管核心字段，高级参数用户编辑 config.json。但 S3 的「编辑丢失」是 bug（应保留原值）而非设计。

### S8. writeWizardConfig 备份 .bak 多次 /setup 会覆盖（只留最后一次）
**config.ts:279**
每次 writeWizardConfig 都 copyFileSync 到 .bak——连续两次 /setup（新增 a，再新增 b），第二次的 .bak 是第一次的结果，第一次的原 config .bak 被覆盖。
**影响**：用户只能回退一步。可接受（多步回退罕见），或加时间戳 .bak（但堆积文件）。当前不修。
