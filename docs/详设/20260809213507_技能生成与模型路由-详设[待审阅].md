### 3. 记录层详设

**记录接入点：`agent.ts:373`（内部 JS 回调，不走 spawn）**。

> 为什么不用 M5 hook？——M5 hook 是 **spawn shell 命令处理器**（`runner.ts:81`），handler 是 shell 脚本/可执行文件，**无法在 JS 里直接 append JSONL**。要在 JS 写文件有两条路：(A) 扩展 hook 框架支持 JS handler；(B) 绕过 hook，在 agent.ts:373（UserPromptSubmit 事件已在此 emit）直接调 `recordObservation()`。**选 B**——零框架改动、信号最精准（用户刚表达意图）、失败可降级（记录失败不影响主循环）。

**信号分类 + 正则过滤**（不全记，防噪音撑爆）：

| signal | 内置正则（命中即记） | 说明 |
|---|---|---|
| `correction` | `下次\|以后\|记住\|总是\|别再\|always\|remember\|next time\|don't` | 用户修正 agent 行为 |
| `preference` | `我喜欢\|prefer\|默认用\|用.{0,8}而不是` | 用户表达偏好 |
| 用户自定义 | `config.skillCapture.patterns` 数组 | 与内置合并，命中即记 |

**记录条目 schema**（JSONL，append-only）：

```jsonc
{
  "ts": "2026-08-09T21:35:07Z",     // ISO 时间（归纳时引用作证据）
  "signal": "correction",            // correction | preference | custom
  "source": "UserPromptSubmit",      // 来源标记（回调时机）
  "content": "下次提交前先跑 npm test",  // ≤500 字符，经 redact.ts 脱敏（不记密钥/token）
  "context": { "file": "src/agent.ts" },  // 可选：关联文件/工具
  "session": "abc123"                // session id，归纳时按会话聚合
}
```

**容量控制 + 脱敏**：

| 控制项 | 阈值 | 机制 |
|---|---|---|
| 磁盘上限 | 1MB / 1000 条 | FIFO 删最老 |
| 去重 | 同 content + 24h | **O(N) 扫描窗口**：只读文件末尾最近 50 条比对，不扫整个 1MB 文件 |
| 截断 | content ≤ 500 字符 | 超长截断 |
| 脱敏 | **新建 `redact.ts`** | 自由文本脱敏：`sk-xxx`/`Bearer xxx`/`token=xxx`/`api_key=xxx`/`AKIA*` → `[REDACTED]`（§9.2 红线，不复用单值掩码 maskSecret） |

**新建文件 `src/skill-capture/recorder.ts`**：`recordObservation(text, ctx, config)` 纯函数化（读配置 → 正则匹配 → redact → FIFO/去重 → append），可单测、可被 agent.ts:373 同步调用（appendFileSync，不阻塞事件循环感知——单次 < 1ms）。

**文件位置**：`<workspace>/.ecode/observations.jsonl`（与 `.ecode/sessions/` 同 gitignore）。

### 4. 归纳层详设

**命令**：`/skill-gen`（picker 无 pending 时直接进归纳；有 pending 且达 maxPending 时提示先审批）。

**流程**：

```
1. 读 .ecode/observations.jsonl 全部记录
2. 估 token：content.length / 2（粗估，零依赖——中文≈1字/token、英文≈2字符/token 的折中）
3. 若 < budget（上下文窗口 50-60%，留空间给 prompt+输出）→ 全量喂 LLM
   若 ≥ budget → 按 session 分批（每批 ≤ budget），LLM 自处理聚类
4. Ratchet prompt 归纳（关键约束见下）→ 每批产 0..N 个候选 skill
5. 合并去重（跨批同名/近义）→ pending 提案写 .ecode/skill-proposals/
```

> 不引 `tiktoken`/`gpt-tokenizer` 等 token 计数依赖——budget 判断只需量级，`length/2` 足够且零原生二进制（§9.3）。

**Ratchet 归纳 prompt 关键约束**（源自 AddyOsmani，防投机）：
- 每个候选 skill **必须引用具体观察记录**（ts + session + content 摘要）作为证据。
- **不 brainstorm**——只从真实记录归纳，记录不足时返回"素材不足，继续记录"而非硬造。
- 输出带 frontmatter 的 SKILL.md，按主题聚类（可一批发多个）。

**提案格式**（照 openclaw frontmatter，**手 split 解析**——`---` 之间按行 `key: value` 切分，不引 `gray-matter`）：

```markdown
---
name: precommit-test
description: 提交前必跑 npm test（≤160 字节）
status: proposal
version: 1
date: 2026-08-09
hash: <content hash>
evidence:                          # Ratchet 证据（归纳时填，apply 时剥除）
  - ts: 2026-08-09T21:35:07Z
    session: abc123
    content: "下次提交前先跑 npm test（已脱敏）"   # 存 redact.ts 脱敏后版本
---
# 提交前测试
提交代码前必须运行 `npm test` 确认全绿……
```

**限额**：maxPending=50（**超限 FIFO 删最老 pending + 归纳时 UI 提示"已达上限，先 /skill 审批"**）、maxSkillBytes=40000、description≤160B（照 openclaw）。

**提案存储**：`.ecode/skill-proposals/<name>.md`。

### 5. 审批层详设

**命令**：`/skill`（picker 列 pending，复用现有 picker-list 组件）。

**状态机**（照 openclaw）：

```
pending ──accept──→ applied（落 .ecode/skills/）
        ├──reject──→ rejected
        ├──quarantine(安全扫描 critical)──→ quarantined
        └──edit──→ pending（修订，version+1，带 hash 校验）
```

**操作**：
- `accept`：security-scan 通过 → 落 `.ecode/skills/<name>/SKILL.md`（剥除 evidence frontmatter，保留 name/description）。
- `reject`：删提案。
- `edit`：用户改内容，version+1。
- `promote`：accept 时选层级 或 `/skill promote <name>` → 复制到 `resolveDataDir()/skills/<name>/SKILL.md`（用户级）。**同名跳过**：用户级已存在同名 → 不覆盖，提示"用户级已存在 precommit-test，跳过（/skill promote --force 覆盖）"。

**审批 UI**：**新建 `skill-dialog.tsx`**（基于 dialog 模式，**不复用 permission-dialog**——后者是 allow/deny 3 态，skill 审批是 accept/reject/edit/promote 4 操作 + SKILL.md diff 展示 + 安全扫描结果，语义不同，见 §16.3）。

### 6. 安全扫描（security-scan.ts）

**规则集**（照 openclaw `scanner.ts:224-268` SKILL_CONTENT_RULES，**增强锚定 + 中文注入 + base64 外泄**）：

| 规则 | 级别 | 模式 |
|---|---|---|
| shell-pipe-to-shell | critical | `curl\|wget ... \| sh\|bash` |
| secret-exfiltration | critical | `process.env` + `fetch\|curl\|wget\|http` |
| base64-exfiltration | critical | `Buffer.from(...,'base64')` + `fetch\|http\|net`（绕过明文扫描的外泄） |
| destructive-delete | warn | `rm -rf` **锚定危险根**：`rm -rf /`、`rm -rf $HOME`、`rm -rf ~`、`rm -rf .`（普通 `rm -rf build/` 不误报） |
| unsafe-permissions | warn | `chmod 777` |
| prompt-injection-ignore | critical | 中英：`ignore (all\|previous) instructions` / `忽略(上面\|之前\|所有)指令` |
| prompt-injection-system | critical | 中英：`system prompt\|developer message\|hidden instructions` / `系统提示词\|开发者消息\|隐藏指令` |
| prompt-injection-tool | critical | 鼓励绕过工具审批（中英） |

**三段式强制**（照 openclaw）：
1. **归纳产出时扫**：扫描结果存进提案 record。
2. **accept 前再扫**：双重保险。
3. **critical 自动 quarantine**：critical 计数 > 0 → state=failed → 强制 quarantined，拒绝 apply。

**额外约束**（照 openclaw）：只允许 `SKILL.md`，support files **禁止可执行位**（`mode & 0o111` 检查）；workspace 守卫（路径不逃逸 `.ecode/`）。

### 10. 启发式复杂度评估

**新增纯函数** `src/router/complexity.ts`：

```ts
export type Complexity = 'simple' | 'medium' | 'complex';

/** 启发式评估任务复杂度（零 LLM 成本、可解释、不需训练）。
 *  信号：任务长度(token) + 关键词 + 预估工具数。 */
export function assessComplexity(taskDesc: string, ctx?: { toolCount?: number }): Complexity;
```

**评分信号**（业界依据：ACL「简单=片段查找，复杂=推理+综合」+ Codacy/IBM 复杂度度量 adapted 到**任务描述**——评估时尚未读代码，故用描述级信号非代码圈复杂度）：

| 信号 | simple 倾向 | complex 倾向 |
|---|---|---|
| 关键词（中英） | 错别字/typo、重命名/rename、格式化/format、检查/lint、列表/list、读取/查看/read、状态/status、是什么/what is、显示/show、计数/count、查找/grep | 重构/refactor、优化/optimize、设计/design、架构/architecture、迁移/migrate、重写/rewrite、实现/implement、集成/integrate、新增/feature、调试/debug、改造、梳理 |
| 任务描述长度 | 短（< token 阈值） | 长 |
| 改动范围信号 | 单文件/单点 | 多文件/多函数/多服务/全部 |
| 综合 | 多数 simple → simple | 多数 complex → complex；混合 → medium |

> 关键词内置**中英双语**（用户中文任务 + 代码英文关键词均覆盖）；用户可在 config `complexityKeywords.complex/simple` 追加项目特定术语。
> 起步用简单启发式（Google ML Rules：「simple heuristic ships, complex heuristic unmaintainable」），积累数据后再考虑训练分类器（RouteLLM 式）。

### 12. 接入点 + 跨 provider + 子代理模型可见性

**subagent 派发**——**新增纯函数 `resolveModelForSubagent`**（不改原 `resolveModelForScenario`，见 §17🔴3）：

```ts
// src/router/rules.ts 新增
export interface SubagentRoutingInput {
  personaModel?: string;        // 人设 frontmatter model（最高优先）
  taskDesc: string;             // 子任务描述（供 assessComplexity）
}
export interface SubagentRoutingResult {
  provider: string;
  model: string;
  source: 'persona' | 'complexity' | 'rule' | 'default';  // 供 UI 标注
}

/** 子代理路由：complexityRouting 分支 + 跨 provider 解耦。 */
export function resolveModelForSubagent(
  input: SubagentRoutingInput,
  config: RoutingConfig,
): SubagentRoutingResult;
```

```
优先级（complexityRouting=true 时）：persona.model > complexity 动态 > rules.subagent > default
         ├─ persona 有 model → source=persona，用 persona alias
         ├─ 否则 assessComplexity(taskDesc) → complexity → alias → source=complexity
         ├─ 否则 rules.subagent → source=rule
         └─ 否则 default → source=default
         （provider 一律从解析出的 AliasTarget.provider 取，不再继承 ctx.provider）

complexityRouting=false 时：退回支点22 静态 —— persona.model > rules.subagent > default，行为不变
```

**RoutingConfig 扩展**：加 `complexityRouting: boolean` + `complexity: { simple, medium, complex }` 字段（向后兼容，缺省=false）。

**跨 provider 解耦**：`subagent.ts:116` 注释「provider 继承主代理，仅同 provider 生效」是**实现限制**（非类型限制）。改为 provider 从 `resolveModelForSubagent` 返回的 `AliasTarget.provider` 取 → cheap 走 deepseek、strong 走 glm 可跨 provider 派子代理。前提：provider factory（M2）已支持多 provider。

**子代理模型可见性（用户决策 §0，见 §17🔴5）**——`ToolResult` 加可选 metadata：

```ts
interface ToolResult {
  content: string;
  isError?: boolean;
  metadata?: {                       // 新增可选（向后兼容，其他工具不填）
    model?: string;
    provider?: string;
    routingSource?: 'persona' | 'complexity' | 'rule' | 'default';
  };
}
```

## 15. 风险与取舍

| 风险 | 应对 |
|---|---|
| 记录噪音（正则太宽记一堆无用） | 内置正则保守 + 用户 patterns 可调 + O(N) 窗口去重 + 容量上限 |
| 归纳质量（LLM 造无用 skill） | Ratchet 强制引用证据 + 不投机 + 人工审批兜底 |
| observations 含敏感信息 | **`redact.ts` 自由文本脱敏**（非单值掩码）+ content 截断 + 本地 gitignore |
| 安全（skill 含恶意模式） | 三段式扫描 + critical 强制 quarantine + 禁可执行 + base64 外泄检测 |
| config JSONC 迁移 | 零迁移（标准 JSON 是合法 JSONC）+ 扩展现有 strip（不引依赖） |
| 跨 provider subagent 性能 | 同 provider 内快路径保留；跨 provider 仅 alias 命中时 |
| 记录回调阻塞主循环 | appendFileSync 单次 < 1ms + 失败静默降级（不影响主循环）；若实测有感知改 async |
| 主对话模型混淆（用户以为被路由） | status-bar 不加路由标记 + 文档明确"主对话只 /model 切换" |

## 16. UI 设计（TUI）

> 原则：**最小新组件**——绝大多数 UI 是现有模式的组合（picker-list、dialog、spinner、status-bar、markdown 着色）。唯**审批需新建 `skill-dialog.tsx`**（4 操作语义超出现有 permission-dialog，见 §16.3）、**子代理气泡需扩展渲染 metadata**（§16.5）。

### 16.1 `/skill-gen`（归纳触发）

输入 `/skill-gen` + Enter：
- **归纳中**：`activity-indicator` + 文本「🔄 归纳中…（读取 N 条观察，分 M 批）」
- **无记录**：「暂无观察记录。开启 `skillCapture.enabled` 后，使用中会自动记录修正/偏好。」
- **素材不足**（Ratchet 判定记录不够）：「素材不足，继续记录（需命中修正/偏好正则）。已记录 N 条。」
- **pending 达上限**：「待审批提案已达上限（50），请先 `/skill` 审批腾出空间。」
- **完成**：「✓ 归纳完成，生成 K 个提案。输入 `/skill` 审批。」

### 16.2 `/skill`（审批 picker，复用 picker-list）

```
❯ precommit-test      提交前必跑 npm test        v1
  format-style        prefer fs.promises         v1
  ci-check            CI 失败先查日志            v1
                                          [↑↓ 选择 · Enter 详情 · Esc 返回]
```
- PickerItem 扩展可选 `meta?` 字段（放 version，右侧 muted 显示）。
- 空列表：「暂无待审批提案。用 `/skill-gen` 从观察记录归纳。」
- Enter → 进提案详情 skill-dialog（16.3）。

### 16.3 提案详情 + 审批（新建 `skill-dialog.tsx`）

> 不复用 permission-dialog：后者是 allow/deny 3 态权限闸；skill 审批是 **accept/reject/edit/promote 4 操作** + 需展示 **SKILL.md 正文 diff** + **安全扫描结果**，语义/信息量不同，强行复用会扭曲。基于现有 dialog 框架新建专用组件。

```
┌─ Skill 提案：precommit-test ─────────────────────────┐
│ description: 提交前必跑 npm test                      │
│ evidence（归纳依据）：                                │
│   • [08-09 21:35] "下次提交前先跑 npm test（已脱敏）" │
│ ─────────────────────────────────────────────────── │
│ # 提交前测试                                          │
│ 提交代码前必须运行 `npm test` 确认全绿…              │
│ ─────────────────────────────────────────────────── │
│ 🔒 安全扫描：clean（0 critical · 0 warn）            │
└──────────────────────────────────────────────────────┘
  [a] accept 项目级   [p] promote 用户级   [e] edit   [r] reject   [Esc] 返回
```
- **critical 安全风险**：`[a]`/`[p]` 禁用，显「⛔ 检测到 critical 风险（如 `rm -rf /`），已 quarantine，不可 apply」。
- **accept 反馈**：「✓ precommit-test 已落盘（项目级 `.ecode/skills/`），下次会话生效。」
- **promote 反馈**：「✓ precommit-test 已提升到用户级（跨项目复用）。」或「⏭ 用户级已存在 precommit-test，跳过（/skill promote --force 覆盖）。」
- SKILL.md 正文 diff 着色复用现有 markdown 渲染（tool-panel 同源 +/- token）。

### 16.4 模型路由 · status-bar（主对话：只显当前模型，不路由）

**主对话 status-bar 保持现状**——只显示当前模型，**不加路由来源标记**（用户决策：主对话不走路由，模型仅 `/model` 切换）：

```
glm-4.6 @ zhipu              ← 主对话，仅此（与现状 status-bar.tsx:92 一致）
```

> 路由来源标记**只在子场景**（子代理气泡 §16.5、compress/skill 子任务日志），不污染主对话 status-bar。`complexityRouting` 开关不影响主对话显示。

### 16.5 模型路由 · subagent 气泡（显示子代理模型，UI 设计好）

> 用户决策：子代理气泡**显示所用模型 + 路由来源**，尤其跨 provider 时让用户一眼看到子代理走了不同模型。基于 `tool-panel.tsx` 的 `BlockTool` 风格扩展（标题行 + 内容行之间插一行 via 信息）。

**数据来源**：`ToolResult.metadata`（§12，subagent.ts 填充）。

**渲染规则**（信息分层，避免噪音）：
- **子代理模型/提供商与主对话相同 且 complexityRouting=false** → 不显示 via 行（最简，与主一致无需重复）。
- **跨 provider 或不同 model** → 显示 via 行（用户需知晓）。
- **complexityRouting=true** → via 行带路由来源。

**跨 provider 场景**（主=zhipu/glm-4.6，子任务复杂度 medium 走 strong）：
```
┌  ✓ Task (搜索日志关键错误)                          ┐
│  ↳ via glm-4.6 @ zhipu · 路由: 复杂度(medium)        │  ← muted 独立行
│  ↳ 子代理结论第一行…                                  │
│  ↳ 子代理结论第二行…                                  │
└  … +3 more lines (ctrl+o 展开)                      ┘
```

**同 provider 不同 model**（人设指定）：
```
┌  ✓ Task (重构 parser)                              ┐
│  ↳ via glm-4.6 @ zhipu · 路由: 人设                 │
│  ↳ 结论…                                             │
```

**跨 provider**（主=zhipu，cheap 走 deepseek）：
```
┌  ✓ Task (查找符号定义)                             ┐
│  ↳ via deepseek-chat @ deepseek · 路由: 复杂度(simple) │
│  ↳ 结论…                                             │
```

**实现**：`tool-panel.tsx` 的 `BlockTool` 加可选 `metadata` prop，标题行后渲染 via 行（`T.muted` 色）；`ToolDone` 对 `name==='Task'` 透传 metadata。Inline 模式（单行结论）也可在摘要后追加 ` · via deepseek`（紧凑）。

### 16.6 记录层 · 无主动 UI（默默记）

记录是后台行为（agent.ts:373 回调），不打扰对话。透明度反馈走 `/skill-gen`（显示已记录 N 条），不占常态 UI。

### 16.7 配置开关 · 可见性

- `skillCapture.enabled=false`（默认）：完全静默，用户无感。
- 开启后：首次记录时状态栏一次性提示「观察记录已开启（/skill-gen 归纳）」，之后静默。
