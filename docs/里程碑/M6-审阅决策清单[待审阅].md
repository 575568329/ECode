## 各条详述（为什么这么推荐）

### D1 — 范围：分阶段还是一次性
分阶段让最重的多渠道（依赖最多、引入网络/并发/鉴权）放最后，Skills/路由先行验证「复用主干道、不动核心」的假设。一旦发现假设不成立，多渠道还没动，返工成本最低。

### D2 — 多渠道前端形态（最影响工作量）⭐ 重点
- **A 服务化先行（推荐）**：只做本地 HTTP+WS 服务 + 会话路由 + 鉴权，**零前端工程**。让 ECode 从「只能人手动开」变成「能被脚本/IDE 插件/未来 Web 或 IM 程序调用」——这是所有网络渠道的公共前提。
- B 新建 Web：引入 CLAUDE.md §4.2 全套栈（react-dom/vite/zustand/shadcn/tailwind 五件套）+ 评估 Vite 平台二进制（§9.3），**工作量翻倍**。
- C IM 优先：先接飞书 bot，无富 UI。

> ⚠️ 这条取决于**前置事实 2**（§4.2 Web 栈是否为本项目预埋）。若那套栈是「为 Web 预埋」，D2 倾向 B；若是「跨项目模板残留」，A 更划算。

### D3 — 路由用规则还是 LLM 决策
路由目的是省钱。若用 LLM 决策派哪个模型，每次任务多一次（可能 strong 的）调用——省下的钱可能还不够这次决策费。规则映射（compress→cheap / subagent→inherit）查表零成本，可解释、可调。

### D4 — Skills 审批 UI 复用还是新建
proposal 审批（accept/reject/defer）与 M4 permission-dialog **同构（三态审批）**，复用零成本；新建是重复造轮子，违反 §1.7。

### D5 — IM 平台（仅当 D2=C 才需要定）
飞书 bot 长连接 + Webhook API 完善；企微限制多，钉钉次之。若 D2≠C，此条跳过。

### D6 — 支点14 注册式重构归 M5 还是 M6 ⭐审阅暴露
斜杠命令当前 `slash-commands.ts` 硬编码 8 条、`SlashCommandDef` 只有 name+description、**无 execute 回调**。M6 要挂 `/skill` `/accept` `/reject` `/proposals` `/channels`，**必须先做注册式重构**（SlashCommandDef 加 execute + 查表 dispatch）。该重构 M5 阶段3 已规划——放 M5 更顺；若 M6 抢跑自带，则与 M5 重复/冲突。

### D7 — Skills proposal 安全扫描方式 ⭐审阅暴露
功能架构 §支点13 既定：proposal 要经「**安全扫描**」才能转正（夜里初稿漏写，审阅抓回）。推荐「自动扫危险模式（rm -rf / / 密钥 / 外发 URL）+ 人工 review 正文」——自动扫兜底机械性危险，人工把关语义质量；纯人工易漏机械模式。

### D-框架 — 多渠道 HTTP/WS 框架
hono 省样板（路由/中间件现成）但加一个依赖；原生 http 零依赖但要手写路由。倾向待 D2 定了再决（若只做服务化，原生够用）。

   - 需确认：它是「**为多渠道 Web 前端预埋**」还是「**跨项目模板残留**」？这直接决定 D2 倾向（B 还是 A）。
