## 1. 核心架构：投影分离

### 1.1 我们要解决的问题

ECode 有两个角色读取「对话记录」，需求完全不同：

| 角色 | 需求 | 矛盾点 |
|---|---|---|
| **用户**（通过 TUI / `/history`） | 看到完整对话——每一轮说了什么、工具返回了什么，一个字不能少 | 完整 = 长 |
| **LLM**（通过 provider.run） | 上下文要在模型窗口内，否则请求被拒（400） | 完整历史经常超窗口 |

如果把两者合一（同一份 messages 既给 UI 显示又喂 LLM），恢复一个长历史会话时，完整历史塞进 LLM 上下文 → 立即超限 → 触发压缩。**用户只是想回看/继续一个会话，结果一进来就被压缩**——这违背直觉。

### 1.2 ECode 的解法：存储与视图分离（投影）

**history 和 context 是两份数据，各司其职**：

- **History**（`~/.ecode/sessions/<id>.jsonl`）：**给用户看的完整记录**。append-only，永不删改，是唯一真相之源。
- **Context**（喂 LLM 的 messages）：history 的一个**投影**（projection）——读时变换，从全量 history 算出「这次请求该给模型看哪些」。

压缩不修改 history，只改变投影规则（往 history 追加一个 boundary 标记，投影函数据此裁剪）。

```
History（全量 append-only，永不压缩，用户数据）
  │
  ├─ restoreFull() → 全量给 UI（用户看到完整历史）
  │
  └─ buildContextMessages() → 投影给 LLM（只取 summary + 近期 + 新消息）
       ↑ 纯函数，读时变换，找最后一个 boundary 行裁剪
```

### 1.3 投影具体怎么做

**history 存储**：保持 M4 现状（append-only jsonl，每行一条 Message）。压缩时**追加一行 boundary**（不删旧消息）：
```jsonl
{"compact_boundary": true, "summary": "<摘要文本>", "tailStartIndex": 42, "preTokens": 95234}
```

**投影函数** `buildContextMessages(allMessages)`（`src/core/context.ts`，纯函数无副作用）：
1. 从末尾向前找最后一个 `compact_boundary` 行
2. 有 boundary → 返回 `[summary 消息, ...从 tailStartIndex 开始的尾部消息, ...boundary 之后的新消息]`
3. 无 boundary → 返回全量（新会话 / 未压缩过）

**为什么用投影而非「压缩时替换 messages」**：
- history 是唯一真相，投影只读不改 → revert/debug/审计自然成立（被压缩的原文仍在文件里）
- UI 和 LLM 各取所需：UI 全量，LLM 投影子集
- **restore 零成本**：恢复会话 = 全量灌进 messagesRef + 刷 UI；loop 喂 LLM 的是 `buildContextMessages` 投影子集（尊重已持久化 boundary），全量进内存 ≠ 进 LLM context，**天然不会恢复即压缩**

### 1.4 压缩的产物：boundary 追加（非覆盖）

压缩策略执行后，产物是往 history **追加**一行 boundary（旧消息留在前面不删）。这是投影的锚点。多次压缩产生多个 boundary，投影只认最后一个。

> 与「就地替换 messages」的区别：那种做法丢了原文、不可 revert、不可审计。ECode 的 append + 投影是读时变换，永不破坏存储。

## 2. 目标 & 验收

**目标**：长对话不因上下文超限崩溃；工具输出不占满窗口；恢复历史会话不触发压缩；切换 model 不爆炸；对话历史完整保存。

**验收**：
- **投影正确**：`buildContextMessages` 无 boundary 返回全量；有 boundary 返回 summary+tail+新消息
- **restore 不触发压缩**：恢复长历史 → UI 显示全量，LLM context 是投影子集，不立即压缩
- **摘要压缩**：context 超阈值 / `/compact` / 400 兜底 → 摘要旧消息（5 段结构化提取工具信息），往 history 追加 boundary
- **切换 model 不爆炸**：1M→200k 切换 → 预检 + 迭代压缩 + /clear 兜底，不发超限请求
- **History 完整**：history 文件含全部原始消息 + boundary 行（append-only，旧消息不删）
- **摘要质量**：压缩后 LLM 仍引用压缩前的文件路径/技术决策
- **400 不重试**：context-too-long 走压缩，非退避重试
- **token 成本核算**：`/cost` 按模型分桶展示 input/output/cacheRead/cacheWrite 维度 + 总成本 $；cache_read 按 0.1× input 单价（不高估）
- **上下文占比**：StatusBar 显示 `x/window (N%)`，用最近一次 (input+cache_read+cache_creation)/contextWindow
- **usage 缺失降级**：端点返回 usage=null → 回退 chars/4 估算 + UI 标「≈估算」（兼容端点刚需）

**不做**（后置）：
- Memory 系统（跨会话结构化记忆）——独立特性，见附录参考
- AGENTS.md 接 runtime——独立小改（低成本高收益），可与 M5 并行
- 外溢到文件（spill）/ 反应式重放等高级策略——接口已留，未来插件
- Skill/MCP（M6）

## 3. 压缩策略

### 3.1 策略接口：可插拔骨架

**问题**：M5 只需一种压缩手段（摘要），但未来会加更多（工具截断、外溢、按模型定制、反应式重放）。如果把策略硬编码进 loop，每加一种都要动心脏。

**ECode 解法**：策略接口 + 注册制 + 编排器。一种压缩手段 = 一个策略实现，注册到 registry。加新策略 = 写一个新文件实现接口 + register，零改动现有代码。

```ts
// src/services/compaction/strategy.ts
export interface CompactionStrategy {
  readonly name: string                   // 'summarize' / 未来 'spill' 等
  readonly cost: 'free' | 'llm'          // 编排器按成本递增排序
  shouldRun(ctx: CompactionContext): boolean   // 自己判断该不该跑
  run(ctx: CompactionContext): Promise<CompactionResult>  // 执行
}

export interface CompactionContext {           // 传给策略（纯计算输入，不含副作用句柄）
  messages: Message[]           // 当前投影 context（喂 LLM 的子集）
  tokenCount: number            // 当前 token（估算，见 §4）
  effectiveWindow: number       // 有效窗口（contextWindow × 0.9）
  trigger: 'pressure' | 'overflow' | 'manual' | 'model-switch'
}

export interface CompactionResult {            // 策略返回（纯计算输出）
  compacted: boolean            // 是否执行了压缩
  summary?: string              // 摘要文本（strip <analysis> 后）
  tailStartIndex?: number       // 保留区起始 index（投影 tail 起点）
}
```

**编排器**（`src/services/compaction/orchestrator.ts`）：注册策略，按 `cost` 排序。触发时遍历——策略 `shouldRun` 为真就 `run`，拿到 `CompactionResult` 后**由编排器构造 boundary 行追加到 `allMessages` + `history.appendCompactBoundary`**（副作用集中在编排器，策略保持纯计算、易测），直到 token 降到阈值下或策略用尽：
```
触发（pre-turn / on-provider-error / on-model-switch / /compact）：
  for strategy of registry.sortByCost():
    if strategy.shouldRun(ctx):
      await strategy.run(ctx)
      if tokenCount <= threshold: break
```

**触发点 = 事件钩子**（策略不关心何时被调）：
- `pre-turn`：每轮 provider.run 前（预防性，避免发出必失败的请求）
- `on-provider-error`：provider 返回 400 context-too-long（反应式救场）
- `on-model-switch`：切换 model 后（预检，见 §3.3）
- 手动 `/compact`

**M5 只注册一个策略**（精而非多）：
- `summarize`（cost: llm）——摘要压缩（§3.2）

接口已留扩展位：未来需要时，加免模型工具截断 / 外溢到文件 / 按模型定制策略，都是新插件实现 `CompactionStrategy` + register，不动现有代码。

### 3.2 策略：摘要压缩（summarize）

**要解决的问题**：对话累积超出模型窗口时，需要把旧对话浓缩成结构化摘要，只保留近期原文。摘要要提取工具结果的关键信息（文件路径、命令、错误），不只压对话文本。

**ECode 做法**：

**切分**：保留尾部 recent 预算（默认 8000 token）原文不动，头部（旧消息，含旧工具结果）送去摘要。切分点精确到字符（尾部从后累加 token 到预算满，切分那条消息按字符劈开）。

**摘要 prompt**（强制结构化 + 草稿剥离）：
```
只用文本回复，不要调用任何工具。
先在 <analysis> 里按时序分析对话（用户意图、处理方式、关键决策、代码片段、文件名、错误及修复、用户反馈），
再在 <summary> 里按以下结构输出（保持段落顺序，空也保留）：
## 目标
- [用户想完成什么]
## 重要细节
- [约束/偏好/决策及原因/文件路径/函数名/命令/错误信息；无则 (none)]
## 工作状态
### 已完成 / ### 进行中 / ### 受阻
## 下一步
1. [立即的下一步]
## 相关文件
- [文件路径: 为什么重要]
规则：精炼要点不要散文；精确保留文件路径/符号/命令/错误串；不要提及压缩过程。
```
5 段结构化模板确保工具结果的关键信息（grep 匹配了哪些文件、bash 报了什么错、read_file 读了什么）被提取到「重要细节」和「相关文件」段——这些是模型继续工作所需的，不能丢。

产出后 **剥离 `<analysis>` 块**（草稿提升摘要质量，但本身无信息价值，剥离省 token）。只留 `<summary>` 内容作为 boundary 的 summary 字段。

**多次压缩——单一锚定摘要（滚动更新）**：
- 多次压缩时，不是「摘要的摘要的摘要」（信息逐级丢失），而是**更新同一个锚定摘要**
- 有上一次 summary → prompt 改为「用上述对话更新锚定摘要：保留仍成立的细节，删除过时的，合并新事实」+ 上轮 summary
- 上轮保留的 recent（当时原文的尾部）这次也进摘要 context → 滚动演化，不丢连续性

**API 不变量保护**：切分时保留区（tail）如果有 tool_result，必须带回配对的 tool_use。**绝不切断 tool_use/tool_result 对**，否则 API 400。

**失败处理**：
- 摘要 prompt 自身超限（历史太长，prompt 都塞不下）→ 预检闸直接放弃本次摘要
- LLM 调用失败 → 静默跳过，下轮重试
- 连续 3 次失败 → 熔断（停止重试，避免压垮 API）
- 都失败 → 终极兜底：开新窗口（只保 system + 最近一条 user + 「历史已截断」提示），保证可用

### 3.3 切换 model 时 context window 变化

**要解决的问题**：用户在 1M 窗口模型上聊了很多（比如 80 万 token），`/model` 切到 200k 模型——整个 context 瞬间超出新窗口，下一发请求必被拒。

**ECode 做法**（检测 + 提示风险 + 用户主动 /compact）：

切换 model 后 ECode **不自动压缩**——只做检测和提示，压缩由用户主动执行 `/compact` 触发。这和压缩的整体设计一致（压缩是用户决策，不是自动行为）。

1. **检测超限**：切 model 后查新 model 的 contextWindow（§5 models.dev）+ 实时重测量当前 context token（§4）
2. **提示 + 告知风险**：超限 → banner 提示：
   ```
   ⚠ 当前对话（约 X tokens）超出 glm-4.6 的窗口（200K）。
   建议 /compact 压缩后继续。
   注意：压缩会浓缩历史对话，可能丢失部分细节。
   或 /clear 起新会话。
   ```
3. **用户执行 /compact**：跑摘要策略，**迭代压缩**到新窗口限制下。单次摘要可能不够（80 万 → 压一次可能还有 30 万），所以 /compact 在 model-switch 场景下做多次（直到低于新阈值或达重试上限）
4. **兜底**：迭代后仍超 → 告知用户「对话过长，即使压缩后仍超出窗口，建议 /clear 起新会话」

```ts
// 切 model 后：只检测+提示，不自动压缩
onModelSwitch(newModel) {
  const newWindow = resolveContextWindow(newModel, cfg.contextWindow)
  const tokens = estimateTokens(system, buildContextMessages(messagesRef))
  if (tokens > newWindow) {
    setBanner(`当前对话（约 ${tokens} tokens）超出 ${newModel} 窗口（${newWindow}）。` +
              `建议 /compact 压缩后继续（注意：压缩会浓缩历史，可能丢失部分细节）。或 /clear 起新会话。`)
  }
}

// 用户执行 /compact（model-switch 场景做迭代压缩）
async compactForModelSwitch(newWindow: number) {
  let tokens = estimateTokens(system, buildContextMessages(messagesRef))
  for (let i = 0; i < MAX_COMPACTS && tokens > newWindow; i++) {
    await orchestrator.run({ ...ctx, trigger: 'model-switch', effectiveWindow: newWindow * 0.9, allMessages: messagesRef })
    tokens = estimateTokens(system, buildContextMessages(messagesRef))  // 重测
  }
  if (tokens > newWindow) setBanner('压缩后仍超出窗口，建议 /clear 起新会话')
}
```

**为什么要告知风险**：压缩是信息有损操作——摘要会丢细节，LLM 压缩后可能"忘事"（引用不了之前的精确代码/输出）。用户需要知道这个权衡再决定是否压缩，而不是被静默处理。特别是 1M→200k 这种大幅度压缩，信息损失更明显。

## 4. token 用量与成本统计（对齐主流）

**核心思路（对齐 claude-code / codex / aider）**：真实 token 一律来自 API 的 `usage`（服务端实测最准），本地估算只用于压缩触发判定（粗估够用）。在此之上加**成本核算 + 上下文占比 + cache 拆分**——这是主流 Agent CLI 的标配。v10 原本「不统计费用」，经主流调研（claude-code/aider/codex 全有成本）后**改判**（见 §4.4）。

### 4.1 三层模型

| 层 | 数据源 | 用途 |
|---|---|---|
| **真实 token**（计费轨）| API `usage`（input/output/cache_read/cache_creation）| 成本、占比、session 累计、展示 |
| **本地估算**（判定轨）| chars/4（零依赖）| 压缩触发判定、请求前预判、usage 缺失降级 |
| **成本** | 本地 pricing 表（model → $/Mtok）| $/session、$/turn |

> 主流共识：**没有项目用真 tokenizer 计费**——opencode/codex 都是 `chars/4` 或 `bytes/4` 只做触发判定；aider 经 litellm 的 tiktoken 也只用于 `/tokens` 分桶展示。本地 tokenizer 无法还原 chat template / tool schema / 图片 tile，偏低 10-30%；API 的 `input_tokens` 是服务端实测，最准。

### 4.2 真实 token：从 API usage 拿（含 cache 四维）

每轮 `provider.run` 返回 `Delta.usage`，四维：
- `input_tokens`：本轮 context 精确占用（system + 全部历史 + 工具 + 结构开销）
- `output_tokens`：本轮生成
- `cache_read_tokens`：命中 prompt cache 的读取（**单价 ~0.1× input**）
- `cache_creation_tokens`：写 cache（**单价 ~1.25× input**）

**关键**：`input_tokens` 已含完整 context，即便开 cache，`cache_read + cache_creation` 也是 context 的一部分。所以**上下文占比 = (input + cache_read + cache_creation) / contextWindow**（用最近一次请求的 usage，非累加值）。

### 4.3 本地估算：chars/4（压缩判定用，零依赖）

**不装 tokenizer**（各模型 tokenizer 不同，tiktoken 只准 OpenAI，对 GLM 仍是估算）。M5 的本地估算只用于压缩触发判定（精度要求低），用 chars/4：

- **时序**：`input_tokens` 是「这轮请求」的值，在 provider.run **之后**拿到。下一轮 provider.run **之前**判定阈值时，用上一轮 `input_tokens` + 本轮新增消息的 chars/4 估算增量（近似，下轮请求回来就精确）。
- **兜底**：首轮 / 切 model / 压缩后（context 变了旧 usage 失效）→ chars/4 粗估。

```ts
// 存最近一次 usage（provider.run 回调更新，含 cache 四维）
let lastUsage = { input: 0, output: 0, cacheRead: 0, cacheCreation: 0 }

// 阈值判定（每轮 provider.run 前）
const estimated = lastUsage.input + charsToTokens(newMessagesSinceLastRequest)
if (estimated > threshold) { /* 触发压缩 */ }
// provider.run 返回后精确化：lastUsage = response.usage
```

### 4.4 成本核算（本地 pricing 表，★ cache 必须拆）

**v10 原决策「不统计费用」推翻**：理由（改价频繁 + 套餐）不成立——成本是用户最关心的指标，claude-code/aider/codex 全有；本地 pricing 表零依赖、可控，符合「自探测自洽」原则。

**做法**：本地 `src/services/pricing.ts`（`Record<model, {input, output, cacheRead?, cacheWrite?} $/Mtok>`），从 models.dev 或公开定价维护。

**算法**（对齐 claude-code `tokensToUSDCost`）：
```ts
cost = input/1e6 × inputPrice
     + output/1e6 × outputPrice
     + cacheRead/1e6 × cacheReadPrice      // 通常 = 0.1 × inputPrice
     + cacheWrite/1e6 × cacheWritePrice    // 通常 = 1.25 × inputPrice
```

**★ cache 必须拆**：cache_read 单价只有 input 的 ~1/10（claude-code：input $3 vs cache_read $0.3）。不拆、全按 input 单价算，**成本高估 ~10×**。ECode 走 Astron/GLM（prompt caching），这点尤其关键。

**未命中模型**：pricing 表查不到 → 显示「成本未知」（对标 claude-code `hasUnknownModelCost`），不瞎算。

### 4.5 usage 缺失降级（★ 兼容端点刚需）

ECode 走 Astron 兼容端点接 GLM——**Cline bug #9433** 证明兼容端点/企业网关可能返回 `usage: null`，此时 token 统计静默归零（占比永远 0%、成本永远 $0）。

**降级**：usage 缺失时回退本地 chars/4 粗估，UI 标记「≈估算」。这是 ECode 场景的刚需，不是可选优化。

> 呼应：之前修的 token bug（message_start 给 0、真值在 message_delta）正是兼容端点 usage 偏差的体现。守卫覆盖聚合 + 缺失降级一起，保证 GLM 场景 token 统计可用。

### 4.6 展示（StatusBar + /cost）

| 维度 | 展示位置 | 数据 |
|---|---|---|
| 上下文占比 | StatusBar `x/200k (45%)` | 最近一次 (input+cache_read+cache_creation) / contextWindow |
| session 成本 | StatusBar `$0.12` + `/cost` 明细 | 累加各轮 cost（cache 拆分算）|
| cache 明细 | `/cost` input/output/cacheRead/cacheWrite 分桶 | 累加 usage 四维 |

`/cost` 命令（对标 claude-code）按模型分桶展示 5 维 + 总成本；session cost 随 HistoryStore 持久化，resume 恢复。

### 4.7 两个协议的字段对应
- **Anthropic**：`usage.input_tokens / output_tokens / cache_read_input_tokens / cache_creation_input_tokens`（message_start + message_delta，守卫覆盖聚合，见 `anthropic.ts` Translator）
- **OpenAI**：`usage.prompt_tokens / completion_tokens / prompt_tokens_details.cached_tokens`（`stream_options.include_usage` 的 final chunk）→ openai.ts 翻译为 `Delta.usage`

## 5. contextWindow 获取（models.dev 远程库，自动跟进新模型）

**不能硬编码**。模型 context window 各异（GLM-5=200K、DeepSeek=64K、GPT-4o=128K），且模型更新频繁（扩窗、新模型涌现）。主流 API 的 `/models` 端点也不暴露 context window。写死的表很快过时。

**ECode 解法**：四级 fallback，远程社区库为主（自动跟进），config 覆盖为 escape hatch。

**GLM 真实窗口**：GLM-5 = **200K**（[z.ai 官方](https://z.ai/blog/glm-5)，训练期 32K→128K→200K 渐进扩展）。GLM-4.6 = 200K。

**四级 fallback**：
```ts
// src/services/contextWindow.ts
const MODELS_URL = 'https://models.opencode.ai/api.json'  // opencode 维护，Flag 可切 models.dev
const CACHE_PATH = path.join(os.homedir(), '.ecode', 'cache', 'models.json')
const CACHE_TTL_MS = 5 * 60 * 1000  // 5min
// 构建期快照—— esbuild define 注入，离线兜底
declare const ECODE_MODELS_SNAPSHOT: Record<string, unknown> | undefined
const FALLBACK_TABLE = { 'glm-5': 200_000, 'glm-4.6': 200_000, 'glm-4': 128_000, /* 应急最小表 */ }

export async function resolveContextWindow(model: string, configOverride?: number): Promise<number> {
  if (configOverride) return configOverride                          // 1. config 覆盖
  const db = await loadModelsDb()                                    // 2. models.dev（缓存+离线兜底）
  const found = lookupByModelName(db, model)                         //    canonical 名子串匹配
  if (found?.limit?.context) return found.limit.context              //    schema: limit.context
  const fb = matchFallbackTable(model, FALLBACK_TABLE)               // 3. 内置最小表
  if (fb) return fb
  process.stderr.write(`[CONTEXT] 未知模型 ${model}，用安全默认 32000。可配 contextWindow 覆盖。\n`)
  return 32_000                                                       // 4. 安全默认 + 告警
}

/** models.dev 加载：缓存命中→用缓存；过期→后台拉新；首次无缓存→同步拉(10s timeout) */
async function loadModelsDb(): Promise<ModelsDb> {
  // ① 缓存未过期 → 直接读（零网络）
  // ② 缓存过期/不存在 → 拉 MODELS_URL（10s timeout + 2 次退避 + 原子写 tempfile+rename + Flock 跨进程锁）
  // ③ 拉失败/无网络 → 构建期快照 ECODE_MODELS_SNAPSHOT（离线兜底）
}
```

**关键设计**：
- **5min 缓存**：models.dev 更新勤，5min 够新且不频繁拉
- **离线兜底**：构建期打包 models.dev 快照（esbuild define 注入）+ 内置最小表
- **原子写** tempfile + rename（防半截写）+ **Flock 跨进程锁**（防多 CLI 并发刷）
- **10s timeout + 2 次退避**（不卡死启动）
- **匹配**：canonical 名子串（longest-id-first）
- **effective = raw × 0.9**（留 headroom 给 system + 工具 + 输出）

**阈值（绝对值）**：
```
effectiveWindow = resolveContextWindow(model) × 0.9
压缩阈值 = effectiveWindow - 20000   （留 buffer land the plane）
```
GLM-5（200K）：eff 180k → 阈值 160k。

## 6. loop 集成（onBeforeRequest hook + 投影 + 编排器）

### 6.1 onBeforeRequest hook

LoopRunOptions 加：
```ts
// 入参：全量 messagesRef；返回：投影后喂 LLM 的子集（内部可能触发压缩 → 往 messagesRef 追加 boundary）
onBeforeRequest?: (messages: Message[]) => Promise<Message[]>
```

loop 每轮 provider.run 前：
```ts
const ctx = opts.onBeforeRequest
  ? await opts.onBeforeRequest(messages)   // 投影 + 超阈压缩 + 返回子集
  : buildContextMessages(messages)          // 无 hook 也走投影（纯函数默认）
// provider.run(ctx) —— ctx 是投影子集，messages 全量不变（不 mutate）
```

> **投影派**：messagesRef 始终维护**全量**（含 boundary + 被压缩旧消息），loop **不做** `length=0;push`。压缩时编排器直接把 boundary 追加到 messagesRef，`onCompacted` 在编排器内部触发（见 §6.2）。

### 6.2 onBeforeRequest 实现（编排器跑 summarize 策略）

```ts
// cli makeDeps 注入：编排器注册 summarize 策略
const orchestrator = new CompactionOrchestrator()
orchestrator.register(new SummarizeStrategy())

let lastUsage = { input: 0, output: 0, cacheRead: 0, cacheCreation: 0 }
const ctxWindow = await resolveContextWindow(providerReq.model, providerReq.contextWindow)
const threshold = Math.floor(ctxWindow * 0.9) - 20000  // effectiveWindow - buffer

onBeforeRequest: async (allMessages) => {
  // 投影出喂 LLM 的子集（找最后 boundary 裁剪；无 boundary 返回全量）
  let ctx = buildContextMessages(allMessages)
  const estimated = lastUsage.input + charsToTokens(messagesSinceLastRequest)
  if (estimated > threshold) {
    // 超阈值 → 编排器跑 summarize（产出 boundary 追加到 allMessages，旧消息不删）
    const compacted = await orchestrator.run({
      trigger: 'pressure', messages: ctx, tokenCount: estimated,
      effectiveWindow: threshold, allMessages, provider, providerReq,
    })
    if (compacted) {
      onWarn(`已压缩对话（追加 boundary，旧消息保留在历史）`)
      opts.callbacks.onCompacted?.(allMessages)  // boundary 已追加，UI 重建 committed
      ctx = buildContextMessages(allMessages)    // 压缩后重新投影
    }
  }
  return ctx  // 投影子集喂 LLM；allMessages 全量不变
}
// provider.run 返回后精确化
onUsage: (inp, out) => { lastUsage.input = inp; lastUsage.output = out; /* ... 更新 StatusBar/成本 */ }
```

> **CompactionContext 需含 provider + providerReq**：summarize 策略要调 LLM 做摘要，必须有 provider。由编排器注入（cli makeDeps 构造闭包持有）。

### 6.3 400 兜底分支（loop recoverable 内，错误码专属）

```ts
// 注意：此分支必须在 streamError.recoverable 判定之前，否则 CONTEXT_TOO_LONG 被 recoverable 退避重试吞掉
if (streamError.code === 'CONTEXT_TOO_LONG') {
  if (pushedThisRound) messages.pop()  // 回滚半截 assistant
  // 投影派：压缩 = 往 messages 追加 boundary（不 mutate 删旧消息）
  await orchestrator.run({ trigger: 'overflow', messages: buildContextMessages(messages), allMessages: messages, /* ...ctx */ })
  opts.callbacks.onCompacted?.(messages)  // boundary 已追加，UI 重建
  continue  // 下轮重新投影（buildContextMessages 读到新 boundary）
}
```

### 6.4 /compact 命令

CommandRegistry action 扩 `'compact'` + 注册。TuiApp onCommand → `orchestrator.run({ trigger: 'manual', allMessages: messagesRef })` → 追加 boundary 到 messagesRef + `setCommitted`（全量含新 boundary，UI 重建）+ `lastUsage` 重置（下次请求精确化）。

> /compact 在 loop 跑时（runningRef=true）被 inactive gate 挡住（和 /model /history 同机制）。压缩用独立 AbortSignal，不复用 loop 的 abortRef。

### 6.5 前置：errors.ts CONTEXT_TOO_LONG 分类

400 body 防御提取（`e.error?.error?.message ?? e.error?.message ?? e.message`）+ `/context.*(length|window|token)|too long|maximum.*token/i` → `CONTEXT_TOO_LONG` code。**设 `recoverable: false`**——跳过 loop:204 的退避重试，直接走 §6.3 的压缩分支。

## 7. History 持久化 + Context 投影

§1 已讲清投影原理，这里讲持久化实现。

**核心**：history 全量 append-only + 压缩追加 boundary 行 + 投影函数读时变换。

### 7.1 History 存储全量 + boundary 追加（append-only，旧消息不删）
- `FileHistoryStore` 保持 append-only（现状不动）
- **压缩时**：往同一个 `<sid>.jsonl` **追加**一行 boundary（不删旧消息）：
  ```ts
  { compact_boundary: true, summary: '<strip analysis 后的摘要>', tailStartIndex: 42, preTokens: 95234 }
  ```
  旧消息留在前面（history 完整），boundary 是投影锚点。

### 7.2 Context 投影（纯函数，每轮现场算）
新增 `src/core/context.ts`（投影纯函数）：
```ts
/** 从全量 messages 投影出喂 LLM 的 context（无副作用） */
export function buildContextMessages(allMessages: Message[]): Message[] {
  // 找最后一个 compact_boundary 行
  // 有 boundary → 返回 [summary_msg, ...从 tailStartIndex 的尾部, ...boundary 后的新消息]
  // 无 boundary → 返回全量（新会话/未压缩）
}
```
- `messagesRef` = history 的**内存全量镜像**（含 boundary 行 + 被压缩旧消息），loop 每轮对它投影：`buildContextMessages(messagesRef)` 喂 LLM
- history 只在 append（新消息 + boundary）时同步写盘，**loop 不每轮读盘**（messagesRef 即全量源）——避免每轮 `restoreFull` 读全量 jsonl 的性能开销

### 7.3 restore 零成本（★ 不触发压缩）
- `restoreSession`：切 sessionId + `messagesRef = history.restoreFull(sid)`（全量含 boundary 灌进内存）+ 刷 UI（全量渲染）
- context 由 loop 每轮现场投影 → **永远尊重已持久化 boundary → 恢复即投影子集 → 天然不触发压缩**
- UI 在 boundary 处显示"已压缩（移除 N 条）"标记（用户知道这段被压缩过，但仍可回看全量）

### 7.4 两份 restore 接口
- `restoreFull(sid)`：全量消息（UI 展示 / 导出 / 审计用）—— 现有 restore 改名
- `buildContextMessages(restoreFull(sid))`：投影子集（喂 LLM）—— loop 每轮调

### 7.5 HistoryStore 接口扩展
```ts
/** 压缩时追加 boundary 行（append-only，旧消息不删；投影锚点） */
appendCompactBoundary(summary: string, tailStartIndex: number, preTokens: number): void
/** 全量读取（UI/投影用） */
restoreFull(sessionId: string): Message[]  // 含 boundary 行（buildContextMessages 识别）
```

**结果**：history 完整保存（全量 + boundary，用户回看/导出/审计）；context 是投影子集（防超限）；**restore 零成本不触发压缩**。三者职责清晰，单一数据源（history）+ 投影（context）。

## 8. 决策结论（v10）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **M5-D1** | Context vs History | **投影分离**：history 全量 append-only + boundary 追加；context 是 buildContextMessages 纯投影；restore 不灌全量 → 不触发压缩 | 用户需求（history 给用户看，context 给 LLM 用）|
| **M5-D2** | 压缩架构 | **插件化策略骨架**：CompactionStrategy 接口 + registry + 编排器按 cost 排序 + 事件钩子触发。加策略=写插件零改动 | 可扩展性（未来加 spill/overflow/按模型定制都是新插件）|
| **M5-D3** | 默认策略 | **一个**（精而非多）：summarize(LLM 锚定摘要)。接口留扩展位（未来加工具截断/外溢等都是新插件）| 摘要 5 段模板已提取工具信息（路径/命令/错误），不需要独立工具清理级 |
| **M5-D4** | summarize 算法 | **select 切分 + 单一锚定摘要（滚动更新 previousSummary）** | 避免 summary 嵌套漂移 |
| **M5-D5** | 摘要 prompt | **结构化模板（目标/细节/状态/下一步/文件）+ `<analysis>` 草稿剥离** | 编码 Agent 显式保留路径/代码/决策 |
| **M5-D6** | API 不变量 | **tool_use/tool_result 配对保护**（保留区有 tool_result 必带回 tool_use）| 协议硬约束（切断对 → API 400）|
| **M5-D7** | 阈值 | **绝对值**（effectiveWindow - buffer），非百分比；编排器各策略自判 | window 差 10 倍（32k-1M），百分比不准；effectiveWindow = window × 0.9 |
| **M5-D7** | token 用量与成本 | **API usage 四维（input/output/cache_read/cache_creation）+ 本地 pricing 表算成本 + chars/4 压缩判定**（对齐主流，不装 tokenizer） | v10「不统计费用」推翻：成本是用户最关心指标（主流全有）；★ cache 必须拆（read 0.1× input，不拆高估 10×）；usage 缺失降级（兼容端点刚需）|
| **M5-D8** | contextWindow 获取 | **models.dev 远程库 + 四级 fallback**：config 覆盖 > models.dev（5min缓存+构建期快照离线兜底）> 内置最小表 > 安全默认 32k | v7：内置查表会过时；models.dev（opencode 自用+同TS栈可参考+收录智谱）优于 litellm（Python副产品）；★ GLM-5=200K 非 1M |
| **M5-D8** | messages 替换 | **投影派**：messagesRef 维护全量（含 boundary + 旧消息），loop 用 `buildContextMessages` 投影子集喂 LLM，不 `length=0;push`；压缩 = 追加 boundary 消息 | 投影分离（D1）的 loop 侧落地；restore 灌全量即天然不超限 |
| **M5-D9** | CONTEXT_TOO_LONG | 错误码专属分支（非 retryable 死字段）| retryable 只写不读 |
| **M5-D10** | loop 集成 | onBeforeRequest hook（单行注入）| 架构师建议：心脏稳定，多级管线留位 |
| **M5-D11** | history 持久化 | **全量存 + 压缩追加 boundary 行**（append-only 不删旧消息）；context 靠 buildContextMessages 投影 | boundary 是投影锚点 |
| **M5-D12** | 压缩次数上限 | MAX_COMPACTS=2/会话 | 防 summary 的 summary 退化 |
| **M5-D13** | ★ 切换 model 超限 | **检测+提示风险（不自动压缩）；用户 /compact 后迭代压缩到新窗口限制；仍超则 /clear** | 压缩是用户决策；告知风险（有损操作） |
