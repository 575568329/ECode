## 🔴 致命问题（3 条，需先修再进 plan mode）

### F1. `resolveDataDir()` 函数在 ECode 源码中**不存在**，但被当作"现有资产"反复引用
- **现象**：M5 三文档多处写「走 `resolveDataDir`（§9.3 跨平台）」并列为现有资产。全仓 grep **零命中**——现状是分散内联：
  - `src/permission/settings-loader.ts:113` → `resolve(homedir(), '.ecode')`
  - `src/providers/config.ts:28` → `join(homedir(), '.ecode', 'config.json')`
  - `src/index.ts:272,300` → `loadInstructions([homedir(), ...])`
- **影响**：子代理 loader / MCP registry / user 级 hooks 加载都依赖这个"现成入口"。按文档直接调用会编译失败；临时内联又违反 §9.3（跨 Windows/WSL 两套 home 必对不上）。
- **建议**：M5 阶段 0 **新增前置小任务**——把 3 处内联抽成 `src/paths.ts` 的 `resolveDataDir()`（纯提取不改语义，符合 §1.7），M5 各模块复用。或文档明示「本里程碑需新建此函数」。
- **状态**：⬜ 待修（已记录到实施方案阶段 0 待办）

### F2. 「CC 5 种 hook handler 含 `mcp_tool`」**凭空捏造**
- **现象**：技术选型 12-T3 写 CC 有 5 种 handler（command/http/**mcp_tool**/prompt/agent）。
- **核实**：CC 源码 `schemas/hooks.ts:176-189` 实际是 `z.discriminatedUnion('type', [BashCommandHook, PromptHook, AgentHook, HttpHook])`——**4 种持久化**（command/prompt/http/agent）+ 1 进程内 `callback`（不可持久化）。**`mcp_tool` 类型根本不存在**。
- **影响**：损坏文档"禁止臆测"承诺；ECode 若日后对齐 CC mcp_tool 会发现无此先例。
- **建议**：改为「CC 4 种持久化 handler（command/prompt/http/agent）+ 1 进程内 callback；ECode 一期只做 command」。
- **状态**：✅ 已修（技术选型 12-T3）

### F3. ✅ 子代理权限继承：**用户确认 A 方案（继承全部）**——夜间自动化子代理须带权限
- **现象**：
  - **支点讨论记录 L661-663（已锁定）**：子代理「默认继承主代理当前模式 + **全部权限规则**…可被人设 tools 收紧」= **A 方案**（继承全部含 allow）。
  - **M5 技术选型 9-T3 / 方案解析 Q3**：倾向 **B 方案**（只继承 deny，allow 子代理自决）。
- **问题**：文档标为「⚠️ 待审阅」，但实为**重新讨论已锁定决策**。若用户未察觉，会以为是细节待定而非方向反转。
- **A vs B 行为差异**：A 下子代理复用主代理已批准命令不打扰；B 下子代理每个新危险操作弹窗到主对话（防代持）。
- **审阅建议**：**选 B**（只继承 deny）——子代理是"不可信分身"（人设可被构造），最小权限最安全；opencode 双源佐证扎实；ask 归主对话不"打扰"。但**必须用户明确确认是否反转支点 9 已锁定决策**。
- **实施细节**：选 B 后，子代理应有**独立 AllowList 实例**（不回写主），而非实施方案 §五现写的「传同一实例」。
- **状态**：✅ **已确认 A（2026-08-09 用户）**。理由：夜间/无人值守自动化执行时子代理须带权限跑，B 方案每个危险操作弹窗打断、自动化无法跑通。A 方案子代理共享主 AllowList 实例，不建独立实例；人设 tools 可收紧。
