## 一、为什么需要 Provider 抽象（心智模型）

### 1.1 问题本质：两家协议"形状不同"

同样是"调工具读文件"，发给 LLM 的 JSON 长这样：

```
Anthropic（content-block 数组）          OpenAI（tool_calls 字段）
─────────────────────────────           ─────────────────────────
content: [                              message: {
  { type:'tool_use',                      role:'assistant',
    id:'toolu_1',                         content: null,
    name:'read_file',                     tool_calls: [{
    input: { path:'x' }    ← 对象          id:'call_1', type:'function',
  }                                        function:{ name:'read_file',
]                                            arguments:'{"path":"x"}'  ← 字符串
                                           }]
                                         }
```

**三处形状差异**：① block 数组 vs tool_calls 字段；② `input` 对象 vs `arguments` 字符串；③ id 在 block 里 vs 在 tool_calls 里。

结果回传又是两套（Anthropic 塞进 user content 的 `tool_result` block，OpenAI 用独立的 `role:'tool'` 消息）。

### 1.2 解法：中间格式 + 双向翻译（Transform 层）

> **核心洞察**：与其在 agent loop 里到处 `if (isAnthropic) {...} else {...}`，不如定义一套 ECode 自己的中间格式，让 loop 只认中间格式，每家协议写一个翻译器。

```
agent loop ──(ECodeMessage)──► Transform ──► Anthropic/OpenAI 原生格式 ──► SDK
agent loop ◄──(ECodeResponse)── Transform ◄── 原生响应 ◄── SDK
```

这是**适配器模式**（Adapter Pattern）。CCode 的 `toAnthropicMessages()` / `toLangChainMessages()`、LiteLLM、Vercel AI SDK 都是这套思路。ECode 的差异只在"翻译目标用原生 SDK 而非 LangChain"（见第五章）。

### 1.3 反例：Claude Code 为什么没有这层

Claude Code v2.1.220 是**纯 Claude 客户端**——它只说 Anthropic Messages API，没有任何 Anthropic↔OpenAI 翻译。要用 GLM/DeepSeek？必须挂一个**实现了 Messages API 的代理网关**，把翻译推到网关侧。

> Claude Code 的哲学："一种内部格式（Anthropic），翻译推给网关"。ECode 的哲学不同——**ECode 自己就是多模型客户端**，翻译必须在内部完成。所以 Claude Code **不是 M2 的好参考**，它绕开了 M2 要解决的核心问题。

## 二、两家协议差异深挖（M1 第三章的延伸，聚焦"怎么翻译"）

### 2.1 差异全景（翻译要处理的 6 个维度）

| 维度 | Anthropic | OpenAI | ECode 内部格式 |
|------|-----------|--------|---------------|
| **system 位置** | 顶层 `system` 字段 | messages 里 `role:'system'` | `ChatRequest.system` 独立字段 |
| **工具调用请求** | content 里 `tool_use` block | `tool_calls` 字段 | `tool_call` block |
| **工具参数** | `input`（对象） | `arguments`（JSON 字符串） | `input`（对象） |
| **工具结果回传** | user content 的 `tool_result` block | 独立 `role:'tool'` 消息 | `tool_result` block |
| **id 字段名** | `tool_use_id` | `tool_call_id` | `tool_use_id` |
| **终止信号** | `stop_reason`（end_turn/tool_use/max_tokens） | `finish_reason`（stop/tool_calls/length） | `stopReason`（统一 Anthropic 词汇） |

### 2.2 system：哲学差异 → 翻译策略

| | Anthropic | OpenAI |
|---|-----------|--------|
| 放哪 | 顶层独立字段 | messages 第一条 system 消息 |
| 哲学 | system 是"第一公民"，恒定独立 | system 是一条特殊消息 |

**翻译方向**：
- `→ Anthropic`：`ChatRequest.system` 直接放进顶层 `system` 参数
- `→ OpenAI`：`ChatRequest.system` 翻译成 `{ role:'system', content: system }` 插到 messages 数组**最前**

> ECode 选了 Anthropic 的"system 独立"模型（`ChatRequest.system` 独立字段），因为：① 当前 agent 已这么传（[agent.ts:78](../src/agent.ts#L78)）；② 独立字段天然适合未来的 prompt caching（system 恒定→缓存命中）。OpenAI 侧翻译时再插回 messages。

### 2.3 工具调用：双向翻译细节

**内部 `tool_call` → Anthropic `tool_use`**：
```ts
{ type:'tool_call', id, name, input }
  → { type:'tool_use', id, name, input }   // 几乎原样，只改 type 名
```

**内部 `tool_call` → OpenAI `tool_calls`**：
```ts
// 内部是 assistant 消息 content 里的 block
{ type:'tool_call', id, name, input }
  → { id, type:'function', function:{ name, arguments: JSON.stringify(input) } }
// 注意：① 套一层 function 包装；② input 对象要 JSON.stringify 成字符串
// OpenAI 的 assistant 消息 content 设为 null，tool_calls 单独成字段
```

**Anthropic 响应 → 内部**：
```ts
{ type:'tool_use', id, name, input }
  → { type:'tool_call', id, name, input }
```

**OpenAI 响应 → 内部**：
```ts
{ id, type:'function', function:{ name, arguments:'{"path":"x"}' } }
  → { type:'tool_call', id, name, input: JSON.parse(arguments) }
// 注意：arguments 字符串要 JSON.parse 回对象（可能解析失败 → 要兜底）
```

### 2.4 工具结果回传：形状差异最大

**内部 `tool_result` block → Anthropic**：塞进一条 user 消息的 content 数组
```ts
{ role:'user', content:[
    { type:'tool_result', tool_use_id, content, is_error }
]}
```

**内部 `tool_result` block → OpenAI**：翻译成独立 `role:'tool'` 消息（**一条 result 一条消息**，不能合并）
```ts
{ role:'tool', tool_call_id, content }   // 注意 id 字段名变了，且无 is_error（靠 content 文本表达错误）
```

> 这是最容易出 bug 的翻译点：① 字段名 `tool_use_id`↔`tool_call_id` 切换；② OpenAI 一条 result 一条消息；③ OpenAI 没有 `is_error`，错误信息只能写进 content 文本。Transform 单测必须覆盖。

### 2.5 工具定义 schema

**内部 `parameters`（中性）→ Anthropic**：
```ts
{ name, description, input_schema: parameters }   // 字段名 input_schema
```

**内部 `parameters` → OpenAI**：
```ts
{ type:'function', function:{ name, description, parameters } }  // 多一层 function 包装
```

> 这就是为什么 M2 要把 `tools/types.ts` 的 `input_schema` 改名中性 `parameters`——Anthropic 和 OpenAI 的字段名都不同，内部不能偏袒任何一方。

### 2.6 stop_reason 统一

两家词汇不同，agent loop 不该关心差异。ECode 统一到 Anthropic 词汇（CCode 的 `ProviderWrapper` 也是这么做）：

| Anthropic | OpenAI | ECode 统一 |
|-----------|--------|-----------|
| `end_turn` | `stop` | `end_turn` |
| `tool_use` | `tool_calls` | `tool_use` |
| `max_tokens` | `length` | `max_tokens` |

选 Anthropic 词汇作基准，因为 M1 已经在用 `stop_reason`，迁移成本最低。

## 三、能力探测哲学：声明 vs 探测

### 3.1 两种流派

| 流派 | 做法 | 代表 | 优缺点 |
|------|------|------|--------|
| **声明式** | config 里写死模型支持什么 | Claude Code `_SUPPORTED_CAPABILITIES`、CCode `visionModels`、continue.dev | ✅ 零额外请求、可控、可预测；❌ 模型升级要改配置 |
| **探测式** | 发请求试一下看支不支持 | 少数框架 | ❌ 费 token、不可靠、兼容端点常不暴露能力查询 |

### 3.2 ECode 选声明式的理由

1. **真实场景**：GLM/DeepSeek 等兼容端点不暴露 OpenAI 的 `/models` 能力查询，探测式根本没数据源
2. **可预测**：用户显式声明 `capabilities: ['tools']`，行为可控，不依赖网络
3. **业界共识**：三个主流参考项目全是声明式
4. **简单**：`hasCapability(model, 'tools') ? tools : []` 一行判断

### 3.3 Claude Code 的能力枚举（可借鉴清单）

Claude Code 逆向出的 capability 枚举值：`tools`、`vision`、`audio`、`web_search`、`citations`、`interleaved_thinking`、`fast_mode`。ECode M2 先支持 `tools`（核心）+ `vision`（预留），其余等用到再加。

### 3.4 能力缺失时的降级策略

模型不支持 `tools` 时：
- **不发 tools 参数** → 模型纯文本对话，不会因不支持而报错
- agent loop 检测到响应里没有 `tool_call` → 直接 `end_turn` 终止（与 M1 终止逻辑一致）
- 适用场景：用便宜模型做纯问答，或某些端点工具支持不稳时临时降级

## 四、Provider 抽象的陷阱（CCode 踩过的坑，整合）

### 4.1 GLM 等弱实现的 tool_calls 丢失

**坑**：某些 OpenAI 兼容端点在**流式**模式下 `tool_calls` 字段丢失或残缺（GLM 尤其明显）。

**CCode 的解法**：两级 fallback —— ① 从 `additional_kwargs` 提取；② 退化成非流式 `invoke()` 重试。

**ECode 对策**：**M2 非流式，天然免疫**（非流式一次性返回完整 `tool_calls`）。**M3 加流式时必须复刻这个 fallback**，已在 [M2-实施方案](./M2-实施方案.md) §10 风险表标注。

### 4.2 Anthropic 强制角色交替

**坑**：Anthropic API 要求 messages 里 user/assistant **严格交替**，连续两条同 role 会 400。

**场景**：工具结果回传时，连续多个 tool_result push 进 user 消息——ECode 当前已正确处理（多个 result 合进一条 user content 数组，见 [agent.ts:144-154](../src/agent.ts#L144-L154)）。但 Transform 层把内部格式翻成 Anthropic 时，仍要保证不产生连续同 role。

**CCode 的解法**：`mergeConsecutiveRoles()` 合并连续同 role 消息。

**ECode 对策**：Transform `toAnthropicMessages` 末尾加交替校验；DEBUG 模式下断言（学 CCode 的 `assertToolCallResultPairing`）。

### 4.3 tool_use / tool_result 孤儿

**坑**：`tool_use` 没有对应 `tool_result`（或反之）→ Anthropic 400。压缩历史时尤其危险（M3 的核心难点）。

**ECode 对策**：M2 Transform 单测覆盖配对完整性；M3 ContextManager 压缩时**成对保护**（已在 00-开发规划 P0 标注）。

### 4.4 arguments JSON.parse 失败

**坑**：OpenAI 的 `tool_calls[].function.arguments` 是字符串，模型可能生成不合法 JSON（截断、转义错误）。

**ECode 对策**：`fromOpenAIResponse` 里 `JSON.parse(arguments)` 包 try-catch，失败则把该 tool_call 标成 `is_error` 回喂（呼应 M1 的"工具失败回喂"模式 P0-4），让 LLM 自我纠正。

### 4.5 Prompt cache 兼容性

**坑**：Anthropic 的 `cache_control` 是优化字段，第三方代理（很多兼容端点）不认，可能报错。

**ECode 对策**：**M2 不启用 prompt cache**（属性能优化，M5+）。等需要省钱时再加 + 配置开关（学 CCode 的 `CCODE_DISABLE_PROMPT_CACHE`）。

## 五、为什么不用 LangChain（与 CCode 的关键分歧）

### 5.1 CCode 用了，ECode 坚决不用

CCode 的 `OpenAICompatProvider` 用 LangChain 的 `ChatOpenAI` + `toLangChainMessages()`。**ECode 明确不用**，理由：

| 维度 | LangChain | 手写 Transform |
|------|-----------|---------------|
| 透明度 | 消息转换/工具绑定/流式合并全在黑盒里 | 每一行翻译自己掌控 |
| 出问题定位 | 翻框架源码 | 翻自己代码 |
| 协议覆盖 | 框架定义的转换，未必贴合 GLM/DeepSeek 怪癖 | 可针对性兜底（如 §4.4） |
| 依赖体积 | LangChain 重 | `openai` SDK 轻 |

### 5.2 这正是 ECode 的立身之本

00-开发规划的"三个不可动摇的原则"之一就是**"手写核心、拒绝框架黑盒"**——"可以用工具库（如 ai-tokenizer），但核心逻辑不假手于框架"。

Provider 适配**是核心逻辑**（agent 怎么跟 LLM 对话），必须自己写。LangChain 恰恰是把这块逻辑包进黑盒的代表，与 ECode 定位冲突。CCode 选 LangChain 是产品取舍（快速覆盖多模型），ECode 选手写是**学习+自主可控**取舍。

> **结论**：M2 的 `OpenAIProvider` 直接 `import OpenAI from 'openai'`，自己写 `toOpenAIMessages` / `fromOpenAIResponse`。

## 六、流式扩展点（M2 非流式，M3 如何平滑过渡）

### 6.1 M2 的设计为流式预留了什么

M2 虽然非流式，但**内部格式天生流式友好**：

- `ECodeContentBlock` 是 block 数组 → 流式天然是"逐 block 到达"，M3 的 `StreamChunk` 就是对单个 block 的包装
- Transform 的翻译逻辑（block → 协议格式）**流式/非流式通用**，M3 不用重写 Transform，只在 Provider 里加 `stream()` 方法
- `ECodeResponse` 是 block 数组的聚合 → M3 加个聚合器（消费流 → 拼成 ECodeResponse）即可复用现有 loop 逻辑

### 6.2 M3 的增量改动（预演）

```ts
interface ModelProvider {
  complete(request): Promise<ECodeResponse>;          // M2 已有
  stream(request): AsyncIterable<ECodeStreamChunk>;   // M3 新增，不动 complete
}

// ECodeStreamChunk（M3 定义，M2 不实现）
type ECodeStreamChunk =
  | { type: 'text'; text: string }
  | { type: 'tool_call_start'; id; name }
  | { type: 'tool_call_delta'; id; partialInput }
  | { type: 'usage'; inputTokens; outputTokens }
  | { type: 'done'; stopReason };
```

CCode 的 `StreamChunk`（`text|tool_call|usage|done|error|thinking`）可直接借鉴。

### 6.3 为什么 M2 不直接做流式

- **范围纪律**：M2 = 协议适配/配置/能力，流式属 M3+（规划明确）
- **风险隔离**：流式涉及 SSE 解析、增量 JSON 拼接（`input_json_delta`）、UI 流式渲染，是个独立大工程，塞进 M2 会拖垮交付节奏
- **YAGNI**：当前 loop 非流式够用，先把多模型跑通

## 七、关键设计答疑（Q&A）

**Q: 为什么 `ECodeResponse.stopReason` 用 Anthropic 词汇，不用中性词汇（如 'stop'/'tools'）？**
统一必须有基准。选 Anthropic 是因为 M1 已在用 `stop_reason`，agent loop 迁移成本最低（基本不用改）。词汇选哪边是表面问题，关键是 loop 只认一套统一词。

**Q: 配置里的 `models` 为什么用扁平 map，不像 CCode 把 models 放在每个 provider 下？**
扁平 map（`models["glm-5.2"]`）让 `--model glm-5.2` 能 O(1) 查到 provider+能力，无需遍历。CCode 放 provider 下需要反查（`resolveSubProvider`）。ECode 模型数量少，扁平更直接。两种都对，ECode 选更简单的。

**Q: API key 为什么放环境变量（`apiKeyEnv`）而不直接写 config？**
安全。config.json 可能被同步/分享/提交，明文 key 是灾难。`apiKeyEnv` 只存"变量名"，真值在环境里。这也是 M1 的做法（[agent.ts:37-43](../src/agent.ts#L37-L43)）。

**Q: 加新模型到底要不要改代码？**
不用。流程：① config.json 的 `providers` 加厂商（或复用已有）；② `models` 加一条 `{ provider, capabilities }`；③ 设好 `apiKeyEnv` 指向的环境变量。完。`--model 新模型` 直接可用。验收标准里有专门测试证明这点。

**Q: 为什么不抽象出"第三个 Provider"（如 Gemini 原生）？**
00-开发规划已定：Gemini 暂不支持，各家兼容 Anthropic/OpenAI 两套协议即可。真正需要时再加 `GeminiProvider`（实现 `ModelProvider` 接口），架构已为此预留——这就是"加 Provider 改代码、加模型只改配置"的分界。

**Q: Transform 层要不要做 OpenAI→Anthropic（反向翻译）？**
M2 不需要。ECode 内部只有一种格式（ECode 格式），Transform 是"ECode ↔ 协议"双向，不存在"协议A ↔ 协议B"直接翻译。如果未来要做"用 Anthropic 格式的会话切到 OpenAI 模型"，那是 M3 持久化+迁移的事。
