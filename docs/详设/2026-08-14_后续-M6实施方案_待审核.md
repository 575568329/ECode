## 0. 总览：Skill 与 MCP 为什么是同一类问题

两者都是 ECode 的**能力扩展面**，且都通过现有 `ToolRegistry` 接入心脏——心脏（AgentLoop）**完全不感知 skill / mcp 概念**，契合详设 §2.4 铁律。

```
                 ┌─────────────────────────────────────────────────┐
                 │            AgentLoop（心脏·零改动）              │
                 │   反复调 LLM → 执行工具 → 回喂（只认 Tool 接口）  │
                 └───────────────────────┬─────────────────────────┘
                                         │ ToolRegistry（统一分支面）
                                         │
            ┌────────────────────────────┼────────────────────────────┐
            │                            │                            │
   ┌────────▼─────────┐        ┌─────────▼────────┐         ┌────────▼─────────┐
   │  内置工具（M3）   │        │   SkillTool      │         │  MCP 工具（动态） │
   │  ls/glob/grep/   │        │   (单入口 Tool)  │         │ mcp__svr__tool…  │
   │  read/write/     │        │                  │         │  (每个一个 Tool) │
   │  edit/bash       │        │                  │         │                  │
   └──────────────────┘        └────────┬─────────┘         └────────┬─────────┘
                                        │                            │
                              ┌─────────▼──────────┐       ┌──────────▼──────────┐
                              │  SkillRegistry     │       │  McpManager         │
                              │  发现/解析 SKILL.md │       │  连接/拉工具/生命周期│
                              │  注入 system 清单   │       │  官方 SDK Client    │
                              └────────────────────┘       └─────────────────────┘
```

**三句话**：
1. **Skill** = 把"工作流指令"打包成可被 LLM 主动发现的单元。LLM 看 system prompt 里的 skill 清单 → 自主调一个统一 `Skill` Tool → 拿到该 skill 的 markdown body（指令）→ 用已有工具干活。
2. **MCP** = 把"外部工具/服务"通过标准协议接入。ECode 用官方 SDK 连 MCP server → 拉 `tools/list` → 每个 server 工具适配成一个 `mcp__server__tool` 注册进 Registry。
3. **两者都注册成 Tool**，loop 的 `executeTools` / `invokeTool` / `confirm` / AJV 校验路径**全部复用**，心脏零改动。

**与内置工具的关键区别**：

| | 内置工具 | Skill | MCP 工具 |
|---|---|---|---|
| 来源 | 编译期写死 | 文件系统（用户/项目级目录） | 运行期连外部 server |
| 注册时机 | `makeDeps` 启动 | `makeDeps` 启动（扫描目录） | `makeDeps` 启动（连 server 后） |
| readonly | 代码声明 | true（Skill 不直接动文件，给的是指令） | **统一 false**（第三方不可信，默认确认） |
| 本地 AJV 校验 | 是 | 是（skill name 字符串） | **否**（透传给 server 校验） |
| 数量 | 7 个固定 | 1 个 `Skill` Tool（清单在 system prompt） | N 个（随 server 数量） |

# 第一部分：Skill 系统

## S1. 核心架构：三层渐进式加载（progressive disclosure）

Skill 区别于"直接写一大段 system prompt"的关键是**省 token**：metadata 始终在 context（几十字），body 仅触发时加载（可能几 KB），附属文件按需 `read_file`。这是 claude-code / opencode / ZCode 三家的共识设计。

```
┌─ Level 0：清单（始终在 system prompt，每条 ~1 行）──────────────┐
│  <available_skills>                                            │
│    <skill><name>pdf</name><description>生成 PDF 报告…</description></skill>│
│    <skill><name>commit</name><description>…</description></skill>          │
│  </available_skills>                                           │
└────────────────────────────────────────────────────────────────┘
                          │ LLM 匹配 description 自主决定
                          ▼
┌─ Level 1：body（SkillTool 调用后，作为 tool_result 注入一次）────┐
│  <skill_content name="pdf">                                    │
│    # Skill: pdf                                                │
│    生成 PDF 的完整步骤：1. 收集需求 2. 调 pdf 工具…（markdown） │
│  </skill_content>                                              │
└────────────────────────────────────────────────────────────────┘
                          │ LLM 按 body 指令用已有工具干活
                          ▼
┌─ Level 2：附属文件（LLM 按需 read_file skill 目录里的脚本）──────┐
│  ~/.ecode/skills/pdf/templates/report.tex  （LLM 主动去读）      │
└────────────────────────────────────────────────────────────────┘
```

**为什么不让 LLM 一开始就看到所有 skill body**：N 个 skill 的 body 累计可能几万 token，全塞进 system prompt 既贵又稀释注意力。清单只暴露 name + description（"何时用 + 做什么"），LLM 像挑工具一样挑 skill，命中后才加载 body。

---

## S2. 目标 & 验收

**目标**：用户/团队能把可复用的工作流写成 markdown（SKILL.md），ECode 启动时自动发现、LLM 按需自主加载，无需改一行 ECode 代码。

**验收**：
- 放一个 `~/.ecode/skills/commit/SKILL.md`，启动后 system prompt 含其清单项；问"帮我提交"，LLM 自主调 `Skill` 工具加载 commit 指令并执行
- 项目级 `.ecode/skills/` 与用户级同名时，**首个胜出**（按优先级，去重），并在日志记录被覆盖者
- `Skill` 工具调用后，下一轮 LLM 能引用 body 里的具体步骤/文件路径（body 完整注入）
- Skill 不存在 / frontmatter 非法 → SkillTool 返回 `is_error`（recoverable，LLM 自纠），不崩主流程
- **心脏零改动**：`src/core/loop.ts` 不出现 `skill` 字样

**不做**（后置，见附录 C）：
- `fork` 执行模式（起 sub-agent 独立 token budget）—— claude-code 有，MVP 用 inline
- `paths` 条件激活（gitignore glob，文件命中才激活）—— claude-code/JetBrains 有
- body 内联 shell（`` !`command` ``）+ `${SKILL_DIR}` 变量替换 —— claude-code 有，安全/复杂度高
- `url` source（从 git 仓库拉 skill）—— opencode 有
- Skill 携带可执行脚本自动信任 —— 安全风险，后置

## S3. 数据结构：SKILL.md 格式

### S3.1 文件布局

```
~/.ecode/skills/commit/        ← 目录名 = skill 名（若 frontmatter 无 name 则回退目录名）
├── SKILL.md                    ← 必需：YAML frontmatter + markdown body
├── templates/                  ← 可选：附属文件（LLM 按需 read_file）
└── scripts/                    ← 可选
```

**只支持目录格式**（`skill-name/SKILL.md`），不支持单文件（抄 claude-code，目录才能携带附属文件，且 frontmatter 缺 name 时可回退目录名）。扫描 glob：`*/SKILL.md`。

### S3.2 frontmatter（★ AJV 校验，参考 JetBrains 规范 + opencode 极简）

```yaml
---
name: commit                       # 必填。正则 ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$，1-64 字符，无连续连字符
description: 按约定生成提交信息     # 必填。≤1024 字符。要写清"何时用 + 做什么"，触发命脉
when_to_use: 用户要求 git 提交时   # 可选。附加触发线索，注入清单时拼到 description 后
disable_model_invocation: false    # 可选。true=不进清单（仅 /skill 手动用，后置）
---
# commit

## 步骤
1. 跑测试（bash: npm test）
2. git diff 看改动
3. 按约定格式写 commit message
…
```

**校验规则**（集中在一个 `SkillFrontmatterSchema`，frontmatter 解析失败 → 跳过该 skill + warn）：
- `name`：正则 `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`，1-64 字符。缺失 → 回退目录名
- `description`：必填，≤1024 字符。缺失 → **回退到 body 第一段**（JetBrains 做法）
- `when_to_use`：可选 string
- 未知字段：忽略（前向兼容，不报错）

**description 写作要点**（抄 skill-creator 共识）：触发可靠性 100% 取决于 description。要写清"何时用 + 做什么"，倾向稍微"激进"一点（模型倾向 under-trigger）。因清单单条截断到 ~250 字符（注入时），触发词前置。**ECode 无关键词匹配器**——description 就是唯一可发现性来源。

### S3.3 规范模型

```ts
// src/services/skill.ts
export interface SkillInfo {
  name: string                    // 规范化后的 name（目录名回退）
  description: string             // 清单展示用（截断到 250）
  whenToUse?: string
  body: string                    // markdown 正文（去 frontmatter）
  baseDir: string                 // skill 目录绝对路径（附属文件相对它）
  source: 'user' | 'project'      // 发现层级（去重/日志用）
}
```

## S4. 流程

### S4.1 发现（多目录分层 + 首个同名胜出）

抄 claude-code + ZCode 的分层模型，两层（MVP，插件级后置）：

| 优先级 | 目录 | 用途 | 数据分层归属 |
|---|---|---|---|
| 1（高） | 项目级 `<cwd>/.ecode/skills/`（从 cwd **向上遍历到 home**，每层都扫） | 团队共享（入库） | 项目级 |
| 2（低） | 用户级 `~/.ecode/skills/` | 个人习惯（不入库） | 用户级 |

> 注：优先级"项目级 > 用户级"——项目级更具体（如某仓库特有的 commit 约定），覆盖个人默认。去重按 **realpath 规范化 + name**，首个同名胜出，被覆盖者写 LogStore（`event: skill_shadowed`）。

**跨平台**（呼应 AGENTS §2.5）：用户目录用 `os.homedir()`，路径内部一律正斜杠，不依赖 shell `~`。项目级向上遍历用 `path.dirname` 循环到 `homedir()` 为止（不到文件系统根，避免扫到无关目录）。

### S4.2 清单注入 system prompt

抄 opencode 的 `<available_skills>` XML 块（比 claude-code 的纯文本 `- name: desc` 更结构化，LLM 解析稳，且与 ECode 既有 reminder 风格一致）。在 `buildSystemPrompt()` 末尾追加：

```ts
// core/system.ts（buildSystemPrompt 加 skills 参数）
export function buildSystemPrompt(skills: SkillInfo[]): string {
  const listing = skills.length === 0 ? '' : [
    '',
    '可用 Skills（按需用 Skill 工具加载具体指令；任务匹配其描述时再用）：',
    '<available_skills>',
    ...skills.map(s => {
      const desc = s.whenToUse ? `${s.description}（${s.whenToUse}）` : s.description
      return `  <skill>\n    <name>${s.name}</name>\n    <description>${truncate(desc, 250)}</description>\n  </skill>`
    }),
    '</available_skills>',
    '调用 Skill 工具时传 skill 的 name。加载后按其指令用已有工具完成任务。',
    '',
  ].join('\n')
  return BASE_SYSTEM_PROMPT + listing
}
```

**清单规模控制**（抄 claude-code 的 token 预算思想，简化）：无 skill 时不输出任何 skill 文本（零开销）；有 skill 时每条 description 截断 250 字符。MVP 不做"清单总 token 预算 + 增量推送"（claude-code 的 `sent` 集合机制）——M5 压缩落地后若清单过大再上增量推送。

### S4.3 触发（SkillTool 工具调用）

注册一个**统一的 `Skill` Tool**（一个 Tool，参数是 skill name）。LLM 看清单 → 自主决定 → 调 `Skill({ skill: "commit" })`。**无关键词匹配**。

```ts
// src/tools/builtin/skill.ts
export const skillTool: Tool = {
  name: 'Skill',
  description: '加载某个 Skill 的具体工作流指令。任务匹配 available_skills 里某项的描述时调用，传入该 skill 的 name。加载后会得到该 skill 的完整步骤指令。',
  readonly: true,                 // Skill 本身只返回指令文本，不动文件
  input_schema: {
    type: 'object',
    properties: { skill: { type: 'string', description: '要加载的 skill name（见 available_skills）' } },
    required: ['skill'],
  },
  execute: async (args, ctx) => {
    const { skill } = args as { skill: string }
    const info = skillRegistry.get(skill)
    if (!info) return { content: `Skill "${skill}" 不存在。可用：${skillRegistry.list().map(s => s.name).join(', ')}`, is_error: true }
    // 抄 opencode：body 作为 tool_result content 返回（<skill_content> XML 包裹）
    return {
      content: [
        `<skill_content name="${info.name}">`,
        info.body.trim(),
        '',
        `该 Skill 的附属文件目录：${info.baseDir}（正文里的相对路径基于此目录，需要时用 read_file 读取）。`,
        '</skill_content>',
      ].join('\n'),
    }
  },
}
```

**为什么 body 走 tool_result（而非 claude-code 的"注入新 user message"）**：ECode 的 Tool 抽象是 `execute → ToolResult.content`。把 body 作为 tool_result content 返回，loop 现有路径（`invokeTool` → `messages.push({role:'user', tool_result})`）原样复用，**零侵入**。LLM 下一轮读到 tool_result 即拿到指令——与 opencode 的 `<skill_content>` 完全一致。claude-code 的 newMessages 注入需要 loop 特判，违反铁律，不抄。

### S4.4 执行（inline）

LLM 拿到 body 后，按其中的步骤用已有工具（bash/read_file/edit_file…）干活。**MVP 只有 inline 模式**——skill body 就是给当前 loop 上下文的指令，不起新 agent、不换 model。`Skill` 工具是一次性的：调用一次、加载一次、LLM 自己消化。

## S5. 接口

```ts
// src/services/skill.ts
export interface SkillRegistry {
  load(): Promise<void>                       // 启动期扫描两层目录 + 解析 frontmatter + 去重
  get(name: string): SkillInfo | undefined
  list(): SkillInfo[]                         // 给 buildSystemPrompt 用
}

// src/tools/builtin/skill.ts
export const skillTool: Tool                   // 注册进 ToolRegistry（makeDeps）
// skillTool 内部依赖 SkillRegistry（构造时注入或模块单例）
```

**集成点**（`src/cli/index.ts` makeDeps）：
```ts
const skillReg = new SkillRegistryImpl()
await skillReg.load()                          // 扫描（启动期同步，量小）
const system = buildSystemPrompt(skillReg.list())
toolReg.register({ ...skillTool, __skillRegistry: skillReg })  // 注入 registry
```

> `skillTool` 持有 `SkillRegistry` 引用的方式：MVP 用模块级单例（skill.ts 导出 `skillRegistry` 单例，skillTool 闭包引用），避免给 Tool 接口加字段。与 `commandRegistry` 单例模式一致。

## S6. 错误处理

| 场景 | 处理 | 归类 |
|---|---|---|
| 目录不存在 / 为空 | 静默，清单为空 | 正常 |
| SKILL.md 读失败（权限/IO） | 跳过 + LogStore warn | 正常（不影响其他 skill） |
| frontmatter 解析失败（YAML 语法错） | 跳过 + warn | 正常 |
| frontmatter 字段非法（name 正则不过 / description 超 1024） | 跳过 + warn | 正常 |
| `Skill` 工具被调不存在的 name | 返回 `is_error` + 列出可用 | recoverable（LLM 自纠） |
| 附属文件 read 失败 | LLM 走 read_file 的既有错误路径 | recoverable |

**铁律**：Skill 系统的任何失败都**不崩主流程**——最坏情况是某 skill 不可用，ECode 仍正常运行。

# 第二部分：MCP 客户端

## M1. 核心架构：Client + Transport + 适配器 + 生命周期

抄 opencode 的四件套骨架（TS、最干净），用官方 SDK（三家源码实证）。

```
┌─ McpManager（生命周期编排）──────────────────────────────────────┐
│  servers: Map<name, { client, status, defs }>                    │
│  start(): 并行连所有已配置 server（急连接，容错）                  │
│  stop():  退出时 SIGTERM 子进程 / 关 HTTP                         │
└────────────────────────────┬─────────────────────────────────────┘
                             │ 每个 server 一个
              ┌──────────────┴──────────────┐
              ▼                              ▼
   ┌─ stdio Transport ──────┐    ┌─ StreamableHTTP Transport ────┐
   │ spawn 子进程           │    │ POST 到 https://host/mcp       │
   │ stdin/stdout JSON-RPC  │    │ （官方 SDK 封装）              │
   │ stderr → LogStore      │    └────────────────────────────────┘
   └───────────┬────────────┘
               │ Client.connect（initialize 握手，SDK 内置）
               ▼
   ┌─ tools/list（拉 server 暴露的工具）──────────────────────────┐
   │  [{ name, description, inputSchema, annotations? }, ...]     │
   └───────────┬──────────────────────────────────────────────────┘
               │ 适配器（convertTool）：mcp__server__tool
               ▼
   ┌─ 注册进 ToolRegistry（每个工具一个 Tool）─────────────────────┐
   │  execute → client.callTool({name, arguments}) → isError?      │
   │  readonly=false（默认确认）/ skipLocalValidate=true（透传）   │
   └───────────────────────────────────────────────────────────────┘
```

**设计共识**（三家源码 + 官方规范）：
1. **用官方 SDK**（`@modelcontextprotocol/sdk`），不自研 JSON-RPC——协议复杂（握手/版本协商/OAuth/取消/进度），价值不在重造轮子。
2. **Transport 用 SDK 的 `StdioClientTransport` / `StreamableHTTPClientTransport`**，差异只在 env 合并策略 + 进程清理。
3. **适配器**把 `tools/list` 的 `{name, description, inputSchema}` 翻译成 ECode `Tool`，是 ECode 最该复刻的核心（opencode `convertTool` ~80 行）。
4. **生命周期管理器**维护状态表，负责启动/关闭/状态广播。

---

## M2. 目标 & 验收

**目标**：用户在配置里声明 MCP server，ECode 启动时连接、拉取工具、注册成 `mcp__server__tool`；LLM 像调内置工具一样调它们，参数透传、结果回喂、错误自纠。

**验收**：
- 配置一个 stdio server（如 `npx -y @modelcontextprotocol/server-filesystem <dir>`），启动后 `mcp__filesystem__*` 工具出现在 ToolRegistry，LLM 能调用
- 配置一个 HTTP server（url + headers），同样能连、拉工具、调用
- 工具命名 `mcp__<server>__<tool>`，跨 server 重名不冲突
- **默认每次调用需用户确认**（ConfirmPrompt 复用 M3），即使 server 声明 readOnlyHint
- server 返回 `isError:true` → 转 `tool_result(is_error:true)`（recoverable，LLM 自纠）
- 某 server 连接失败 → 标记 failed、warn、**不阻塞其他 server 和主流程**（除非 config 标 `required`）
- 用户 Ctrl+C → 透传 AbortSignal，中断当前 `tools/call`
- 退出时子进程被清理（SIGTERM；Windows 用 `taskkill` 或进程树终止），不留孤儿
- **心脏零改动**：loop.ts 不出现 `mcp` 字样

**不做**（后置，见附录 C）：
- resources / prompts（MCP 另两类原语）—— MVP 只 tools；但 `tools/call` 返回的 `resource_link` / embedded resource content 要能渲染成文本
- OAuth（HTTP server 鉴权）—— MVP 只支持静态 `headers`（Bearer token / API key）；交互式 OAuth 后置
- elicitation（server 反向问用户输入 / MRTR）—— 新协议特性，后置
- per-tool 审批白/黑名单、`supports_parallel_tool_calls` 声明 —— codex 有，MVP 全默认确认
- 自动重连 —— opencode 也不做（标 failed，手动重连）；后置

## M3. 数据结构

### M3.1 配置 schema（★ 抄业界 de-facto 的 `mcpServers` 结构）

配置来源两处，合并（同名项目级覆盖用户级 + warn）：
- **用户级**：`~/.ecode/config.json` 的 `mcpServers` 字段
- **项目级**：`<cwd>/.mcp.json`（随仓库走、团队共享；**secret 不入库**，用 `${ENV_VAR}` 占位符从环境读，呼应 AGENTS §5.2）

```ts
// src/services/config.ts（Config 增字段）
export interface McpServerConfig {
  /** stdio 与 http 二分（discriminated union，抄 opencode） */
  type: 'stdio' | 'http'
  /** stdio 专属 */
  command?: string                 // 启动命令，如 'npx'
  args?: string[]                  // 如 ['-y', '@modelcontextprotocol/server-filesystem', '/tmp']
  env?: Record<string, string>     // 透传给子进程（合并在 process.env 之上）
  cwd?: string                     // 子进程工作目录（默认当前 cwd）
  /** http 专属 */
  url?: string                     // 如 'https://mcp.sentry.dev/mcp'
  headers?: Record<string, string> // 如 { Authorization: 'Bearer xxx' }
  /** 通用 */
  enabled?: boolean                // 默认 true
  required?: boolean               // 默认 false。true=连接失败视为 fatal（抄 codex）
  timeout?: number                 // 连接 + 单次调用超时 ms，默认 30000
}
export interface Config {
  // ...既有字段
  mcpServers?: Record<string, McpServerConfig>
}
```

**配置示例**（`.mcp.json`）：
```jsonc
{
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "C:/Users/me/Desktop"]
    },
    "brave-search": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-server-brave-search"],
      "env": { "BRAVE_API_KEY": "${BRAVE_API_KEY}" }   // 占位符从环境读，不入库
    },
    "sentry": {
      "type": "http",
      "url": "https://mcp.sentry.dev/mcp",
      "headers": { "Authorization": "Bearer ${SENTRY_TOKEN}" }
    }
  }
}
```

**`${ENV_VAR}` 占位符解析**：加载时把 `${XXX}` 替换成 `process.env.XXX`，缺失则 warn 并跳过该 server（密钥缺失不崩）。呼应 AGENTS §5.2「密钥优先从环境变量读」。

### M3.2 规范模型：MCP 工具适配成 ECode Tool

```ts
// src/services/mcp.ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js'
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js'
import { StreamableHTTPClientTransport } from '@modelcontextprotocol/sdk/client/streamableHttp.js'

interface ManagedServer {
  name: string
  client: Client
  status: 'connecting' | 'ready' | 'failed'
  transport: StdioClientTransport | StreamableHTTPClientTransport
  toolNames: string[]              // 该 server 注册的工具全名（退出时反注册用）
}

export class McpManager {
  private servers = new Map<string, ManagedServer>()
  /** 启动期：并行连接所有已配置 server，成功的拉工具并 register 进 ToolRegistry */
  async start(config: Record<string, McpServerConfig>, toolReg: ToolRegistry, logger: Logger): Promise<void>
  /** 退出期：关所有 client（stdio 终止子进程） */
  async stop(): Promise<void>
}
```

**适配器**（核心，抄 opencode `convertTool`）：
```ts
function adaptTool(serverName: string, def: McpToolDef, client: Client, cfg: McpServerConfig, logger: Logger): Tool {
  const fullName = `mcp__${sanitize(serverName)}__${sanitize(def.name)}`   // 双下划线（事实标准）
  return {
    name: fullName,
    description: def.description ?? `MCP tool ${def.name} (from ${serverName})`,
    input_schema: def.inputSchema ?? { type: 'object', properties: {} },    // 透传 server schema 给 LLM
    readonly: false,                  // ★ 默认需确认（第三方不可信），即使 annotations.readOnlyHint
    skipLocalValidate: true,          // ★ 透传给 server 校验（见 M4.4）
    timeout_ms: cfg.timeout ?? 30_000,
    async execute(args, ctx) {
      // signal 透传 + resetTimeoutOnProgress（抄 opencode：空 onprogress 触发 SDK 发 progress token）
      const result = await client.callTool(
        { name: def.name, arguments: args ?? {} },
        undefined,
        { signal: ctx.signal, timeout: cfg.timeout ?? 30_000, resetTimeoutOnProgress: true, onprogress: () => {} },
      )
      // isError → recoverable（LLM 自纠）；协议层 JSON-RPC error → catch 转 toAppError
      const text = renderContent(result.content)   // text 原样 / image→[image] / resource_link→路径
      return { content: text, is_error: result.isError === true }
    },
  }
}
```

**`skipLocalValidate`（Tool 接口新增可选字段）**：
```ts
// tools/interface.ts
export interface Tool {
  // ...既有
  /** true=跳过本地 AJV 校验，参数透传给实现自校验（MCP 工具用：信任 server schema） */
  skipLocalValidate?: boolean
}
// tools/registry.ts validate：
validate(name, input) {
  const tool = this.tools.get(name)
  if (!tool) return { ok: false, error: `工具 ${name} 不存在` }
  if (tool.skipLocalValidate) return { ok: true }   // MCP 工具：透传，由 server 校验
  // ...既有 AJV
}
```
理由：MCP server 是工具实现方，最懂自己的参数约束；server 在 `tools/call` 时参数不对会返回 `isError`/JSON-RPC error，走既有 recoverable 路径。且避免 AJV 对 server schema 里 `$ref`/复杂结构的兼容问题。opencode 同样信任 server schema 不重校验。

## M4. 流程

### M4.1 配置加载与合并

`loadConfig()` 读 `~/.ecode/config.json.mcpServers`（用户级）；`McpManager.start` 额外读 `<cwd>/.mcp.json`（项目级，向上到 home 每层）。合并规则：
- 同名 server：项目级覆盖用户级，warn 记录
- `${ENV_VAR}` 占位符解析；缺失 env → skip + warn
- `enabled === false` → skip

### M4.2 连接（stdio spawn / http）

```ts
// stdio（抄 opencode connectLocal，env 合并 + stderr pipe）
const transport = new StdioClientTransport({
  command: resolveCommand(cfg.command!),    // Windows: npx 可能需 cmd /c 包裹（见 M6 跨平台）
  args: cfg.args ?? [],
  cwd: cfg.cwd ? path.resolve(cwd, cfg.cwd) : cwd,
  env: { ...process.env, ...cfg.env },      // 继承父环境 + 用户覆盖（抄 opencode/claude-code）
  stderr: 'pipe',                           // ★ server 日志不污染 TUI，转 LogStore
})
// stderr → LogStore（category: `mcp.<server>`）
transport.stderr?.on('data', chunk => logger.debug(`mcp.${serverName}`, 'stderr', { text: chunk.toString() }))

// http
const transport = new StreamableHTTPClientTransport(new URL(cfg.url!), {
  requestInit: { headers: cfg.headers ?? {} },
})

const client = new Client({ name: 'ecode', version: PKG_VERSION })
await client.connect(transport)             // SDK 完成 initialize 握手 + 版本协商
```

**连接超时**（抄 opencode + claude-code 兜底）：`Promise.race([client.connect(...), timeout(cfg.timeout ?? 30_000)])`。SDK 内部超时在 SSE 断流时不靠谱，外包一层。

### M4.3 工具发现与注册

```ts
const { tools } = await client.listTools()   // SDK 封装 tools/list
for (const def of tools) {
  const tool = adaptTool(serverName, def, client, cfg, logger)
  toolReg.register(tool)                      // 注册成普通 Tool
  managed.toolNames.push(tool.name)
}
// server 支持 notifications/tools/list_changed 时（SDK 事件），可后续增量同步（后置）
```

**命名**：`mcp__${sanitize(serverName)}__${sanitize(toolName)}`。`sanitize` 把非法字符（非 `[A-Za-z0-9_-]`）替成 `_`。双下划线分隔（claude-code/codex/cursor/ZCode 事实标准），可从名字反解出 server/tool。

### M4.4 调用（isError → recoverable）

LLM 调 `mcp__filesystem__read_file({path})` → loop 现有 `invokeTool` 路径：
1. `validate` → `skipLocalValidate` 直接 `ok:true`（参数透传）
2. `confirm`（readonly=false → ConfirmPrompt，M3 复用）
3. `execute` → `client.callTool({name: 'read_file', arguments})`
4. 返回：`isError===true` → `{content, is_error:true}`（recoverable，LLM 自纠）；JSON-RPC 协议错误 → catch → `toAppError`（recoverable 转 is_error，fatal 抛顶层）

**结果渲染**（`renderContent`）：MCP content 是数组，混合类型：
- `{type:'text', text}` → 原样
- `{type:'image', data, mimeType}` → `[图片: ${mimeType}, ${bytes}B]`（MVP 不支持图像输入，占位）
- `{type:'resource_link', uri, name}` → `[资源: ${name}] (${uri})`
- `{type:'resource', resource:{uri,text}}` → resource.text
- 多个 → `\n---\n` 连接

### M4.5 生命周期（急连接 + 退出清理 + Windows 进程组）

**启动**（`McpManager.start`，抄 opencode 急连接）：
```ts
await Promise.all(Object.entries(config).map(async ([name, cfg]) => {
  if (cfg.enabled === false) return
  try {
    managed = await connectOne(name, cfg)       // connect + listTools + register
    managed.status = 'ready'
  } catch (e) {
    logger.warn('mcp', 'connect_failed', { server: name, message: errMsg(e) })
    if (cfg.required) throw toFatal('MCP_REQUIRED_FAILED', `必需的 MCP server ${name} 连接失败：${errMsg(e)}`)
    // 非 required：标记 failed，不阻塞
  }
}))
```

**退出**（注册到 `process.on('exit')` / SIGINT，呼应 cli/index.ts:104 既有 exit handler）：
```ts
async stop() {
  for (const { client, transport } of this.servers.values()) {
    await client.close()                        // SDK close：stdio 发 SIGTERM 终止子进程
  }
}
```
**Windows 进程组**（AGENTS §2.5 + codex 教训）：`npx`/`node` spawn 的子进程可能再 spawn 孙进程，`client.close()` 只杀直接子进程。Windows 下用 `taskkill /pid <pid> /T`（杀进程树）兜底；POSIX 下进程组（spawn 时 `detached` + `process.kill(-pgid)`）。**MVP 先用 SDK 默认 `client.close()`，孤儿进程问题若复现再上进程树清理**（YAGNI，先验证）。

## M5. 错误处理

| 场景 | 处理 | 归类 |
|---|---|---|
| server 连接失败（spawn ENOENT / 超时 / 握手错） | warn + 标 failed；`required:true` 才 fatal | recoverable / fatal(required) |
| `tools/list` 失败 | 标 failed，已注册的工具保留（若有） | recoverable |
| `tools/call` 返回 `isError:true` | 转 `tool_result(is_error:true)` | recoverable（LLM 自纠） |
| `tools/call` JSON-RPC 协议错误（-32602 unknown tool 等） | catch → `toAppError` → recoverable 转 is_error | recoverable |
| `tools/call` 超时 | Promise.race 超时 → recoverable is_error | recoverable |
| `tools/call` 网络断（HTTP）/ 子进程崩（stdio） | catch → recoverable is_error；stdio 子进程崩后该 server 工具标记不可用 | recoverable |
| 用户 Ctrl+C（AbortSignal） | SDK 透传 signal，stdio 发 `notifications/cancelled`，HTTP 关流 | aborted |
| 退出时子进程未死 | SDK close → 超时强杀（POSIX SIGKILL / win taskkill /T） | — |

**脱敏**（呼应 AGENTS §5.2 + 现有 redact.ts）：`env` 里的 API key、`headers` 的 Authorization 走 `redact.ts` 统一规则；LogStore 记录 MCP 配置时用 `getMaskedConfig` 等价脱敏。

## M6. 跨平台（Windows / Git Bash，呼应 AGENTS §2.5）

- **路径**：`node:path` + 正斜杠，`os.homedir()`，不依赖 shell `~`
- **npx 启动坑**：Windows 上 `npx` 是 `.cmd`，`spawn('npx', ...)` 可能 ENOENT。`resolveCommand` 按 `process.platform` 分流——win32 下若 `command` 是 `npx`/`npm`/`node` 且直接 spawn 失败，包一层 `cmd /c`（官方文档专门提此坑）。不写死，按需探测降级
- **进程清理**：见 M4.5
- **shell**：MCP stdio server 是独立子进程，**不经 Git Bash**（与 bash 工具不同）；直接 spawn `command`（node/npx/uvx/docker 等）

# 决策结论（M6 全部）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **M6-D1** | Skill 触发方式 | **LLM 自主调 SkillTool**（无关键词匹配），清单注入 system prompt | 三家共识：description 是唯一可发现性来源；关键词匹配脆弱 |
| **M6-D2** | Skill body 注入方式 | **作为 tool_result content（`<skill_content>` XML）**，非注入新 user message | 零侵入心脏（loop 现有路径复用）；抄 opencode；claude-code 的 newMessages 需 loop 特判违反铁律 |
| **M6-D3** | Skill 文件格式 | 目录 `skill-name/SKILL.md` + frontmatter（name/description/when_to_use），AJV 校验 | 目录才能携带附属文件；frontmatter 缺 name 回退目录名、缺 description 回退 body 首段 |
| **M6-D4** | Skill 发现层级 | 项目级（cwd 向上到 home）> 用户级；realpath+name 去重，首个胜出 | 项目级更具体覆盖个人默认；抄 claude-code/ZCode |
| **M6-D5** | Skill MVP 范围 | inline 模式 + 两层发现。fork/paths/inline-shell/url-source 后置 | YAGNI；inline + 两层已覆盖核心价值 |
| **M6-D6** | MCP SDK | **官方 `@modelcontextprotocol/sdk@^1.30`** | opencode/codex/claude-code 三家源码实证；API 稳定有参考。`client@2.0` 太新无本地源码，列开放问题 |
| **M6-D7** | MCP transport | **stdio + Streamable HTTP 都做** | stdio 是社区 server 主流（npx/uvx）；HTTP 接云端服务；两者共用 Client，分支小 |
| **M6-D8** | MCP 工具命名 | `mcp__<server>__<tool>`（双下划线） | 事实标准（claude-code/codex/cursor/ZCode）；可反解；防跨 server 冲突 |
| **M6-D9** | MCP 工具确认策略 | **统一默认确认**（readonly=false），即使 readOnlyHint | 规范明示 annotations 不可信；MCP server 是第三方代码；三家共识 |
| **M6-D10** | MCP 参数校验 | **透传给 server**（skipLocalValidate），不本地 AJV | server 是实现方最权威；避免 AJV 对复杂 schema 兼容问题；opencode 同策略 |
| **M6-D11** | MCP 配置 | 用户级 `config.json.mcpServers` + 项目级 `.mcp.json`，合并（项目级覆盖）+ `${ENV_VAR}` | 对齐业界 de-facto；secret 不入库从 env 读（AGENTS §5.2） |
| **M6-D12** | MCP 生命周期 | 启动急连接（并行容错）+ 退出清理（SIGTERM/进程树）；`required` 可 fatal | 抄 opencode 急连接 + codex required 标志 |
| **M6-D13** | MCP env 合并 | `{...process.env, ...userEnv}`（继承父环境） | 抄 opencode/claude-code；ECode 场景需 PATH 等；codex 的 env_clear 太严，后置为可选 |
| **M6-D14** | MCP stderr | pipe → LogStore（category `mcp.<server>`） | server 日志不污染 TUI；呼应 AGENTS §2.7 唯一日志入口 |
| **M6-D15** | resources/prompts | **MVP 不做**（只 tools）；resource_link/resource content 要能渲染 | tools 是主价值且接入点自然；resources 需 TUI 选择 UI；prompts 与斜杠命令重叠 |
| **M6-D16** | Skill/MCP 与心脏关系 | **都注册成 Tool 进 ToolRegistry，loop.ts 零改动** | 契合详设 §2.4 铁律 + 可插拔分支面；最大复用 confirm/AJV/并行串行/错误二分 |

| MCP SDK 大版本断裂（`client@2.0` 无状态协议） | 中 | 锁 `^1.30`；适配层薄（只依赖 Client/Transport/callTool），升级面小；列开放问题持续关注 |
| MCP server 是第三方代码，可能有副作用/不安全 | 高 | **默认每次确认**（D9）；readonlyHint 不豁免；未来可加 server 级信任配置 |
| stdio 子进程孤儿（Windows 进程组） | 中 | SDK close 兜底；Windows taskkill /T、POSIX 进程组；MVP 先验证默认 close，复现再上进程树 |
| npx 在 Windows ENOENT | 中 | resolveCommand 平台分流 + cmd /c 降级（官方文档已知坑） |
| server schema 含 `$ref`/复杂结构，AJV 不兼容 | 低 | skipLocalValidate 透传（D10），根本不经本地 AJV |
| Skill 清单随数量膨胀吃 system prompt token | 低 | 无 skill 零开销；description 截断 250；M5 压缩落地后可上 claude-code 的增量推送 + token 预算 |
| Skill body 过大（KB 级）单次注入 | 低 | body 是 tool_result（不进 system prompt，M5 Tool Clearing 会清）；进度式加载本就为省 token |
| description 写得差导致 LLM under-trigger | 中 | 文档示例 + 校验时 warn description 过短；抄 skill-creator「写得稍微激进」建议 |
| `.mcp.json` 入库泄露 secret | 高 | `${ENV_VAR}` 占位符从环境读；文档强调 secret 不入库；脱敏 |
| MCP 工具与内置工具重名（如 server 也叫 read_file） | 低 | `mcp__` 前缀天然隔离；内置工具无前缀 |

## B. 调研依据（精炼；完整三家对比见调研记录）

**Skill**：
- `claude-code-main`（概念发源地）：Skill = PromptCommand 子集 + 统一 SkillTool；frontmatter 字段最全（15+）；清单 system-reminder 注入 + 1% token 预算 + 增量推送；fork/paths/inline-shell 能力最强。关键文件 `src/skills/loadSkillsDir.ts`、`src/tools/SkillTool/SkillTool.ts`
- `opencode`（TS，骨架最干净）：frontmatter 极简（name/description/slash）；清单 `<available_skills>` XML 注入 system prompt；body 作为 tool_result `<skill_content>` 返回；Effect SystemContext 增量更新。关键文件 `packages/core/src/skill.ts`、`packages/core/src/skill/guidance.ts`、`packages/opencode/src/tool/skill.ts`
- `jetbrains-cc-gui`（规范参考）：frontmatter 校验逻辑最清晰（name 正则、desc 长度、回退策略）—— 直接作 ECode AJV 规则参考
- **共识**：三层渐进式加载 / LLM 自主调 SkillTool（无关键词匹配）/ Skill 是正交扩展点（不定义新工具）/ 多目录分层首个胜出

**MCP**：
- `opencode`（TS，最贴合）：用官方 SDK 1.29；`convertTool` ~80 行最干净；急连接 + Effect Service；stdio `{...process.env,...env}`；命名 `server_tool`（单下划线，ECode 不抄此点，用双下划线事实标准）。关键文件 `packages/opencode/src/mcp/index.ts`、`catalog.ts`
- `codex`（Rust，最严谨）：`required` 标志（失败可 fatal）；`env_clear()`+白名单（安全最高）；命名 SHA1 去重（为 ≤64B，ECode 无此约束不抄）。关键文件 `codex-rs/config/src/mcp_types.rs`、`rmcp-client/src/stdio_server_launcher.rs`
- `claude-code`（TS，超时兜底）：`Promise.race` 外包超时（SDK 内部超时不靠谱）；单例 stub MCPTool 克隆展开；默认超时 ~27.8h（ECode 用 30s 合理默认）。关键文件 `src/services/mcp/client.ts`
- **共识**：用官方 SDK（无人自研 JSON-RPC）/ 工具命名加 server 前缀 / 默认每次确认 / isError→recoverable / stderr pipe / AbortSignal 透传 + resetTimeoutOnProgress

**协议规范**（modelcontextprotocol.io）：
- MCP = Anthropic 2024-11 开源的 LLM 应用 ↔ 外部工具/数据标准协议（JSON-RPC 2.0），现捐赠 Linux Foundation 旗下 Agentic AI Foundation
- 两类 transport：stdio（spawn 子进程，换行分隔 JSON-RPC）/ Streamable HTTP（POST，可选 SSE 流）
- 三类原语：tools（model-controlled，主价值）/ resources（application-driven，只读数据）/ prompts（user-controlled，模板）
- `tools/list` 返回 `{name, description, inputSchema, annotations?}`；`tools/call` 返回 `{content[], isError}`——isError 二分与 ECode recoverable 契约对齐
- 工具 `name` 跨 server 不保证唯一 → client 应前缀消歧（`mcp__server__tool` 惯例来源）

## C. 开放问题 / 后置项

**Skill 后置**：
- fork 执行模式（sub-agent 独立 token budget）—— claude-code 有
- `paths` 条件激活（gitignore glob）—— claude-code/JetBrains 有
- body 内联 shell `` !`cmd` `` + `${SKILL_DIR}` 变量 —— claude-code 有，需安全评估
- `url` source（git 仓库拉 skill）—— opencode 有
- 清单 token 预算 + 增量推送（已发过的 skill 不重发）—— claude-code 有；M5 压缩落地后视清单规模再上
- `/skill` 斜杠命令手动列出/触发（配合 `disable_model_invocation`）

**MCP 后置**：
- resources / prompts 原语（MVP 只 tools）
- OAuth（HTTP 交互式鉴权）—— MVP 只静态 headers
- elicitation / MRTR（server 反向问用户）—— 新协议特性
- per-tool 审批白/黑名单、`supports_parallel_tool_calls` —— codex 有
- 自动重连（server 断线后重连 + 工具重注册）—— opencode 也不做
- `notifications/tools/list_changed` 增量同步工具
- `env_clear` 高安全选项（抄 codex，作为 server 级可选配置）
- **协议演进**：`@modelcontextprotocol/client@2.0`（无状态核心 / `server/discover` 取代 initialize / 拆包）—— 持续关注；MVP 用稳定的 `sdk@1.30`，适配层薄，未来升级面小

**里程碑建议**：Skill（S-P1~P4）与 MCP（M-P1~P7）解耦，可分两个 PR 独立交付、独立验收。建议 Skill 先行（零依赖、纯本地、风险低），MCP 后行（引入外部依赖 + 子进程 + 网络）。
