# M3.5 TUI 对话布局重构设计文档

> **目标**: 重构 ECode 的 REPL 对话显示结构，解决"视觉区分不明显、对话混乱"问题
> **技术栈**: ink 7 + React 19（不变）
> **参考**: OpenCode (opencode)、OpenClaw (openclaw)、InkUI 组件库
> **状态**: Phase 1 已落地（2026-08-06）；Phase 2-4 待实施

## 一、问题分析

### 1.1 当前 ECode 对话布局的痛点

通过实际运行 `ecode` REPL，当前对话显示存在以下问题：

| 问题 | 描述 | 严重度 |
|------|------|--------|
| **角色区分弱** | 用户消息和 assistant 消息视觉差异太小，难以一眼区分 | P0 |
| **工具展示凌乱** | 所有工具都用同样的面板展示，简单工具（如 read）也占多行 | P0 |
| **信息层级扁平** | 文本、工具、状态混在一起，没有清晰的视觉层次 | P0 |
| **缺少元数据** | 看不出用的是什么模型、用了多少 token、耗时多久 | P1 |
| **思考过程无区分** | LLM 的思考/规划过程与最终回答混在一起 | P1 |
| **滚动体验差** | 历史消息和当前流式区域没有明确分隔 | P2 |

### 1.2 参考项目对比

| 维度 | OpenCode | OpenClaw | ECode (当前) |
|------|----------|----------|-------------|
| **框架** | `@opentui/solid` + SolidJS | `@earendil-works/pi-tui` (OOP) | ink 7 + React 19 |
| **布局** | scrollbox + sidebar(宽屏) | Container 手动管理 | Static + 动态区 |
| **User 消息** | 左边框 + 背景色 + padding | 背景色 Markdown | 无明显标记 |
| **Assistant 消息** | paddingLeft 缩进 + Markdown 渲染 | HyperlinkMarkdown 组件 | 纯文本流 |
| **工具展示** | **双模式**: Inline(单行) / Block(多行) | Box 折叠面板 | 统一面板 |
| **思考过程** | ReasoningPart 折叠组件 | 无 | 无 |
| **元数据行** | `▣ Code · model · 3.2s` | footer: token/耗时 | StatusBar 单独行 |
| **Diff 显示** | 自研 `<diff>` 组件(split/unified) | 无 | 无 |
| **Sidebar** | 宽屏自动展开(文件列表/上下文) | 无 | 无 |

## 二、业界最佳实践（调研结论）

### 2.1 终端 TUI 设计原则

来源: [vue-tui Terminal UI Best Practices](https://github.com/Simon-He95/vue-tui/blob/main/docs/terminal-ui-best-practices.md)、[Building a Terminal UI Broke My Brain](https://dev.to/manasmudbari/building-a-terminal-ui-broke-my-brain-hpc)

1. **行×列思维，不是像素思维** — 终端布局就是行×列的网格，每个字符占一个固定位置
2. **Flexbox 式布局** — Ink 内部用 Yoga（Facebook Flexbox 引擎），支持 flexDirection/alignItems/justifyContent
3. **动态宽度适配** — 窄终端（<80列）和宽终端（>120列）需要不同布局策略
4. **Buffering 流式内容** — 流式 Markdown 在渲染前需要 buffer，避免半解析的 token 破坏布局
5. **最少 DOM（Screen Cell）更新** — 静态内容（历史消息）不应参与重绘

### 2.2 Chat UI 布局模式

来源: [AI Chat UI Best Practices for 2026](https://thefrontkit.com/blogs/ai-chat-ui-best-practices)、[Streaming chat scroll to bottom with React](https://davelage.com/posts/chat-scroll-react/)

1. **Static/Dynamic 分区** — 历史消息冻结（不重绘），只有当前流式区域动态更新
2. **Sticky Scroll** — 流式输出时自动滚到底部，用户上翻时暂停自动滚动
3. **角色视觉分隔** — 用户消息和助手消息必须有明确的视觉区分（左边框、背景色、缩进）

### 2.3 工具调用展示模式

来源: OpenCode 源码、[awesome-cli-coding-agents](https://github.com/bradagi/awesome-cli-coding-agents)、[AI Agent CLI Frameworks](https://zylos.ai/research/2026-02-21-ai-agent-cli-frameworks/)

业界共识：**工具调用分两级展示**

| 级别 | 触发条件 | 展示方式 |
|------|---------|---------|
| **Inline**（内联） | 工具执行中 / 执行完成但无输出 / 简单工具 | 单行显示，图标 + 状态 + 简要信息 |
| **Block**（块） | 工具有大量输出 / diff / 需要用户审阅 | 多行面板，带左边框、背景色、可折叠 |

### 2.4 Ink 生态滚动方案

来源: [ink-scroll-list](https://www.npmjs.com/package/ink-scroll-list)、[InkUI](https://inkui-lib.vercel.app/)、[ink Issue #222](https://github.com/vadimdemedes/ink/issues/222)

| 方案 | 说明 | 适合度 |
|------|------|--------|
| `<Static>` (ink 内置) | 子元素渲染一次后冻结，适合历史消息 | ✅ 已在用 |
| `ink-scroll-list` | 社区滚动列表组件 | ⚠️ 可能与 Static 冲突 |
| 自定义 scrollbox | 基于 ANSI escape codes 实现 | ❌ 复杂度高 |
| ink Box + overflow: hidden | 模拟滚动（只显示最近 N 行） | ⚠️ 简单但不够 |

**结论**: 保持 `<Static>` 用于历史消息 + 动态区只显示当前轮次的方案，这是 ink 下最稳定的选择。

### 3.2 组件详细设计

#### 3.2.1 UserMessage — 用户消息

**核心改动**: 加左边框 + 背景色 + padding，让用户消息一眼可辨

```
┌─ 实现 (ink Box) ────────────────────────────────────────┐
│ ❰ 灰色左边框                                                 │
│ ████ 背景色背景                                              │
│   paddingLeft=2, paddingTop=1, paddingBottom=1               │
│   "读一下 package.json 告诉我依赖"                              │
│   (可选) 时间戳: 14:30:25                                    │
└─────────────────────────────────────────────────────────┘
```

```tsx
// props: { text: string; timestamp?: string }
<Box
  borderLeft
  borderColor={theme.userBorder}       // 灰色或用户选择的颜色
  paddingLeft={2}
  paddingTop={1}
  paddingBottom={1}
  marginTop={1}                        // 与上方消息留一行间距
>
  <Text>{props.text}</Text>
  {props.timestamp && (
    <Text dimColor> {props.timestamp}</Text>
  )}
</Box>
```

**Ink 可行性**: ⚠️ **修正（见 §9.6-7.1）**：单独 `<Box borderLeft>` 不渲染——ink 必须配 `borderStyle="single"` + 显式关另三边。Phase 1 已抽 `leftBorder` props 实现。

#### 3.2.3 工具展示 — 双模式（Inline + Block）

**关键设计决策**: 参照 OpenCode，工具分两种展示模式

##### Inline 模式（单行内联）

适用：执行中 / 简单完成 / 无大量输出

```
✗  bash: rm -rf node_modules/     ← 失败 (红色)
✓  read: package.json            ← 完成 (绿色/灰色)
⏳  bash: npm install             ← 执行中 (带 Spinner)
```

```tsx
// InlineTool 组件
<Box paddingLeft={3} marginTop={0}>
  <Text color={statusColor}>{statusIcon}</Text>
  <Text dimColor> {toolName}: </Text>
  <Text>{summary}</Text>
</Box>
```

| 状态 | 图标 | 颜色 |
|------|------|------|
| 执行中 (pending) | `⏳` 或 Spinner | theme.text |
| 完成 (completed) | `✓` | theme.success (灰绿) |
| 失败 (error) | `✗` | theme.error (红) |
| 被拒绝 (denied) | `⊘` | theme.warning + 删除线 |

##### Block 模式（多行面板）

适用：有大量输出 / diff / 需要审阅

```
❰ 深色左边框
████ toolBg 背景
  # $ npm run build
  > Added 3 files, removed 1
  > Build success in 2.1s
  (点击 Enter 展开完整输出 / 再次点击折叠)
```

```tsx
// BlockTool 组件
<Box
  borderLeft
  borderColor={theme.toolBorder}
  paddingLeft={2}
  paddingTop={1}
  paddingBottom={1}
  backgroundColor={theme.toolBg}
  marginTop={0}  // 紧跟 InlineTool, 不额外留间距
>
  <Text dimColor>{title}</Text>
  {expanded && <Text>{output}</Text>}
  {!expanded && overflow && (
    <Text dimColor> ... ({truncatedLines} more lines, Enter to expand)</Text>
  )}
</Box>
```

**切换逻辑**:
```tsx
const shouldShowBlock = completed && (hasOutput || hasDiff || isError);
const shouldShowInline = !completed || (!hasOutput && !hasDiff);
```

**Ink 可行性**: ✅ `<Box borderLeft backgroundColor={hex}>` 是 ink 原生支持

#### 3.2.4 思考/规划过程（ReasoningPart）

**设计**: 可折叠的思考区域，默认展开一行摘要

```
+ Thought: 分析项目结构...     ← 折叠态 (单行, 点击展开)
- Thought: 详细分析内容...    ← 展开态 (多行, markdown)
```

```tsx
// ReasoningPart 组件
<Box paddingLeft={3} marginTop={1}>
  <Box onPress={() => setExpanded(!expanded)}>
    <Text color={theme.thinking}>
      {expanded ? '- ' : '+ '}
      Thought: {title}
      {done && ` · ${duration}s`}
    </Text>
  </Box>
  {expanded && (
    <Box paddingLeft={2} marginTop={1}>
      <Text dimColor>{thinkingContent}</Text>
    </Box>
  )}
</Box>
```

**Ink 可行性**: ⚠️ ink 不支持 `<Box onPress>`。替代方案：
- 用全局键盘监听 + 状态机
- 或用 `useInput` hook 在对应行拦截按键

### 3.3 间距与颜色规范

#### 间距规范

```
// 消息之间
UserMessage ↔ AssistantMessage: marginTop=1 (一行间距)
AssistantMessage 内部组件: marginTop=0 (紧凑排列)
InlineTool ↔ BlockTool: marginTop=0 (紧贴)

// 区域之间
Static(历史) ↔ Dynamic(流式): 无额外间距(自然衔接)
ChatView ↔ ToolPanel: 无间距(ToolPanel 仅展开时出现)
ChatView ↔ StatusBar: 自然衔接
StatusBar ↔ InputBar: 无间距
```

## 四、Ink 技术可行性分析

### 4.1 已验证可行的 Ink 能力

| 能力 | Ink API | 用途 |
|------|--------|------|
| **Flexbox 布局** | `<Box flexDirection="column">` | 整体布局 |
| **边框** | `<Box borderLeft borderColor={hex}>` | UserMessage/ToolPanel |
| **背景色** | `<Box backgroundColor={hex}>` | UserMessage/BlockTool |
| **文本颜色** | `<Text color={hex} dimColor>` | 角色区分/状态色 |
| **Spinner** | `<Spinner label="..." />` (ink 内置) | 工具执行中 |
| **Static 冻结** | `<Static items={history}>` | 历史消息 |
| **TextInput** | `<TextInput value={...} />` | 输入栏 |

### 4.2 需要变通的方案

| 需求 | Ink 限制 | 变通方案 |
|------|---------|---------|
| **点击折叠** | ink 不支持 `<Box onPress>` | 全局键盘监听 + 状态机。当前 ToolPanel 已有类似机制 |
| **滚动** | ink 无原生 scrollbox | 保持 Static + 动态区方案。历史不可滚（只显示最近 N 条），当前轮次可滚 |
| **hover 高亮** | ink 不支持 mouse hover | 放弃。终端 UI 不依赖 hover |

### 4.3 Ink 组件库参考

| 库 | 地址 | 可用组件 |
|----|------|---------|
| ink (核心) | `npmjs.com/package/ink` | Box, Text, Static, Spinner, TextInput |
| ink-ui | `github.com/vadimdemedes/ink-ui` | TextInput, Select |
| InkUI | `inkui-lib.vercel.app` | Spinner, Badge, ProgressBar, Select, Table, Toast, Dialog |
| cli-highlight | `npmjs.com/package/cli-highlight` | 代码语法高亮（已在依赖中） |
| marked | `npmjs.com/package/marked` | Markdown 解析（已在依赖中） |

**结论**: 不需要引入新依赖。ink 7 原生 + 已有依赖（marked、cli-highlight）足够实现全部方案。

## 九、二次校验修订记录（2026-08-06，读真实代码后）

> **校验背景**：§八审阅基于"预设代码"做技术判断。本次实读 `src/ui/`（chat-view/tool-panel/theme/reduce-agent-event/types）+ `src/agent.ts` 后，发现文档与现状有 5 处出入，逐一修订并回写对应章节（§3.3 / §8.2-2.4 / §8.3 / §8.5-R4 / §8.6）。本节为汇总，便于实施时一眼对照。

### 9.1 R4 前置改动——结构性升级（非 tweak）

**原文档说法**：consumeStream 逐 chunk yield，~1h。
**真实情况**：`consumeStream`（agent.ts:136-181）是纯累加器，整轮 `text += part.text` 后返回 Promise；`runAgentStream` 在整轮结束后才 yield 一次 `text_delta`（agent.ts:293）。**当前动态流式区每轮只收到一坨完整文本，并不流式。**
**修订方案**：把 text 路径从"累加器返回后一次性 yield"改为"runAgentStream 边迭代 provider 流边即时 yield `text_delta`"；tool_call 仍跨 chunk 累积 input JSON（原逻辑不变）。工作量 ~1.5-2h（含单测）。**这是 Phase 1 硬前置**——不做，Static/Dynamic 分区无意义。

### 9.2 颜色 token——新增项从 8 个砍到 3 个

**原文档说法**：新增 userBorder/userBg/success/error/warning/toolBg/toolBorder/thinking。
**真实情况**：theme.ts 已有 `success/error/warning/thinking/border/tool`；`border=#45475A` == 原文档 userBorder；`thinking=#94E2D5`（青）与原文档 `#F9E2AF`（黄）冲突，复用现有即可。
**修订方案**：仅新增 `userBg=#313244` / `toolBg=#181825` / `toolBorder=#313244` 三个。见 §3.3。

### 9.3 UserMessage 现状——P0 痛点坐实

chat-view.tsx:16-21 当前 UserMessage **无任何边框/背景**，仅"❯ 你"标签 + paddingLeft 4 灰字。§1.1 列的"角色区分弱"P0 属实，borderLeft+background 方案对症，无修订。

### 9.4 工具折叠——foldContent 与 Inline/Block 的维度冲突

**原文档说法**（§8.3）：ToolDone 拆分为 InlineTool + BlockTool（暗示替换现有）。
**真实情况**：现有 `foldContent`（tool-panel.tsx:39-64）已按**工具类型**折叠（read→行数 / bash→3或5 / edit/write→完整 / grep→3）。Inline/Block 是按**输出量/diff**折叠，维度不同。
**修订方案**：两者**叠加**，不替换——Inline/Block 决定"单行还是面板"（外层形态），foldContent 的 per-type 规则决定"面板内显示多少行"（内层裁剪）。实施时保留 foldContent。

### 9.5 现存 gap——tool_result 未透传 input

**真实情况**：`tool_result` 落地的 DisplayMessage（reduce-agent-event.ts:34-44）未带 `input`；chat-view.tsx:34 调 `<ToolDone name content isError />` 也不传 `input` → `summarizeArg` 拿不到参数 → **bash 命令、文件路径等摘要在历史区从不显示**（仅动态区 ToolRunning 能显示 arg）。
**修订方案**：重构 Phase 2 一并补——确认 `tool_result` AgentEvent 是否携带 input；若不携带，需在 reducer 从 `tool_call_start`/activeTools 记录 input 并在 tool_result 时补全。属增强项，不阻塞 Phase 1。

### 9.6 实施期新增发现（2026-08-06，Phase 1 落地时）
