# OpenClaw 参考研究:什么值得学 / 什么不值得

> **一句话定位**:OpenClaw 是「跑在自己设备上的**多渠道个人 AI 助手 + 网关**」(Telegram/Discord/WhatsApp + iOS/Android/macOS app + Canvas),**不是 coding agent**。和 ECode(终端 coding agent)不是同赛道。
>
> ECode 的同赛道对标是 opencode / CCode / claude-code-main(已在 `docs/memory/project.md` 记录)。OpenClaw 只因它有两块独立特色能力(**skill 自动归纳** + **远程操控**)才单独研究。
>
> **调研方式**:实读源码(遵循 `debugging.md #004`,所有结论带 `file:line`,不靠 README 臆测)。
>
> 创建:2026-08-06 ｜ 关联:ECode 未来 M5+(Subagent/MCP/Hooks)

---

## 0. 总判断(先看这个)

| 能力 | OpenClaw 怎么做 | ECode 该不该学 |
|------|----------------|----------------|
| Skill 自动归纳 | **纯正则捕获 + 强制审批**,非 LLM 自主总结 | **格式抄、归纳逻辑别抄**;现在不做,M5+ 用 LLM 重做 |
| 远程操控 | **Gateway 控制平面 + 边缘 node 闭合命令 + 不可变审批** | **外壳别碰**(单机过度设计);**审批守恒模型抄**(bash 权限分级时) |

**核心结论**:OpenClaw 这两块的「产品外壳」(Gateway/跨设备/Canvas/正则捕获)对单机 CLI 全是过度设计;但各有一块「内核思想」是金子——**skill 的 md 格式 + 懒加载注入 + proposal 审批队列**,和 **systemRunPlan 审批守恒**。ECode 到对应里程碑时直接读那几个文件即可,单文件、几十行,不需要搬它的外围架构。

## 一、Skill 自动归纳

### 1.1 真相(和直觉相反)

**它不是「LLM 自主总结对话生成 skill」。** 实读源码定论:OpenClaw 的 skill 归纳是「**半自动捕获(纯正则,不调 LLM)+ 强制审批**」,分三条路径:

| 路径 | 怎么干 | 自动程度 |
|------|--------|----------|
| **autocapture** | 每个 agent turn 结束,用 **7 条正则**抓用户话里的 `remember to / next time / from now on / always.../prefer...` → 套固定模板 → 生成**提案** | 半自动,**纯正则无 LLM** |
| **skill_workshop 工具** | agent 主动调工具写 skill 内容,但 `apply` **强制走审批** | 半自动(LLM 写,人批) |
| **手写** | 仓库内置 58 个 `SKILL.md`(skill-creator / coding-agent / summarize 等) | 全手动 |

关键:autocapture 命中后**不直接落盘**,先进 `PROPOSAL.md` 提案库,过安全扫描 + apply/reject/quarantine 才转正。

### 1.2 skill 的定义格式(值得抄的部分)

`SKILL.md` + YAML frontmatter,对齐 [agentskills.io](https://agentskills.io) 规范:

```markdown
---
name: skill-creator              # 必填,小写 a-z/0-9/-,≤64 字符,必须=父目录名
description: "Create, edit... AgentSkills"  # 必填,≤1024 字符——模型靠它判断要不要用
disable-model-invocation: false  # 可选,true 时模型看不到但仍可被代码强调调
---
# 正文:触发后才加载的完整指令
```

- 加载器:`packages/agent-core/src/harness/skills.ts:124-221`(`loadSkills` 递归遍历 + frontmatter 解析 + SHA-256 算 `promptVersion`)
- 类型:`packages/agent-core/src/harness/types.ts:63`(`Skill { name, description, content, filePath, promptVersion }`)

### 1.3 注入机制(懒加载,值得抄)

- **启动时**:`formatSkillsForSystemPrompt()` 只把每个 skill 的 `name + description + location + version` 拼成 `<available_skills>` XML 块塞进 system prompt(`system-prompt.ts:5-35`)——**正文不进 prompt**,避免爆炸
- **触发后**:模型决定用某 skill 时,`formatSkillInvocation()` 才把正文全文注入(`skills.ts:46-49`)
- **热更**:harness 暴露 `setResources()`(`agent-harness.ts:1099`),运行时可替换 skills 列表
- `promptVersion`(SHA-256 截短):skill 改了模型自动重读——聪明的小优化

### 1.4 ⚠️ 必须纠偏的陷阱:`active-memory` 扩展

`extensions/active-memory/` 这名字**严重误导**——它不是「主动归纳」,而是 **memory recall**(RAG 式检索历史记忆再注入 prompt)。

**对 ECode 的直接影响**:你现有的 `docs/memory/`(MEMORY.md 索引 + 分类文件)**已经覆盖了 active-memory 的功能**。别看到这名字就以为 OpenClaw 有更强的「主动归纳」要去抄——它没有。

### 1.5 值得学 / 别抄 / 怎么落地 ECode

**✅ 值得学(架构理念)**

| 项 | 价值 | ECode 落地 |
|----|------|-----------|
| skill = `SKILL.md` + frontmatter | 零依赖、git diff 友好、可读、对齐社区规范 | M5+ 加 skill 时直接抄格式 |
| catalog 进 prompt + 触发后读正文(懒加载) | 防 system prompt 爆炸 | `src/system-prompt.ts` 未来扩 skill 走这路 |
| `promptVersion`(SHA-256 截短) | 模型自动检测改动重读 | 小优化,可借鉴 |
| **proposal 审批队列** | agent 生成的东西不直接落盘,先进提案库待批 + 安全扫描 | **强烈推荐**:ECode 若让 agent 自动写记忆/skill,这套防垃圾机制必学 |
| `disableModelInvocation` 双轨 | 某 skill 只给代码调不给模型看 | flag 设计可抄 |

**❌ 别抄**

| 项 | 为什么 |
|----|--------|
| autocapture 的 7 条正则 | 对 coding 场景识别率极低(用户纠错是「这里用 enum 别用 string」,不匹配「remember to」句式) |
| gateway-protocol 那 1000 行 skill schema | 给多客户端 + ClawHub 商店用的,ECode 单机 YAML 直接读就够 |
| skill_workshop 工具 | 强依赖 Subagent/Hooks 审批链,ECode M5+ 才有,现在接不上 |

**📅 落地时机**

- **现在(M3.5/M4)**:不做。skill 当**纯手写 md**(放 `skills/` 或并入 `docs/memory/decisions/`),写个 30 行 `loadSkills.ts` 抄 `skills.ts:124-221` 的目录遍历 + frontmatter 解析即可
- **M5+ Hooks 落地后**:再做「自动归纳」,但**用 LLM 归纳(非正则)** + prompt 引导模型从 transcript 抽「可复用工作流/决策」+ 输出走 **proposal 队列**不直接落盘 + 用户 `/accept` 才转正。**这是 OpenClaw 没做、但 ECode 做了会更强的地方**

## 二、远程操控

### 2.1 真相 + 两个纠偏

**OpenClaw 的「远程操控」≠ 鼠标键盘控屏。** 它是「**集中式 Gateway 跑 agent + 边缘 node 闭合命令集 + 不可变审批计划**」三件套。

**纠偏 1**:这里没有「控整台电脑」。node 端能做的是**闭合命令集**(`camera.snap` / `system.run` / `canvas.navigate` / `location.get` / `sms.send`...),由原生 app 调平台 API 完成。

**纠偏 2**:`ACP` = **Agent Client Protocol**(外部 coding harness 协议,agentclientprotocol.com,让 Gateway 把 Codex/Claude Code 当外部 harness spawn),**不是** "Agent Control Protocol"。

### 2.2 架构(控制流)

```
                 ┌─────────────────────────────────────────────┐
                 │  Gateway(单一常驻进程,127.0.0.1:18789)      │
                 │  ─ 跑 agent loop(LLM + 工具)                │
                 │  ─ 持有所有渠道(Telegram/Discord/WhatsApp)  │
                 │  ─ 持 session/配置/审批/配对(SQLite)        │
                 │  ─ HTTP + WS 同端口                          │
                 └──────────┬──────────────────┬───────────────┘
                            │ WebSocket        │ WebSocket
                 ┌──────────┴────────┐ ┌───────┴──────────────┐
                 │ operator(控制者) │ │ node(被控端)        │
                 │ CLI/WebChat/      │ │ iOS/Android/macOS app│
                 │ macOS menubar/IDE │ │ role:"node" 连接     │
                 └───────────────────┘ └──────────────────────┘
   控制方向:operator/node 都是 Gateway 的客户端。agent 决策在 Gateway 完成,
   Gateway 通过 node.invoke 把「命令」推给 node 执行。
```

**典型远程执行流**(Telegram → 在 iPhone 上跑 shell):
Telegram 消息进 Gateway → agent 决定调 `system.run` → Gateway 规范化成 `systemRunPlan` + 签名 → 广播审批请求给 operator → operator 批准 → Gateway 用**存储的 plan**(非 agent 当前声称)调 `node.invoke system.run` → iPhone 执行 → 结果回传。

### 2.3 审批守恒机制(systemRunPlan)—— 这块是金子

两阶段设计(`src/infra/system-run-approval-binding.ts` + `src/gateway/server-methods/exec-approval.ts:146-329`):

1. **prepare**:把 agent 的工具调用**规范化成 canonical `systemRunPlan`**(`{argv, cwd, commandText, agentId, sessionKey}`),对 `{argv, cwd, agentId, sessionKey, envHash}` 算签名 `systemRunBinding`;**原始 argv 都不存**
2. **resolve**:审批人只能调 `exec.approval.resolve({id, decision})`——schema **只允许 id + decision 两字段**,审批人**不能改请求**
3. **执行 + 校验**:用**存储的 plan** 调 `node.invoke`,执行前再逐字节比对 argv/cwd/session + SHA-256 比对 envHash,任何偏离返回 `APPROVAL_REQUEST_MISMATCH` 拒绝

**这个设计保证:agent 中途篡改 command/cwd/session 都会被拒,审批人看到的就是执行人执行的。**

### 2.4 computer-use 真实成熟度(确定结论)

| 能力 | 状态 | 位置 |
|------|------|------|
| 浏览器自动化(click/type/snapshot) | ✅ 完整 | `extensions/browser/`,Playwright + CDP |
| 手机能力(相机/屏幕/位置/SMS/日历) | ✅ 在原生 app | iOS/Android 各 Handler |
| macOS/iPhone/Android 跑 shell | ✅ `system.run` | node 命令 |
| Canvas(远程 UI) | ✅ 实验 | `extensions/canvas/`,WKWebView |
| **OS 级鼠标/键盘/打开 app** | ❌ **只是 roadmap** | VISION.md:30 明确列为「未达成的 next priority」 |
| Codex computer-use | ⚠️ 非 OpenClaw 能力 | `extensions/codex/` 只是帮 Codex 装插件,功能在 Codex 那边 |

**定论:OpenClaw 没有「控整台电脑」的能力。**

### 2.5 值得学 / 别抄 / 怎么落地 ECode

**✅ 值得学(轻量抽象)**

| 项 | 价值 | ECode 落地 |
|----|------|-----------|
| **systemRunPlan + Binding 审批守恒** | 工具的「审批版」和「执行版」是同一份不可变计划,审批人只 yes/no,agent 改 argv 一律拒 | **强烈推荐**:ECode 的 `src/tools/bash.ts` 未来做「写操作二次确认/高危命令审批」时,**单文件照抄**,不需要任何 Gateway 外壳 |
| operator scope 闭集 + method→scope 静态映射 | 6 个 scope 字符串 + 一张表,替代 if-else 长链 | ECode 工具加权限层级(read-only/standard/dangerous/admin)时的策略映射范式(呼应 CLAUDE.md §1.3) |
| idempotencyKey + ack/final 两阶段响应 | 副作用 RPC 幂等;长任务先 ack 再异步 final | agent loop 跑长 bash 时可借鉴(`tool_use_id` 配对已是同类思想) |
| WS 帧三件套(req/res/event) | 极简协议审美 | 仅当 ECode 未来做「TUI 与 agent 后端进程分离」才参考;**当前别引入** |

**❌ 别抄(过度设计)**

| 项 | 为什么 |
|----|--------|
| Gateway WS 控制平面 | ECode 单机单进程,自己既是 agent 也是 UI,没有「另一台机器的 node」 |
| node.invoke + 跨设备 pairing | 零价值。ECode 的「远程」至多是「用户在终端和 agent 对话」,不是远程操控 |
| Canvas A2UI / pluginSurface | 为桌面/手机 GUI 服务,对 CLI 零价值 |
| ACP / acpx / 多 harness 路由 / codex-supervisor fleet | ECode 自己就是 coding agent,不需要 spawn 外部 CLI |

**📅 落地时机**

- **现在(M3.5/M4)**:不做远程操控,单机不需要
- **M4 权限系统做 bash 分级时**:去读 `src/infra/system-run-approval-binding.ts` + `system-run-approval-context.ts` + `exec-approvals.ts`,把「规范化 plan → 哈希绑定 → 审批只 yes/no → 执行前再校验」这套**单文件抽象**搬过来。**这是这次调研最大的收获。**
