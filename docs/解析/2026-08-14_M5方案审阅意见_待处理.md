## 三角色高度共识的真问题（修订必改）

### 1. messages mutate 契约破坏（架构师 P0 + 开发 P0）
- 文档 §5.4 写 `messages = result.messages`（重赋值局部变量）
- 但 TuiApp.tsx:100 / cli/index.ts 都**不捕获 runLoop 返回值**，靠 `messagesRef.current` 原地 mutate
- 重赋值后 messagesRef 仍指旧数组 → 压缩结果丢失 + committed 错乱
- **修法**：原地替换 `messages.length = 0; messages.push(...result.messages)`

### 2. retryable 是死字段（架构师 P1 + 开发 P0）
- errors.ts:108/111/114 设了 retryable，但 loop.ts **从不读它**（grep 确认）
- 文档说「loop 区分 retryable」=首次让它生效，但未定义语义
- 开发建议：不走 retryable，改**错误码专属分支**（CONTEXT_TOO_LONG → pop 半截 + compact + continue）

### 3. autoApprove 与「MCP 零改动」矛盾（架构师 P1 + 开发 P1）
- D10 承诺 autoApprove 跳过确认，但 Tool 接口只有 readonly，confirm 拿不到 autoApprove
- **修法**：Tool 接口加 `confirm?: 'always'|'never'`，与 readonly 解耦

### 4. 压缩后 history 持久化未定义（架构师 P1 + 开发 P0）
- HistoryStore append-only，压缩替换内存 messages 后磁盘仍是全量
- 重启 /history restore 拿回未压缩历史 → 白压 + 再触发
- 开发建议方案 3：append `{compact_boundary}` 标记，restore 遇到丢弃之前的行

### 5. token 全量重编码性能（开发 P0-4）
- 每轮 provider.run 前 estimateTokens 全量 encode 100k tokens ≈ 0.1-0.4s
- 建议：增量计数 + 缓存（仅 messages 变化时重算）

### 6. MCP spawn 串行 + 无 timeout（开发 P0-5）
- 一个 server hang（非 fail）→ 启动卡死
- 建议：Promise.allSettled + 每 server 10s timeout + makeDeps 改 async

## 产品视角的关键决策（影响范围）

PM 强烈建议拆 M5，三特性独立交付（用户更早用上单个）：
- **价值排序**：压缩（防崩溃）> Skill（少数高级用户）> MCP（极少数 + 成本最高 + Windows spawn 坑多）
- **建议 M5 只做手动 `/compact`**（砍自动阈值 + 不装 tokenizer，0 心脏主流程改动 + 0 依赖）
- 理由：ECode 终端 CLI 单任务几轮就完，GLM 128k 少撞限；唯一真触发场景是 /history 恢复长会话；现有超限处理是「recoverable + 提示 /clear」不崩。手动 /compact 覆盖 80% 需求，自动触发 ROI 低。
