## 1. 解决什么问题

一个场景：你在公司电脑上用 ECode 跑着一个长任务，下班了想在路上看一眼进度、顺手批准一个操作、或者补一句话插话。

困难在于：

- 电脑在家里/公司内网，手机在外面的移动网络——**双方互相找不到对方**；
- 就算打通了网络，**谁来保证路上没人偷看**？对话内容、代码、密钥都在里面；
- 电脑总不能为这事**对外网开个端口**——那是把家门拆了。

ECode 的答案概括成一句话：**电脑主动去找一个公网上的「信箱」，手机也去信箱取信；信箱只递包裹、看不到信的内容；第一次使用时电脑当面把钥匙交给手机（扫码）。**

## 2. 三个角色（快递站比喻）

```
┌─ 你的电脑 ────────────┐      ┌─ 公网信箱 ─┐      ┌─ 你的手机 ─┐
│ ECode daemon          │      │   relay    │      │ 浏览器/PWA │
│ （干活的+守在家里）    │◀────▶│ （只递包裹）│◀────▶│（扫码进门）│
│  主动出门连信箱        │ 出站  │  不看内容  │ 双向  │  只认二维码 │
└───────────────────────┘      └────────────┘      └────────────┘
```

| 角色 | 比喻 | 实际是什么 |
|---|---|---|
| **daemon** | 守在家里干活的人 | 电脑上的常驻进程（`ecode serve`），管理会话、执行工具 |
| **relay** | 小区门口的快递柜 | 跑在公网服务器（如 nodetime.cn）上的转发程序，只有 100 多行逻辑：收包裹、递包裹 |
| **手机/PWA** | 收件人 | 浏览器打开一个网页，网页里就是 ECode 的对话界面 |

三个关键事实：

1. **电脑不出租屋门**：daemon 是「纯出站」——它主动伸手去连快递柜，家里路由器不用开任何端口（对比传统方案要端口转发/内网穿透）。
2. **快递柜是瞎子**：relay 转发的每个包裹都是加密信封，它既没有钥匙也没有偷看的机会（详见 §5）。
3. **快递柜不存件**：所有的信（会话、代码、密钥）都在电脑本地，relay 内存里过一遍就忘。skill/MCP/历史数据零上云。

## 3. 思路：四个关键决策与为什么

### 决策一：配对 = 当面发钥匙（为什么是扫码）

手机第一次接入前，双方互不相识。怎么建立信任？最古老的办法——**当面交换**。

电脑上执行 `/devices`（TUI）或 `ecode pair 手机名`，生成一张**二维码**。二维码里打包了三样东西：

- 这台设备的**专属门禁卡**（per-device 令牌——48 位随机字符，只对这一台手机有效）；
- 电脑的**公钥指纹**（手机之后用它核对「对面真的是我家电脑」，防止快递柜冒充）；
- **去哪个快递柜取信**（relay 地址 + 一张临时通行证）。

手机相机扫一下 → 浏览器打开 → 三样东西自动落位 → 直接进入对话。全程不需要在手机上打一个字。

> 为什么不让手机直接填令牌？令牌只是「门禁卡」，缺少「去哪个柜子」和「公钥指纹」——手机连上了也认不出自家电脑。这就是早期版本「打开网页让填 token」填不通的根因。

### 决策二：信封在手机上封，在电脑上拆（为什么中继看不到内容）

加密用的是业界标准三件套（不是自创密码学）：

| 步骤 | 干什么 | 白话 |
|---|---|---|
| X25519 密钥交换 | 双方各出一把「一次性锁具」拼出同一把会话钥匙 | 快递柜看着两人拼锁，但拼不出钥匙 |
| HKDF 派生 | 从会话钥匙分出「上行钥匙」「下行钥匙」「会话编号」 | 去程回程用不同的锁，杜绝「自己骗自己」的反射攻击 |
| AES-256-GCM 加密 | 每一帧数据加封条 + 防伪编号 | 改一个字节都会被识破；重放旧信件因编号对不上被拒收 |

三个白话保证：

- **每连一次换一次钥匙**——录下这次的密文，下次连接重放无效（编号必须严丝合缝地递增）；
- **方向分锁**——发给电脑的信和电脑发的信用不同钥匙，黑客没法「照抄你说的原话发回给你」；
- **公钥当面钉死**——配对二维码里带着电脑的公钥，中继想中途换锁冒充电脑，手机当场识破。

### 决策三：每台设备一张独立门禁卡（为什么不是共用密码）

配对时电脑为这台手机单独生成一张卡，记录在电脑的 `devices.json` 里：

- 卡丢了/手机丢了 → 电脑上**单独吊销这一张**，其他设备不受影响，且**吊销即时生效**（正在连着的立刻被踢下线）；
- 每张卡有权限档：`chat`（对话+只读，默认）或 `full`（全功能）——手机丢了，最坏损失是「别人能跟你正在跑的会话聊天」，改不了配置、删不了会话；
- 这也是为什么**配对动作只能从电脑侧发起**（终端或电脑上的 web）——手机自己的卡没有「再发新卡」的权限，否则手机丢了等于钥匙无限复制。

### 决策四：会话钥匙一断就换（为什么断线重连不乱）

网络总会闪断。为防止「僵尸连接复活」「旧数据混进新连接」，每个到信箱报到的新电脑领一个**号牌（generation 代次）**和一张**限时门牌（租约，120 秒）**：

- 正常断线重连 → 出示号牌+暗号，**同号接管**，手机那头甚至无感；
- 长时间失联（租约过期）→ 号牌作废，必须领新号，旧连接的全部作废；
- 两台电脑冒同一名字来抢位 → 后来者被拒（位上有主）。

## 4. 一条消息的旅程

在手机上发「帮我看看构建日志」，会发生什么：

```
手机浏览器                     relay（快递柜）                    电脑 daemon
    │  ① 封进加密信封                │                              │
    │ ────────────────────────────▶ │ ──── 原样递送（看不懂）──────▶ │
    │                               │                              │ ② 拆信封验编号
    │                               │                              │ ③ 当作本地命令执行
    │                               │                              │    （与电脑/web 完全同一套）
    │                               │ ◀─── 回信加密封箱 ──────────── │
    │ ◀──────────────────────────── │                              │
    │  ④ 验封条→拆信→显示            │                              │
```

两个设计上的「偷懒」其实是优点：

- **relay 不理解包裹**——它只做「手机 ↔ 电脑」的逐帧搬运，连里面是什么语言都不知道。这让 relay 永远不需要升级就能兼容新功能；
- **电脑收到中继转来的命令后，走的是和自己网页一模一样的入口**（loopback 自取：daemon 收到后回头调用自己的本地接口）——所以权限校验、会话路由、断线续传这些逻辑一行都不用重复写，天然不会出现「中继通道绕过了安全检查」的缝隙。

## 5. 用到的技术（每样一句话）

| 技术 | 在哪用 | 白话说明 |
|---|---|---|
| WebSocket（WS） | 全部三条连接 | 打一次洞、双向持续说话的管道（对比：每次问一句开一扇门） |
| 出站连接 | daemon → relay | 电脑只往外拨电话、从不接电话——内网穿透问题直接消失 |
| X25519 + HKDF + AES-256-GCM | 数据腿加密 | 浏览器和 Node 都内置的「官方密码学积木」，零第三方加密库 |
| 严格递增计数器 | 每一帧加密 | 每帧带唯一流水号，收方要求号码一个不差地递增——重放/乱序/篡改当场拒收 |
| `qrcode-terminal` / `qrcode.react` | 配对二维码 | 同一张码，终端里用方块字符画、网页里用 SVG 画；本地渲染，密钥不出电脑 |
| 一次性邀请凭证（invite） | 手机连快递柜 | 配对时发的短期通行证，可随时作废；作废=正在用的连接立刻断 |
| SSE / mux 事件流 | 电脑→手机推送 | daemon 把所有会话动态汇成一条频道，手机订阅后实时看到打字流/审批请求 |
| Ink（React for 终端） | TUI /devices 面板 | 用写网页的方式写终端界面——面板/列表/二维码都是组件 |
| node-pty 探针 | 自测 | 造一个假终端真敲命令，验证面板真的能开、码真的能出 |

## 6. 交互流程（分场景）

### 场景 A：第一次配对（一次性，约 30 秒）

```
电脑 TUI                          手机
│ /devices                         │
│ （面板打开）                      │
│ 选「配对新设备」回车               │
│ → 面板出现二维码+链接              │
│                                  │ 相机/微信扫码
│                                  │ → 浏览器打开链接
│                                  │ → 自动配对，直接进对话
│ （列表里多出这台设备 [中继]）      │
```

网页版的设备面板（电脑浏览器打开本机 web → 手机图标）有同样的「配对新设备」按钮——生成链接发给手机即可。**配对入口永远在电脑侧**，手机上只有管理和使用。

### 场景 B：日常远程使用

```
手机打开 https://<你的relay>/ecode/（或收藏夹/PWA）
→ 顶栏绿点「已连接」+ 电脑名（多台电脑时显示当前连的是谁）
→ 选项目 → 看历史会话 → 发消息/插话/审批（该弹的审批卡照弹）
```

手机放下几分钟再拿起来：自动重连，丢的帧自动补齐，不丢内容。

### 场景 C：手机丢了/换手机

```
电脑 TUI：/devices → 光标移到那台设备 → 回车两次（二次确认）
→ 该设备立刻被踢下线，卡作废；其他设备不受影响
```

### 场景 D：两台电脑（多机）

每台电脑各自配对一次 → 手机设备面板里出现两台主机（带在线徽标）→ 点谁进谁。

## 7. 安全设计对照（谁想使坏 → 会撞上什么）

| 坏人 | 想干什么 | 撞上的墙 |
|---|---|---|
| 中继运营方/被黑的快递柜 | 偷看对话内容 | 全程密文，它只有信封（GCM 认证加密，改一字节即碎） |
| 同上 | 录下密文明天重放 | 帧编号严格递增，旧号码当场拒收并断线 |
| 同上 | 冒充你的电脑换锁 | 配对二维码钉死了电脑公钥，对不上号即断 |
| 捡到手机的人 | 用你的对话 | 可立即吊销（即时断连）；默认 chat 档改不了配置 |
| 陌生微信用户 | 给机器人发指令 | 白名单缺省全拒；审批要 4 位短码且只认绑定者 |
| 局域网里的邻居 | 扫描你电脑 | daemon 缺省只听 127.0.0.1；对外只有 relay 的 443 |

## 10. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 手机打开是「填写 token」页 | 直接开了裸网址——那是本机/局域网形态的入口 | 手机必须走配对链接（扫码，或电脑 `/devices`/`ecode pair` 生成后发过去） |
| 提示「设备连接已失效」 | 该设备被吊销或中继上无此主机 | 电脑重新 `/devices` 配对 |
| 浏览器提示不支持 X25519 | 浏览器太旧（加密是强制的，无明文降级） | 换 Chrome 133+/Safari 18.4+ |
| 电脑重启后手机连不上 | daemon 没在跑 | 电脑跑一次 `ecode serve`（或任意 `ecode` 自动拉起） |
| 想让新项目出现在手机上 | 设备凭据不枚举项目（防泄露电脑目录结构） | 重新配对（配对时的项目快照会带上），或在电脑 web 添加 |
