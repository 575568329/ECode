# Agent 成本优化实战文章精华提取（Harness 成本篇）

> 来源：《Agent 终章（Harness 成本篇）：一次百炼账单降低 88% 实战》（公众号文章，2026 年第 54 篇；无公开 URL，本文据 2026-08-21 会话粘贴的全文转述，忠实性核对见对照篇 §7 审阅记录）。作者团队在生产环境（百炼 qwen3.7-max、故障诊断/成本分析类 agent）的实战总结，借鉴 oh-my-pi、Codex CLI、Grok Build 与 Anthropic Agent 工程笔记。
> 本文是**纯提取**：忠实转述原文各阶段的核心观点与做法，不含 ECode 侧评价。ECode 对照见姊妹篇 [2026-08-21_Agent成本优化ECode对照与差距清单_已完成.md](./2026-08-21_Agent成本优化ECode对照与差距清单_已完成.md)。

## 0. 总纲

文章的核心账本：**88% 降幅 = "少发"（实际发送量 820k→532k）× "发得便宜"（缓存折扣让计费再降到 96.9k 等价全价）两把杠杆叠加**，二者缺一只有 81.6%。

总纲一句话：成本优化不是外挂式技巧，它就是 Harness 实践本身——模型只负责生成，Harness 决定**哪些内容要发（少发）、已发的以什么价格发（缓存）、哪些过程要隔离（Subagent）、什么时候该停（Hook）、这次任务该用什么模型（分流）**。

效果数据：
- 隐式缓存命中率 33% → 80%；显式缓存加权命中近九成（0.898），无全量 miss；
- 一轮 20 轮的会话，输入费用降到原来的约 1/10。

背景判断：token 使用进入精细化时代，agent 逐渐同质化，最终胜出的是"谁用最少的钱跑出最好效果"——优化 token 不是锦上添花，是 agent 能不能活下去的前提。

## 1. Token 去向：为什么几个字能撬动几十 M Token

用户可见的 prompt 只是冰山一角，水面下是：工作守则（system prompt）、几十个工具的 schema、每一轮的对话历史、工具查回的结果。三个放大机制：

1. **循环反复跑**——agent 一来一回就是 30-40 轮；
2. **历史每轮全量重发**——模型无记忆，唯一办法是把之前的内容原样再发一遍（第一轮搜索返回 8K，下一轮这 8K 就成了输入）；
3. **工具结果不断堆**——循环每多转一圈，历史和工具结果再叠一层。

原文案例（三轮对话示意图）：固定前缀（工作守则 + skills 目录 + 常驻工具 schema + MCP 工具 schema）×6 次请求 = 120k，占总量 57%，而用户输入只有 0.3k。结论：**固定前缀每轮全量重发，前缀里砍 1k，30 轮会话就是 30k**——少发无小事，每个字符都乘以轮次。

## 2. 度量先行：三条链路交叉验证

优化前先立尺子，否则没有数据支撑：

1. **自研采集**：从每次 LLM API 返回的多个 token 字段写入本地。`cache_hit_rate = cached_tokens / prompt_tokens`；接口未返回 usage 时记空不记 0。cache_mode 从响应推断（有 `cache_type: "ephemeral"` 为显式缓存；有 cached_tokens 无 cache_type 为隐式缓存）。
2. **自建 Langfuse**：一次调用 = 一条 Generation，一个 Agent 任务 = 一条 Trace，Subagent 独立 Trace 经 parent_task_id 挂回父级；异步队列上报不阻塞主 loop。
3. **自建评测 Agent**：任务结束后先从工具轨迹标记重复调用、连续失败等异常，再由轻量模型从相关性/工具效率/重复操作/错误恢复/完整性五维评分；低分任务自动沉淀诊断包，形成持续改进闭环。

铁律：**质量是成本优化的基础，不能因为控制成本降低质量**（文章 6/7 月总分基本持平为证）。

## 3. 少发：缩小每轮请求的输入体积

### 3.1 删掉过时的"教学文本"

早期 system prompt 里的 ReACT 循环说明、工具调用协议说明、错误重试策略、few-shot 示例（约 1.2k token），在新模型上已是冗余——最新模型在海量 agent trace 和框架文档上训练过，这些范式早已内化。删除后工具调用准确率与任务完成率无观测下降。

### 3.2 System prompt 每轮重建，不写进历史

反例是把 system 消息存进历史（第 N 轮历史里有 N 份 system）。正解：每轮拼装 `[sys 当场构建] + [历史只存 user/assistant] + [当前输入]`，system 永远 ×1。system prompt 常占 context 5%-10%，这是收益最高的一项；OpenAI 接口原生不支持 system 字段，尤其依赖框架层正确处理（Anthropic 原生支持 system 字段，放对位置即无此问题）。

### 3.3 工具 schema 按需读取（Deferred Tools）

工具 schema 是每轮固定消耗，常驻工具+多 MCP server 时可能比 system prompt 还大。Anthropic/OpenAI 已原生支持 defer 语义，但百炼两个 API 均静默忽略相关字段，因此文章在 harness 层自实现等价机制：

- **两个池子**：常驻池（Read/Edit/Bash/Grep/Glob/Write/ToolSearch 等）每轮带完整 schema；延迟池（MCP 工具、WebSearch/WebFetch、DB 系列、AppSkill）只在 system prompt 里留一行目录（"工具名 — 一句话提示"，按名称排序，最多 50 行，reveal 后不从目录删除）。
- **两条激活路径**：模型主动 ToolSearch(query) 返回 reveal payload（name+schema+guidance）；或 Skill 激活时逐词匹配正文自动 reveal。
- **核心不变量**：tools 数组每次请求字节相同（stub 只占 name），前缀缓存永远命中；完整 schema 经 tool result 走 message 层注入（追加在对话尾部），**不碰 tools 数组**。同一工具再搜一次只回"之前已加载"，不重复塞 schema。

### 3.4 常驻工具标准化：照抄 Claude Code 定义

无法 deferred 的常驻工具，入参出参与 Claude Code 保持一致即可精简 schema——CC 作为最流行的 coding 工具，其工具定义早已刻入 LLM 训练。模仿它既省 token，又避免自定义同名工具出入参不一致导致的首调出错（错一次浪费轮次+时间+token 三样）。

### 3.5 Skills 去重：同一份全文只激活一次

一份 skill 正文几千 token，连续多轮激活就重复塞多遍。依据《Lost in the Middle》（TACL 2024）：长上下文中**落在**中间的信息利用效果差，重复塞入既浪费也不增效。

做法：全文只注入一次固定在历史中作锚点；后续无论手动（/name）还是自动（LLM 调 ActivateSkill）再次激活，只在尾部补一条 ~150 字符短提醒"指令已在上文，本轮仍生效"。**单份不变式**：同一 skill 全文在任意一次请求的 messages 中至多出现一次；谁先激活谁持有全文，后来的拿短回执；激活集合每轮从历史推导（不依赖内存状态，重启后一致）。锚点固定即稳定前缀，缓存持续命中。

### 3.6 重复 Read 去重

模型常对同一文件多次 Read。做法：维护已读路径集合（文件 mtime 判变），每批工具执行前检查——路径已读过或同批次内重复 → 不执行，直接返回"文件未改变"；mtime 变了自然放行。真想读还有 sed/cat 等 shell 路径可用。

### 3.7 MCP 迁往 CLI + Skills：从根上干掉 schema

Deferred 解决了"不每轮占位"，但 MCP 形态还有结构性成本：目录条目、reveal 至少付一次全价、工具结果是不可过滤的 JSON 全量进历史、**每接一个 server 等于运行时教模型一套新接口格式且按 token 付费**（文章案例：MongoDB MCP 只注册 24 个工具就带来近万字符描述 + 76 处参数注解，每轮两三千 token 固定开销）。

做法是把这类能力迁成 CLI + skill：tools 数组只剩 Bash+常驻工具（字节级不变）；用法是 ActivateSkill 加载正文 + 一行 bash；结果可 head/grep/jq 过滤，只要需要的行进历史。论据：

- 模型预训练语料里 Unix 材料海量（man page、--help、shell 脚本），调 CLI 是权重里现成的直觉；而 arXiv 研究（扫描 103 个 MCP server 的 856 个工具）显示 97.1% 描述至少带一种质量坏味道，56% 连用途都没说清；
- 缓存友好：MCP server 增删会合法改变 tools 集合炸掉前缀，CLI 形态下能力增减请求不变一个字节；
- 无"历史对话污染"：MCP 调用记录以旧工具名+旧参数沉进历史，server 升级改名后模型照抄旧范式反复调错；CLI 历史沉淀的是稳定 shell 命令，skill 正文是唯一事实源，一次整体替换；
- 佐证趋势：MCP 2026-07-28 规范主线是无状态化（退役 initialize 握手、tools/list 确定性排序+ttlMs 缓存，官方明说为了 prompt cache 稳定）；Anthropic 的 Code execution with MCP（server 暴露成可执行模块，agent 写代码组合调用）官方示例单任务 150k→2k（-98.7%），全是 CLI 化套路。

新建能力先问一句：**能不能是一个 CLI + 一份 skill？**

## 4. 发得便宜：让已发的尽量命中缓存折扣

原理：Transformer 生成每个 token 要对前文做运算；首次输入做全量 prefill（算力最密集），之后每 token 只查已有 K/V。KV Cache 把 prefill 产物留在显存，下次请求**前缀字节相同**即可跳过 prefill——变一个字节，从那里往后的 KV 全部作废。

百炼计价：显式缓存命中 = 标准输入价 ×10%（创建时 ×125%）；隐式 = ×20%（无创建费，但不保证命中率）。显式四规则：缓存内容 ≥1,024 token、单次最多 4 个标记、5 分钟有效且命中续期、tools 定义也参与 system 前缀缓存计算。

同场景实测对比（qwen3.7-max，诊断任务三 subagent）：

| | 显式 ON | 隐式 ON |
|---|---|---|
| 加权命中率 | 0.898 | 0.800 |
| 最低单轮 | 0.640（无灾难脱靶） | **0.000（两次灾难脱靶）** |
| 中位 | 0.939 | 0.899 |

结论：**显式缓存是合约（打标记+前缀稳定=5 分钟内必命中），隐式是抽奖**；显式 TTL 过期后隐式仍可兜底一部分。命中后费用降到无缓存的约 12%，首 token 延迟随命中比例线性缩短。

### 4.1 System prompt 按稳定性分层

system prompt 里混着变化频率不同的内容（memory 索引、应用上下文、skills 列表），不分层则任何一处变化让整段前缀连同后面几十 k 历史一起失效。按变化概率从低到高排，控制爆炸半径：

```
│ Constant │ SessionStable │ MidConversation │ Dynamic │ messages │
│ 跨会话不变 │ 会话内禁变化   │ 跨 reveal 稳定   │ 每轮可变 │ 全部历史  │
```

- Constant：产品身份、固定规则（发版才动）；SessionStable：AGENTS.md、skills 列表、应用信息；MidConversation：deferred tools 目录（列出所有延迟工具，不因 reveal 删减重排）。
- 动态区限流：每块 ≤4,000 字符、总量 ≤16,000；memory 索引超 8,000 不再硬塞只提醒用工具查；skills 列表超长时从完整描述逐级缩成短描述、只留名称、最后才截断。
- **顺序是最大坑**：工具列表 A,B,C 变 B,A,C，一个没多没少但字节变了缓存照样失效。纪律：tools 只构建一次后面引用同一份；列表先固定排序再截断。
- 时间戳这类每轮必变的：放本轮 user 消息末尾（本来就是新内容，不破坏已缓存前缀）。

### 4.2 缓存断点标在请求尾部

每轮都在 messages 最后一条消息上重新标 `cache_control`，标记范围为整个输入（sys+tools+全部历史）；官方明确不对已缓存旧前缀重复收费。第 1 轮全量创建 ×125%；第 2 轮起旧前缀命中 ×10%、仅增量 Δ 创建 ×125%，轮数越多加权单价越接近 ×10%（实测第 6 轮命中率 0.996）。

实现：在序列化出口，从 messages 末尾往前找第一条有文字的消息，累计 ≥4,096 字符才标（下限 1,024 token），标在其最后一个 text 块；不够长跳过，不占 4 个断点配额。

## 5. 少想：让模型不要思考太多

prompt 里写"少想多干"没用——prompt 只是建议，模型觉得值得想还是会想，而思考链按输出 token 计费（有的回答思考 1w+ 字符）。要从**请求参数**硬控：

1. **辅助调用直接关 thinking**：标题生成、意图分类、查询富化、轮后建议、字段提取、简单压缩——输入短输出短答案空间窄，全部关；只有主 Agent Loop 和需要判断的 Subagent 才开。关后 token 明显下降、首包变快。
2. **开了思考就设上限**：`thinking_budget`（最多允许花多少思考 token，简单问题可提前结束，复杂问题到上限必须转答案）。文章在故障诊断样本上扫出拐点 4,096：从不思考→4K 工具选择和根因判断明显变好；4K→8K→16K reasoning 越来越长但完成率不涨、耗时涨。同时给最终回答预留 4,096——允许推理，但不许吃掉交付空间。**该数字无通用性，各场景需自扫拐点**。

## 6. SubAgent：探索过程不进主上下文，只回传结论

问题：有用结论可能只有一句，但为了这句要查几百行日志、十几次搜索、几条走错的路；全在主上下文里做，窗口动辄塞满触发 compact（故障诊断场景一 compact 就是几分钟）。

做法：子代理带独立 system prompt + 主代理写的任务说明，在独立 Agent Loop 里完成调查；完整结果落文件；**主代理默认只收到 ≤600 字符摘要 + 结果路径**，需要复核证据才按路径读原文。文件是冷存储，摘要才是进主上下文的热数据。

### 6.1 派发规则

唯一判断标准：**会不会产生大量主 Agent 后面用不到的过程**。量化：主上下文少重发的 token ≈ 父级剩余轮数 ×（探索过程 − 回传摘要）。查一次 Pod 状态这种 2k 的事别拆——Subagent 也有自己的 system prompt、工具目录、委派与回传成本。**并发不自动省钱**：三个 Subagent 并行只是等待变短，三份上下文照付；只有方向互不重叠且都能压成短结论才值得同派。

| 适合拆出去 | 留在主 Agent |
|---|---|
| 查多个目录/日志/数据源 | 一次工具调用能回答 |
| 日志、指标、变更三个独立方向 | 下一步完全依赖上一步结果 |
| 过程长、只要结论和证据位置 | 主 Agent 最终仍要通读全部原文 |
| 只读探索、边界容易划清 | 多人同时修改同一份文件/状态 |

### 6.2 任务书与回传格式

委派必须写成能独立执行的说明（工具 description 直接提醒主代理"Subagent 看不到当前会话"）：背景（为什么查/已出现什么现象）、目标（只需回答哪几个问题）、范围（可看哪些目录/应用/时间段/数据源）、已知事实（已确认什么/已排除什么）、边界（只读还是可写）、返回（结论/证据位置/未确认项/验证过什么）。

回传同样要限格式，否则子代理跑 100k token 回传 20k 报告，隔离失效：**状态**（完成/部分/阻塞）、**结论**（几句话）、**证据**（文件/行号/时间范围/查询条件）、**未确认项**、**下一步**、**结果路径**。超时/预算耗尽/权限不足时用 hook 强制注入一轮自总结，要求明确说查了什么没查什么。

## 7. Hook：在循环边界拦截无效轮次

模型输入不稳定，复读、空转、假忙靠 prompt 劝不住（模型进入退化状态时必须由 Agent Loop 在外面停）。且重复内容会进历史变下一轮输入，**越转越贵**。四类检测：

1. **一条 SSE 内重复**：边接收边按句检查（代码块与"好的"类短句不参与），同一正常句完整出现第 3 次即断流，hook 注入"你在重复"；重新回答仍复读就结束本轮。来源：DeepSeek flash 曾把一句话重复 685 次直到手动 abort。
2. **跨 Turn 重复**：回答前 500 字符生成指纹，与最近 3 个 Turn 比对，相似度 >80% 判无新进展。一二次提醒换方法/换工具/问用户；第三次结束循环；回答变化即清零重计。
3. **工具假忙**：同组工具+参数连续 8 Turn → 提醒重判，不改 → 结束；连续 5 Turn 工具结果全错/全空（即使换了工具）→ 要求换思路；shell 累计失败 4 次 → 提醒换路径；**用户连续 3 次未响应工具确认 → 人已离开，停止发起需确认的动作**。
4. **空回答与假动作不进历史**：只输出 reasoning 无正文、连续"让我查询"却不执行——视为无效回答不保存，hook 注入拦截强制调工具；纠正 3 次仍空则停轮（模型已死循环无法恢复）。大段 prompt 复述/自我指令同样丢弃并生成可读总结兜底。

所有 hook 的核心：纠正行为、避免无意义空转——省钱同时提效。

## 8. 模型分流：不是每个任务都需要最贵的模型

一次完整任务里真正需要重推理的只有主循环和核心 subagent 轮次；标题/分类/富化/建议/内存刷写是"开卡车送信封"。做法：ModelRegistry 四角色指针，所有调用**按角色间接引用**而非直接指定模型名（后端换模型客户端不发版）：

```
default_chat_alias ─ 旗舰 · 主循环/Subagent
classify_alias ──── Flash · 分类/标题/富化/建议/内存/质量评估首轮/压缩降级
responses_alias ─── 场景模型 · Responses 工具
file_extract_alias ─ 长文本模型 · 文件提取
```

classify 型调用成本只有旗舰 1/10~1/20；质量评估自相矛盾时才升旗舰重判。Subagent 也按角色分（explore/data-query 走 Flash，general/plan/verification/code-review 走旗舰）；高度模式化的 K8s Agent 四角色全 Flash，单次诊断费 1/15。用户前端切换的是主对话模型，classify 不开放选择，防止后台调用被带贵。

## 9. 88% 怎么算的

20 轮会话、每轮输入 S + i×Δ（S=固定前缀，Δ=每轮增量），无缓存总发送 = 20S + 210Δ：

| 场景 | 实际发送 | 等价全价 token | 输入费用 | 降幅 |
|---|---|---|---|---|
| 无优化 | 820k | 820k | ¥9.84 | — |
| 仅加缓存 | 820k | 151k | ¥1.81 | 81.6% |
| 裁剪+缓存 | 532k | 96.9k | ¥1.16 | **88.2%** |

仅加缓存时实际仍发送 820k，只是大部分按折扣计费；再做裁剪发送量降到 532k。**88% 不是任何单项优化的功劳，是"少发"和"发得便宜"的乘积**（统一假设下测算，只算主 Agent 输入侧，假设 20 轮都在 5 分钟 TTL 内连续命中）。

## 10. 文章的前提与限定（平移前必读）

> 注：以下五条均出自原文自身陈述；小节标题与条目措辞为提取者归纳，跨系统对照时请回看原文语境（ECode 侧对照见姊妹篇）。

1. 计费模型是百炼（显式 ×10%/创建 ×125%/隐式 ×20%），各家平台的缓存计价与支持度不同，数字不可直接平移；
2. 场景是生产级诊断 agent：30-40 轮、多 subagent、无人值守长会话；
3. 质量护栏先行（第 2 节），所有优化以不降任务完成率为前提；
4. deferred tools 是因为百炼不支持原生 defer 语义才在 harness 层自实现；平台原生支持时实现成本更低；
5. thinking_budget=4096 是其业务样本扫出的拐点，文章明说无通用性。
