# 多模态图片输入 — 详细设计

> 状态：已完成 | 2026-06-10 | 基于 Claude Code + opencode 调研（见同目录调研记录）

---

## 1. 背景与目标

ECode 目前是纯文本输入的 agent。用户无法在对话中粘贴/拖拽图片让 LLM "看"。

**目标**：支持用户在 TUI 输入栏中附带图片（文件路径引用 + 终端粘贴），图片以 base64 编码随消息发送给 LLM，兼容 Anthropic 和 OpenAI 兼容端点。

**非目标**（一期不做）：
- 图片压缩/缩放管道（sharp/photon 等原生依赖）——先跑通链路，后续按需加
- WebP/GIF 动图处理
- 剪贴板直接粘贴图片二进制（终端协议限制，见 §6 分析）

---

## 2. 调研结论（Claude Code vs opencode）

| 维度 | Claude Code | opencode | ECode 选型 |
|------|-------------|----------|-----------|
| **内部格式** | 原生 Anthropic `ImageBlockParam` | 中间 `image_url`（OpenAI 风格）| **中间格式**（ECode 已有 `ECodeContentBlock` 判别联合 + `transform.ts` 双向转换层，天然适配） |
| **输入方式** | 终端剪贴板命令 + 文件路径 + 拖拽 | 前端 UI 上传/粘贴 + read 工具 | **文件路径引用**（拖拽/粘贴文本路径 → 检测图片后缀 → 读文件） |
| **编码** | 纯 base64 | data URL | **base64**（data URL 仅在 OpenAI 方向拼接） |
| **格式检测** | magic bytes（4字节签名） | 文件扩展名 | **magic bytes**（不依赖扩展名，更可靠） |
| **压缩** | sharp 4级降级 | photon WASM | **暂不做**（先跑通链路） |

---

## 3. 改动链路总览

```
用户输入文本（可能含图片文件路径）
  ↓
① UI 层：InputBar 检测文本中的图片路径 → 解析出图片附件
  ↓
② Controller：submit(text) → submit(text, images?)
  ↓
③ Agent 入口：runAgentStream(task, opts) → task 可携带图片
  ↓
④ 消息构造：user message content 从 string 变成 ECodeContentBlock[]（含 image block）
  ↓
⑤ Transform 层：ECodeContentBlock image → Anthropic source.base64 / OpenAI image_url
  ↓
⑥ Provider 发送请求 → LLM "看到"图片
```

## 4. 各层改动详述

### 4.1 类型层 — `src/providers/types.ts`

**新增 `image` 变体到 `ECodeContentBlock`：**

```typescript
export type ECodeContentBlock =
  | { type: 'text'; text: string; providerOptions?: Record<string, unknown> }
  | { type: 'image'; source: ImageSource; providerOptions?: Record<string, unknown> }  // ← 新增
  | { type: 'tool_call'; id: string; name: string; input: Record<string, unknown>; providerOptions?: Record<string, unknown> }
  | { type: 'tool_result'; tool_use_id: string; output: ECodeToolResultOutput; providerOptions?: Record<string, unknown> };

/** 图片来源 — base64 编码（参考 Anthropic Base64ImageSource 结构） */
export interface ImageSource {
  type: 'base64';
  mediaType: string;   // 'image/png' | 'image/jpeg' | 'image/gif' | 'image/webp'
  data: string;         // base64 编码字符串
}
```

**设计依据**：
- 参考 opencode 中间格式但简化：ECode 不用 data URL 做中间表示（data URL 需要正则拆解），直接存 `{ mediaType, data }`，到 transform 层按需拼接。
- `ImageSource` 目前只有 `base64`，预留 `url` 变体（如未来需要传图片 URL）。

### 4.2 Transform 层 — `src/providers/transform.ts`

**ECode → Anthropic 方向**（`toAnthropicBlock` 新增 case）：

```typescript
case 'image':
  return {
    type: 'image',
    source: {
      type: 'base64',
      media_type: block.source.mediaType,  // 注意 snake_case

```

**ECode → OpenAI 方向**（`toOpenAIMessages` 的 user 消息处理新增 case）：

```typescript
// user 消息中的 image block → OpenAI image_url 格式
case 'image': {
  const dataUrl = `data:${b.source.mediaType};base64,${b.source.data}`;
  result.push({ role: 'user', content: [{ type: 'image_url', image_url: { url: dataUrl } }] });
  break;
}
```

> **注意**：OpenAI 方向，如果一个 user 消息同时有 text 和 image block，需要把它们合并到同一条消息的 content 数组里（而非拆成两条消息）。当前 `toOpenAIMessages` 把 user text 和 tool_result 分别 push 独立消息，需要调整逻辑：同一 user 消息内的 text+image block 合并为一条 `role:'user'` 消息（content 为多部分数组），tool_result 仍独立成 `role:'tool'` 消息。

/** magic bytes → mediaType 映射 */
function detectImageType(buffer: Buffer): string | null {
  if (buffer[0] === 0x89 && buffer[1] === 0x50 && buffer[2] === 0x4e && buffer[3] === 0x47)
    return 'image/png';
  if (buffer[0] === 0xff && buffer[1] === 0xd8 && buffer[2] === 0xff)
    return 'image/jpeg';
  if (buffer[0] === 0x47 && buffer[1] === 0x49 && buffer[2] === 0x46)
    return 'image/gif';
  if (buffer[0] === 0x52 && buffer[1] === 0x49 && buffer[2] === 0x46 && buffer[3] === 0x46 &&
      buffer[8] === 0x57 && buffer[9] === 0x45 && buffer[10] === 0x42 && buffer[11] === 0x50)

### 4.7 UI 输入层 — `src/ui/input-bar.tsx`

**核心交互流程**：

1. 用户输入文本（可能含图片文件路径，或从终端拖拽文件得到的路径文本）
2. 按 Enter 提交时，`handleSubmit` 先用 `extractImagePaths(text)` 检测文本中是否包含图片路径
3. 有图片路径 → 逐个 `readImageFromFile()` 读取 → 得到 `ImageSource[]`
4. 调用 `onSubmit(text, images)` 携带图片

**`onSubmit` 签名扩展**：

```typescript
interface InputBarProps {
  onSubmit: (text: string, images?: ImageSource[]) => void;
  // ... 现有 props ...
}
```

**提交逻辑修改**（从同步改为 async）：

```typescript
// 现有（useInput 内）
const trimmed = edit.text.trim();
if (!trimmed) return;
onSubmit(trimmed);
dispatch({ type: 'push', text: trimmed });
setEdit({ text: '', cursor: 0 });

// 改为
const trimmed = edit.text.trim();
if (!trimmed) return;
// 图片检测 + 读取（async）
const imagePaths = extractImagePaths(trimmed);
const images: ImageSource[] = [];
for (const p of imagePaths) {
  const img = await readImageFromFile(p);
  if (img) images.push(img);
}
onSubmit(trimmed, images.length > 0 ? images : undefined);
dispatch({ type: 'push', text: trimmed });
setEdit({ text: '', cursor: 0 });
```

> **注意**：`useInput` 回调是同步的，但 `readImageFromFile` 是 async（读文件 IO）。需要把提交逻辑抽成独立 async 函数，在 useInput 回调中 `void handleSubmitAsync()`。ink 7 下 useInput 回调中 fire async 不影响按键捕获（useInput 是事件驱动的）。

## 6. 终端粘贴图片的限制分析

**问题**：用户在终端按 Ctrl+V / Cmd+V 粘贴**图片**时，终端无法接收图片二进制数据——终端粘贴协议（bracketed paste）只能传文本。

**Claude Code 的解法**：检测到空 bracketed paste 事件后，调用平台命令读系统剪贴板图片（macOS: osascript / Windows: PowerShell Get-Clipboard / Linux: xclip）。

**ECode 一期策略**：**不实现剪贴板图片粘贴**，只支持文件路径引用。原因：
1. 跨平台剪贴板命令复杂度高（3 套平台命令 + 格式转换 + BMP→PNG）
2. Windows Terminal / Git Bash 的 bracketed paste 行为不一致
3. 文件路径引用已覆盖拖拽场景（终端拖文件进来会粘贴为路径文本）
4. 后续可作为体验增强单独迭代

**后续增强路径**（不在一期范围）：
- 检测 `Ctrl+V` 快捷键（非 bracketed paste）→ 调用 `powershell Get-Clipboard -Format Image` 读图 → base64
- macOS: `osascript -e 'the clipboard as «class PNGf»'`
- Linux: `xclip -selection clipboard -t image/png -o`
