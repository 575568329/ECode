## 0. 背景与输入

M12 交付了 daemon（`ecode serve` 多项目 HTTP + 协议双枚举 + 审批可答帧 + TUI 客户端化），Web/手机滑入 M13。2026-08-24 用户连续拍板三轮，构成本方案的直接输入：

| 输入 | 内容 | 锚点 |
|---|---|---|
| 需求收窄 | Web/移动端打开→见本机哪些项目有历史→点项目新建/恢复对话→可输新项目路径开聊；恢复走历史文件，不做活接管 | M12 方案 §15 |
| 架构批扩容 | 同项目多对话并发（会话级并发+项目级共享）+ mux 单流同步多基座；原三小块（半天）被吸收 | M12 方案 §15.1 |
| 源码实证 | harness/opencode 的会话建模/并发/回收/mux 全量锚点对照（本方案的设计证据链，本文不重复贴码，**全部引用该文档**） | [解析/2026-08-24_M13多会话并发与Web同步调研_已完成](../解析/2026-08-24_M13多会话并发与Web同步调研_已完成.md) |
| M12 地基 | 协议 27 事件/18 命令、ApprovalBroker、ProjectRegistry、serveMulti、daemon token/loopback | M12 方案 §3-§5 + §13 实施记录 |

继承的 M12 决策（Q1-Q13 摘要）：React 19 + Vite + Tailwind（Q3）；REST + SSE 单流（Q4）；Basic Auth 首发 + token 并存（Q5）；手机=响应式 Web + PWA 不做原生（Q6）；企微/飞书 M13（Q8，本方案列为可选批）。

## 1. 目标与非目标

**目标**（验收场景 G3 展开，M12 §15 已定）：

1. 手机/Web 打开 → 看到本机所有有历史记录的项目（registered ∪ active ∪ 历史聚合）
2. 点项目 → 会话列表（冷热合并）→ 新建对话 / 恢复历史对话，恢复后继续聊、能答审批
3. 同项目多个对话**并行进行**（A 跑长任务 B 同时聊天，互不换台）
4. 可输入新项目路径开聊（428 confirm 栅栏已有）
5. 多端同帧共享；审批谁先答谁得

**非目标（明确不做，防翻烧饼）**：

- 活流回填 / SSE 补帧 / 断线增量重放——恢复走 session/read 全量或尾页（两家同款全量重放路线；mux 是汇流不是回放）
- TUI 跨进程连 serve（用户核心入口是 Web/移动端，不挂账）
- 手机原生 App；个人微信接入（封号风险）
- 模型难度自动路由（2026-08-24 讨论定论：代码任务难度不可先验判定 + 逐轮换模型丢缓存前缀 + 弱模型工具循环烧轮次，三头不讨好；便宜模型靠 roles 静态指派，见成本方案 §4.5）
- 双人协作语义（同时编辑/光标同步等）——多端是"共享会话"不是"协同编辑"

## 2. 总体架构

```
浏览器 / 手机 PWA（React 19 + Vite + Tailwind）
   │  GET /            静态资源（daemon 托管 dist）
   │  GET /api/events.mux      ← 唯一 EventSource：mux 信封帧 + host 级生命周期帧
   │  POST /api/p/<path>/cmd   ← 命令信封 {sessionId, op}（协议命令零改动）
   ▼
serveMulti（M12 交付 + 本方案扩展）
   ├─ ProjectRegistry：path → ProjectHost（锁语义不变=项目唯一）
   │     ├─ ProjectHost（项目级共享，常驻）
   │     │    config/provider/tools 装配/MCP/checkpoint/quality/hooks/skills
   │     ├─ ConversationHost A（会话级私有）
   │     │    messages/loop/channel/broker/插话队列/usage/sandbox 档/rewind
   │     ├─ ConversationHost B ←── 同项目并行对话
   │     └─ Map<sessionId, ConversationHost>（幂等单飞）
   └─ mux 汇流层：所有 ConversationHost 的 channel 订阅 → 信封包装 → 单流广播
```

分层依据（源码实证见调研文档 §1 对照表、§4 改造清单）：opencode 的 Instance/Session 两层同构；harness 的 Session+Agent 1:1 与 mux 单流同形。

## 3. 架构批设计（W1-W4）

### 3.1 两层宿主（W1）

`HostSession`（M12 单体）拆为：

| | ProjectHost（项目级，registry 持有） | ConversationHost（会话级） |
|---|---|---|
| 生命周期 | acquire 创建，**常驻不回收**（两家实证，见调研 §3.5） | prompt 隐式创建 / restore ensure；闲置 sweep |
| 持有 | makeDeps 的项目级件：providerRegistry、tools（HookedToolRegistry）、MCP manager、checkpoint、quality、hookRunner、logger、config getter、skills/plugin 装配 | messages 权威、runLoop 运行态、InMemoryChannel、ApprovalBroker、插话队列、usage 累计器、sandbox 当前档、FileHistoryStore（按 sessionId）、rewind 线 |
| 复用 | 同项目全部对话共享一份 | 一对话一份，互不串台 |

- `makeDeps` 拆两段：`makeProjectDeps(config, logger, cwd)`（现 makeDeps 去会话件）+ `makeConversationDeps(projectDeps, sessionId)`（history/usage/broker/channel）。
- **TuiApp 与 argv 保持等价形态**：REPL = makeProjectDeps + 单 ConversationHost（行为与 M12 完全一致，现有 386 条 TUI 用例是等价性安全网）；argv = runOnce 内联同构。
- 宿主事件翻译/afterTools/hooks 分发逻辑随 ConversationHost 走（这些是轮次语义）；mountBridges 的桥挂 ProjectHost（skill/MCP 项目级）+ 会话窄端口指到当前 ConversationHost（D5 模式延续）。
- 子代理（makeTaskTool）继续吃 projectDeps 的 getter 闭包，confirm/askUser 经 session 窄端口到所属 ConversationHost——多会话下子代理审批不串台。

### 3.2 协议信封与命令路由（W2）

- **MuxFrame 信封**（内层 27 事件枚举零改动）：`{ project: string, sessionId?: string, ev: ProtocolEvent } | HostEvent`——汇流层包装，不改内层帧结构；单项目端点 `/api/p/<path>/events` 保持现状裸帧（调试端点）。
- **HostEvent 新增 5 枚举**：`project/added`、`project/removed`、`session/created`（含 cwd/sessionId/firstUser）、`session/removed`、`session/baseline`（连接时全量活会话清单）。
- **命令信封**：`POST /api/p/<path>/cmd` body 从裸 ProtocolCommand 改为 `{ sessionId?: string, op: ProtocolCommand }`——缺省 sessionId = 项目默认会话（兼容 TUI 语义）；**prompt 不带 sessionId = 新建对话**（隐式创建，回执带新 sessionId，后续帧全带）。
- `session/restore`（枚举已有，M12 未接 case）接线：**ensure 语义**——ConversationHost 已活复用；不存在则 history 读全量行 restoreFrom 载入新建；并发同 id 幂等单飞（harness `sessionCreations` 同款，deferred 模式——M12 实测坑⑤）。
- 审批可答帧带 sessionId（ApprovalBroker 本就是会话级——拆分后天然成立）。

### 3.3 mux 端点与汇流（W3）

- `GET /api/events.mux`：每连接遍历所有 ProjectHost 的全部 ConversationHost subscribe（复用 M12 SSE 工程包：drain 背压/15s 心跳/token/loopback/断连退订）+ ProjectRegistry 的项目增删订阅。
- 连接三连（对齐 harness mux，调研 §2.4）：①`session/baseline`（当前所有活会话+项目清单）；②重放各会话 pending 审批帧（broker 订阅即重放已有，汇流层接上）；③连接后持续广播信封帧。
- 单项目 events 端点保留；两个端点可并存订阅（互不干扰——channel 本就多订阅 fan-out）。

### 3.4 会话生命周期与回收（W2/W4）

- 创建：prompt 隐式（见 3.2）；显式 restore ensure；冷会话（历史文件存在、宿主无实例）restore 时载入。
- 回收（对齐调研 §3.5 结论）：**项目基座常驻**（sweepIdle 的项目维度退役；daemon 退出 disposeAll 不变）；**会话级 sweep**——无订阅者 && brokerPending=0 && loop 空闲 && 超过 `sessionIdleMinutes`（默认 120，0=不收）→ ConversationHost.dispose（messages 内存释放/channel dispose；**历史文件/checkpoint 不动**，restore 即续）。会话被收后 mux 广播 `session/removed`。
- 运行态会话（loop 在跑/审批挂起/有订阅者）永不收。

### 3.5 历史与项目发现（W4，原三小块）

1. **meta 补 cwd**：`FileHistoryStore` 构造收 cwd，MetaLine 增 `cwd` 字段（启动期校验绝对路径）；`makeConversationDeps` 传入。存量文件首行无 cwd 不可归档（不回填）——Web 列表归入"未归类"。
2. **`/api/projects` 增强**：registered ∪ active ∪ 历史聚合（扫 `~/.ecode/sessions/` 首行 meta.cwd 去重；loadAll 首行 2048B 读法现成）。
3. **`session/list` 冷热合并**：活 ConversationHost（含 running 态）∪ 历史文件 meta（含 cwd/firstUser/createdAt），按 updatedAt 降序。

### 3.6 冲突防护（对齐调研 §3.4/§3.5，不建大机制）

- checkpoint content-addressed：多会话快照哈希天然去重，无需 gitdir 锁。
- edit per-file 信号量：**挂账观察**（真出现两对话编辑同文件再上，进程级全局锁 10 行内）。
- git autoCommit 多会话交织：git 原子不坏仓库，提交历史交织低危——挂账观察。
- write 无锁 last-write-wins：与两家同为社会约束（"别同时让两个对话改同一个文件"），文档提示即可。

### 3.7 网络与鉴权（W3/W5）

- **绑定放开**：`ECODE_SERVE_HOST`（默认 `127.0.0.1`）。设为非 loopback 地址时**强制要求 `ECODE_SERVER_PASSWORD`**，否则拒绝启动（手机局域网访问的前提；防"忘了密码裸奔局域网"）。
- Web 鉴权双通道（M12 Q5 首发）：server.json token（本机浏览器：首次访问输入一次存 localStorage）或 Basic 密码（局域网手机）；两者校验逻辑已并存（Bearer/Basic 均可，M12 已做）。
- 审批代答防线不变：所有端点（除 health）鉴权 + 非 loopback 强制密码。

## 4. Web 客户端（W5-W6）

- **形态**：React 19 + Vite + Tailwind 手写组件（Q3）；构建产物 dist 由 daemon 直接托管（`GET /`→index.html，静态路由 fallback 到 index.html 的 SPA 语义），不另起服务器。
- **数据层**：全局单 EventSource（mux）+ 按 `project/sessionId` 过滤分发；命令走 fetch POST（回执式）。状态管理选型（Zustand vs useReducer）W5 批定，原则：服务端权威、前端仅渲染态。
- **页面结构**：
  - 左栏两级树：项目列表（含"未归类"+ 输入新项目路径入口）→ 会话列表（running 标记/新建按钮）
  - 右侧对话区：流式 delta 渲染、工具卡（item started/completed 折叠详情）、usage/cost 角标
  - 审批可答帧 UI：按 ApprovalKind 分策略提示（sensitive 标红强调不可"始终允许"）；askSelect/askUser 面板；插话输入框（StartOrSteer）
- **断线策略**：EventSource 自动重连；重连后对当前打开会话 `session/read` 补拉全量（不做增量补帧——非目标）；mux baseline 帧刷新列表。
- **B5 缩水命令最小子集**：`model/set`（顶栏切模型，W6 带）；rewind/panel/command/exec 维持挂账（Web 无对应 UI 前不做）。

## 5. 手机 PWA（W7）

- 响应式布局（列表页/对话页两态自适应窄屏）；manifest + service worker 离线壳（仅壳缓存，对话需在线）。
- 移动端交互适配：审批大按钮、工具卡默认折叠、软键盘弹起视口处理。
- 弱网：SSE 断线重连已有；PWA 仅前台连 mux（后台自动断，回前台 baseline 重建）。
- G3 真机验收（DevTools 移动模拟 + 用户真机各一轮）。

## 7. 决策台账

| # | 问题 | 决策 | 依据 / 被否决备选 |
|---|---|---|---|
| Q1 | 会话并发粒度 | 会话级宿主（ConversationHost 轻对象） | 两家同构（opencode Session/Runner、harness Agent）；被否决：维持项目级换台（Web 同项目多开是明确需求） |
| Q2 | mux 帧维度实现 | 信封包装，内层 27 枚举零改动 | 改动最小、单项目端点兼容；被否决：帧结构内嵌 project/sessionId（全枚举动一遍，协议不稳定） |
| Q3 | 新对话创建语义 | prompt 不带 sessionId 隐式创建，回执带 id | 少一次往返；被否决：显式 session/create 命令（多一枚举多一步，收益仅语义显式） |
| Q4 | restore 语义 | ensure（活复用/死载入/并发单飞） | 幂等天然；被否决：每次 restore 重建（丢运行态，A 端正在跑会被拆） |
| Q5 | 项目基座回收 | 常驻不收 | 两家实证（调研 §3.5）；被否决：沿用 30 分钟 sweep（冷启动卡顿，Web 体验差） |
| Q6 | 会话回收阈值 | 120 分钟 + 三闸（订阅/审批/运行态） | 会话内存态重（完整 messages）确需回收，但比 M12 项目级 30 分钟放宽 |
| Q7 | Web 托管 | daemon 直接托管 dist | 零新进程零新端口；被否决：独立 Web 服务器（部署面翻倍） |
| Q8 | 手机访问 | ECODE_SERVE_HOST 放开 + 强制密码 | loopback 默认安全不动；密码与绑定联动防裸奔 |
| Q9 | IM（企微/飞书） | 可选批，用户确认需求后排期 | 本方案不展开设计 |
| Q10 | 断线恢复 | 重连后 session/read 全量补拉 | 非目标已定不做补帧；全量拉取实现最简且冷热同源 |

## 10. 验收

- **G-架构门（W4 末）**：同项目双 ConversationHost 并行对话互不串台（双 HttpTransport 各连各的会话同帧）；会话 sweep 三闸断言；项目基座常驻断言；TUI/argv 全部既有用例零改动通过。
- **G3 真机门（W7 末）**：手机打开 → 项目列表（含 REPL 历史项目）→ 恢复会话续聊 → 答审批 → 新建对话并行 → 双端同帧。
