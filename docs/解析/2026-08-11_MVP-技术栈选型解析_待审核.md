# ECode MVP 技术栈选型解析

> 解析日期：2026-08-11 · 状态：待审核

> 结论已落入详设对应章节；本文保留论证过程作为决策依据。

## 决策 1：Node 模块格式 → ESM

### 问题陈述
ECode 是新项目，无 CJS 历史包袱。Node 同时支持 CJS 与 ESM，需选定一种作为工程基线，避免混用导致互操作坑。

### 备选方案

**A. ESM**（`package.json:"type":"module"`，`tsconfig:"module":"NodeNext"`）
- ✅ 现代标准；顶层 `await`（启动期 `await` 读 config / 烟测端点友好）；TS/Node≥18 方向；依赖栈全 ESM-ready
- ❌ import 路径须带 `.js` 扩展名（即使源是 `.ts`）；CJS 互操作（纯 CJS 包默认导入）；`__dirname`/`__filename` 不存在；JSON import 要 assertion

**B. CJS**（`require/module.exports`）
- ✅ 老生态兼容好；无互操作问题
- ❌ 遗产路径；无顶层 `await`；与现代 Node/TS 方向相悖

### 论证
- 依赖核实：`@anthropic-ai/sdk`、`ink`、`react`、`ajv`、`fast-glob`、`dotenv` 均原生 ESM。`ink-text-input`/`ink-spinner`/`marked`/`cli-highlight` 的 ESM 导出形态须在 M1 烟测核实（若某核心依赖只有 CJS 构建且互操作踩雷严重，才回退）。
- 顶层 `await` 对流式初始化（启动时 `await` 加载 config、烟测端点）有实际价值，CJS 要包 async IIFE。
- ESM 的 4 个坑都是已知、可规避的工程约定，不是阻断性问题。

### 结论
**选 ESM。** 4 个坑记入详设 0.2「ESM 约定」。

### 反驳
**最大风险**：某个核心依赖（最可能 `ink-text-input` 等 Ink 生态包）只有 CJS 构建，named import 拿不到，需 `createRequire` 或默认导入绕行，DX 变差。
**什么情况反悔**：M1 烟测发现 ≥2 个核心依赖互操作踩雷严重 → 回退 CJS。可证伪点明确：M1 烟测。

## 决策 2：TUI 框架与实现深度 → 标准 Ink 7 + 自建三件

### 问题陈述
TUI 要兼顾：流式渲染 + Ctrl+C 中断 + 折叠/展开内容 + 工具调用展示 + 终端 Markdown。需选定框架，并决定「用标准库拼」还是「自建底层渲染引擎」。

### 备选方案

**A. 标准 Ink 7 + `@inkjs/ui` + 自建三件**（Markdown / 折叠 / 流式分阶段）
- ✅ TS 生态唯一成熟的组件化 TUI；被 Claude Code / Gemini CLI / Qwen Code 验证；React DX 最好；`<Static>` 处理大量历史；`useFocus` 焦点基础
- ❌ 折叠/Markdown/流式无现成活跃库，须自建（~5-7 天）；alt screen 无原生回滚；不可 pipe；超长内容性能靠 `<Static>` 缓解

**B. 自建 React reconciler + Yoga 移植 + ANSI 解析器**（Claude Code 路线）
- ✅ 生产级渲染性能（60FPS）、复杂键绑定（chord 序列）、精确终端控制
- ❌ 投入巨大（Claude Code 的 Yoga 移植 ~2700 行 + 自定义输入系统 + 完整 ANSI/CSI/DEC/OSC 解析器 + 25+ 组件，数工程师·数月）；MVP 不需要这个精细度

**C. 流式 stdout**（`process.stdout.write`，Aider 式）
- ✅ 最省事；可 pipe；性能好；零框架
- ❌ **打出去定型，不能折叠/展开**（恰好砍掉需求）；UX 朴素；无焦点导航

**D. blessed / neo-blessed / terminal-kit**
- ✅ 内置折叠/list/widget
- ❌ 维护停滞（blessed）；命令式 + 坐标布局；TS 支持差；DX 远不如 Ink

### 论证
- **关键调研事实**（2026-08）：
  - Claude Code 用自定义 React reconciler + 纯 TS Yoga 移植（~2700 行）+ 自定义输入系统 + 扩展 ANSI 解析器 + 25+ 组件（REPL/StreamingText/Markdown/Select…）。来源：[Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built)、[dev.to 源码分析](https://dev.to/minnzen/i-studied-claude-codes-leaked-source-and-built-a-terminal-ui-toolkit-from-it-4poh)。
  - 官方 [`@inkjs/ui`](https://github.com/vadimdemedes/ink-ui)（vadimdemedes）仅 13 个基础件（TextInput/Select/MultiSelect/Spinner/ProgressBar/Badge/StatusMessage/Alert/ConfirmInput…），**无 Markdown、无折叠、无 Focus、无 ScrollArea**。
  - 第三方 [inkui-lib](https://inkui-lib.vercel.app/) 亦无折叠/Markdown。
  - [wrxck/ink](https://github.com/wrxck/ink)（Ink 5）有 ink-tree（折叠）+ Markdown + diff，但 **9 提交 / 1 star，停滞**，不可硬依赖。
- **组件库覆盖矩阵**（ECode 要的件）：

  | 需求 | @inkjs/ui | wrxck/ink(停滞) | 结论 |
  |---|---|---|---|
  | 输入/Spinner/Select/确认/StatusBar | ✅ | ✅ | 直接用 |
  | 消息列表滚动 | ❌ | ✅ | Ink `<Static>` + 自建 |
  | Markdown 渲染 | ❌ | ✅(停滞) | **必须自建** |
  | 折叠/展开 | ❌ | ✅(ink-tree,停滞) | **必须自建** |
  | 流式分阶段渲染 | ❌ | ❌ | **必须自建** |

- **三件自建的本质**：应用层 React 问题（state + 条件渲染 + 字符串处理），**不是**底层引擎（reconciler/Yoga/ANSI）。各约：流式分阶段 ~2 天、终端 Markdown ~2-3 天、折叠 ~1-2 天。
- **「必须自建」≠「难」**：不走 Claude Code 的 reconciler 路线，MVP 的 TUI 是可控的（~2 周）。

### 结论
**选 A：标准 Ink 7 + `@inkjs/ui` + 自建三件（Markdown / 折叠 / 流式分阶段渲染）。**
- `@inkjs/ui` 虽只 6 提交，但基础件（输入/选择/spinner）稳定，活跃度够用。
- wrxck/ink 仅作**思路参考**（抄 ink-tree 折叠实现、Markdown 宽度处理），不引依赖。
- 工作量：M2（接 TUI + 流式 + Ctrl+C）~3-5 天，M3（折叠 + diff 确认 + 工具展示 + 焦点）~5-7 天。

### 反驳
**最大风险**：Ink 7.0 是重大更新（重做输入处理），`ink-text-input`/`ink-spinner`/`@inkjs/ui` 是否跟上 7.0 未核实；`<Static>` 在真实会话长度（几百条消息）下重绘性能未实测。
**什么情况反悔**：M2 烟测发现官方组件未跟上 Ink 7、或 `<Static>` 重绘 > 100ms → 评估切流式或引入增量渲染。可证伪点：M2 烟测。

## 决策 3：grep 实现 → 纯 JS

### 问题陈述
grep 工具要跨平台（Windows/Git Bash ↔ macOS ↔ Linux）一致、零外部依赖（呼应 1.1「配置与依赖方向」）。实现路径有四种。

### 备选方案

| 方案 | 速度 | 外部依赖 | 跨平台 | 体积 | 零配置自洽 |
|---|---|---|---|---|---|
| **A. 纯 JS**（fast-glob 取文件 + RegExp） | 慢 | 无 | ✅ 完美 | 0 | ✅ |
| B. 内置 ripgrep 二进制（`@vscode/ripgrep`） | 快 | postinstall 下载 | ✅ | 几 MB | ⚠️ 内网/离线失败 |
| C. 检测系统 `rg`，回退纯 JS | 快(有rg) | 可选 | ⚠️ | 0 | ❌ 依赖外部环境 |
| D. 调系统 `grep`（Git Bash 自带 GNU） | 快 | Git Bash | ⚠️ BSD≠GNU | 0 | ❌ 依赖 shell |

### 论证
- ECode 首要运行环境是 Windows/Git Bash，但不能假设用户装了 rg；postinstall 下载在内网/离线会失败（违 1.1）。
- 纯 JS 的「慢」在大仓库（几十 MB）才到秒级，MVP 够用；性能瓶颈出现时（后续版本）切 B。
- 纯 JS 的额外好处：**零 OS 差异**（grep 行为跨平台完全一致），与 ls/glob 共用同一套文件遍历 + `.ecodeignore` 逻辑。

### 结论
**选 A：纯 JS。** MVP 够用；性能不足时后续切内置 rg。

### 反驳
**最大风险**：大仓库/大文件搜索慢（秒级），LLM 频繁调用 grep 时拖累 Loop。
**什么情况反悔**：实测单次 grep > 3s 且为高频操作 → 引入 `@vscode/ripgrep`（B）。

## 决策 4：ls 工具 → 新增独立只读 ls（工具集 6→7）

### 问题陈述
LLM 需要「列目录内容 / 看文件元信息」。原设计 6 工具无 ls，靠 bash+ls 实现。问题：bash 是副作用工具（`readonly:false`），ls 走它会被要求 y/n 确认，且跨平台不一致、不尊重 `.ecodeignore`。需决定 ls 的归属。

### 备选方案

**A. 新增独立只读 ls 工具**（readonly:true）
- ✅ 免确认、可与 read_file/glob/grep 并行；纯 JS（fs.readdir + fs.stat）零 shell 依赖；尊重 `.ecodeignore`；输出结构化
- ❌ 工具集 +1（7 个），LLM 工具选择空间略增

**B. 砍 glob，用 bash+ls/find 替代**
- ❌ bash `readonly:false` → **每次列目录要确认**（读操作不该确认）；shell glob `**` globstar 跨 shell 行为不一（bash 默认关、zsh 默认开）；GNU find ≠ BSD find；不尊重 `.ecodeignore`（node_modules 爆量 + 密钥进 context）；输出非结构化

**C. 让 bash 工具识别只读命令（ls/cat）自动免确认**
- ❌ 命令分类器静态识别不准（`ls; rm -rf /` 复合、管道、变量展开）；把「命令识别」塞进工具层是泄漏；二元 `readonly` 标志比命令嗅探干净

### 论证
- **核心论据**：详设 4.5 已定 bash 是副作用工具（确认 + 串行）。ls 经 bash = 每次确认，读目录体验不可接受。
- **对标**：Claude Code 把 LS 做成独立只读工具（LS + Glob + Grep + Bash 四个分开），原因相同——只读操作走免确认通道。
- **判断标准**：只读操作（读文件/列目录/搜内容/找文件）都该是独立只读工具；bash 只留给真正副作用命令。
- **职责区分**（避免 LLM 在 ls/glob 间犹豫）：

  | 工具 | 回答 | 典型 |
  |---|---|---|
  | ls | 这个目录里有什么(+详情) | "src 下有什么" |
  | glob | 按模式匹配的文件路径 | "所有 *.ts" |
  | grep | 文件内容里匹配的行 | "哪行调用 foo()" |
  | read_file | 单文件完整内容 | "看 foo.ts" |

### 结论
**选 A：新增独立只读 ls。** 工具集 6→7（只读通道：read_file/ls/glob/grep；副作用通道：write_file/edit_file/bash）。ls/glob/grep 共用 `.ecodeignore`。
- input_schema（扁平，呼应决策 7）：`path`(必填) / `depth`(1-3，默认 1) / `all`(默认 false)。
- MVP 不显示权限字段（Windows chmod 语义不同），只给 type/size/mtime。

### 反驳
**最大风险**：工具增多，LLM 在 ls vs glob 间选错（用 glob 列目录、用 ls 做模式匹配）。
**缓解**：system prompt 里写清四工具职责边界（上表）；description 写明典型场景。可证伪点：集成测试观察 LLM 工具选择准确率。

## 决策 5：glob 大小写 → 显式 caseSensitiveMatch

### 问题陈述
`fast-glob` 在 Windows 默认大小写**不敏感**、Linux **敏感**。同一模式 `*.TS` 在不同 OS 结果不同，行为飘忽。

### 备选方案
- **A. 显式 `caseSensitiveMatch: true`**：全平台一致（敏感）。
- B. 用平台默认：Win 不敏感、Linux 敏感 → 同模式结果跨 OS 不一致。

### 论证
工具行为应跨平台可预期。LLM 传 `*.ts` 应在所有 OS 只匹配小写。让平台默认会导致「在我机器上能搜到」的玄学问题。

### 结论
**选 A：显式 `caseSensitiveMatch: true`。** 跨平台行为唯一一致的选择。

### 反驳
**风险**：Windows 用户习惯不敏感匹配，传 `*.TS` 搜不到 `a.ts`。
**缓解**：这是 LLM 调用，不是用户手输模式；LLM 按 schema 约束传小写即可。

## 决策 6：bash 跨 OS 一致性 → LLM 负责，MVP 只保证 Git Bash

### 问题陈述
bash 工具跑用户/LLM 给的命令。Git Bash(GNU) ↔ macOS(BSD) ↔ Linux(GNU) 三套 coreutils：`sed -i`、`date`、`ls`/`grep` flag、`cp`/`mv` 行为都有差异。工具层无法保证命令跨 OS 行为一致。

### 备选方案
- **A. MVP 工具层只保证 Git Bash（Windows），跨 OS 一致性由 LLM 负责**：文档明说，coreutils 差异不归工具管。
- B. 工具层翻译/规范化命令：不可行（shell 语法复杂，静态翻译不准，违 KISS）。
- C. 强制统一 shell（如永远 Git Bash）：macOS/Linux 用户强装 Git Bash 不现实。

### 论证
- 工具层能保证的是「执行环境」（cwd、timeout、危险命令拦截、输出截断），**不能**保证「命令语义跨 OS 一致」——那是 shell/coreutils 的事。
- ECode 首要环境是 Windows/Git Bash，MVP 锁定它合理。macOS/Linux 用户用系统 shell，命令可移植性靠 LLM 判断（LLM 知道目标平台时可给可移植命令）。

### 结论
**选 A。** 详设 2.3 bash 约束 + 4.6 跨平台明说：「MVP 工具层只保证 Git Bash，跨 OS coreutils 差异由 LLM 负责，不在 MVP 承诺内」。

### 反驳
**风险**：同一 prompt 在 Win/macOS/Linux 跑出不同结果，用户困惑。
**缓解**：system prompt 注入当前 `process.platform`，LLM 据此给平台适配命令；后续版本可考虑 platform-aware 提示。

## 决策 7：JSON Schema 复杂度 → 扁平化

### 问题陈述
AJV 用完整 JSON Schema，但 GLM（经 Astron 兼容端点）对复杂特性（`oneOf`/`anyOf`/`$ref`/`pattern`/`enum` 嵌套）的支持度未知。工具 schema 若用了不支持的特性，LLM 可能给出畸形输入或拒调。

### 备选方案
- **A. MVP 工具 schema 扁平化**：只用 `type` + `properties` + `required` + 基础约束（`minimum`/`maximum`/`default`），避开 `oneOf`/`anyOf`/`$ref`。
- B. 用完整 JSON Schema：表达力强，但 GLM 兼容度未知，风险高。

### 论证
- 评审报告已标「Astron 兼容度风险」为项目级单点风险。MVP 6→7 个工具的入参都简单（路径、字符串、布尔、整数），扁平 schema 完全够表达，不需要高级特性。
- 扁平 schema 还降低 AJV 校验复杂度、减少 LLM 误用。

### 结论
**选 A。** 详设 2.1 注明：MVP 工具 schema 用扁平结构；GLM 对高级特性的支持度列为 M1 烟测项。

### 反驳
**风险**：未来某工具需要枚举/联合类型（如 `type: file|dir`），扁平表达不了。
**缓解**：用 `type: string` + `description` 约束 + 工具内自行校验；确需高级特性时先在 M1 烟测验证 GLM 支持。
