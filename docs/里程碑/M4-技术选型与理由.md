# M4 技术选型与理由

> **里程碑**：M4 "信任问题" —— 安全进阶 + 正确性 + 健壮性  
> **前置依赖**：M3.5（权限档 A + REPL 已完成）  
> **目标**：从"能用"到"敢用" —— 危险操作拦得住、编辑错误能自愈、异常恢复有章法

---

## 一、核心问题与选型总览

M3.5 已实现权限档 A（dangerous 二元判断 + 弹窗确认 + allow 白名单）和基础 REPL。M4 要解决三个核心问题：

| 问题域 | 当前缺陷 | M4 目标 | 技术选型 |
|--------|----------|---------|----------|
| **权限控制精细化** | 只有 dangerous/safe 二元判断，无法细粒度控制（如"允许编辑但拒绝删除"） | 四档模式（default/acceptEdits/plan/bypass）+ deny/ask 规则 + 命令解析 | 兼容 `.claude/settings.json`，参考 Claude Code 权限系统 |
| **edit 工具正确性** | 匹配失败直接报错，agent 无上下文修正 | 匹配失败 → 回喂真实行号+内容 → LLM 重试 | 增强 tool_result.is_error + 上下文回喂（参考 aider） |
| **错误恢复完整性** | 仅有基础 API 重试，无死循环防护、工具错误回喂不完整 | 三条恢复路径：API 退避 / 工具回喂 / 死循环检测 | 结构化错误类型 + 退避策略 + 重复动作检测 |

## 二、权限系统进阶（档位 B/C）

### 2.1 设计目标

- **兼容 Claude Code 配置**：读取 `~/.claude/settings.json` 的 `permissionMode` 字段
- **四档模式**：
  - `default`：危险操作需确认（档 A 行为）
  - `acceptEdits`：自动允许文件编辑，其他危险操作仍需确认
  - `plan`：所有操作需确认（最严格）
  - `bypass`：自动允许所有操作（开发调试用，生产禁用）
- **精细规则**：`allowedCommands` / `deniedCommands` / `alwaysAllowPaths` / `alwaysDenyPaths`
- **持久化记忆**：单次会话的 `yes-always` 选择可保存到配置，下次免询问

### 2.2 技术选型

| 选项 | 方案 | 理由 |
|------|------|------|
| **配置格式** | 兼容 `.claude/settings.json` | 用户已有 Claude Code 配置，迁移成本低 |
| **命令解析** | 自研轻量解析器（引号 / 管道 / 重定向识别） | Bash 完整解析需 shell-quote（8.4KB），我们只需提取主命令+危险参数，200 行可解决 |
| **规则引擎** | deny 优先级 > ask 优先级 > allow | 参考防火墙规则：黑名单优先，白名单兜底 |
| **yes-always 持久化** | 写回 `allowedCommands` / `alwaysAllowPaths` | 用户显式选择"总是允许"时生效，会话内临时存储不写盘 |

**放弃方案：**
- ❌ 完整 Bash AST 解析（shell-quote / bash-parser）：过重，且无法覆盖所有 shell 方言
- ❌ 沙箱执行（Docker / VM）：M5+ 功能，M4 阶段通过权限拦截即可

### 2.3 命令解析策略

**目标**：识别主命令 + 危险参数（如 `rm -rf` / `git push --force`），无需完整 AST。

**解析层次**：
1. **管道分割**：`cmd1 | cmd2` → 分别检查每段
2. **引号处理**：`rm "file with spaces.txt"` → 主命令 `rm`
3. **危险参数识别**：
   - `rm` + `-rf` / `-r` → 危险
   - `git push` + `--force` / `-f` → 危险
   - `chmod` / `chown` → 始终危险
4. **路径提取**：检查操作目标是否在 `alwaysDenyPaths`

**实现**：轻量正则 + 状态机（200 行，无依赖）

## 三、edit 工具正确性闭环

### 3.1 问题根源

当前 `edit_file` 实现（基于字符串匹配 `old_string` → `new_string`）：
- **匹配失败**：模型给的 `old_string` 与文件实际内容不符（缩进差异、多余空格、部分匹配）
- **LLM 无上下文**：tool_result 只返回 `"not found"`，模型无法判断是"文件不存在"还是"匹配失败"
- **无重试机制**：一次失败后 agent 可能放弃或胡乱重试

**参考数据**：aider 编辑格式测试显示，正确的错误恢复能将重构成功率从 20% 提升到 61%。

### 3.2 设计方案

**核心思路**：匹配失败时，**把文件真实行号+内容回喂给 LLM**，让它自己对比差异、生成正确的匹配串。

**流程**：
```
1. 模型调用 edit_file(old_string="...", new_string="...")
2. 执行匹配
   ├─ 成功 → 返回 {success: true}
   └─ 失败 → fuzzy search 找最接近的 5 行
3. 返回增强 tool_result：
   {
     is_error: true,
     content: "匹配失败。文件实际内容（第 10-15 行）：\n<actual lines>\n请检查缩进/空格差异"
   }
4. 模型根据真实行重新构造 old_string → 再次调用 edit_file
```

### 3.3 技术选型

| 组件 | 方案 | 理由 |
|------|------|------|
| **fuzzy search** | Levenshtein 距离（`fastest-levenshtein`，1KB） | 找到最接近的行，无需复杂 diff 算法 |
| **上下文窗口** | 匹配失败时返回 ±5 行 | 足够让 LLM 看清缩进/格式，不至于占用过多 token |
| **重试次数** | 同一文件+位置最多重试 3 次 | 防止死循环，3 次失败后要求模型换思路 |
| **工具签名扩展** | 增加可选参数 `line_number`（精确行号编辑） | 模型可选择"基于行号"或"基于匹配"两种模式 |

**参考实现**：
- aider 的 `EditBlockFencer`（whole/diff/udiff 三格式）
- Claude Code 的 `Edit` 工具（返回 `file_path:line_number` 链接）

## 四、错误恢复三条路径

### 4.1 分类与策略

| 错误类型 | 场景 | 恢复策略 | 技术方案 |
|----------|------|----------|----------|
| **API 错误** | 429/529/500/504 | 指数退避 + jitter | 结构化 RetryPolicy，区分可重试/不可重试 |
| **工具错误** | 文件不存在、权限拒绝、命令失败 | 回喂 `is_error` + 详细错误信息 | tool_result.is_error + 上下文增强 |
| **死循环** | 重复相同操作、迭代超上限 | 重复动作检测 + 强制中断 | 滑动窗口哈希 + 25 轮上限 |

### 4.2 API 退避策略

**目标**：区分"短暂过载"（可重试）和"请求非法"（不可重试）。

**分类表**：

| 状态码 | 含义 | 策略 |
|--------|------|------|
| 429 | Rate limit | 重试（指数退避，最多 3 次，初始 1s） |
| 500/502/503 | 服务端瞬时故障 | 重试（初始 2s） |
| 504 | Gateway timeout | 重试 1 次（可能是长响应） |
| 400/401/403 | 客户端错误 | 不重试，直接报错 |

**实现**：
```ts
class RetryPolicy {
  constructor(
    public maxRetries: number,
    public baseDelay: number,
    public maxDelay: number
  ) {}

  async execute<T>(fn: () => Promise<T>): Promise<T> {
    let lastError: Error;
    for (let i = 0; i <= this.maxRetries; i++) {
      try {
        return await fn();
      } catch (err) {
        if (!this.shouldRetry(err) || i === this.maxRetries) throw err;
        lastError = err;
        const delay = Math.min(
          this.baseDelay * 2 ** i + Math.random() * 1000, // jitter
          this.maxDelay
        );
        await sleep(delay);
      }
    }
    throw lastError!;
  }

  private shouldRetry(err: unknown): boolean {
    if (err instanceof APIError) {
      return [429, 500, 502, 503, 504].includes(err.status);
    }
    return false; // 网络错误等也可重试
  }
}
```

### 4.3 死循环检测

**问题**：agent 可能陷入"读文件 → 编辑失败 → 再读文件 → 再失败"的循环。

**检测方法**：
1. **全局迭代上限**：25 轮（Claude Code 基准）
2. **重复动作检测**：滑动窗口（最近 5 轮）内，相同工具+参数哈希出现 ≥3 次 → 触发警告
3. **强制中断**：超上限或检测到循环后，返回特殊 stop_reason，要求模型"换思路或放弃"

**实现**：
```ts
class LoopDetector {
  private history: string[] = []; // 最近 5 轮的动作哈希
  private roundCount = 0;

  check(toolName: string, input: unknown): void {
    this.roundCount++;
    if (this.roundCount > 25) {
      throw new MaxIterationsError('达到最大迭代次数');
    }

    const hash = `${toolName}:${stableHash(input)}`;
    this.history.push(hash);
    if (this.history.length > 5) this.history.shift();

    const count = this.history.filter(h => h === hash).length;
    if (count >= 3) {
      throw new LoopDetectedError(`检测到重复操作: ${toolName}`);
    }
  }
}
```

## 五、强制后置验证

### 5.1 问题

**模型自报"完成"不可信**：22.6% 的失败源于模型说"改完了"，但代码实际不能编译/测试挂了（来源：Claude Code 内部数据）。

### 5.2 方案

**强制验证链**：每次编辑后，agent 必须执行：
1. **编译检查**：`npm run build` / `tsc --noEmit`（根据项目类型自动选择）
2. **测试**：`npm test`（如果有测试）
3. **Lint**：`npm run lint`（可选）

**执行时机**：
- 工具调用 `edit_file` / `write_file` 后，**自动插入验证工具调用**（agent 无法跳过）
- 验证失败 → 回喂错误输出 → 模型必须修复

**实现**：
```ts
async function executeToolWithValidation(
  tool: Tool,
  input: unknown
): Promise<ToolResult> {
  const result = await tool.execute(input);
  
  // 如果是文件修改工具，自动验证
  if (['edit_file', 'write_file'].includes(tool.name)) {
    const validation = await runValidation();
    if (!validation.success) {
      return {
        is_error: true,
        content: `文件已修改，但验证失败：\n${validation.output}\n请修复后重试`
      };
    }
  }
  
  return result;
}
```

## 六、混合流式输出

### 6.1 需求

- **文本内容**：逐 token 流式输出（提升体验）
- **工具调用**：非流式（需完整 JSON 才能解析）
- **Ink 渲染**：流式文本实时更新，工具调用完成后一次性显示

### 6.2 技术方案

**已有基础**（M3.5）：
- `agent.ts` 已实现 `text_delta` 逐 chunk yield
- `ui/app.tsx` 已有流式 reducer（`reduce-agent-event.ts`）

**M4 扩展**：
1. **工具调用开始**：yield `tool_use_start` 事件 → UI 显示 loading spinner
2. **工具执行中**：yield `tool_progress` 事件（如 bash 命令的 stdout）→ UI 实时追加
3. **工具完成**：yield `tool_use_complete` → UI 显示结果（成功/失败样式）

**数据流**：
```
Agent                    UI
  |                      |
  |-- text_delta ------> | 逐字追加到消息
  |-- tool_use_start --> | 显示 "🔧 reading file..."
  |-- tool_progress ---> | 显示 stdout（bash 特有）
  |-- tool_use_complete->| 替换为 "✓ read 123 lines"
  |-- text_delta ------> | 继续文本输出
```

## 八、非功能需求

### 8.1 性能

- **命令解析**：< 1ms（轻量正则，无 AST）
- **fuzzy search**：< 10ms（文件 < 5000 行时）
- **权限检查**：< 5ms（内存规则引擎）

### 8.2 可测试性

- **权限规则**：纯函数，输入命令 → 输出 allow/deny/ask
- **错误恢复**：Mock API 返回特定错误码，验证退避逻辑
- **死循环检测**：构造重复动作序列，验证触发条件

### 8.3 可观测性

- **权限日志**：每次检查记录 `[permission] check: rm -rf /tmp → denied (matched denyRule)`
- **重试日志**：`[retry] attempt 2/3 for API call (429 rate limit)`
- **验证日志**：`[validation] tsc failed: 3 errors`

## 九、技术风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 命令解析遗漏边缘 case（嵌套引号、复杂转义） | 危险命令漏过检查 | 保守策略：解析失败 → 默认标记为 dangerous |
| fuzzy search 性能（超大文件） | 编辑卡顿 | 限制搜索范围（±100 行窗口），超大文件提示用行号模式 |
| yes-always 误用（用户点错） | 危险操作批量通过 | 仅会话内生效，重启清除；deny 规则优先级高于 allow |
| 强制验证拖慢迭代 | 每次编辑多等 2-5 秒 | 可配置跳过（`skipValidation: true`），但默认开启 |
