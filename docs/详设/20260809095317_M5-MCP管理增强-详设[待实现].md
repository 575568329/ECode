## 一、背景与目标

### 1.1 现状缺口

ECode 当前 MCP 子系统（M5 阶段 3 已落地）只解决了「能连、能用」，管理体验存在 **5 个真盲区**：

| 缺口 | 现状 | 后果 |
|------|------|------|
| 🔴 连接无超时 | `loader.ts` 裸 `Promise.all`（claude/opencode 都是 30s `Promise.race`） | 配错的 server 会让**整个 agent 启动卡死** |
| 🔴 `/mcp` 状态不可信 | `app.tsx:300` 显示 `e.enabled?'✓':'✗'`——是 enabled 开关，不是连接结果 | 用户配错的 server 也显示 ✓，无法确认「装对没」 |
| 🔴 失败原因丢失 | `client.ts` `failedConn()` 不带 reason，失败只 `console.warn` | REPL 里看不到为什么连不上 |
| 🔴 无重连/测试手段 | 改配置或 server 崩了只能重启 ECode | 排错成本高 |
| 🔴 Windows 进程残留 | stdio server 断开只 `transport.close()`，不杀进程树（opencode 在 Windows 也漏这步） | npx→node 孙子进程残留（§9 红线） |

### 1.2 目标

引入 **集中式 `McpManager`**，一次性补齐：
- 30s 连接超时（修启动卡死）
- `/mcp` 显示**真实连接状态 + lastError**（超越 claude——它也不显示错误）
- `/mcp reconnect`（重连 = 测试连通，不重启）
- `/mcp add/remove`（命令式登记，免手写 JSON）
- `/mcp info/tools`（详情 + server 作用）
- 跨平台进程树清理（Windows `taskkill /T` / POSIX 进程组）

### 1.3 范围决策（已与 owner 确认）

| 决策 | 结论 | 理由 |
|------|------|------|
| 子命令范围 | **完整集**：list/info/tools/reconnect/add/remove/enable/disable | 一体做比拆两次干净 |
| registry 作用域 | **user-only**（`~/.ecode/mcp/registry.json`） | YAGNI，project 层后置；与现状一致 |
| stdio 自动重连 | **不做**（靠手动 `/mcp reconnect`） | claude 也不做（进程死了复活不如让用户重连） |
| http transport | **不在本次**（仍是远期字段） | ECode 当前 stdio-only，http 自动重连/OAuth/debug 等 http 专属能力后置 |

## 二、对标调研关键结论（claude-code-main + opencode）

| 维度 | claude | opencode | ECode 取舍 |
|------|--------|----------|-----------|
| 连接超时 | 30s `Promise.race` | 30s `withTimeout` | ✅ 抄 30s |
| stdio 自动重连 | 不重连（直接 failed） | 不重连 | ✅ 不做 |
| http 自动重连 | 指数退避 5 次 | 无 | ⏸ http 后置 |
| 状态机 | 5 态（connected/pending/needs-auth/failed/disabled） | 5 态 | ✅ 抄 4 态（无 pending/needs-auth，stdio 用不上） |
| 失败显示 lastError | ❌ 隐式遗漏（有 error 字段但 UI 没读） | ⚠️ CLI list 显示 error | ✅ **超越**：list+info 都显示 |
| `/mcp` UI | 全屏 TUI 5 视图状态机 | 文本 list + sidebar 状态点 | ✅ 文本子命令（ink 单屏滚动范式） |
| `mcp add` | CLI `add`（flag）+ 交互式 | CLI `add`（clack 交互式 + fast path） | ✅ 抄 opencode：fast path + 交互式 |
| `mcp debug` | — | HTTP probe + token 脱敏 | ⏸ http 专属，后置 |
| 进程清理 | SDK close | POSIX pgrep 递归，**Windows 空实现** | ✅ **补 Windows `taskkill /T`** |
| 工具热更新 | `tools/list_changed` 事件 + 按前缀替换 | `ToolListChangedNotification` 订阅 | ⏸ 后置（本次重连即全量重抓） |

### 3.2 McpManager 契约（`src/mcp/manager.ts`）

```ts
/** 单个 server 的运行时状态（/mcp 显示 + agent 工具表的数据源）。 */
export interface McpServerState {
  name: string;
  status: 'connected' | 'failed' | 'disabled' | 'disconnected';
  transport: 'stdio';
  tools: ToolDefinition[];
  prompts: McpPrompt[];
  lastError?: string;          // RCE拦截 / spawn失败 / listTools失败 / 超时
  entry: McpRegistryEntry;     // 原始配置（info/add/remove 用）
}

/** 连接变更回调（use-agent-stream 订阅，用于重注册 prompts 斜杠命令）。 */
type McpChangeListener = () => void;

export class McpManager {
  constructor(opts?: { connectMcpServer?: typeof connectMcpServer; dataDir?: string });

  // 生命周期
  connectAll(): Promise<void>;               // 启动：读 registry → filter(enabled) → 并行 connect
  connect(name: string): Promise<McpServerState>;
  reconnect(name: string): Promise<McpServerState>;  // 断旧→重连（= 测试连通）
  disconnect(name: string): Promise<void>;
  disconnectAll(): Promise<void>;            // 退出清理（含进程树清理）

  // 配置变更（add/remove/enable/disable 写回 registry 后调用）
  reload(): Promise<void>;

  // 查询（/mcp handler + getRunOpts 用）
  getStatus(name?: string): McpServerState | McpServerState[];
  getAllTools(): ToolDefinition[];           // 合并所有 connected server 的工具，喂给 agent
  getAllPrompts(): Array<{ serverName: string; prompt: McpPrompt }>;

  // 订阅（use-agent-stream 注册，变更时重注册 prompts 斜杠命令）
  onChange(listener: McpChangeListener): () => void;  // 返回 unsubscribe
}
```

**核心数据**：`private pool = new Map<string, { connection: McpConnection; state: McpServerState }>()`——所有状态查询的唯一来源，根除「`/mcp` handler 拿不到连接状态」的盲区。

## 四、连接增强（`client.ts`）

### 4.1 30s 连接超时（修启动卡死）

新增 `raceWithTimeout` helper + 常量，`connectMcpServer` 整个流程（connect + listTools + listPrompts）包在一个 30s 超时内：

```ts
const MCP_CONNECT_TIMEOUT_MS = 30_000;  // 对齐 claude/opencode

function raceWithTimeout<T>(p: Promise<T>, ms: number, onTimeout: () => Promise<void>): Promise<T> {
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<T>((_, reject) => {
    timer = setTimeout(() => reject(new Error('MCP_TIMEOUT')), ms);
  });
  return Promise.race([p, timeout])
    .finally(() => timer && clearTimeout(timer))
    .catch(async (e) => {
      if (e instanceof Error && e.message === 'MCP_TIMEOUT') await onTimeout();
      throw e;
    });
}

// connectMcpServer 内：
await raceWithTimeout(
  client.connect(transport),
  MCP_CONNECT_TIMEOUT_MS,
  async () => { await transport.close().catch(() => {}); },  // 超时→清理 transport
);
```

超时 → `failedConn('连接超时(30s)')`。

### 4.2 lastError 链路（超越 claude）

`failedConn()` 改为 `failedConn(reason: string)`，各失败点传具体原因：

| 场景 | lastError |
|------|-----------|
| RCE 白名单拦截 | `命令 "rm" 不在白名单` |
| 非 stdio / disabled | `仅支持 stdio 且 enabled` |
| connect 抛错 | `连接失败: <err.message>` |
| 超时 | `连接超时(30s)` |
| listTools 抛错 | `获取工具失败: <err.message>` |

manager 把 reason 存进 `state.lastError` → `/mcp` list/info 显示。

### 4.3 reconnect（manager 层编排，client.ts 不改连接逻辑）

```ts
async reconnect(name: string): Promise<McpServerState> {
  const old = this.pool.get(name);
  if (old?.connection) await old.connection.disconnect();  // 杀旧（含进程清理）
  const state = await this.connect(name);                   // 重 connectMcpServer（带超时）
  this.pool.set(name, { connection, state });
  this.emitChange();                                        // 通知 use-agent-stream 重注册 prompts
  return state;                                             // connected 或 failed(带 lastError)
}
```

**= 测试连通，不重启 ECode**。失败也返回 state（带 lastError），`/mcp` 显示。

## 五、跨平台进程树清理（`process-cleanup.ts`，§9 红线）

stdio server 断开时杀**整棵进程树**（npx→node 的孙子进程别残留）：

```ts
export async function killProcessTree(child: { pid?: number }): Promise<void> {
  if (!child.pid) return;
  if (process.platform === 'win32') {
    // taskkill /T /PID <pid>：/T 递归杀子进程树
    await spawnAsync('taskkill', ['/T', '/F', '/PID', String(child.pid)]);
  } else {
    // POSIX：进程组 SIGTERM（StdioClientTransport 需 detached:true，kill -pgid）
    try { process.kill(-child.pid, 'SIGTERM'); }
    catch { /* 已退出或非组长，忽略 */ }
  }
}
```

**触发点**：`McpConnection.disconnect()` 内 `transport.close()` 之后补 `killProcessTree`；`disconnectAll`（退出）/ `reconnect` 杀旧时同样。

### 5.1 WSL 考量（§9.3）

| 运行环境 | `process.platform` | 清理分支 |
|---------|-------------------|---------|
| Windows 原生（含 Git Bash） | `'win32'` | `taskkill /T /F /PID` |
| WSL 里跑 ECode | `'linux'` | POSIX 进程组 SIGTERM |
| macOS / Linux 原生 | `'darwin'`/`'linux'` | POSIX 进程组 SIGTERM |

**安全性论证**：`process.platform` 判断成立的前提是「ECode 和它 spawn 的 stdio server 同环境」。该前提成立，因为：
- stdio server 由 SDK `StdioClientTransport` 直接 `spawn(command, args)`，command 跑在 ECode 同环境；
- **RCE 白名单挡住跨边界命令**：`wsl.exe`/`cmd.exe` 不在 19 个白名单 → 用户无法配 `command:"wsl"` 让 Windows ECode 跑 WSL server（避免「taskkill 杀不到 WSL 孙子」的最坑场景）。

> ⚠️ **实现时验证点**：`taskkill /T` 需要子进程 pid，须确认 SDK `StdioClientTransport` 是否暴露 child pid。
> - 若暴露（如 transport 实例的 `_childProcess.pid` 或等价）→ 直接用；
> - 若不暴露 → ECode 自建轻量 stdio transport（自己 `spawn` 拿 pid，包成 SDK `Transport` 接口），备选方案，writing-plans 阶段先验证 SDK 再定。

### 6.4 `/mcp add` 双形态（对齐 opencode）

**fast path（一行，脚本/熟练用户友好）**：
```

```
- `--` 分隔：后为启动命令 + 参数（避免 args 与 flag 歧义）
- `--env KEY=VALUE`：可重复，凭证（解析用 `indexOf('=')`，支持 value 含 `=`）
- `--desc`：可选说明
- transport 默认 stdio

例：
```
/mcp add github --desc "GitHub issue/PR 管理" --env GITHUB_PERSONAL_ACCESS_TOKEN=ghp_xxx -- npx -y @modelcontextprotocol/server-github
```

**交互式（无参 `/mcp add`，新手友好）**：

## 七、数据流与状态同步

### 7.1 接线（`use-agent-stream.ts`）

```ts
const mcpManagerRef = useRef<McpManager | null>(null);

useEffect(() => {
  const manager = new McpManager();
  mcpManagerRef.current = manager;
  manager.onChange(syncPrompts);        // 变更时重注册 prompts 斜杠命令
  void manager.connectAll().then(syncPrompts);
  return () => { void manager.disconnectAll(); };  // 退出清理（含进程树）
}, []);
```

- **工具表实时**：`getRunOpts().tools = [...builtin, ...manager.getAllTools()]`——每轮 agent 调用读 manager，reconnect/add 后**自动反映新工具**（去掉旧 `mcpToolsRef`）。
- **prompts 全量重注册**：`syncPrompts()` 先 `unregisterCommand` 所有旧 mcp prompt 命令，再 `registerCommand` 当前 `manager.getAllPrompts()`（reconnect/add/remove 不频繁，全量重注册简单不出错）。
- **mcpApi 分层**：`use-agent-stream` 返回 `mcpApi`（封装 manager 操作 + 格式化输出文本），`app.tsx` 的 `/mcp` handler 闭包捕获，只管「解析子命令 → 调 mcpApi → addMessage 显示」。

### 7.2 数据流图

```
启动: useEffect → new McpManager → connectAll() → syncPrompts()（注册初始斜杠命令）
每轮 agent: getRunOpts().tools = [...builtin, ...manager.getAllTools()]   ← 实时读
/mcp <cmd>: handler 解析 → mcpApi.<cmd>(args) → manager 操作 → 返回文本 → addMessage
reconnect/add/remove/enable/disable: manager 变更 → emitChange → syncPrompts()（全量重注册）
退出: useEffect cleanup → manager.disconnectAll()（进程树清理）
```

### 7.3 分层职责

| 层 | 职责 | 文件 |
|----|------|------|
| manager | 状态/连接池/生命周期（纯逻辑，可单测） | `mcp/manager.ts` |
| mcpApi | 操作 + 输出文本格式化 | `ui/use-agent-stream.ts`（返回值） |
| handler | 解析子命令 + addMessage 显示 | `ui/app.tsx` |

## 八、错误处理

| 场景 | 处理 |
|------|------|
| 启动时某 server 连接失败 | 标 `failed` + lastError，**不阻塞其他 server 和 agent 启动**（已实现，保留） |
| `/mcp reconnect` 失败 | 返回 failed state（带 lastError），`/mcp` 显示，不抛穿 |
| `/mcp add` 后 connect 失败 | server 已写入 registry（enabled），但状态 failed + lastError；提示用户 `/mcp reconnect` 重试或检查配置 |
| 运行中工具调用断线 | 沿用现有 adapter：返回 `isError` 给模型，不破回合（M5 已实现，保留） |
| 进程清理失败 | `taskkill`/`kill` 抛错 → catch + warn，不影响 disconnect 流程 |
| registry 损坏/非数组 | `loadMcpRegistry` 已降级空数组（保留） |

**原则**：MCP 失败永远不 crash agent，永远把原因回显给用户（lastError）。

## 九、安全

| 红线 | 说明 |
|------|------|
| RCE 白名单不变 | spawn 前仍过 `SAFE_COMMAND_HEADS`（19 个），`taskkill` 是 ECode 自己调（清理用，非 user command），不进白名单校验 |
| env 脱敏 | `/mcp info` 显示 env **必须脱敏**（§9.2）：`KEY = 前4位****`，凭证不透传到 UI |
| description | 用户自填纯文本，无安全顾虑（不作为命令执行） |
| add 不自动跑包管理器 | add 只写 registry + spawn 用户声明的 command（过白名单），不替用户 `npm install`（避免 supply chain） |
| 跨边界 spawn | RCE 白名单挡 `wsl`/`cmd`，避免 Windows↔WSL 跨边界进程树清理难题（§5.1） |
