# ECode 后续 M10 实施方案：感知扩展与配置可视化

> 日期：2026-08-16 · 状态：**设计稿 v1.3（待启动；三次修订——v1.2 多模态扩 PDF+粘贴升 P2+排期盘点；v1.3 扩后台子进程任务（§4，四家一手源码调研证据附录 B）+ 发现 bash 杀进程不杀树的现存缺陷）**
> 主题一句话：让 Agent **看得见图和文档**（多模态输入 ImageBlock+PDF）、**搜得到网**（WebSearch）、**配置不用手编 JSON**（/config 面板）、**长命令不堵路**（后台子进程任务）。
> 来源：2026-08-16 用户排期拍板（多模态要排期 / WebSearch 调研可行 / config 面板可以做但要设计好 TUI）+ 观察区吸走。WebSearch 可行性调研结论：Bing API 已死（2025-08-11 退役）、Anthropic/OpenAI 服务端搜索走不通（Astron 兼容端点）、**智谱 Web Search API 首选**（¥0.01-0.03/次、国内直连、与 GLM 同 key 体系）。

---

## 0. 目标与验收

**目标**：扩展 LLM 的输入通道（图像、全网搜索）+ 配置的可视化修改（不再手编 JSON）。

**验收**：
- **多模态**：`ToolResult` 扩展可选 `blocks` 字段（image block 经 tool_result content 数组回喂——Anthropic 协议原生支持；OpenAI 侧翻译时转移至紧随 user 消息）；`read_file("截图.png")` → 双协议正确翻译 → 模型能描述图片内容；TUI 占位行；压缩序列化不炸；**PDF 同管道**（v1.2 扩入：`read_file("设计稿.pdf")` → document block，模型侧不支持时 is_error 如实回喂）
- **WebSearch**：`web_search("query")` 返回编号列表（标题/URL/摘要/来源/日期）+ Sources 提醒回喂；未配置 key 时工具不注册；1701/1702/1703 错误 recoverable
- **/config 面板**：`/config` 打开三页签面板（搜索模式优先）；常用项可视化改；**未覆盖的键原样保留**（jsonc 非破坏性修改，保注释）；底部永久"打开原始文件"逃生口
- **图片粘贴（P2 可选，v1.2 升级）**：Windows 剪贴板图片 → PowerShell `GetImage` 读取 → 存临时文件 → 注入路径引用；macOS/Linux 后置
- **后台子进程任务（P3，v1.3 扩入）**：bash `run_in_background` 立即返回 task_id，输出落文件；task_output 增量读取 / task_stop 终止；**统一杀树**（Unix 进程组 / Win taskkill /T /F + SIGTERM→200ms→SIGKILL）——顺带修复现存缺陷：bash 超时单点 kill 导致 npm 类孙进程泄漏；完成通知轮末注入

**不做**（后置）：**视频/音频输入**（v1.2 调研确认维持：四家终端 CLI 无一做视频；音频仅 codex 在 app-server 协议层定义且非默认 modality、aider 的 /voice 是 Whisper STT 转文字而非音频直发——终端 Agent 场景无真实需求，触发=用户明确提出）、Tavily 适配（接口位留，等真实需求）、多模态输出（模型生图）、keychain（用户拍板：key 无法被完全保护，优先级极低，维持观察区）。

## 1. 多模态输入 ImageBlock（P0，~3-4 天）

**问题**：用户想让 ECode 看截图/UI 图/报错截图——模型有视觉能力（GLM-4V 系列），ECode 的管道只传文本。types.ts 从 M1 就留了 ImageBlock 占位，本节把血肉写上。

**流程图（一张图从文件到模型）**：

```
用户：「看下这个截图哪里错了 D:\shot.png」
  │
  ▼
LLM 调 read_file("D:\shot.png")
  │
  ├─ 文本文件（现状路径）：读内容 → TextBlock → ……不变
  │
  └─ 图片（按扩展名/Magic Number 判定 png/jpeg/webp/gif）
        │ 守卫：≤5MB / 格式在支持列表（超限 is_error 提示压缩）
        ▼
      ImageBlock { type:'image', source:{ base64, media_type } }
        │
        ├─ TUI 渲染：占位行 [图片 D:\shot.png]（终端显示不了图，诚实占位）
        │
        ├─ Anthropic 翻译（tool_result 的 content 数组原生支持）：
        │     { type:'image', source:{ type:'base64', media_type, data } }
        │
        ├─ OpenAI 翻译（tool 消息不支持 image → 转移至紧随 user 消息）：
        │     content parts { type:'image_url', image_url:{ url:'data:…;base64,…' } }
        │
        └─ 压缩序列化（M5 serializeMessage）：ImageBlock → '[图片 shot.png]'
           （摘要不吞 base64——几十 KB 的编码串进摘要只会污染）
```

**详细讲解**：
- **前置接口扩展（v1.1 调研修订，必做第一步）**：ECode 现行 `ToolResult { content: string }` 装不下图。CC 的正路是把 image block 放进 **tool_result 的 content 数组**（Anthropic 协议原生形态）。扩展：`ToolResult` 加可选 `blocks?: ContentBlock[]`，loop 透传进 `ToolResultBlock`（content 从 string 扩展为 `string | ContentBlock[]`）——口径修正为"接口扩展+透传"（与 M9 onBeforeWrite 同级，非逻辑改动）。**OpenAI 侧差异**：chat.completions 的 tool 消息不支持 image——`toOpenaiMsgs` 把 tool_result 内 image 转移至紧随的 user 消息 content parts（`image_url` data URI）
- **入口只有 read_file 路径引用**（MVP 拍板）：`@文件` 语法、终端粘贴、拖拽后置——CC 的三平台粘贴（osascript/xclip/PowerShell）证明可行但每平台一套，MVP 不付；路径引用零新基建
- **格式判定 magic bytes 优先**（CC `detectImageFormatFromBuffer` 同款）：扩展名只做初筛，读缓冲区前 16 字节判真实格式（扩展名可伪造）
- **限制双维守卫**：单图 ≤5MB（取双端点最严——Anthropic 5MB / GLM 系 10MB）+ **≤8000×8000px**；格式 png/jpeg/webp/gif。**不做客户端缩放**（调研否决 sharp=原生依赖重、photon WASM=非必要复杂度）：Anthropic 服务端自动缩到 1568px、传大图只浪费流量不加细节，守卫拒绝+提示即可；缩放链进观察区（触发=图片 token 成本痛）
- **token 估算**：(w×h)/750（2000×2000 ≈ 5.3k token），计入压缩估算与 /cost
- **模型守卫现实化**（调研修订）：GLM 视觉是独立模型名（`glm-4.6v`，128K 上下文，另有 FlashX 轻量与 **Flash 免费**版；不支持图/文件/视频混输入）——read_file 读图时 current model 非 V 系列 → is_error 提示"用 /model 切换到 glm-4.6v"（models.dev 的视觉标记 + 名称后缀双判定）
- **system prompt 教学**：加一行"read_file 支持图片路径（png/jpeg/webp/gif），用户让你看图/截图时直接读"

### 1.1 PDF 输入（v1.2 扩入，与图片同管道）

**为什么加**：四家 CLI 源码调研（2026-08-16，附录 B）——CC（`document` block 一等公民 + poppler 页渲染兜底）、opencode（`application/pdf` 与图片同走 FilePart 通道）、aider（`pdfs-2024-09-25` beta header + PDF 计入图片扩展名集）**三家都做**，仅 codex 没有。终端场景"读 PDF 设计稿/论文/接口文档"与看截图同级高频；协议层 Anthropic `document` block（base64 source + `application/pdf`）与 image block 完全同构，翻译/压缩/守卫管道复用，增量极小。

- **类型**：`ContentBlock` 加 `DocumentBlock { type:'document', source:{ type:'base64', media_type:'application/pdf', data } }`；判定按扩展名 `.pdf` + `%PDF-` magic bytes（CC 同款校验）
- **守卫差异**：单 PDF ≤32MB / ≤100 页（Anthropic 官方双限）；超出 is_error 提示拆分——**不做页渲染兜底**（CC 的 pdftoppm 路线引入 poppler 外部依赖，MVP 不付，进观察区）
- **模型侧验证关卡（启动后第一件事）**：GLM 系对 PDF 输入的支持未验证（4.6V 官方口径以图为主）——真机验证 glm-4.6v 的 PDF 输入；不支持则 document block 翻译前守卫 is_error 如实回喂"当前模型不支持 PDF 输入"（Anthropic 直连场景仍可用），**不静默降级**
- **压缩序列化**：`'[PDF 文件名]'` 占位（与图片同规矩，base64 不进摘要）
- **OpenAI 侧**：与 image 同款转移至紧随 user 消息（chat.completions content parts 不支持 document——若智谱端点走 openai 协议且有自有 PDF 形态，验证关卡时一并核实）

### 1.2 图片粘贴（P2 可选，v1.2 从"不做"升级）

**为什么升级**：v1.1 以"剪贴板图像协议复杂、每平台一套"后置——调研推翻了"每平台"的成本担忧：opencode 的跨平台剪贴板读取已给出三平台完整实现（macOS osascript / **Windows PowerShell `System.Windows.Forms.Clipboard::GetImage()`** / Linux wl-paste+xclip），每平台一段子进程调用即止，无重依赖。ECode 首发环境正是 Windows/Git Bash，价值直接。

- **触发**：输入框空闲态按 Ctrl+V → 读剪贴板 → 有图 → 存 `~/.ecode/tmp/paste-<ts>.png` → 输入框自动插入路径引用（模型侧走 read_file 既有管道，**零协议改动**）
- **范围**：只做 Windows（首发环境）+ macOS（osascript 一段）；Linux 后置（wl-paste/xclip 探测链最碎）
- **降级**：剪贴板无图 → 不动作（无提示，避免噪音）；读取失败 → warn 一行
- **仍是 P2**：时间盒内做不完就滑入 M11，不阻塞主交付

## 2. WebSearch 工具（P1，~2 天）

**问题**：模型对"最新的库版本/端点行为/新闻"只能猜或靠 web_fetch 碰运气——fetch 需要 URL，不知道 URL 时无路可走。

**流程图（一次搜索的完整路径）**：

```
LLM：需要最新信息 ──► 调用 web_search("vite 8 breaking changes")
  │
  ▼
启动时装配：
  config.webSearch = { provider:'zhipu', apiKey? }
  ├─ 有 apiKey（或 provider baseURL 命中 bigmodel.cn 回退复用）──► 注册 web_search 工具
  └─ 没配 key ──► 工具不注册，零配置不炸（模型不知道有这能力）
  │
  ▼
执行（readonly 免确认）：
  POST open.bigmodel.cn/api/paas/v4/web_search
    { search_engine:'search_pro', search_query, count:5 }
  ├─ 成功 ──► search_result[] → "1. 标题\n   URL\n   摘要" 拼接回喂
  │            （LLM 下一步常自己调 web_fetch 抓最相关那篇全文）
  ├─ 429/限流/网络 ──► recoverable is_error（模型自纠：换个问法/放弃）
  └─ key 无效 ──► 提示配置路径（不重试）
```

**详细讲解**（智谱 HTTP 规格已核实，v1.1）：
- **接口**：`POST https://open.bigmodel.cn/api/paas/v4/web_search`，`Authorization: Bearer <key>`——**与 chat completions 同一把智谱 key**；apiKey 缺省回退规则：当前 provider baseURL 含 `bigmodel.cn` 时复用其 key（智谱用户零额外配置），否则要求显式配 `webSearch.apiKey`
- **engine 默认 `search_std`（¥0.01/次）**，config 可改 pro（¥0.03，多引擎协作空结果率低）/sogou/quark（¥0.05）——成本可控哲学（v1.1 拍板，否决"默认 pro"）
- **工具参数**：`query`（≤70 字符）+ `domain`（映射 search_domain_filter，白名单单域名）+ `recency`（oneDay/oneWeek/oneMonth/oneYear）——CC 的 allowed_domains 证明模型会用好这些旋钮；`count` 固定 10（1-50 上限不暴露，防刷）
- **结果格式化（CC 范式）**：编号列表 `1. 标题\n   URL\n   摘要（500 字截断）\n   来源媒体 · 日期` + 尾注提醒模型"回答时列出 Sources"（生态习惯，方便用户核对）
- **限制**：25s 超时（opencode 同款）；1701 并发上限 / 1702 无引擎 / 1703 无有效数据 → recoverable 回喂（模型可换 engine 重试或放弃）
- **防滥用**：description 写明"优先本地代码/文档，真需要最新线上信息才搜索"
- **成本透明**：工具结果尾部带一行 `(web_search 1 次 ¥0.01)`；/cost 不计（外部 API 非 LLM token）

## 3. /config 应用内面板（P2，~2-3 天）

**问题**：`/config` 现在用 $EDITOR 打开 config.json 手编 JSON——字段名记不住、JSON 语法易错、改完才发现键名拼错。

**TUI 设计约束（用户拍板：设计好界面，避免太长、避免覆盖不全）——两个问题的解法是同一个：分层 + 非破坏性**：

```
/config 打开面板（PanelShell tabs，←→ 切页签）
  │
  ├─ 页签①「常规」：高频项可视化改
  │    当前 Provider（列表选）→ 模型（该 provider 的 models 列表选）
  │    → temperature / maxTokens / thinking（枚举选，不手敲数字）
  │
  └─ 页签②「Providers」：provider 列表 → 只读详情（v1.1 降级：低频且敏感，
       面板代编收益低风险高——对齐 CC 的克制，它 19 项里也没有 provider 编辑）
       展示 baseURL/apiKey(脱敏)/models + 「打开原始文件」引导改
  │
  └─ 页签③「高级」：兜底覆盖，两层设计
       ├─ 已知高级键（mcpServers/webSearch/hooks/plugin 启用态）
       │  → 只读展示 + 回车跳 $EDITOR 定位到该键（引导不代编）
       └─ 底部永久项：「打开原始 config.json」（$EDITOR 逃生口）
  │
  ▼
保存 = jsonc modify 只改目标键（PluginLoader.setEnabled 同款先例）
  ├─ 用户注释原样保留
  ├─ 面板没覆盖的键一个字节不动   ← "覆盖不全"的结构性解药：
  │     面板不需要覆盖所有内容——改常用项，其余键非破坏性保留
  └─ 超长防抖：页签分组 + PanelShell 既有 12 行窗口滚动 + 详情页单键单页
```

**详细讲解**：
- **非破坏性是本节的命根**：面板永远不重写整个 config.json——jsonc-parser 的 `modify(text, path, value)` 只动目标路径（M7 PluginLoader.setEnabled 已在生产用它保注释），未识别键、注释、格式全部原样。所以面板"覆盖不全"不构成数据风险，只构成便利性梯度——高频项点选，低频项 $EDITOR
- **搜索模式优先**（CC 范式吸收）：PanelShell 的即时搜索天然就是 CC 专门写的 SearchBox——设置项多时输入即过滤，新人不用逐页翻
- **交互范式**（CC 吸收）：布尔项 = 回车 toggle（开/关）；枚举项 = 回车进子菜单选（PanelShell 列表）；数值项（temperature/maxTokens）= 枚举档位代替手敲（0/0.2/0.5/0.7/1）
- **即时生效边界**：provider/模型/参数改完即生效（下一轮请求读 config 内存态）；提示"重启生效"的场景=改了 config 文件里的结构（面板保存走落盘+重读）
- **与 CC 的差异化**：CC 无逃生口（first-party 封闭配置 19 项）；ECode config 是 jsonc 全量用户领地（mcpServers/hooks/plugins 全在里面）——**保留逃生口 + 非破坏修改**是覆盖不全的结构性解药，维持原设计

## 4. 后台子进程任务（P3，v1.3 扩入；滑 M11 不阻塞）

**问题**（2026-08-16 四家源码调研后扩入，证据见附录 B）：
1. **长命令阻塞轮次**：npm test / build / dev server / 爬虫脚本动辄分钟级，现有 bash 30s 超时直接杀——模型无法"让它在后台跑，我先干别的"。
2. **现存缺陷（顺带发现）**：bash 超时/中断是**单点 kill**（`child.kill('SIGKILL')` 只杀 bash.exe 自己）——`npm test`/`npm run dev` 起的孙进程全部泄漏成孤儿。四家全部实现进程树杀（CC tree-kill / codex 进程组+kill_on_drop+Win Job Object / opencode taskkill /T/F），ECode 缺。

**四家实现形态**（浓缩，一手证据附录 B）：

| 维度 | CC | codex | opencode | aider |
|---|---|---|---|---|
| 后台任务 | `run_in_background` + TaskOutput(offset 增量)/TaskStop + 15s 自动转后台 + Ctrl+B | Unified Exec：`exec_command` 持久 PTY 会话 + `write_stdin`（上限 64 进程） | BackgroundJob 仅子代理（实验）；shell 无后台 | 无 |
| 输出缓冲 | file mode（stdio 直写文件 fd 零 JS 开销）/ pipe mode 8MB 内存→5GB 磁盘 | HeadTailBuffer 1MiB（头 50%+尾 50% 丢中间） | 滑动窗口+溢出落盘 | 内存无上限 |
| 杀树 | tree-kill SIGKILL（无梯度，反面教材） | 进程组 SIGTERM→50ms→SIGKILL；Linux PDEATHSIG；Win Job Object | Unix `kill(-pid)` SIGTERM→200ms→SIGKILL；Win `taskkill /T /F` | 无 |
| PTY | 不用（管道+文件 fd） | Unified Exec 用 portable-pty（ConPTY） | shell 不用；desktop 用 node-pty | pexpect（非 Win TTY） |

**ECode 方案**（P3，~2-3 天）：
- **bash 加 `run_in_background` 参数**：spawn 时 stdio 直写输出文件（CC file mode 同款，零 JS 开销）`~/.ecode/tmp/task-<id>.log`，立即返回 task_id + 输出文件路径 + 提示用 task_output 读
- **TaskRegistry**：内存 Map（id → { child, outputFile, status, exitCode, startedAt }）+ 会话结束/退出 cleanup 全杀；并发上限 8（codex 64 过宽，MVP 收紧）
- **task_output 工具**：`offset` 增量读（CC getTaskOutputDelta 语义：返回新内容 + newOffset，不加载全文件）+ 可选 `wait_ms` 短等待（等新输出或退出）
- **task_stop 工具**：杀任务（走统一杀树）
- **完成通知**：轮末检查（afterTools 同链）——本轮启动且已结束、模型尚未读过的任务，下轮前注入 user 文本摘要（`[task] #2 npm test 已完成 exit 0`）——与 quality 回喂同通道（M9 偏差②先例：协议禁无主 tool_result，信息性注入走 user 文本）
- **统一杀树（修现存缺陷，独立于后台任务先行）**：Unix `detached:true` + `process.kill(-pid)`；Windows `taskkill /PID <pid> /T /F`（opencode 同款，KISS 不上 Job Object）；梯度 SIGTERM→200ms→SIGKILL（给编译进程清理机会；CC 无梯度直接 SIGKILL 是反面教材）
- **治理**：输出文件随会话 tmp 清理；沙箱 blockedCommands/full-access 黑名单同样适用后台命令；后台任务也过 checkpoint 近修改集兜底（bash 同款）

**不做**（后置观察）：PTY 持久交互会话（codex 路线：ConPTY/交互式命令支持重基建；ECode "bash 不支持交互命令"的心智不变）、shell snapshot（CC/codex 的 rc 快照——ECode 是 Git Bash `-c` 每命令新进程（opencode 同款参数注入），Windows 环境 rc 定制价值低）、auto-background 15s / Ctrl+B 手动转后台（运营级特性）、Job Object / PDEATHSIG 硬防护（M12+ 按需——taskkill /T /F 已覆盖主场景）。
