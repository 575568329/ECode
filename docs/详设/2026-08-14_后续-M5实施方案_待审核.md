# ECode 后续 M5 实施方案：上下文压缩

> **演进**：v1 三特性打包（压缩+Skill+MCP）→ v2 经三角色审阅拆分（压缩聚焦 + 手动优先）→ **v3 用户定：自动压缩也必做**（手动 + 自动双触发）。

> - M6 = Skill（后置）/ M7 = MCP（后置）

## 1. 目标 & 验收

**目标**：ECode 长对话不因上下文超限崩溃——自动阈值触发压缩 + 手动 /compact + 400 错误捕获三道防线。

**验收标准**：
- **自动**：对话 token 接近 contextWindow 时（阈值 = `contextWindow − max(maxOutput,20000) − 13000`）自动压缩，不中断，UI 反映压缩后状态
- **手动**：`/compact` 主动压缩，messages 替换 + committed 重建
- **400 捕获**：context-too-long 不再退避重试，走压缩或提示
- **摘要质量**：压缩后 LLM 仍能引用压缩前的关键上下文（文件路径、已做决定）
- **持久化**：压缩后 /history restore 拿到压缩态（非全量旧历史）

**不做**（后置）：
- 多级管线（microcompact 折叠工具结果 / snipCompact 删整段 / reactive 捕获）—— MVP 用 aider 全量递归 summarize
- Skill（M6）、MCP（M7）

---

## 2. 三道防线

```
对话累积 → 每轮 provider.run 前 estimateTokens 判定
   │
   ├─ 未超阈值 → 正常请求
   │
   ├─ 超阈值（自动触发）→ compactMessages → 原地替换 messages → continue 重试本轮
   │
   └─ 请求返回 400 context-too-long（兜底）→ 错误码专属分支 → compactMessages → continue
                                          └─ 压缩次数超上限 → onWarn 提示 /clear + break

手动：/compact 命令 → compactMessages → 原地替换 + committed 重建
```

自动阈值是**预防性**（请求前判定，避免发出必失败的请求）；400 捕获是**兜底**（估算误差/阈值不准时救场）；手动是**用户掌控**。

## 3. 前置：修 errors.ts 的 400 context-too-long 误重试（P0）

**现状 bug**（审阅核实）：`fromHttpStatus` 对 400 无专门分支 → 落兜底 `HTTP_ERROR / recoverable:true` → loop 对所有 recoverable 退避重试 → **context 超限被无意义重试 3 次**。

**关键发现**：`retryable` 字段是**只写不读的死字段**（errors.ts 设了，loop.ts 从不读）。

**修订**（开发建议）：**不走 retryable 信号**，改**错误码专属分支**：
```ts
// errors.ts：400 防御性取 body（各 SDK 字段不同：e.error?.error?.message ?? e.error?.message ?? e.message）
if (status === 400) {
  const body = e.error?.error?.message ?? e.error?.message ?? e.message
  if (/context|too long|prompt/i.test(body)) {
    return { code: 'CONTEXT_TOO_LONG', recoverable: true, retryable: false, message, context: { status, body } }
  }
}
```
loop.ts recoverable 分支按错误码分流（§6.2）。

## 4. token 计数（M5-D2，增量缓存）

新 `src/services/tokenizer.ts`：
```ts
import { encode } from 'gpt-tokenizer'

/**
 * 增量 token 计数器（P0-4：避免每轮全量重编码 100k+ tokens 的性能陷阱）。
 * 记住上次编码到哪条 message，只对新消息增量编码，累加到缓存。
 */
export class TokenCounter {
  private cached = 0
  private lastEncoded = 0  // 已编码的 messages 长度

  /** 估算 system + messages 的 token 数；messages 增长时增量编码新部分 */
  count(system: string, messages: Message[]): number {
    // system 每次重算（通常短且可能变）
    const sysTokens = encode(system).length
    // messages 增量：只编码 lastEncoded 之后的新消息
    // 注意：压缩/清空后 messages 可能变短 → 重置
    if (messages.length < this.lastEncoded) {
      // messages 被压缩/截断 → 全量重算
      this.cached = countMessages(messages)
      this.lastEncoded = messages.length
    } else {
      for (let i = this.lastEncoded; i < messages.length; i++) {
        this.cached += countMessage(messages[i])
      }
      this.lastEncoded = messages.length
    }
    return sysTokens + this.cached
  }

  /** 压缩/清空后调，重置缓存（compactMessages 替换 messages 后） */
  reset() { this.cached = 0; this.lastEncoded = 0 }
}

function countMessage(m: Message): number {
  return m.content.reduce((n, b) => {
    if (b.type === 'text') return n + encode((b as TextBlock).text).length
    if (b.type === 'tool_use') return n + encode(JSON.stringify((b as ToolUseBlock).input)).length + 20
    if (b.type === 'tool_result') return n + encode((b as ToolResultBlock).content).length + 10
    return n
  }, 0)
}
```

> gpt-tokenizer 对 GLM/DeepSeek 是**估算**（各家 tokenizer 不同），但 buffer 留足（13000），误差可接受。精确 tokenizer 后置（各 provider 提供时换）。
> **TokenCounter 抽象成接口**（架构师建议 P2）：未来换各 provider 精确 tokenizer 时，loop 调用点不改。

## 6. 压缩算法 + loop 集成

### 6.1 compactMessages（aider 递归，M5-D1）

新 `src/services/compact.ts`：
```ts
export interface CompactResult {
  messages: Message[]
  removedCount: number
  summaryTokens: number
}

/**
 * aider 递归 split-summarize：
 *   1. 按 halfMax 切 head（旧）+ tail（新）
 *   2. summarize(head) → 独立 LLM 调用（强制无工具，maxTokens=1024）
 *   3. 返回 [summary_msg, ...tail]
 *   4. 仍超 → 递归；深度 > 3 退化 summarize_all
 *
 * 摘要失败不重试（M5-D7），降级硬截断（保留最近 N 条 + 「历史已截断」提示）。
 */
export async function compactMessages(
  messages: Message[],
  opts: { provider: LLMProvider; providerReq: ProviderReq },
): Promise<CompactResult>
```

摘要 prompt（参考 claude-code + aider）：强调保留文件路径/决策/未完成事项，`<analysis>` 分析 + `<summary>` 摘要，strip analysis。

### 6.2 loop.ts 集成（P0 修订 + onBeforeRequest hook）

**架构师建议**：压缩判定抽成 hook（`onBeforeRequest`），loop 主流程只留一行，为多级管线留位。

LoopRunOptions 加：
```ts
/** provider.run 前的预处理 hook（M5：压缩判定；未来：多级管线）。返回处理后的 messages 或原样 */
onBeforeRequest?: (messages: Message[]) => Promise<{ messages: Message[]; compacted: boolean }>
```

loop 每轮 provider.run 前：
```ts
for (let iter = 1; ...; iter++) {
  // M5：provider.run 前预处理（自动阈值压缩）
  if (opts.onBeforeRequest) {
    const { messages: newMsgs, compacted } = await opts.onBeforeRequest(messages)
    if (compacted) {
      // P0-1 修订：原地 mutate（TuiApp/cli 靠 messagesRef mutation，不捕获 runLoop 返回值）
      messages.length = 0
      messages.push(...newMsgs)
      opts.callbacks.onCompacted?.(messages)  // P1-1：通知 UI 重建 committed
    }
  }
  // ... 原有 provider.run ...
```

**onBeforeRequest 实现**（cli/makeDeps 注入，含 TokenCounter + 阈值判定）：
```ts
const tokenCounter = new TokenCounter()
onBeforeRequest: async (messages) => {
  const tokens = tokenCounter.count(system, messages)
  const ctx = providerReq.contextWindow ?? DEFAULT_CONTEXT_WINDOW
  const threshold = ctx - Math.max(providerReq.maxTokens ?? 8192, 20000) - 13000
  if (tokens <= threshold) return { messages, compacted: false }
  if (++compactCount > MAX_COMPACTS) {  // P1-8：上限防退化循环
    onWarn('上下文已无法进一步压缩，建议 /clear 或 /history 起新会话')
    return { messages, compacted: false }
  }
  const r = await compactMessages(messages, { provider, providerReq })
  tokenCounter.reset()  // 压缩后重置计数缓存
  onWarn(`已自动压缩（移除 ${r.removedCount} 条）`)
  return { messages: r.messages, compacted: true }
}
```

**400 兜底分支**（loop recoverable 内，错误码专属）：
```ts
if (streamError.code === 'CONTEXT_TOO_LONG') {
  if (pushedThisRound) messages.pop()  // 回滚半截（P1-9 已修）
  if (++compactCount > MAX_COMPACTS) { onWarn('建议 /clear'); break }
  const r = await compactMessages(messages, { provider: opts.provider, providerReq: opts.providerReq })
  messages.length = 0; messages.push(...r.messages)  // 原地 mutate
  opts.callbacks.onCompacted?.(messages)
  continue  // 压缩后重试
}
```

LoopCallbacks 加 `onCompacted?: (newMessages: Message[]) => void`。

### 6.3 /compact 命令（手动）

CommandRegistry action 扩 `'compact'` + 注册 /compact。TuiApp onCommand 加分支 → compactMessages → **原地 mutate** + setCommitted(messagesToCommitted) + tokenCounter.reset()。

## 7. 压缩持久化（history boundary，P0 修订）

**问题**：HistoryStore append-only，压缩替换内存后磁盘仍是全量 → restore 拿回未压缩 → 白压。

**方案**（开发建议方案 3，最小破坏 append-only）：
- 压缩时：append `{compact_boundary: true, summary, keptCount}` 标记行 + summary 消息
- `restore()` 遇到 boundary 行：丢弃之前的所有消息，从 summary 继续

HistoryStore 加 `appendCompactBoundary(summary, keptCount)`，restore 读到 `{compact_boundary:true}` 清空累积 + push summary_msg。

### 单测
| 模块 | 场景 |
|---|---|
| errors | 400 context-too-long → CONTEXT_TOO_LONG / 各端点 body 文案 / 非 context 400 不误判 |

- /compact：MockProvider → compactMessages → messagesRef **原地替换**（断言引用不变+内容替换）+ committed 重建

## 11. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 压缩动心脏（onBeforeRequest hook + recoverable 分支）| 中 | hook 是单行注入，recoverable 只加错误码分支不改原有重试；集成测覆盖 |
| token 估算误差（gpt-tokenizer 对 GLM）| 中 | buffer 13000 兜底；contextWindow 可配；400 捕获是第二防线 |
| TokenCounter 每轮计数开销 | 低 | 增量缓存（仅新消息编码），避免全量重编码 |
| 摘要丢关键上下文 | 中 | prompt 强调保留路径/决策；验收含摘要质量 |
| history boundary 破坏 append-only | 低 | 方案 3 只 append 不改写 |
| 摘要 LLM 失败 | 低 | D7 降级硬截断 |
