# 上下文压缩调研报告

> 2026-08-14，为 M5 压缩算法设计做网上调研。聚焦「编码 Agent 的上下文压缩最新实践」，不凭记忆。
> 核心问题：多级压缩（工具内容 / 对话）+ context 与 history 分离（压缩不破坏对话历史）。

---

## 一、Claude 官方 Context Engineering 三原语（最权威）

来源：[Claude Platform Cookbook — Context Engineering: Memory, Compaction, and Tool Clearing](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)

Anthropic 把上下文管理抽象为三个正交原语，针对不同痛点分层组合：

### 1. Tool-Result Clearing（工具输出清理）— 对应「闲时压缩工具内容」
- **思想**：tool_use（调用记录）保留，但庞大的 tool_result（返回内容）用占位符替代。模型知道「我执行过这个操作」，需要具体数据时重新调用工具。
- **适用**：可低成本重新获取的数据（本地文件读、无害 API 查询）。bash 输出 30KB、read_file 大文件是典型大户。
- **API 参数**（`clear_tool_uses_20250919`，服务端原生）：
  - `trigger`：触发清理的 token 阈值（如 30000）
  - `keep`：保留最近 N 次工具调用的完整结果（如最近 4 次）
  - `clear_at_least`：每次至少释放的 token 数（**避免高频微量清理打断 prompt cache**——缓存雪崩）
  - `exclude_tools`：排除特定工具（如记忆工具，防刚写入的索引被清）
- **效果**：100 轮网页搜索评估中，token 消耗降 **84%**，保留对话核心。

### 2. Compaction（对话压缩）— 对应「主动压缩对话内容」
- **思想**：对窗口内**所有内容**（user 指令、assistant 思考、工具调用与结果）做高保真摘要，用浓缩总结替代历史细节。
- **适用**：无法重新获取的隐性上下文（推理过程、已做决定）的最后防线。
- **触发**：服务端达 token 阈值自动触发，生成 summary block，下一轮丢弃该 block 之前的所有历史。
- **Prompt 策略**（关键）：默认保留「状态、下一步、学习成果」；**编码 Agent 必须显式覆盖**——「Focus on preserving code snippets, variable names, and technical decisions」。要保留特定细节（报错栈、重试次数）必须在 prompt 里明说。

### 3. Memory（持久记忆系统）
- **思想**：结构化外部记事本，模型自己决定何时存取，跨会话持久。
- **实现**：客户端文件系统（API 只给协议）。System Prompt 强制「ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE」。
- **双轨**（claude-code 实战）：用户定义记忆（CLAUDE.md，硬编码规范）+ 模型自动记忆（调试中总结的坑/偏好）。

### 三原语的关系：分层组合，非互斥
```
Tool Clearing（低阈值 ~30K）→ 先解决体量最大的工具输出
Compaction（高阈值 ~150K）→ 再压缩推理记录
Memory（跨会话）→ 稳定信息外置于对话窗口
```

## 二、claude-code 的阈值演进（实战教训）

来源：[Hyperdev — How Claude Code Got Better by Protecting More Context](https://hyperdev.matsuoka.com/p/how-claude-code-got-better-by-protecting)

| | 旧策略 | 新策略 |
|---|---|---|
| 触发阈值 | 90-95%（常因空间不足失败）| **64-75%**（200k 窗口 150k 触发）|
| 缓冲 | 极限压榨 | 留 25%（约 50k）空闲 |
| 哲学 | 最大化利用率 | **land the plane before resetting**（让当前任务先优雅完成再压缩）|

**核心洞察**：「free context space」不是浪费，是模型思考 + 完成当前任务的跑道。提早停止（留缓冲）反而**维持一致质量**，比极限压榨更可靠。

**对 ECode 的启示**：buffer 不能只 13000（v3 的值），应按 contextWindow 比例留（如 25%）。GLM 128k → 触发阈值约 96k，留 32k 缓冲。

## 四、对 ECode M5 的核心启示

### 启示 1：Context 与 History 必须分离（用户核心要求 ✓）
- **Claude 的做法**：Message List 是完整记录，靠「就地编辑」（clear/compact）动态管理——没有分离的 history。
- **ECode 应做得更稳**（用户要求）：**history 文件完整 append-only 永不压缩**（对话历史是用户数据，要保存好）；**只压缩 runtime context**（喂 LLM 的 messages）。
- **模型**：
  ```
  History（~/.ecode/sessions/*.jsonl）   Context（runtime messages[]）
  完整对话记录，append-only，永不压缩  →  派生 →  喂 provider.run，可压缩
  /history 恢复拿完整历史              ←  续写  ←  压缩只改 context，不动 history 文件
  ```
- **压缩产物不落 history**（v3 的 boundary 方案废弃）：压缩是 runtime 优化，history 始终完整。/history restore 恢复完整历史到 context（重置压缩态——可接受，恢复是新会话）。

### 启示 2：多级压缩（用户说的「很多层」）
ECode M5 做两级（对应 Claude 三原语的前两个，Memory 由 history 承担）：
- **Level 1 Tool Clearing**（闲时 / 低阈值）：tool_result 占位符化，保留 tool_use。低阈值触发（context ~50%）。
- **Level 2 Compaction**（主动 / 高阈值）：summarize 旧消息。高阈值触发（context ~75%）。

### 启示 3：阈值留缓冲（land the plane）
- 不极限压榨。按 contextWindow 比例留缓冲（25%）。
- GLM 128k：Compaction 触发 ~96k，留 32k 缓冲。
- Tool Clearing 更早（~64k，工具输出是大户）。

### 启示 4：摘要 Prompt 策略
- 编码 Agent 必须**显式覆盖**默认摘要 prompt。
- ECode 摘要 prompt：「保留代码片段、变量名、文件路径、技术决策、未完成事项；省略寒暄和重复」。

### 启示 5：clear_at_least 避免缓存雪崩
- 清理要「划算」（一次清够多），避免高频微量清理打断 prompt cache。ECode 暂无 prompt cache（GLM 端点），但概念预留。

## 六、补充调研：context window 获取 + token 计数（★ 修正 v4 硬编码错误）

> 本节是二次调研（应「GLM-5.2 是 1M，调研怎么拿准确数据」要求），修正 v4 凭记忆写的 128k。

### 6.1 GLM 真实窗口（★ 纠正 v4/v5 的 1M 错误）

| 模型 | context window | 来源 |
|---|---|---|
| **GLM-5 / 5.1** | **200K**（训练期渐进扩展 32K→128K→200K）| [z.ai/blog/glm-5 官方](https://z.ai/blog/glm-5) |
| GLM-4.6 | 200K（从 128K 扩展）| [docs.z.ai/glm-4.6](https://docs.z.ai/guides/llm/glm-4.6) |
| GLM-4.6V | 128K | 智谱官方 |

**重要纠正**：v4/v5 写的「GLM-5=1M」是**错的**——早期搜索结果混淆（1M 是其他长上下文模型）。GLM-5 官方是 200K。但「不能硬编码」原则不变（模型会变,如 GLM-5 训练期就在扩展）。

### 6.2 context window 怎么拿（★ 不能硬编码，调研 4 家 + D:\study 源码）

**核心发现**：主流 API 的 `/models` 端点**都不标准暴露 context window**（[OpenAI 社区讨论](https://community.openai.com/t/request-for-context-total-parameter-under-usage/838272)、[llm-context-limits](https://github.com/taylorwilsdon/llm-context-limits)、[r/LocalLLaMA 讨论](https://www.reddit.com/r/LocalLLaMA/comments/1iq7yea/)）。需查表或探测。

**四家做法（D:\study 源码级）**：

| 项目 | 方式 | 缓存 | 代码位置 |
|---|---|---|---|
| claude-code | 硬编码 200k + 名称匹配（`[1m]` 后缀/`claude-sonnet-4`）；/models API **仅 ant 内部用户** | — | `src/utils/context.ts` `getContextWindowForModel` L51-98 |
| **codex** | 后端 `/models` API 动态拉取（最动态）；effective = window × 90% | 300s | `protocol/src/openai_models.rs` L374-479 + `models-manager/src/manager.rs` |
| opencode | models.dev 社区库（`models.opencode.ai/api.json`）；构建期快照兜底 | 5min（后台 60min 刷） | `packages/core/src/models-dev.ts` |
| aider | litellm JSON 库（`model_prices_and_context_window.json`）+ OpenRouter 爬取兜底 | 24h | `aider/models.py` `ModelInfoManager` L161-323 |

**★ 关键：内置查表会过时**——模型更新/新模型涌现，写死的表很快失效（GLM-6 出来、某模型扩窗）。正确做法是**远程社区库自动跟进 + 缓存 + 离线兜底**。

**★ 选型：models.dev（抄 opencode，而非 litellm）**

调研确认两者都收录智谱，但 models.dev 更适合 ECode：

| 维度 | models.dev | litellm |
|---|---|---|
| 维护方 | **opencode 团队，自家产品在用**（吃狗粮，维护上心）| BerriAI，模型库是副产品（主业 proxy/路由）|
| GLM 覆盖 | ✅ [models.dev/labs/zhipuai](https://models.dev/labs/zhipuai) 收录 GLM-5/GLM-5-Turbo/GLM-4.6 | ✅ 收录 glm-4.5/4.6/4.7/5/5-code |
| 同栈参考 | **opencode 是 TS，`models-dev.ts` 集成代码 ECode 可直接参考**（schema/缓存/fallback 现成）| Python 生态，ECode 只能裸拉 JSON |
| 聚焦度 | **专门做模型数据库**（75+ provider）| 模型库是副产物 |
| 数据源 URL | `models.opencode.ai/api.json`（Flag 可切 models.dev）| `model_prices_and_context_window.json` |

**models.dev schema**（opencode 源码 `packages/schema/src/models-dev.ts` L87-89）：
```ts
limit: { context: number, output: number }  // context window 在 limit.context
```

**opencode 集成模式**（`packages/core/src/models-dev.ts`，ECode 可直接借鉴）：
- URL: `https://models.opencode.ai/api.json`
- 缓存: **5min TTL**（`Duration.minutes(5)`），路径 cache/models.json
- 离线兜底: 构建期 `OPENCODE_MODELS_DEV` 快照（`typeof !== "undefined"` 判断）
- 跨进程锁: Flock（防多 CLI 并发刷缓存）
- 超时: **10s**（`Effect.timeout`）
- 原子写: tempfile + rename
- 重试: 2 次指数退避

**ECode 四级 fallback**（★ v7，抄 opencode）：
```
config.contextWindow 手动覆盖（escape hatch）
  >  models.dev 远程库（5min 缓存 + 构建期快照离线兜底）  ← 自动跟进新模型
  >  内置最小表（GLM-5=200K 等高频，应急）
  >  安全默认 32k + 告警
```
- **models.dev 远程为主**：拉 `models.opencode.ai/api.json`，缓存 `~/.ecode/cache/models.json`（抄 opencode 5min TTL + 原子写 + Flock）
- **离线兜底**：构建期打包 models.dev 快照（抄 opencode `OPENCODE_MODELS_DEV`）+ 内置最小表（GLM-5=200K 等高频）
- **config 覆盖** escape hatch（最高优先）
- **effective = raw × 90%**（抄 codex，留 headroom）

### 6.3 token 计数（★ 不装 tokenizer，颠覆 v4 的 gpt-tokenizer 方案）

**四家实际做法（D:\study 源码级）**：

| 项目 | 方案 | 真实 tokenizer？ | 代码 |
|---|---|---|---|
| **claude-code** | **API usage 锚定 + chars/4 增量估算** | 否 | `tokens.ts` `tokenCountWithEstimation` L226-261；JSON 用 chars/2，图片 ~2000 |
| codex | API TokenUsage + `len/常量` 估算 | 否 | `session/mod.rs` L1264 + `realtime_context.rs` L574 |
| opencode | `round(len/4)` | 否 | `util/token.ts` L5 |
| aider | `litellm.token_counter(model, messages)` | **是**（按 model 选 tiktoken/anthropic） | `models.py` L647-670 |

**关键结论**：**除 aider 外，三家都不用真实 tokenizer**。claude-code 的 `tokenCountWithEstimation` 是典范——**锚定最后一次 API 响应的精确 usage**（input+output+cache），只对之后的新增量用 chars/4 粗估。这避免了：
- 装重依赖（gpt-tokenizer ~1MB，且对 GLM 也是估算）
- 各模型 tokenizer 不同（tiktoken 只准 OpenAI）

**ECode 应**（修正 v4）：
- **不装 gpt-tokenizer**
- 主路径：**API usage 锚定 + chars/4 增量估算**（抄 claude-code）
  - 每轮 provider.run 后，从 Delta.usage 更新精确基准（input_tokens）
  - 新消息用 chars/4（JSON/代码 chars/2，图片固定 ~2000）增量累加
  - 压缩/clearing 后重置基准（下次 usage 回来重新锚定）
- 零新依赖 + 零估算模型差异 + 足够准（有 usage 锚点防漂移）

### 6.4 阈值用绝对值（★ 修正 v4 的百分比方案）

window 差 10 倍（32k vs 1M），**百分比让小窗口过早压缩、大窗口太晚**。

| 项目 | 阈值公式 | 代码 |
|---|---|---|
| claude-code | `window - min(maxOutput, 20k) - 13k buffer` | `autoCompact.ts` L72-91 |
| codex | `window × 90%`（effective） | `openai_models.rs` L468-479 |
| opencode | `context - max(output, 20k buffer)` | `compaction.ts` L225-236 |
| aider | `max_input_tokens × 0.7`（reactive 报警） | `base_coder.py` L1646 |

**ECode 应**：
```
effectiveWindow = contextWindow × 0.9  （留 10% headroom 给 system+tools+output）
Level 1 Tool Clearing 触发 = effectiveWindow - 30k  （工具输出大户，早清）
Level 2 Compaction 触发 = effectiveWindow - 20k  （留 buffer land the plane）
buffer = 20k（抄 claude-code/opencode）
```
绝对值派生自真实 contextWindow（GLM-5=1M → effective 900k → Level 2 触发 880k）。

## 五、ECode M5 压缩架构方向（基于调研修正）

```
┌─────────────────────────────────────────────────────────┐
│ History（永不压缩）                                       │
│ ~/.ecode/sessions/<id>.jsonl — append-only 完整对话记录   │
│ /history 恢复 / 审计 / 导出 — 用户数据，保存好            │
└─────────────────────────────────────────────────────────┘
                         │ 派生（restore / 新对话）
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Context（runtime messages[]，可压缩，喂 provider.run）    │
│                                                          │
│  每轮 provider.run 前 TokenCounter 判定：                │
│   ├─ > 50% contextWindow → Level 1 Tool Clearing         │
│   │   （tool_result 占位符化，保留 tool_use + 最近 N 次） │
│   ├─ > 75% contextWindow → Level 2 Compaction            │
│   │   （summarize 旧消息 → [summary, ...tail]）          │
│   └─ 400 context-too-long → 兜底 Compaction              │
│                                                          │
│  手动：/compact → Level 2                                │
└─────────────────────────────────────────────────────────┘
```

**与 v3 的关键差异**：
1. ~~history boundary~~ → **history 不动**（完整保存，压缩只影响 context）
2. ~~单级 compaction~~ → **两级**（Tool Clearing + Compaction）
3. ~~buffer 13000 固定~~ → **按 contextWindow 比例**（25% 缓冲）
4. 摘要 prompt 显式保留代码/路径/决策
